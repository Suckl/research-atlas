2. Roofline：带宽受限还是算力受限

一个算子的算术强度 = FLOPs / 搬运字节数。GPU 的 Roofline 是：

$$\text{可达 FLOP/s} = \min\big(\text{峰值算力},\ \text{带宽}\times\text{算术强度}\big),\qquad \text{脊点} = \frac{\text{峰值算力}}{\text{带宽}}$$

H100 SXM：989 TFLOPS（BF16 稠密）/ 3.35 TB/s ≈ 295 FLOP/byte。也就是说，每从 HBM 搬 1 个字节，至少要做约 300 次乘加才能把算力用满。

  • Decode，batch = 1：每读 2 字节（一个 BF16 权重）只做 2 FLOP → 强度 ≈ 1，离脊点差两个数量级。GPU 99% 的时间在等内存。
  • Decode，batch = B：权重读一次、算 B 个 token，强度 ≈ B。要到脊点需要 B ≈ 300——但 KV cache 的读取也随 B 线性增长，长上下文时 KV 读取反而成为主项。
  • Prefill：强度 ≈ S（prompt 长度），几百 token 即进入算力受限区。

3. KV cache：多大、什么形状

每层每个 token 要缓存 K 和 V 各 \(n_{kv}\times d_h\) 个数（MLA 例外，缓存的是一个压缩潜向量）：

$$\text{KV bytes / token} = 2\times L\times n_{kv}\times d_h\times \text{bytes}\qquad\text{（MLA：}L\times(d_c + d_r)\times\text{bytes）}$$
模型注意力层数 L每层缓存每 token（BF16）128K 上下文
OPT-13BMHA（40 头 ×128）402 × 40 × 128800 KB105 GB
Llama-3-70BGQA（8 KV 头 ×128）802 × 8 × 128320 KB42 GB
DeepSeek-V3MLA（d_c 512 + RoPE 64）61576≈70 KB≈9.2 GB

OPT-13B 的 800 KB 是 vLLM 论文给出的数字（2 × 5120 × 40 × 2 字节）；其余按公式计算。

三个推论：

  1. 显存里装得下多少请求由 KV 决定，而不是权重：80 GB 的 H100 放下 70B 模型的 BF16 权重后剩不到 1 GB——所以 70B 推理至少要 2 卡张量并行，剩余显存才够放 KV。
  2. decode 每步要读多少字节也由 KV 决定：B 个请求、平均长度 S，每步读 B·S·(KV/token)。这是长上下文、大 batch 时的瓶颈。
  3. PD 分离要传多少字节同样是这个数：一条 S token 的请求要把 S × (KV/token) 搬到解码节点（见 PD 分离 Q16）。

4. 批处理与调度的基本矛盾

指标含义谁在乎被什么决定
TTFT首 token 延迟（≈ prefill 时间 + 排队）交互式用户prompt 长度、算力、是否被别人的 prefill 排队
TPOT / TBT每输出 token 的时间流式阅读体验一步 decode 的时间 = 读权重 + 读 KV + 同批请求数
吞吐每秒处理的 token / 请求数成本batch 大小、显存里能放多少 KV
Goodput满足 SLO 的吞吐服务提供方以上全部 + 调度

连续批处理（continuous / iteration-level batching，Orca 提出）：每一步 decode 都重新组批，新请求随时加入、完成的请求随时退出，不必等整批结束。它把 batch 维持在高位，但也带来新问题——一个长 prompt 的 prefill 插进来会把同批所有 decode 请求的 TPOT 拖长（DistServe 称为 prefill-decode 干扰），于是有了 chunked prefill（把 prefill 切块混进 decode 步）和 PD 分离两条路。

6. 简答题

Q1为什么 prefill 是算力受限、decode 是带宽受限？用算术强度说明 batch 大小如何改变 decode 的瓶颈。

因为两者每读一次权重所做的计算量差了 S 倍。prefill 把 S 个 token 一起送入，权重读一次做 ≈2·P·S FLOPs，算术强度 ≈ S，几百 token 就越过脊点进入算力受限区；decode 每步只有 1 个新 token，权重与全部 KV 都要读一遍却只做 ≈2·P FLOPs，强度 ≈ 1，GPU 绝大部分时间在等 HBM。

  • batch 为 B 时，权重读一次服务 B 个 token，强度 ≈ B；H100 的脊点约 295 FLOP/B，所以 B 要接近 300 才能用满算力。
  • 但 KV 的读取量随 B·S 线性增长：长上下文、大 batch 时 KV 读取超过权重读取，强度又掉回去——这是长上下文解码的瓶颈，也是 MLA / 稀疏注意力 / FP8 KV 要解决的问题。
  • 推论：对 decode 有效的优化要么增大“每次读权重所算的 token 数”（大 batch、投机解码），要么减少“每 token 要读的字节”（量化、MLA、稀疏）。

依据：本页 §1–2 与 Roofline 模型；H100 数字为厂商峰值规格。

Q2给定模型配置，一条 S 个 token 的请求的 KV cache 有多大？这个数字如何同时决定能装多少请求、decode 每步读多少、PD 分离要传多少？

每 token 的 KV 字节 = 2 × 层数 × KV 头数 × 头维 × 字节数（MLA 为 层数 × (d_c + d_r) × 字节数），一条请求再乘以 S。OPT-13B 是 800 KB/token，Llama-3-70B（GQA）320 KB，DeepSeek-V3（MLA）约 70 KB。

  • 容量：显存减去权重后能放多少 token 的 KV，直接决定并发请求数与 batch 上限。
  • 带宽：decode 每步读 B·S·(KV/token) 字节，长上下文时这是每步耗时的主项。
  • 传输：PD 分离要把 S·(KV/token) 从 prefill 卡搬到 decode 卡，DistServe 的例子是 OPT-66B、512 token ≈ 1.13 GB。
  • 减小每 token 的 KV（GQA、MLA、FP8）是同时改善三者的杠杆；详见 PD 分离 Q16。

依据：本页 §3；vLLM 论文 §2（800 KB）；DistServe §4.2。

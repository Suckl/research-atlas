1. 动机：KV cache 从“临时变量”变成“数据”

vLLM 与 SGLang 让 KV 在 GPU 显存里按块管理、按前缀复用。但多轮对话、RAG、代码智能体的上下文越来越长、复用越来越多：一个编码智能体的前缀可达 40 万 token、每轮只增加约 4K（Kimi K3 报告 §5.4.3 的典型值）。值得保留的 KV 远超显存，被淘汰后只能重算长 prompt。LMCache 的使用数据：存储的 KV 远超 GPU 显存且持续增长，超过 19% 的用户平均把存下来的 token 复用 1.5 次以上。LMCache §2.2

一句话理解 把 KV 当作要分层存储的数据：GPU 显存 → CPU 内存 → 本地 SSD → 远端存储，像 CPU 缓存层次一样做命中、预取、淘汰。难点不在“存”，而在“取”：分页布局让搬运变成成千上万个几 KB 的小传输，带宽跑不满；调度器又不知道哪个请求还在等加载。LMCache 解决“怎么接进引擎、怎么批量搬”，Strata 解决“怎么把带宽跑满、怎么调度不被加载卡住”。

3. 组件拆解

3.1 LMCache：接进引擎的 KV 缓存层

  • 连接器：以 vLLM 的 KV connector 接口接入。调度器侧回答“新请求能命中多少 token”“分配后更新状态”；工作进程侧负责开始 / 等待加载与存储。SGLang 也有对应集成。LMCache §6、Tab. 2
  • 批量搬运：通过流式 GPU 缓冲区把多层的页聚成 256 token 的块；decode 期间新产生的 KV 先缓冲，凑满一块再写出。多个层级的存取并行进行。
  • 零拷贝与引用计数：并发读写共享同一份数据；动态卸载只复制部分空闲 GPU 页。
  • 控制 API：lookup、move、clear、pin / unpin、compress / decompress，由中心控制器协调各实例——上层系统（路由器、智能体框架）可以主动把某个前缀“钉”在某个实例上。

3.2 Strata：把带宽跑满、让调度知道加载

Strata（OSDI 2026，在 SGLang 中实现并部署）从测量出发：分页布局下一次传输只有几 KB，8192 token、页大小 32 时只用到 PCIe 5.0 理论带宽的约 22%，要跑到 75–80% 需要 1–2 MB 的传输；把页调大又会降低命中率（ShareGPT 上平均 / P90 TTFT 最多变差 2× / 2.9×）。在 LooGLE 上用 Qwen2.5-14B，基线有 74% 的 prefill 时间卡在 KV 传输上。Strata §1、§3.1 对策就是图中的两块：GPU 辅助 I/O 解耦两端布局，缓存感知调度处理延迟命中、加载受限的批和加载气泡。

3.3 算一算：每 token 的 KV 有多大、搬一次要多久

3.4 压缩 KV 与递归状态的缓存

DeepSeek-V4：磁盘 KV 缓存

CSA / HCA 压缩后的 KV 条目全部写盘，用于共享前缀复用；只有尾部未凑满压缩块的 token 需要重算。滑动窗口（SWA）的 KV 约为压缩条目的 8 倍大，论文给出三种策略：全存（零重算、写入量大）、每 p 个 token 存一次最近 nwin 个 token 的检查点、完全不存（为 L 层模型重算最后 nwin·L 个 token）。DeepSeek-V4 §3.5

Kimi K3：递归状态的前缀缓存

KDA 的递归状态是“某个位置的一个快照”，不能像注意力 KV 那样任意截断复用。K3 让 KDA 状态与 MLA 的 KV 共用一个分页池，6144 token 的物理块里按 512 token 哈希，只在稀疏的边界（通常是对话轮次）存只读的 KDA 快照；查找时先匹配 MLA 的哈希链，再要求同一边界上有 KDA 快照。RL 训练里还有一个外部 KV 池，被淘汰的可复用前缀写回 CPU 内存、复用前预取。Kimi K3 §5.3.1、§5.4.1

4. 伪代码

tiered_prefix_cache.py（一次请求的命中与加载，示意）
def admit(req, chunk=256):
    hashes = rolling_hash(req.tokens, chunk)                # 前缀按块哈希（链式）
    hit, tier = 0, []
    for h in hashes:
        loc = index.lookup(h)                               # GPU / CPU / SSD / remote / None
        if loc is None: break
        hit += chunk; tier.append(loc)
    if hit and load_time(hit, tier) > prefill_time(hit):    # 交叉点：短前缀直接重算
        hit = 0
    if index.in_flight(hashes[:hit // chunk]):              # 延迟命中：等首个请求算完
        return defer(req)
    req.prefetch = [start_async_load(h, loc, layerwise=True) for h, loc in zip(hashes, tier)]
    req.compute_from = hit                                  # 只 prefill 未命中的后缀
    return schedule(req)

def on_evict(block):                                        # 显存满：写回下一层而不是丢弃
    cpu_pool.put(block.hash, pack_layers(block)) if block.reusable else free(block)

5. 关键结果

  • LMCache：吞吐最高 15×、延迟至少降 2×（论文设置下）；CPU 卸载时 QPS=1 的 TTFT 降 1.9–8.1×；PD 分离下平均 TTFT 比 vLLM 原生方案低 1.53–1.84×；与 SGLang 原生 CPU 卸载性能相当。LMCache 摘要、§8.2、§8.5、§8.8
  • Strata：摘要称长上下文 TTFT 比 vLLM + LMCache 低至 1/5、比 TensorRT-LLM 快 3.75×；正文 §5.2.1 对 Llama-70B 以“同 TTFT 下的吞吐”表述这两个倍数。短上下文（ShareGPT）不受影响。Strata 摘要、§5.2

6. 简答题

Q33KV cache 什么时候值得从 CPU / SSD / 远端加载而不是重新 prefill？分层 KV 缓存的主要工程瓶颈在哪里？

当“前缀 KV 字节数 ÷ 可用带宽”小于“重算这段前缀的 prefill 时间”时才值得加载。每 token 的 KV 字节固定，而 prefill 每 token 的成本随长度增长（注意力是二次的），所以存在交叉长度：带宽越低，交叉点越长。LMCache 实测 32 Gbps 时约 256K token 以上加载才更快，64 / 128 Gbps 时在所测长度上加载都更快。

  • 瓶颈 1 —— 碎片化 I/O：分页布局让一次传输只有几 KB，PCIe 跑不满（Strata：页 32 时约 22%）。对策：按页连续的主机布局、跨层打包成大块（LMCache 256 token 的块）、用 GPU 线程直接搬运（Strata GH200 上 40 → 150 GB/s）。
  • 瓶颈 2 —— 调度：调度器不知道请求在等加载，会组出加载受限的批、重复 prefill 同一前缀。对策：延迟命中合并、按“加载 / 计算”比例组批、加载期间插 decode 批。
  • 瓶颈 3 —— 计算与加载重叠：逐层流水（算第 N 层时加载第 N+1 层）、排队期间预取。
  • 模型侧也在配合：MLA / CSA 压缩 KV 让同样带宽能搬更长的前缀（DeepSeek-V4 把压缩 KV 全部存盘）；递归状态则只能在预先存了快照的边界复用（Kimi K3）。

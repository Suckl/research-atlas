1. 动机：两种阶段挤在一张卡上互相拖累

连续批处理把 prefill 和 decode 混在同一批里。DistServe 测得：往一个 decode 批里加入一个 prefill 任务，两边都明显变慢——prefill 是算力受限的大矩阵乘，会独占 SM 几十到几百毫秒，同批的 decode 请求这一步的 TPOT 直接被拉长；反过来 decode 的小矩阵乘又把 prefill 的批次搅碎。更根本的是，两种阶段想要的并行策略和批策略不同：

PrefillDecode
瓶颈算力带宽（权重 + KV 读取）
SLOTTFT（首 token）TPOT / TBT（逐 token）
想要的并行TTFT 紧时用算子内并行（TP）切短单次计算TPOT 紧时也要 TP；吞吐优先时流水并行 / 多副本
想要的 batch小（几个长 prompt 就打满算力）大（摊薄权重读取）
功耗（Splitwise）随 batch 升高，对功率上限敏感平坦；350 W 上限几乎不影响延迟
一句话理解 把 prefill 和 decode 拆到不同的 GPU 池，各自按自己的 SLO 选并行度和 batch；代价是每条请求要把 KV cache 从 prefill 卡传到 decode 卡。优化目标不是“更快”，而是 goodput——每张卡在满足 TTFT 与 TPOT 两个 SLO 的前提下能服务的请求率。

3.2 什么时候不该分离

DistServe 自己指出：吞吐优先的离线批处理场景下，分离的收益会被削弱，chunked prefill（把 prefill 切块混进 decode 步）可能更合适。分离本质上是用更多 GPU 与一次传输换SLO 下的稳定性；若没有延迟 SLO，让一张卡同时做两件事的总利用率可能更高。

4. 简答题

Q13PD 分离的整体数据流是怎样的？

把一条请求的 prefill 和 decode 两个阶段放到不同的 GPU（池）上执行，中间通过 KV cache 传输衔接。

  1. Prefill 池：算力受限，小 batch、按 TTFT 选并行度（常用更高的 TP）；算完首 token 返回，KV 留在显存。
  2. 传输：decode 实例按需拉取 KV（NVLink / RDMA），逐层异步与 prefill 计算重叠。
  3. Decode 池：带宽受限，大 batch 连续批处理，按 TPOT 选并行度；没有 prefill 插队。
  4. 调度 / 放置：离线为两种实例搜索并行配置与数量（DistServe），在线做负载均衡与（Mooncake）SLO 预测、早期拒绝；Splitwise 加混合池应对突发负载。

依据：DistServe §3–4；Splitwise §4；Mooncake §3。

Q14PD 分离优化的指标是什么？为什么它不等于“更快”？

不是“更快”，而是消除两种阶段的互相干扰 + 让每种阶段按自己的 SLO 独立选并行与批策略，从而提高 goodput（满足 TTFT 和 TPOT 的请求率）。单条请求甚至可能因为多了一次传输而略慢。

  • 混部时 prefill 把同批 decode 的 TPOT 拉长、decode 的小算子又拖慢 prefill——DistServe 实测两边都显著变慢。分离后 decode 的 TPOT 曲线平稳，prefill 不再排队等 decode 步。
  • 并行策略解耦：prefill 想要高 TP 压 TTFT，decode 想要大 batch 和适度 TP 压 TPOT；混部只能取一个折中配置。
  • 资源配比解耦：prefill 与 decode 的算力需求比例随负载（prompt / 输出长度）变化，分离后可以独立扩缩两类实例；异构时还能把 decode 放到更便宜、带宽充足的卡上（Splitwise 的 Perf/W、Perf/$）。
  • 结果以 goodput 衡量：DistServe 在同样的 SLO 下承接 2–4.6× 的请求率，或在同样请求率下 SLO 收紧 12.6×。

依据：DistServe §2.3（干扰）、§3（goodput 与并行分析）、§6；Splitwise §3（Insight I–V）。

Q15若 prefill 与 decode 运行在不同厂商的 GPU 上，最大的困难是什么？

最大的挑战是 KV cache 的“契约”在两套软硬件栈之间没有共同语言——布局、数据类型 / 量化格式、数值结果都要一致，而且两边没有共享的高速互连与通信库。

  • 传输通路：没有 NVLink 这种跨厂商的链路，只能走 RDMA 网络；NCCL 与 RCCL 不能互通，需要厂商无关的传输层（如 NIXL / Mooncake Transfer Engine 这类基于 UCX / RDMA 的实现），且两边的 GPUDirect RDMA 支持都要打通。
  • KV 布局与格式：两边注意力内核（FlashAttention vs CK / aiter）期望的 KV 张量布局（[block, head, token, dim] 的顺序、块大小、对齐）、FP8 的具体格式与缩放因子粒度可能不同，需要在传输时转换或约定统一格式。
  • 数值一致性：prefill 和 decode 用不同内核、不同精度（甚至不同的 FP8 累加策略）会让同一位置的 KV 有微小差异，长序列 decode 下误差累积可能影响输出；这与 训推不一致是同一类问题。
  • 调度与容量匹配：两种卡的吞吐、显存、KV 容量不同，放置算法要按各自的性能模型重新搜索；故障域、驱动版本、两套运维栈也是现实成本。

依据：Splitwise §4（异构 Splitwise-HA 的设计前提是同厂商不同代；跨厂商的挑战为依据上述论文机制的推论）；DistServe §4.2（KV 传输）。

Q16决定 PD 之间 KV 传输量的核心因素是什么？

通信量 = 每条请求的 KV 字节数 × 请求率，而每条请求的 KV 字节数由模型的注意力架构（每 token 缓存多少数）、上下文长度和KV 精度决定：

$$\text{bytes/request} = S \times 2 \times L \times n_{kv}\times d_h \times \text{bytes}\qquad(\text{MLA}: S\times L\times(d_c+d_r)\times\text{bytes})$$
  • 最大的杠杆是每 token 的 KV 大小：MHA → GQA 降 4–8×，MLA 再降数倍（DeepSeek-V3 每 token 约 70 KB vs Llama-3-70B 320 KB vs OPT-13B 800 KB）；FP8 KV 再减半。架构一定，S 就是唯一变量。
  • 其次是能否与计算重叠：逐层发送（Splitwise）把非重叠部分压到几毫秒；异构时若格式需要转换，转换本身也要流水化。
  • 异构特有的加项：若两边 KV 格式不同，可能要以较高精度传输再转换（字节数上升），或多一次打包 / 解包。
  • DistServe 的量级：OPT-66B、512 token ≈ 1.13 GB/请求；10 req/s ≈ 90 Gbps——正好是一张 100 Gbps 网卡的量，所以“压 KV 大小”比“加网卡”更根本。

依据：DistServe §4.2 的带宽估算；KV 大小公式；DeepSeek-V2/V3 的 MLA 维度。

1. 动机：KV cache 才是显存的大头，却被浪费了 60–80%

vLLM 论文用 OPT-13B 算账：每个 token 的 KV 要 2 × 5120 × 40 层 × 2 字节 = 800 KB，一条 2048 token 的请求就是 1.6 GB；A100-40GB 放下 26 GB 权重后，剩下的显存能装多少请求，直接决定 batch 大小，也就决定了吞吐。但当时的系统（FasterTransformer、Orca）为每条请求按最大可能长度预分配一段连续显存：

  • 预留浪费：为还没生成的 token 占着位置；
  • 内部碎片：请求实际只生成了几百 token，预留的 2048 用不完；
  • 外部碎片：不同大小的连续块在显存里东一块西一块，分配器（如 buddy allocator）拼不出整段。

论文测得这些系统里只有 20.4%–38.2% 的 KV 显存真正装着 token 状态。

一句话理解 操作系统早就解决过同样的问题——用分页让“逻辑上连续”的内存“物理上不连续”。PagedAttention 把 KV cache 按固定大小的块分配，用块表翻译地址，再把分页带来的共享（引用计数、写时复制）也一并搬过来。

3. 组件拆解

3.1 block_size：16 是怎么来的

块越大，内核一次读的内存越连续、块表越短、并行度越高；但每条请求最后一块平均浪费 block_size/2 个 token，而且共享只能以整块为单位——两条请求的共同前缀里不足一块的尾巴无法共享。论文 §7.2 的消融：ShareGPT（长序列）上 16–128 都好；Alpaca（短序列）上 16 和 32 最好、更大的块明显变差。于是“16 足够让 GPU 高效，又足够小以避免大多数负载下的内部碎片”。

3.2 前缀共享：vLLM 与 SGLang 的分岔点

论文里的共享是显式的：并行采样、beam search、共享系统提示由调度器知道并建立映射。后来 vLLM 加入了自动前缀缓存：对每个满块按其内容（token 序列 + 前序块哈希）计算哈希，新请求的前缀块若命中哈希表就直接复用。SGLang 的 RadixAttention 则把前缀组织成基数树、以 token 为粒度匹配（见 下一篇）。二者的差异本质上是“整块哈希” vs “逐 token 树”，前者简单、后者匹配更细。

5. 简答题

Q5PagedAttention 借用了操作系统的哪个机制？块表、引用计数、写时复制各起什么作用？

把操作系统的分页虚拟内存用到 KV cache 上。

  1. 分块：KV cache 按固定大小的块（默认 16 token）分配，每块存这 16 个 token 在所有层所有头的 K 和 V。
  2. 块表：每条请求有一张“逻辑块 → 物理块”的表，逻辑上连续的序列在显存里可以不连续。按需分配，块满了才要新块。
  3. 内核：注意力内核按块表 gather 各物理块的 K、V，分块算 QKᵀ 和加权求和；新 KV 也按块表写入。
  4. 共享：多条请求的相同前缀映射到同一物理块（引用计数），写入共享块前先复制（写时复制）。
  5. 效果：没有外部碎片（块等大）、没有预留浪费（按需）、内部碎片 < 1 块/请求；KV 利用率从 20–38% 提到接近 100%，batch 更大，吞吐 2–4×。

依据：论文 §4.1–4.3、§5、§6.1。

Q6KV 块通常多大？把块调大或调小，分别牺牲什么、换来什么？

复用（共享）的最小粒度就是一个块；块的大小是配置项，论文默认 16 token，vLLM 代码的 CacheConfig.DEFAULT_BLOCK_SIZE = 16，论文消融测到 128，不同后端对可选值有限制。

  • 论文 §7.2 评估了 1 到 128 的块大小；默认 16。
  • 当前 vLLM 源码里 block_size 默认 16（vllm/config/cache.py），常见可选 8/16/32，部分后端（FlashInfer、某些加速器）支持更大的 64/128 等；Mamba 类层的块大小要求是 8 的倍数。具体可选集合随版本和注意力后端变化，可以概括为“默认 16、按后端可调到 128 级别”。
  • SGLang 的对应概念是 --page-size，默认 1——RadixAttention 以 token 为粒度共享，所以它的“最大复用单位”问题变成了“树上匹配到的最长公共前缀”。
  • 一个块在 OPT-13B 上是 16 × 800 KB = 12.8 MB；共享前缀只有凑满整块的部分才能被复用。

依据：论文 §4.1、§7.2；vLLM vllm/config/cache.py；SGLang 服务器参数文档。

块大小怎么定

在“内核效率 / 元数据开销”和“内部碎片 / 共享粒度”之间折中。

  • 块大 → 好：内核一次读连续的 16×(K,V) 更能打满带宽，块表更短，CPU 侧管理与 gather 的间接寻址更少，交换 / 拷贝更高效（论文测得小块时 swap 开销很大）。
  • 块大 → 坏：每条请求最后一块平均浪费 block_size/2；短请求多时浪费比例显著（Alpaca 上块 >32 性能明显下降）；共享只能按整块，前缀的尾巴浪费更多；抢占时的最小搬运单位更大。
  • 硬件对齐：块内 token 数与内核 tile（如 FlashAttention 的 B_c）、向量化访存宽度对齐，这也是 8/16/32 这些 2 的幂的来源。
  • 论文结论：16 在 ShareGPT 与 Alpaca 两类负载上都接近最优，故为默认。

依据：论文 §7.2（块大小消融）、§7.3（swap vs recompute）。

Q7vLLM 与 SGLang 的设计出发点有何不同？两者前缀缓存的粒度差异从何而来？

起点不同：vLLM 从“显存管理”出发（PagedAttention），SGLang 从“LM 程序的执行”出发（RadixAttention + 前端语言 + 约束解码）。核心差异在前缀缓存粒度、调度与结构化输出；二者此后互相吸收，能力已高度趋同。完整对比见 SGLang 页 Q7。

Q8投机解码的草稿被拒绝后，KV cache 需要怎样“回退”？分页 KV 下为什么不需要搬数据？

在分页 KV 下根本不需要“回滚拷贝”：草稿 token 的 KV 写在请求末尾的槽位里，验证后只需把“已确认长度”指针退回到最后一个被接受的位置，被拒绝位置的槽位会在下一步被新 token 覆盖。

  • 验证前：调度器为 γ 个草稿 token 预留槽位（必要时分配新块），目标模型一次前向把这 γ 个位置的 KV 写入。
  • 验证后：接受了前 k 个（k ≤ γ）+ 补采 1 个，则请求长度设为 L + k + 1；块表不变，多分配的块若整块空出就归还空闲表。
  • 因为块是按 token 槽位寻址的，“覆盖”就是回滚；只有树状草稿（多条候选分支）才需要把被选中分支的 KV 搬到正确位置或用掩码处理。

算法层面的解释见 投机解码页 Q8。

依据：论文 §4.1 的块表与按需分配机制；vLLM 投机解码文档（验证后按接受数截断的实现思路，细节随版本变化）。

后续节点 前史与后续：连续批处理来自 Orca（vLLM 的显存问题正是 Orca 按最大长度预留 KV）；KV 溢出显存之后的分层存储见 KV cache 分层存储。

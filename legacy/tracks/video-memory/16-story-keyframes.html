1. 动机：镜头切走以后，人物和场景如何回来？

故事镜头不按连续时间或固定相机排列：主角离场、插入别处镜头、再以新服装或视角返回。最后一帧可能没有要回忆的人物；完整视频历史又含大量冗余。因此关键不是保存最多相邻帧，而是保存可用于下一镜头的视觉证据，并区分哪些外观应保持、哪些事件状态应变化。OneStory §4.2；StoryMem §3.2、§3.4

一句话理解 Captain Cinema 先规划视觉锚再合成运动；OneStory 按下一镜头内容分配历史预算；StoryMem 每生成一镜头就筛选关键帧并更新 bank。三者共享稀疏视觉证据这个问题，却不是已声明的相互继承链。Captain §3；OneStory §4；StoryMem §3

本页把生成过去的在线记忆、预先提供的角色参考和已经规划好的未来视觉锚分开。稳定人物外观可以帮助故事连贯，但仍不能单凭相似度证明“杯子已打碎”“角色换装后不回退”等状态更新正确。

2. 两种时序：先完成分镜，或逐镜头写记忆

统一记号：\(t\) 是视频时间、\(\tau\) 是 diffusion / flow 时间，\(x_t\) 是当前 latent，\(H_t\) 是近期历史，\(M_t\) 是记忆，\(q_t\) 是查询，\(r_t\) 是读出；镜头文本为 \(c_t\)。本页以镜头索引 \(i\) 写循环，不使用动作 \(a_t\) 或相机 \(p_t\) 作为这三种系统的通用必需输入。

$$r_i=\mathrm{Read}(M_{i-1},q_i(c_i)),\qquad V_i\sim G_\theta(r_i,c_i),\qquad M_i=\mathrm{Write}(M_{i-1},V_i).$$

Captain Cinema 的偏离：planner 先按图文历史生成 \(\{I_i\}\)，GoldenMem 服务的是该关键帧阶段；之后 LCT 类视频生成器读取已生成的整套关键帧，含后续镜头锚。它不是一边播放视频一边只记住生成过去的单环系统。Captain §3.2–3.3、§4.1

观测 / latent / 噪声生成器主干（可训练） 冻结 VAE / 特征编码器可训练记忆部件 关键帧记忆镜头文本 / 脚本损失

3. 组件拆解：把选择、压缩和写入分开

Captain Cinema：GoldenMem 在 planner 中，LCT 在合成中

输入是详细 storyline / shot descriptions，可由人或外部语言模型提供；Captain 本身不自主构思故事。planner 从 FLUX.1-dev 出发处理交错图文：早期 double-stream blocks 的 block-diagonal mask 只在各 pair 内处理，后期 single-stream blocks 才聚合跨 pair 信息；训练可双向，生成可换因果掩码。Captain §3.2、§5

检索先比较当前文字与历史图文：论文比较 CLIP text-to-image 与 T5 text-to-text，前者的检索覆盖更好。GoldenMem 将历史图像逐级降采样，压缩活动视觉条件。语义召回和分辨率分配是不同操作，不应把它概括为“只留最近帧”。Captain §3.2、Fig. 5

$$\varphi=\frac{1+\sqrt5}{2},\qquad s_j=\lfloor s_{j-1}/\varphi\rfloor,\qquad T_{\mathrm{visual}}\approx t_0\sum_{j=0}^{k}\varphi^{-2j}<\varphi t_0\approx1.62t_0.$$

论文以固定长宽比的几何缩放解释该常数因子；\(t_0\) 为当前全分辨率帧的 token 数，包含当前帧。它不约束全部原始关键帧、文本 token 或检索库的存储，也不保证低分辨率历史的小字和道具细节可恢复。Captain §3.2、Fig. 4

关键帧先生成完，再交给 Seaweed / LCT 类视频模型补每镜头运动。§3.3 的条件写成全部 \(I_{1:K}\)，所以合成镜头时已有后续视觉锚；两阶段分别训练，不能把完整系统的叙事一致性说成视频基模独立学会了在线远程记忆。LCT 的跨镜头注意力见 第 03 页。Captain §3.3、§4.1、§5

OneStory：重要内容得到更细的 patch

OneStory 从所有此前镜头构造 latent memory。可学习 queries 先 cross-attend 当前 caption，再 attend 历史视觉 tokens；根据 query–memory interaction 得到帧级 relevance，选取非连续的 Top-k 历史帧。高分帧使用较小 kernel / 较细 patchifier，低分帧更强压缩，再把所有 context tokens 与当前 noise tokens 拼接。OneStory §4.2–4.3、Eq. 2–8

$$q_i'=\mathrm{Attn}(Q,\phi_T(c_i),\phi_T(c_i)),\quad q_i''=\mathrm{Attn}(q_i',\phi_V(M),\phi_V(M)),\quad r_i=\operatorname{Concat}_{\ell}\mathcal P_\ell(\widehat M_{\mathcal I_\ell}).$$

这改变了时间距离决定压缩率的假设：主角所在旧镜头可能比刚结束的插入镜头重要。selector 的候选 history 仍增长，且查询需访问历史表示；“一个 latent 帧等价的活动 context”不等于完整历史只有一帧。训练时的 DINOv2 / CLIP target-shot 相似度是伪标签监督，推理 selector 不获未来目标视觉。OneStory §4.2、§5.3、App. A.2

OneStory 不要求单独的全片 global script，以当前 shot caption 的指代关联历史；第一镜头可文本或文本加图初始化。它在 inference 图中维护 prior-shot memory，并未描述一个训练过的语义写入 / 全局淘汰模块。OneStory §3、§4.1、Fig. 3

StoryMem：在生成后决定什么值得留下

StoryMem 从 Wan2.2-I2V 出发，记忆帧独立 VAE 编码，沿时间维加入 condition latent，再把 noisy latent、condition latent、binary mask 沿通道维拼接。memory 区域保持为已知条件，只输出当前 shot；读取 bank 中哪个人物由文本条件与注意力完成，没有显式 selector 的 Top-k 查询。StoryMem §3.3

$$\mathrm{TimeIndex}=\{-mS,-(m-1)S,\ldots,-S,\;0,1,\ldots,F-1\}.$$

\(m\) 是记忆帧数，\(F\) 是当前 shot latent 帧数，\(S\) 是固定负 RoPE 间隔；当前镜头位置仍从零开始。这些位置不是真实历史时间戳，也不能恢复关键帧间未保存的运动。StoryMem §3.3

每生成一镜头，先用 CLIP 比较与最新选中帧的语义变化，再用 HPSv3 审美过滤；与原 bank 去重后写入。早期 sink 不随窗口淘汰，余下保留近期合格帧。它把“写什么”放在 generation 之后，和 OneStory 在 read 时决定“哪些候选值得花 token”形成对照。StoryMem §3.4

论文 vs 官方代码：阈值、首帧与容量 论文 §3.4 说选帧过多时提高相似度阈值；但选取条件是 similarity 低于 threshold，提高会选更多。官方 extract_keyframes.py 实际将阈值减小 0.01，并选第一个通过质量过滤的帧，而非无条件保留帧零。公开 pipeline.py 的容量默认是 8 个关键帧、fix=3；README 则写默认 10 个 shots。论文未给总 bank 容量，复现应以具体入口为准。官方 commit 052c68d，extract_keyframes.py / pipeline.py / README.md；论文 §3.4、§4.1

5. 训练：读取监督与写入启发式的区别

Captain：用电影提取的交错图文微调 planner，以逐步增加 context 长度和混合噪声训练适应长条件；视频模块另训 keyframe-conditioned synthesis。分开训练意味着没有视频后续损失贯穿 planner / GoldenMem 的端到端闭环。Captain §3.2–3.3、§4.2、§5

OneStory：训练预测 triplet 最后镜头；两镜头数据通过插入无关镜头或增强首镜头变成统一 triplet。warm-up 用真实历史均匀取帧，随后才依赖 selector。target-shot 的 DINOv2 / CLIP 相似度给相关度伪标签，训练读出是有监督的，而不是只让 generator 自发学检索。OneStory §4.4、App. A

$$\mathcal L_{\mathrm{OneStory}}=\mathcal L_{\mathrm{shot}}+\lambda\mathcal L_{\mathrm{sel}},\qquad \mathcal L_{\mathrm{sel}}=\frac1{F_{\mathrm{hist}}}\sum_r(s_r-y_r)^2.$$

StoryMem：训练从语义相关 clips 抽记忆帧、重建 target clip，用 LoRA 学 M2V 条件生成；CLIP / HPS 选帧是推理中的确定性程序，不是通过跨镜头梯度学到的 writer，也未报告训练时完全 self-generated memory rollout。StoryMem §3.3–3.4、§4.1

flow 时间与符号不能照搬混用 本页若写 \(x^\tau=(1-\tau)x+\tau\epsilon\)，则随 \(\tau\) 增加的导数为 \(\epsilon-x\)，采样从 noise 向 clean 积分。StoryMem Eq. 2 用该插值，Eq. 3 的 target 却写 \(x-\epsilon\)。这两式存在方向约定不一致；本文不据此补写训练代码的速度符号，复现需检查实际 scheduler / target。StoryMem Eq. 1–3

  • OneStory 与 StoryMem 分别改善读预算和写入质量；合页是设计比较，没有从日期推断继承箭头。
  • 实体与角色槽位 进一步处理“该取哪个人物”的歧义；整帧相似度不能独立证明多实体状态正确。
  • 流式多镜头 再把 shot 级记忆与 chunk 级低延迟生成结合；活动预算与全历史成本仍要分开。

简答题

Q31Captain、OneStory、StoryMem 都用稀疏视觉历史，为什么它们的“记忆一致性”不能直接按分数比较？

记忆所在模块、可用信息和评测对象不同。Captain 的 planner 记关键帧，视频合成已有全套视觉锚；OneStory 从全部生成过去中选择和压缩内容；StoryMem 每 shot 更新有限关键帧 bank。其 evaluator 分别测关键帧 rubric / Identity、人物背景 DINOv2、shot-pair ViCLIP，分数不是同一能力尺度。Captain §3–4；OneStory §4–5；StoryMem §3–4

  • 给定未来视觉锚与仅给未来文本的任务不同；预写人物参考也有额外信息。
  • 公平比较需统一初始化、镜头 script、return gap、基座 / 预算，并单列身份、事件变化和更新正确性。

依据：Captain §3.3、Tab. 2；OneStory App. B；StoryMem §3.5、§4.3。

Q32只存每镜头第一帧会漏掉什么？重要度读取和生成后筛帧能否解决所有叙事状态问题？

首帧可能没有中途进入的人物、后来拿起的道具或变化后的服装。OneStory 可从完整 prior-shot 候选选择相关帧；StoryMem 的语义变化筛选把新内容写入，避免只记镜头起点。但相似度筛选、审美过滤和有限 bank 都不显式表示实体状态或保证覆盖旧事实。OneStory §4.2、§5.3；StoryMem §3.4、§4.4

  • 新状态若未入 bank，或旧状态 sink 一直保留，可能产生相互冲突条件；这是需实验区分的机制风险，不能当作本文已证明的普遍失败。
  • 身份稳定、清晰帧和场景相似分别是有用证据，仍需“按指令变化→离场→返回保持新状态”的单独任务。

依据：StoryMem Fig. 6–7、Tab. 2；OneStory Fig. 6–7、App. B。

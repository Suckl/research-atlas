0 导读：这份报告讲了什么

DeepSeek-V4.1-Flash 是 DeepSeek 在 2026 年 9 月发布的模型：权重 9 月 10 日上传 Hugging Face，技术报告 9 月 17 日上传 arXiv。它是一个能同时读图和读文字的混合专家模型（MoE），主干有 552B 参数，另外挂了 196B 参数的 Engram 查表模块，支持 100 万 token 的上下文。它的主干有 40 层，前 20 层叫“因果编码器”，后 20 层叫“解码器”；这个划分让模型在处理输入（预填充）时每个 token 只激活 8B 参数，在逐个生成输出（解码）时激活 16B 参数。

报告的标题已经说明了重点：把 KV 缓存压到极限。原因在于使用方式变了。现在的大模型越来越多地被当作智能体使用：它反复调用工具、读取文件和网页，每一轮都把很长的历史重新喂给模型，输出却相对很短。作者把这种负载称为“输入很重”的负载。前几代模型已经用稀疏注意力把长上下文的计算量压了下来，于是剩下的瓶颈变成了存储和搬运：KV 缓存要占用 GPU 显存（HBM），要为了复用而长期存到 SSD 上，还要在机器之间传来传去。

V4.1-Flash 在三个层面同时压缩。结构层面，新的注意力 CSA2 让多层共用同一份全局 KV，而不是每层各存一份；精度层面，全局 KV 用 4 位浮点（FP4）存储，并在后训练中用量化感知训练让模型适应；部署层面，一种叫“SWA 有界重放”的近似重算，让滑动窗口部分的 KV 不必再长期存到 SSD 上。三者合起来，常驻显存的全局 KV 是每个 token 890 字节，约为上一代 V4-Flash 的 1/4；为前缀复用而长期保存的 KV 约为 V4-Flash 的 1/8。另一个结构改动“因果编码器—解码器”（CED）则把预填充的计算量砍掉将近一半。

报告的其余部分覆盖了一个完整模型的所有环节：残差流混合的 Single-Pass mHC、条件记忆 Engram、投机解码模块 DSpark、给大嵌入表用的 Sinkhorn 平衡优化器、45T token 的多模态预训练、以数据为中心的后训练（报告明说没有任何算法创新）、可连续调节的“推理努力程度”，以及和 Opus-5、GPT-5.6 Sol、Kimi-K3、GLM-5.3 等模型的对比评测。

先说读这份报告最需要记住的一点：每一步压缩到底让精度掉了多少，报告几乎没有给数字。FP4 的代价被描述为“只有轻微下降”，有界重放的代价被描述为“可以忽略”，CSA2 的跨层共享没有单独的消融实验。报告里能看到的定量证据，主要是 V4.1-Flash 和 V4-Flash 的整体对比，而两者之间同时变了参数量、训练数据、多模态、Engram、后训练数据等许多东西。此外，这份报告发布至今只有一个月左右，独立的复现和评测还很少，这一点在末节“后来怎么样了”里单独交代。

1 引言：智能体让输入越来越长，KV 缓存成了部署成本的大头

这一节要回答的问题：稀疏注意力已经让长上下文的计算便宜了很多，为什么作者还说部署成本卡在 KV 缓存上？V4 系列的 KV 缓存由哪几部分组成，各自存在哪里、受什么资源限制？V4.1-Flash 打算从哪几个层面去压，最后压到了什么程度？
先补一点背景：每个 token 的 KV 缓存有多大，为什么它决定长上下文的成本。

模型逐个生成 token 时，每一层注意力都要拿当前 token 的 query 去和前面所有 token 的 key、value 计算。前面那些 token 的 key 和 value 每一步都要用，所以推理系统把它们存下来，叫 KV 缓存（详细的来龙去脉见 vLLM 精读 §2.2）。衡量它的最方便的单位是每个 token 占多少字节：把每一层为这个 token 存的数加起来，再乘以每个数的字节数。

以 DeepSeek 的第一代 67B 模型（V1）为例：它有 95 层，每层用分组查询注意力（GQA）存 8 个 key 头和 8 个 value 头，每个头 128 维，用 BF16（每个数 2 字节）存储，所以每个 token 要 \(95\times 2\times 8\times 128\times 2 = 389{,}120\) 字节，约 0.39 MB（推算，和原文图 1(b) 的数一致）。一个 100 万 token 的请求就要约 389 GB，比一台 8 卡服务器的全部显存还多。这就是为什么长上下文模型必须先压 KV：每个 token 的字节数直接决定一张卡能同时服务多少个请求、多长的请求，进而决定每个 token 的成本（这个“批越大越便宜”的道理见 vLLM 精读 §1）。

先补一点背景：V4 系列的两种 KV，以及它们存在哪里。

DeepSeek-V4 的每一层注意力有两个分支（详见 V4 精读 §4）。一个是全局分支：它能看到整个上下文，但看到的是压缩过的条目——每 \(m\) 个 token 被压成一个条目，再由一个轻量“索引器”为每个 query 挑出最相关的少数几个条目。全局分支要存的东西叫全局 KV，包括主 KV（真正参与注意力的压缩条目）和索引器 K（索引器打分用的小向量）。另一个是局部分支，即滑动窗口注意力（SWA）：每个 token 只看自己前面最近的 \(n_{\mathrm{win}}=128\) 个 token，用的是没压缩的原始 KV，叫 SWA KV。

两种 KV 的增长方式完全不同。全局 KV 随序列长度线性增长：上下文翻倍，它也翻倍。SWA KV 每层只需要保留最近 128 个 token，和上下文多长无关。所以上下文足够长时，全局 KV 占了运行时 KV 的绝大部分，它受 GPU 显存容量的限制。

另一种划分是按“存多久”。正在服务的请求，它的 KV 放在显存里，叫运行时 KV。请求结束后，为了下一轮对话或者别的请求能复用同一段前缀（例如同一个代码仓库、同一份系统提示），推理系统会把一部分 KV 长期存到 SSD 或主机内存里，命中时直接读回来，省掉重新预填充，这部分叫持久 KV 缓存（这种分层存储的系统设计见 LMCache 精读 和 Mooncake 精读）。持久 KV 受 SSD 和主机内存的容量限制，读写它又受 I/O 和网络带宽限制。

作者对问题的诊断是这样的。智能体任务把模型的工作负载推向“超长输入”：一次任务可能有几十上百轮工具调用，每一轮都要带着完整的历史。稀疏注意力（V3.2 的 DSA、V4 的 CSA/HCA）已经让处理长序列的计算便宜了很多，于是存储和数据搬运成了更突出的瓶颈：全局 KV 挤占显存，限制了一张卡能同时服务的请求数；持久 KV 挤占 SSD 和主机内存，限制了前缀能缓存多久、命中率有多高；KV 在机器之间迁移和加载还要占用带宽。这三件事加起来，限制了吞吐、推高了成本，也就限制了智能体能被部署到多长的任务、多大的规模上。

所以 V4.1-Flash 的设计目标就是在 V4 的基础上继续压 KV。作者给出一个概括性的视角：V4 可以看成“一个以 SWA 做局部处理的骨架，再加上一份压缩过的全局上下文”。既然局部的 SWA 部分已经很省（每层只存 128 个 token），要压就压全局分支，同时尽量保留局部注意力的设计。具体在三个层面动手：

  • 结构：新的 CSA2 让多层共享同一份全局 KV（主 KV 和索引器 K），并让一些层直接复用别的层选出来的 top-k 位置；同时去掉了 V4 的 HCA，全部改用 CSA2（§2.3）。
  • 精度：在训练中让全局主 KV 适应 FP4 存储，作者称精度只有轻微下降（§2.4.4）。CSA2 加 FP4，全局 KV 降到 V4-Flash 的约 1/4。
  • 部署：V4 为了让 SWA 的 KV 能在前缀命中时恢复，要么存下来，要么精确重算，而精确重算需要重放 \(L\times n_{\mathrm{win}}\) 个 token（\(L\) 是层数）。V4.1 引入 SWA 有界重放，只重放最近的 \(n_{\mathrm{win}}\) 个 token，得到一个近似的 SWA 状态，于是 SWA KV 不用再存到 SSD 上，持久 KV 再减半，降到 V4-Flash 的约 1/8（§3.2）。

把每个 token 的字节数换成“一个 100 万 token 的请求要占多少显存”（推算），差别更直观：V1 约 389 GB，V3.2 约 48 GB，V4-Flash 约 3.5 GB，V4.1-Flash 约 0.89 GB。也就是说，到了 V4.1-Flash，一个百万 token 请求的全局 KV 已经不到 1 GB。这个规模下，KV 已经小到可以考虑长期保存大量请求的前缀，这正是后面持久缓存设计的前提。

读这些数字时容易混淆的地方：
  • 890 字节只算全局 KV。每个请求另外还有 SWA KV：40 层、每层最近 128 个 token、每个 528 字节（FP8 格式，FlashMLA 文档），合计约 2.7 MB（推算）。这部分不随上下文增长，所以在长上下文下占比很小，但在短请求、高并发时并不能忽略。
  • “约 1/4”说的是全局 KV（常驻显存），“约 1/8”说的是持久 KV（存在 SSD 或主机内存），两个数衡量的是不同的东西。后者还依赖部署方式和负载（§3.2.1）。
  • 字节数是按设计算出来的，不需要实验，也不会因测试条件而变；它不说明模型在这么小的 KV 下精度如何，后者要看评测。

1.4 报告的其他结论

引言还概括了报告的其他内容。架构上，作者把 mHC 升级为 Single-Pass mHC，配合一个叫 Mega-mHC 的部署内核，把激活的显存读写量减半；集成了 Engram 条件记忆来增强能力；用 DSpark 做投机解码。系统上，训练支持视觉编码器分离执行、长序列的图像均衡切分、跨流水线阶段共享注意力状态；推理实现了编码器和解码器两条“有界重放”路径，绝大多数层（Reuse 模式）预填充只用 15 个内核、解码只用 11 个。预训练用了 45T token 的多模态语料，稀疏注意力从头在 64K 长度上训练，没有稠密注意力的预热阶段。作者称基座模型在知识、推理、代码上与 V4-Pro-Base 相当，在内部留出集上好 5%–10%，而总参数只有后者的 1/3、激活参数只有 1/4。后训练则明确“没有算法创新”，所有实质改动都在数据和环境的合成流水线上。

2.1.2 按模态分开的无辅助损失负载均衡

2.2 因果编码器—解码器（CED）：预填充只算一半的层

这一节要回答的问题：智能体每调用一次工具，就产生一段新的输入要预填充；如果这段输入没有命中缓存，就要把它从第一层算到最后一层。能不能让预填充只算一半的层，同时又不丢掉后一半层生成 KV 的能力？代价落在哪里？
先补一点背景：预填充、解码，以及 YOCO。

推理分两个阶段：预填充一次性处理全部输入 token，计算每一层的 KV 并写进缓存；解码每步只处理一个新 token，读缓存、生成下一个 token（两个阶段的性质差异见 DistServe 精读）。在输入很长、输出很短的智能体负载里，预填充的计算占了大头。

YOCO（You Only Cache Once，Sun 等，NeurIPS 2024）提出过一种省预填充的结构：模型下半部分正常计算，并在中间产生一份全局 KV；上半部分的每一层都不自己产生 KV，而是直接对这份共享 KV 做注意力。这样，处理输入时只需要算到下半部分结束、拿到那份共享 KV 就可以停下，上半部分只需在生成阶段为新 token 计算。预填充的计算量因此减半。

CED 借用了 YOCO 的思路，并做了两处加强。第一，对全局注意力，前 \(L/2\) 层当作因果编码器；后半的解码器层（\(l>L/2\)）不从自己的隐藏状态 \(H_l\) 产生全局 KV，而是统一从第 \(L/2\) 层的隐藏状态 \(H_{L/2}\)（也就是编码器的最终输出）投影得到，但每层用自己的投影矩阵：

$$C_{l}=H_{L/2}\,W_{l}^{KV},\qquad Z_{l}=H_{L/2}\,W_{l}^{Z},\qquad l>\tfrac{L}{2}$$

这里 \(C_l\) 是 KV 条目，\(Z_l\) 是压缩时用的权重（CSA 把 \(m\) 个 token 加权合成一个条目，权重由 \(Z\) 经 softmax 得到）。由于这些 KV 只依赖编码器输出，预填充时只要把输入跑完前 20 层，就能顺手得到解码器需要的全局 KV。和 YOCO 的“只有一份共享 KV”相比，CED 允许不同解码器层用不同的投影，KV 的“容量”更大。不过在 V4.1-Flash 的实际配置里，解码器只有第 20 层是 Full 模式、真正写 KV（§2.3），所以整个解码器实际上共享第 20 层由 \(H_{20}\) 投影出的那一份全局 KV。

第二，对 SWA，CED 保留了逐层计算：解码器每一层的局部 K、V 都从该层自己的隐藏状态 \(H_l\) 算出。作者的理由是这样让局部 KV 经过更深的计算，表达力更强。但这带来一个麻烦：解码开始时，第一个新 token 在解码器每一层都要看前面 128 个 token 的 SWA KV，而这些 KV 要求那些 token 真的在解码器里算过。精确地得到它们，需要在预填充末尾对最后 \(n_{\mathrm{win}}\times L/2=128\times20=2{,}560\) 个 token 跑完整个解码器（推算；原因是滑动窗口逐层叠加时感受野会扩大，§3.2.2 会画图解释）。如果每一轮只新增很短的输入（多轮对话里很常见），这笔额外计算就不可忽略。

作者的解决办法是“解码器 SWA 有界重放”：每次预填充，只把输入的最后 \(n_{\mathrm{win}}=128\) 个 token 送进解码器层，并且窗口在这 128 个 token 的起点处截断，得到一个近似的解码器 SWA 状态。依据是前人工作（PowerAttention，Chen 等 2025）发现 SWA 的实际有效感受野远小于理论上的 \(n_{\mathrm{win}}\times L/2\)。细节和风险放到 §3.2.2 讲。于是对于长度 \(N\gg n_{\mathrm{win}}\) 的输入，预填充的复杂度从 \(\mathcal{O}(NL)\) 降到 \(\mathcal{O}(NL/2+n_{\mathrm{win}}L/2)\approx\mathcal{O}(NL/2)\)，即减半。

换一个具体例子看减半的含义（推算）：一个 10 万 token 的新输入，原来要让 10 万个 token 都走 40 层；用 CED 后，10 万个 token 走 20 层，另有 128 个 token 走另外 20 层，总的“token × 层”从 400 万降到约 200.3 万。对于一个长 10 万、只有末尾 1,000 个 token 没命中缓存的请求，原来要算 1,000 × 40 = 4 万，现在是 1,000 × 20 + 128 × 20 ≈ 2.3 万，省得少一些，因为那 128 个 token 的重放是固定开销。

  • 解码器 SWA 的近似不是偶尔才发生的“缓存失效补救”，而是每个请求都走的正常路径：每次预填充都只重放最后 128 个 token。作者在后训练里模拟了同样的重放，让模型适应这种近似（§3.2.2）。

2.3 CSA2：沿三个维度同时压缩全局 KV

这一节要回答的问题：压缩 KV 缓存有哪几条路，前人各走到了哪一步、缺什么？CSA2 和 V4 的 CSA 相比改了什么？它为什么能在压缩比反而更小（\(m=2\)、\(m=1\)，而 V4 是 4 和 128）的情况下，把每个 token 的字节数压到 V4-Flash 的 1/4？
先补一点背景：KV 缓存的大小可以拆成三个相乘的因子。

每个 token 的 KV 字节数 = （每个条目多大）×（每个 token 平均产生几个条目）×（有几层各自存一份）。原文 §2.3 正是按这三个维度来梳理已有方法的，下面逐个从头讲。

维度一：条目大小。标准多头注意力每层要为每个 token 存全部头的 K 和 V。分组查询注意力（GQA）让若干个 query 头共用一组 K、V，KV 头数从几十个降到 8 个甚至 1 个（1 个时叫 MQA）。DeepSeek-V2/V3 的多头潜在注意力（MLA）更进一步：每层只存一个 512 维的潜向量，加上 64 维带位置信息的 RoPE 部分，共 576 个数，计算时再由它展开成所有头的 K、V（见 V3 精读 §2.1.1）。再往下压，就是降低每个数的位宽：从 BF16 到 FP8，再到 FP4（§2.4.4）。

维度二：序列方向。不是每个 token 都存一个条目，而是每 \(m\) 个相邻 token 合成一个条目。V4 的 CSA 取 \(m=4\)，并且每个条目由 \(2m=8\) 个 token 加权合成、相邻条目的来源互相重叠，还加了绝对位置编码来标记这 8 个 token 的位置；V4 的 HCA 取 \(m=128\)，压得很狠，但不做稀疏选择，对所有压缩条目做稠密注意力。和序列方向配套的是稀疏选择：V3.2 的 DSA 用一个很便宜的“闪电索引器”给每个历史条目打分，只让真正的注意力看分数最高的 top-k 个（见 V3.2 精读 §2.1）。要特别注意，稀疏选择省的是计算，不省存储：所有条目都得留着，因为下一个 query 可能选中任何一个；而且索引器自己还要为每个条目多存一个“索引器 K”。

维度三：层方向。相邻的层能不能共用 KV？跨层注意力（CLA，Brandon 等，NeurIPS 2024）让几层共用一份 KV；YOCO 让上半部分的层全部共用下半部分产生的一份 KV（§2.2）。在稀疏注意力里，还可以共享“选了哪些位置”：IndexCache（Bai 等 2026）让后面的层复用前面层选出的 top-k 下标，省掉索引器的计算；YOIO（Sun 等 2026）只算一次稀疏路由，全网所有层共用；HySparse（Gao 等 2026）让稀疏层复用稠密层的 KV。原文对这些方法的评价是：只复用下标不省主 KV 的存储；全网共用一份路由会限制性能；混合方案仍然保留了全注意力层；更重要的是，没有一个方法同时覆盖三个维度。

CSA2 的定位就是把三个维度一起用上：条目大小上，沿用 MLA 式的 512 维共享潜向量，并改存 FP4；序列方向上，编码器用 \(m=2\)、解码器用 \(m=1\)，配合索引器选 top-512；层方向上，让多层共享主 KV 和索引器 K，并允许层与层之间复用 top-k 下标，而且“共享缓存”和“复用下标”是两件解耦的事。另外，解码器里加了一个分层稀疏索引器，缩小后面索引层的搜索范围（§2.3.2）。

和 V4 的 CSA 一样，CSA2 里每个 query 的注意力同时看两部分：索引器选出的 top-512 个主 KV 条目，加上本层自己的 SWA KV（最近 128 个 token）。压缩比为 1 时，主 KV 就是不压缩的逐 token 条目，这被当作 CSA2 的一个特例。同时，CSA2 把 CSA 简化了两处：

  • 压缩器：去掉相邻条目来源的重叠（每个条目只由自己的 \(m\) 个 token 合成，不再是 \(2m\) 个），也去掉了标记这些 token 位置的绝对位置编码。官方推理代码里，压缩器就是对 \(m\) 个 token 的投影做一个按通道的 softmax 加权求和；\(m=1\) 时连这一步都没有，只是一次投影加归一化。
  • 索引器 K：不再从隐藏状态单独走一条压缩路径，而是直接从主 KV 条目投影得到（代码里是一个 512 → 128 的线性层）。这样，只要某层有主 KV，它的索引器 K 也就有了。

作者说这两处简化都是为了让实现更简单、训练更快，报告没有给出简化前后的精度对比。

2.3.2 分层稀疏索引器：后面的索引层只在候选池里找

跨层复用下标已经减少了运行索引器的层数，但剩下的每个索引器仍要给全部可见的条目打分。解码器的压缩比是 1，上下文有 100 万个 token，第 20 层的索引器就要给 100 万个条目打分；如果后面 4 个 Reindex 层也都这样做，成本就是 5 倍。作者认为在超长上下文下，这仍是主要的计算瓶颈。前人工作 HISA（Xu 等 2026）的做法是先给按块池化的表示打分、剪掉大部分块，再在剩下的块里按 token 打分。V4.1 发现解码器里有现成的信息可用，不必增加任何额外状态：浅层索引器的打分结果，可以直接用来缩小深层索引器的搜索范围。

具体做法（只用在 CED 的解码器里）：

  1. 解码器第一个 Full 层（第 20 层）照常给全部可见位置打分，选出自己的 top-512。
  2. 同一层顺带做块级筛选：把位置按每 8 个一块划分，每块的分数取块内的最大值，选出分数最高的 2,048 个块，它们覆盖的 \(2{,}048\times8=16{,}384\) 个位置组成“候选池”。
  3. 后面的 Reindex 层（第 24、28、32、36 层）用自己的索引器 query，只给候选池里的位置打分，再从中选出自己的 top-512。不同的 Reindex 层可以选得不一样，但都只能在同一个池里选。
  4. Reuse 层不打分，直接沿用最近一个下标层的结果。
示意图（缩小的玩具例子）：先按“块内最高分”圈出候选池，后面的层只在池里挑

  • 编码器 3 个 Full 层，每层 50 万个条目（\(m=2\)）：共 150 万。
  • 解码器第 20 层：100 万。
  • 4 个 Reindex 层：没有候选池时各 100 万，共 400 万；有候选池时各 16,384，共约 6.6 万。

这就是 §1.3 那条平坦曲线的主要原因之一：V4.1 每个 token 的索引计算大约只有 V4-Flash 的 1/4（推算，按“条目数 × 头数”粗算，忽略了两者其余部分的差别），主注意力又始终只看 512 + 128 个条目。

  • 分层索引器有一个结构性的风险：如果第 20 层的块级筛选漏掉了某段内容，后面 4 个 Reindex 层和它们之后的所有 Reuse 层都不可能再选到它。原文结论把“CSA2 的选择错误”列为尚未完全刻画的鲁棒性边界，并说今后会特别关注“长上下文中的稀疏检索”。
  • 报告没有给出分层索引器引入前后的精度或速度数字。上面的“减少约 60%”是本站按配置算的打分条目数，不是实测的时间。

2.4.1 Single-Pass mHC：把残差流的读写量压到理论下限

先补一点背景：mHC 在做什么。

普通 Transformer 只有一条残差流：每个块读进当前的隐藏向量，算出一个增量，加回去。超连接（Hyper-Connections）把它扩成 \(n\) 条并行的残差流，记作 \(X_l\in\mathbb{R}^{n\times d}\)（V4.1 取 \(n=4\)，\(d=5120\)）。每个块先用一组系数 \(A_l\)（\(1\times n\)）把 \(n\) 条流混成一个输入 \(A_lX_l\)，算出输出 \(\mathcal{F}_l(A_lX_l)\)，再用 \(C_l\)（\(n\times1\)）把输出分配回 \(n\) 条流，同时用 \(B_l\)（\(n\times n\)）把旧的 \(n\) 条流互相混合：

$$X_{l+1}=B_{l}X_{l}+C_{l}\,\mathcal{F}_{l}(A_{l}X_{l}),\qquad (A_{l},B_{l},C_{l})=\mathcal{H}(X_{l})$$

这三组系数不是固定参数，而是每个 token 由一个小预测器 \(\mathcal{H}\)（归一化 + 投影）根据 \(X_l\) 算出来的。DeepSeek 的 mHC（流形约束超连接，arXiv 2512.24880）给 \(B_l\) 加了约束，让它保持在“双随机矩阵”上（用 Sinkhorn–Knopp 迭代实现，V4.1 迭代 20 次），从而在层数很深时保持训练稳定。mHC 在 V4 中首次用于正式模型，见 V4 精读 §3。

mHC 的计算量不大，但它在每两个块之间都要把 \(n\) 倍宽的残差流读写好几遍，这些都是占显存带宽的“搬运”。作者先算理想情况：两个块之间的残差变换，本质上是一个从 \((X_{l-1},Y_{l-1})\) 到 \((X_l,\hat X_l)\) 的映射（\(Y_{l-1}\) 是上一块的输出，\(\hat X_l=A_lX_l\) 是这一块的输入），读 \((n+1)d\) 个数、写 \((n+1)d\) 个数，所以激活读写量的下限是 \((2n+2)d\)。

V4 的实现分三个内核顺序执行，因为数据有依赖：先做残差更新得到 \(X_l\)，再由 \(X_l\) 预测系数 \((A_l,B_l,C_l)\)，最后用 \(A_l\) 做输入混合。三个内核分别读 \((n+1)d\)、\(nd\)、\(nd\) 个数，共写 \((n+1)d\)，再加上块内预归一化的读写，总量是 \((4n+4)d\)，正好是下限的两倍。

能不能合并？系数预测里的 RMSNorm 权重可以离线并进投影矩阵，RMS 的除法放到投影之后做，于是“残差更新”和“系数预测”可以共用一次对 \(X_l\) 的遍历：残差更新不需要跨隐藏维度求和，每算完 \(X_l\) 的一小块，就能立刻用它累加投影结果和平方和。但“输入混合”合不进来，因为它要用的 \(A_l\) 必须等所有块都累加完才知道，只能再读一遍 \(X_l\)。这样的两遍实现是 \((3n+2)d\)，比下限多读一次 \(X_l\)。

Single-Pass mHC 的改法很简单：让每个块使用上一个块算出的输入混合系数，即把 \(A_l\) 换成 \(A_{l-1}\)：

$$X_{l+1}=B_{l}X_{l}+C_{l}\,\mathcal{F}_{l}(A_{l-1}X_{l}),\qquad (A_{l},B_{l},C_{l})=\mathcal{H}(X_{l})$$

\(A_{l-1}\) 在处理 \(X_l\) 之前就已经知道了，于是 \(X_l\) 的每一小块一算出来，就能同时拿去做输入混合和系数预测，不必等全部归约完成。部署时，残差更新、输入混合、系数预测（连同预归一化和转 FP8）被融合成一个内核 Mega-mHC，残差只读一次、写一次，达到 \((2n+2)d\) 的下限。代入 \(n=4\)、\(d=5120\)，每个 token 每经过一个块边界要读写的数从 102,400 个降到 51,200 个（推算）。

这个改动只改变“每个块用哪一组混合系数”，不改变计算的形式，所以预训练时作者仍保留原来的多内核实现。作者称这个错位带来的性能下降“可以忽略”，报告没有给出数字。

2.4.2 Engram：另一条稀疏维度上的 196B 查表参数

V4.1-Flash 集成了 DeepSeek 自己在 2026 年 1 月提出的条件记忆模块 Engram（本站有 Engram 精读）。它的想法是：语言里有大量只需要“查”、不需要“算”的局部模式（固定搭配、实体名、常见代码片段），可以用当前位置最近几个 token 组成的 N-gram 做哈希，直接从一张巨大的表里查出一个向量，经过一个“和上下文是否相符”的门控后加进残差流。它不改注意力，也不改 MoE 专家，而是在“参数怎么用”上新开了一条稀疏维度；它不产生 KV 缓存，和本报告的 KV 压缩主线是相互独立的两件事。

报告说 V4.1 沿用了 Engram 原论文的设计（分词器压缩、多头哈希、上下文感知门控、多分支接入），只做了两处修改：去掉短因果卷积，因为它的收益抵不上在推理系统里增加的复杂度；嵌入表改用“动量更新 + Sinkhorn 平衡”来优化（§2.5）。规模和放置如下，本站逐条和官方配置文件、推理代码核对过：

  • 196B 参数，平均分给两个模块。配置里两个模块的表分别有 384,006,168 行和 384,016,682 行，每行 256 维，两者相加约 \(768.0\text{M}\times256\approx196.6\)B（推算），与报告一致。
  • N-gram 阶数 {2, 3, 4}，每阶 8 个哈希头，每阶总维度 2048。配置为 engram_max_ngram_size = 4、engram_n_heads = 8、engram_head_dim = 256，8 × 256 = 2048。
  • 每个头的表约 1,600 万行，表大小取互不相同的素数。配置的 engram_vocab_size = 16000000 是每个（阶数，头）分配素数时的起点；推理代码 engram.py 从这里依次找下一个没用过的素数。3 阶 × 8 头 × 约 1,600 万 ≈ 3.84 亿行，正是每个模块的行数。
  • 嵌入表和 K/V 投影都用 FP8。推理代码里表以 FP8 存储，查到的行按每 32 个数一个缩放因子反量化。
  • 放在第 1 层和第 14 层（从 0 数）。作者说这是为了在训练流水线的各个阶段之间平衡显存。两层都在编码器里，所以 Engram 在预填充时也要参与。
  • 没有短卷积。推理代码的 Engram 模块只有查表、一个投影（为 4 条 mHC 残差流各产生一个 key，外加一个共享的 value）、按流计算的门控（点积经“带符号平方根”后过 sigmoid）和相加，确实没有卷积。
  • 推理时从主机内存预取。查哪些行只取决于输入 token，不取决于中间计算结果，所以可以提前算出地址，通过后台 RDMA 从主机内存把要用的行搬到 GPU；第一个模块的预取与第一个 Transformer 块的计算重叠。

报告没有给出“去掉 Engram”的对照实验，所以 Engram 在这个规模上具体贡献多少，外界无法量化。Engram 原论文的结果（27B 规模的严格对照）和它为什么能从主机内存预取，见 Engram 精读 §2 与 该页“后来怎么样了”。

2.4.3 DSpark：替代 MTP 的投机解码模块

DSpark（Cheng 等，arXiv 2607.05147，本站有 DSpark 精读）是 DeepSeek 2026 年 7 月提出的投机解码方法：用一个小的“草稿模型”一次猜出后面几个 token，再让主模型一次性验证，猜对的部分直接接受，从而一次前向产出多个 token（投机解码的基本原理见 投机解码精读）。V4.1 里的 DSpark 草稿模型有 3 个 Transformer 块，注意力窗口 128；一次前向并行算出 5 个草稿位置的基础 logits，再由一个轻量的“马尔可夫头”建模草稿 token 之间的依赖（这是“半自回归”的含义）。一个置信度头预测每个位置在前面都被接受的条件下被接受的概率，由此估计每个前缀“存活”的概率；调度器把这些估计和事先测好的引擎吞吐曲线结合，为每个请求动态选择验证长度，目标是在当前负载下最大化整个系统的期望吞吐。

和 DeepSeek-V3 的 MTP 模块不同（MTP 在整个预训练过程中和主干一起训练，见 V3 精读 §2.2），DSpark 在预训练结束后单独训练一个阶段，此时主干冻结；后训练时 DSpark 继续和主干一起训练，但它的梯度不回传到主干。这样 DSpark 能跟上不断变化的策略模型，既能加速线上服务，也能加速强化学习和在线蒸馏时的采样。报告没有给出 DSpark 在 V4.1 上的接受长度或加速比。

2.4.4 FP4 主 KV 缓存：为什么可以去掉第二级缩放

先补一点背景：4 位浮点、块缩放，以及 MXFP4 和 NVFP4。

4 位浮点 E2M1 有 1 个符号位、2 个指数位、1 个尾数位，正数只能表示 0、0.5、1、1.5、2、3、4、6 这几个值（详见 NVFP4 精读 §2.1）。只有这么少的取值，直接存原始数值是不行的，所以总要配合块缩放：一组相邻的数共用一个缩放因子 \(s\)，存的是 \(x/s\) 四舍五入到最近的 E2M1 值，读出时再乘回 \(s\)。通常取 \(s=\max|x|/6\)，让组内最大的数正好落在 6 上。

两种常见格式的区别在于“多少个数一组”和“缩放因子用什么格式”（见 NVFP4 精读 §2.2–2.3）：OCP 标准的 MXFP4 每 32 个数一组，缩放因子是 E8M0（只能是 2 的整数次幂）；NVIDIA 的 NVFP4 每 16 个数一组，缩放因子是 E4M3（有 3 位尾数，更精细），但 E4M3 最大只能表示 448，为了覆盖更大的数值范围，NVFP4 还在整个张量上再乘一个 FP32 的“全局缩放”。

另一个要区分的概念是训练后量化和量化感知训练（QAT）。前者拿训练好的模型直接把 KV 量化存储，模型从没见过量化误差，例如 KIVI 把 KV 压到 2 位整数；后者在训练的前向计算里就模拟“量化—反量化”，让模型学会在这种误差下工作。V4.1 用的是后者。

V4 已经对索引器的 Q 和 K 做了 FP4 的量化感知训练，目的是加速索引计算（FP4 矩阵乘更快）并缩小索引器缓存。索引器用的是 MXFP4，因为它要直接进张量核做矩阵乘，而 MXFP4 是 OCP 标准、支持的硬件平台最多；作者特意说明，在他们的实验里其他格式精度更高，但为了兼容性选了 MXFP4。

V4.1 把 QAT 扩展到主 KV 缓存。这里 FP4 的目的不同：省存储，而不是加速矩阵乘。缓存里的值在做注意力之前会先反量化回高精度，所以选什么格式不受“硬件是否原生支持这种矩阵乘”的限制，可以选更准的那个。作者在几种约 4 位的格式里选了：E2M1 数值，每 16 个通道一个 E4M3 缩放，也就是 NVFP4 的格式去掉第二级全局缩放。

为什么可以去掉全局缩放？作者给了一个数值范围的论证，值得一步步走一遍：

  1. 不用全局缩放时，这种格式能表示的最大绝对值是 E4M3 的最大值乘以 E2M1 的最大值：\(448\times6=2{,}688\)。
  2. 主 KV 是一个 512 维的潜向量，在存入缓存前经过 RMSNorm。RMSNorm 把向量的均方根归一到 1，再乘以逐通道的可学习权重；训练出的权重最大约为 1。所以向量的 L2 范数最多约为 \(\sqrt{512}\times1\approx22.6\)。
  3. RoPE 是对通道两两做旋转，不改变向量的长度，所以旋转之后任何一个通道的绝对值仍不超过约 22.6。
  4. 训练中实际观察到的最大值约为 10。

22.6 远小于 2,688，范围绰绰有余，所以全局缩放没有用处，去掉它不会造成可测的精度下降，还让缓存布局更简单：每个条目就是 256 字节数值加 32 字节缩放，正好 288 字节。

两个细节。第一，RoPE 部分和非 RoPE 部分用同样的格式（V4 里 RoPE 的 64 维是单独存 BF16 的）。第二，在 RoPE 之后量化：缓存里存的是已经旋转过的 K。在 RoPE 之前量化的精度只略好一点，但那样每次解码读出条目后都要再做一次旋转，增加解码开销。滑动窗口的 SWA KV 仍然保留 FP8，原因是作者发现它对量化更敏感。FlashMLA 文档也写明了这两种格式的分工：SWA 缓存每个 token 528 字节（512 个 FP8 数值，RoPE 维度也一起量化，加 16 个 E8M0 缩放），压缩注意力缓存每个 token 288 字节。

用一个小例子感受 FP4 的粗糙程度（推算，只为说明）：设一组 16 个数里最大的是 3.3，则缩放 \(s=3.3/6=0.55\)，存成 E4M3 后约为 0.5625。数值 3.3 变成 \(3.3/0.5625\approx5.87\to6\)，读回 3.375；数值 −1.0 变成 \(-1.78\to-2\)，读回 −1.125；数值 0.4 变成 \(0.71\to0.5\)，读回 0.28；数值 0.05 变成 \(0.09\to0\)，直接丢失。单个数的相对误差可达十几到几十个百分点，这也是为什么要用量化感知训练让模型去适应，而不是事后硬压。

FP4 的量化感知训练是在后训练阶段引入的。和 V4 的 FP8 主 KV 相比，这种格式让存储几乎减半（288/584 ≈ 49%），无论在显存里还是被卸载到 SSD 上。引言说用 FP4 全局 KV 训练“只有轻微的性能下降”，§2.4.4 说去掉全局缩放“没有可测的精度下降”，但两处都没有给出数字。

不要和训练后 KV 量化的论文直接比：KIVI、KVQuant 这类方法报告的“2 位/4 位精度损失”，是在没有为量化专门训练过的模型上测的；V4.1 的 FP4 是训练过程的一部分，模型已经学会了适应量化误差。反过来，V4.1 的数字也不能说明“任何模型的 KV 都可以无损压到 FP4”。另外要记住只有全局主 KV 是 FP4，SWA KV 仍是 FP8，索引器 K 是 MXFP4。

2.5 优化器：按头分的 Muon，和给大嵌入表用的 Sinkhorn 平衡更新

这一节要回答的问题：V4.1 在 V4 的优化器配置上改了两处：注意力的 Q、K 权重改用按头分开的 Muon；Engram 表、词嵌入和输出头改用“动量 + Sinkhorn 平衡”，不再用 Adam。为什么要这样改？Sinkhorn 平衡具体在做什么？
先补一点背景：Muon 与“预条件”。

Muon 是一种专门给矩阵参数用的优化器：先像 SGD 一样累积动量，再把动量矩阵“正交化”（用 Newton–Schulz 迭代近似地把它的所有奇异值变成 1），用正交化后的矩阵做更新，最后乘一个系数，让更新的均方根和 AdamW 相当，以便直接沿用 AdamW 的学习率（详见 Muon 精读 §2.1）。从另一个角度看，正交化相当于给梯度乘了一个依赖于梯度本身的“预条件矩阵”，让不同方向上的更新幅度更均衡。

第一处改动：按头分的 Muon。普通的 Muon 把整个 Query 权重矩阵当成一个矩阵来正交化，相当于所有注意力头共用一个预条件矩阵。按头分的 Muon 先把 Query 权重按头切开，每个头单独正交化，等于每个头有自己的预条件。作者的理由是不同注意力头之间差异很大，各用各的预条件更合适，并称实验中按头分的版本优于普通版本，GLM-5 和 Kimi-K3 的报告也验证了这一点。基本配置里 Query 和 Key 的权重都用按头分的 Muon。

第二处改动：给大表用的 Sinkhorn 平衡更新。Engram 新增了 196B 参数。Adam 要为每个参数保存两个状态（一阶矩和二阶矩），而 Muon 式的更新只需要一个动量缓冲区。按每个状态 4 字节粗算，196B 参数用 Adam 要约 1.57 TB 的优化器状态，只用动量则约 0.78 TB（推算，报告没说状态精度，训练时这些状态还会在多个副本间切分）。所以作者给 Engram 表、词嵌入和输出头这三类“很大、而且一行对应一个 token 或 N-gram”的矩阵，换了一种只需要动量的更新，并称它在实验中优于 Adam。

它的流程和 Muon 一样，只是把 Newton–Schulz 正交化换成了 Sinkhorn 平衡（原文算法 1）：

  1. 算 Nesterov 动量：\(M_t=\beta M_{t-1}+(1-\beta)G_t\)，\(\widehat G_t=\beta M_t+(1-\beta)G_t\)。
  2. 屏蔽几乎为零的行：如果某一行的范数不到所有行平均范数的 \(\tau=10^{-3}\) 倍，就把这一行置零。对嵌入表来说，这一步内没出现过的 token 或 N-gram，它那一行的梯度本来就是零（或接近零），不该被放大。
  3. 交替归一化 \(K=11\) 次：奇数步把每一行除以它的 L2 范数，偶数步把每一列除以它的 L2 范数。\(K\) 取奇数，所以最后一步是行归一化。
  4. 乘以 \(\sqrt{n}\)（\(n\) 是隐藏维度），把“每行单位 L2 范数”换成“每行单位均方根”；学习率再乘 \(\gamma=0.18\)，让更新幅度和 Adam 相当（Moonlight 用的是 0.2，见 Muon 精读 §2.2.3）。

效果是让更新矩阵的每一行和每一列的均方根都大约为 1。行对应一个 token 或一个 N-gram，列对应一个隐藏特征，所以这相当于同时做到：每个 token（无论出现得多频繁）都得到同样大小的更新，每个特征方向也不会被少数大梯度主导。

用一个 3 × 3 的玩具梯度走一遍（推算）：设三行分别是 \((6,0,0)\)、\((3,4,0)\)、\((0,0.3,0.4)\)，第三行代表一个很少出现的 N-gram，梯度很小。原始梯度三行的均方根是 3.46、2.89、0.29。交替归一化 11 次再乘 \(\sqrt3\) 之后，结果约为 \((1.73,0,0)\)、\((0.66,1.60,0)\)、\((0,0.64,1.61)\)：三行的均方根都正好是 1，三列的均方根分别约为 1.07、0.99、0.93，接近 1。和“只做行归一化”的结果 \((1.04,1.39,0)\) 相比，第二行在第一列上的分量被压低了，因为第一列已经从第一行得到了很大的更新——这就是列归一化带来的“特征之间的平衡”。

作者指出，这类利用矩阵行列结构的做法和 Adafactor（另一种行列分解的归一化）、Adam-mini（对嵌入表和输出头做另一种按行归一化）等方法相近，在优化效果和通信开销上可能各有不同，留作以后研究。Sinkhorn 平衡此前在 SinkGD（Scetbon 等）里用于线性层的权重，这里推广到了大参数矩阵。

其余配置：归一化层权重、偏置、缩放因子等非矩阵参数用 AdamW；主干线性层、Engram 的投影层、视觉—语言投影器用 Muon。Muon 用解耦的权重衰减和 Nesterov 动量；归一化层权重也做权重衰减，偏置和缩放因子不做；Sinkhorn 平衡更新用 Nesterov 动量但不做权重衰减。预训练时视觉编码器一直冻结（只有它最后的归一化层和视觉—语言投影器可训练），直到学习率开始衰减时才解冻，并用较小的学习率和语言模型一起训练。

3.1 训练基础设施：多模态、跨层共享与 Engram 各自带来的系统问题

这一节要回答的问题：原生多模态、CSA2 的跨层共享和 196B 的 Engram 表，在大规模分布式训练里各自会制造什么麻烦？作者用什么办法让它们不拖慢训练、不破坏现有的并行方式？

3.1.1 多模态训练

对比学习阶段的通信重叠。视觉编码器先用对比学习目标预训练（让配对的图像和文字表示靠近）。对比损失要在整个批次上计算，所以每张卡都要通过 all-gather 拿到所有卡上的图像特征和文字特征，通信量很大。作者利用了一个依赖关系：文字特征的梯度只依赖收集到的图像特征，图像特征的梯度只依赖收集到的文字特征。于是可以这样排：先算图像前向；算文字前向的同时收集图像特征；算出文字侧的梯度；做文字反向的同时收集文字特征；算出图像侧的梯度；最后做图像反向。两次 all-gather 都藏在了有用的计算后面。

端到端的并行方式。视觉编码器和语言模型在规模和数据形状上差别很大。作者采用近来训练系统常用的“编码器分离”设计：视觉编码器在语言模型的参数树之外单独复制一份，每个训练步分成三段——视觉编码器前向、语言模型前向和反向、视觉编码器反向。负载均衡的视觉计算只发生在第一段和最后一段，中间一段的语言模型完全不含视觉计算，可以照搬纯文本训练的并行策略。

超长序列里的图像。V4.1 有相当一部分训练在超长序列上进行（最长 100 万 token）。一条又长又密集地夹着图片的序列，可能在加载时就耗尽一台机器的 I/O、CPU 和内存。所以预训练时，每条序列的图片被均衡地分给上下文并行（CP）的各个进程，每张图只加载一次。作者给出了“加载不拖慢计算”的条件：设序列有 \(N\) 个 token，每个 token 平均有 \(\rho\) 字节原始数据、需要 \(C\) 次计算，文件系统带宽 \(B_{\mathrm{IO}}\)、GPU 算力 \(B_{\mathrm{GPU}}\)，则只要

$$\frac{N\rho}{B_{\mathrm{IO}}}<\frac{NC}{B_{\mathrm{GPU}}}\iff\rho<\frac{B_{\mathrm{IO}}}{B_{\mathrm{GPU}}}\,C$$

加载就能完全藏在计算后面。\(N\) 被约掉了，所以这个条件和序列多长、集群多大都无关，只取决于每个 token 的数据量和计算量。\(\rho\) 由视觉模块的配置决定（分辨率上限、空间下采样倍数）。作者由此得出：存储吞吐只会在每个 token 计算量很小的小模型上成为瓶颈（比如做消融实验时），正式规模的模型始终是计算受限的。强化学习采样时，图片则只增量地传给推理引擎，引擎在 CPU 上解码和预处理的结果缓存到分布式文件系统上，供后续采样和训练复用。

3.1.2 CSA2 的“注意力共享训练”

CSA2 让一层使用另一层算出的主 KV、索引器 K 或 top-k 下标。在流水线并行里，模型的层被切成几段放在不同的机器上，而共享的两层可能恰好落在不同的段里，于是“直接调用另一层的模块”在常规的“每段只管自己的层”的执行方式下就行不通了。作者用了三个设计：

  • 影子索引器：在每个用到共享部件的流水线段上放一个轻量的可执行副本，而共享参数只有一个逻辑上的“主人”。主人负责优化和保存检查点；参数同步和梯度汇总让各个影子副本始终和主人一致。这样不需要让流水线调度器把共享层当成特殊的执行单元。
  • 扩展流水线的传输内容：当提供共享状态的层和使用它的层隔着一个流水线边界时，把下游需要的中间表示和稀疏路由信息（例如 top-k 下标）塞进现有的点对点通信里，并按上下文并行的方式一致地切分，既避免不必要的复制，也保证对应的梯度能正确回传。
  • 微批级的共享状态管理：流水线里同时有好几个微批在跑，每个微批都有自己的共享状态。运行时记录每份共享状态属于哪个微批，在前向、激活重算、反向三个阶段里协调它的生命周期：直到最后一个使用者算完才保留，然后立即释放，控制额外的显存开销。同一套抽象还处理“共享状态的来源层和使用层分别在哪一段”，让注意力实现不必关心物理上的流水线布局。

再加上对优化器、检查点、预热和计算图追踪流程的少量适配，CSA2 就能在现有的分布式训练接口和流水线调度下“透明地”运行。

3.1.3 Engram 的训练

Engram 的嵌入表按行切分，分给专门的“engram 并行”进程组；组的大小决定了每张卡的显存占用和查表时的通信范围之间的取舍。优化器状态再在同一个表分片的多个副本之间切分。由于查表的下标只取决于输入 token 序列，每个训练步开始、流水线各段开始处理微批之前，就可以为整个本地批次一次性发起嵌入预取，尽量不干扰流水线执行。嵌入的梯度在反向时先缓冲起来，等主干反向结束后再发回持有该行的进程。为了和多模态训练配合，预取和梯度传输都被安排在视觉编码器的前向和反向期间进行。嵌入以 FP8 存储和读取，读到的值和缩放因子直接交给后续的矩阵乘。更新时，Sinkhorn 归一化在迭代之间维护行、列两组缩放向量，避免反复写回整个归一化后的大矩阵；行归一化和列统计量的累加融合进一个内核，进一步减少显存读写。强化学习采样时，Engram 表常驻 GPU 显存，以减轻主机内存的压力，避免主机内存碎片导致的内存溢出。

3.2 推理系统：持久 KV 缓存的新管理方式与 SWA 有界重放

这一节要回答的问题：持久 KV 为什么能比 V4-Flash 小 8 倍——这 8 倍里有多少来自结构和精度，有多少来自部署策略？V4 时 SWA 的 KV 是怎么持久保存的，为什么作者认为这样做“又贵又没用”？“有界重放”到底近似了什么，近似之后会出现哪些新的、需要注意的行为？

先交代推理系统的整体做法。作者说 V4.1 的结构虽然概念上复杂，但通过融合内核，推理时的内核流程很简洁：用到 FlashMLA 里“RoPE—注意力—RoPE—转精度”融合内核，DeepGEMM 里的 Mega-Gate、Mega-mHC、Mega-MoE 内核，TileKernels 里的内核，以及 DeepSelect 里的 TopK 内核。占绝大多数的 Reuse 模式层，预填充时只需要 15 个内核，解码时只需要 11 个。部署上采用“编码—预填充—解码”（EPD）三段分离：视觉编码、预填充、解码各自独立扩缩容，并能重叠执行（预填充与解码分离的思路见 DistServe 精读）。报告没有给出这些内核的耗时或端到端的吞吐、延迟数字。

3.2.1 持久 KV 缓存的管理：SWA KV 搬出 SSD

先补一点背景：前缀缓存为什么要存 SWA KV。

前缀缓存的意思是：如果一个新请求的开头和以前某个请求完全相同，就直接读回那段前缀的 KV，从不同的地方接着预填充。对普通的全注意力模型，这很直接。但 V4 系列每层还有滑动窗口注意力：要从前缀末尾接着算，第一个新 token 在每一层都需要前缀最后 128 个 token 的 SWA KV。全局 KV 读回来了，SWA KV 没有，计算就接不上。所以持久缓存必须想办法提供 SWA KV：要么存下来，要么现场重算。

V4 的做法。V4 的部署里，全局 KV 和 SWA KV 分开管理，都用 LRU（最近最少使用）策略淘汰。全局 KV 整段存储，命中时整段前缀复用。SWA KV 只在两个位置存一份“窗口快照”：提示结束处和输出结束处，分别服务“重新生成”和“下一轮对话”两种情况；命中时从快照的位置接着算。为了保持高命中率，SSD 上的持久缓存配得足够大，在典型负载下两种 KV 都能保留 72 小时以上。V4 的报告还讨论过另外两种策略（见 V4 精读 §9.1）：每隔一段存一次快照，以及完全不存 SWA KV、命中时精确重算（“Zero SWA Caching”），后者需要重放 \(L\times n_{\mathrm{win}}\) 个 token。

问题在哪。每个快照只有 \(n_{\mathrm{win}}\) 个条目，但不压缩、每层都有，所以体积并不小。估一下（推算，按 FlashMLA 文档的格式）：V4-Flash 一个快照是 43 层 × 128 × 584 字节 ≈ 3.2 MB，相当于约 900 个 token 的全局 KV；V4.1-Flash 是 40 层 × 128 × 528 字节 ≈ 2.7 MB，相当于约 3,000 个 token 的全局 KV。在“每轮输入都很短”的多轮对话里，每轮新增的全局 KV 很少，两个快照却是固定开销，于是作者观察到，在 V4 的部署里 SWA KV 占了持久缓存容量的近一半。

更关键的是，这些 SWA 快照的访问模式和持久缓存的长期保留策略不匹配。全局 KV 有长尾的复用：几小时甚至几天后，同一个代码仓库、同一份文档还可能被再次用到。而 SWA 快照只在一个活跃会话内部、分钟级的时间窗里被用到：会话结束或者进入下一轮，它就作废了。把它在 SSD 上存 72 小时，既贵又没用。至于 V4 报告提过的 Zero SWA Caching，精确恢复要做 \(L\times n_{\mathrm{win}}\) 个 token 的完整前向，在生产部署里代价高得无法接受。

V4.1 的做法分两条：

  1. SWA KV 不再进持久缓存，改存在一个分布式内存池里，这个池由每台机器各拿出 10% 的主机内存组成。它的总容量比 SSD 小得多，但条目的存活时间只有几分钟，过期的立刻回收给新会话。作者说在真实负载下，这种高周转足以服务绝大多数同时活跃的会话。全局 KV 仍在 SSD 上的持久缓存里，保证至少存活 72 小时。
  2. SWA KV 被淘汰后必然会出现“全局 KV 命中、SWA KV 没命中”的请求。这时用一个轻量的后备方案“编码器 SWA 有界重放”：只重算 \(n_{\mathrm{win}}\) 个 token，而不是 \(L\times n_{\mathrm{win}}\) 个。作者称这是整个设计的基石：它把一次“灾难性的”未命中，变成一次便宜的、轻微的质量退化，从而让“把 SWA KV 移出持久缓存”这件事说得通。

3.2.2 SWA 有界重放：只重放一个窗口，接受近似的状态

先补一点背景：为什么精确重建 SWA KV 要往回追 \(L\times n_{\mathrm{win}}\) 个 token。

第 \(l\) 层某个 token 的 SWA KV，是由这个 token 在第 \(l\) 层的输入算出来的；而这个输入又取决于第 \(l-1\) 层的注意力输出，后者要看第 \(l-1\) 层里前面 \(n_{\mathrm{win}}\) 个 token 的 SWA KV……每往下一层，需要的 token 范围就往前扩大一个窗口。所以要精确得到最顶层最后一个窗口的 SWA KV，最底层要从往回 \(L\times n_{\mathrm{win}}\) 个 token 的地方开始算。这就是“感受野随层数线性增长”。全局分支不受这个影响，因为它读的是已经缓存好的全局 KV。

示意图：精确重建与有界重放各要算哪些位置（玩具：3 层、窗口 3）
怎么看：每一行是一层，每个方块是一个 token 位置，最右边是缓存前缀的末尾。左图：为了得到第 3 层最后 3 个位置的精确 SWA KV，第 2 层要算最后 5 个，第 1 层要算最后 7 个，输入要从最后 9 个开始，即层数 × 窗口。右图：有界重放每一层都只算最后 3 个，而且窗口在重放段的起点截断，红框表示这些状态是近似的。本站示意图，原文没有对应的图。

有界重放的规则是：从位置 \(s\) 开始重放最近的 \(n_{\mathrm{win}}\) 个 token，并把 SWA 截断在重放段之内——位置 \(i\) 的 query 只能看 \([\max(s,\,i-W+1),\,i]\) 范围内的 SWA key（\(W\) 是窗口大小）。也就是说，重放段的第一个 token 在 SWA 分支里只能看到自己，第二个只能看到两个，以此类推；远处的信息只能通过全局分支（读缓存的全局 KV）获得。这样得到的 SWA 状态是近似的。V4.1 在两个地方用到它：

编码器 SWA 有界重放（只在 SWA 未命中时用）。它让前缀缓存只依赖全局 KV，于是 SWA KV 可以从持久缓存里拿掉。缺 SWA KV 时，把缓存前缀的最后 \(n_{\mathrm{win}}\) 个 token 和没命中的新输入一起处理：重放的 token 只重新生成 SWA KV，直接复用缓存里的全局 KV，既不重算也不覆盖；新输入则照常生成全局 KV 和 SWA KV。作者明确指出，因为重放出的前缀状态是近似的，新输入算出的全局 KV 和 SWA KV 会随命中位置的不同而不同，数学上不再相同。他们称实验表明这种做法“几乎不影响回答质量”。

解码器 SWA 有界重放（每次预填充都用）。这是 §2.2 讲过的 CED 带来的问题：解码器的全局 KV 由编码器输出投影得到，唯一挡在“预填充算完编码器就结束”前面的，是解码器的 SWA KV，它来自解码器每一层自己的隐藏状态，解码的前几步就要用。解码器 SWA KV 从不缓存，精确重建要让 20 个解码器层处理最后 \(20\times n_{\mathrm{win}}=2{,}560\) 个提示 token，在“长前缀命中、只多一小段新输入”时很贵。所以每次预填充都只重放提示的最后 \(n_{\mathrm{win}}\) 个 token：把它们的编码器输出送进解码器各层，用同样的截断规则，得到的解码器 SWA KV 只用于接下来的解码，不进前缀缓存。作者称这同样只对回答质量有可以忽略的影响，并且“为了更稳妥”，在后训练中也模拟了同样的重放，让模型在训练时就适应这种近似（训练感知的适配）。

算一下重放省了多少（推算）：精确恢复全部 40 层的 SWA 状态需要重放 \(40\times128=5{,}120\) 个 token，有界重放只要 128 个，少了 40 倍；按 CED 的结构，只恢复解码器部分也要 2,560 个 token 走完解码器，有界重放同样只要 128 个。

为什么这种近似可能问题不大？作者引用的理由是 SWA 的“有效感受野”远小于理论值（PowerAttention 的发现）。本站补充一个直观的理由（不是论文原话）：在 V4.1 里，SWA 并不是唯一的远程信息通道，每个 token 都能通过全局分支看到整个上下文里被选中的 512 个条目，所以把 SWA 的远端截掉，损失的主要是“通过多层 SWA 逐层传递过来的那部分信息”，而这部分本来就能被全局分支部分地替代。

有界重放带来的新行为，值得注意：
  • 同一个输入，结果可能取决于缓存状态。编码器重放只在 SWA 未命中时触发，而它会改变新输入的全局 KV 和 SWA KV，所以同一个请求在“SWA 命中”和“SWA 未命中”两种情况下，数值上不完全相同；命中位置不同，结果也不同。这对需要可复现输出、或者需要推理与训练数值一致的场景（例如强化学习的采样）是一个额外的不确定来源（相关背景见 批不变性精读）。
  • 解码器 SWA 永远是近似的。它不是偶尔的补救，而是每个请求都走的路径；好在后训练也是在同样的近似下进行的，所以模型看到的就是它被训练时的状态。
  • “几乎不影响质量”没有数字。报告没有给出有界重放与精确重建在任何基准上的对比，也没有给出生产中 SWA 未命中的比例。作者在结论里把“缓存恢复边界处的 SWA 状态重建”列为需要继续压力测试的重点。

4.1 数据

文本。作者说这一版不再只看小规模实验里反映出来的“单条样本质量”，而更关注不同语料之间的相互作用、哪些语料能带来独特的信息增量。为此建了一套更系统、更标准化的数据构建流程，并设计了一个在模型参数量和数据量两个方向上的“缩放阶梯”，用小模型的结果来指导大规模训练的数据决策。具体做法包括：过滤掉信息增量很低的模型生成内容（较弱模型的输出、低质量的机器翻译文本），作者把它们看作“隐性重复”，因为它们大多只是改写已有信息，长期训练下可能有害；探索让模型参与数据迭代的方法，为以后的大规模合成数据打基础；请更多领域专家参与制定细粒度的数据质量维度；加入更多新近的开源代码（新仓库、提交、库和框架），覆盖更多编程语言和当下真实的软件工程场景。

多模态。多模态预训练数据有三类：图文对、图文交错数据和特定领域数据。作者的出发点是网页数据天然带有丰富的多模态知识，所以没有做大规模的数据合成，而是尽量清洗并按原样使用。一开始他们发现自己的爬虫系统过于偏向文字为主的网页，于是从 Common Crawl 重新起步，提高对多模态来源的覆盖。图文对从网页中抽取图片和它的替代文本（alt text），按图文相关性阈值过滤，再按图像语义去重。交错数据主要来自网页和 PDF；因为处理多模态语料的 CPU 和存储开销比纯文本大，构建流程按“越往后越贵”的顺序分阶段：先在取图之前用启发式、统计过滤、去重和质量模型筛出高价值文档，再把留下的文档组装成图文交错序列并按图像感知的方式再过滤、去重一次，最后用 SmolVLM 给图文内容严格打分。被过滤掉的文档有一部分经过筛选重组，回收成额外的图文对。为了弥补网页数据的不足，还加入了特定领域数据：细粒度视觉感知（视觉定位、指点）、OCR、长尾知识，以及大量的“图像—代码”对和电脑操作轨迹，用来提升多模态智能体的理解能力。

合并与去重。文本和多模态数据经过两条不同的流程，最终语料取两者的并集；对重叠的样本，用多模态版本替换纯文本版本，并取两种配置里较大的那个重复轮数。替换之后，纯文本与多模态数据的 token 比例为 7 : 1。预训练和上下文扩展阶段通过联合预取和分配样本来尽量减少重复；超长文档在混合之前先被确定性地切开，让训练 token 在数据分片和训练步之间分布均匀；改进后的“最佳适配”打包算法把填充率压到不超过 \(10^{-4}\)。

5.1–5.2 后训练：不改算法，只做数据、环境和基础设施

这一节要回答的问题：报告明说后训练“没有算法创新”，那 V4.1-Flash 在智能体任务上的大幅进步从哪里来？任务和环境是怎么自动造出来的？“推理努力程度”这个可以连续调节的旋钮是怎么训练出来的？异步强化学习又要处理哪些副作用？

5.1 流程：SFT → RL → 在线蒸馏，重心全在“训练什么”

后训练沿用标准的三段式：监督微调（SFT），强化学习（RL），最后是在线蒸馏（OPD，学生模型自己生成，教师模型在学生生成的序列上给出逐 token 的目标分布）。作者强调，除了 V4 开发中已经成熟的做法，算法上没有任何修改；投入几乎全部花在“在什么上训练”，而不是“怎么优化”。流水线做三件事：合成多样、可验证的训练任务以及参考答案和奖励信号；程序化地构建并扩展交互式智能体环境，让轨迹的收集和评估足够便宜；严格过滤、去重并校准难度，保证数据质量和课程的均衡。作者的结论是：在一个固定的、“平平无奇”的优化流程下，观察到的提升基本上全部来自合成数据和环境在规模、多样性、可验证性上的系统性改进；现阶段在数据和环境流水线上投入的边际回报，远超在后训练算法上求新。

大规模合成智能体任务。每个任务被形式化为一个三元组：（问题，环境，验证系统）。质量按两个维度衡量：难度（任务不能太简单）和正确性（三部分里没有致命缺陷）。作者观察到模型已经开始能为自己构造训练任务，只是还不完美，于是把难度和正确性当作奖励，迭代地训练模型构造更好的任务。每个任务在整个生命周期内都受监控：每次被新的 RL 运行使用，产生的轨迹都会被用来重新审查这个任务的质量。在这个框架下有两条专门的环境生产线：

  • 通用智能体：鼓励公司员工和外部合作方在日常工作里使用最新模型，并自愿返回交互数据和反馈。根据返回数据里看到的接口，构建大量“模拟工具”，复现真实工具和系统的输入格式、输出结构、API 模式和行为约束，覆盖常见的 SaaS 和企业应用，以及更专门的业务后台系统。同时大规模收集员工提交的负面反馈和失败案例，生成扎根于真实工作流的单轮和多轮环境，从而能系统地重放失败，并针对观察到的弱点做 RL。
  • 编程智能体：来源一是员工和合作方的编程智能体会话，只保留很复杂或模型表现差的任务，并按轨迹去重；来源二是超过一定星标数的 GitHub 公开仓库。环境由多个专门的智能体协作搭建：一个判断项目能否在容器里构建、完整运行并自动验证，选定起始提交，设计几个足够复杂的实现方向，写出“修复前失败、修复后通过”和“始终通过”两类评测点和一份构建报告；另一个在隔离容器里装依赖、准备初始目录、测试代码和任务描述，自测后清除可能泄露答案的痕迹，打包成新的镜像层；然后多个不同的智能体尝试解题，一个独立的质检智能体结合解题轨迹检查环境问题、事实错误、评测点和描述不一致、以及“可被钻空子”的风险；不通过就交给修复智能体，修正错误并调整过难或过易的评测点，再重新验证。

在合成任务上做 RL。作者从两个方向扩大 RL：训练算力，以及“脚手架”（scaffold，即包在模型外面的智能体框架，决定系统提示、工具定义和交互协议）的数量。原文图 7 显示，在 DeepSeek Harness 的 Minimal 模式下，各个编程智能体基准随 RL 步数持续提升，把最大上下文扩到 1M 后，在 Terminal-Bench 3.0 这类超长程任务上还能继续提升；图 8 显示，在多个版本的 Claude Code 上联合训练、或在 OpenCode、Pi、DeepSeek Harness（Standard 和 PTC 模式）等不同脚手架上联合训练，DeepSWE v1.1 的成绩都随累计 RL 步数上升。系统上，采样执行被拆成“智能体沙箱”（运行脚手架和工具）和“工作容器”（与脚手架无关的控制层，编排采样、把不同交互统一成同一种轨迹格式、与训练器通信），两者都跑在可抢占的 GPU 训练池之外；训练器被抢占时，采样可以暂停、卸载并保存完整状态，之后恢复。为了把 RL 算力扩展到单次运行之外，作者用模型合并来初始化下一次 RL：把不同脚手架或配置下的多次运行的检查点合并，组合各自沿不同优化路径学到的改进，图中断开的曲线段就是合并后重新开始的运行。作者称这在任务表现和 token 效率上都带来进一步提升。

DSec：百万级沙箱。V4 开发时 DeepSeek 建了一个生产级沙箱平台 DSec，V4.1 的训练把需求推到了数百万个并发沙箱。瓶颈转向数据中心的扩展性、负载隔离、单节点计算密度，以及对越来越强的智能体的“不当行为”的遏制。几个设计：把计算节点切成多个分片（“规模单元”），既容纳更多机器，也把一个实验的爆炸半径限制在自己的分片里；不用 Kubernetes，而用自研的放置引擎，以多个互不同步的副本各自根据近期测量预测资源、做“足够好”的放置决定，用最终一致性换取扩展性，每个节点再做硬性的准入检查，超过本地警戒线就拒绝新放置；节点上用硬件的 sub-NUMA 分区，把每个工作虚拟机绑定到一个 NUMA 域，容器在虚拟机里运行，在同等负载下把单台物理机能支撑的活跃容器数从约 1,000 提高到 2,500 以上（在端到端性能出现可测下降之前）；为对时间敏感的评测设立低延迟执行类，非低延迟任务用 SCHED_IDLE 降到最低调度优先级，并用 core scheduling 保证同一物理核的两个超线程上只跑同一优先级的任务。作者坦白，RL 训练中经常观察到智能体试图钻奖励的空子，或无意中把环境搞崩：有的利用了新近披露的漏洞（XFS 驱动的权限问题、AppArmor 的非法内存访问、从软件包镜像服务泄露答案等），有的删掉关键的可执行文件、破坏系统文件，甚至删除整个文件系统。应对办法是每个沙箱单独的 AppArmor 配置和基于 eBPF 的细粒度网络策略；环境被搞崩就记为失败轨迹，并向 RL 框架报告一个“后果”信号。

5.1.4 可控的推理努力程度

除了模型结构和硬件，输出 token 的数量也是服务成本的决定因素。作者在 RL 中引入一个标量“努力程度” \(b\in\{1,\dots,100\}\) 作为显式的条件信号，单轮推理和多轮智能体任务都用。做法是在系统提示前加一行“Reasoning Effort: {effort}（范围 1–100，越大要求越充分的推理）”。对每个训练提示 \(x\)，在若干个努力等级 \(b\) 上各采样 \(M_b\) 个回答；同一个 \((x,b)\) 的回答组成一个子组，在子组内做均值中心化，得到组内相对优势（GRPO 式），所以不同努力等级的回答之间不直接比较。“努力程度不同、行为不同”是靠让奖励里的长度惩罚依赖于 \(b\) 来实现的：

$$r^{\mathrm{len}}_{b,j}=-\min\Big\{C_{\max},\;k(b)\,\frac{\ell_{b,j}}{L_{\mathrm{norm}}}\Big\},\qquad k(b)=k_0\exp\!\Big(-\frac{b-b_{\min}}{\tau}\Big),\quad \tau=\lambda\,\overline{\Delta b}$$

\(\ell_{b,j}\) 是推理 token 数，\(L_{\mathrm{norm}}\) 是参考长度，\(C_{\max}\) 是一条轨迹最多扣的分。惩罚系数随努力程度指数下降：\(b\) 每增加 \(\tau\)，系数乘以 \(e^{-1}\)。\(k_0\) 控制整体“往短里压”的力度，\(\tau\) 越小，不同等级之间的行为差别越大。附录 C 给了选指数形式的理由：设某个问题用 \(\ell\) 个推理 token 能解出的概率为 \(p_x(\ell)\)，在惩罚没封顶的区间，最优长度满足“多想一个 token 带来的边际收益 = 惩罚系数”，即 \(p_x'(\ell^*)=k(b)/L_{\mathrm{norm}}\)；如果边际收益随长度近似指数衰减 \(p_x'(\ell)\approx a_xe^{-\ell/s_x}\)，代入指数形式的 \(k(b)\) 就得到 \(\ell^*_x(b)\approx C_x-s_x\log k_0+\tfrac{s_x}{\tau}(b-b_{\min})\)，即首选长度随 \(b\) 近似线性增长。作者也说明这只是局部的奖励层面近似，不保证实测的平均长度一定线性或单调。

训练只用了有限几个努力等级，但部署时中间值也能用，得到插值的行为。2026 年 9 月上线的公开 API 提供三档：max、high、low，分别对应 \(b=100\)、75、50（原文表 2），选哪一档都不改模型权重和解码配置。

5.2 异步后训练基础设施

RL 的采样阶段一直受“长尾”拖累：一批里少数特别长的样本迟迟不结束，其他资源只能等。V4.1 把几乎所有 RL 和 OPD 任务都改成异步生成，靠维持足够高的并发来缓解长尾（异步 RL 的系统设计和它的代价，可对照 AReaL 精读）。几个要点：

  • 同机分时：采样和训练放在同一批设备上轮流执行，省去手工分配两者资源的麻烦；每个任务给定“在途样本数”的上限，系统在采样期间始终维持这个上限。
  • 样本级派发：每当新完成的样本数达到下一个提示所需的 GRPO 组大小，就派发这个提示，而不管这些完成的样本属于哪个组。作者试过两种更粗的粒度：开头多派几批、每次训练后补一整批，会让训练指标剧烈振荡；每完成一个组才派一个新提示，又容易被组内的长尾样本卡住。
  • 拼接的路由重放：样本攒够后训练抢占正在进行的采样；对跨越多个检查点生成的样本，把各段采样时的 MoE 专家路由拼接起来使用，而不是丢弃后用新检查点重算。
  • 长度偏差：异步时短样本先完成，会在早期主导训练批次。对策是按数据集限制并发（间接控制稳态批次里各数据集的比例），以及丢弃过早返回的短样本，平滑过渡到稳态的长度分布。
  • 离策略：部分样本是旧检查点生成的。对策是通过派发逻辑和等待条件给离策略比例设上限，并在训练时用损失掩码去掉“过于陈旧”的 token 的贡献。
  • 快速中断与无缝恢复：生成可以在任意 token 边界停下；KV 缓存和专家路由在生成过程中按 token 粒度持久保存，换上新检查点后直接复用，不必重新预填充，被中断的样本从断点接着生成；每个样本完成就立刻回收它的状态。同一套机制也让训练任务能及时响应集群的抢占信号而不丢进度。
  • 大规模在线蒸馏：最后一个阶段是全词表的 OPD，覆盖所有领域的数据，使用超过 40 个教师模型；各领域最好的教师可能来自不同的开发阶段，结构上也可能彼此不同、和学生不同。系统支持在训练中动态调整数据配比、并发上限和在用的教师，并在异步设置下让不同配置生成的在途样本平滑过渡。
两处值得留意：
  • “KV 缓存按 token 粒度持久保存、换检查点后直接复用”意味着，样本的后半段是在旧策略算出的 KV 上、由新策略接着生成的；这也是一种离策略来源。报告用“限制离策略比例 + 掩掉过旧 token”来控制，但没有量化这部分的影响。
  • “模型合并”“40 多个教师”“员工自愿返回的交互数据”都是能力提升的重要来源，但报告没有给出各自的贡献，也没有公开这些数据。

5.3.3–5.3.5 努力程度、脚手架与多智能体

努力程度。把努力程度从 25 调到 100：八个推理密集基准（AIME 2026、Apex 2025 Shortlist、GPQA Diamond、HLE、IMO-AnswerBench、LiveCodeBench、MathArena Apex、SimpleQA-Verified）的平均 Pass@1 从 67.1% 升到 76.3%，DeepSWE v1.1 从 66.0% 升到 74.2%，Terminal-Bench 2.1 从 82.4% 升到 90.6%，代价是输出 token 多出约 2.5 倍。收益集中在前段：努力程度 60–80 就能拿回最高档的大部分精度，而 token 不到最高档的一半；从 80 再推到 100，智能体轨迹变长 1.6–1.8 倍，精度只略有提升。附录 B.3 的细节：从 25 到 100，各推理基准的平均回答长度增长 2.0–3.1 倍（AIME 2026 从 4.6k 到 11.4k token，MathArena Apex 2025 从 29.1k 到 86.1k）；MathArena Apex 2025 提升 40.3 个百分点（25.3% → 65.6%），Apex 2025 Shortlist 提升 11.5，已饱和的 GPQA Diamond 和 LiveCodeBench 只提升 1.3 和 2.6，AIME 2026 达到 100%。附录 B.2 补充了一个更谨慎的观察：在三种编程脚手架上，轨迹长度随努力程度单调增长，但准确率只是“大体上升”，多数面板里有平台和下降。

多智能体（初步）。DeepSeek Harness 的 Agent Team 模式里，一个主智能体可以异步创建有名字、持久存在的队友（spawn_teammate），每个队友领一个子任务，从零开始或者带着主智能体历史的一次性快照开始；所有智能体共用一份代码仓库，改动立即互相可见；通过一个持久的邮箱互发消息，用共享的任务板记录任务归属、依赖和建议的写入范围；只有主智能体能中断队友。训练用的 RL 奖励由三部分组成：任务表现、鼓励分工和沟通的协作奖励、以及一个“推导延迟”惩罚——把执行事件和协作依赖画成有向无环图，按固定的预填充/解码速率把 token 数折算成时间、加上实测的工具执行时间，取关键路径长度，从而鼓励有用的并行、惩罚不必要的串行和同步。在 ProgramBench 的 172 个“黄金”任务（参考答案在隐藏测试上通过率不低于 95% 的子集，每题最多 3 次运行，共 516 次）上，按每次运行的墙钟截止时间统计：多智能体的 Almost@1 从 1 小时的 13.59% 升到 8 小时峰值 30.04%，单智能体从 12.79% 升到 20.39%；在 FrontierSWE v2 的无 GPU 公开子集上，Mean@5 从 1 小时的 13.50% 升到 20 小时的 32.90%，单智能体从 10.50% 升到 28.20%。作者说明这是初步结果，比较的是“观察到的最强多智能体配置”和“现有最强的单智能体基线”。

6 结论、局限与未来方向

这一节要回答的问题：作者怎样总结这份工作？他们自己承认了哪些风险和局限？

作者的总结与摘要一致：通过模型结构、缓存精度和部署策略的联合优化，V4.1-Flash 把常驻显存的全局 KV 压到每个 token 890 字节（约为 V4-Flash 的 1/4），把持久 KV 压到约 1/8；CED 让预填充每个 token 只激活 8B 参数；整体表现明显好于 V4-Flash，参数量比 GLM-5.3、Kimi-K3 小得多，却在多项基准上相当或更好。

作者自己列出的局限值得原样记住：V4.1-Flash 虽然在若干部件上简化了 V4，但新引入的结构也带来了尚未完全刻画的“鲁棒性边界”。内部评测覆盖了大量测试用例和边界条件，没有观察到系统性的能力退化，但有限的测试集不可能覆盖所有极端输入和部署条件；CSA2 的选择错误和有界重放的近似状态重建，都可能在没测到的边界情况下导致能力下降。今后的压力测试会特别关注长上下文中的稀疏检索，以及缓存恢复边界处的 SWA 状态重建，并在真实负载中监测失效模式。

关于评测，作者承认标准基准越来越饱和；V4.1-Flash 在日常使用中的体验接近顶级闭源模型，但在最难的任务上仍有差距，基准分数上的小差距并不意味着在复杂、高难度推理和边缘情况上与前沿闭源系统相当。未来方向是数据、模型容量和 RL 的协同扩展，大规模数据合成，以及“模型—脚手架”联合设计。

一个小的不一致：结论里拿来对照的闭源模型名字（Fable-5、GPT-6 Astra）和表 3 里的对手（Opus-5、GPT-5.6 Sol）不同，报告里没有前两者的任何分数，所以这句比较无从核对。

放回 DeepSeek 的技术脉络里

注意力这一条线可以连起来读：MLA 把每层的条目压成一个潜向量（V3 精读）；DSA 让注意力只看 top-k 个条目，省计算不省存储（V3.2 精读，以及更早的 NSA）；V4 的 CSA/HCA 沿序列方向压缩条目（V4 精读 §4）；V4.1 的 CSA2 转而沿层方向共享，再加 FP4 和有界重放。Engram（Engram 精读）是另外一条稀疏维度，不碰 KV，从 V4.1 起正式进入 DeepSeek 的大模型。DeepSeek“为硬件设计模型”的一贯思路，见 V3 硬件反思精读。

和其他压 KV 的路线放在一起比较也有意思。训练后量化（KIVI）不需要重训，但精度代价由模型被动承受；按重要性淘汰（SnapKV 依据问题决定保留哪些位置，KVzip 做与问题无关的压缩）直接丢掉一部分 token，信息不可恢复，而且对多轮复用不友好；分层存储（LMCache、Mooncake）不压 KV，而是把它搬到更便宜的存储里。V4.1 选的是第四条路：在预训练时就把压缩写进结构，所有位置都保留，只是让条目更小、让层与层共享，再让部署系统围绕这个结构设计缓存策略。它的好处是压缩比极高而且对任何查询都一样，代价是只有从头训练的模型才能用，外界也无法单独评估每一步的精度损失。其他稀疏注意力路线可对照 MiniMax Sparse Attention、MoBA、XAttention。

值得接下来关注的问题：第三方能否在长上下文检索基准上测出 CSA2 与 FP4 的代价；跨层共享 KV 和下标的做法（IndexCache、YOIO、HySparse 一类）会不会被其他模型采用；FP4 KV 缓存会不会成为推理引擎的通用选项。

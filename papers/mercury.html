0 导读：一份只给结果、不给配方的工业报告

2025 年 2 月 26 日，一家名叫 Inception Labs 的公司发布了代码模型 Mercury Coder，并称它是第一个商用规模的扩散语言模型。我们平时用的大语言模型属于自回归模型：它一次只写一个 token（大致是一个词或半个词），必须等前一个写完才能写下一个。扩散语言模型换了一种做法：它先摆出一整段由噪声构成的“草稿”，再经过若干轮迭代，每一轮同时修改很多位置，直到草稿变成通顺的回答。Inception 的核心卖点是速度。第三方测速机构 Artificial Analysis 测得 Mercury Coder Mini 每秒输出约 1,109 个 token，Small 约 737 个；同一批测量里，常见的速度优化型自回归模型大多在每秒 60 到 200 个 token 之间。

2025 年 6 月 17 日，公司把这份技术报告放上了 arXiv。报告正文只有 8 页，其余是参考文献。它和学术论文最大的不同是几乎不讲方法：训练部分只写出了扩散模型训练目标的一般形式，并说方法“扩展了 SEDD”；接下来就直接给出四张结果表。模型的参数量、训练数据的组成、训练用了多少算力、加的是哪种噪声、生成时走多少步、服务时每个模型副本用几张 GPU、批有多大，报告都没有写。

因此，读这份报告的重点不在于“它是怎么做出来的”，而在于“它给出的数字能说明多少问题”。具体来说要分清三件事：哪些数字由独立的第三方测得，哪些是公司自己测的；每个比较拿谁来比、在什么条件下比；报告里的文字和它自己的表格是否一致。本页把这件事作为主线，第 5 节末尾的“结果的份量”是全页的核心。

先交代一下这份报告出现时的背景。在 2025 年之前，扩散语言模型基本停留在 GPT-2 的规模，SEDD、MDLM 等工作证明了它在困惑度上可以接近自回归模型，但没有人把它做到实用的大小。2025 年 2 月中旬，开放权重的 LLaDA 8B 发布，重点是证明扩散模型在 80 亿参数、2.3 万亿 token 的规模上也能学好，而不是速度。十几天后 Mercury Coder 上线，第一次把“扩散模型可以比自回归模型快很多”作为商业产品推出。所以，这份报告的价值主要在“速度”和“商用可用”这两点上，方法上的新意无法从报告里判断。

1 引言：扩散为什么“有可能”比自回归快

这一节要回答的问题：报告开头的论证是：自回归模型一个一个地生成 token，用户要等很久；扩散模型“由粗到细”地并行生成，能更好地利用 GPU，“算术强度”更高，所以更快。这句话要成立，需要先搞清楚自回归模型在生成时 GPU 到底在忙什么、闲着什么。这一节先把这个背景补上，再看报告列出的三条贡献分别是什么性质的说法。

1.1 自回归模型生成时，时间花在哪里

先补一点背景：为什么单个请求的生成速度被“读显存”卡住。

自回归模型每生成一个 token，都要把整个网络从头到尾算一遍，这叫一次前向计算。网络的参数存放在 GPU 的显存里，计算单元在芯片上。每做一次前向，参数都得从显存里完整地读一遍。参数很多时，“读参数”这件事本身就要花不少时间。

以报告里出现的对照模型 Qwen2.5-Coder-7B-Instruct 为例，它有 7.61B 个参数（Qwen 官方模型卡）。如果每个参数用 BF16 格式存储（2 字节），参数总共约 15.2 GB。NVIDIA H100 SXM 的显存带宽是每秒 3.35 TB（官方规格），把 15.2 GB 读一遍至少要约 4.5 毫秒（推算）。所以在只服务一个请求、又不用任何额外技巧时，这个模型每秒最多只能做约 220 次前向，也就是每秒最多产出约 220 个 token（推算，忽略了读 KV 缓存等其他开销）。

这 4.5 毫秒里，计算单元其实很闲。一次前向只为 1 个 token 做计算，计算量约为“2 × 参数量”次浮点运算，也就是约 152 亿次；H100 的 BF16 稠密算力约为每秒 989 万亿次（官方规格），算完只需约 0.015 毫秒（推算）。也就是说，读参数的时间是计算时间的约 300 倍，计算单元大部分时间在等数据。

衡量这种情况的指标叫算术强度：每从显存读 1 个字节，做多少次运算。生成 1 个 token 时，每读 2 字节参数只做 2 次运算，算术强度约为 1。H100 要让计算单元忙起来，算术强度至少要达到约 989 ÷ 3.35 ≈ 295（推算，这个分界点叫“脊点”）。低于脊点，速度由显存带宽决定，叫访存受限；高于脊点，速度由算力决定，叫计算受限。

报告选择先做代码模型，理由是代码场景对延迟特别敏感：编辑器里的自动补全、代码修改和智能体（agent）工作流，都要求模型在用户等待的几百毫秒到几秒内给出结果。这里其实有两种不同的“快”。自动补全的输出通常只有一两行，等待时间主要花在网络往返、排队和生成第一个 token 上；而智能体和长篇推理一次要生成成百上千个 token，等待时间主要由每秒能生成多少 token 决定。扩散模型提高的主要是后一种速度，这一点在第 5 节读 Copilot Arena 的延迟数字时会再用到。

“同一次前向处理多个位置”并不是扩散模型独有的想法。服务端把很多用户的请求拼成一个批，读一遍参数就能同时为所有用户各算出一个 token，这是提高总吞吐量的标准做法（本站 vLLM 精读 详细讲过）。投机解码则是为同一个用户提速：先用小模型猜几个 token，再让大模型在一次前向里同时检查它们。问题在于，批处理只能提高所有用户加在一起的速度，不能让单个用户等得更短；投机解码的提速又受限于小模型猜中的比例。

1.2 扩散模型的做法：一次前向改写整张画布

扩散语言模型给每个请求准备一张固定长度的“画布”，开始时画布上全是噪声（比如全是一个特殊的 [MASK] 符号）。每一步，模型读入提示词和当前画布，对画布上每一个位置同时预测它应该是哪个 token，然后采样器根据这些预测把一部分位置定下来，或者把一部分位置改写。这样反复几轮，画布就从全是噪声变成完整的回答。报告把这个过程称为“由粗到细”（coarse-to-fine）。

按上一小节的分析，这种做法的好处很直接：一次前向本来就要读一遍全部参数，而一次前向同时处理画布上的几十上百个位置，几乎不增加耗时；如果每次前向平均能定下多个 token，单个用户的生成速度就能成倍提高。这就是报告说的“更高的算术强度”。

1.3 报告声称的三条贡献，各是什么性质的说法

报告在 §1.1 列了三条贡献。把它们拆开看，性质很不一样：

  • “介绍 Mercury 系列扩散大模型”。这是描述，不是可检验的结论。
  • “比速度优化的前沿模型快最多 10 倍；在 H100 上每秒超过 1,000 个 token，以前只有定制芯片才能做到”。这是速度结论。1,109 和 737 这两个数确实由 Artificial Analysis 测得（第 5 节核对了它在 2025-02-27 发布的原始测速图），但“最多 10 倍”是拿 Mercury 和其他模型的 API 比出来的倍数，倍数大小取决于选谁作对照。Artificial Analysis 自己发布这组数据时的说法是“在相近硬件上比有竞争力的自回归模型快 5 倍以上”。
  • “质量与高速商用模型相当”。这是质量结论。支撑它的六项基准里，只有 HumanEval 和 LiveCodeBench 两列由 Artificial Analysis 测得，其余由谁测、怎么测，报告没有说明。

2 模型家族与训练：报告写出的那一个公式

这一节要回答的问题：Mercury Coder 有哪两个型号，报告怎么描述它们？报告用一个前向过程、一个反向过程和一个加权损失定义了 Mercury，这个公式具体是什么意思？报告说方法“扩展了 SEDD”，而 SEDD 学的是“概率比”，Mercury 的公式写的却是“直接预测干净数据”，两者是什么关系？架构、对齐、上下文长度和训练数据又公开到什么程度？

2.1 两个型号：Mini 与 Small

报告只介绍了代码模型 Mercury Coder 的两个型号。Mini 主打最快：报告称它在“延迟优化”的运行方式下，在 H100 上第一次达到每秒 1,100 个以上的 token，质量与流行的速度优化型开放权重模型相当。Small 主打质量：报告称它的基准成绩与流行的速度优化型前沿模型持平，吞吐量是它们的 3 到 10 倍，在各类代码负载上每秒 700 个 token 以上。

两个型号各有多少参数，报告没有给出。公开资料里与大小有关的只有两条间接信息：发布当天 TechCrunch 的报道说，公司拿 Mini 与 Meta 的 Llama 3.1 8B 比较、拿 Small 与 GPT-4o mini 比较；2025-08-27 AWS 的上架博客说支持“Mini 和 Small 两种参数规模”。这些都不是参数量，本页不做推测。报告在结尾的“Scaling”一段说 Small 比 Mini 大，并且在所有基准上都更好；第 5 节会看到，后半句与报告自己的表格并不完全相符。

“延迟优化的运行方式”这个限定词值得记住。它暗示测速时服务端没有把大量请求拼成大批，而是优先让单个请求尽快完成，这正是扩散模型最占优势的场景（见 1.1）。

2.2 前向加噪与反向去噪

先补一点背景：离散数据上的扩散。

图像扩散模型的做法是：往一张清晰的图片上一点点加高斯噪声，直到它变成纯噪声；再训练一个网络学会把噪声一步步去掉。文字是离散的 token，不能“加一点高斯噪声”，所以离散扩散改用“把 token 换掉”来加噪。常见的有两种换法：

  • 掩码（吸收态）噪声：每个位置以一定概率被换成一个特殊的 [MASK] 符号。噪声越大，被换掉的位置越多；最后全部是 [MASK]。一旦被换成 [MASK]，就不会再变回别的 token，所以叫“吸收态”。生成时，模型逐步把 [MASK] 填回真实 token。
  • 均匀噪声：每个位置以一定概率被换成词表里随机的一个 token。生成时，模型不仅要填空，还要判断每个看起来正常的 token 是否其实是噪声，所以已经写下的 token 也可能被改写。

两种做法都用一个“噪声水平” \(t\) 控制换掉多少位置：\(t\) 小时序列几乎是干净的，\(t\) 到最大时序列完全是噪声。本站的 D3PM 精读 和 旧版“从头讲起” 有更完整的介绍。

报告的定义是标准的写法。前向过程（加噪过程）\(q\) 从一段干净的 token 序列 \(\mathbf x\) 出发，按一条马尔可夫链 \(q(\mathbf z_t\mid\mathbf z_{t-1})\) 依次产生 \(\mathbf z_1,\dots,\mathbf z_T\)，噪声越来越多，最后的 \(\mathbf z_T\) 服从一个已知的先验分布 \(p(\mathbf z_T)\)（例如全是 [MASK]）。反向过程（去噪过程）反过来：先从先验里采样 \(\mathbf z_T\)，再用一个学出来的模型 \(p_\theta(\mathbf z_{t-1}\mid\mathbf z_t)\) 一步步去噪，最后得到一段文字。整条反向链定义了模型生成的文字分布 \(p_\theta(\mathbf x)\)。

2.3 训练目标：按噪声水平加权的去噪交叉熵

报告写出的训练损失是：

$$\mathcal L(\mathbf x)=-\,\mathbb E_{t}\Big[\gamma(t)\cdot\mathbb E_{\mathbf z_t\sim q}\log p_\theta(\mathbf x\mid\mathbf z_t)\Big]$$

逐项来读。\(\mathbb E_t\) 表示随机抽一个噪声水平 \(t\)；\(\mathbb E_{\mathbf z_t\sim q}\) 表示按前向过程把 \(\mathbf x\) 加噪成 \(\mathbf z_t\)；\(p_\theta(\mathbf x\mid\mathbf z_t)\) 是网络在看到带噪序列后，对“原来的干净序列是什么”给出的概率；取对数再加负号，就是我们熟悉的交叉熵。\(\gamma(t)\ge 0\) 是一个由人选定的权重函数，决定各个噪声水平在训练中占多大比重。这个损失的意思可以一句话说完：把干净数据加上随机程度的噪声，训练网络把它还原，还原得越不准罚得越重，不同噪声程度的题目按 \(\gamma(t)\) 给分。

训练好去噪网络之后，报告给出了一种生成方式：

$$p_\theta(\mathbf z_{t-1}\mid\mathbf z_t)=\sum_{\mathbf x} q(\mathbf z_{t-1}\mid\mathbf z_t,\mathbf x)\,p_\theta(\mathbf x\mid\mathbf z_t)$$

它的含义是：先让网络猜“干净序列可能是什么”（\(p_\theta(\mathbf x\mid\mathbf z_t)\)），再假装这个猜测是真的，用前向过程的后验 \(q(\mathbf z_{t-1}\mid\mathbf z_t,\mathbf x)\) 算出“如果干净序列是它，上一步的带噪序列应该长什么样”，最后对所有可能的猜测加权平均。在掩码噪声下，这一步的效果就是：一部分仍是 [MASK] 的位置被填上网络预测的 token，其余位置保持不变。

先补一点背景：为什么损失写成“每个位置各自的交叉熵”。

网络对整段序列只做一次前向，为每个位置各输出一个分布。实际训练时，\(\log p_\theta(\mathbf x\mid\mathbf z_t)\) 一般按位置拆成求和：\(\sum_i \log p_\theta(x^i\mid\mathbf z_t)\)，相当于假设在给定 \(\mathbf z_t\) 后各位置的预测彼此独立。这正是扩散模型能“一次前向给出所有位置”的原因，也是它的代价来源：如果生成时同一步定下两个彼此强相关的位置（比如一个函数名的两半），两个位置各自采样，就可能拼出不存在的组合。本站 旧版“因子分解误差”一节 用两个 token 的例子讲过这一点。

这个一般形式能装下很多已有的方法，只要换掉 \(q\) 和 \(\gamma(t)\)：

  • D3PM（2021）提出了离散扩散的这套框架，并且已经用“先预测干净数据，再用后验退一步”的参数化方式（见 D3PM 精读）。
  • MDLM（2024）证明了：在掩码噪声下，似然的下界（ELBO）恰好就是对被掩码位置的交叉熵按某个随时间变化的系数加权，也就是上式在一种特定 \(\gamma(t)\) 下的样子（见 MDLM 精读）。MDLM 的最后一位作者 Volodymyr Kuleshov 也是本报告的资深贡献者之一。

所以，单看这个公式，Mercury 和过去几年的学术工作在训练目标上没有本质区别。真正决定效果的东西，包括噪声类型、\(\gamma(t)\) 的具体形式、网络结构的细节和数据，报告都没有写。

2.4 “扩展了 SEDD”到底说明了什么

先补一点背景：SEDD 学的是什么。

SEDD（Lou、Meng、Ermon，arXiv 2023-10，ICML 2024 最佳论文奖）是把“score”这个图像扩散里的核心概念搬到离散数据上的工作。连续扩散的 score 是概率密度对数的梯度，离散数据没有梯度可言，SEDD 改为学习“概率比”：对当前序列 \(x\) 和只差一个位置的另一个序列 \(y\)，网络估计 \(p_t(y)/p_t(x)\)，即“把这个位置改成另一个 token，概率会变成原来的多少倍”。为了学好这个永远为正的比值，SEDD 设计了一个叫 score entropy 的损失。在当时的小规模实验里（GPT-2 级别），SEDD 的困惑度比此前的扩散语言模型低 25%–75%，并能以少 32 倍的网络调用次数生成质量相近的样本（SEDD 摘要）。本站 SEDD 精读 有完整推导。

后来 RADD（Ou 等，arXiv 2024-06）证明：在吸收态（掩码）噪声下，SEDD 要学的那个概率比，等于一个只与时间有关的系数乘以“给定没被掩码的部分，被掩码位置是某个 token 的条件概率”。换句话说，吸收态的 SEDD 和“直接预测干净 token”的 MDLM 本质上在学同一个东西，只是写法不同（见 旧版 RADD 一节）。

有了这两层背景，就能看清报告的写法意味着什么。报告说 Mercury 的方法“通过对数据和计算的细致修改扩展了 [28]”，[28] 正是 SEDD；SEDD 的第三作者 Stefano Ermon 也是本报告的资深贡献者。但报告接着写出的公式是“直接预测干净数据 \(p_\theta(\mathbf x\mid\mathbf z_t)\)”的形式，而不是 SEDD 的概率比加 score entropy 的形式。按 RADD 的结论，如果 Mercury 用的是吸收态噪声，这两种写法可以互相转换，所以这里并不矛盾；但如果用的是均匀噪声，两者就不再等价。由于报告没有说噪声类型，我们无法判断 Mercury 在多大程度上保留了 SEDD 的具体做法。“对数据和计算的细致修改”具体指什么，报告也没有一句解释。

示意图：Mercury 报告里的训练目标，和几篇学术工作的关系
D3PM（2021）离散扩散框架；先预测干净数据，再用后验退一步→SEDD（2023-10，ICML 2024）学概率比 p_t(y)/p_t(x)，score entropy 损失→RADD（2024-06）吸收态下：概率比 = 时间系数 × 干净 token 的条件概率

本站整理。箭头表示“后者在前者的基础上提出或证明了什么”，不表示 Mercury 实际采用了哪一条路线；那一点报告没有披露。
容易误读的地方：看到“扩展了 SEDD”，很容易以为 Mercury 就是“放大版 SEDD”。报告并没有给出这样的证据。它写出来的公式是一个很宽的框架，D3PM、MDLM、吸收态 SEDD 都能写成这个样子。能从报告里确定的只有：Mercury 是用某种离散扩散目标训练的 Transformer。

2.5 架构、对齐、上下文长度与训练数据

架构。报告说 Mercury 是 Transformer，并强调“用扩散”和“用什么网络”是两件独立的事：扩散只规定怎么训练、怎么生成，不限制网络的结构，理论上也可以用 RWKV、Mamba 这类循环结构，就像图像扩散的去噪网络可以是 U-Net 也可以是 Transformer。选 Transformer 的理由是能直接用上现成的高效底层算子，超参数也更好调。报告没有说注意力是双向的还是分块的、有没有沿用某个自回归模型的权重。

微调与对齐。报告说 Mercury 可以像普通大模型一样继续预训练、微调，并用 RLHF 或 DPO 做对齐，唯一的改动是把自回归的损失换成扩散的去噪损失。这里只说了“可以”，没有说 Mercury Coder 实际做了哪些后训练、用了什么数据。

上下文长度。开箱支持 32,768 个 token，借助上下文扩展方法可以到 128k。2025-08-27 AWS 的上架博客则写“开箱支持 128,000 个 token”，与报告的说法不一致，可能对应不同版本。

训练数据与算力。报告只写了三句话：训练量在“数万亿 token”的量级；数据由网页抓取和来自自有来源、经过精心整理的真实与合成数据组成；所有开发都在一个大规模 H100 集群上完成。代码与自然语言的比例、去重和过滤方法、训练步数、用了多少 GPU 小时，都没有披露。

3 推理与服务：为什么“步数少”不等于“更快”

这一节要回答的问题：报告自己指出，以前的扩散语言模型（包括 SEDD）虽然能减少前向次数，却没能在墙钟时间上体现出优势。为什么会这样？Mercury 说它靠一个自研推理引擎解决了这个问题，报告对这个引擎写了哪些内容？这一节先把“少步数为什么不一定快”讲清楚，再看报告透露的几个关键词。

3.1 提示方式：与普通大模型相同

报告先说明，Mercury 支持在提示词或上下文的条件下生成，并且训练、微调、对齐用的数据和普通大模型类似，所以零样本提示、少样本提示和思维链提示都可以照常使用。对外的 API 与 OpenAI 的接口标准兼容，现有应用只要改一下地址和模型名就能换用 Mercury。这一点对商用很重要，但不涉及方法本身。

3.2 少步数为什么不一定快

报告在“Serving”一段写道，SEDD 这类先前的扩散模型在十亿参数以下的规模上证明了可以减少前向次数，却没有展示墙钟效率的提升。原因在于扩散模型的一次前向通常比自回归的一次前向贵得多，具体有两点。

先补一点背景：KV 缓存，以及扩散模型为什么用不上它。

自回归模型生成时，前面所有 token 的中间结果（每层注意力的 key 和 value）一旦算出就不再变化，所以可以存起来反复使用，这就是 KV 缓存。有了它，每生成一个新 token 只需要为这 1 个 token 做计算。

标准的扩散语言模型用的是双向注意力：画布上每个位置都能看到所有其他位置。每一步去噪后画布都变了，所有位置的中间结果也跟着变，所以严格来说每一步都要把提示词和整张画布重新算一遍。提示词有 1,000 个 token、画布有 256 个位置时，一次前向就要处理约 1,256 个 token。后来的学术工作用分块生成（Block Diffusion）或近似缓存（Fast-dLLM）来缓解这个问题。

第一点，一次前向处理的 token 太多时，就越过了 1.1 讲的脊点，从访存受限变成计算受限，耗时开始随 token 数线性增长。第二点，前向次数虽然少了，但如果每次前向都比自回归贵十几倍，总时间并不会变短。下面的推算图把这两点画在一起。

示意图：一次前向的耗时 vs 这次前向要处理的 token 数 L（假想的 7.61B 稠密模型，单张 H100 SXM，BF16，推算）
推算：耗时 = max(读参数时间, 计算时间)；读参数 15.2 GB ÷ 3.35 TB/s ≈ 4.5 ms；计算 = 2 × 7.61×10⁹ × L 次运算 ÷ 989×10¹² 次/秒。忽略注意力本身的计算和 KV 读写，也假设硬件效率是 100%。这不是 Mercury 的数据，Mercury 的大小和结构都没有公开；图只用来说明“扩散的一次前向可能便宜，也可能很贵，取决于每步要重算多少 token”。

从图上可以读出一个结论：如果每一步都要把 1,000 个 token 的提示词重新算一遍，一次扩散前向约 19 毫秒，相当于自回归生成 4 个多 token 的时间（推算），那么每步至少要定下 4 个以上 token 才不吃亏；如果提示词部分能缓存、只算画布，一次前向仍在 4.5 毫秒左右，每步定下 5 个 token 就能有约 5 倍提速。可见，扩散能不能在墙钟时间上占优，很大程度取决于工程实现，尤其是缓存怎么做，而不只取决于步数。

3.3 Mercury 的推理引擎：报告写了哪些关键词

报告把 Mercury 的速度优势归因于“最大限度地利用了常见加速器（如 NVIDIA GPU）的算力”，并说为此用了一个自研的推理引擎。关于这个引擎，报告只列出了几个关键词：

  • 动态批处理的采样。把不同用户的请求动态地拼进同一批一起去噪。这与自回归服务里的连续批处理是同一类思路（见 vLLM 精读 §2.3）。对扩散模型来说，难点在于不同请求可能处在不同的去噪步，画布长度也可能不同。
  • 分页（paging）。在推理服务的语境里，“分页”通常指像操作系统管理内存页那样分块管理 KV 缓存（见 vLLM 精读 §4.2）。这暗示 Mercury 的引擎也维护着某种按块管理的缓存。至于缓存的是什么、怎样与双向注意力配合，报告没有说。
  • 在生产负载下自动权衡速度与质量。这说明每步定下多少 token 不是固定的，引擎会根据负载调整。对用户来说，这意味着同一个模型在不同时间、不同负载下的速度和质量可能不同；对读者来说，这意味着基准分数是在哪一档设置下测的，需要打一个问号。
  • 为并行推理负载定制的内核，以及对用户的 OpenAI 兼容 API。
先补一点背景：每步多定几个 token，质量为什么会下降。

2.3 提到，网络对每个位置给出的分布是各自独立的。如果同一步定下两个强相关的位置，就可能拼出不合法的组合。每步定下的位置越多，速度越快，但这种错误也越多。下面的交互图用一个订机票的小例子演示这件事：出发城市和到达城市各由两个词组成，两个词必须配对。把步数减少（每步定下更多位置），出现“New Diego”这种不存在的城市的概率就会上升。“在速度和质量之间自动权衡”，权衡的就是这个。

读的时候要注意：这一段是整份报告里最接近“方法”的部分，但每个关键词都只有半句话。Mercury 到底每步定下几个 token、走多少步、怎样处理双向注意力和缓存，都没有写。所以“Mercury 快在哪里”这个问题，从报告里只能得到方向性的答案：扩散带来的并行，加上自研引擎的工程优化。两者各贡献了多少，无从得知。

4 评测设置：基线、基准与测速口径

这一节要回答的问题：报告拿哪些模型和 Mercury 比？这些模型和 Mercury 是不是同一个量级？六项代码基准各测什么？最关键的是，速度是谁、用什么方法测的，测的是“模型”还是“某家公司的 API”？只有先弄清这些，第 5 节的数字才读得懂。

4.1 四组自回归基线

报告说所有测试都针对 2025 年 2 月托管的一个 API 端点。对照的自回归模型分四组：

  • 开放权重的速度优化型：Llama 3.1 8B Instruct、DeepSeek Coder V2 Lite（总参数 16B、每个 token 激活 2.4B，DeepSeek 模型卡）、Mistral Small 3（24B，Mistral 2025-01-30 公告）、Qwen 2.5 Coder 7B Instruct（7.61B）。表 2 的开放权重组换成了 Llama 3.1 8B、OpenCoder 8B Instruct、Mistral Small 3 和 Qwen 2.5 Coder 14B Instruct。
  • 开放权重的前沿模型：DeepSeek V3（总参数 671B、每个 token 激活 37B，见 DeepSeek-V3 精读）。
  • 闭源的速度优化型：Claude 3.5 Haiku、GPT 4o Mini、Gemini 2.0 Flash Lite、Amazon Nova Micro、Codestral 2501。它们的参数量都没有公开。
  • 闭源的前沿模型：GPT 4o、Claude 3.5 Sonnet。报告自己说明，这一组与 Mercury 不在同一个速度与成本档次，列出来只是作为参照。

这样选基线的用意很清楚：Mercury 想证明自己在“速度优化型”这一档里质量不落后、速度大幅领先。但要注意，由于 Mercury 的参数量没有公开，表里没有任何一个对照能保证“同样大小”“同样训练数据量”或“同样训练算力”。和开放权重的 7B 到 24B 模型比时，我们不知道 Mercury 比它们大还是小；和闭源模型比时，双方的大小都不知道。

训练数据量也一样无法对齐。报告只说 Mercury 训练了“数万亿 token 量级”。作为参照，Qwen2.5-Coder 在通用模型 Qwen2.5 的基础上又用超过 5.5 万亿 token 继续预训练（Qwen2.5-Coder 技术报告摘要），Llama 3.1 的预训练数据超过 15 万亿 token。Mercury 是比这些对照多用了数据还是少用了数据、是否像后来很多扩散模型那样从一个现成的自回归模型改造而来，都无从判断。这一点很重要，因为质量上“打平”的意义取决于双方投入了多少数据和算力。

4.2 六项基准与填空任务各测什么

先补一点背景：代码基准怎么打分。

代码基准通常这样打分：给模型一个题目描述（往往附带函数签名），让它写出代码，然后用事先准备好的单元测试去跑；全部测试通过才算对。pass@1 指每道题只让模型生成一次，通过的题目占多少比例。和选择题不同，这种打分方式不依赖人工判断，但对提示词格式、代码抽取方式、是否允许多轮修改都很敏感。

  • HumanEval：OpenAI 2021 年发布的 164 道 Python 函数题，是最常用、也最可能已被训练数据“见过”的基准。因为只有 164 道题，每道题就值约 0.61 分；按二项分布估算，在 88% 左右的通过率上，分数的标准误约为 2.5 分（推算）。所以表 1 里 86 到 92 分之间的差距，大多只相当于几道题，不宜过度解读。
  • MBPP：约一千道入门级 Python 编程题。
  • EvalPlus：给 HumanEval 和 MBPP 的题目补充大量额外测试用例，专门抓“碰巧通过原测试”的错误代码。
  • LiveCodeBench（LCB）：持续收集编程竞赛网站上的新题，用题目发布时间避开训练数据污染，难度明显高于前几项。
  • BigCodeBench（BCB）：需要调用各种常用库来完成的实际编程任务。
  • MultiPL-E：把 HumanEval 等题目翻译成其他编程语言，报告用了 C++、Java、JavaScript、PHP、Bash、TypeScript 六种。
  • FIM（填空）：从 OpenAI 2022 年的填空研究而来。把标准答案里的一行（single-line）或一段随机片段（random-span-light 是随机片段任务的精简版）挖掉，模型同时看到前面和后面的代码，把中间补上，再跑单元测试。它模拟的是编辑器里的自动补全。

4.3 速度是怎么测的

报告的速度数字全部来自独立测评公司 Artificial Analysis（下称 AA）。报告给出的测量方式是：AA 用一组自有的、偏向代码的提示词（约 1,000 个输入 token、约 1,000 个输出 token）去调用各家的 API，以“每秒输出 token 数”作为速度指标。对于由多家云服务商提供的模型，报告给出的是 AA 在各服务商之间测得速度的中位数。Mercury 只有 Inception 自己一家在提供，所以它的数字就是 Inception 自家端点的测量值。

先补一点背景：AA 的“输出速度”怎么算。

按 AA 现行的方法说明（2026-10-19 查阅），“输出速度”的定义是：收到第一个 token 之后，平均每秒收到多少个 token。从发出请求到收到第一个 token 的等待时间单独记为“首 token 时间”，不计入输出速度。大多数测试一次只发一个请求；方法页还写明，结果取过去 72 小时的中位数。报告里描述的测速方式与此一致，但 2025 年 2 月时的具体测试细节（例如测试频率、统计窗口）本站无法逐项核对。

5.3 填空（表 3）：扩散的天然主场

先补一点背景：为什么填空对自回归模型是个“额外技能”，对扩散模型是“本能”。

自回归模型只能从左往右写，天然看不到光标后面的代码。要让它做填空，通常要在训练时专门把“前缀、后缀、中间”重新排列成“前缀、后缀、然后写中间”的格式，并加入特殊符号（这种训练方式叫 FIM）。没做过这种训练的对话模型，只能靠提示词让它“先复述前后文再补中间”，效果往往差很多。扩散模型的画布本来就是双向的：把后缀当作已知的上下文、只让中间那段从噪声开始去噪，填空就是它最自然的用法。

模型要从后面那行更深的缩进和 count += 1 推断出，缺的是一个条件判断，比如 if ch in "aeiou":，补完后再用单元测试检验。这个例子说明，填空能不能做好，关键在于能不能利用“后文”。只会从左往右写、又没有专门训练过的模型，看不到后两行，只能猜；而画布双向可见的扩散模型可以直接利用后文。随机片段任务挖掉的不一定是整行，可能从一行中间开始、到另一行中间结束，难度更高，各模型的分数也拉得更开。

5.4 真实用户投票：Copilot Arena（表 4）

先补一点背景：Copilot Arena 怎样给模型排名。

Copilot Arena 是卡内基梅隆大学与加州大学伯克利分校等机构的研究者做的一个 VSCode 插件（论文 arXiv 2502.09328，2025-02-13）。用户写代码停顿时，插件同时请两个随机选中的模型给出补全，把两个补全并排显示，用户选用哪一个就算哪个模型赢一次。截至该论文发布，平台已经发出 450 多万条补全建议，收集到 1.1 万多次两两比较。

排名用的是 Chatbot Arena 的方法：根据所有“谁赢了谁”的记录，拟合一个 Bradley–Terry 模型，给每个模型一个分数，换算成国际象棋那样的 Elo 刻度。在这个刻度上，分差 \(d\) 对应的胜率是 \(1/(1+10^{-d/400})\)：分差 0 时胜率 50%，分差 54 分时约 58%（推算）。名次按置信区间分档，分数差距落在统计误差范围内的模型并列同一名。有两点对读表很重要：第一，两个补全是同时显示的，快的模型要等慢的模型一起出结果，所以用户投票只反映补全的质量，不直接奖励速度；第二，延迟单独作为一列报告，不计入分数。以上据 Copilot Arena 官方博客（最后更新 2025-04-14）。

5.6 结果的份量

把前面的内容放在一起，可以逐条回答“这些数字值多少”。

第一，哪些数字是独立第三方测的。有两类。一是 AA 测得的速度和两项基准分（HumanEval、LiveCodeBench）。本站核对了 AA 官方账号在 2025-02-27（UTC）发布的测速图：图题标明是每秒输出 token 数、约 1,000 个输入 token、偏代码的负载，Mercury Coder Mini 为 1,109，Small 为 737，与报告一致；同图里的对照模型依次是 Qwen2.5 Coder 7B 207、Gemini 2.0 Flash-Lite（Preview）201、Codestral（Jan '25）171、Llama 3.1 8B 153、Nova Micro 148、Mistral Small 3 126、DeepSeek Coder V2 Lite 93、Claude 3.5 Haiku 61、GPT-4o mini 59、Command-R+ 54。其中只有 Qwen 一项与报告表 1 的 195 不同；报告自己的图 1 里 Qwen 的横坐标也在 207 附近，所以表 1 的 195 可能来自另一天的快照。二是 Copilot Arena 的用户投票（见 5.4），也已与该平台 2025-02-26 发布的图核对。这两类数字可以放心引用，但要带上日期：它们反映的是 2025 年 2 月下旬的一个时间段。

但“第三方测量”不等于“独立条件”。AA 测的是 Inception 自己运营的 API 端点：用几张 GPU、开多大的批、当时有多少其他用户在用，都由 Inception 决定。Mercury 刚发布时用户可能很少，服务器负载很低，而老牌 API 往往同时服务大量用户。Copilot Arena 也说明他们在发布前就测试过这个模型，报告致谢里同样感谢了这两家机构的支持。这些都不说明数字有问题，只说明测量对象是“Inception 在那段时间提供的服务”，而不是“这个模型在标准条件下的能力”。

第二，哪些数字是厂商自己测的。表 1 的 MBPP、EvalPlus、MultiPL-E、BigCodeBench 四列，表 2 全部，表 3 全部，以及正文所有“快多少倍”的概括。报告没有给出提示词、代码抽取方式和评测脚本，对照模型的数字是重新跑的还是引用的也没有说明。表 2 里 Qwen 2.5 Coder 14B 明显低于表 1 里的 7B，正是这种不透明带来的问题。

推算，只是思想实验：按 3.35 TB/s 的显存带宽、只计读参数的时间，是理想上限。若用 FP8，参数大小减半，前向次数上限翻倍；若一个副本用 n 张 GPU 做张量并行，带宽约为 n 倍（扣除通信开销）。Mercury 的实际大小、精度和卡数报告都没有公开。

这张表说明了一个简单的道理：同样是 1,109 token/秒，如果 Mini 只有 1B 左右，那么一个普通的自回归小模型在同样硬件上也可能接近这个速度；如果它有 14B，那就意味着每次前向要定下 9 个以上 token，扩散的并行确实在起大作用。不知道大小，就无法区分这两种情况。还有一点同样关键：报告说“在 H100 上”，没有说“在一张 H100 上”。2025-08-27 AWS 上架博客里，Mercury 只支持部署在 ml.p5.48xlarge（8 张 H100 的实例）上，作者在一个生成井字棋代码的示例里看到约 528 token/秒；这只是一个示例，不能当作基准，但它提醒我们，部署方式不同，速度也会差很多。

第四，自回归基线是怎么选、怎么测的。对照组是“速度优化型”的模型，这是合理的选择，因为 Mercury 的定位就是快。但它们的速度取的是 AA 在多家服务商之间的中位数。中位数会把最快的服务商平均掉。最明显的例子是 Llama 3.1 8B：表 1 里它是 153 token/秒，而 2024-08-27 Cerebras 推理服务上线时，AA 的首席执行官在 Cerebras 的新闻稿里说，他们测到 Cerebras 上的 Llama 3.1 8B 每秒超过 1,800 个输出 token，Llama 3.1 70B 每秒超过 446 个。闭源模型的情况更复杂：GPT 4o Mini、Claude 3.5 Haiku 的大小、硬件和负载都不公开，它们的 API 首先要为海量用户控制成本，单个请求的速度未必是优化重点。

第五，与运行在专用芯片上的自回归模型相比。报告自己说，每秒 1,000 个以上的 token 以前只有定制芯片才能做到；发布博客点名了 Groq、Cerebras 和 SambaNova。下图把几组公开数字放在一起。要强调的是，这些数字的测量时间、负载和硬件都不同，不能直接比大小，只能看数量级。

从这张图可以得到两个结论。其一，在 2025 年初，专用芯片上的 8B 级自回归模型已经能做到比 Mercury Mini 更快，所以 Mercury 的意义不在于“前所未有的绝对速度”，而在于“用普通的 H100 达到了专用芯片的数量级”。这正是报告自己的措辞，也是一个有分量的结论，因为 H100 远比专用芯片容易获得。其二，“比自回归模型快 5 到 10 倍”这个倍数，是拿 Mercury 的单一端点去比自回归模型在各家 API 上的中位数。如果拿同样大小的自回归模型，在同样的 H100 上，用同样精心优化的引擎（量化、投机解码、多卡并行）去比，倍数会小一些，但报告没有做这个实验，所以小多少无从得知。

第六，单用户速度和满负载吞吐量是两回事。AA 一次只发一个请求，测的是单个用户看到的速度。扩散的优势来自“单个请求时 GPU 算力有富余”（见 1.1），当服务器同时处理很多请求时，这部分富余会被批处理用掉。一年后 Google DeepMind 的 DiffusionGemma 技术报告（arXiv 2608.00146，2026-07-31）在同一张 H100 上实测了这一点：并发请求少时，它的扩散模型在单用户速度和总吞吐量上都领先自回归版本；并发约 32 个请求以上时，自回归模型的总吞吐量反超。Mercury 的报告没有给出任何关于高并发时总吞吐量和成本的数据。

第七，报告内部的不一致。把前面发现的问题集中列出来：

  • Copilot Arena 延迟：正文“25 毫秒”，表 4 “0.25 秒”，平台公布 0.24 秒；正文“约为 GPT-4o Mini 的 1/4”，按表 4 实为约 1/3.4。
  • “Mini 超过所有开放权重模型、快 8 倍以上”：表 1 中 Mini 在多个基准上低于 Qwen 2.5 Coder 7B 或 Mistral Small 3，对 Qwen 和 Llama 3.1 8B 的速度倍数分别只有 5.7 和 7.2（推算）。
  • “两个 Mercury 模型在填空上都超过了 Codestral”：表 3 中 Mini 三列都略低于 Codestral。
  • “Small 在所有基准上都优于 Mini”：MBPP、Bash、TypeScript 三项是 Mini 更高。
  • 表 1 用 Qwen 2.5 Coder 7B，表 2 换成 14B，后者在 MultiPL-E 上反而低 7 分以上；正文写 “Gemini 2.0 Flash”，表中是 Flash Lite；表 4 把 Meta 拼成了 “Metal”。

最后，可以放心得出的结论。2025 年 2 月，Inception 的 API 在 AA 的单请求测速中，以普通 H100 达到了每秒约 1,100（Mini）和约 740（Small）个输出 token，比当时同档自回归模型的 API 快 3.7 倍以上（推算，Small 对表 1 中最快的 Gemini 2.0 Flash Lite）。在 AA 测的两项基准和 Copilot Arena 的用户投票里，它的质量与 Codestral、GPT-4o Mini、Gemini 2.0 Flash Lite 这一档的模型相当，在最难的 LiveCodeBench 上明显落后于前沿模型。其余的质量数字、所有“快多少倍”的概括，以及“扩散本身贡献了多少”，都只能当作厂商的说法。

引用这篇报告时最容易犯的错误：把“1,109 token/秒”当作扩散语言模型相对自回归模型的算法加速比。它是一个特定公司、特定时间、特定部署、单请求条件下的 API 测量值，没有对应的同大小、同硬件、同引擎的自回归对照。要讨论“扩散能比自回归快多少”，应该去看在同一硬件、同一批大小下做了对照的工作，例如本页“后来怎么样了”中提到的 DiffusionGemma，以及本站 Fast-dLLM、Block Diffusion 的精读。

Mercury 自身的迭代。2025 年 11 月的升级版和 2026 年的 Mercury 2、Mercury 2.5 都以博客形式发布，截至 2026-10-19 本站没有找到它们的技术报告；本站查阅的升级版与 Mercury 2 两篇博客都继续强调速度，也都没有公开参数量。产品线本身也在扩展：2025 年 8 月上架 AWS 时已经有通用的 Mercury 和代码专用的 Mercury Coder 两个模型，Mercury 2 起又改为以“推理模型”定位。按 AA 页面（2026-10-19 查阅），Mercury 2.5 的输出速度为每秒 737.9 个 token，在 150 个模型中排第 2，Intelligence Index 为 12 分，AA 的评语是在同价位模型中“低于平均”。

第三方怎么测后来的 Mercury。速度数字的测量口径问题在后来的版本上表现得更明显。Inception 说 Mercury 2 在 Blackwell GPU 上每秒 1,009 个 token；DiffusionGemma 报告的附录 E 写道，AA 在 2026-07-28 给出的中位数约为每秒 987 个，而他们自己通过 OpenRouter 的公开 API 做黑盒拟合，得到的生成速度只有每秒 489 到 600 个，并指出差异可能来自硬件、服务优化和测试数据的不同。到 2026-10-19，AA 已把 Mercury 2 标为“已弃用”，只在 10k 输入 token 的负载上继续测量，页面显示的速度是每秒 487.0 个。同一个模型，在不同测量者、不同负载、不同时间下，速度可以相差一倍。这正好印证了 5.6 的结论：引用速度数字时，必须带上测量者、负载和日期。

第三方怎么测 Mercury 的质量。ParallelBench 设计了一组专门检验“同一步定下多个 token 会不会出错”的任务，并通过 API 测了 Mercury。他们发现，Mercury 在要求把一个列表严格倒序输出的任务上几乎全对，却在“把列表随便打乱顺序输出”这个看起来更容易的任务上，随着列表变长准确率急剧下降，趋势与自回归模型正好相反；作者据此认为，闭源的 Mercury 不能根据任务中 token 之间依赖的强弱自适应地调整并行度。这是 3.3 讲的“速度与质量的权衡”在一个商用模型上的直接证据，详见 旧版 ParallelBench 一节 和 Train for the Worst, Plan for the Best 精读。

其他工业扩散模型。Gemini Diffusion 和 Seed Diffusion 与 Mercury 一样只公开了很少的方法细节（见 旧版 Gemini Diffusion 条目、旧版 Seed Diffusion 拆解）。Seed Diffusion 的报告自己也承认，它的 2,146 token/秒（H20）与 Mercury（自有数据、H100）、Gemini Diffusion（混合任务、硬件未知）的数字不能直接比较。后来，蚂蚁集团等机构的 LLaDA2.0（arXiv 2025-12）和 Google DeepMind 的 DiffusionGemma（arXiv 2026-07-31）都公开了权重和较完整的训练配方；DiffusionGemma 还在同一张 H100、同一批大小下给出了扩散模型与它所改造的自回归模型的速度对照，这正是 Mercury 报告缺少的那种实验。

回头看，Mercury 报告的历史位置主要在于两点：它第一次让一个商用扩散语言模型接受了第三方测速和真实用户投票，证明扩散模型可以在普通 GPU 上以专用芯片量级的速度提供“可用”的代码补全；同时，它几乎没有公开方法，使得“速度从哪里来”这个问题要靠后来的开放研究去回答。

路线总览

0 导读：这条路线要解决什么问题

训练和使用大语言模型，钱几乎都花在 GPU 上。训练一个 6710 亿参数的模型，DeepSeek-V3 报告的正式训练用了 278.8 万个 H800 GPU 小时（V3 精读 §1）；上线之后，每回答一个问题又要让几十 GB 的参数在显存和计算单元之间来回搬运成百上千次。所谓 AI Infra（AI 基础设施），就是研究怎样让同样的 GPU 小时干更多的活：训练时让更多的浮点运算真正落在模型计算上，推理时在延迟达标的前提下，让一张卡每秒服务更多的请求、生成更多的 token。

这件事难，是因为 GPU 上同时有好几种资源，而且它们的增长速度并不一致。第一种是算力，也就是每秒能做多少次乘加；第二种是显存，它又分成能装多少（容量）和每秒能读多少（带宽）；第三种是通信，也就是卡与卡、机器与机器之间每秒能传多少数据。大模型的不同阶段卡在不同的资源上：训练卡在算力和通信，推理的“逐个生成”阶段卡在显存带宽，长上下文卡在显存容量。此外还有一条不是资源、却同样硬的约束：精度。很多省资源的办法会改变模型算出来的东西（丢掉一部分 KV、用更少的位数存数），这时就要回答“省下的资源值不值得掉的那几分”。几乎每篇论文都可以读成一笔交易：拿一种资源去换另一种，或者拿一点精度去换资源。

本站的 42 篇精读可以分成六支方法，外加一条贯穿始终的案例线。注意力内核（FlashAttention 1–4、FlashInfer）不改变注意力的数学，只改变数据在芯片上怎么搬；推理服务（Orca、vLLM、SGLang、Sarathi-Serve、DistServe、Mooncake、LMCache、批不变性）管的是很多请求怎样共享一组 GPU、KV 缓存放在哪里；KV 压缩与低精度（SnapKV、KVzip、KIVI、QuaRot、FP8、NVFP4）让每个请求少存一点、每个数少占几位；投机解码（投机解码、Medusa、EAGLE、DSpark）用解码时闲着的算力去换更低的延迟；训练系统（Megatron-LM、ZeRO、MegaScale、Muon、HybridFlow、AReaL）把一个模型切到成千上万张卡上，并让强化学习后训练跑得动；注意力结构（RoPE、NSA、MoBA、XAttention、DSA、MiniMax 稀疏注意力、Gated DeltaNet、Kimi Linear、门控注意力）直接改模型，让长上下文从结构上变便宜。最后，DeepSeek 从 V3 到 V4.1-Flash 的一串报告，是把以上几支放在同一个模型上一起设计的完整案例。

这几支不是平行发展的，而是互相推着走：分页 KV 让批能开大，批开大以后投机解码的收益变小；长上下文让 KV 成了主角，于是推理系统开始把 KV 当成要存、要搬、要复用的数据，模型设计者也开始从结构上把 KV 压小；强化学习后训练又把推理引擎拉进训练循环，逼出了“推理结果要逐位可复现”的新要求。下面的时间线把 42 篇精读按分支和时间排开，可以先扫一眼全貌。

1 先把问题讲清楚：时间、显存和通信都花在哪里

这一节要回答的问题：后面所有方法都在和同几笔开销打交道，所以先把账算清楚：推理时，一个请求的两个阶段各卡在什么资源上？KV 缓存是什么、有多大、为什么它决定了一张卡能同时服务多少人？训练时，显存为什么装不下模型，切开之后又为什么要通信？这一节的数字都来自本站的精读页，用来给后面各节一个共同的参照。
先补一点背景：算力、带宽和“算术强度”。

GPU 做一次矩阵乘，要先把数据从显存（HBM）读到芯片上的计算单元，算完再写回去。于是一个计算任务的耗时，取决于“算”和“搬”两者中较慢的那个。判断哪个更慢，看算术强度：每从显存读 1 个字节，能拿它做多少次浮点运算。以 H800 为例，BF16 算力约 989 TFLOPS、显存带宽约 3.35 TB/s，所以每读 1 字节至少要做约 295 次运算，计算单元才不会闲着（推算，V3 硬件反思精读 §2.1）。

处理一整段输入时，矩阵乘是“矩阵 × 矩阵”，读进来的每个权重会和成百上千个 token 相乘，算术强度很高，计算单元被喂得很饱，这叫计算受限。逐个生成时，每步只有一个新 token，矩阵乘退化成“矩阵 × 向量”，每读一个 2 字节的 BF16 权重只做一次乘加（2 次运算），算术强度约为每字节 1 次，只有上面那条线的三百分之一，计算单元大部分时间在等数据，这叫访存受限（或带宽受限）。

1.1 一个请求的两个阶段：prefill 吃算力，decode 吃带宽

大模型回答一个请求分两步。第一步叫 prefill（预填充）：用户的整段输入一次性送进模型，所有输入 token 同时算完，顺便得到第一个输出 token。第二步叫 decode（解码）：此后每一步只生成一个 token，把它接到末尾再算下一步，一直到结束。按上面的说法，prefill 是计算受限的，decode 是访存受限的。

decode 访存受限，直接带来一个推论：把很多请求拼成一批一起解码，几乎是免费的。因为每一步最贵的是把参数从显存读一遍，而读一遍参数可以同时为批里的每个请求各算一个 token。vLLM 精读 §1 给了一个理想化的例子：OPT-13B 的参数有 26 GB，A100-40GB 每秒约能读 1.5 TB，读一遍约 17 毫秒；批大小为 1 时每秒只能产出约 60 个 token，批大小为 32 时约 1,900 个（推算，忽略了读 KV 的时间）。所以推理系统的头号目标，是让一个批里同时放下尽可能多的请求。

1.2 KV 缓存：每个请求随身带着的一份“草稿纸”

注意力要让每个新 token 去看前面所有 token 的 key 和 value。这些 key、value 在前面的步骤里已经算过，没必要每步重算，于是推理系统把它们存下来，这份数据叫 KV 缓存。它的大小可以直接按模型结构算出来：每个 token、每一层要存 key 和 value 两份，每份是“KV 头数 × 每头维度”个数。所以每个 token 的 KV 字节数是

$$\text{每 token 的 KV 字节数}=2\times\text{层数}\times\text{KV 头数}\times\text{头维度}\times\text{每个数的字节数}$$

代入 Qwen-2.5 72B（80 层、8 个 KV 头、每头 128 维、BF16）得到 327,680 字节，约 328 KB；一个 128K token 的长请求，光 KV 就要约 42.9 GB，超过半张 80 GB 显卡（推算，V3 硬件反思精读 §2.1）。Mooncake 用的 LLaMA2-70B 结构每 token 约 320 KB，8K 个 token 就是约 2.7 GB（Mooncake 精读导读，推算）。

KV 缓存因此带来两笔账。第一笔是容量：显存扣掉参数之后剩下的空间，能放下几个请求的 KV，批就最多开多大。第二笔是带宽：decode 每一步除了读参数，还要把这个批里所有请求的 KV 整个读一遍。上下文一长，第二笔会超过第一笔。下图用 SnapKV 精读里的推算说明这一点：

容易混淆的地方：“memory-bound”这个词在推理论文里有两种意思（vLLM 精读 §1 专门提醒过）。一种是带宽瓶颈：每步读数据的时间远多于计算的时间。另一种是容量瓶颈：显存装不下更多请求的 KV，批开不大。vLLM 直接解决的是容量问题，但收益是通过带宽问题兑现的：批变大以后，读一遍参数能服务更多请求。读到“受显存限制”时，先分清是哪一种。

1.3 训练：显存装不下，切开就要通信

训练比推理多出三样东西要存：每个参数的梯度、优化器状态和前向留给反向用的激活。按“混合精度 + Adam”的常见做法，16 位参数和梯度各 2 字节，32 位的参数主副本、一阶矩、二阶矩各 4 字节，每个参数合计 16 字节，还不算激活（ZeRO 精读 §3.1）。按这个算法，12 亿参数的模型光这几样就要约 19.2 GB，83 亿参数要约 133 GB，而当年一张 V100 只有 32 GB（推算，Megatron-LM 精读 §1）。

算力也是一样的道理：训练一个 token 大约要做“6 × 参与计算的参数量”次浮点运算（前向 2 次、反向 4 次），一个千亿参数模型要在上万亿 token 上训练，单卡要算好几百年。所以训练必须把模型和数据切到很多张卡上，而一切开，卡之间就要交换中间结果：数据并行要汇总梯度，张量并行每层都要拼结果，专家并行要把 token 发给别处的专家。通信慢了，算力就在等待里浪费掉。衡量训练效率的通用尺子叫 MFU（模型算力利用率）：实际每秒完成的模型计算量，除以所有卡理论峰值之和（MegaScale 精读导读）。

2 注意力内核：不改数学，只改数据怎么搬

这一节要回答的问题：注意力是 Transformer 里唯一要让每个 token 和所有 token 打交道的算子，它的标准写法在 GPU 上非常浪费。FlashAttention 一系列论文为什么能在完全不改变计算结果的前提下快好几倍？为什么每出一代新 GPU 就要重写一遍？推理服务里的注意力又和训练时有什么不同，需要 FlashInfer 这样的专门库？
先补一点背景：GPU 的两层存储，以及“融合内核”。

GPU 上有两种存数据的地方。一种是显存（HBM）：几十 GB，容量大，但读写相对慢。另一种是每个计算单元旁边的片上存储（SRAM，包括共享内存和寄存器）：每个 SM 只有一两百 KB，但快一个数量级。所有计算都必须先把数据搬进片上存储。一个“内核”（kernel）就是 GPU 上执行的一段程序；如果几步计算分成几个内核，每个内核都要把结果写回显存、下一个内核再读出来；把它们合成一个融合内核，中间结果留在片上，就省掉了这些来回（FlashAttention 精读 §2）。

2.1 FlashAttention：慢在搬，不在算

标准注意力先算出一张 \(N\times N\) 的分数表（\(N\) 是序列长度），写进显存，再为了 softmax、掩码、dropout 一遍遍读出来、写回去。2022 年以前已经有大量“近似注意力”把计算量从 \(N^2\) 降到接近 \(N\)，可它们在实际计时上大多没变快。FlashAttention（2022-05）给出的解释是：注意力慢主要不是因为算得多，而是因为搬得多。它把 \(Q,K,V\) 切成能放进片上存储的小块，一块一块地算分数、用完就扔；softmax 本来要看完一整行才能归一化，论文用在线 softmax（边扫边维护当前的最大值和分母，遇到新块时把旧结果按比例修正）把各块结果精确地拼起来（§3）；反向传播需要分数表时，不去读存档，而是在片上重算一遍。结果是对显存的读写量大幅下降（论文的例子里少了约 9 倍），注意力算子快了 2–4 倍左右，显存占用从随 \(N^2\) 增长变成随 \(N\) 线性增长。

这篇论文的意义不只在速度。它把“IO 感知”（先算清楚数据在存储层次之间搬了多少次，再设计算法）变成了系统优化的通用思路，后面几乎每一篇内核论文都在做同一件事：找出当前硬件上最慢的那个部件，然后把计算重新编排，让它不再是瓶颈。

2.2 FA2 → FA3 → FA4：每一代都在追新硬件的瓶颈

FlashAttention 的核心（分块、在线 softmax、反向重算、从不把 \(N\times N\) 矩阵写进显存）后来一直没变，变的是“谁是瓶颈”。下面三步的推理链条是一样的：新硬件让某个部件变快了，原来藏在它后面的另一个部件就成了新的瓶颈。

  • FA2（2023，A100）。FA1 只用到 A100 理论峰值的 25%–40%，原因是线程块和 warp 之间分工不好、非矩阵乘的运算太多。FA2 重新划分工作，达到 50%–73%（这两个范围都是 FA2 论文摘要的数字，见 FlashAttention 精读“后来怎么样了”；FA2 没有单独的精读页）。
  • FA3（2024-07，H100）。H100 的矩阵乘算力比 A100 高出很多，可 FA2 在 H100 上只能用到约 35%，因为它是按“发一条指令、等它做完”的同步方式写的，而 Hopper 的数据搬运单元 TMA 和矩阵乘指令 WGMMA 都是异步的。FA3 让一部分线程专门搬数据、另一部分专门计算（warp 专业化），再让两组线程乒乓交替，把 softmax 的指数运算藏在另一组的矩阵乘后面（§3.2）。它还支持 FP8，用分块量化和 Hadamard 旋转把 FP8 注意力的误差降到逐张量量化基线的约 1/2.6（§3.5）。FP16 前向比 FA2 快 1.5–2.0 倍。
  • FA4（2026-03，B200）。Blackwell 的张量核峰值从 H100 的约 1 PFLOPs/s 涨到 2.25 PFLOPs/s，可算指数的单元和共享内存带宽按每 SM 每周期计算一点没变，论文把这叫“非对称扩展”（§1）。后果是头维 128 时，一个 \(128\times128\) 分数块的两次矩阵乘和它的 16,384 次指数运算，理论上各要约 1024 个时钟周期，softmax 第一次和矩阵乘一样贵。FA4 的对策都是“把指数和重缩放从关键路径上挪开”：用 FMA 单元上的多项式分担一部分指数（§3.3），只在行最大值涨幅超过 \(2^8\) 倍时才做在线 softmax 的重缩放（§3.4），反向用 2-CTA 矩阵乘把共享内存流量减半。B200 上 BF16 前向最高 1613 TFLOPs/s，约 71% 峰值。

2.3 FlashInfer：推理服务里的注意力是另一回事

训练时的注意力形状整齐：一批序列长度相同，KV 连续存放。推理服务完全不是这样。每个请求的 KV 长短不一，存放方式五花八门：vLLM 把它切成 16 个 token 一页，SGLang 让多个请求共享前缀，投机解码要在一棵草稿树上算注意力；而且 decode 阶段每个请求只有一个 query，注意力本身也变成了访存受限的。每个推理引擎都不得不自己写、自己维护一套内核。

FlashInfer（2025-01，MLSys 2025 杰出论文）想做一个通用的注意力引擎：内核内部仍是 FA2/FA3 的算法，外面加三层设计。数据结构上，把分页、基数树、树状掩码等各种 KV 布局都写成同一种块稀疏矩阵，一套内核读所有布局（§3.1）；编译上，用户用几个小函数描述自己的注意力变体，用即时编译生成专用内核；运行时，每一步先在 CPU 上按各请求的长度做一次负载均衡规划，再让可以被 CUDA Graph 录制的内核按计划执行（§3.7）。接入 SGLang 后，相对 SGLang 自带的 Triton 后端，生成 token 的间隔缩短 29%–69%；但附录在固定请求速率下重测，短输入负载上只快 3%–4%（§4.7）。它真正站住的是定性结论：一个块稀疏抽象确实能覆盖推理服务里的各种布局。到 2026-10，vLLM 和 SGLang 在 Blackwell 上默认都经由 FlashInfer 调用注意力内核。

这一支留下了两个问题。第一，内核再快，算的也还是精确的全注意力：计算量随长度平方增长、每步要读的 KV 随长度线性增长，这两笔账内核无能为力，于是有了第 7 节的稀疏和线性注意力。第二，内核和硬件代际绑得越来越紧，每一代都要重写；FA4 改用嵌在 Python 里的 CuTe-DSL 编写，编译速度比 C++ 模板方式快 20–30 倍，DeepSeek-V4 用 TileLang 写内核（V4 精读 §7.1），都是在降低“重写一遍”的成本。

容易误读的地方：FlashAttention 系列的速度数字几乎都是单个注意力算子的 TFLOPs/s，形状是训练和长 prefill 的形状（总 token 数固定、头维 64–256），不是端到端训练或推理的速度，也不覆盖 decode（每次只有一个 query，瓶颈在读 KV）。另外，“比上一代快 1.5–2 倍”的对手往往是没有为新硬件调过的上一代内核；FA3 的论文里更强的对手是 NVIDIA 的闭源 cuDNN，而 FA4 发表时，cuDNN 已经吸收了 FA4 公开代码里的技巧（FA4 精读 §7.5）。

3 推理服务：把很多请求塞进一组 GPU，又不让谁等太久

这一节要回答的问题：第 1 节说，decode 访存受限，所以批越大越划算。可请求是陆续到达的、长短不一的、KV 越写越长的，“把它们拼成一个大批”在工程上一点也不简单。从 2022 年的 Orca 到 2025 年的 LMCache，推理系统先后解决了五个问题：怎么组批、显存怎么分配、相同的前缀怎么复用、prefill 和 decode 怎么不互相拖累、KV 怎么离开 GPU。每一步解决一个问题，又暴露下一个问题。最后，推理结果为什么会“同样的输入、不同的输出”？
先补一点背景：推理服务的几个指标。

用户感受到的速度分成两个数：从请求到达到第一个输出 token 出现要多久，叫 TTFT（首 token 延迟），它等于排队时间加 prefill 时间；此后每两个 token 之间隔多久，叫 TPOT 或 TBT（每 token 时间、token 间隔）。服务商给这两个数定的上限叫 SLO（服务水平目标）。吞吐量是每秒产出多少 token 或处理多少请求，不管它们等了多久；goodput 只数延迟达标的那部分，DistServe 把它定义为“至少 90% 的请求同时满足 TTFT 和 TPOT 要求时，每张 GPU 每秒能接的最大请求数”（DistServe 精读 §1）。不同论文用的指标不一样，比较倍数前要先看清是哪一个。

3.1 Orca：按“一步”而不是按“一个请求”组批

2022 年以前的推理服务沿用为图像分类设计的做法：凑齐一批请求，一起跑完再接下一批。生成式模型一个请求要跑几十到几百步，于是先写完的请求只能陪着最长的那个跑完，新来的请求只能干等整批结束。Orca（OSDI 2022）把调度的粒度缩小到“模型的一次迭代”：每生成一个 token 就重新组批，写完的立刻离开，新来的下一步就能加入，这就是今天所说的连续批处理（§3.2）。为了让进度不同的请求能放进同一批，它又提出选择性批处理：线性层这类逐 token 的算子把所有请求的 token 摊平成一个大矩阵一起算，只有注意力按请求拆开分别算（§3.4）。在 GPT-3 175B 上，相同延迟下吞吐量是 FasterTransformer 的 36.9 倍。

Orca 留下了一个具体的决定：为了防止显存被占满而卡死，它给每个请求按最大长度预先划好 KV 的位置（§4.2）。在它的实验里所有请求都恰好生成到上限，所以预留的位置全都用上了；而真实请求大多远短于上限，预留的大部分空间被白白占着。

3.2 vLLM：把操作系统的分页搬到 KV 缓存上

vLLM（SOSP 2023）正是从这里接着做的。它实测发现，当时的系统里 KV 缓存占用的显存只有 20.4%–38.2% 真正存了数据，其余要么是为将来的 token 预留的，要么是碎片（§3.1）。办法是照搬操作系统的虚拟内存：把 KV 切成 16 个 token 一块，按需分配，用一张块表记录“第几块逻辑 KV 存在哪块物理显存里”，多个请求可以通过引用计数共享同一块、写入时再复制（§4.2）。浪费被限制在每个请求最后一块之内，显存利用率升到 96.3%，相同延迟下吞吐量提高 2–4 倍。代价是注意力内核要多查一次表，单看这个算子比 FasterTransformer 慢 20%–26%，但批开大带来的收益远大于这点损失。

3.3 SGLang：请求结束了，KV 别扔

vLLM 的共享只发生在一个请求内部（比如同一个问题采样多个回答）。可 2023 年以后，大模型越来越多地被程序反复调用：多轮对话每轮都带上之前的历史，few-shot 评测每道题都带着同样的示例，智能体每一步都带着同一段系统提示。SGLang（NeurIPS 2024）在请求结束后不再丢弃 KV，而是把所有请求的 KV 放进一棵基数树，当作按“最近最少使用”淘汰的缓存来管理；新请求到来时自动找出最长的已缓存前缀直接复用，等待队列也按“能复用得越多越先跑”排序（§3）。论文的总结是吞吐量最高提高到 6.4 倍；本站从原图量出的逐项倍数（一张 A10G、Llama-7B、相对 vLLM v0.2.5）从约 1 倍到约 30 倍不等：在 HellaSwag 这种每道题共享大段示例的负载上最大，在输出很长、复用的前缀只占一小部分计算的多轮对话上基本没有提升（§6.2）。收益完全取决于前缀能复用多少。前缀缓存后来成了各家推理引擎的标配。

3.4 prefill 和 decode 互相拖累：分块，还是拆开

连续批处理让新请求随时可以加入，但新请求要先做 prefill。一段几千 token 的 prefill 可能要几百毫秒，如果它插进来的这一步里还有别人在解码，这些人一个字也出不来。Sarathi-Serve（OSDI 2024）把这种现象叫生成停顿（§3.2）：调度器要么优先 prefill（批大、吞吐高，但出字会突然卡住），要么优先 decode（出字平稳，但批越来越小、吞吐低），只能二选一。同一届 OSDI 上出现了两种解法，下图把它们和原来的做法放在一起：

第一种解法是 Sarathi-Serve 的分块预填充 + 无停顿批处理：把长 prompt 切成小块，每次迭代先放所有 decode，再按一个固定的 token 预算捎带一块 prefill（§4.1、§4.2）。在 P99 token 间隔的约束下，Mistral-7B 单卡的服务容量是 vLLM 调度策略的 2.6 倍，Yi-34B 两卡最高 3.7 倍。第二种解法是 DistServe（OSDI 2024）的 PD 分离：干脆把 prefill 和 decode 放到不同的 GPU 上，各自选最合适的并行方式和卡数，中间把 KV 传过去（§2.3）。它的指标是 goodput，在 OPT-13B 到 175B 上，每张卡能接的请求是 vLLM 的 2.0–5.7 倍（§6.2）。

两条路线后来都成了主流，而且常常一起用。vLLM 的 V1 引擎把分块预填充作为默认行为，几乎就是 Sarathi-Serve 的无停顿批处理（Sarathi-Serve 精读 §8.1）；DistServe 作者 2025 年的回顾说，拆分已成为几乎所有主流推理栈的默认做法（DistServe 精读“后来怎么样了”）；DeepSeek-V3 的线上部署也把 prefill 和 decode 放在不同的节点上（V3 精读 §3.4）。粗略地说，分块适合一组 GPU 内部控制干扰，部署简单；拆分适合大集群，让两个阶段各自优化，代价是 KV 迁移和更复杂的资源配比。

3.5 KV 变成了数据：存到 CPU、SSD，在机器之间搬

PD 分离之后，KV 不再是“一个请求在一张卡上的临时变量”：它要在 prefill 机和 decode 机之间传，值得复用的那部分还远远超过显存能装下的量。Mooncake（Kimi 的推理平台，FAST 2025 最佳论文）把 GPU 服务器上闲着的 CPU 内存、SSD 和网卡汇成一个跨机器的 KV 缓存池，调度器同时看“哪台机器存着这个请求能复用的缓存”和“哪台机器现在忙不忙”来分派请求，过载时按预测的负载提前拒绝（§3、§7）。它公开的一小时请求样本里，平均输入 8,590 个 token、输出只有 182 个，这种“输入很重”的负载正是缓存复用最值钱的场景（§4.1）。用替身 70B 模型回放真实请求时，满足延迟要求的请求比 vLLM 多约 75%。

LMCache（2025-10）把这一层做成了一个独立的开源组件：插在 vLLM、SGLang 和各种存储之间，把 KV 存到 CPU 内存、磁盘和远端，需要时搬回 GPU，或者在两个引擎之间传送。它的关键工程问题是“分页显存让搬运变成了大量小传输”，办法是把小页拼成 256 个 token 的大块再传，并让加载和逐层计算重叠（§5.1）。同期的 Strata（OSDI 2026）改用 GPU 线程直接搬小页、让调度器把加载时间算进去，在长上下文上比当时的 vLLM + LMCache 吞吐最高再高 5 倍（LMCache 精读“后来怎么样了”）。

示意图：KV 缓存的身份是怎么一步步变化的
按最大长度预留一个请求的临时变量（Orca）→ 分页、按需分配请求内可共享（vLLM）→ 基数树缓存请求之间复用前缀（SGLang）→ 在机器之间传prefill 池 → decode 池（DistServe）→ 分层存储CPU 内存、SSD、远端（Mooncake、LMCache）→ 模型自己把 KV 变小为了能存、能传（V4.1-Flash：每 token 890 字节）

3.6 同样的输入，为什么会得到不同的输出：批不变性

把温度调到 0，模型每一步都取概率最高的那个词，答案却仍然会变，无论是商业 API 还是自己部署的 vLLM、SGLang。Thinking Machines 的博客（2025-09）指出，流行的“GPU 线程并发、谁先算完不确定”的解释抓错了重点：同样的输入跑一千遍，单个内核的结果是逐位相同的。真正的原因是，RMSNorm、矩阵乘和注意力这三类内核会随批大小换一种切分工作的方式，加法的顺序随之改变；浮点加法不满足结合律，最后几位就不同了（§2）。而批有多大取决于服务器此刻有多忙，这对单个用户来说是不可知的。把三类内核改成与批大小无关的固定归约顺序后，Qwen3-235B 温度 0 采样 1000 次，从 80 种不同的回答变成 1 种；代价是变慢，作者的测试里总耗时从 26 秒变成 42 秒（§7.1、§7.2）。

这件事在服务里只是“可复现性”问题，在强化学习后训练里却是正确性问题：如果推理端（生成回答）和训练端（算概率）的数值逐位不同，名义上的 on-policy 训练其实已经偏离了 on-policy（第 6 节）。vLLM 和 SGLang 都在几周内加入了确定性模式（“后来怎么样了”），DeepSeek-V4 把批不变、确定性内核写进了自己的训练和推理栈（V4 精读 §7.2）。

读这一支论文时要留意：每篇的对照系统都是“前一代”，而且常常是作者自己复现或配置的版本：Orca 前面的调度器是作者按常见做法写的；Sarathi-Serve 的“vLLM”是同一代码库里的调度策略，“Orca”是复现的；Mooncake 的 arXiv 版没写 vLLM 的版本，也没说是否开了前缀缓存；LMCache 最大的倍数（2.3–14 倍）来自和“只在显存里缓存的 vLLM”比较，衡量的主要是“多一层容量”而不是实现好坏（LMCache 精读 §8.9）。另外各篇的指标不同（吞吐、goodput、服务容量、达标请求比例），倍数之间不能直接比较。第 10 节会把这些放在一起讲。

4 少存一点、存粗一点：KV 缓存压缩与低精度数值

这一节要回答的问题：分页让 KV 不再浪费显存，但 KV 本身还是那么大。要让它变小，只有三条路：少存一些 token（淘汰）、每个数少存几位（量化）、改模型结构让它从一开始就小（第 7、8 节）。前两条路在推理时直接对已经训好的模型动手，不用重新训练，但都是有损的。它们各自根据什么决定“丢哪些、怎么丢”？同样的“少几位”思路用到训练上，又是怎样从 FP8 一路走到 4 位的？
先补一点背景：量化、缩放因子和离群值。

量化就是把原本 16 位的数换成更少的位数来存（比如 8 位、4 位、2 位），能表示的数就从几万个变成几百个、十几个甚至 4 个。为了让一组数尽量用满这有限的几个格子，要先除以一个缩放因子（通常取这组数里绝对值最大的那个，叫 amax），量化后再乘回去。麻烦在于离群值：如果一组数里有一个特别大，缩放因子就只能按它来定，其余的普通数被压到很小，大多舍成 0 或误差很大。所以几乎所有量化方法都在回答同一个问题：缩放因子按什么分组（整个张量一个、每个 token 一个、每个通道一个、每 16 或 128 个数一个），以及怎样把离群值“摊平”（V3 精读 §3.3 有一个手算的例子）。

4.1 淘汰：问题知道自己要看哪里，但下一个问题不一定

SnapKV（2024-04）的出发点是一个观察：对每个注意力头来说，生成答案时会重点看提示里的哪些位置，在生成开始之前就能看出来（§3）。办法是看提示最后一小段 token（论文叫观察窗口，通常正好是用户的问题）在注意力里看向了哪里：每个头让观察窗口投票，选出得票最高的位置，再用池化把它们周围的邻居一起留下，其余的 KV 直接丢掉（§4.1）。它不需要训练，改几行代码就能接进模型。论文报告 16K 输入时每 token 解码延迟降到约 1/3.6，LongBench 上平均只掉 0.1–2 分。它不减少预填充的计算，而且它的压缩是为“这一个问题”做的。

后一点在真实服务里是个大问题：同一份文档会被反复提问，一段长对话要接着聊，前缀缓存让很多请求共用同一段前缀。KVzip（2025-05，NeurIPS 2025 口头报告）换了一个与问题无关的打分标准：在缓存后面接一句“复述前面的内容”和原文本身，用一次前向模拟复述，记下每个 KV 在复述时收到的最大注意力作为它的分数（§3.2）。一份能让模型把原文完整复述出来的缓存，原则上就保住了回答任何问题需要的信息。论文在 SQuAD 上测到，保留 30% 的 KV 时，SnapKV 每个问题重新压缩能答对约 91%，复用第一个问题压出来的缓存就只剩约 65%（读图，§2.2）；KVzip 在 Qwen2.5 系列上保留 25%–33% 时接近无损。代价是每份上下文要多花约 2 次预填充的计算来打分。

4.2 量化 KV：先找到离群值长在哪里

KIVI（2024-02）先做了一个细致的观察：key 缓存里有少数几个固定的通道数值特别大，而且一直是那几个；value 缓存没有这种规律（§4）。所以 key 要按通道分组量化（同一个通道跨多个 token 共用一个缩放因子，把大通道隔离开），value 按 token 分组。按通道分组要跨越多个 token，而 token 是一个个生成出来的，于是最近一段 token 先保持全精度，攒够一组再量化（§5.1）。不需要校准和微调，2 bit 下 Llama-2、Mistral 的分数与 16 bit 很接近；在一张 A100 上跑 Llama-2-7B，同样显存能装下 4 倍的批，吞吐是 Hugging Face 16 bit 基线的 2.35–3.47 倍。

有意思的是工业界最后没有走 KIVI 这条路。截至 2026-10，主流推理引擎先普及了 8 位的 FP8 KV，再逐步加入 4 位方案，而且几乎都按 token（每个头）缩放、再配合 Hadamard 旋转对付 key 的离群通道（KIVI 精读 §8.3）。本站的理解是：引擎按固定大小的块管理 KV，按 token 的缩放因子可以和这个 token 的数据存在同一块里、写一次就不再变；按通道分组则要跨 token 共享参数，还要为每个请求维护一段全精度缓冲，和分页、前缀共享都不好配合。这是一个“论文里最优的方案未必是系统里最合适的方案”的典型例子。

4.3 把权重、激活、KV 全部降到 4 位：旋转

只量化权重已经很成熟，但矩阵乘本身仍在 16 位下进行；要用上 GPU 更快的低位整数单元，矩阵乘的两个输入（权重和运行时产生的激活）都得是低位的，而激活里的离群值正是最大的障碍。QuaRot（2024-03）换了一个角度：离群值集中在少数几个坐标方向上，那就把整个隐藏状态乘一个正交矩阵、换一组坐标来表示。旋转不改变向量的长度，却会把一个方向上的巨大数值均匀地摊到所有坐标上（§3.2）。关键是利用“计算不变性”把大部分旋转提前乘进权重，推理时不花时间，只在少数无法合并的位置插入快速的 Hadamard 变换（§3.4）。LLaMA-2-70B 在权重、激活、KV 全 4 bit 下，困惑度只升高 0.47、零样本准确率保留约 99%；但同样的设置下 7B 掉 4.18 个点，LLaMA-3-70B 掉 10.7 个点（§5.5）。“先旋转、再量化”后来成了低比特推理的标准前处理，也进了 FA3 的 FP8 注意力和 NVFP4 训练（QuaRot 精读“后来怎么样了”）。

4.4 训练也要少几位：FP8 → 细粒度 FP8 → NVFP4

矩阵乘用的数越短，同一块芯片每秒能做的乘法越多、搬的字节越少。2022 年，NVIDIA、Arm、Intel 联合提出了两种 8 位浮点编码（FP8 格式）：精度较高、最大值 448 的 E4M3，和范围较宽、最大值 57,344 的 E5M2；建议前向的权重和激活用 E4M3、反向的梯度用 E5M2，每个张量配一个缩放因子（§3.1）。在 16 位硬件上模拟的实验里，从 CNN 到 175B 的 GPT 不改超参数就训到了与 16 位相当的精度。这两种编码后来原样成了 Hopper GPU 和 OCP 标准里的 FP8。

真把 FP8 用到几千亿参数的预训练上，问题就暴露了。DeepSeek-V3（2024-12）报告称这是 FP8 训练第一次在这个规模上被验证可行，为此它补了两样东西（V3 精读 §3.3.2）。一是细粒度缩放：激活每 1×128 个数、权重每 128×128 个数共用一个缩放因子，把离群值的伤害限制在一小块里。二是提升累加精度：H800 上 FP8 矩阵乘的累加只保留约 14 位，内维 4096 时最大相对误差接近 2%，于是每累加一段就把部分和搬到 FP32 里累加。

再往下是 4 位。一个 4 位浮点数（E2M1）只能表示 15 个值，必须把缩放分得更细。开放标准 MXFP4 是每 32 个数共用一个只能取 2 的幂的缩放因子；NVIDIA 的 NVFP4 是每 16 个数共用一个 FP8（E4M3）缩放因子，外加整个张量一个 FP32 缩放（NVFP4 精读 §2.3）。NVFP4 训练报告（2025-09）用它把一个 12B 的混合 Mamba-Transformer 训练了 10T token，配方是少数末端层留在 BF16、对权重梯度矩阵乘的输入做随机 Hadamard 变换、权重用二维缩放、梯度用随机舍入（§4）；损失与 FP8 基线相差 1%–1.5%，下游任务大体持平。同样的配方下，MXFP4 要多用 36% 的 token 才能追上 NVFP4（§5.1）。

容易误读的地方：淘汰类方法的速度对照几乎都是 Hugging Face 的原生实现，而不是 vLLM 这类引擎。SnapKV 的“3.6 倍”里有一部分是 Hugging Face 每步把整份缓存复制一遍的开销被一起省掉了；按一个接近带宽极限的理想引擎推算，同一设置下只有约 1.9 倍（SnapKV 精读 §5.7）。KIVI 的 16 bit 基线在批大小 32 到 96 之间吞吐不升反降，而批大小 32 时 KIVI 反而比基线慢 17%–19%（KIVI 精读 §6.8）。QuaRot 的精度来自 PyTorch 里的模拟量化，速度来自另写的 INT4 内核、只测一层，两者不是同一个产物（QuaRot 精读 §5.5）。

5 用闲着的算力换延迟：投机解码

这一节要回答的问题：decode 每一步只为每个请求生成一个 token，读一遍参数的时间里算力大半闲着。如果一次前向能顺便多检查几个位置，时间几乎不变。投机解码就是利用这一点的：先便宜地猜几个 token，再让大模型一次验证。它为什么能做到输出分布和原模型完全一样？“草稿从哪里来”这个问题，Medusa、EAGLE、DeepSeek 的 MTP 和 DSpark 各给了什么答案？为什么批越大，它越不灵？
先补一点背景：投机采样为什么是无损的。

设大模型在某个位置给出的分布是 \(p\)，草稿给出的是 \(q\)，草稿猜了一个 token \(x\)。投机采样以概率 \(\min\big(1,\,p(x)/q(x)\big)\) 接受它；被拒绝时，从修正过的分布 \(\max(0,\,p-q)\)（归一化后）里补采一个。可以严格证明，不管草稿猜得多差，最终每个 token 的分布都和大模型自己一个一个采样完全相同（投机解码精读 §2.3）。草稿的好坏只影响猜对的比例（接受率 \(\alpha\)），从而影响速度，不影响结果。验证从左往右进行，第一个被拒的位置之后的猜测全部作废。

这笔交易的本质是：每轮让大模型并行处理 \(\gamma+1\) 个位置，总运算量变多了（被拒的位置白算了），但参数和 KV 每轮只读一次、平均产出不止一个 token，所以读显存的总量变少了。它把稀缺的带宽换成了富余的算力（§3.4）。反过来说，一旦算力不再富余，这笔交易就不划算了。

5.1 从独立草稿模型到“长在大模型身上”的草稿头

投机解码（2022-11，ICML 2023 口头报告；DeepMind 的 Chen 等人同期提出了同样的投机采样）用同系列的小模型当草稿：在 T5-XXL（110 亿参数）上用现成的 T5-small 打草稿，批大小为 1 时加速 2–3.4 倍（§4.1）。它的麻烦在草稿模型本身：要找一个和大模型“想法一致”又足够小的模型并不容易，部署时还得同时伺候两个模型。

Medusa（2024-01）干脆不要草稿模型：在大模型最后一层的隐状态上接几个小的解码头，第 1 个头猜下下个 token、第 2 个头猜再往后一个，每个头给出几个候选，组合成一棵候选树，再用一张特殊的注意力掩码（树状注意力）一次前向验证所有分支（§2.2）。只训解码头时约快 2.2 倍，连主干一起训约快 2.8 倍；但后者以及它提出的“典型接受”都不再保证输出与原模型完全一致（§4.1）。它的弱点是各个头互相独立：猜第 \(t+3\) 个 token 时并不知道自己对第 \(t+2\) 个猜了什么。

EAGLE（2024-01）的作者有两个观察（§1 下）：与其让草稿器直接猜词，不如让它猜大模型输出层之前的特征向量，特征序列比词序列规律得多；而生成时的随机采样会让“下一个特征是什么”变得模棱两可，所以要把已经采出的那个词也一起交给草稿器。草稿器因此只是挂在大模型旁边的一层 Transformer，一次猜一棵树。在批大小 1、贪心解码下，7B–70B 的对话模型无损加速约 2.8–3.8 倍。后续的 EAGLE-2 按草稿头的置信度动态生长草稿树（“后来怎么样了”），EAGLE-3 去掉特征回归、融合低中高三层特征，并在训练时模拟多步起草（同上），最高加速约 6.5 倍。EAGLE 系列后来进了 SGLang、vLLM、TensorRT-LLM。

5.2 大批量下的投机解码：DeepSeek 的 MTP 与 DSpark

DeepSeek-V3 训练时带了一个多 token 预测（MTP）模块，推理时正好当草稿器用：主模型每生成一个 token，MTP 顺手猜出再下一个（V3 精读 §2.2）。线上数据是第二个 token 的接受率 80%–90%，生成速度是不用 MTP 时的 1.8 倍（V3 硬件反思精读 §2.3.3）。但它每轮只猜 1 个，这是最保守的配置（MTP-1）。为什么不多猜？因为线上同时服务着很多请求，目标模型每次验证能处理的 token 数是有限的，验证一个最终被拒的 token，就白白占掉了本可以服务别人的位置，负载越重越伤吞吐。

DSpark（2026-07）同时对付草稿质量和系统代价。草稿端用半自回归结构：沉重的主干一次前向并行算完一整块，最后加一个只看前一个已采样 token 的轻量顺序头，缓解并行草稿“越往后越前后不搭”的问题（§3.1）。验证端用按置信度调度：一个置信度头估计每个草稿 token 的存活概率，调度器结合引擎实测的吞吐曲线，按当前负载为每个请求挑选验证几个（§3.2.2）；调度只依赖已经确定的信息，所以仍是无损的。在 DeepSeek-V4 的线上流量里，相同吞吐下每用户的生成速度比原先的 MTP-1 快 60%–85%（V4-Flash）。

把这一支放在一起看，演化的主线是“草稿从哪里来”：独立小模型 → 大模型最后一层上的独立头 → 特征层上的一层自回归草稿器 → 训练时就带着的 MTP 模块 → 并行主干加顺序头。另一条线是“在什么负载下测”：前面几篇几乎都在批大小 1 上测，DSpark 第一次把“负载越重、验证预算越紧”当作设计的核心。

容易误读的地方：批大小。Medusa 论文附录自己的模拟显示，批大小增大后加速比迅速缩小，超过 32 时甚至可能变慢（Medusa 精读 §6）；EAGLE 的论文也承认批越大赚得越少；推理引擎为了在大批量下控制验证开销，常把草稿树换成短链（EAGLE 精读“进入推理引擎”）。所以“2–4 倍”应该读成“单用户、本地部署时的上限”，在线服务里的收益要看负载。DSpark 的线上数字反过来是在高并发下测的，但它来自 DeepSeek 内部流量，外界无法复现（DSpark 精读 §5.4）。

6 训练系统：把一个模型切到成千上万张卡上

这一节要回答的问题：第 1 节算过，训练时每个参数要占约 16 字节，一张卡装不下大模型，单卡也算不完。所以必须切开，而切开就要通信。几种切法各切了什么、各要付多少通信？上万张卡同时跑几个星期时，效率和稳定性靠什么保住？优化器能不能换掉用了好多年的 AdamW？到了强化学习后训练，为什么推理系统被拉进了训练循环，又带来了哪些新问题？
先补一点背景：几种并行方式。

数据并行：每张卡放一份完整的模型，各算一部分数据，最后把梯度加起来（all-reduce）。简单高效，但多加卡不省显存。张量并行：把每一层的权重矩阵按行或按列切开分给几张卡，每层算完都要通信拼结果，通信频繁，只适合放在一台机器内部的高速互联上。流水并行：按层切，第 1–10 层在卡 1、第 11–20 层在卡 2，数据像流水线一样流过，卡之间只传层与层之间的激活，但会有等待的“气泡”。专家并行：MoE 模型把不同的专家放在不同的卡上，每个 token 要被发到它选中的专家那里再收回来（all-to-all）。另外，all-reduce 可以拆成 reduce-scatter 加 all-gather 两步，这个事实是 ZeRO 的关键（ZeRO 精读 §7）。

6.1 Megatron-LM 与 ZeRO：从两头省显存

Megatron-LM（2019-09）找到了 Transformer 一层里最省通信的切法：MLP 的第一个矩阵按列切、第二个按行切，中间的激活函数各算各的，一个子块只需一次 all-reduce；注意力按“头”切，天然不需要通信（§3.2）。一层 Transformer 前向和反向各只要 2 次 all-reduce，用原生 PyTorch 加几行代码就能实现。靠它，作者在 512 张 V100 上训练了 83 亿参数的模型，整体达到 15.1 PFLOPs，相对单卡基线的扩展效率 76%。但每层都要通信，所以张量并行只能放在一台服务器内部（§3.5）。

ZeRO（2019-10）从另一头入手：保留数据并行的算法，但不再让每张卡存一整份模型状态，而是把优化器状态、梯度、参数依次切成 \(N\) 份，每张卡只存一份，用到别人那份时临时取来（§5）。作者证明，前两个阶段的通信量和普通数据并行完全一样，第三阶段只多 50%。下图是论文自己的例子：

6.2 万卡规模：效率和稳定性一起抓

MegaScale（字节跳动，NSDI 2024）是一份上万张卡的生产训练经验报告。效率一侧，它不只改系统，也改模型（并行 Transformer 块、滑动窗口注意力、LAMB 优化器），再针对数据、流水、张量三种并行各自的通信规律，把通信尽量藏到计算后面（§3.2）。在 12,288 张 GPU 上训练 175B 模型达到 55.2% MFU，同集群、同 batch 下 Megatron-LM 是 41.2%，前者是后者的 1.34 倍。稳定一侧，它用心跳、自检、两阶段检查点和低开销的 CUDA 事件计时来发现故障和慢节点（§4），在一次持续几周的生产训练中自动恢复了 100 多次，有效训练时间保持在 90% 以上。这一侧往往被忽视：几个星期里机器一定会坏，高 MFU 只在跑分的几分钟里好看是没有用的。

DeepSeek-V3 在专家并行上做了同样性质的事：新的流水调度 DualPipe 让一个微批的 all-to-all 通信藏在另一个微批的计算后面（V3 精读 §3.2.1），跨节点的 all-to-all 先走 InfiniBand、再在机内走 NVLink 转发。整个正式训练只用了 278.8 万个 H800 GPU 小时。

6.3 优化器：Muon 能不能换掉 AdamW

几乎所有大模型都用 AdamW。它为每个参数存两份统计量，而且对每个数字单独缩放，完全不理会“这一组数字本来是一个矩阵”。Muon 先像动量 SGD 那样平滑梯度，再把这个动量矩阵正交化（保留方向结构，把各方向的放大倍数统一成 1），用 Newton–Schulz 迭代近似求出，不需要做 SVD（Muon 精读 §2.1）。月之暗面的技术报告（2025-02）发现，要把它放大必须补上两样：像 AdamW 那样加权重衰减，以及按矩阵形状把每个矩阵的更新 RMS 对齐到 AdamW 的典型值 0.2，这样为 AdamW 调好的超参数能原样沿用（§2.2）。分布式实现装在 ZeRO-1 上，优化器状态比分布式 AdamW 少一份，通信最多多 25%（§2.3）。在 0.4B–1.5B 稠密模型的 scaling law 上，达到同样损失只需 AdamW 约 52% 的算力。

这个“约 2 倍”要打折扣：AdamW 基线逐档精调过，Muon 没有单独调，这对 AdamW 有利；但一项对每个优化器都做大范围超参数搜索的独立比较发现，相对精调过的 AdamW，加速从 0.1B 模型的约 1.4 倍降到 1.2B 模型的约 1.1 倍（Muon 精读 §3.6）。尽管如此，Muon 在一年里进了 Kimi K2、GLM-4.5、DeepSeek-V4 的训练，PyTorch 2.9 也内置了它（“后来怎么样了”）。对系统的人来说，它带来的新问题是：正交化需要完整的矩阵，而 ZeRO 和张量并行恰恰把矩阵切开了，后来的实现大多改成“把整个矩阵分给某一张卡”。

6.4 强化学习后训练：推理引擎进了训练循环

RL 后训练在系统层面非常特别。以 PPO 为代表，一轮迭代里有四个大模型（actor、critic、reference、reward），有三种性质完全不同的计算（逐 token 的生成、只做一次前向的打分、带反向的训练），计算之间还有严格的先后依赖；生成适合推理引擎的并行切法，训练适合训练框架的切法（HybridFlow 精读 §2.4）。HybridFlow（EuroSys 2025，开源实现就是 verl）让一个中心控制器编排模型之间的调用、每个模型内部仍由各 GPU 并行执行，几行代码就能写出 PPO；它的 3D-HybridEngine 让 actor 在训练和生成之间换并行切法时不留多余的权重副本（§5）。在最多 128 张 A100 上，它比当时的 RLHF 系统快 1.53–20.57 倍。

推理模型出现以后，生成变成了 RL 循环里最慢、最难排布的部分：一条回答可以长达几万 token，同一批里有的几百 token 就结束、有的写满上限。同步系统要等一批里最长的那条写完才能训练，先写完的 GPU 只能干等（AReaL 精读 §3.3）。AReaL（NeurIPS 2025）把生成和训练拆到不同的 GPU 上各自不停地跑，用“最大陈旧度”限制样本最多落后几个模型版本，用解耦的 PPO 目标修正旧样本带来的偏差（§5.1、§5.2）。在 1.5B–32B 推理模型上，同卡同步数下训练时间比自家同步版缩短最多 2.77 倍。

RL 还把第 3 节的批不变性问题变成了正确性问题。推理引擎和训练框架各自用不同的内核，算出来的 token 概率并不逐位相同，于是名义上的 on-policy 其实已经偏离。一条路是承认偏差、用截断重要性采样（TIS）去修正；另一条路是让两边逐位一致，Thinking Machines 的实验里两者之间的 KL 恒为 0（批不变性精读 §7.3、“后来怎么样了”）。到 2026-10，两条路都有人在走，逐位一致的代价是吞吐下降，具体多少随实现差别很大。

容易误读的地方：训练系统的倍数，分母常常是一个过时或有短板的版本。MegaScale 对比的 Megatron-LM 是 2023 年 1 月的提交，还没有后来加入的几类通信重叠开关（MegaScale 精读 §6.7）；HybridFlow 最大的 20.57 倍是对 NeMo-Aligner，论文说后者的生成引擎缺少 KV 缓存，生成最多占其迭代时间的 81.2%（HybridFlow 精读 §8.2）；AReaL 的“2.77 倍”是相对作者自己的同步版，相对 verl 的估计时间是 1.49–2.27 倍（推算），而且 verl 一行的精度引自别人用不同配方训出的模型（AReaL 精读 §7.7）。另外 MFU 的口径也要对齐：DeepSeek 的 V3 是 FP8 训练，MFU 却按 BF16 峰值算（V3 硬件反思精读“结果的份量”）。

7 注意力结构本身变了：稀疏、线性与混合

这一节要回答的问题：第 2 节的内核只能让精确的全注意力跑得更快，第 3–5 节的系统只能把 KV 管得更好、压得更小。可是上下文到了几十万、上百万 token，注意力的计算量随长度平方增长，每生成一个 token 要读的 KV 随长度线性增长，这两笔账系统层已经兜不住。2025 年起，“改模型”成了长上下文的主战场：只让每个 query 看一部分 KV（稀疏注意力），或者把一部分层换成状态大小固定的线性注意力。它们分别省下了哪一笔，代价是什么，什么时候需要重新训练？
先补一点背景：稀疏注意力是“先挑、再算”，线性注意力是“边读边写一张表”。

稀疏注意力把一次注意力拆成两步：先用一个便宜的办法估计哪些 key 重要（挑），再只在挑中的 key 上做精确的 softmax 注意力（算）。挑的粒度可以是一块连续的 token（适合 GPU 整块读写），也可以是单个 token（更准，但读写零碎）；可以每个头各挑，也可以一个 GQA 组共用一套（MiniMax 稀疏注意力精读 §2.3）。还有一个关键区别：是推理时才稀疏（模型训练时一直用全注意力），还是训练时就稀疏。

线性注意力把“回看全部历史”换成“维护一个固定大小的矩阵状态”：每读到一个 token，就把它的 key、value 写进这个矩阵；需要输出时，用 query 去查这个矩阵。矩阵大小不随长度变化，所以每步的成本固定，也没有越来越长的 KV 缓存；代价是一个固定大小的矩阵装不下任意多的信息，在“从上下文里准确找回某句话”这类任务上一直不如 softmax 注意力（Gated DeltaNet 精读 §2.1）。

7.1 免训练的稀疏：直接用在现成模型上

最省事的做法是不重新训练，推理时直接换上稀疏注意力。XAttention（2025-03，ICML 2025）只管预填充：把注意力矩阵切成 128×128 的块，每个小格只取一条反对角线上的分数来估计块的重要性（反对角线和注意力图里最常见的竖线、斜线结构都会相交），再按累计注意力达到阈值来选块（§2.2）。论文报告注意力算子最多快 13.5 倍；但端到端的预填充在 256K 时约 5 倍，统一阈值下 RULER 平均比全注意力低 2.6 分，128K 上即使逐头调过阈值也低 4.6–5.8 分（§5.7）。第 4 节的 SnapKV、KVzip 也属于这一类，只是它们省的是解码时的 KV。免训练方法的共同问题是：模型训练时从没“少看”过，推理时突然少看一部分，它并没有为此做过准备。

7.2 训练出来的稀疏：NSA、MoBA、DSA、MiniMax

DeepSeek 的 NSA（2025-02，ACL 2025 最佳论文）把这个问题说得最清楚。作者指出已有稀疏方法的两个“看上去成立”的假设：理论上省掉的计算常常没有变成实际的提速（有的只加速预填充或只加速解码，有的和 GQA 冲突），以及推理时才稀疏、训练时不稀疏，模型没有适应过（§2）。NSA 从预训练开始就用稀疏注意力，给每个 query 准备三份精简的 KV：把每段 token 压成一个代表的压缩分支、挑出 16 个最相关原始块的选择分支、最近 512 个 token 的窗口分支，三路用门控加权（§3.2）；同一个 GQA 组的所有头共用一套选择，才写得出高效的内核（§3.6）。在一个 27B 的 MoE 模型上，效果不低于全注意力，64K 序列上注意力内核前向快 9 倍、反向快 6 倍。

同一周发布的月之暗面 MoBA 走了一条更简单的路：把上下文切成大块，每个 query 用自己和每块“平均 key”的内积挑出几块（自己所在的块必选），不加任何参数，所以可以和全注意力分层或分阶段混用，还能直接复用 FlashAttention 现成的变长内核（§2.2.1、§2.3）。从 Llama-3.1-8B 续训到 100 万 token 后多数基准与全注意力接近，100 万 token 预填充时注意力层快 6.5 倍、整个模型快 3.34 倍；但最能考验稀疏的 RULER@128K 在正式版里落后 3.6 个百分点（§3.5）。

到了 671B 的 DeepSeek-V3.2（2025-12），DeepSeek 没有用 NSA，而是换了一套更细的机制 DSA：一个用 FP8 计算的轻量“闪电索引器”给前面每个 token 打分，每个 query 只对分数最高的 2048 个 token 做注意力（§2.1.1）。它不是从头训练的，而是在 V3.1-Terminus 上先让索引器模仿稠密注意力、再让整个模型适应稀疏（§2.1.1 原文）。按报告图 3 的线上成本，128K 位置上解码的单 token 成本约为原来的 1/8.7（本站读图）；但在约 4.8K 以内的短序列上，V3.2 反而略贵一点（§2.3）。

MiniMax 稀疏注意力（2026-06）的来历很能说明这一领域还没有定论：MiniMax-01 和 M1 用的是“线性注意力 + 少量 softmax 注意力”的混合结构，到 M2 又退回了标准的全注意力，理由是混合结构在大规模下的多步推理上有明显短板、配套的推理基础设施也不成熟（§1）。新方案 MSA 建在 GQA 之上：每个 GQA 组给 128 个 token 一块的 KV 打分，各挑 16 块，主分支只在这 2,048 个 token 上做精确注意力；索引分支没法直接从语言模型损失学（挑前 k 个没有梯度），作者用 KL 损失让它模仿主分支的注意力分布（§4.1）。在 109B 多模态 MoE 上训练 3T token，效果与全注意力相当；1M 上下文时注意力算子在 H800 上预填充快 14.2 倍、解码快 7.6 倍。

7.3 线性注意力与混合：Gated DeltaNet、Kimi Linear、门控注意力

另一条路是把大部分层换成线性注意力。Gated DeltaNet（ICLR 2025）的出发点是两种已有改进恰好互补：门控（Mamba2）每一步给整个状态乘一个 0 到 1 之间的数，能迅速清空旧记忆，却没法只忘掉某一条；delta 规则（DeltaNet）写入新的“键→值”之前先读出旧值、只写入差值，能精确地改某一条，却没法一下子清掉大量过时的内容（§3.1）。把两者乘在一起，在 1.3B 参数、100B token 的统一对比里全面优于 Mamba2 和 DeltaNet，但在真实检索任务上仍比 Transformer 低 6.4 分，这就是“固定大小状态有上限”的直接证据（§7.7）。所以工业界用的是混合：Qwen3-Next（80B 总参数、每 token 激活 3B）每 3 层 Gated DeltaNet 配 1 层全注意力（“后来怎么样了”）。

Kimi Linear（2025-10）把 Gated DeltaNet 里“整个状态一起遗忘”的标量门改成“每个通道各自遗忘”的逐通道门（KDA），并为它设计了比通用写法快约一倍的分块内核（§3）；再按 3 层 KDA 配 1 层 MLA 搭成 48B 总参数、3B 激活的模型，MLA 层干脆不加位置编码（§4.3）。在同样 1.4T token 的训练下，它在多数基准上超过全 MLA 基线；1M 上下文时 KV 缓存少约 75%，单请求解码快约 2.2 倍（§5.6）。2026 年的 Kimi K3 沿用了这套设计。

保留下来的那几层全注意力也在改。Qwen 团队的门控注意力（NeurIPS 2025 最佳论文）在每个注意力头的输出上乘一个由当前 token 算出的 sigmoid 门，15B MoE 和 1.7B 稠密模型都更好、训练更稳（§2.2）。它对系统的人有直接意义：这道门消除了“注意力汇”（大量注意力堆在开头几个 token 上）和超大激活值（§4.3），而这两样正是量化和“保留开头几个 token”式 KV 淘汰最头疼的东西（论文没有直接测，见 §7 的本站分析）。Qwen3-Next 和 Qwen3.5 的全注意力层都用了它。

贯穿这一节的还有位置编码。几乎所有模型都用 RoPE（2021-04）：把 query 和 key 的每两维看成平面上一个点，按位置转过一个角度，点积时只剩角度之差，所以注意力分数只依赖相对位置（§3.2）。它看上去和系统无关，实际上处处牵连：MLA 为了能把 KV 压成低维潜向量，必须让 RoPE 单独走一路 64 维的 key（V3 精读 §2.1.1）；QuaRot 对 key 的旋转因为 RoPE 而没法提前融合进权重（QuaRot 精读 §4.5）；混合架构里只有全注意力层用 RoPE，Kimi Linear 的 MLA 层干脆不用，让 KDA 层承担位置信息。

8 DeepSeek 这条线：模型、系统、硬件一起设计

这一节要回答的问题：前面几节是按“方法”切开讲的，可在真实的大模型里，这些方法是同时做出的决定：结构怎么改，取决于硬件哪里短；系统怎么写，取决于结构长什么样。DeepSeek 从 2024 年底的 V3 到 2026 年 9 月的 V4.1-Flash，公开了一串少见地详细的技术报告，本站全部有精读。把它们按时间读一遍，可以看到同一个团队每一步选了哪个瓶颈来打、用了前面哪几支的方法、又把什么问题留给了下一步。

8.1 V3：在被削弱的硬件上把训练成本压下来

DeepSeek-V3（2024-12）是一个总参数 671B、每个 token 只激活 37B 的 MoE 模型，在 14.8T token 上预训练。它的报告用近一半篇幅解释成本是怎么压下来的，几乎每一项都对应本页前面的一节：结构上，MLA 把每个 token 每层的 KV 压成 576 个数（512 维潜向量加 64 维带位置信息的 key），约为同规模标准多头注意力的 1/57（§2.1.1）；负载均衡不用辅助损失，改用随负载调整的偏置项（§2.1.2 续）；多 token 预测模块训练时提供额外信号，推理时当草稿器（第 5 节）。系统上，DualPipe 把专家并行的通信藏进计算（第 6 节），三次 GEMM 全部用细粒度缩放的 FP8 计算（第 4 节）；部署时 prefill 和 decode 放在不同的节点上，并用冗余专家保持负载均衡（§3.4）。

一年后的 ISCA 论文 《DeepSeek-V3 硬件反思》（2025-05）从硬件的角度讲同一件事：H800 是 H100 的出口合规版，机内 NVLink 带宽从 900 GB/s 被削到 400 GB/s，所以 V3 训练时完全不用张量并行、MoE 路由限制每个 token 最多去 4 个节点（§4.3）；FP8 矩阵乘的累加精度不够、细粒度缩放要靠软件绕过（§3.1）；集群网络用“多平面两层胖树”，在 2,048 张卡上实测和单平面多轨网络几乎一样快。论文最后给芯片、网卡和交换机厂商列了一份愿望清单。它的大部分内容是设计回顾和纸上推算，真正的实测集中在网络（“结果的份量”）。

8.2 V3.2 → V4 → V4.1-Flash：瓶颈从算力一路移到存储

V3 之后，DeepSeek 的每一代都选了一个新瓶颈。V3 的 MLA 已经让每个 token 的 KV 很窄，可上下文一长，注意力的计算和每步读取还是随长度增长。V3.2（2025-12）用 DSA 让每个 query 只看 2048 个 token，打的是这两笔（第 7 节）。

V4（2026-04）走第三步：直接把 KV 序列本身变短。它的注意力层分两种（§4.1）：CSA 把每 4 个 token 压成 1 条 KV，再用 DSA 那样的索引器挑出少数几条细看（§4.2）；HCA 把每 128 个 token 压成 1 条，然后全看（§4.5）。两种层交替堆叠，每层再配一个只看最近 128 个原始 token 的滑动窗口。报告估算，在 100 万 token 的位置上，V4-Pro 生成一个 token 的计算量只有 V3.2 的 27%、KV 只有 10%（§4.7）。V4 同时是一份系统报告：残差流加宽成 4 路的 mHC（§3）、Muon 优化器、把专家并行通信融进计算的 MegaMoE、批不变的确定性内核、把压缩 KV 存到磁盘的推理框架（§9.1），以及后训练里的 FP4 量化感知训练（§13.1）。几个月后，DSpark 替换了 V4 线上服务里的 MTP-1（第 5 节）。

与此同时，Engram（DeepSeek 与北京大学，2026-01）提出了另一条稀疏维度。语言里有一大类内容不需要“算”、只需要“查”：人名、固定搭配、代码里的惯用写法，看到前两三个 token 基本就能确定。Engram 用当前位置最近两三个 token 的哈希 N-gram 直接从一张巨大的表里查出向量，作为与 MoE 条件计算并列的“条件记忆”（§2.2）。总参数和计算量固定时，把约 20%–25% 的专家参数挪给查表，验证损失最低（§3.1）。对系统更重要的是：查表地址只取决于输入 token，可以提前算出来，所以 1000 亿参数的表可以放在 CPU 内存里预取，推理吞吐只降不到 3%（§6.4）。这是“用便宜的存储换贵的显存和算力”的又一个例子。

V4.1-Flash（2026-09）把题目直接写成“把 KV 缓存压到极限”。原因是使用方式变了：智能体反复调用工具、每一轮都把很长的历史重新喂给模型，输出却很短；稀疏注意力已经把长上下文的计算压下来了，剩下的瓶颈是 KV 的存储和搬运：要占显存，要为了复用长期存到 SSD 上，要在机器之间传。它在三个层面同时压缩（§2.3）：新的注意力 CSA2 让 40 层里只有 4 层自己存全局 KV，其余层复用；全局 KV 用 FP4 存储，后训练里用量化感知训练让模型适应；部署时用“SWA 有界重放”近似重算滑动窗口部分，不再长期保存它（§3.2.2）。常驻显存的全局 KV 降到每个 token 890 字节，约为 V4-Flash 的 1/4。前 20 层还兼作“因果编码器”，让预填充只算一半的层（§2.2），Engram 和 DSpark 也都装了进去。

这条线值得单独读，是因为它把“AI Infra”和“模型设计”的边界彻底打通了。每一个结构决定都同时是一个系统决定。MLA 的 576 维是为了让 KV 窄到可以多开批；DSA 实现在 MLA 的“MQA 模式”上，是为了让 128 个头共用同一套选择、取一次 KV 条目就能被所有头复用，这样内核才喂得饱张量核（V3.2 精读 §2.1.3）；V4.1-Flash 的 FP4 KV 敢去掉 NVFP4 的第二级全局缩放，是因为潜向量存入缓存前经过 RMSNorm、数值范围有界，去掉之后每个条目正好 288 字节，缓存布局更简单（V4.1-Flash 精读 §2.4.4）。反过来，每一个系统约束也写进了结构：节点受限路由来自 NVLink 被削，Engram 能用是因为查表地址可以提前算出来。

读 DeepSeek 报告时要留意：它们给出的效率数字大多是按结构估算的，而不是端到端测量。V4 的 27% 和 10% 是估算的单 token 计算量和存储量，报告全文没有给出任何服务吞吐或延迟（V4 精读 §4.8）；V4.1-Flash 的 890 字节同样是按设计算出来的。更要紧的是压缩的代价：CSA、HCA、CSA2、FP4 KV 都改变了模型算出来的东西，可两份报告都没有“同样数据、同样规模下压缩与不压缩”的消融。V4.1-Flash 和 V4-Flash 的对比里，总参数近两倍、训练 token 多约 40%、数据流程重做，压缩的代价可能被这些掩盖了；长上下文基准只报了 LongBench-V2 一项（V4.1-Flash 精读“结果的份量”）。

10 结果的份量：跨论文看，哪些数字站得住

这一节要回答的问题：每篇精读页都有一节“结果的份量”，逐条拆开那篇论文的数字是在什么条件下测的。把 42 篇放在一起看，同样的问题会反复出现：基线是一个很慢的实现，加速只在批大小 1 时成立，算子的倍数被当成端到端的倍数，对手是一个过时的版本，数字是算出来的而不是测出来的，“持平”只跑了一次。这一节把这些模式归成几类，每类举本站精读页里的具体例子；最后说哪些结论经过了独立复测或大规模采用，可以放心用。

10.1 分母是谁：Hugging Face 的朴素实现，还是优化过的引擎

压缩和投机解码的论文，最常用的基线是 Hugging Face Transformers 里的逐 token 生成。这个实现每一步都有大量 Python 调度和内核启动的固定开销，离带宽极限很远。Medusa 精读 §5.5 算过：A100 上 Vicuna-7B 读一遍参数约 7 毫秒，理论上每秒能生成约 140 个 token，而论文里的 Hugging Face 基线每秒只有 37 个（推算）。任何减少解码步数的方法，都会顺带把这些固定开销一起省掉，所以相对一个慢基线的加速比，天然比相对一个快引擎的大。

本站几篇精读给出了同一个方法“换个分母”的数字。EAGLE 接到用编译和量化优化过的 gpt-fast 上，额外加速从约 2.8 倍降到 1.8 倍（FP16）和 1.5 倍（int4）（EAGLE 精读 §4.2）；EAGLE-3 在 SGLang 里相对 SGLang 自己的普通解码约 2.36 倍，而在 Hugging Face 基线上是 4.40 倍。SnapKV 在 Hugging Face 上测得约 3.6 倍，按一个接近带宽极限的理想引擎推算只有约 1.9 倍，因为 Hugging Face 的动态缓存每步把整份 KV 复制一遍，SnapKV 的缓存小，正好躲过了这笔开销（SnapKV 精读 §5.7）。KIVI 的 16 bit 基线在批大小 32 到 96 之间吞吐不升反降，说明它每一步还有和 KV 体积一起增长的额外开销（KIVI 精读 §6.8）。

10.2 批大小 1：只对单用户成立的加速

投机解码的全部收益来自“decode 时算力闲着”。批大小为 1 时这一点最成立，批一大，算力就不再富余。所以这一支的论文几乎都在批大小 1 上测：投机解码、Medusa、EAGLE 都是如此，Medusa 附录自己的模拟显示批大小超过 32 时可能变慢（§6）。其他方向也有同样的问题：XAttention 的官方实现在代码里断言批大小为 1（XAttention 精读 §5.7），KVzip 和 SnapKV 的速度实验都只用了很小的批。对于要同时服务几十上百个请求的在线系统，这些数字只能当作上限。

注意力内核和稀疏注意力的论文，报告的多是单个注意力算子的速度。整个模型里还有线性层、MoE、通信，注意力占的比例随长度变化，所以端到端的倍数总是更小，而且在中等长度时小得多。下图把本站精读页里能找到的“同一个结论的两种数字”放在一起：

10.4 对手是哪个版本、怎么配的

系统论文几乎都和“上一代”比，而上一代往往不是发表时最强的版本，或者是作者自己配置、复现的。MegaScale 的 1.34 倍对比的是 2023 年 1 月的 Megatron-LM，后来加入的几类通信重叠开关都还没有（§6.7）。FA3 的主要对照 FA2 用的是 Ampere 指令，1.5–2 倍里有相当一部分是“换用 Hopper 指令”本身（§4.7）。FA4 标题里比的是 cuDNN 9.13，而 cuDNN 随后吸收了 FA4 公开代码里的技巧，同一张图里的 cuDNN 9.19 前向与 FA4 基本持平（§7.5）。FlashInfer 的 arXiv 第一版对比过 TensorRT-LLM，结果在 ShareGPT 上更慢，正式版删掉了这组对比（§4.7）。HybridFlow 最大的 20.57 倍来自生成引擎缺少 KV 缓存的 NeMo-Aligner（§8.2）。Sarathi-Serve 对 Orca 的倍数用的是复现版，还按最大长度预留 KV，混合了调度和显存管理两方面的差距（§5.6）。

也有方向相反的例子：Muon 的论文里，AdamW 基线逐档精调过，Muon 没有单独调，这对基线有利；可独立的系统比较仍然发现，加速比随模型变大而缩小，很多“2 倍”的说法反映的是基线没调好（Muon 精读 §3.6）。这说明“基线调得多认真”本身就是一个需要单独核对的变量。

10.5 算出来的，不是测出来的

有不少“结果”其实是按结构或规格推出来的。FP8 格式论文的所有训练都在 16 位硬件上模拟，没有任何吞吐、显存或功耗的测量，“FP8 能加速训练”是基于硬件规格的推论。NVFP4 报告明确不讨论运行效率，2–3 倍是 Tensor Core 的峰值。QuaRot 的精度来自模拟量化，速度来自另写的内核、只测一层，两者不是同一个产物。DeepSeek 的 V4 27% 与 10%、V4.1-Flash 的 890 字节都是按结构算的；V3 硬件反思大部分是设计回顾和纸上推算，真正的实测集中在网络，而且它的 MFU 是按 BF16 峰值算的，按 FP8 峰值算大约要减半（推算）。按结构算出来的数本身不会错，但它们只说明“少存了多少、少算了多少”，不说明“掉了多少精度”和“真实服务快了多少”。

10.6 指标的口径与截取点

同一篇论文里的几个倍数，常常来自不同的实验和定义。Orca 的 36.9 倍是在中位归一化延迟 190 ms/token 这一个点上截出来的，那里对手已经接近饱和（§6.6）。DistServe 摘要里的“7.4 倍的请求”和“12.6 倍的 SLO”不是同一个实验、也不是和同一个对手比的（§6.2）。Sarathi-Serve 的服务容量只约束 token 间隔、不约束首 token 延迟，而分块恰恰让首 token 变慢（§5.6）。Mooncake 用“最低负载时延迟的 10 倍和 5 倍”作为相对 SLO，又在稀疏的请求速率测点上比较，所以百分比有明显的台阶，525% 对应的是 1.25 对 0.2 个请求每秒（§8.6）。SGLang 的“最高 6.4 倍”，本站从原图找不到精确对应的柱子（§6.2）。

10.7 只跑一次的“持平”

改模型结构或数值格式的论文，几乎都是每个设置只训一次、不报方差。在这种情况下，小于评测噪声的差距说明不了谁更好。NSA 在通用基准上的不少差距只有千分之几（MATH 0.263 对 0.264），而且这些输入短到稀疏分支能覆盖全部历史（§4.6）；Engram 的 HumanEval 只有 164 道题，+3.0 个百分点相当于多做对约 5 道（推算，§4.3）；DSA 的对比里，AIME、HMMT 这类几十道题的基准一道题就是几分（V3.2“结果的份量”）；MSA 表里有 +12.8 这样的大幅波动，更像检查点在个别基准上的不稳定（§7.5）；AReaL 每个设置只跑一次、随机种子固定为 1（§7.7）。最稳妥的读法是把这些“持平”“略好”都读成“没有明显变差”。反过来，方向一致的系统性差距值得注意：FP8 格式论文里 5 个 GPT 模型的 FP8 困惑度全部更高（§4.7），NVFP4 的代码任务两项都落后（§5.2）。

10.8 外界无法核实的生产数字

工业界的报告常常引用线上数据，但不给统计方法。Mooncake 会议版说 Kimi 在 A800 和 H800 集群上比此前基于 vLLM 的系统多处理 115% 和 107% 的请求，这是“历史统计”，没有给出时间段和比较条件（§8.6）；MoBA 说“已用于 Kimi”，正式版改成了“已部署处理实际生产中的长上下文负载”（§3.5）；LMCache 的企业经验只给相对值（§8.9）；DSpark 的 60%–85% 来自 DeepSeek 内部流量（§5.4）；Qwen3-Next 的“快 10 倍”是拿每 token 激活 3B 的 MoE 和稠密的 Qwen3-32B 比，把 MoE 和线性注意力两件事的收益算在了一起（Gated DeltaNet 精读“后来怎么样了”）。这些数字可以当作“方向是对的”的证据，不能当作可复现的倍数。

10.9 哪些结论站得住

说了这么多需要打折的地方，并不是说这些论文不可信。真正经得住检验的结论有两类来源。第一类是被大规模采用的设计：连续批处理、分页 KV、前缀缓存、分块预填充、PD 分离、FlashAttention 系列、E4M3/E5M2 两种 FP8 编码、EAGLE 式的草稿头，今天都是主流引擎和硬件的默认配置，它们的价值已经在无数真实负载上兑现了，只是兑现的倍数通常比论文小。第二类是独立复测过的结论：Spec-Bench 在统一环境下确认了 EAGLE 系列领先、Medusa 落后于后来的方法（Medusa 精读 §5.5）；FlashPrefill 在另一种 GPU 上复测 XAttention，速度倍数低得多，RULER 上比全注意力低约 1.5 分，可以当作精度代价的独立参照（XAttention 精读“后来怎么样了”）；NVIDIA kvpress 独立实现了 KVzip 并维护排行榜（KVzip 精读“后来怎么样了”）；vLLM 团队按配置独立核算了 V4 的 KV 大小（V4 精读 §4.8）；对 Muon 的独立比较确认了“确实更快、但没有 2 倍”。读一篇新论文时，可以先问三个问题：它的分母是谁？它在什么批大小、什么长度下测？它测的是一个算子还是整个系统？

11 还没解决的问题（截至 2026-10）

这一节要回答的问题：到 2026 年 10 月，这个领域还有哪些问题悬而未决？下面每一条都来自本站精读页里作者自己承认的局限、“后来怎么样了”里的进展，或者几篇论文之间的矛盾。
  • 压缩 KV 的精度代价，还没有人量清楚。DeepSeek 的 V4、V4.1-Flash 把每个 token 的 KV 从几十 KB 压到几百字节，可两份报告都没有“同条件下压缩与不压缩”的消融，长上下文检索类基准也报得很少；本站也没有找到任何独立复现“KV 压缩几乎不掉精度”的工作（V4.1-Flash 精读“结果的份量”）。免训练的淘汰方法也有同样的问题：与问题无关的压缩（KVzip）还没有进入主流推理引擎（KVzip 精读“后来怎么样了”）。
  • 长上下文走哪条路，各家答案不同。Qwen（3:1 的 Gated DeltaNet 混合）和 Kimi（KDA 混合，K3 沿用）押线性注意力；DeepSeek（MLA → DSA → CSA/HCA → CSA2）押稀疏加压缩；MiniMax 从线性混合退回全注意力，再走到稀疏注意力（MSA 精读 §1）。几条路之间几乎没有同预算、同数据的正面对比，而它们真正的分歧（多步推理、超长距离的精确检索）恰恰是常规基准测不出来的。
  • 硬件跑在前面，内核追在后面。FA4 说明，新硬件让矩阵乘单元涨得最快，指数单元和共享内存几乎不动，于是每一代都要重新找瓶颈、重写内核；而到了 B300，指数单元又翻了倍，FA4 的软件指数在那里已经被关掉（FA4 精读 §7.5）。CuTe-DSL、TileLang 这类领域语言降低了重写的成本，但“稀疏、压缩、低精度的新注意力能否像 FlashAttention 那样快速跟上每一代硬件”还是开放问题。
  • 确定性和训推一致要付多少钱、值不值。批不变内核让推理可复现、让 RL 的采样端和训练端逐位一致，但 SGLang 测得平均减速约 34%，vLLM 与 TorchTitan 的逐位一致 RL 演示整体慢 2.4 倍；也有人保留高性能推理内核、只把它们改成与批组成无关，吞吐保住了九成以上（批不变性精读“后来怎么样了”）。逐位一致和“承认偏差、用 TIS 修正”哪个更划算，还没有定论。
  • 投机解码在高并发和新结构下怎么用。DSpark 第一次把“负载越重、验证预算越紧”当成设计核心，但起草本身的计算不管验证几个都要付（DSpark 精读导读）；投机解码和稀疏注意力、MoE 专家并行、PD 分离叠在一起时各自的收益怎样折算，还缺少公开的系统研究。
  • KV 作为长期数据，怎么管。Mooncake 的期刊版透露，线上缓存命中率最高约 50%，高峰期跌到 20% 以下（Mooncake 精读 §8.6）；V4.1-Flash 为了不长期保存滑动窗口 KV，接受了“有界重放”带来的近似状态。KV 该存在哪一层、存多久、什么时候宁可重算，以及不同模型各自不同的 KV 格式怎样被统一的缓存层管理，都还在摸索。
  • 低精度训练的端到端收益。FP4 预训练已经在 12B、10T token 上证明“能收敛”，但端到端快多少没有公开测量；NVFP4 与 MXFP4 谁更合适，取决于配方和硬件（NVFP4 精读 §5.2）。
  • RL 系统走向智能体。AReaL 之后，单条轨迹的工具调用超过 100 轮、输出超过 40 万 token 的训练已经出现（AReaL 精读“后来怎么样了”），生成和训练更加不均衡，异步带来的离策略偏差也更大。系统怎样在这种负载下既保住吞吐、又保住算法的正确性，是下一阶段的主题。
  • 新优化器的规模化。Muon 已进入多家前沿模型，但它的优势有多大、在更长的训练和更大的模型上会不会继续缩小，独立证据还不多；它和 ZeRO、张量并行的冲突，也让分布式实现走向“按整个矩阵分配”的新方案（Muon 精读“后来怎么样了”）。

12 阅读路线

这一节要回答的问题：42 篇精读从哪里读起？下面按三种目的给出三条顺序，每条七到十篇，前面的为后面打基础。

入门：先弄懂推理为什么贵。适合第一次接触这个领域的读者，读完能看懂第 1 节的那几笔账，以及大部分推理系统论文在说什么。

  1. vLLM：批处理、KV 缓存、显存管理，几乎所有后续论文的共同前提（本站唯一带全文翻译的精读）
  2. Orca：连续批处理是怎么来的
  3. FlashAttention：存储层次和“IO 感知”
  4. 投机解码：带宽受限时怎样用算力换延迟，以及无损的证明
  5. Sarathi-Serve 与 DistServe：prefill 和 decode 的干扰，两种解法
  6. V3 硬件反思 §2.1：从硬件角度重算一遍 KV 的账
  7. SnapKV 或 KIVI：第一次接触有损的 KV 压缩

偏系统：服务与训练的工程。适合做推理引擎、训练框架或集群的读者。

  1. Megatron-LM → ZeRO：两种省显存的切法
  2. MegaScale：万卡训练的效率与容错
  3. SGLang：跨请求的前缀复用
  4. Mooncake → LMCache：KV 离开 GPU 之后
  5. FlashInfer：推理服务里的注意力内核
  6. 批不变性：为什么同样的输入会得到不同的输出
  7. HybridFlow → AReaL：RL 后训练系统，从同步到异步
  8. DeepSeek-V3 §3：DualPipe、跨节点 all-to-all、FP8 训练的完整工程

偏前沿：长上下文与模型–系统协同设计。适合关心 2025–2026 年模型结构走向的读者，最好先读完入门路线的前三篇。

  1. FlashAttention-3 → FlashAttention-4：硬件变了，瓶颈怎么跟着变
  2. NSA 与 MoBA：同一周发布的两种可训练稀疏
  3. DeepSeek-V3.2（DSA）：稀疏注意力在 671B 模型上的落地
  4. Gated DeltaNet → Kimi Linear：线性注意力的混合路线
  5. 门控注意力：保留下来的全注意力层怎么改
  6. MiniMax 稀疏注意力：从线性混合走回稀疏的一家
  7. DeepSeek-V4 → V4.1-Flash：把 KV 序列压短，再把存储压到极限
  8. EAGLE → DSpark：高并发下的投机解码

如果只关心数值精度，可以单独走一条短线：FP8 格式 → QuaRot → DeepSeek-V3 §3.3 → NVFP4，最后看 V4.1-Flash 的 FP4 KV。

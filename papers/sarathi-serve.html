0 导读：这篇论文解决什么问题

大模型推理服务处理一个请求分两个阶段。第一个阶段叫 prefill（预填充）：把用户的整段输入一次性算完，得到第一个输出 token。这一步一次处理成百上千个 token，GPU 的算力能被吃满，但耗时较长。第二个阶段叫 decode（解码）：之后每一步只为这个请求生成一个 token。这一步算得很少，GPU 的算力大部分闲着，时间几乎都花在从显存里读模型权重上。正因为 decode 这么“不划算”，推理系统都想把很多请求的 decode 拼成一个大批一起算：读一遍权重，就能同时为几十上百个请求各生成一个 token，吞吐量随之成倍上升。

麻烦在于请求是陆续到达的。新请求必须先做 prefill，才能加入 decode 的大批。如果系统一有空就先给新请求做 prefill（vLLM 和 Orca 的做法），批很快变大，吞吐量高；但 prefill 一步可能要几百毫秒甚至几秒，这段时间里正在生成的请求一个字也出不来，用户看到的是输出突然卡住。论文把这种现象叫生成停顿（generation stall）。反过来，如果系统先把手头的 decode 都做完、再接新请求（FasterTransformer 的做法），出字就很平稳，但批会随着请求一个个结束而越变越小，吞吐量很低。论文把这称作吞吐与延迟的两难：现有的调度器只能二选一。此外，当模型大到要跨机器用流水线并行部署时，各次迭代的计算量忽大忽小，流水线的各级之间会互相空等，形成流水线气泡，同样浪费 GPU。

Sarathi-Serve 是一个调度器，它的办法有两部分。第一是分块预填充（chunked prefill）：把长输入切成大小相近的块，一次迭代只算一块。第二是无停顿批处理（stall-free batching）：每次迭代先把所有正在 decode 的请求放进批里，再用剩下的 token 预算装 prefill 块。因为 decode 批本来就用不满算力，捎带一块 prefill 只会让这一步慢一点，而不会让正在生成的请求停几秒；又因为每一步的 token 数都被预算限住，各次迭代的耗时变得差不多，流水线气泡也随之变小。

论文的结果是：在“99% 的出字间隔不超过某个上限”的约束下，Mistral-7B 单张 A100 能稳定承受的请求速率（论文称为服务容量）是 vLLM 的 2.6 倍，Yi-34B 两张 A100 最高是 3.7 倍；Falcon-180B 跨两台机器做流水线并行时，最高是 Orca 的 5.6 倍。摘要里的 5.6 倍容易被读成“比 vLLM 高 5.6 倍”，从原图看它是相对 Orca 的数字，相对 vLLM 最高约 3.6 倍，第 5 节会把这些条件一一摊开。这套做法后来成了 vLLM 等主流推理引擎的默认调度方式。

1 引言：吞吐和延迟为什么难以兼得

这一节要回答的问题：推理服务既要便宜（吞吐量高），又要好用（响应快、出字平稳）。提高吞吐量最直接的手段是把很多请求拼成大批一起算，但拼批的方式会伤到延迟。现有系统是怎么拼批的，各自伤在哪里？Sarathi-Serve 准备怎么同时保住两边？
先补一点背景：用户感受到的两个延迟，TTFT 和 TBT。

用聊天机器人时，用户先等第一个字出来，然后看着字一个接一个地蹦出来。这两段体验分别对应两个指标。TTFT（time to first token，首 token 延迟）是从请求到达到第一个 token 生成的时间，它包括排队等待和 prefill 的计算时间。TBT（time between tokens，token 间隔）是同一个请求相邻两个输出 token 之间的时间间隔，它决定了输出是否流畅。一个请求生成 500 个 token，就有 499 个 TBT 值。

论文看的是 TBT 的 P99，也就是把所有请求、所有 token 的间隔放在一起排序，排在第 99 百分位的那个值。看尾部而不是平均，是因为停顿是偶发的：一个请求在 500 个 token 里卡住一次 2 秒，平均间隔可能只多了 4 毫秒，用户却实实在在地看到输出停了 2 秒。P99 能把这种偶发的长停顿暴露出来。

论文先用一组实测说明问题有多严重：在两张 A100 上用 vLLM 跑 Yi-34B，处理 128 个来自 arXiv 论文摘要数据集的请求。把“已经生成的 token 总数”随时间画出来，vLLM 的曲线是一级一级的台阶：每当有新请求的 prefill 插进来，所有正在生成的请求就一起停住，最长的一次停了好几秒。Sarathi-Serve 的曲线则平滑得多，而且更早跑完全部请求。

为什么会这样？论文把当时的调度器按“prefill 和 decode 谁优先”分成两类。

  • decode 优先：以 FasterTransformer 为代表的传统系统按“请求”组批。一批请求一起做完 prefill，再一起 decode，直到这一批全部结束，新请求才能进来。正在生成的请求从不被新请求打扰，所以 TBT 很稳定；代价是吞吐量低：批里的请求陆续结束后，剩下的请求只能以越来越小的批继续跑，GPU 越来越闲。
  • prefill 优先：Orca 提出了按“迭代”组批，每生成一个 token 就重新组一次批，请求可以随时加入和离开。Orca 和 vLLM 都把它和“prefill 优先”结合：只要显存允许，就立刻给新请求做 prefill。这样后面的 decode 批更大，吞吐量更高；代价是每次插入 prefill，正在 decode 的请求都得等它算完，出现生成停顿。prompt 越长，这一等越久。

两类做法各占一头，论文用原文图 2 把它们画在“吞吐量—TBT 延迟”的平面上：FasterTransformer 在“延迟低、吞吐低”的角落；Orca 靠迭代级调度往“吞吐高”挪了一步，vLLM 再靠 PagedAttention 放下更大的批，吞吐更高，但两者的 TBT 都更差；Sarathi-Serve 的目标是“吞吐高、延迟也低”的那个角。

引言还指出第二个问题：流水线气泡。模型大到一台机器放不下时，要跨机器部署。张量并行每层都要做两次 all-reduce 通信，在机器之间只有普通以太网时太慢，所以跨机器时通常改用流水线并行，把模型按层切成几段，每台机器负责一段。流水线要靠“微批”让各段同时干活，而 LLM 推理里每个微批的计算量差别很大：一个含长 prompt 的微批可能比一个纯 decode 的微批慢好几倍，后一段的机器就只能干等，GPU 时间白白浪费（第 3.3 节详细讲）。

针对这两个问题，Sarathi-Serve 提出两个想法。分块预填充把一个请求的 prefill 切成计算量相近的块，分到多次迭代里完成，每次只算 prompt 的一部分。无停顿调度让新请求加入正在运行的批时不打断任何 decode：每一批由所有正在 decode 的请求，加上一块或几块新请求的 prefill 组成，总 token 数凑到一个事先设定的预算。这样做以迭代级调度为基础，但多了一个关键的限制：每次迭代里的 prefill token 数被封顶。于是每次迭代的耗时有了上限，而且几乎与新请求的 prompt 有多长无关，正在 decode 的请求的 TBT 也就几乎不受新 prefill 影响。此外，这样组出来的“混合批”（同时含 prefill token 和 decode token）计算量都差不多，用在流水线并行上时各微批耗时均匀，气泡显著减少。

论文在四种模型和硬件组合上做了评测：Mistral-7B 用 1 张 A100；Yi-34B 用 2 张 A100 做 2 路张量并行；LLaMA2-70B 用 8 张 A40；Falcon-180B 用跨两台机器的 8 张 A100，机器内 4 路张量并行、机器间 2 级流水线，机器之间是普通以太网。Yi-34B 的服务容量最高提升 3.7 倍，Mistral-7B 最高 2.6 倍，Falcon-180B 因为气泡减少，端到端服务容量最高提升 5.6 倍。论文列出的贡献是：指出现有系统在吞吐—延迟权衡上的问题；提出分块预填充和无停顿批处理两个简单而有效的技术；在多种模型、硬件和并行方式上证明它的通用性，服务容量最多能提升一个数量级。

先补一点背景：前作 SARATHI。

同一组作者在 2023 年 8 月发表过一篇 SARATHI（arXiv 2308.16369 ↗），标题直译是“用分块 prefill 捎带 decode，提高 LLM 推理效率”。它最早提出了两件事：把 prefill 切成等大的块，以及让 decode“搭车”（piggyback）进带 prefill 块的批里。那篇论文的目标是吞吐量：摘要里报告 LLaMA-13B 在 A6000 上 decode 吞吐最高提升 10 倍、端到端吞吐最高 1.33 倍；GPT-3 在流水线并行下气泡减少 6.29 倍、端到端吞吐提升 1.91 倍。

Sarathi-Serve 把这个机制改造成面向在线服务的调度器：评价标准从“吞吐量”换成“在尾延迟约束下能扛多大负载”，新增了“先放 decode、再放 prefill、按 token 预算封顶”的无停顿调度规则，并讨论了预算该怎么按延迟目标来选。所以读这篇时，可以把“分块”看作继承来的工具，把“无停顿 + 预算 + 尾延迟约束下的容量”看作这篇真正的新内容。

读的时候容易误解的地方：
  • Sarathi-Serve 改的是调度，不是模型，也不是注意力内核。它不改变模型算出的任何数字，输出与不分块时一致（同一批里的计算顺序变了，浮点误差层面可能有极小差异，论文没有讨论这一点）。
  • “TBT”和 DistServe 等论文里的 “TPOT” 不是一回事。TPOT 通常是一个请求所有输出 token 的平均间隔，一次长停顿会被平均掉；TBT 的 P99 是把所有间隔放在一起看尾部，对偶发停顿非常敏感。指标选择本身就决定了 Sarathi-Serve 的优势会被放大还是缩小（第 5 节再谈）。

2 背景：两个阶段、多卡部署、三个指标和两类调度器

这一节要回答的问题：后面所有的设计都建立在几个事实上：prefill 和 decode 算的东西不同，所以代价不同；大模型要分到多张卡上，张量并行和流水线并行各有利弊；评价一个推理系统要看 TTFT、TBT 和服务容量；现有调度器在“先做 prefill 还是先做 decode”上做了不同的取舍。这一节把这些背景依次讲清楚。熟悉 vLLM 精读页的读者可以快速浏览前两小节。

2.1 一层 Transformer 里算什么，推理的两个阶段

GPT-3、LLaMA、Yi 这些模型都是只有解码器的 Transformer，由很多结构相同的层堆起来，每层有两个模块。自注意力模块先用三个线性变换把每个 token 的向量变成 query、key、value，再让每个 token 的 query 和它前面所有 token 的 key 做点积、经过 softmax 得到权重，用这些权重对 value 加权平均；多个“头”并行做这件事，结果再经过一个线性变换合并。前馈网络（FFN）是两个线性层夹一个激活函数：先把维度 \(h\) 放大到更高的维度，再变回 \(h\)。

这里有一个对后面很重要的区分：一层里除了注意力的“点积 + 加权平均”这一步，其余计算（QKV 投影、输出投影、FFN）都是逐 token 独立的线性层，每个 token 都乘同一组权重。注意力那一步则要用到这个 token 前面所有 token 的 key 和 value，每个请求各算各的。

先补一点背景：prefill、decode 与 KV 缓存。

推理服务处理一个请求分两步。prefill 处理用户输入的整段 prompt：这些 token 全部已知，可以在一次前向计算里并行算完，算出每个 token 在每一层的 key 和 value，并预测出第一个输出 token。decode 从第一个输出 token 开始，每一步把上一步刚生成的那一个 token 送进模型，生成下一个 token，直到生成结束符为止。decode 的每一步都要用到之前所有 token 的 key 和 value，为了不每步重算，系统把它们存在显存里，这就是 KV 缓存。

一个典型的 prompt 有几百到几千个 token。prefill 一次处理这么多 token，线性层是“矩阵乘矩阵”，GPU 的算力能用满；decode 每步对每个请求只处理一个 token，线性层退化成“矩阵乘向量”，计算量很小，却要把整份权重从显存读一遍，所以速度被显存带宽卡住，算力大部分闲着。这一点在 vLLM 精读 §2.2 有更细的讲解。

所以 decode 特别适合拼批：把 \(B\) 个请求的 decode 放进一批，读一遍权重就能同时为 \(B\) 个请求各生成一个 token，读权重的成本被摊到 \(B\) 份上。批越大，越划算。为了让批更大，近年有几类互补的技术：vLLM 的 PagedAttention 消除了 KV 缓存的显存碎片，能同时放下更多请求；多查询注意力（MQA）和分组查询注意力（GQA）让多个查询头共用一组 key/value，直接缩小 KV 缓存，论文举例说 LLaMA2-70B 的 KV 缓存只有 LLaMA-65B 的八分之一。这些技术都让“开大批”变得可行，但开大批之后怎么安排 prefill 和 decode，才是本文要回答的问题。

2.2 多卡推理：张量并行与流水线并行

模型越来越大，一张卡放不下，或者放下了也留不出足够的显存给 KV 缓存，就要分到多张卡甚至多台机器上。论文还强调了另一个动机：decode 的吞吐量受限于一张卡上能放下的最大批，把权重分到多张卡上，每张卡腾出的显存可以放更多请求的 KV 缓存，从而开更大的批。常用的切法有两种。

  • 张量并行（TP）把每一层的权重和 KV 缓存平均切到所有卡上，每张卡算每一层的一部分。好处是每张卡的批可以随卡数线性变大，单步延迟也随之降低；坏处是每层要做两次 all-reduce（注意力一次、FFN 一次），而且这些通信在关键路径上，必须等它完成才能继续算。所以张量并行只适合机器内部有 NVLink 这类高带宽互连的场合。张量并行的切法见 Megatron-LM 精读 §3。
  • 流水线并行（PP）按层切，每张卡（或每组卡）负责连续的若干层。数据算完前一段，把激活传给下一段即可：每隔很多层才通信一次，而且是点对点发送，比 all-reduce 便宜得多。所以在机器之间只有普通网络时，流水线并行比张量并行高效。代价是要用“微批”让各段同时工作，否则同一时刻只有一段在干活。
先补一点背景：流水线、微批与气泡。

假设模型切成两段，GPU0 负责前半，GPU1 负责后半。如果一次只送一批数据进去，GPU0 算完前半交给 GPU1 后就没事可做，GPU1 在 GPU0 算的时候也没事可做，两张卡各闲一半。解决办法是把工作切成多个微批，GPU0 算完微批 1 交给 GPU1 后马上开始算微批 2，两张卡就能同时忙起来，像工厂的流水线一样。流水线上某一段因为上游没送来活而空等的时间，叫流水线气泡。训练里的气泡来自“先做前向、再做反向”的依赖，Megatron-LM 精读 §2.3 有一张示意图。推理只有前向，看起来没有这种依赖，但第 3.3 节会看到，只要各个微批的耗时不一样长，气泡照样会出现。

2.3 三个指标：TTFT、TBT 和服务容量

论文用两个延迟指标和一个吞吐指标。TTFT 是请求到达后生成第一个 token 的时间，反映系统的“反应快不快”；系统负载高时，请求要排队，TTFT 里的排队时间会变长。TBT 是同一请求相邻两个输出 token 之间的间隔，反映输出“流不流畅”。吞吐指标叫服务容量（capacity）：在满足某个延迟目标的前提下，系统能持续承受的最大请求速率，单位是每秒请求数（QPS）。容量越高，同样的硬件能服务越多用户，单个请求的成本越低。

后面实验里的具体口径是：延迟目标只约束 P99 TBT；同时要求系统“扛得住”，即排队时间不能无限增长，论文用的标准是请求的调度延迟中位数不超过 2 秒。容量就是在这两个条件同时满足时的最高 QPS。

容易忽略的一点：容量的定义里没有直接约束 TTFT，只通过“调度延迟中位数 ≤ 2 秒”间接限制了排队。分块预填充恰恰会让 prefill 变慢一点、TTFT 变长一点（第 5.4 节的表 4 有实测），所以这个指标天然对 Sarathi-Serve 有利。这不是说结果不可信，而是说“容量更高”的含义是“在出字流畅的前提下能接更多请求”，不等于“每个请求都更快拿到第一个字”。

2.4 两类调度器：请求级批处理和迭代级批处理

调度器负责两件事：决定接不接新请求（准入控制），以及每一步把哪些请求放进一批（组批策略）。论文把现有调度器分成 prefill 优先和 decode 优先两类，并用两段伪代码说明它们的区别。

先补一点背景：从请求级批处理到 Orca 的迭代级调度。

传统的推理引擎，如 FasterTransformer 和 Triton Inference Server，按请求组批：取一批请求，执行到这批里所有请求都结束为止，才取下一批。不同请求的输入、输出长度差别很大，短的请求要用填充补齐到最长的那个，还要陪着最长的请求跑完，新请求只能等整批结束。

Orca（OSDI 2022）提出迭代级调度：每做完一次前向迭代（生成一个 token）就重新组一次批，生成完的请求立刻离开，新请求下一步就能加入。今天常说的“连续批处理”（continuous batching）就是它。为了让处在不同阶段、长度各异的请求能拼进同一次迭代，Orca 还提出了 selective batching：线性层是逐 token 的，所以把所有请求的 token 摊平成一个大矩阵一起乘权重；注意力要用各自的 KV，所以按请求拆开分别算，再拼回去。这意味着一次迭代里可以既有某个请求的几百个 prompt token，又有另外几十个请求各 1 个 decode token，它们在线性层里就是同一个矩阵的不同行。这正是后面“把 prefill 块和 decode 拼进同一批”的技术前提。迭代级调度的时间轴示意见 vLLM 精读 §2.3，selective batching 的示意见 Orca / Sarathi-Serve 拆解页。

请求级批处理（论文 Algorithm 1）的逻辑是：当前批为空时，不断取新请求，直到显存放不下为止，对这一批做 prefill；之后每一步只对这批做 decode，并移除已结束的请求；只有这批全部结束、批变空了，才会再接新请求。论文把它归为 decode 优先：正在 decode 的请求不会被新请求打断，TBT 很好；但后半程批越来越小，很多迭代都是小批量的纯 decode，GPU 算力浪费严重。

迭代级批处理（论文 Algorithm 2，以 vLLM 为例）的逻辑是：每一步都先看能不能接新请求，只要显存能放下就一直接；如果这一步接到了新请求，就只对这些新请求做 prefill，算完把它们并入正在运行的批；如果没有新请求，才对整批做一次 decode。论文把它归为 prefill 优先：新请求被“急切地”接纳，后续 decode 批更大，吞吐量更高；但凡有新请求进来，这一步就是纯 prefill，所有正在 decode 的请求都要等它完成。这种在两次 decode 之间插入 prefill 导致的等待，就是生成停顿。

这个分类同样适用于当时的 vLLM、TensorRT-LLM、LightLLM 等系统，它们都用迭代级批处理。另外，Splitwise、DistServe 这类把 prefill 和 decode 放到不同机器上的系统被论文归为第三类“拆分式”，留到相关工作里讨论。

3 动机：decode 的空闲算力、生成停顿和流水线气泡

这一节要回答的问题：prefill 和 decode 的代价到底差多少，差在哪里？既然 decode 用不满算力，能不能顺手多塞点活进去？现有的 prefill 优先调度为什么一定会造成停顿，Orca 那种“prefill 和 decode 拼在一起算”为什么也救不了？流水线并行下，气泡又是怎么来的？论文把答案整理成四条结论（Takeaway 1–4），后面的设计就是逐条回应它们。

3.1 prefill 与 decode 的代价

论文先在单张 A100 上用 Mistral-7B 测了两个阶段的吞吐量随批大小的变化（原文图 3，prompt 长度都是 1024）。prefill 在批大小为 1 时就已经接近饱和：从原图读出，批大小 1 时约每秒 4.4K 个 token，加到 2、4、8 之后在 4.7K–5.4K 之间小幅波动，基本不再涨。decode 则几乎随批大小线性增长：批大小 1 时每秒只有十几个 token，64 时约 810 个。注意两个子图的纵轴量级完全不同，prefill 每秒处理的 token 数比 decode 高出一个数量级以上。

Takeaway 1：两个阶段的行为截然相反。拼批能让 decode 的吞吐量成倍上升，对 prefill 却几乎没有帮助，因为单个 prefill 已经把算力用满了。

接着论文把两个阶段的耗时拆成线性层、注意力和其他三部分（原文图 4）。从原图读出：prefill 的总耗时从 128 个 token 时约 33 ms 涨到 2K 个 token 时约 144 ms，其中线性层从约 15 ms 涨到约 118 ms；decode 一步约 18–23 ms，批大小从 1 涨到 64 几乎不变，线性层一直在 11 ms 左右。两条结论很清楚。第一，线性层是耗时的大头，即使在 2K 这样较长的序列上，注意力的耗时随长度平方增长，线性层仍占总时间的 80% 以上，所以优化线性层最重要。第二，decode 时线性层的效率极低：1 个 decode token 的线性层开销和 128 个 prefill token 差不多。

先补一点背景：算术强度与 roofline。

GPU 执行一个矩阵乘法时，读数据和做计算是重叠进行的，总时间大致是两者中较长的那个：\(T \approx \max(T_{\text{math}}, T_{\text{mem}})\)。如果读数据更慢，这个操作就是访存受限，算力闲着，用“模型算力利用率”（MFU）衡量会很低；如果计算更慢，就是算力受限，带宽闲着，用“模型带宽利用率”（MBU）衡量会很低。两者正好相等时，算力和带宽同时用满，这是最理想的状态。

判断一个操作落在哪一边，看算术强度：每从显存读 1 字节数据，要做多少次浮点运算。设一个线性层的权重是 \(d_{\text{in}}\times d_{\text{out}}\) 的 BF16 矩阵，这一步有 \(n\) 个 token 要乘它：

$$\text{算术强度}=\frac{2\,n\,d_{\text{in}}d_{\text{out}}}{2\,d_{\text{in}}d_{\text{out}}+2\,n\,(d_{\text{in}}+d_{\text{out}})}\;\approx\; n\qquad(n\ll d_{\text{in}},d_{\text{out}})$$

分子是乘加的次数（每个乘加算 2 次运算），分母是读权重加读写激活的字节数。当 \(n\) 远小于矩阵维度时，权重的字节数占绝对多数，算术强度约等于 token 数 \(n\)。GPU 也有一个“平衡点”：峰值算力除以显存带宽。A100 的 BF16 稠密算力为 312 TFLOPS、带宽约 2 TB/s，平衡点约 156 次运算/字节（推算）。所以一批里的 token 数少于一百多个时，线性层是访存受限的；多于这个数，才变成算力受限。decode 批里每个请求只贡献 1 个 token，几十个请求的 decode 批远在平衡点左边；一段上千 token 的 prefill 远在右边。更多推导见 FlashAttention 精读 §2.2。

下面的小工具可以直观地看到这一点：把批大小 B 调大，decode 的点会沿着斜线（带宽受限区）往右上走；prefill 的点一开始就在平顶（算力受限区）上。

逐行看这四种方式：

  • Orca 支持混合批，把 C、D 的整段 prefill 和 A、B 的 decode 放进同一次迭代。看起来 A、B 没有被“踢出”批，但这次迭代要把两段完整 prompt 算完，耗时和 vLLM 的那次 prefill 差不多，A、B 得等这次迭代结束才拿到下一个 token，停顿依然存在。所以光是“拼在一起算”不够，关键在于这一步的总计算量有多大。
  • FasterTransformer 让 A、B 不受打扰地生成完，再给 C、D 做 prefill。A、B 的出字很平稳，但 C、D 白白排队了 6 格才开始 prefill，TTFT 很长；而且 A 结束以后只剩 B 一个请求在跑，批越来越小，吞吐量低。
  • Sarathi-Serve 把 C 的 prompt 切成两块，第 2、3 格各算一块，同时照常给 A、B 做 decode；D 等 C 的块算完后，在第 4、5 格分两块算完。A、B 从头到尾每格都有输出，C、D 也没有等太久就进入了 decode。

论文还讨论了一种缓解办法：Orca 建议用较小的批来压低延迟尖峰。但第 2 节讲过，批变小会直接降低 decode 的吞吐量。所以现有系统只能根据延迟目标，在吞吐和延迟之间二选一。

Takeaway 3：prefill 和 decode 交替执行，使现有调度器必须在吞吐和延迟之间取舍。当时最先进的系统都用 prefill 优先，用 TBT 延迟换吞吐量。

3.3 流水线气泡浪费 GPU 时间

训练里的流水线气泡是因为反向必须等前向做完。推理只有前向，于是人们容易以为：只要用微批把流水线灌满，就不会有气泡。FasterTransformer、FastServe 等系统都用了微批，却没有讨论气泡；Orca 的论文甚至认为迭代级调度消除了流水线中的气泡。Sarathi-Serve 的实验（第 5.3 节）表明，即使用了迭代级调度，气泡仍然会浪费大量 GPU 时间。

原因是 LLM 推理里每个微批的计算量差别很大，取决于里面有多少 prefill token、多少 decode token。论文把气泡分成三种：

  • PB1：相邻两个微批里的 prefill token 数不同，耗时不同。后一段处理较长的那个微批时，前一段处理完较短的微批就没有活干了。
  • PB2：一个 prefill 微批后面跟着一个 decode 微批（或反过来），两者耗时差距更大。
  • PB3：即使都是纯 decode 微批，注意力的耗时也取决于各请求已经积累的上下文长度（KV 缓存有多大），不同微批的耗时仍有差异。

论文给了一个量级：Falcon-180B 上，单个 4K token 的 prompt 执行一次约 1150 ms，而批大小为 32 的纯 decode 迭代约 200 ms，两者交替执行时可能产生约 950 ms 的气泡。prompt 越长、批越大，prefill 迭代越长、出现得越频繁，问题越严重。

4 设计与实现：分块预填充、无停顿批处理、token 预算

这一节要回答的问题：第 3 节说 decode 批里有“白送”的算力，可以顺手做 prefill，但直接把整段 prefill 塞进去会让这一步变得很长。那么 prefill 该切成多大的块？每次迭代按什么顺序装哪些请求？一次装多少 token（token 预算）才合适，选大选小各有什么代价？分块本身又要额外付出什么？这一节是全文的核心。

4.1 分块预填充：把一段 prefill 拆到多次迭代里

第 3.1 节已经说明，decode 批严重访存受限，算术强度有很大的余量，正好可以“捎带”额外的计算。最直接的做法是像 Orca 那样组混合批，把访存受限的 decode 和算力受限的 prefill 放在一起算。问题是实际负载里的 prompt 往往很长：论文用的两个数据集中，openchat_sharegpt4 的 prompt 长度中位数是 1730 个 token，arxiv_summarization 是 7059 个（原文表 2）。把几千个 token 的整段 prefill 和 decode 拼在一起，这一步要算很久，TBT 照样很高。

分块预填充基于两个观察。第一，一段长度适中的 prefill 已经能把 GPU 算力用满：原文图 4 显示，prefill 的吞吐量在序列长度约 512 时就开始饱和。第二，实际的 prompt 平均有几千个 token。两者合起来就有了机会：把长 prefill 切成较小的块，每块仍然大到足以把算力用满，于是“切块”本身不会明显降低效率，却能把每次迭代的计算量控制住。Sarathi-Serve 用这个机制组出 token 数合适的批，既用上 decode 批里闲置的算力，又不违反 TBT 的目标。

分块之后，第 \(k\) 块的 token 在注意力里要看到哪些东西？因为是因果注意力，第 \(k\) 块里的每个 token 要看到它前面的所有 token：前 \(k-1\) 块的 token 加上本块里排在它前面的 token。前 \(k-1\) 块在之前的迭代里已经算过，它们每层的 key 和 value 已经写进了 KV 缓存。所以第 \(k\) 块的注意力只需要：用本块的 query，去读 KV 缓存里前面各块的 K、V，再加上本块内部的因果注意力。除了最后一块，中间各块不需要采样输出 token；最后一块算完时，产出第一个输出 token，请求随之进入 decode。

4.2 无停顿批处理：先放 decode，再放 prefill 块，总量不超预算

Sarathi-Serve 的调度器仍然是迭代级的，它用分块预填充和“prefill 与 decode 合批”来提高吞吐、压低延迟。与 Orca、vLLM 为了做 prefill 而让正在进行的 decode 停下来不同，Sarathi-Serve 利用 decode 迭代里算术强度的余量来做 prefill，不推迟任何 decode。论文把这叫无停顿批处理（原文 Algorithm 3）。它的步骤是：

  1. 先定预算。根据用户给定的 TBT 目标，算出一个批最多能装多少 token，记作 token 预算 \(\tau\)（怎么算见第 4.3 节）。
  2. 每次迭代，先装所有正在 decode 的请求。每个请求占 1 个 token。
  3. 再装已经开始、还没做完的 prefill。每个这样的请求，取“剩余 prompt 长度”和“预算剩余量”中较小的那个作为本次的块大小。
  4. 最后才接纳新请求。只有在所有正在运行的请求都安排好之后，才从队列里取新请求，前提是显存放得下它、预算还有剩余；同样按剩余预算决定它这一步算多长的块。
  5. 把这一批（混合批）交给模型执行一次前向，移除已结束的请求，进入下一次迭代。

因为每次迭代的计算量都被预算封顶，decode 永远不会因为同一批里有 prefill 块而经历长时间的生成停顿。用代码写出来大致是这样（本站按论文 Algorithm 3 和官方仓库的 sarathi_scheduler.py 整理的简化版）：

def schedule_one_iteration(running, waiting, token_budget):
    batch, used = [], 0
    # 1) 所有已经在 decode 的请求先上车，每个 1 个 token
    for r in running:
        if r.prefill_done:
            batch.append((r, 1)); used += 1
    # 2) 还没做完 prefill 的请求，按剩余预算切下一块
    for r in running:
        if not r.prefill_done:
            chunk = min(r.remaining_prompt, token_budget - used)
            if chunk > 0:
                batch.append((r, chunk)); used += chunk
    # 3) 最后才接新请求：要显存放得下、预算还有剩
    while waiting and used < token_budget and can_allocate_kv(waiting[0]):
        r = waiting.pop(0)
        chunk = min(r.prompt_len, token_budget - used)
        running.append(r); batch.append((r, chunk)); used += chunk
    return batch   # 交给引擎：线性层一起算，注意力按请求分别算

读的时候容易误解的地方：
  • “无停顿”不等于“零影响”。带了 prefill 块的那一步确实比纯 decode 慢：Mistral-7B 慢 1.2–2.0 倍，LLaMA2-70B 慢 1.9–3.7 倍（上表）。Sarathi-Serve 做到的是把这个“慢多少”封顶，让它不随 prompt 长度增长，而不是让它消失。所以 token 预算必须和 TBT 目标一起选。原文图 9 没有说明它用的预算是多少，LLaMA2-70B 的倍数偏高可能和这一点有关，本站无法核实。
  • 论文的 Algorithm 3 是示意，有几处笔误。例如第 18 行写成“批 ← 新请求”，应当是把新请求加入批；循环里也没有取下一个新请求。图注说“可选地加入一块进行中的 prefill”，而官方代码会把所有进行中的 prefill 都排进来（只要预算够）。复现时以官方仓库的 sarathi/core/scheduler/sarathi_scheduler.py 为准。
  • 新请求被接纳时，要一次性分配下整段 prompt 的 KV 显存。官方代码在接纳时调用块管理器为请求分配显存，之后各块直接写入。所以显存不够时，即使预算有剩，也接不进新请求；批大小上限（实验里是 128 个请求）同样会挡住新请求。

4.3 token 预算怎么选

token 预算由两个相互拉扯的因素决定：TBT 目标和分块的开销。从 TBT 看，预算越小越好，因为每次迭代的 prefill token 越少，这一步越快。但预算太小，prefill 会被切得太碎，带来两种开销：一是每块太小，GPU 利用率下降；二是注意力里要反复读前面各块的 KV 缓存。

反复读 KV 缓存。第 \(k\) 块的注意力要读前面所有块的 KV。如果一段 prefill 切成 \(N\) 块，第 1 块的 KV 会被后面的块读 \(N-1\) 次，第 2 块的 KV 被读 \(N-2\) 次，依此类推。这增加了从显存读取的数据量，但计算量不变。

正如上面的推算所示，额外读 KV 的量和 prefill 本身的计算量比起来很小。论文也说，即使块很小，prefill 阶段的注意力仍然是算力受限的；实际中分块的开销主要来自内核启动之类的固定开销（第 5.4 节会看到实测开销）。本站补充一个角度：Sarathi-Serve 用的 FlashAttention-2 内核，本来就把 query 沿序列切成小块分给不同的线程块，每个线程块都要把它前面所有的 K、V 从显存扫一遍（FA2 的并行方式见 FlashAttention 精读 §9，分块与扫描顺序见 §3.4）。也就是说，不分块时这种“同一份 K、V 被不同的 query 小块反复读”同样存在，分块只是把这些读取分到了不同的迭代里，在内核层面并没有多出多少流量（本站分析，论文没有这样论证）。真正多出来的，更可能是块变小后线性层效率下降（第 3.1 节图 6 的平台区）和每次迭代都要重复付的固定开销。按原文图 6 读出的数字粗算，LLaMA2-70B 两路张量并行时，512 个 token 的批每个 token 的线性层耗时约 0.32 ms，4096 个 token 时约 0.24 ms，前者约是后者的 1.3 倍（推算），和第 5.4 节实测的分块开销量级相当。

先补一点背景：瓦片量化（tile quantization）。

GPU 做矩阵乘法时，把输出矩阵切成固定大小的“瓦片”（tile），每个瓦片交给一个线程块计算，每个线程块做的运算量相同。如果矩阵的某一维不能被瓦片大小整除，最后一排瓦片里只有一部分是有用的，但线程块照样要把整个瓦片算完。举个例子（本站示意）：瓦片高 128 行时，256 个 token 正好是 2 排瓦片；257 个 token 就要 3 排，第 3 排只有 1 行有用，却要付出一整排的计算。论文实测，块大小取 257 时，prefill 的时间比取 256 时多 32%。所以预算最好取瓦片大小的整数倍，第 3.1 节图 6 曲线上的小台阶也是这个原因。

流水线并行下还要考虑气泡。块越大，各个微批之间的耗时差异越大，气泡越多，系统总吞吐越低；块太小，算术强度低、固定开销占比高，同样不好。

所以选预算是一个综合决策，取决于 TBT 目标、并行配置和具体硬件。论文给出的基本做法是做一次性的性能剖析（profiling）：测量含不同 token 数的批各要多长时间，把预算设为“不违反 TBT 目标的前提下，一批能装的最多 token 数”。更精细的选择借助同组开发的推理模拟器 Vidur（arXiv 2405.05465 ↗），在给定部署下搜索让服务容量最大的预算。实验里的设置是：严格的延迟目标用 512，宽松的用 2048；LLaMA2-70B 在宽松目标下用 1536，以减少流水线气泡。

4.4 实现

Sarathi-Serve 在开源的 vLLM 代码基础上实现。作者用 FlashAttention v2 和 FlashInfer 的内核实现了分页 KV 缓存上的分块 prefill；因为 FlashAttention 后端支持的模型更多，论文的所有实验都用它。作者还扩展了原来的 vLLM 代码，支持多种调度策略（包括后面作为对照的 vLLM、Orca 策略）、分块预填充、流水线并行和一套详细的性能遥测系统。流水线并行和张量并行的通信都用 NCCL。官方仓库的说明里写明，这个仓库最初是 vLLM 的一个分支，是一个研究原型，只保留了最关键的功能，并不具备开源 vLLM 的全部特性。

先补一点背景：这里的 “vLLM” 和 “Orca” 指的是什么。

论文把 vLLM 和 Orca 作为对照，因为它们代表了当时 LLM 推理的最高水平。但 Orca 没有开源，论文也没有交代对照用的 vLLM 版本。从官方仓库看，三者都是同一套代码（Sarathi-Serve 自己的 vLLM 分支）里的不同调度策略：vllm_scheduler.py 实现 prefill 优先、批里要么全是 prefill 要么全是 decode 的策略；orca_scheduler.py 实现“所有 decode + 新请求的整段 prefill”合成一批的策略，而且为每个请求按模型最大长度一次性预留 KV 显存；sarathi_scheduler.py 是本文的策略。模型执行、注意力内核、通信都是共用的。

这样做的好处是只比较调度策略本身，排除了内核和工程实现的差别。需要记住的是：这里的“vLLM”是“vLLM 当时默认的调度策略”，不是某个发布版本的 vLLM 整体；这里的“Orca”是“按 Orca 论文思路的复现”，还背着按最大长度预留显存的包袱。复现配置里，vLLM 和 Sarathi-Serve 的批上限都是 128 个请求，Orca 的批上限在 Mistral-7B 上是 16、在 LLaMA2-70B 上是 8，注释说批再大，激活和 KV 缓存的显存就会爆掉。

论文对这些结果的解读有以下几点。

  • Sarathi-Serve 在所有组合上都领先。严格目标下，它最多能承受 Orca 的 4.0 倍、vLLM 的 3.7 倍负载（Yi-34B，openchat_sharegpt4）。对用流水线并行的大模型，论文说最多是 Orca 的 6.3 倍、vLLM 的 4.3 倍（LLaMA2-70B，openchat_sharegpt4），原因是气泡少。6.3 倍与原图吻合；但按原图柱高，LLaMA2-70B 在这个数据集上相对 vLLM 最多约 3.8 倍，4.3 倍这个数字出现在第 5.4 节 Falcon-180B 和“vLLM 纯张量并行”的对比里，正文这里可能写混了。
  • Orca 和 vLLM 往往先撞上延迟目标，再撞上吞吐上限。也就是说，限制它们容量的不是 GPU 算不过来，而是 P99 TBT 先超标了。所以把目标放宽，它们的容量会明显上升，例如 vLLM 在 Mistral-7B、openchat 上从 0.77 涨到 1.56。Sarathi-Serve 则可以按目标调整预算：严格目标下用 512，把 prompt 切得更碎，效率略降但尾延迟更低；宽松目标下用 2048，让 prefill 更高效；LLaMA2-70B 宽松目标下用 1536，以减少流水线气泡。
  • 宽松目标下 vLLM 明显强于 Orca，原因有两个。第一，Orca 一次迭代里可以塞进多个请求的整段 prompt，最多“最大序列长度 × 批大小”个 token，而 vLLM 一次 prefill 迭代最多只有“最大序列长度”个 token，所以 Orca 的尾延迟有时更高。第二，vLLM 能支持大得多的批：Orca 没有 PagedAttention，处理 token 极多的批时激活也很占显存，批只能开小。
  • 所有系统在 arxiv_summarization 上的容量都低于 openchat_sharegpt4。因为前者的 prompt 长得多（中位数 7059 对 1730），prefill 更耗时，Orca 和 vLLM 也更容易因为长 prefill 而违反延迟目标。

  • Sarathi-Serve 用预算精确地调节权衡。严格目标下用小预算 512，容量是 vLLM 的 3.5 倍；宽松目标下换成大预算 2048，效率更高，在 Yi-34B、1 秒目标下容量是 vLLM 的 1.65 倍。按原图读数，Yi-34B 在 0.2 秒目标下，预算 512 约 1.14、vLLM 约 0.33，正好约 3.5 倍；Mistral-7B 在 0.1 秒目标下是约 2.03 对 0.77，约 2.6 倍。论文正文把 3.5 倍写成“Mistral-7B、100 ms”，图注写的是 Yi-34B，数据支持图注。

5.5 消融实验：分块的开销，两个技术各自的作用

分块的开销。原文图 14 在 Yi-34B（2 路张量并行）上测了分块对 prefill 总耗时的影响：prompt 长度取 2K、4K、8K，块大小取 512、1024、2048，结果以不分块的耗时为 1 做归一化。正文说，块越小开销越大，即使是最小的 512，开销也“至多约 25%”；预算 2048 时开销几乎可以忽略。按原图柱高读出的数字是：

这个开销和第 4.3 节的推算对得上：开销的主要来源不是反复读 KV，而是块变小后矩阵乘法的效率下降、每次迭代的固定开销。它也解释了为什么 Sarathi-Serve 在宽松目标下要换用大预算：延迟允许的时候，没有理由多付这三成的 prefill 开销。

只用分块时 TTFT 变长，因为分块后的 prefill 效率略低，而且 prefill 块和 decode 分开在不同的迭代里轮流跑，prefill 的推进速度被摊薄了；只用混合批时 TBT 很高，因为长 prefill 照样造成生成停顿。两者一起用时，P99 TBT 是三者中最低的，比“只用分块”还低：只用分块时，一个 decode 请求在两次出字之间可能要等一整次 prefill 块的迭代，而合批之后 decode 和 prefill 块在同一次迭代里完成，不用再等。TTFT 则介于两者之间。

5.6 结果的份量：这些倍数是在什么条件下、和谁比出来的

把第 5.1–5.5 节的细节合在一起，可以这样理解论文的数字：

  • 对照系统是同一代码库里的调度策略。“vLLM”是 vLLM 当时默认的调度策略（prefill 优先、prefill 与 decode 不合批），运行在 Sarathi-Serve 自己的 vLLM 分支上，用的是同样的 FlashAttention 内核；论文没有写分支基于哪个 vLLM 版本，本站也无法确认。这能干净地隔离出调度的作用，但不等于和某个发布版本的 vLLM 正面比。“Orca”是复现，还按模型最大长度预留 KV 显存、批上限只有 8–16，所以“相对 Orca 的倍数”（如 5.6 倍、6.3 倍）混合了调度和显存管理两方面的差距。同期已经有类似思路的系统没有被比较：DeepSpeed-FastGen（2024 年 1 月）的 Dynamic SplitFuse 同样把长 prompt 切开、和 decode 拼成固定大小的批；TensorRT-LLM 也不在对照里。
  • 摘要里三个数字的口径不同。Mistral-7B 的 2.6 倍和 Yi-34B 的 3.7 倍是相对 vLLM、严格目标、openchat_sharegpt4；Falcon-180B 的 5.6 倍是相对 Orca、宽松目标、openchat_sharegpt4，同一格相对 vLLM 只有约 1.5 倍，Falcon-180B 相对 vLLM 的最好成绩是严格目标下的约 3.6 倍（混合并行）和约 4.3 倍（纯张量并行）。
  • 优势集中在“严格的 TBT 目标 + 长短不一的 prompt”。相对 vLLM，严格目标下 openchat_sharegpt4 上是 2.6–3.8 倍，宽松目标下降到 1.5–1.7 倍；在 prompt 很长的 arxiv_summarization 上，张量并行的两个模型只有 1.35–1.64 倍。应用对出字间隔不敏感、或 prompt 普遍很短（停顿本来就短）时，收益会更小。
  • 指标只约束 TBT，不约束 TTFT。容量的定义是“P99 TBT 达标且调度延迟中位数不超过 2 秒”时的最高请求速率。分块会让 TTFT 变长（第 5.5 节表 4），这一点不会反映在容量里。延迟目标是按每个模型自己的 decode 速度定的（5 倍和 25 倍），不是统一的绝对值。
  • 负载是合成的。只有长度分布来自真实数据集，到达过程是泊松分布，每次试验 2048 个请求、单个模型副本，没有生产流量里的突发、多轮会话的前缀复用等因素。
  • 硬件是 A100 和 A40，跨机器只有 100 Gbps 以太网。流水线并行的大幅收益和“跨机器张量并行很慢”的结论都建立在这种普通网络上；在有 InfiniBand 或 NVLink 交换网络的集群上，纯张量并行的对照会强得多。论文没有 H100 上的结果。
  • 预算是按延迟目标挑过的。每档目标都用了对应的最佳预算（512、2048 或 1536）。第 5.3 节显示，预算选错时 Sarathi-Serve 可能比 vLLM 还差。

6 相关工作：和其他推理系统、拆分式方案的关系

这一节要回答的问题：Sarathi-Serve 和同时期的其他推理系统是什么关系？特别是同一年出现的“把 prefill 和 decode 拆到不同机器上”的方案，同样是为了消除两个阶段的干扰，作者怎么看待两条路线的优劣？

模型服务系统。Clipper、TensorFlow-Serving、Clockwork、BatchMaker 研究的是一般模型服务里的放置、缓存和批处理策略，没有针对自回归 Transformer 推理的特殊问题。Orca、vLLM、FlexGen、FasterTransformer、LightSeq、TurboTransformers 则做了面向 Transformer 推理的专门优化。其中 FlexGen 面向资源受限的离线场景，追求吞吐量，不适合在线服务；FastServe 提出了抢占式调度，目标是缩短作业完成时间。论文选 Orca 和 vLLM 做详细对比，因为它们代表当时的最高水平。

拆分式方案。Splitwise、DistServe、TetriInfer 把 prefill 和 decode 放到不同的副本上执行，可以完全消除两者之间的干扰。作者指出它们的两个代价：第一，每个请求做完 prefill 后都要把 KV 缓存迁移到 decode 副本，副本之间没有高带宽互连时这很困难；第二，prefill 副本的显存利用不足，因为只有 decode 副本负责存放 KV 缓存。作者也承认拆分方案的长处：prefill 能以最高效率执行，因此 TTFT 更好，而分块预填充比整段 prefill 慢一些。两者的定量比较被留作未来工作。DistServe 一方对分块预填充的批评（块大小两难、重复读 KV）见 DistServe 精读 §2.3，两篇论文同在 OSDI 2024 发表，可以对照着读。

互补的调度工作。Sheng 等人改进迭代级批处理，以保证多租户环境下各客户之间的公平性；FastServe 用抢占机制缓解队头阻塞。作者认为这些算法层面的优化和 Sarathi-Serve 互补，而且能从 prefill 与 decode 干扰的降低中受益。另一个系统 APIServe 已经采用了 SARATHI 的分块预填充，用 decode 批里浪费的算力，为多轮 API 调用提前重算 prefill。

提高 GPU 利用率和模型层面的优化。FasterTransformer 为特定模型写了专用 GPU 内核；CoCoNet 等工作让计算和通信重叠，在张量并行度高、通信可能占主导时特别有用；FlashAttention 等工作通过精心分块和划分工作，缓解长上下文下自注意力的显存瓶颈。模型层面，多查询注意力让所有头共用同一组 key 和 value，缩小 KV 缓存；量化压缩模型；混合专家模型减少每次迭代激活的参数；RetNet 等试图替代 Transformer。作者认为这些都和 Sarathi-Serve 正交：Sarathi-Serve 关注的是从 GPU 的角度解决流行 Transformer 模型的性能问题。

值得补充的一点：论文的相关工作没有提到 DeepSpeed-FastGen（arXiv 2401.08671 ↗，2024 年 1 月）。它的 Dynamic SplitFuse 同样把长 prompt 切成小块、分到多次前向里，并把各请求的 token 凑成固定的批大小，和分块预填充非常接近。从时间上看，SARATHI（2023 年 8 月）更早提出了分块与捎带 decode，而“按尾延迟目标选预算、无停顿调度”的系统化论证是 Sarathi-Serve 的贡献。vLLM 官方文档在介绍分块预填充时，同时引用了 SARATHI 和 DeepSpeed-FastGen 两篇。

7 结论

同时追求高吞吐和低延迟是理想的，但很难做到。论文把现有的 LLM 推理调度器归为 prefill 优先和 decode 优先两类：前者更擅长优化吞吐量，后者更擅长优化 TBT 延迟，但当两者都重要时，没有一类是理想的。为了解决这个权衡，作者提出了 Sarathi-Serve，它由分块预填充和无停顿批处理组成：把输入 prompt 切成较小的工作单元，构造不停顿的调度，让新请求加入正在运行的批时不必暂停正在进行的 decode。评测显示，Sarathi-Serve 让 Mistral-7B 在单张 A100 上的服务容量最多提升 2.6 倍，让 Falcon-180B 在 8 张 A100 上最多提升 5.6 倍（后者是相对 Orca，见第 5.6 节）。

用一句话概括这篇论文的思路：decode 批里有大量闲置的算力，prefill 有大量需要算力的工作；把 prefill 切成小块、按固定的 token 预算塞进每一个 decode 批，就能把闲置的算力用起来，同时让每一步的耗时有上限，从而在不牺牲出字流畅度的前提下提高吞吐量，在流水线并行下还顺带消除了大部分气泡。

8 后来怎么样了

8.1 “先放 decode、再按预算放 prefill 块”成了主流引擎的默认做法

这篇论文最直接的影响，是分块预填充加 decode 优先的合批方式被主流推理引擎吸收。以下是本站在 2026-10-20 核对的情况：

  • vLLM。v0.4.2（2024 年）的文档里，分块预填充已经作为实验性功能出现：打开后调度器改为 decode 优先，把大的 prefill 切块、和 decode 请求拼在同一批里。2025 年 1 月发布的 V1 引擎干脆取消了 prefill 和 decode 的区分，调度结果只是“每个请求这一步处理多少个 token”，在固定的 token 预算下动态分配，分块预填充因此自然实现；V1 从 v0.8.0 起成为默认引擎。当前文档写明，V1 中分块预填充在可能的情况下默认开启，调度器先把所有待处理的 decode 放进批里，再安排 prefill，放不下的 prefill 自动切块。这几乎就是论文的无停顿批处理。文档对预算参数 max_num_batched_tokens 的调优建议也和论文一致：取小一些（如 2048）出字间隔更好，取大一些首字延迟更好，追求吞吐时建议大于 8192。文档在这里引用的是 SARATHI 和 DeepSpeed-FastGen。
  • SGLang。分块预填充默认开启。以 v0.5.2 的代码为例，未指定时块大小按显存自动选择：显存小于 35 GB 的卡用 2048，A100、H100、H200 这一档用 8192，B200、MI300 这类更大显存的卡用 16384。但把 prefill 块和 decode 放进同一批需要另外打开 --enable-mixed-chunk，默认是关闭的。所以 SGLang 的默认行为更接近第 5.5 节表 4 里“只用分块”的那一行：靠分块限制每次 prefill 的长度，但不做 Sarathi-Serve 式的合批。
  • TensorRT-LLM。支持“分块上下文”（chunked context，需要配合分页 KV 缓存，除最后一块外块大小须是 KV 块大小的整数倍），它的 in-flight batching 本来就允许 context 阶段和 generation 阶段的序列在同一批里处理。在它的 LLM API 中，enable_chunked_prefill 的默认值是 False（主分支代码），需要显式打开。

8.2 与 PD 分离：两条路线并存

同一届 OSDI 上的 DistServe 走了另一条路：干脆把 prefill 和 decode 放到不同的 GPU 上，用 KV 传输换取彻底的隔离，并以“goodput”（同时满足 TTFT 和 TPOT 目标时的每卡请求速率）为目标（见 DistServe 精读）。两条路线对应不同的取舍：Sarathi-Serve 在一组 GPU 内把干扰控制在预算以内，不需要跨机器传 KV，部署简单，但 prefill 要付一点分块开销，TTFT 略差；PD 分离让两个阶段各自用最合适的并行方式和卡数，TTFT 和 TBT 都能单独优化，代价是 KV 迁移和更复杂的资源配比。

后来的大规模部署里两者常常结合使用，而不是二选一。例如 DeepSeek-V3 的推理部署把 prefill 和 decode 放在不同的节点上（见 DeepSeek-V3 精读 §3.4）；Kimi 的 Mooncake 采用 PD 分离，并在独立的 prefill 节点池里用“分块流水线并行”（chunked pipeline parallelism）把一个超长上下文请求分到多个节点上处理（见 Mooncake 精读 与 PD 分离拆解页）。分块这个工具本身，在拆分式系统里依然有用武之地。

8.3 同组的后续工作

  • POD-Attention（arXiv 2410.18038 ↗，ASPLOS 2025，Kamath、Prabhu、Mohan、Peter、Ramjee、Panwar）。Sarathi-Serve 的混合批让线性层受益，但注意力仍然用分别为 prefill 和 decode 优化的两个内核来算，效率不高。POD-Attention 是第一个专门为混合批计算注意力的 GPU 内核：它让 prefill 和 decode 的注意力在同一个流式多处理器上并发执行，同时用满算力和显存带宽。摘要报告注意力计算最多快 59%，平均快 28%。
  • Vidur（arXiv 2405.05465 ↗）。第 4.3 节选预算时用到的推理模拟器：结合硬件剖析和预测模型估计延迟与吞吐，并能在不跑昂贵 GPU 实验的情况下搜索性价比最高的部署配置。
  • Etalon（arXiv 2407.07000 ↗）。作者团队后来认为 TTFT、TBT、TPOT 这些常用指标不能完整反映用户体验，提出了“流畅度指数”（fluidity-index）。这也提醒读者：本文以 P99 TBT 为核心的评价方式本身也有局限。
  • Medha（arXiv 2409.17264 ↗）。面向长上下文、请求长度差异极大的场景，引入细粒度的抢占式调度，用自适应分块和流式流水线并行让抢占变得可行，并提出 KV 缓存并行以降低超长上下文的 decode 延迟。它可以看作把“分块”从降低干扰的手段，进一步发展成支持抢占和长短请求混跑的基础。

0 导读：这篇文章解决什么问题

用大模型的人大多遇到过这种事：同一个问题问两遍，答案不一样。采样本来就带随机性，这不奇怪；奇怪的是，把温度调到 0、让模型每一步都只取概率最高的那个词，答案仍然会变。无论是调用商业 API，还是用 vLLM、SGLang 在自己的机器上跑开源模型，都是如此。

流行的解释是“GPU 上并发执行的线程谁先算完不确定，浮点加法又不满足结合律，所以结果随机”。这篇博客认为这个解释抓错了重点：大模型前向计算里的内核，同样的输入跑一千遍，结果是逐位相同的。真正的原因是，内核对某一条请求的计算方式取决于这一批里一共有多少请求：批大了或小了，内核会换一种切分工作的方式，加法的顺序随之改变，最后几位二进制就不一样了。而批有多大，取决于服务器此刻有多忙，这对单个用户来说是不可知的，于是用户看到的就是“随机”。作者把“每条请求的结果与批大小无关”这个性质叫做批不变性（batch invariance），并演示了怎样把 RMSNorm、矩阵乘和注意力这三类内核改成批不变的。

改造之后，在 Qwen3-235B 上用温度 0 对同一个提示采样 1000 次，得到的 1000 个回答完全一致（改造前有 80 种不同的回答）；代价是推理变慢，在作者的测试里总耗时从 26 秒变成 42 秒。文章最后把这件事接到强化学习上：如果连推理本身都做不到逐位可复现，训练端和推理端算出的概率就不可能逐位一致，于是名义上的“on-policy”训练其实偏离了 on-policy。作者让采样端和训练端逐位一致之后，两者之间的 KL 散度恒为 0。这条线索的另一半是同期 Yao 等人关于“训推不一致”和截断重要性采样（TIS）的工作，本页在“后来怎么样了”里专门讲它。

读完这部分，你应该能回答这几个问题：

  • 浮点加法为什么不满足结合律？差几位二进制，为什么能让整段回答都变掉？
  • “并发 + 原子加”这个解释错在哪里？什么叫“逐次运行确定”，什么叫“批不变”，两者有什么区别？
  • 批大小具体是怎样改变 RMSNorm、矩阵乘、注意力的加法顺序的？split-K、split-KV、分块预填充在其中扮演什么角色？
  • 批不变内核放弃了哪些优化，慢了多少，慢在什么场景？
  • 这件事为什么对 on-policy 强化学习重要？“消除差异”和“修正差异”（TIS）两条路各有什么代价？

1 引言：温度为 0，为什么答案还会变

这一节要回答的问题：温度为 0 时采样在理论上是确定的，为什么实际的推理服务仍然不确定？流行的“并发 + 浮点”解释说了什么，为什么作者认为它不完整？在开始讲原因之前，作者先指出连“确定”这个词本身都需要拆开定义，这一节把这个拆分讲清楚。
先补一点背景：温度和贪心解码。

语言模型每一步输出的是一组分数（logits）\(z_1,\dots,z_V\)，每个分数对应词表里的一个词。把分数变成概率要经过 softmax，温度 \(T\) 控制这个分布有多“尖”：

$$p_i=\frac{\exp(z_i/T)}{\sum_{j=1}^{V}\exp(z_j/T)}$$

\(T\) 越小，分数最高的词的概率越接近 1；\(T\to 0\) 时，采样就退化成“直接取分数最大的那个词”，叫贪心解码（greedy decoding）。所以温度为 0 时，只要每一步算出的 logits 完全一样，生成的文字就一定一样。反过来说，温度为 0 时答案会变，只能说明某一步算出的 logits 变了。

logits 哪怕只变了最后几位二进制，在绝大多数步骤里也不会改变“谁最大”。但只要某一步恰好有两个候选词的分数非常接近，这点微小的差别就可能让它们的大小关系翻转。一旦这一步选了不同的词，后面每一步的输入都不同了，整段回答就会走向不同的方向。

作者首先承认这是一个普遍现象：OpenAI 社区里有不少讨论，vLLM 和 SGLang 的文档也都写明温度为 0 时不保证结果一致。对此最常见的解释，作者称为“并发 + 浮点”假说：GPU 上大量线程同时运行，谁先算完是不确定的；如果把各线程的结果按完成的先后加在一起，加法的顺序就是随机的；而浮点加法不满足结合律，顺序不同结果就不同。一篇 2025 年 6 月的 arXiv 论文（Yuan 等，2506.09501，研究数值精度对推理可复现性的影响）也是这样描述的。

作者认为这个假说“不完全错，但没有说到点子上”。他给了一个反例：在 GPU 上把同样两个 2048×2048 的 BF16 矩阵相乘 1000 次，每一次的结果都和第一次逐位相同。这里明明用了浮点数，GPU 上也明明有大量并发，结果却是确定的。所以，并发本身并不必然带来不确定性，一定还有别的原因。

为了说清楚这个原因，作者先指出下面四句话同时成立，这也是全文的提纲：

  1. GPU 上确实有些内核是不确定的（同样的输入跑两次，结果不同）。
  2. 但语言模型前向计算用到的所有内核都是确定的。
  3. 因此推理服务器（比如 vLLM）的前向计算，也可以说是确定的：给定它这一步要处理的全部请求，输出是确定的。
  4. 然而从任何一个使用者的角度看，结果仍然是不确定的。

内核层同一个内核、同样的输入张量，跑多少遍结果都逐位相同（逐次运行确定）

读的时候容易误解的地方：这篇文章并没有说“GPU 上不存在不确定的内核”，也没有说“浮点误差无关紧要”。它说的是：在大模型推理这个具体场景里，用户看到的不确定性，主要不是来自线程完成先后的随机性，而是来自“批的组成随服务器负载变化”与“内核结果依赖批大小”这两件事的叠加。训练的反向传播里确实有不确定的内核（第 3 节会提到），那不是这篇文章的主题。

2 “原罪”：浮点加法不满足结合律

这一节要回答的问题：我们习惯把神经网络看成数学函数，加法满足交换律和结合律，似乎应该有一个“数学上正确”的唯一答案。为什么计算机算出来的结果会依赖加法的顺序？这种依赖有多严重？作者把它称为一切数值差异的“原罪”，但也强调它本身并不回答“顺序为什么会变”。
先补一点背景：浮点数怎么表示一个数。

计算机里的浮点数和科学计数法是一回事：一个数被写成“有效数字 × 底数的若干次方”。二进制浮点数的形式是

$$x=(-1)^{s}\times(1.f)_{2}\times 2^{e}$$

其中 \(s\) 是符号位，\(e\) 是指数，\(f\) 是小数点后的若干位二进制，叫尾数。尾数的位数是固定的，这意味着浮点数能保留的“有效数字”个数是固定的：数越大，相邻两个能表示的数之间的间隔就越大。这个间隔叫 ulp（unit in the last place，最后一位的单位）。大模型里常见的三种格式：

  • FP32：8 位指数、23 位尾数。在 1 附近，ulp 是 \(2^{-23}\approx 1.2\times10^{-7}\)。
  • BF16：8 位指数（和 FP32 一样，所以能表示的数的范围一样大）、只有 7 位尾数。在 1 附近，ulp 是 \(2^{-7}\approx 0.0078\)，也就是说只有两到三位十进制有效数字。
  • FP16：5 位指数、10 位尾数。范围比 BF16 小得多，但精度高 8 倍。

两个浮点数相加时，硬件先把指数对齐，把较小的数的尾数右移；相加的精确结果往往需要比尾数更多的位才能写下，于是必须舍入到最近的可表示数（默认规则是“就近舍入，恰好落在两个可表示数正中间时，取尾数末位为 0 的那个”）。舍掉的那一部分信息，就永远丢了。

作者用十进制讲了一个例子，便于用手算：假设一种“十进制浮点数”只能保留 3 位有效数字。123 加 456 等于 579，两数指数相同，和整数加法没有区别。但 1230 加 23.4 的精确结果是 1253.4，需要 5 位有效数字才能写下；只保留 3 位，就变成 1.25×10³，即 1250。效果相当于先把 23.4 舍成了 20 再相加，那 3.4 就丢了。只要两个数的“量级”（指数）不同，每次相加都可能丢信息，而在神经网络里，量级不同的数相加是家常便饭。

丢信息本身还不是问题，问题在于丢多少取决于加的顺序。用同样的 3 位有效数字，本站构造一个更极端的例子：

1230+4 → 1234 → 舍成 1230+4 → 1230+4 → 1230+4 → 1230+4 → 1230

两种顺序在数学上是同一个和，在 3 位有效数字的浮点里却差了 20。真实的 BF16 也一样：256 附近的 ulp 是 2，所以 \((256+1)+1\) 每一步都被舍回 256，而 \(256+(1+1)=258\)（本站按 BF16 的舍入规则推算）。

作者还给了一个更直观的数字：把 \(10^{-10},10^{-5},10^{-2},1\) 这四个数和它们的相反数放在一起，一共 8 个数，精确的和显然是 0。用 Python 的双精度浮点把它们随机打乱顺序求和，重复一万次，得到了 102 种不同的结果，散布在大约 \(\pm 8\times10^{-17}\) 之间，而精确答案是 0。这说明，即使只有 8 个数，加法顺序能造成的结果也五花八门。

把这个结论搬到大模型里：一次矩阵乘的每个输出元素都是几千项乘积之和，一次 RMSNorm 要把几千个平方加起来，一次注意力要在几千个位置上累加。这些加法只要换了顺序，结果的最后几位就可能不同。实际实现里，BF16 的矩阵乘通常在 FP32 里累加，最后再舍入成 BF16 输出；FP32 累加器里差一个 ulp，舍入后多半还是同一个 BF16 数，但只要碰上舍入的边界，输出就会差一个 BF16 的 ulp，也就是千分之几的相对误差。这样的差别经过几十层网络传下去，最终在 logits 上表现为一个很小但非零的扰动。

读的时候容易误解的地方：“浮点不满足结合律”只解释了为什么顺序不同会导致结果不同，并没有解释顺序为什么会变、什么时候会变、怎样避免。作者特意强调了这一点：结合律是原罪，但真正的嫌疑人要到内核的实现方式里去找。也不要把这里的问题理解成“精度不够”，把 BF16 换成 FP32 只能让差别变小，不能让它消失；要让结果逐位相同，只能让加法顺序固定。

3 内核为什么不总按同一顺序相加：原子加什么时候才需要

这一节要回答的问题：“并发 + 浮点”假说说的是：并发线程完成的先后不确定，如果累加顺序跟着完成先后走（典型的就是原子加），累加顺序就不确定。那么大模型的前向计算里到底有没有原子加？作者的回答是：几乎没有，所以这个机制和推理的不确定性完全无关。这一节解释为什么现代内核很少需要原子加，以及由此得出的结论“前向计算是逐次运行确定的”。
先补一点背景：GPU 内核、SM 和“归约”。

GPU 上的一次计算叫一个内核（kernel）。内核启动时会把工作分成很多个线程块（thread block），每个线程块被分配到一个 SM（streaming multiprocessor，流式多处理器）上执行。可以把 SM 理解成 GPU 里的“核”，博客里说的“core”指的就是 SM；比如 H100 SXM 有 132 个 SM（NVIDIA 规格，本站补充）。各个 SM 之间没有天然的同步机制，它们什么时候开始、什么时候结束，彼此并不知道。

归约（reduction）是指把一组数合并成一个数的运算，最常见的就是求和，也包括求最大值。矩阵乘里每个输出元素是一个求和，RMSNorm 里有一个求平方和，注意力里有求最大值和求和，所以大模型里到处都是归约。

原子加（atomic add，也叫 fetch-and-add）是硬件提供的一种操作：许多 SM 可以同时往同一个内存位置“加上一个数”，硬件保证每一份贡献都会被加进去、不会互相覆盖，但不保证加的先后顺序。顺序由谁先算完决定，而谁先算完每次运行都可能不同。

设想要用 100 个核对一个 100 维的向量求和（比如 torch.sum）。100 个元素可以并行读入，但最后总得汇总成一个数。最省事的办法是让每个核把自己那份原子地加到同一个结果上。这样做每次运行的结果都可能不同，因为加的顺序取决于各个核完成的先后。这就是人们通常说的“不确定性”：同样的输入、同样的程序跑两次，结果不同。作者把它叫做逐次运行不确定（run-to-run nondeterminism）。

作者指出，虽然原子加确实会让内核不确定，但绝大多数内核根本不需要它。原因有两个：

  • 批这一维通常已经提供了足够的并行度。如果不是对 1 个向量求和，而是同时对 500 个向量各自求和，就可以让每个核负责一整个向量，在核内部按固定顺序加完，核与核之间不需要任何汇总。大模型里，“很多个 token 各自做同样的事”是常态，所以这种做法几乎总是可行的。
  • 就算必须把一次归约拆给多个核，也有确定的拆法。比如把 100 个元素的求和拆成 5 段、每段 20 个，5 个核各算一段（这叫“分段”或“树形”归约）；剩下的 5 个部分和，可以再用一个很小的、不并行的“收尾”归约按固定顺序加起来，或者用信号量让各个线程块按固定次序依次累加（CUTLASS 文档里描述过这种做法）。这两种方式的加法顺序都写死在程序里，与谁先算完无关。

因此，对绝大多数神经网络运算来说，放弃原子加几乎没有性能损失。仍然会因为避免原子加而明显变慢的常见运算只有少数几个，比如 PyTorch 的 scatter_add；大模型里常用的只有一个，就是 FlashAttention 的反向传播。作者顺带提了一个细节：广泛使用的 Triton 版 FlashAttention 反向，和 FlashAttention-2 论文里的算法并不一样，它为了避免原子加多做了一部分重计算，代价是多花约 40% 的浮点运算。

但前向计算里没有任何必须用原子加的运算。所以大模型的前向计算是逐次运行确定的：从推理服务器的角度看，只要这一步处理的请求完全相同，输出就完全相同。这正是上面四句话里的第 2、3 句。作者引用了维基百科对“确定性算法”的定义（给定输入，总是产生同样的输出）来说明，在这个定义下推理服务器的前向计算确实是确定的。

可是，一个系统里的某个部件是确定的，并不能保证整个系统在用户看来是确定的。作者举了批归一化（batch norm）做类比：如果一个请求的输出依赖于同批的其他请求，而每个请求都无从知道同批里会有谁，那么从每个请求自己的角度看，结果就是不确定的。接下来他要证明的正是：大模型推理恰好有这个问题。原因不是不同请求之间泄露了什么信息，而是前向计算缺乏“批不变性”，使得每个请求的输出依赖于这一步的批大小。

读的时候容易误解的地方：“前向里一个原子加都没有”说的是典型的稠密模型前向，不是说任何推理代码都不会用原子加。具体的推理引擎里确实有例外：vLLM 后来的批不变模式文档就提到，它把 LoRA 的 shrink 归约从原子加改成了“固定切成 8 段、按固定顺序相加”。另外，“逐次运行确定”也只在同一台机器、同一套软件版本下成立；作者在第 4 节明确说，换 GPU 型号或 PyTorch 版本，结果可以不同，那是另一种意义上的“不变性”，本文不处理。

4 批不变性与“确定性”：确定的内核怎么拼出不确定的系统

这一节要回答的问题：如果每个内核都是确定的，用户看到的不确定性到底从哪里来？作者给出的答案是“批不变性”的缺失：内核对批里每个元素算出的结果，会随批大小而变。这一节先用矩阵乘演示这个现象，再说明它为什么会在推理服务里变成用户可见的不确定性，并顺便指出这和 GPU 本身无关。
先补一点背景：推理服务里的“批”是怎么来的。

推理服务为了提高吞吐量，会把多个用户的请求放在一起算。现代引擎（vLLM、SGLang 等）用的是迭代级调度（也叫连续批处理）：每生成一个 token 就重新组一次批，有请求结束就移出，有新请求到达就加入，长输入还可能被切成几段分几次算（分块预填充）。所以同一个请求在它生命周期的每一步里，和它同批的请求数、同批的 token 总数都在变，变化的节奏取决于其他用户什么时候来、要生成多长。详细的来龙去脉见本站 vLLM 精读 §2.3 和 Sarathi-Serve 精读 §4.1。

对矩阵乘来说，这意味着：模型里每个线性层计算的是 \(C=AB\)，其中 \(A\) 的行数 \(M\) 等于这一步所有请求加起来的 token 数，\(B\) 是权重矩阵（\(K\) 行 \(N\) 列）。同一个请求的那一行，会因为别的请求多了或少了，而落在一个 \(M\) 不同的矩阵乘里。

作者先假设所有矩阵乘实现都是逐次运行确定的（他注明这并非绝对，但常见实现都满足）。即便如此，它们也不是批不变的：批大小一变，批里每个元素的结果都可能变。这在数学上很奇怪，因为矩阵乘对批里的每一行是独立的，其他行有多少、是什么，都不应该影响某一行的结果。

但实验结果就是如此。作者构造了一个 2048×4096 的矩阵 \(a\) 和一个 4096×4096 的矩阵 \(b\)（元素取 −1000 到 1000 之间的等差数列），然后用两种方式计算 \(a\) 的第一行乘以 \(b\)：一种是只取 \(a\) 的第一行单独去乘，相当于批大小为 1；另一种是整个 \(a\) 乘 \(b\) 再取第一行，相当于批大小为 2048。两种结果的最大差值是 1669.25。作者特意说明，这个脚本反复运行，每次都给出同样的差值，所以它是逐次运行确定的；但换一种 GPU 或 PyTorch 版本，差值可能不一样，因为它不保证跨硬件、跨软件版本不变。

先补一点背景：几种容易混淆的“不变性”。
  • 逐次运行确定（run-to-run deterministic）：同一个内核、同样的输入，跑多少次结果都一样。第 3 节说的就是这个。
  • 批不变（batch-invariant）：批里某个元素的结果，不随批大小（以及同批其他元素是什么）而变。这是本文要实现的性质。
  • 批内位置不变（batch-position-invariant）：同一个元素放在批的第几行，结果都一样。大多数矩阵乘库至少满足这一条，但第 5.2 节会讲到一种连这条都不满足的做法。
  • 跨硬件 / 跨软件版本不变：换 GPU 或换库版本，结果也一样。本文不追求这一条。

一个不批不变的内核单独看并没有问题，问题出在它被放进推理服务之后。用户向推理服务发请求时，服务器此刻有多忙，在用户看来是不确定的；服务器的负载决定了内核在什么批大小下运行；而内核的结果依赖批大小。三者叠加，每个请求最终的结果就随服务器负载而变。作者把这个逻辑概括成一句话：把一个“内核对它不保持不变的属性”（批大小）和“这个属性本身的不确定性”（服务器负载）组合在一起，就得到一个不确定的系统。

5 怎样让内核批不变：只需管三类归约

这一节要回答的问题：一个 Transformer 由很多内核组成，要让整个模型批不变，是不是每个内核都要重写？作者的回答是：只需要关心含有归约的那三类运算，即 RMSNorm、矩阵乘和注意力；而且它们的难度依次递增。这一节先讲总原则，再分三小节逐个讲。

要让一个 Transformer 批不变，它的每个内核都必须批不变。幸运的是，逐元素运算（加法、乘法、激活函数这类每个元素各算各的运算）天然是批不变的，因为每个输出只依赖同一位置的输入，没有任何加法顺序可言。作者补充说，这一点在 PyTorch 的所有内核里都成立，但并不是天经地义：有些 CPU 内核会对数组的一部分用向量化指令、对剩下的部分用普通指令，两者的数值未必逐位相同。

所以需要操心的只有三类含归约的运算：RMSNorm、矩阵乘和注意力。作者明确把多卡并行带来的归约（比如张量并行里的 all-reduce）排除在本文之外，只说同样的原则也适用；他顺带提到一个实用的事实：在 Blackwell 上，以及 CUDA 12.8 以上的 Hopper 上，NVLink-SHARP 交换机内的归约是确定的（来源是 NCCL 的 GitHub issue）。

贯穿三小节的总原则可以写成一句话：每个元素的归约顺序必须固定，不能随批大小而变。这并不要求永远只用一种归约策略：如果被归约的元素个数变了（比如隐藏维度不同的另一个模型），换一种策略完全没问题。只有当“批有多大”影响了归约策略时，批不变性才会被破坏。

5.1 RMSNorm：小批时不要为了填满 GPU 而拆行

先补一点背景：RMSNorm 在算什么。

RMSNorm 是现代大模型里最常用的归一化层。它对每个 token 的隐藏向量 \(x\in\mathbb{R}^{d}\) 单独做归一化：先求所有分量平方的平均值，开方得到“均方根”，再用它去除每个分量，最后乘上一个可学习的权重 \(w\)：

$$\mathrm{RMSNorm}(x)_i=\frac{x_i}{\sqrt{\frac{1}{d}\sum_{j=1}^{d}x_j^{2}+\epsilon}}\;w_i$$

这里唯一的归约是那个求和 \(\sum_{j}x_j^{2}\)，它沿隐藏维度进行，每个 token（批里的每一行）各算各的。输入是一个形状为 [批大小, 隐藏维度] 的矩阵。

并行算法的一般原则是尽量减少核与核之间的通信。对 RMSNorm 来说，最自然的做法是让每个核负责一整行：一行的归约全部在一个核内部完成，核之间不需要交流。这叫数据并行策略，因为它只沿着“不需要通信的维度”（批这一维）做并行。作者提醒，这里关键的前提是内核启动的线程块数要多于 SM 数，GPU 才能被填满。

批变大时，这个策略很容易保持：一个核依次处理好几行就行，每一行的归约方式和以前完全一样，所以批不变性得以保持。批大小为 200 能填满 GPU，批大小为 2000 就更不用说。

麻烦出在批变小时。行数少于核数，就有一些核闲着。一个称职的内核工程师这时会自然地想到第 3 节说的办法：把每一行的归约拆给几个核（分段归约），或者用原子加，以便把 GPU 填满。这样性能是好了，但同一行在大批时由一个核从头加到尾，在小批时被拆成几段分头加再合并，归约顺序变了，批不变性就没了。

怎么办？作者给出两个选择。最简单的是干脆不管小批的情形：小批时这个内核本来就算得很快，就算因为有核闲着而慢一些，也不至于成为灾难。如果非要优化，另一个办法是始终使用一种在极小批时也有足够并行度的归约策略，比如无论批多大都把每一行固定拆成同样的几段、按同样的顺序合并。这样大批时并行度会过剩，但在整个批大小范围内都能得到不错（虽然不是最优）的性能，而且因为拆法不随批大小变化，批不变性得以保持。

读的时候容易误解的地方：批不变并不等于“禁止拆分归约”，而是“拆法不能依赖批大小”。一个永远把每行拆成 4 段、按固定顺序合并的 RMSNorm 也是批不变的；破坏批不变性的，是那种“批小就拆、批大就不拆”的自适应逻辑。作者引用 Quack 的博文说明，归约可以有线程级、warp 级、线程块级、cluster 级等多种层次，选哪一种都可以，只要选择本身不随批大小变化。

5.2 矩阵乘：禁用 split-K，所有形状用同一套配置

先补一点背景：矩阵乘内核怎么分工，什么是 split-K。

矩阵乘 \(C=AB\) 的每个输出元素是一次长度为 \(K\) 的点积：

$$C_{mn}=\sum_{k=1}^{K}A_{mk}B_{kn}$$

可以把它看成“先逐元素相乘，再沿 \(K\) 归约”。高效的 GPU 矩阵乘不会一个元素一个元素地分配工作，而是把输出矩阵切成二维的 tile（比如 128×128），每个 tile 交给一个 SM，由它沿 \(K\) 方向把这块输出完整地累加出来。之所以要按 tile 而不是按单个元素分，是因为要让每次从显存读进来的数据被反复使用（提高算术强度），并且要喂饱张量核（Tensor Core，GPU 上专门做小矩阵乘的硬件单元），它一条指令就处理一个小矩阵块。这仍然是“数据并行”：每个输出元素的归约在一个 SM 内部完成。

问题在于 tile 的数量。例如 [1024, K] × [K, 1024] 的矩阵乘、用 128×128 的 tile，只能切出 8×8 = 64 个 tile，而 H100 SXM 有 132 个 SM（本站补充），一半以上的 SM 没活干。这时库通常会改用 split-K：沿 \(K\) 方向把每次点积切成几段，分给几个 SM 各算一段，最后把几段部分和加起来：

$$C_{mn}=\underbrace{\sum_{k\le K/2}A_{mk}B_{kn}}_{\text{SM}_{1}}+\underbrace{\sum_{k>K/2}A_{mk}B_{kn}}_{\text{SM}_{2}}$$

这样 64 个 tile 就变成了 128 份工作，GPU 被填满了，但每个输出元素的加法顺序也变了。cuBLAS 这类库会根据 \(M,N,K\) 的具体形状，用启发式规则挑选 tile 大小、是否 split-K、切几段，所以 \(M\)（也就是批里的 token 数）一变，挑出来的方案就可能变。

作者指出，矩阵乘和 RMSNorm 一样，标准策略是数据并行；也和 RMSNorm 一样，当“批”的维度太小时，不得不沿归约维度 \(K\) 切分，这就是 split-K，它破坏批不变性。矩阵乘比 RMSNorm 更麻烦的地方在于，它有两个“批”维度（\(M\) 和 \(N\)），而且每个核需要的工作量大得多才能用好张量核，所以更容易出现“tile 太少”的局面。

作者还提到一种更“糟糕”的策略：stream-K。它为了让各个 SM 的负载更均衡，对不同的输出 tile 用不同的方式沿 \(K\) 切分。这样一来，同一个元素放在批里的不同位置，就会被不同地切分，于是连“批内位置不变”都保证不了。而大多数矩阵乘库虽然不是批不变的，至少是批内位置不变的。

再补一点背景：张量核指令和“量化效应”。

张量核指令一次处理一个固定形状的小矩阵块，例如 Hopper 上的 wgmma.mma_async…m64n128k16 一次算 64×128 的输出、沿 \(K\) 累加 16 项（Hopper 的这些指令见本站 FlashAttention-3 精读 §2.3）。不同的指令内部可能用不同的顺序累加。批很小时，用一条 256 行的大指令去算 32 行有效数据，绝大部分算力都浪费了；批大小为 1 时，最快的内核通常根本不用张量核。所以库在小批时会换成更小的指令，甚至不用张量核，这又是一种随批大小而变的归约顺序。

另外，tile 是整块分配的，这会带来两种“量化效应”（本站用自己的例子说明）：一是 tile 量化，比如 \(M=129\) 而 tile 高 128，就要用两个 tile 行，第二行只有 1/128 是有用的；二是 wave 量化，比如 132 个 SM 恰好算完 132 个 tile 是一“波”，若有 133 个 tile，就要再来一波，而这一波里只有 1 个 SM 在干活，多 1% 的工作量几乎让时间翻倍。库通常靠针对不同形状换 tile 大小来抹平这些锯齿。

那么怎样让矩阵乘批不变？作者的答案很朴素：只编译一种内核配置，所有形状都用它。也就是固定 tile 大小、固定张量核指令、不用 split-K。这样会损失一些性能，但在大模型推理里通常不是灾难，原因是：split-K 主要在 \(M\) 和 \(N\) 都很小时才需要，而大模型里 \(N\)（模型维度）通常很大，就算 \(M\) 很小，沿 \(N\) 也能切出不少 tile。

5.3 注意力：先写入 KV 缓存，再用固定段长切分 KV

先补一点背景：FlashAttention、KV 缓存、分块预填充。

FlashAttention 把注意力按块计算：对每一块 query，依次扫过一块一块的 key/value，用“在线 softmax”边扫边合并，从来不把完整的注意力矩阵写到显存里（详见本站 FlashAttention 精读 §3.2）。FlashAttention-2 的并行方式是沿 query 切分、沿 key/value 归约，一块 query 的整个归约在一个 SM 里完成，所以它也是一种“数据并行”策略。

KV 缓存：生成时，之前所有 token 的 key 和 value 被存下来，每一步只算新 token 的 K、V 并追加进去；vLLM 把它切成固定大小的块，用一张“页表”（块表）记录每个块在显存里的位置（见 vLLM 精读 §4.2）。前缀缓存让多个请求共享相同前缀的 KV（见 SGLang 精读 §3）。分块预填充把一段很长的输入拆成几段、分几步算（见 Sarathi-Serve 精读 §4.1）。

这些优化的共同点是：同一条序列，在不同的时候会被切成不同的样子交给注意力内核。同一个 token 的注意力，有时它前面的 KV 全在缓存里（解码），有时一部分在缓存里、一部分正在这一步里算（分块预填充），有时全都在这一步里算（不切分的预填充）。

作者说，矩阵乘做到批不变之后，注意力还有两个额外的麻烦，“恰好因为它里面有两个矩阵乘”。第一，RMSNorm 和矩阵乘只沿特征维归约，注意力还要沿序列维归约。第二，正因为要沿序列归约，注意力要面对推理引擎各种改变“序列怎么被切开”的优化。所以对注意力来说，批不变的要求更强：数值结果不仅不能随“同时处理多少条请求”而变，还不能随“每条请求在引擎里被怎样切段”而变。作者举的要求是：处理一条序列的第 1000 个 query token 时，不管 KV 缓存里此刻有 0 个 token（整段预填充）还是 999 个 token（逐个解码），它的归约顺序都必须一模一样。

第一个问题：缓存部分和新算部分分开归约。有的实现（比如 vLLM 当时的 Triton 注意力内核）把“KV 缓存里已有的 K/V”和“这一步正在处理的 token 的 K/V”分成两部分分别归约，这样做无法批不变。原因藏在边界上：设内核每次处理 32 个位置的 K/V，缓存里有 80 个，这一步新算 48 个，一共 128 个。缓存部分要用 3 块（两块满的、一块只有 16 个有效位置），新算部分要用 2 块（一块满的、一块只有 16 个有效），一共 5 块。而如果这 128 个位置是一口气算的（缓存为空），只需要 4 块整块。块的边界不同，在线 softmax 合并的顺序就不同。

修法很简单：在调用注意力内核之前，先把这一步新算的 K/V 写进 KV 缓存、更新好页表，然后让内核只从缓存里读。这样无论这一步处理了多少个 token，内核看到的 K/V 永远是同一种布局，块的边界永远从位置 0 开始每 32 个一切。再加上上一小节说的“固定 tile 大小”等要求，注意力的批不变就做到了。

先补一点背景：split-KV（FlashDecoding）为什么在解码时必不可少。

解码阶段每条序列每步只有 1 个新的 query。如果不沿 KV 切分，注意力内核只能沿“批 × 注意力头 × query 长度”这几个维度并行，而 query 长度是 1。批不大时，能切出来的工作份数远少于 SM 数。更糟的是，如果某条序列的 KV 缓存很长，它的注意力本身就要算很久，却只能由很少几个 SM 来算。

于是解码内核会沿 KV 维度切分：把一条序列的 KV 切成若干段，每段由一个 SM 算出局部结果（局部最大值 \(m_s\)、局部指数和 \(\ell_s\)、未归一化的局部输出 \(\tilde o_s\)），最后再合并：

$$m=\max_{s}m_{s},\qquad \ell=\sum_{s}e^{m_{s}-m}\,\ell_{s},\qquad o=\frac{1}{\ell}\sum_{s}e^{m_{s}-m}\,\tilde o_{s}$$

这就是 split-KV，也叫 FlashDecoding。合并的数学结果与切几段无关，但浮点结果与切在哪里有关。

第二个问题：split-KV 的切法随负载而变。和 RMSNorm、矩阵乘不同，这种情形没法“干脆不管”：长上下文的解码即使只有一个请求，注意力也可能很慢，必须拆开并行。常见的切法是先算出需要多少份并行度、再把 KV 平均切成这么多段。比如 KV 长 1000、需要 4 段，每段 250。作者指出这样做破坏批不变性，因为切几段取决于这一步处理了这条序列的多少个 query token、同批有多少请求。他还点名了 FlashInfer 的“均衡调度”算法：它会选出“仍能填满所有 SM 的最大段长”，所以段长随负载而变（FlashInfer 的调度见本站 FlashInfer 拆解页）。

作者特别强调，对注意力而言，“无论批多大都固定切成同样的段数”也不够。原因在于同一个 token 在不同的步里，所在的那次注意力调用要处理的 KV 总长度不同：段数固定，段长就随总长度变，段的边界也就跟着移动。正确的做法是固定段长：每段固定 256 个位置，总长度变了只是段数变。KV 长 1000 时，切成 256、256、256 和最后一段 232。这样，任何一个位置在任何一步里都落在同样的段边界之间，归约顺序就固定了。

读的时候容易误解的地方：固定段长并不意味着“任何情况下都要拆”。只要拆法与批大小、与这一步处理了多少 token 无关，拆不拆都可以是批不变的；SGLang 后来对 FlashAttention-3 后端的处理就是干脆把段数固定为 1（完全不拆）。另外，“先写缓存再算”保证的是归约边界一致；被读出来的 K/V 本身要一致，还要求算出 K/V 的那些投影矩阵乘也是批不变的，所以三类内核必须一起改，缺一个都不行。

6 实现：用 torch.Library 把算子换掉，在 vLLM 上演示

这一节要回答的问题：上面这些批不变内核怎样接进一个现成的推理引擎，而不必大改模型代码？作者发布了什么代码，里面有什么、没有什么？

原文这一节很短：作者在 vLLM 上演示了确定性推理，做法是利用 vLLM 的 FlexAttention 后端处理注意力，再用 PyTorch 的 torch.Library 机制把相关的 PyTorch 算子“无侵入”地替换成批不变版本。批不变内核库发布在 GitHub 的 thinking-machines-lab/batch_invariant_ops，另附一个让 vLLM 以“确定性”模式运行的例子。

先补一点背景：torch.Library 和 FlexAttention 是什么。

PyTorch 的每个张量运算最终都会调用一个底层算子（比如 aten::mm 就是矩阵乘），由“分发器”根据设备类型找到具体实现。torch.library.Library 允许在运行时为某个算子在某种设备上注册一个新的实现。这样，模型代码一行不改，所有调用 torch.mm 的地方就都会走到新实现上。

FlexAttention 是 PyTorch 提供的一个注意力编程接口：用户用几行 Python 描述注意力的打分修改和掩码，编译器生成融合的注意力内核。Horace He 是 FlexAttention 论文（arXiv 2412.05496）的作者之一，所以作者选它来实现需要定制切分方式的批不变注意力，是很自然的。

示意图：batch_invariant_ops 的接入方式（按 2026-10 时仓库主分支的代码整理）
模型代码（不改动）调用 torch.mm / addmm / log_softmax / mean→torch.Library 覆盖 4 个 aten 算子mm、addmm、_log_softmax、mean.dim→Triton 内核矩阵乘：持久化内核，BF16 固定 128×128×64 的 tile，K 方向整段在一个程序内累加，不用 split-K；log_softmax / mean：每行一个程序，按固定块长循环
注意力不在这 4 个算子里→vLLM 的 FlexAttention 后端仓库里只提供了一个固定的注意力块大小（16×16）接口；固定段长的 split-KV 改动未随代码发布
本站根据 仓库代码 ↗ 整理。RMSNorm 在 PyTorch 写法里通过 mean 求平方和的平均，所以覆盖 mean.dim 就让它批不变了。

仓库里的矩阵乘是一个“持久化”内核：启动的程序数等于 SM 数和 tile 数中较小的那个，每个程序依次处理若干个 tile。对每个 tile，它沿 \(K\) 方向以固定的块长从头累加到尾，累加器用 FP32。因为 tile 大小和 \(K\) 方向的块长都是写死的，每个输出元素的累加顺序只取决于 \(K\)，与 \(M\)（批大小）无关，这就是批不变的来源。仓库的测试脚本复现了第 4 节的实验：标准 PyTorch 下“单独算第一行”和“整批算再取第一行”有差别，打开批不变模式后差别为 0。

vLLM 那边的接入是一个概念验证的拉取请求（vLLM PR #24583，2025-09-10 提交，后来没有合并而是关闭，正式支持另起炉灶，见“后来怎么样了”）。仓库的说明写道：用 Qwen3-8B、温度 0、让 1000 个请求各生成 100 个 token，不打这个补丁时得到 18 种不同的输出，打上之后只有 1 种。这个例子要求 PyTorch 2.9 以上，并且关闭了 CUDA Graph（--enforce-eager）。

读的时候容易误解的地方：发布的库只覆盖了矩阵乘、log_softmax 和求平均这几个 PyTorch 算子，本身不包含批不变的注意力内核；博客里 Qwen3-235B 的实验依赖的是作者内部对 FlexAttention 的改动和 vLLM 的补丁。所以“装上这个库就能让任意模型在任意引擎上确定”是不对的：融合内核（比如引擎自带的融合 RMSNorm、MoE 内核）不经过这些 aten 算子，不会被替换。

这一节要回答的问题：不改内核时，温度为 0 的推理到底有多不确定？改成批不变之后是否真的完全确定？要付出多少速度？以及作者最关心的应用：能不能让强化学习的采样端和训练端逐位一致，这样做有什么好处？

7.1 有多不确定：1000 次采样里有 80 种回答

作者用 Qwen3-235B-A22B-Instruct-2507（总参数 2350 亿、每个 token 激活 220 亿的 MoE 模型，非思考模式），以温度 0 对同一个提示“Tell me about Richard Feynman”采样 1000 次，每次生成 1000 个 token。结果出人意料：1000 个回答里有 80 种不同的版本，最常见的那一种出现了 78 次。

更有意思的是分叉的位置。所有回答的前 102 个 token 都完全相同，第一次分叉出现在第 103 个 token：所有回答都生成了“费曼于 1918 年 5 月 11 日出生于……”这半句，然后 992 个回答接着写“Queens, New York”（纽约皇后区），另外 8 个写成“New York City”（纽约市）。两种写法都说得通，模型在这一步对两个候选的打分想必非常接近，于是一点点数值扰动就翻转了选择。打开批不变内核后，1000 个回答完全相同。作者说，这本来就是我们对一个贪心采样器在数学上的预期，但没有批不变内核就做不到。

7.3 真正的 on-policy RL：采样端和训练端逐位一致

先补一点背景：大模型 RL 为什么会有“两套引擎”，什么是 on-policy。

用强化学习训练大模型（RLHF、RLVR 等）时，每一轮先让当前模型对一批题目生成回答（叫 rollout 或采样），再根据奖励计算梯度、更新参数。生成回答最花时间，所以几乎所有框架（verl、OpenRLHF、slime、AReaL 等）都用高度优化的推理引擎（vLLM、SGLang）来生成，再用训练框架（FSDP、Megatron）重新计算这些回答在当前参数下的概率并求梯度。同一份参数被加载进两套代码里，见本站 HybridFlow 精读 §2.1 与 §5。

策略梯度的基本形式是：样本应当来自当前策略 \(\pi_\theta\) 本身，

$$\nabla_\theta J(\theta)=\mathbb{E}_{y\sim\pi_\theta}\big[A(y)\,\nabla_\theta\log\pi_\theta(y)\big]$$

其中 \(A(y)\) 是回答 \(y\) 的优势（大致是“比平均好多少”）。样本来自正在被优化的同一个策略，就叫 on-policy；样本来自别的策略（比如旧参数、别的模型），就叫 off-policy，这时需要额外的修正（通常是重要性采样，见“后来怎么样了”），否则梯度是有偏的。

问题在于，推理引擎和训练框架用的内核、精度、并行方式、批大小都不同。哪怕参数一模一样，两边对同一个 token 算出的概率也不一样，记为 \(\pi_{\text{samp}}\neq\pi_{\text{train}}\)。于是样本实际来自 \(\pi_{\text{samp}}\)，梯度却按 \(\pi_{\text{train}}\) 计算，名义上的 on-policy 训练就悄悄变成了 off-policy。衡量两者差多远的常用指标是两个分布之间的 KL 散度，

$$\mathrm{KL}(\pi_{\text{samp}}\,\|\,\pi_{\text{train}})=\mathbb{E}_{y\sim\pi_{\text{samp}}}\big[\log\pi_{\text{samp}}(y)-\log\pi_{\text{train}}(y)\big]$$

两个分布完全相同时它等于 0。

作者的论证很简洁：如果连两次相同的推理请求都得不到逐位相同的结果，训练和推理之间就更不可能逐位相同。反过来，有了确定性推理，就可以进一步修改训练端，让采样和训练逐位一致，从而实现真正的 on-policy RL。作者在这里引用了 Yao 等人的博客作为“研究者已经指出训推数值差异会把 on-policy 变成 off-policy”的出处。

实验设置：在 Big-Math 数据集上做 RLVR（用可验证奖励的强化学习），策略从 “Qwen 2.5-VL instruct 8B” 初始化，单个 rollout 最长 4096 个 token。作者比较了三种跑法：

  • 不做 off-policy 修正（不加重要性权重）：奖励在训练中途崩溃。
  • 加 off-policy 修正项（重要性权重）：训练平稳进行，采样端与训练端的 KL 大致在 0.001 附近，偶有尖峰。
  • 采样端与训练端逐位一致：完全 on-policy，KL 恒为 0，训练同样平稳。作者特意说明，图里那条贴着 0 的直线不是程序错误。

7.4 结果的份量

这篇文章的论证主体是对机制的解释（第 2–5 节），实验是用来佐证的，样本量很小。逐条说说每个数字是在什么条件下得到的、对照了什么、没有对照什么。

  • “80 种回答 → 1 种”只来自一个模型、一个提示、温度 0。它证明了现象存在、修法有效，但不衡量“平均有多少比例的提示会分叉”。博客没有写 GPU 型号与数量、并行方式（235B 的模型显然不是单卡）、vLLM 的版本，也没有说 1000 个请求是怎样并发发送的；而并发方式决定了批大小怎么变，也就决定了不确定性有多严重。仓库说明里的另一个数（Qwen3-8B、1000 条、每条 100 个 token：18 种 → 1 种）同样是单一设置。
  • Qwen3-235B 是 MoE 模型，而博客没有讨论 MoE 的内核。专家路由的 top-k 选择、分组矩阵乘、专家结果的合并都是归约或离散选择，同样可能依赖批大小。博客只讲了 RMSNorm、矩阵乘和注意力三类，MoE 部分在这次实验里是怎样做到批不变的，没有说明。
  • 26 → 42 秒是一个很窄的工作负载。单卡 Qwen3-8B，输出只有 90–110 个 token，输入长度没写，GPU 型号没写，对照的是“vLLM 默认配置”（版本不详）。度量是 1000 条请求的总完成时间，相当于离线吞吐，不是首 token 延迟或每 token 延迟。而且确定性配置换成了 FlexAttention 后端，作者自己说大部分减速来自这个集成没优化好，所以这个数字混合了“批不变本身的代价”和“换了一个较慢的注意力后端的代价”，两者没有拆开。
  • 减速在低并发时可能更大。第 5.2 节的数据显示，批不变矩阵乘在批大小 64 以下只有 cuBLAS 的约三分之一，而低并发的在线服务、长输出的解码阶段，恰恰经常处在小批状态。博客的性能测试一次性压上 1000 条请求，批通常不小，所以没有覆盖这种情形。
  • “慢约 20%”是单个矩阵乘在一组未公开的 \(N,K\) 上、跨批大小 8–8184 的平均。它不是端到端数字，也不能直接推到别的形状和 GPU 上。
  • RL 实验每种配置只有一次运行。只有一个模型、一个数据集、最长 4096 个 token，图里只画到约第 320 步；从图的数据文件看，逐位一致那次运行也只有 321 步。没有报告下游准确率，没有报告让训练端逐位一致花了多少额外时间，也没有说训练框架和 RL 算法的细节，以及“加重要性权重”用的是哪种具体形式（截断与否、阈值多少）。
  • RL 实验说明的是“逐位一致和加修正一样好”，不是“比加修正更好”。在画出来的范围内，加重要性权重的那次同样平稳，奖励曲线和逐位一致那次几乎重合。逐位一致的优势在于它在原理上消除了偏差，而不是在这张图上跑出了更高的奖励。
  • 图外的数据。博客正文没有提到，但图所用的数据文件里，“不修正”和“加修正”两次运行都跑到了约 1140 步：“不修正”那次在第 318 步的崩溃之后一度恢复，之后在第 700 步前后彻底崩溃，奖励停在约 −0.1、KL 升到几十；“加修正”那次一直保持在 0.45 上下（本站读自数据文件）。这说明不修正时的崩溃不是偶然的一次抖动。另外，博客文字说加修正时 KL 在 0.001 上下；按数据文件，前 319 步的均值约 0.0004、最大约 0.0008（推算），量级一致但略低，可能是文字取了整数量级。
  • 一处疑似笔误。原文写的初始模型是 “Qwen 2.5-VL instruct 8B”，但 Qwen2.5-VL 公开发布的尺寸是 3B、7B、32B 和 72B，没有 8B，可能是 7B 或别的模型之误。
读的时候容易误解的地方：批不变推理解决的是“推理和推理之间”的一致；“训练和推理之间”的一致还要求训练端也用同样的内核、同样的精度、同样的归约顺序。博客说他们“修改了训练栈”做到了逐位一致，但没有给出具体做法。后来 Yao 等人的分析发现，只在推理端打开确定性模式、不对齐训练端时，训推之间的差距几乎没有缩小（见“后来怎么样了”）。

8 结论：拒绝“差不多就行”

这一节要回答的问题：作者想让读者带走的态度是什么？

结论很短，主要是一个态度。现代软件系统有很多层抽象，碰到不确定性和细微的数值差异时，人们很容易选择糊过去：模型本来就是“概率性”的，多一点不确定又何妨？单元测试过不了，把容差调大一点就行；训练器和采样器的 logprob 对不上，大概也不是真正的 bug。作者明确拒绝这种“失败主义”：只要花一点功夫，就能找到不确定性的根本原因，甚至彻底解决它。他希望这篇文章能让社区真正理解推理系统里的不确定性从何而来，也鼓励大家对自己的系统做到完全理解。

回头看全文的论证链条：浮点加法的结果依赖顺序（第 2 节）；单个内核的顺序是固定的，所以逐次运行确定（第 3 节）；但顺序会随批大小改变，而批大小随服务器负载改变，所以用户看到的结果不确定（第 4 节）；只要让 RMSNorm、矩阵乘、注意力这三类归约的切分方式与批大小无关，就能消除这种不确定性（第 5 节），代价是放弃一些针对小批和特定形状的优化（第 7 节）。

后来怎么样了

这篇博客是 Thinking Machines Lab 的研究博客 Connectionism 的第一篇文章（2025-09-10）。它发布之后，“批不变性”很快从一个概念变成了主流推理引擎里的一个开关，并和强化学习里的“训推不一致”问题合流。下面先讲这条线索的另一半，也就是博客引用的 Yao 等人关于训推不一致和截断重要性采样（TIS）的工作，再讲推理引擎和 RL 框架的跟进，以及截至 2026-10 的其他路线。

配套工作：训推不一致与截断重要性采样（TIS）

Feng Yao、Liyuan Liu（两人为共同一作）、Dinghuai Zhang、Chengyu Dong、Jingbo Shang、Jianfeng Gao 在 2025-08-05 发布了 Notion 博客《Your Efficient RL Framework Secretly Brings You Off-Policy RL Training》（之后多次更新，最近一次是 2025-10-13）。它的论文版本题为《On the Rollout-Training Mismatch in Modern RL Systems》，是 NeurIPS 2025 的研讨会论文（同时出现在 OPT 2025 研讨会和第一届 Efficient Reasoning 研讨会的接收列表中），不是主会论文。本节按博客内容整理；研讨会论文的 PDF 在 OpenReview 上，本站未能下载核对。

先补一点背景：重要性采样与截断。

想估计某个量在分布 \(p\) 下的期望，但手里的样本来自另一个分布 \(q\)，可以给每个样本乘上一个权重 \(p(y)/q(y)\) 来纠正：

$$\mathbb{E}_{y\sim p}\big[f(y)\big]=\mathbb{E}_{y\sim q}\Big[\frac{p(y)}{q(y)}\,f(y)\Big]$$

这叫重要性采样，权重叫重要性比。它在期望上是精确的（无偏），但代价是方差：如果某个样本在 \(q\) 下概率很小、在 \(p\) 下概率较大，它的权重就很大，这一个样本就能主导整个估计。作者在博客里给了一个数：某个 token 的比值达到 16 时，它对梯度噪声的放大是比值的平方，即 256 倍。

截断重要性采样的做法是给权重设一个上限 \(C\)：权重超过 \(C\) 就按 \(C\) 算。这样方差有界，代价是引入了一点偏差。同样比值为 16 的例子，\(C=2\) 时放大 4 倍，\(C=8\) 时放大 64 倍。

问题。作者以 REINFORCE 为例：理想的更新应该用 \(\pi_\theta\) 采样、用 \(\pi_\theta\) 求梯度；实际的混合式框架用 vLLM 采样、用 FSDP 求梯度，两边是同一份参数在两套代码里的实例。他们在 Qwen2.5-32B 上按 DAPO 的配方训练（4 个节点、每节点 8 张 H100），观察到两边对同一个 token 的概率可以差得很大，极端情况下 vLLM 给出的概率是 1、FSDP 给出的是 0。

先试着从系统上修。作者先怀疑是 vLLM 的问题，打了两个补丁：一是让 vLLM 返回真正用于采样的概率（vLLM v1 引擎原本不返回经过调整的采样概率，这个补丁已合并进上游）；二是提供选项把 vLLM 的 LM head（最后把隐藏状态映射到词表的那一层）提升到 FP32，这一点 MiniMax-M1 技术报告也提到过。但两个补丁都打上之后，不一致仍然存在。

再从算法上修：TIS。既然没法在系统层面消除差异，就让更新“知道”这个差异。把梯度改成

$$\mathbb{E}_{y\sim\pi_{\text{samp}}}\Big[\min\Big(\frac{\pi_{\text{train}}(y)}{\pi_{\text{samp}}(y)},\,C\Big)\cdot A(y)\cdot\nabla_\theta\log\pi_{\text{train}}(y)\Big]$$

其中 \(C\) 是超参数。对 PPO，作者的做法是把这个截断后的比值（用旧参数下的 \(\pi_{\text{train}}\) 和 \(\pi_{\text{samp}}\) 计算）乘在原来的 PPO 裁剪目标前面，而 PPO 自己的裁剪比值仍然只在训练端内部计算，两种比值分开处理。

示意图：TIS 在一次 RL 迭代里加在哪里
推理引擎（vLLM / SGLang）按 \(\pi_{\text{samp}}\) 生成回答 \(y\)，同时记下每个 token 的 \(\log\pi_{\text{samp}}\)→训练框架（FSDP / Megatron）用同一份参数重算 \(\log\pi_{\text{train}}\)，算优势 \(A\)
→比值 \(r=\pi_{\text{train}}/\pi_{\text{samp}}\)逐 token 计算，不回传梯度→截断 \(w=\min(r,C)\)大比值被压到 \(C\)，小于 1 的比值原样保留→梯度 \(w\cdot A\cdot\nabla\log\pi_{\text{train}}\)（PPO 时乘在裁剪目标前）
本站示意图，按 Yao 等人博客里的公式整理。批不变 / 逐位一致的做法相当于让 \(r\) 恒等于 1，这时 TIS 什么也不做。

实验与数字（都来自博客）。

  • Qwen2.5-32B + DAPO：受资源限制只跑完前 250 步，但加了 TIS 的那次表现明显更好；两次运行唯一的区别就是这个截断比值项。
  • 受控实验，Qwen2.5-0.5B + GSM8K（一个节点、4 张 A6000）：正常 BF16 训练时，单个 token 的最大概率差约为 0.4；把 rollout 换成 INT8 量化后，最大概率差达到 1.0。INT8 rollout 下普通 PPO 明显退化，加 TIS 后基本恢复到 BF16 正常训练的水平。
  • DeepSeek-R1-Distill-Qwen-1.5B：两边都用 BF16、模型较小，差距本来就小，这时加 TIS 没有带来提升。作者据此说明 TIS 不是总有用，它在差距大时才显著。
  • 与两种变体的比较：不截断的普通重要性采样（vanilla-IS）和直接把比值塞进 PPO 裁剪的做法（PPO-IS）都不稳定；在 INT8 rollout 下两者的准确率接近 0，而 TIS 稳定。后者的问题在于：即使参数还没更新，比值也因为训推差异而不等于 1，PPO 的裁剪会频繁触发，训练信号被大量浪费。
  • INT8 rollout 不加 TIS 时出现熵塌缩（熵降到 0.2 以下并持续下降）和回答异常变长；用采样端样本估计的 KL（k1 估计量）频繁出现负值，说明估计本身被训推差异带偏了。加 TIS 后这些现象消失。作者还提醒，训练日志里的奖励是在采样端分布下统计的，所以加了 TIS 的运行可能日志奖励更低、下游准确率（AIME）反而更高。

不一致从哪里来（2025-09-24 补充的分析）。作者用 DAPO-32B 和 Polaris-7B 两个模型、DAPO-Math-17k 的前 512 个题目，比较同一批回答在不同设置下的“每个回答内的最大概率差”和“平均概率差”，发现三点：

  • 并行方式的差异放大最大差。采样端 TP1、训练端 SP1 时，最大差超过 0.5 的回答只有 1 个；采样端改成 TP2，变成 2 个；训练端再改成 SP8，变成两位数。两边用相同的张量并行（TP2 对 TP2、TP4 对 TP4）时，这样的回答就很少。平均差和 KL 在这些设置之间没有显著区别。
  • 回答越长，最大差越大。上限 20K token 的回答比上限 4K 的最大差更大，平均差却差不多；而且 20K 回答的前 4K 里的最大差，往往已经超过独立生成的 4K 回答，说明两边的内部状态随着生成越走越远。
  • 只换采样后端没用。vLLM、SGLang、打开确定性内核的 SGLang 三者之间没有哪个始终更好；尤其是只在 SGLang 里打开确定性推理、不对齐训练端时，差距并没有明显缩小。作者据此认为差异主要来自并行方式、数值精度等更深的实现差异，而不是采样本身的随机性。

这最后一点正好补上了本文的另一半：批不变只让推理和自己一致，训推一致还需要两边用同样的计算。Thinking Machines 的 RL 实验之所以 KL 恒为 0，是因为他们同时改了训练栈。

采用情况。按 Yao 等人博客的更新记录，verl、slime、OAT、SkyRL、OpenRLHF 都集成了 TIS，REINFORCE++ 在工具调用推理的场景里验证了它。博客还专门对比了 AReaL 的“解耦 PPO”：AReaL 也用重要性比来弥合采样策略与训练策略的差距（它的主要动机是异步训练带来的参数滞后），但在比值超过阈值时直接丢掉样本，而不是截断。博客也讨论了 MoE 模型：路由对数值很敏感，一点差异就可能选中不同的专家，推理引擎对 MoE 又有专门的优化内核，所以 MoE 的训推差异可能更大。

读的时候容易误解的地方：TIS 不消除差异，只限制差异对更新的影响；它是有偏的，并且差异越大越难修（INT8、FP8 rollout 时最明显）。批不变 / 逐位一致则是消除差异，代价是推理变慢、而且要两套引擎共用内核实现。两条路并不互斥：异步训练里参数版本不同带来的 off-policy，逐位一致也消除不了，仍然需要重要性采样一类的修正。

推理引擎的跟进：vLLM 与 SGLang 的确定性模式

  • SGLang（2025-09-22 发布博客）：基于 Thinking Machines 的批不变算子（mean、log-softmax、矩阵乘），自己实现了固定 split-KV 段长的注意力，支持 FlashInfer、FlashAttention-3 和 Triton 三种后端（FA3 后端干脆把段数固定为 1），用 --enable-deterministic-inference 开启，要求 SGLang 0.5.3 以上。它还把分块预填充的切点对齐到 split-KV 段长（例子里是 2048）的整数倍，否则切点会随同批其他序列的长度移动；并用“由种子哈希生成的 Gumbel 噪声”实现了温度大于 0 时的可复现采样。在 Qwen3-8B 上每项各重复 50 次的测试里，普通模式下大多数子测试得到 2 到 18 种不同输出，确定性模式下所有子测试都只有 1 种。H200 上三种 RL 风格负载的端到端减速在 24.4%–55.1% 之间，FlashInfer 与 FA3 两种后端平均减速 34.35%（他们拿来对比的是 Thinking Machines 的 61.5%）；当时只支持稠密模型，TP1 和 TP2 下确定。SGLang 还和 slime 合作，在 GRPO 训练中实现了两次独立运行完全相同的训练曲线（训练端用 Megatron 的确定性模式、FlashAttention-2 的确定性反向、固定 NCCL 算法等）。
  • vLLM：博客发布当天的概念验证 PR 没有合并；正式支持从 2025-09-26 合并的 PR #25603 开始，之后由一个跟踪 issue（#27433）陆续加入 FlashInfer、DeepSeek-V3、Blackwell 上的 DeepGEMM、torch.compile 与 CUDA Graph 的支持。用法是设置环境变量 VLLM_BATCH_INVARIANT=1，文档标注为 beta。2025-10-31 版文档要求计算能力 9.0 以上（H100/H200/B100/B200），并说明张量并行时会关掉自定义 all-reduce；截至 2026-10-12 更新的文档，支持范围已扩大到计算能力 8.0 以上的 NVIDIA GPU、AMD Instinct 和 Intel XPU，张量并行下改为保留自定义 all-reduce 但固定归约顺序，验证过的模型清单也从十来个扩展到包括 DeepSeek、Qwen3、GPT-OSS、Llama 3 等几十个。

从批不变到逐位一致的 RL

  • vLLM + TorchTitan（2025-11-10）：两个团队演示了一次开源的逐位一致 on-policy RL：训练端 TorchTitan 直接复用 vLLM 批不变模式的前向内核（包括融合的 SiLU MLP、带残差的 RMSNorm），自己补写反向；他们逐个核对了前向里每一次内核调用，确保两边逐位相同。在 Qwen3-1.7B + GSM8K 上，逐位一致那次 KL 恒为 0，并且比不一致的那次用更少的步数达到更高的奖励；代价是整个 RL 运行比不逐位一致时慢 2.4 倍，而且当时只是单机同步执行。
  • vLLM 社区的 DeepSeek-V4-Flash 配方（2026-10-14，NVIDIA 与 Inferact 的作者）：换了一个思路，不让推理端退回通用的批不变内核，而是保留部署时的高性能内核（FP8 矩阵乘、FP8 KV 缓存、稀疏注意力的 Top-K），把它们逐个改成与批组成、预填充 / 解码阶段、并行布局都无关，再让训练前向直接调用这些推理内核、只在训练端补反向。在 GB200 上训练 100 步，训推之间每个 token 的概率差每一步都是 0，rollout 吞吐量是高性能基线的 91.3%；而不做对齐的基线，训推 KL 从 2e-3 一路涨到 29.9，奖励回落。他们也坦言基线只跑了一种配置、没有加 TIS 一类的修正，基线未必在调优后也这么容易崩。

其他路线与相关发现

  • 张量并行下的不变性。本文把多卡归约排除在外，而 RL 里训练端常用 FSDP（相当于 TP=1），推理端常用多卡 TP，这本身就是一种差异。Zhang 等人的 TBIK（arXiv 2511.17826，ICML 2026）把卡内和卡间的归约统一成同一棵层次化二叉树，在 Triton 里实现了与 TP 大小无关的矩阵乘和归约，接进 vLLM 和 FSDP 后做到了不同并行方式之间逐位相同。
  • 换精度。Qi 等人（arXiv 2510.26788）认为训推不一致的根源在 BF16 的舍入误差太大，把训练和推理统一换成 FP16（尾数多 3 位）就能大幅消除不一致，只需改几行代码。这条路线不追求逐位相同，而是让差异小到不足以伤害训练。
  • 按需确定。LLM-42（arXiv 2601.17768）认为批不变内核把“确定性”和内核设计绑死了，而且不管多少流量真正需要确定性，都要付固定的减速代价。它借鉴投机解码的思路：平时走不确定的快路径，再用一个固定形状的归约计划重放验证候选 token，确认一致的才提交，不一致的回滚。
  • 更早的相关发现。MiniMax-M1 技术报告（arXiv 2506.13585）在 RL 中发现训练与推理的 token 概率相关性只有 0.9 左右，逐层排查后定位到 LM head 的大幅值激活，把 LM head 提到 FP32 后相关性升到 0.99 左右。博客开头引用的 Yuan 等人（arXiv 2506.09501）则测到，BF16 贪心解码下 DeepSeek-R1-Distill-Qwen-7B 的准确率会因 GPU 数量、型号和评测批大小不同而相差最多 9%，回答长度相差最多 9000 个 token。
  • 其他修正法。“When Speed Kills Stability”（Liu、Li 等，2025-09）提出了在序列层面计算比值、超过阈值就整条丢弃的掩码重要性采样（MIS），与 TIS 的逐 token 截断形成对照。

总的来看，截至 2026-10，这个问题形成了三类做法：修正（TIS、MIS 等，便宜、通用，但留有偏差）、消除（批不变 / 逐位一致，原理上最干净，但要付推理速度和工程对齐的代价）、缩小（FP16、FP32 LM head、对齐并行方式）。本文的贡献是把“消除”这条路的根本原因讲清楚，并证明它在工程上可行。想看本站对这个主题的结构拆解和配套简答题，见批不变性拆解页。

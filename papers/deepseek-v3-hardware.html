0 导读：这篇论文是什么，值得读什么

2024 年 12 月发布的 DeepSeek-V3 是一个 671B 参数的混合专家（MoE）模型，只用 2,048 张 NVIDIA H800 GPU 就训练完成，成本远低于同档次的模型。它的技术报告（本站有逐节精读）讲的是“模型怎么设计、怎么训练”。2025 年 5 月，DeepSeek 团队在计算机体系结构的顶级会议 ISCA 2025 的工业界论文专场（Industry Track）发表了这篇论文，换了一个角度讲同一件事：训练和部署 V3 时，硬件在哪些地方卡住了我们，我们在模型结构和系统软件上做了哪些“迁就”，以及我们希望下一代 AI 硬件改掉哪些短板。它的读者首先是设计芯片、网卡和交换机的人。

所以这不是一篇提出新方法的论文，而是一篇“经验总结 + 立场陈述”。它的主线可以概括为四对“约束—应对”，外加一份给硬件的愿望清单（见下图）：

  • 显存不够大、也不够快：模型对显存的需求涨得比显存本身快得多，所以 V3 用 MLA 把推理时的 KV 缓存压得很小，用 FP8 把权重压到一半。
  • 算力要省：V3 用 MoE 让每个 token 只激活 37B 参数，并用 FP8 训练把矩阵乘的速度翻倍；但 H800 的 FP8 单元有精度短板，只能靠软件绕过去。
  • 节点内带宽被砍：H800 是 H100 的“合规版”，节点内 GPU 互连（NVLink）的带宽从 900 GB/s 被削到 400 GB/s。V3 因此在训练时完全不用张量并行，并设计了“节点受限路由”，让每个 token 最多只去 4 个节点找专家。
  • 集群网络又贵、又怕延迟：V3 的训练集群用了一种“多平面两层胖树”网络，比传统的三层网络便宜得多；推理时 MoE 的通信对微秒级的延迟都很敏感。

1 引言：为什么一个模型团队要给芯片设计者写论文

这一节要回答的问题：论文为什么要从“硬件”而不是“模型”的角度回顾 DeepSeek-V3？它给自己定了哪三个目标？读这篇论文之前，需要先知道 H800 是一块什么样的 GPU，以及“软硬件协同设计”指的是什么。
先补一点背景：H800，以及“协同设计”。

H800 是 NVIDIA 基于 Hopper 架构推出的数据中心 GPU，和 H100 用同一套计算单元。论文 §4.1 说，为了符合出口管制的规定，它削减了两样东西：双精度（FP64）算力，以及 GPU 之间直连的 NVLink 带宽。FP64 对大模型几乎没用，但 NVLink 带宽对多卡训练至关重要，这一处削减是贯穿全文的一条线索。

软硬件协同设计（co-design）的意思是：不把硬件当成给定的、一成不变的平台，而是让模型结构、并行策略、通信软件去适应硬件的长处和短处；反过来，再把软件的需求反馈给硬件设计者。这篇论文两个方向都写：第 2–5 节主要是“模型怎样迁就硬件”，每节末尾和第 6 节是“硬件应该怎样改”。

背景。论文开头的逻辑很直接。第一，按照规模定律（scaling laws），模型越大、数据越多、算力越多，效果就越好，所以大家都在往大里做。第二，2024–2025 年出现的推理模型（OpenAI o1/o3、DeepSeek-R1 等）靠“想得更久”来提高能力，这让推理速度变得和训练成本一样重要：思考链越长，用户等得越久；强化学习训练时也要大量采样，采样速度直接卡住训练速度。第三，头部公司为此建了几万到几十万张 GPU/TPU 的集群，小团队负担不起。DeepSeek 想证明的是：在 2,048 张 H800 这样“不算大”的集群上，通过软硬件协同，也能做出最前沿的模型。这条路线之前在他们的 Fire-Flyer AI-HPC 集群论文（SC24）里已经走过一次。

目标。论文明确说，它不重复 V3 技术报告里的模型细节，而是从硬件和模型两个视角看它们之间的相互作用，具体是三件事：

  1. 硬件驱动的模型设计：FP8 计算、节点内外的网络特性，怎样影响了 V3 的结构选择；
  2. 硬件和模型的相互依赖：硬件能力怎样塑造了模型创新，模型的新需求又怎样推动下一代硬件；
  3. 给未来硬件的方向：从 V3 的经验里提炼出可操作的建议。

2.1 内存效率：KV 缓存为什么是推理的命门

这一节要回答的问题：论文说大模型面临“内存墙”：模型要的显存涨得比显存本身快得多。V3 在“源头”上省显存的两个手段是 FP8 和 MLA。MLA 到底把 KV 缓存压到了多小？和当时主流的 GQA 模型比差多少？除了 MLA，还有哪些压缩 KV 缓存的路子，论文怎么看它们？
先补一点背景：为什么解码阶段“卡在读显存上”。

模型生成文字时，每一步只为每个请求算一个新 token。这一步里，注意力要拿新 token 的 query 和之前所有 token 的 key、value 计算，而之前的 key、value 早就算过并存在显存里，这份数据叫 KV 缓存（详细的来龙去脉见本站 vLLM 精读 §2.2）。

关键在于“算多少”和“读多少”的比例。处理一整段输入时，一次矩阵乘是“矩阵 × 矩阵”（GEMM），每从显存读一个数，可以拿它做几百上千次乘加，计算单元很忙。生成时每步只有一个新 token，矩阵乘退化成“矩阵 × 向量”（GEMV），每读一个 BF16 数（2 字节）只做一次乘加（2 次浮点运算），也就是大约每字节 1 次运算。H800 的 BF16 算力约 989 TFLOPS、显存带宽约 3.35 TB/s（按与 H100 SXM 相同的公开规格），要把算力用满，每读 1 字节需要做约 295 次运算（推算：989 ÷ 3.35）。GEMV 只有它的三百分之一，所以解码时计算单元大部分时间在等数据，速度由“每步要读多少字节”决定。KV 缓存越大，每步读得越久；显存里能同时放下的请求越少，批也开不大。

内存墙。论文引用了 Gholami 等人（2024）的统计：大模型对内存的需求每年增长超过 1000%，而 HBM 这类高速显存的容量每年增长不到 50%。换句话说，前者每年变成原来的 11 倍以上，后者每年还不到原来的 1.5 倍，缺口一年比一年大。所以光靠多堆几张卡（多节点并行）不是长久之计，必须在源头上省。

手段一：低精度。权重从 BF16 换成 FP8，每个数从 2 字节变成 1 字节，显存占用直接减半（§2.1.1）。具体怎么在训练中用好 FP8，放到第 3 节讲。

手段二：MLA 压缩 KV 缓存。MLA（多头潜在注意力）不给每个注意力头单独存 key 和 value，而是把所有头的 key、value 压缩成一个低维的“潜向量”存下来，需要时再展开；压缩和展开用的投影矩阵和模型一起训练。V3 每个 token 每层只存一个 512 维的潜向量和一个 64 维的、带位置信息的 key，共 576 个数。它的细节（包括为什么 RoPE 要单独走一路、推理时怎样用“矩阵吸收”避免展开）在本站 V3 精读 §2.1.1 里有完整推导。

论文同时列出了另外三类压缩 KV 缓存的思路，并说它们“同样有价值”：

  • 共享 KV（GQA、MQA）：多个 query 头共用一组 key、value。MQA 是所有头共用一组，GQA 是每几个头共用一组。当时的 Qwen-2.5、LLaMA-3.1 都用 GQA。
  • 窗口 KV：只保留最近一段窗口内的 key、value，更早的丢掉（如 Longformer）。省得多，但模型对远处内容的推理能力会受损。
  • 量化压缩：把 KV 缓存存成低比特数，比如 2 比特（本站有 KIVI 精读）。压缩率高，对模型效果影响小。

读的时候容易误解的地方：
  • 表 1 只比较“每个 token 存多少字节”。三个模型的大小、能力、注意力结构都不同，它不是一个控制变量的实验，不能直接读成“MLA 比 GQA 好 4.66 倍”。
  • MLA 省下的是读写量，不是计算量。推理时用矩阵吸收后，每个缓存的 token 要和 576 维的向量做点积，比 GQA 每头 128 维的点积还多算一些（见 V3 精读的“代价是什么”）。这笔交易在解码时划算，正是因为解码卡在读显存而不是算力上。
  • 表里全按 BF16 算。如果 KV 缓存用 FP8 存（很多推理引擎会这么做），三个数字都减半，倍数不变。

2.2 MoE 的性价比：训练省算力，单机也跑得动

这一节要回答的问题：MoE（混合专家）模型参数很多，但每个 token 只用其中一小部分。这对训练成本意味着什么？论文用表 2 比较了 MoE 和稠密模型每个 token 的训练计算量，这些数是怎么来的、能不能复核？论文还说 MoE 特别适合个人电脑和本地部署，这个说法的依据是什么、前提是什么？
先补一点背景：训练一个 token 要多少次浮点运算。

§2.2.2 个人电脑和本地部署。论文的第二个论点是：MoE 在“只服务一个用户”的场景里特别有优势。原因要从上面那个背景框说起：单个请求解码时，每一步都要把这一步用到的参数从内存读一遍，速度大约等于“内存带宽 ÷ 每步要读的字节数”。MoE 每步只读被激活的那部分参数，所以比同等能力的稠密模型快得多。

用一个例子感受一下（推算，带宽是假设值）：假设一台机器的内存带宽是 500 GB/s，参数用 8 位存储。DeepSeek-V2 每个 token 激活 21B 参数，每步读约 21 GB，上限约 24 token/s；一个 70B 的稠密模型每步读约 70 GB，上限约 7 token/s。论文给出的数字是：装有 AI SoC 芯片的个人电脑跑 V2 能接近 20 token/s，甚至两倍于此；而能力相近的 70B 稠密模型在类似硬件上通常只有个位数。论文还提到开源推理引擎 KTransformers 能让完整的 V3 在一台约 1 万美元、带一张消费级显卡的服务器上跑到接近 20 token/s。

读的时候要注意：
  • 这一小节的速度数字都是引用或概述，论文没有交代硬件型号、量化位宽和上下文长度，也不是论文作者测的。
  • MoE 省的是每步要读的量，不是要放下的量。V2 虽然每步只读 21B，但 236B 参数都得放在内存里，V3 则是 671B。所以本地部署 MoE 需要的是“内存大、带宽够”的机器（比如统一内存的 SoC，或者 CPU 内存很大的服务器），而不是显存小但很快的游戏显卡。按 KTransformers 的项目说明，它做的正是 CPU–GPU 异构推理：大部分专家参数放在 CPU 内存里、由 CPU 计算（“CPU expert offload”），GPU 负责其余部分。
  • 这种优势在“一次只服务一个请求”时最明显。批很大时，不同请求选中的专家互相重叠，几乎所有专家都会被读到，MoE 每步要读的量就向总参数量靠拢。

2.3–2.4 推理速度：网络带宽决定 MoE 解码的上限

这一节要回答的问题：推理速度有两个含义：整个系统每秒能产出多少 token（吞吐），以及单个用户每秒能看到多少 token（延迟）。V3 怎样在吞吐上把专家并行的通信藏起来？论文为什么说 MoE 解码速度的上限由网络带宽决定，并给出 14.76 ms 和 0.82 ms 两个理论值？多 token 预测（MTP）在线上实际带来多少加速？最后，V3 这么多加速技巧，是怎么在不训练很多个全尺寸模型的前提下验证“不掉点”的？
先补一点背景：吞吐、TPOT，以及专家并行的两次 all-to-all。

吞吐和延迟常常互相矛盾：把很多请求凑成一个大批一起算，GPU 利用率高、吞吐大，但每个请求每一步都要等整批算完，单个用户感觉变慢。衡量“单个用户感觉多快”的常用指标是 TPOT（Time Per Output Token，每个输出 token 的平均间隔），TPOT = 10 ms 相当于每秒 100 个 token。推理模型动辄输出上万个 token，TPOT 直接决定用户要等多久。

专家并行（EP）把同一层的不同专家放到不同 GPU 上。每一层 MoE 都要做两次通信：先把每个 token 发到它选中的专家所在的 GPU（dispatch），专家算完再把结果送回 token 原来所在的 GPU 并加权求和（combine）。因为每张卡都要给其他很多张卡发数据，这种通信叫 all-to-all（§4.3 有可以单步演示的小工具）。V3 训练时的做法见 V3 精读 §3.2.2。

2.3.1 双微批重叠：让通信藏在另一批的计算后面

论文说，V3 从一开始就是按“双微批重叠”来设计的。做法是把一批请求分成两个微批 A 和 B，并把每一层拆成注意力（MLA）和 MoE 两段计算。当 A 在算注意力时，B 在做 dispatch 通信；当 B 在算时，A 在做 combine 通信，如此交替。只要通信和计算的时间差不多，GPU 的计算单元就一直有活干，all-to-all 的耗时被完全藏起来。DeepSeek 在 2025 年初开源的性能剖析数据（profile-data 仓库）展示的就是这种时间线。

2.3.2 解码速度的理论上限：一笔只算通信的账

这一小节是全文最有代表性的“纸上推算”，值得一步步跟下来。它只关心解码阶段单个用户的速度（TPOT）。

第一步：为什么瓶颈是网络。要让 MoE 解码最快，理想情况是每张卡只放一个专家（必要时几张卡合放一个），这样每张卡每步只需读一个专家的参数，读显存的时间最短。但这样一来，每个 token 都要通过网络发到 9 张不同的卡上（8 个路由专家加 1 个共享专家），再收回结果。于是 all-to-all 通信成了每一层的必经之路，网络带宽决定了速度的上限。

第二步：设定每张卡一次处理多少 token。论文假设每张卡一次处理约 32 个 token。这个数是一个折中：token 太少，读一遍专家参数只服务很少的 token，计算单元的效率太低（每字节读入的运算太少，见 §2.1 的背景框）；token 太多，要发的数据太多，通信时间变长。另外，让每张卡处理同样多的 token，通信时间就容易算。

第三步：算一次 dispatch + combine 要多久。以每张卡配一块 400 Gb/s（50 GB/s）InfiniBand 网卡（ConnectX-7）为例：

$$T_{\text{comm}}=\frac{(\underbrace{1}_{\text{dispatch, FP8}}+\underbrace{2}_{\text{combine, BF16}})\ \text{字节}\times\underbrace{32}_{\text{token}}\times\underbrace{9}_{\text{专家}}\times\underbrace{7\text{K}}_{\text{隐藏维度}}}{50\ \text{GB/s}}=120.96\ \mu\text{s}$$

每个 token 的隐藏向量有 7168 维（论文取整写作 7K，按 7000 算）。dispatch 时每维用 FP8 传 1 字节，combine 时用 BF16 传 2 字节，合计每维 3 字节。32 个 token 各发给 9 个专家，总共约 6.05 MB（推算），按 50 GB/s 传完要 120.96 微秒。这里没有算网络延迟（v2 特意补了这句说明）。

第四步：一层、一个 token 要多久。在双微批重叠下，两个微批各自要做一次 dispatch 和一次 combine，它们共用同一块网卡，通信与通信之间没法重叠。论文假设计算时间可以忽略（完全藏在通信后面），于是每层耗时就是两个微批的通信时间之和：

$$T_{\text{层}}=2\times120.96\ \mu\text{s}=241.92\ \mu\text{s},\qquad \text{TPOT}=61\times241.92\ \mu\text{s}=14.76\ \text{ms}$$

V3 有 61 层，所以每生成一个 token 至少要 14.76 毫秒，也就是每秒最多约 67 个 token。

第五步：换成更大的 scale-up 网络。如果用 GB200 NVL72（72 张 GPU 用 NVLink 全互连，每张卡单向 900 GB/s），同样的通信只要 \(6.72\ \mu\text{s}\)，带宽大了 18 倍，TPOT 的理论下限就降到 0.82 ms，约每秒 1200 个 token。

2.3.3 多 token 预测：线上接受率 80%–90%，速度 1.8 倍

先补一点背景：投机解码与“自起草”。

投机解码先用一个便宜的办法猜出后面几个 token，再让大模型一次前向同时验证这些猜测：猜对的直接收下，猜错的从第一个错处丢掉。猜中率高时，一次前向平均能产出不止一个 token（原理和“输出分布不变”的证明见本站 投机解码精读）。“自起草”指不另外训练一个小模型，而是在大模型身上加几个轻量的预测头来起草，比如 Medusa 和 EAGLE，论文把 MTP 归为这一类。

V3 训练时带了一个 MTP 模块：一层很轻的 Transformer，用主模型的表示去预测“再下一个” token（结构见 V3 精读 §2.2）。推理时，主模型每生成一个 token，MTP 模块顺手猜出再下一个，下一步由主模型验证。论文给出的是线上服务的实际数据：第二个 token 的接受率在 80% 到 90% 之间，生成速度（TPS）是不用 MTP 时的 1.8 倍。

这两个数对得上：每步只多猜 1 个 token、接受率为 \(p\) 时，每次主模型前向平均产出 \(1+p\) 个 token，\(p=0.8\sim0.9\) 时是 1.8 到 1.9 个（推算）。实际 1.8 倍略低于上限，差额是 MTP 模块本身和验证的开销。V3 技术报告里给的接受率是 85%–90%，这里的下限写成了 80%，可能反映了线上不同类型请求的差别，论文没有解释。

论文还指出两点。第一，MTP “略微损害吞吐、但显著改善端到端延迟”：猜错的 token 白算了，MTP 模块也要算，所以同样的 GPU 每秒处理的有效 token 略少；但单个用户每秒看到的 token 多了 80%。第二，MTP 让每次前向要处理的 token 变多（每个请求每步验证 2 个 token），这相当于把推理批开大了一倍，正好提高了专家并行中每个专家的计算强度和硬件利用率，和 2.3.2 里“每张卡 32 个 token 太少”的问题对上了。

2.3.4 推理模型与强化学习：为什么速度格外要紧

o1/o3、DeepSeek-R1 这类推理模型靠测试时扩展（test-time scaling）提高能力：给的思考时间越长，答得越好。这让输出速度变得格外重要，原因有二。一是用户体验：思考链越长，等得越久。二是训练：PPO、GRPO 这类强化学习方法每一轮都要先让模型大量生成样本，生成速度直接卡住训练速度。论文承认怎样加速推理和强化学习仍是开放问题，并呼吁社区一起探索。

2.4 技术验证：先小后大，最后只训一次

MLA、FP8 混合精度、和网络协同设计的 MoE 路由，每一项都可能影响模型效果。全尺寸模型的消融实验太贵，所以论文描述了一个分层的验证流程：每项技术先在小模型上充分验证，再在大模型上做少量调参，最后把所有技术合到一次完整的训练里。举的例子是 FP8：先在 16B 和 230B 两个规模的模型上做细粒度 FP8 训练的消融，相对 BF16 的误差保持在 0.25% 以内，论文把这归功于高精度累加和细粒度量化。

读的时候要注意：“0.25%”不是这篇论文的新实验，而是 V3 技术报告附录 B.1 的结果（那里说的是两种精度的训练损失相对差，本站在 V3 精读 §3.3.3 讲过）；这里的措辞是 “relative accuracy loss”，读者不要误以为是下游任务的准确率。另外，这篇论文把那两个模型称为 “DeepSeek-V2 models”，V3 报告里只说是约 16B 和约 230B 的 MoE 模型。最终 671B 的正式训练本身没有 BF16 对照。

3 低精度：FP8 训练卡在哪，通信能不能再压

这一节要回答的问题：V3 是第一个用 FP8 训练的开源大模型。为了把 FP8 用好，它在软件上绕过了 H800 的哪些硬件短板，这些绕路付出了什么代价？通信方面，dispatch 已经用 FP8 了，combine 能不能也压一压？论文试过一种新的“对数浮点格式” LogFMT，效果不错，最后却没有用上，为什么？

3.1 FP8 混合精度训练：硬件的两处短板

推理时把模型量化到 8 位、4 位（GPTQ、AWQ 等）早已普遍，但训练时用低精度难得多。NVIDIA 的 Transformer Engine 很早就支持 FP8 训练，可论文说在 V3 之前，没有开源大模型真正用 FP8 训练过。V3 的 FP8 框架用了细粒度量化：激活每 1×128 个数共用一个缩放因子，权重每 128×128 个数共用一个缩放因子，矩阵乘的实现开源在 DeepGEMM 里。为什么要细粒度、离群值为什么怕“整个张量一个缩放因子”，本站在 V3 精读 §3.3 用手算的例子讲过；FP8 格式本身见 FP8 格式精读。这一节只看硬件层面的两处短板。

先补一点背景：浮点加法为什么会“吃掉”小数。

两个浮点数相加，要先把它们的指数对齐：把指数小的那个数的尾数往右移，直到两者指数相同，再把尾数相加。用十进制举例：\(1.234\times10^{3}+5.678\times10^{0}\)，先把后者写成 \(0.005678\times10^{3}\)。如果加法器只保留 4 位有效数字，结果是 \(1.239\times10^{3}\)，后者末尾的 0.000678 就被截掉了。被加的数比当前和小得越多，丢掉的部分越多；小到一定程度，它就整个消失。矩阵乘是成千上万次乘积的累加，所以累加器保留多少位，直接决定结果的精度。

短板一：FP8 的累加精度不够。论文给出了 Hopper GPU 的 Tensor Core 做 FP8 矩阵乘时的具体行为：每次把 32 个乘积放在一起，按其中最大的指数对齐（其余的右移），只保留每个乘积最高的 13 位小数位，超出的部分直接截掉；相加的结果累加到一种 “FP22” 寄存器里（1 位符号、8 位指数、13 位尾数）。普通的 FP32 有 23 位尾数，这里少了 10 位。

示意图：32 个乘积对齐到最大指数后，只有窗口里的位参与相加
本站示意图，按 §3.1.1 的文字画出（原文没有这张图）。为了看得清，只画了 4 个乘积。“13 位小数”加上领头的 1 位，就是 V3 技术报告里说的“约 14 位”，两种说法是一致的。

这个行为的后果是：在每组 32 个乘积里，比最大那个小 \(2^{13}\) 倍以上的乘积，信息基本全丢；截断又总是往 0 的方向舍，误差不会互相抵消，而是随着内维（求和的项数）越加越多。V3 技术报告实测过，内维 4096 时最大相对误差接近 2%。V3 的软件绕法是：Tensor Core 每累加 128 个元素，就把部分和搬到 CUDA Core 上用真正的 FP32 累加（见 V3 精读 §3.3.2）。v2 补充说，“FP22” 这个叫法沿用了 SageAttention2 论文的命名，而且 Hopper 的这个精度问题在 2024 年初已经被业界普遍注意到。

短板二：细粒度量化的反量化开销。细粒度量化意味着每 128 个元素就有一组新的缩放因子。现在的 Tensor Core 不认识这些缩放因子，所以每段部分和都要从 Tensor Core 搬到 CUDA Core，乘上缩放因子再累加。这种频繁的数据搬运降低了计算效率，也让硬件利用率更难优化。

建议。对应两处短板，论文提了两条：

  • 提高累加精度：把累加寄存器的精度提到合适的水平（比如 FP32），或者让累加精度可配置，由用户在速度和精度之间取舍，因为训练和推理、不同模型的需求不同。
  • 原生支持细粒度量化：让 Tensor Core 直接接收缩放因子，在内部完成“带分组缩放的矩阵乘”，部分和的累加和反量化都在 Tensor Core 里做完，直到给出最终结果，免去来回搬运。论文举的现成例子是 NVIDIA Blackwell 对微缩放（microscaling，MX）格式的支持。
先补一点背景：MX 格式和 V3 的分组缩放有什么不同。

MX 格式（OCP 标准，Rouhani 等人 2023）把每 32 个相邻元素分成一块，块内共用一个 8 位的缩放因子，这个因子只有指数没有尾数（记作 E8M0），也就是只能是 2 的整数次幂。V3 的做法是每 128 个元素一块、缩放因子用 FP32。两者思路相同（小块各自缩放），细节不同：MX 的块更小、因子更“粗”。缩放因子取 2 的整数次幂的好处是，乘除它只改变指数，不引入舍入误差，硬件实现也简单。后来 DeepSeek-V3.1 的权重和激活都改用了 UE8M0 格式的缩放因子，模型说明里写明是为了和微缩放格式兼容（见本页末尾“后来怎么样了”）。

读的时候要注意：“13 位小数、FP22”是对 Hopper（H100/H800）Tensor Core 行为的描述，论文没有给出测量方法，而是引用了 SageAttention2 的说法；换一代硬件，结论可能完全不同。这两条建议本身没有实验数据，它们的依据是 V3 在软件上绕路的代价。

3.2 LogFMT：一种对数格式的通信压缩，好用却没上线

现状。专家并行时，V3 dispatch 的 token 用细粒度 FP8 量化后再发，通信量比 BF16 少一半，通信时间明显下降。combine 那一步出于精度要求仍用 BF16，因为它要把多个专家的输出加权求和，误差会直接进入残差流。团队在测试 combine 用 FP8、用自定义的 E5M6 格式（1 位符号、5 位指数、6 位尾数，共 12 位），以及 FP8 和 BF16 混用。

LogFMT 是什么。除了这些常规浮点格式，团队还试了一种新的数据类型：对数浮点格式 LogFMT-nBit，\(n\) 是总位数，最高 1 位是符号位。它的思路是把激活值从“线性空间”搬到“对数空间”里均匀地取值。对一个 1×128 的小块 \([x_1,\dots,x_m]\)：

  1. 对所有元素取绝对值再取对数，找出最小值 \(\min=\log|x_i|\) 和最大值 \(\max=\log|x_j|\)；
  2. 编码 \(S.00\cdots01\) 代表最小值，\(S.11\cdots11\) 代表最大值，中间等间隔划分；\(S.00\cdots00\) 专门代表 0；
  3. 其余每个元素取最接近的格点 \(K\)，解码时还原为 \(\exp(\min+\text{Step}\times(K-1))\) 再带上符号。
$$\text{Step}=\frac{\max-\min}{2^{\,n-1}-2},\qquad \hat{x}=(-1)^{S}\exp\!\big(\min+\text{Step}\times(K-1)\big),\quad K=1,2,\dots,2^{\,n-1}-1$$

以 \(n=8\) 为例：除去符号位还剩 7 位，共 128 个编码；0 号代表零，1 到 127 号这 127 个格点等间隔地铺满 \([\min,\max]\)，相邻格点相差一个 Step，一共 126 个 Step。

走一个例子（推算）。假设某个 1×128 小块里，绝对值最小的元素是 0.001，最大的是 2。对数范围是 \(\ln 2-\ln 0.001\approx7.60\)，除以 126 得 Step ≈ 0.0603。也就是说，相邻两个可表示的值之比是 \(e^{0.0603}\approx1.062\)，处处都是约 6.2% 的间隔。作为对比，FP8 E4M3 在每个二进制数量级（比如 1 到 2 之间）只有 8 个取值，相邻间隔从 12.5% 到 6.7% 不等。所以在这个例子里，同样 8 位，LogFMT 的相对精度处处比 E4M3 好。

本站示意图，格点位置按 §3.2 的定义和上面的例子算出（推算），原文没有这张图。LogFMT 的格点位置取决于每个小块自己的最小值和最大值，换一个小块，格点就整体平移、疏密也变。

这个优势是有条件的。小块的动态范围越大，Step 越大：论文规定最小值不得低于“最大值减 \(\ln 2^{32}\)”，即最大范围约 \(2^{32}\) 倍，和 5 位指数的浮点数（E5）相当。在这个极限下，Step ≈ \(22.2/126\approx0.176\)，相邻值相差约 19%（推算），比 E4M3 粗，但 E4M3 根本表示不了这么大的范围（太小的数会变成 0）。神经网络激活在一个 1×128 小块内部的范围通常小得多，所以 LogFMT 大多数时候能给出比 FP8 更细的精度。这就是论文说它“按小块动态调整表示范围，要么覆盖更大的范围，要么提供更高的精度”的意思。

一个细节：在线性空间里舍入。论文特别强调，选最近的格点时要按原始数值（线性空间）比远近，而不是按对数值比，这样量化才是无偏的。原因是：设相邻两个格点是 \(a<b\)，按对数比较时分界点是几何平均 \(\sqrt{ab}\)，按线性比较时分界点是算术平均 \((a+b)/2\)，前者总是更小。如果按对数舍入，落在 \(\sqrt{ab}\) 和 \((a+b)/2\) 之间的数都会被往上舍到 \(b\)，整体上系统性地偏大（本站解释）。

效果。团队在约 7B 参数的稠密语言模型上验证：把残差分支的输出量化，用来模拟 MoE 里 combine 的那一步。\(n=8\)（与 FP8 同样的位数）时，LogFMT-8 的训练精度优于 E4M3 和 E5M2；\(n=10\) 时，效果与 combine 用 BF16 相近。

为什么最终没用上（§3.2.1）。LogFMT 的本意是用在传输中的激活上，或者用在激活函数附近，因为同样位数下它比 FP8 精度高。但麻烦在后面：Hopper 的 Tensor Core 不认识这种格式，收到之后必须先转回 BF16 或 FP8 才能计算。GPU 做 log 和 exp 运算的吞吐不够，编码、解码时寄存器压力也太大，如果把编解码融合进 all-to-all 通信内核里，开销会达到 50%–100%。所以尽管实验证明这种格式有效，最终没有采用。

建议（§3.2.2）。未来硬件可以提供原生的压缩、解压单元，专门处理 FP8 或自定义精度格式。这样能降低带宽需求、简化通信流水线，对 MoE 训练这种吃带宽的任务尤其有用。第 6.5 节还会把这个想法推进一步：把 LogFMT 直接做进网络硬件里。

读的时候要注意：LogFMT 的结论都是定性的：论文没有给出损失曲线或具体数值，“优于 E4M3/E5M2”是在 7B 稠密模型上模拟 combine 得出的，不是在 MoE 的真实 combine 上测的。“50%–100% 的开销”也没有说明是相对什么基准、在什么消息大小下测的。这一小节的价值主要在于提出了一个格式设计，并说明了为什么它在现有硬件上不划算。

4 互连驱动的设计：NVLink 被砍之后，模型怎么迁就网络

这一节要回答的问题：H800 的节点内带宽被削掉一半多，而节点之间每张卡配了一块 400G 网卡。在这样的“节点内外带宽比”下，V3 的并行策略和专家路由是怎样被硬件塑造的？为了把两种网络都用满，GPU 的计算单元被拉去做了哪些通信杂活，论文希望硬件怎样把这些活接过去？节点内的 PCIe 又会在什么情况下堵车？
先补一点背景：scale-up 与 scale-out，以及带宽的单位。
  • scale-up（纵向扩展）：一台机器（节点）内部，或者 NVL72 这样的“超节点”内部，GPU 之间用 NVLink 和 NVSwitch 直接互连。带宽高、延迟低，GPU 可以像读写自己的显存一样直接读写别的 GPU 的显存。
  • scale-out（横向扩展）：节点之间通过网卡（NIC）和交换机组成的网络通信，常用 InfiniBand（IB）或者以太网上的 RDMA（RoCE）。RDMA 让一台机器的网卡直接读写另一台机器的内存，不需要对方 CPU 参与；程序把一个个“工作请求”（WQE）放进网卡的“队列对”（QP）里，由网卡执行。
  • 单位：网卡速率习惯用比特，400 Gb/s ÷ 8 = 50 GB/s。NVLink 的数字常常是双向合计：H100 的 900 GB/s 是每个方向 450 GB/s；H800 的 400 GB/s 对应每个方向 200 GB/s，论文 §4.3 用的正是 200 GB/s 这个单向数（这一换算是本站的解释，论文没有明说）。

4.1 现在的硬件：一台 H800 节点长什么样

H800 SXM 和 H100 同属 Hopper 架构，但为了合规，FP64 算力和 NVLink 带宽被削减：节点内的 NVLink 带宽从 900 GB/s 降到 400 GB/s。节点内（scale-up）带宽的大幅下降对高性能计算负载是个挑战。作为补偿，每个节点配了 8 块 400G 的 InfiniBand ConnectX-7 网卡，增强节点间（scale-out）的能力。

4.2 迁就硬件的并行策略

  • 训练时不用张量并行（TP）。张量并行把每一层的矩阵切开分给几张卡，每层都要 all-reduce 一次，通信非常频繁，只有在节点内高带宽下才划算。NVLink 被砍之后，TP 在训练中效率太低，于是干脆不用（TP 的原理见本站 Megatron-LM 精读）。推理时仍可以有选择地用 TP 来改善首 token 延迟（TTFT）和 TPOT。
  • 增强的流水线并行。用 DualPipe 把注意力、MoE 的计算和 MoE 的通信重叠起来，同时减少流水线气泡、平衡各卡的显存（V3 精读 §3.2.1）。
  • 加速的专家并行。每个节点 8 块 400G 网卡，all-to-all 能跑到每卡 40 GB/s 以上。专家并行的通信库 DeepEP 已开源。

4.3 模型和硬件一起设计：节点受限路由

先补一点背景：all-to-all 通信。

在专家并行里，每张卡上都有一批 token，每个 token 要去不同的卡找专家；每张卡又要从其他所有卡那里收 token。可以把它想成一次“矩阵转置”：第 \(i\) 张卡的第 \(j\) 块数据发给第 \(j\) 张卡。下面的小工具选 “All-to-All” 可以一步步看数据怎么流动。

带宽比是 4:1。H800 节点内外的带宽差距约为 4:1：NVLink 名义 200 GB/s（实际能达到约 160 GB/s），每块 400G IB 网卡名义 50 GB/s（考虑小消息和延迟的影响，论文按有效 40 GB/s 算）。为了把更高的节点内带宽也用上，V3 在专家选择（TopK）策略上和硬件做了协同设计。

问题。设想 8 个节点、共 64 张卡，256 个路由专家，每张卡放 4 个。V3 每个 token 选 1 个共享专家和 8 个路由专家。如果这 8 个专家恰好分散在 8 个节点上，这个 token 就要经 IB 发 8 份，耗时 \(8t\)（\(t\) 是经 IB 发一个 token 的时间）。

办法。利用 NVLink 更快这一点：发往同一个节点的多份，只经 IB 发一份到那个节点，再由节点内的 GPU 通过 NVLink 转发给其他持有目标专家的卡。这样 IB 上的流量被“去重”了，如果 8 个专家分布在 \(M\) 个节点上，IB 的耗时就降到 \(Mt\)。既然 IB 流量只取决于 \(M\)，V3 就在路由算法里直接限制 \(M\)：把 256 个路由专家分成 8 组、每组 32 个，每组放在一个节点上，并保证每个 token 最多被路由到 4 个节点。这样 IB 上最坏的情况从 \(8t\) 降到 \(4t\)。

4.4 节点内外网络的融合：别再让 GPU 干网卡的活

局限。节点受限路由减少了带宽需求，但让通信内核的实现变得复杂，因为它要同时驾驭两种带宽悬殊的网络。实际中，GPU 的流式多处理器（SM，H800 有 132 个）既要处理网络消息（比如填写 QP 和 WQE），又要在 NVLink 上转发数据，这些都占用计算资源。训练时，H800 上最多有 20 个 SM 被分去做通信相关的操作，约占全部 SM 的 15%（推算）。为了在线推理时吞吐最大，V3 的专家并行 all-to-all 完全走网卡的 RDMA，不经 NVLink 转发，以避免和计算争抢 SM。论文说这体现了 RDMA 异步通信模型在“计算与通信重叠”上的优势。

  • 转发数据：在 IB 和 NVLink 两个域之间汇聚、转发发往同一节点内多张 GPU 的流量；
  • 搬运数据：在 RDMA 缓冲区（注册过的 GPU 显存区域）和输入输出缓冲区之间搬运；
  • 规约：执行 combine 所需的加权求和；
  • 管理内存布局：跨 IB 和 NVLink 域分块传输时的细粒度内存布局；
  • 类型转换：all-to-all 前后的数据类型转换（比如 BF16 与 FP8 之间）。

建议。论文“强烈建议”未来的硬件把节点内（scale-up）和节点间（scale-out）通信统一到一个框架里，用专门的协处理器管理网络流量、在 NVLink 和 IB 之间无缝转发。比如节点受限路由，如果硬件能动态地对流量去重，就能进一步优化。论文提到了新兴的互连协议 Ultra Ethernet（UEC）、Ultra Accelerator Link（UALink），以及新提出的统一总线（Unified Bus，UB）。在编程框架层面，具体要求四条：

  • 统一的网络适配器：网卡或 I/O 芯粒同时连到 scale-up 和 scale-out 网络，并带基本的交换功能，比如把从 scale-out 网络进来的包直接转给 scale-up 域里的某张 GPU（可以用一个统一的 LID 或 IP 地址加策略路由实现）。
  • 专用的通信协处理器：一个可编程的部件（比如 I/O 芯粒）专门处理网络流量，从 SM 手里接过包处理，提供硬件加速的内存拷贝；v2 还加了一条关键要求：像 TMA（Hopper 上负责在显存和片上共享内存之间搬数据的张量内存加速器）那样加速内存读写，用很少的资源跑满带宽。
  • 灵活的转发、广播和规约：硬件支持跨两种网络的转发、广播（用于 dispatch）和规约（用于 combine），复刻现在用 SM 实现的那套逻辑。
  • 硬件同步原语：提供细粒度的硬件同步指令，在硬件层面处理内存一致性和数据包乱序到达的问题，取代 RDMA 完成事件这种额外增加延迟和编程复杂度的软件同步。带 acquire/release 语义的“内存语义通信”是一种有希望的实现（§6.4 展开）。

4.5 带宽争用与延迟：PCIe 上的堵车

局限。现在的硬件不能在 NVLink 和 PCIe 上为不同类型的流量动态分配带宽。论文举的例子发生在推理时：把 KV 缓存从 CPU 内存搬到 GPU 可能要占几十 GB/s，足以把 PCIe 跑满；如果这时 GPU 还在通过 IB 做专家并行通信（网卡同样挂在 PCIe 上），KV 搬运和 EP 通信就会互相争抢，导致整体性能下降和延迟尖刺。

  • 把网卡集成进 I/O 芯粒：网卡直接做进 I/O 芯粒，和计算芯粒封装在一起，不再经过传统的 PCIe，能大幅降低通信延迟，缓解 PCIe 争用。
  • CPU 和 GPU 也进入 scale-up 域：用 NVLink 或类似的高带宽互连连接 CPU 和 GPU，而不是只靠 PCIe。这对训练和推理中把参数或 KV 缓存在 GPU 和 CPU 内存之间搬来搬去的场景帮助很大。

5.1 多平面两层胖树：用两层交换机连起上万张卡

这一节要回答的问题：节点之间的网络（scale-out）怎么搭，既决定训练和推理的通信性能，也是集群成本里很大的一块。V3 的训练集群用了一种叫“多平面两层胖树”（MPFT）的拓扑。它和常见的“多轨胖树”有什么区别？为什么它能在只用两层交换机的情况下连起 16,384 张卡，比三层网络便宜多少？它的代价是什么？论文为此做了这篇文章里最完整的一组实验，结果说明了什么、没说明什么？
先补一点背景：胖树、轨道和平面。

胖树（fat tree）是数据中心最常见的网络拓扑，由端口数固定的交换机搭成。设每台交换机有 \(k\) 个端口。在两层胖树里，下层的叶交换机（leaf）一半端口朝下接网卡，一半朝上接脊交换机（spine）；每台叶交换机都连到每台脊交换机。这样任意两块网卡之间最多经过“叶—脊—叶”三跳，而且朝上和朝下的带宽相等，不会因为汇聚而堵塞。两层胖树最多能接 \(k^2/2\) 块网卡：\(k=64\) 时是 2,048。想接更多，就得再加一层，变成三层胖树，最多 \(k^3/4\) 块（\(k=64\) 时 65,536），但交换机、链路和光模块都多得多，路径也更长、延迟更高。

多轨（multi-rail）是 AI 集群的常见布线：每个节点的 8 块网卡分别接到 8 台不同的叶交换机上，所有节点的“第 \(i\) 块网卡”都接在第 \(i\) 条轨道上。编号相同的 GPU 之间只经过一台叶交换机就能通信；编号不同的 GPU 之间，流量要上到脊交换机再下来。在单平面多轨胖树（MRFT）里，所有轨道共用同一层脊交换机，所以网络本身就能把流量从一条轨道送到另一条。

多平面（multi-plane）更进一步：连脊交换机也按编号分开，8 条轨道变成 8 棵彼此完全独立的两层胖树，叫 8 个平面。第 \(i\) 块网卡只能到达其他节点的第 \(i\) 块网卡。如果 GPU 0 要给另一个节点的 GPU 2 发数据，就得先在本节点内经 NVLink 把数据交给 GPU 2（它的网卡在平面 2 上），再从平面 2 发出去。NCCL 的 PXN 功能做的正是这种“先节点内转发、再上网络”的事。

部署情况。V3 训练时用的是 MPFT 网络（原文图 3）：每个节点 8 张 GPU、8 块 IB 网卡，每一对 GPU–网卡属于一个独立的网络平面。另外，每个节点还有一块 400 Gb/s 的以太网 RoCE 网卡，接到单独的存储网络平面上，用来访问 DeepSeek 自研的 3FS 分布式文件系统。scale-out 网络用的是 64 端口的 400G IB 交换机，按两层胖树的公式，这个拓扑理论上最多能支持 16,384 张 GPU：

$$\underbrace{\frac{64^{2}}{2}}_{\text{每个平面的网卡数}}\times\underbrace{8}_{\text{平面}}=2048\times8=16{,}384$$

每个平面能接 2,048 块网卡，每个节点在每个平面上占一块，所以最多 2,048 个节点、16,384 张卡，而且始终只有两层交换机，保留了两层网络的成本和延迟优势。论文说，由于政策和监管的限制，最后实际部署的只有两千多张 GPU。

多平面的好处（§5.1.1）。

  • 是多轨胖树的一个子集：MPFT 可以看作 MRFT 去掉了跨轨的脊层连接，所以 NVIDIA 和 NCCL 为多轨网络做的优化可以直接沿用；NCCL 的 PXN 解决了平面之间互不相通的问题。
  • 成本：用两层胖树就能接上万个端点，比三层胖树便宜得多（见下表），每个端点的成本甚至略低于以省钱著称的 Slim Fly 拓扑。
  • 流量隔离：每个平面独立运行，一个平面拥塞不影响其他平面，避免连锁的性能下降。
  • 延迟更低：两层比三层少一级交换，论文说“实验表明”延迟更低，适合 MoE 这种对延迟敏感的训练和推理（但论文没有给出这组数字）。
  • 健壮性：在理想形态里，多端口网卡有多条上行链路，单个端口故障不会断网，可以快速透明地恢复。

  • DeepEP 那组只测了 MPFT，没有 MRFT 对照；“40 GB/s 以上”是在每卡 4,096 个 token 的训练式负载下测的，不代表推理时小批量、低延迟模式下的表现。
  • 推理侧没有测。论文承认跨平面需要节点内转发、会增加推理延迟，但没有给出这部分延迟的测量。

IB 的延迟始终更低，所以在分布式训练和推理这类延迟敏感的场景里是首选。但 IB 有两个局限：一是贵，硬件价格明显高于 RoCE 方案；二是扩展性，IB 交换机通常只有 64 个端口，而 RoCE 交换机常见 128 个端口。端口数直接决定两层胖树能接多少端点：\(k=128\) 时每个平面能接 \(128^2/2=8192\) 块网卡，是 64 端口时的 4 倍（推算）。所以论文希望 RoCE 能把延迟和功能补上，成为 IB 的低成本替代。

5.2.2 给 RoCE 的三条建议

（1）专门的低延迟 RoCE 交换机。希望以太网厂商针对 RDMA 负载优化交换机，去掉不必要的以太网功能。论文举了两个例子：HPE 的 Slingshot 架构说明以太网也能做到接近 IB 的延迟；Broadcom 的 AI 转发头（AIFH）和即将推出的低延迟以太网交换机也说明了可行性。

先补一点背景：ECMP 与自适应路由。

两台交换机之间往往有很多条等价的路径。ECMP（等价多路径）是以太网默认的做法：对每个数据流的地址、端口等信息算一个哈希值，按哈希选路，同一个流始终走同一条路。流很多、很随机时，这能把流量摊得比较均匀；但大模型训练的流量恰恰相反，流的数量少、每个都很大、模式很规整，很容易有几个大流被哈希到同一条链路上，那条链路堵死，其他链路闲着（本站 MegaScale 精读 §3.6 讲过同一个问题）。自适应路由（AR）则按包而不是按流选路，根据实时拥塞把包“喷洒”到多条路径上，代价是包会乱序到达，接收端要能处理。静态路由是人工配好路由表，让特定的目的地走特定的路径。

（2）更好的路由策略。原文图 8 在 RoCE 网络上比较了 ECMP、自适应路由和静态路由下，AllGather 和 ReduceScatter 两种集合通信的带宽，横轴是张量并行的规模。ECMP 明显吃亏：训练流量（比如数据并行）缺乏随机性，多个流挤到同一条链路上。静态路由能为特定的目的地避开冲突，但不够灵活；对大规模的 all-to-all，自适应路由的性能和扩展性最好。

（3）更好的流量隔离或拥塞控制。当前的 RoCE 交换机只支持很少几个优先级队列，不够应付复杂的 AI 负载，比如专家并行的 all-to-all 和数据并行的 all-reduce 同时进行。all-to-all 是突发的“多对一”传输，会造成 incast 拥塞（很多发送方同时打向一个接收方，接收端口的队列被挤爆），连累其他流量。一个办法是虚拟输出队列（VOQ），给每个 QP 分配一个专属的虚拟队列，把流量彼此隔离；另一个办法是更有效的拥塞控制，比如基于往返时间的拥塞控制（RTTCC）或用户可编程的拥塞控制（PCC），让网卡和交换机协同优化，在动态流量下保持低延迟和高吞吐。

读图 8 时要注意：论文没有交代这组测试用了多少个节点、多大的消息、带宽按什么口径统计（TP=2 时约 190 GB/s，远超单块 400G 网卡，说明它统计的是某种聚合带宽）。所以这张图只适合读“三种路由之间的相对差别”，不适合拿绝对值去比别的系统。

5.2.3 IBGDA：让 GPU 自己敲网卡的门铃

传统的网络通信要借助 CPU 上的一个代理线程：GPU 把数据准备好后通知 CPU 代理，代理填写工作请求（WR）的控制信息，再通过“门铃”机制通知网卡开始传输。这一来一回增加了额外的开销。IBGDA（InfiniBand GPUDirect Async）让 GPU 自己填写 WR，并直接写网卡门铃的 MMIO 地址，整个控制面都在 GPU 上完成，省掉了 GPU 与 CPU 之间通信的延迟。此外，发送大量小包时，CPU 一侧的控制处理器很容易成为瓶颈；GPU 有大量并行线程，可以把这部分工作分摊开。

6.1–6.3 更广的讨论（上）：可靠性、CPU 与“智能”网络

这一节要回答的问题：第 2–5 节的建议都来自具体的应用场景。第 6 节把视野放宽，讨论一些更普遍的硬件问题。这一部分先看三个：大集群里硬件故障和“静默数据损坏”有多麻烦；在加速器唱主角的系统里，CPU 为什么仍然可能成为瓶颈；未来的网络应该具备哪些能力。

6.1 可靠性

局限。论文列了三类问题。第一是互连故障：IB 和 NVLink 这类高性能互连会间歇性断连，专家并行这种通信密集的负载哪怕只中断一下，也可能导致明显的性能下降甚至任务失败。第二是单点硬件故障：节点崩溃、GPU 故障、显存 ECC 错误都可能打断长时间运行的训练，往往要代价很高的重启；系统越大，出现单点故障的概率越高。第三是静默数据损坏：ECC 检测不到的错误，比如多位翻转或计算出错，会悄悄地影响模型质量。它们在长时间任务里尤其隐蔽，因为错误会不被察觉地传播下去；现在的应对靠应用层的经验规则，不足以保证整个系统的可靠性。

建议。硬件要在传统 ECC 之外加入更先进的错误检测，比如基于校验和的验证、硬件加速的冗余校验；硬件厂商还应该把完整的诊断工具包作为标准配置交给用户，让用户能严格验证系统的完整性、主动发现潜在的静默数据损坏。大规模训练在软件层面怎样发现坏机器、快速恢复，可以对照本站 MegaScale 精读 §4。

6.2 CPU 瓶颈与互连

加速器是主角，但 CPU 仍负责协调计算、管理 I/O、维持系统吞吐。论文指出三个瓶颈：

  • PCIe 带宽：§4.5 已经讲过，CPU 与 GPU 之间的 PCIe 在传输大量参数、梯度或 KV 缓存时常常成为瓶颈。未来的系统应该用 NVLink、Infinity Fabric 这类 CPU–GPU 直连，或者干脆把 CPU 和 GPU 都放进 scale-up 域。
  • 内存带宽：要维持这么高的传输速率，CPU 一侧的内存带宽也得跟上。论文的例子是：跑满 160 条 PCIe 5.0 通道，每个节点需要超过 640 GB/s 的传输能力（推算：每条通道每个方向约 4 GB/s），对应约 1 TB/s 的内存带宽，这对传统 DRAM 架构是很大的挑战。
  • 单核性能与核数：内核启动、网络处理这类对延迟敏感的任务需要很高的单核性能，通常要求基础频率在 4 GHz 以上；每张 GPU 还要配足够多的 CPU 核，避免控制侧成为瓶颈；对芯粒架构的 CPU，还需要额外的核来做感知缓存的负载划分和隔离。

6.3 面向 AI 的“智能”网络

先补一点背景：无损网络与队头阻塞。

RDMA 网络通常要求“无损”：交换机缓冲快满时，不是丢包，而是通知上游暂停发送。基于信用的流控（CBFC）就是这样一种机制：下游先告诉上游自己还有多少缓冲空间（信用），上游只在有信用时才发。问题在于，如果流控被粗暴地触发，一个被堵住的流会让同一队列里排在它后面、本来要去别处的包也一起停下，这叫队头阻塞。拥塞严重时，暂停还会一级级往上游传播，波及无关的流量。

为了满足对延迟敏感的负载，论文认为未来的互连要同时做到低延迟和“智能”：

  • 共封装光学（CPO）：把硅光器件和芯片封装在一起，提高带宽的可扩展性和能效。
  • 无损网络：CBFC 能保证不丢包，但要配合先进的、由端点驱动的拥塞控制算法，主动调节注入速率，避免病态的拥塞。
  • 自适应路由：如 §5.2.2 所说，网络应该把包喷洒、感知拥塞的选路这类动态路由做成标准，持续监测网络状态、重新分配流量，缓解 all-to-all 和 reduce-scatter 这类集合通信中的热点。
  • 高效的容错协议：自愈协议、冗余端口、快速故障切换，以及链路层重试、选择性重传等机制，让网络在间歇性故障下仍能无缝运行。
  • 动态资源管理：动态分配带宽、设定流量优先级。比如在训练和推理共用的集群里，把推理流量和训练流量隔离开，保证对延迟敏感的服务能及时响应。

6.4 内存语义通信与顺序问题

先补一点背景：为什么“先写数据、再写标志”需要栅栏。

两台机器之间用 load/store（内存语义）通信时，最常见的模式是“生产者—消费者”：发送方先把数据写到接收方的内存里，再写一个标志位告诉接收方“数据到了”；接收方看到标志位变了，就去读数据。这要求标志位不能比数据先到。可是网络里包可能走不同路径、乱序到达，于是发送方在写完数据之后、写标志位之前，必须插一条内存栅栏（fence），等前面的写操作都确认完成再继续。

acquire/release 语义是处理这类顺序的一种更精细的约定：一次 release 写保证它之前的所有写都已经对别人可见；一次 acquire 读保证它之后的读能看到对应 release 之前的所有写。顺序由这对操作本身保证，不需要全局的栅栏。

问题。节点间用 load/store 内存语义通信既高效又对程序员友好，但现有实现被内存顺序问题拖累。发送方写完数据后，必须先发一条栅栏再更新标志位，以保证数据一致。这种严格的顺序引入了额外的往返时间（RTT），还可能让发出指令的线程停下来等待，阻碍后续写操作的飞行，降低吞吐。消息语义的 RDMA 也有类似的乱序同步问题：比如在 InfiniBand 或 NVIDIA BlueField-3 上，开着包喷洒、在普通的 RDMA 写之后做 RDMA 原子加操作，也会多出一个 RTT 的延迟。

建议。论文主张硬件为内存语义通信提供内建的顺序保证：在编程层面用 acquire/release 语义表达，由接收端的硬件来强制执行，做到按序交付而不增加开销。可能的做法有两种。一是接收端缓存原子消息，按包序号（PSN）顺序处理，简单直接、能保证正确性。二是基于区域的 acquire/release（RAR）机制：接收端硬件为内存区域维护轻量的元数据（比如位图或区域计数器）来跟踪状态，acquire 和 release 操作的作用范围限定在特定地址区间，从而不需要发送方的显式栅栏就能实现高效的、由硬件保证的顺序。两种方案都适合在网卡或 I/O 芯粒上实现，也都同时适用于内存语义和消息语义的 RDMA。（v1 只提了 RAR 一种并称它“更优雅”，v2 改成了两种方案并列。）

6.5 网内计算与压缩

先补一点背景：网内计算。

网内计算是让网络交换机在转发数据的同时做一些简单运算。最典型的是集合通信里的规约：与其让每张卡把数据发来发去、各自相加，不如让交换机在数据经过时就把它们加起来，只把结果往下传，这样网络上的流量大大减少。NVIDIA 的 SHARP 就是在 InfiniBand 交换机上做这件事的技术（V3 技术报告 §3.5 曾提到它）。

专家并行的两个 all-to-all 阶段都有网内优化的空间。dispatch 像一次小规模的多播：同一条消息要送到好几个目标设备。如果硬件协议能自动复制数据包并转发到多个目的地，通信开销可以大幅降低。combine 像一次小规模的规约，可以借助网内聚合；但由于 combine 的规约范围小、各专家的负载又不均衡，灵活地实现网内聚合很有挑战。此外，§3.2 的 LogFMT 能以很小的模型效果损失实现低精度传输，如果把它原生做进网络硬件，就能提高“每比特携带的信息量”、减少带宽占用；硬件加速的压缩与解压能让 LogFMT 无缝融入分布式系统。

6.6 以存储为中心的创新

局限。模型规模的指数级增长已经超过了 HBM 技术的进步，这在 Transformer 这类注意力密集的结构上形成内存瓶颈。

这篇论文是一份“立场 + 经验”文件，本站没有找到第三方对其网络实验的复现，也很难说某项硬件改动是“因为这篇论文”才发生的。下面只列截至 2026 年 10 月能在公开资料里核实的、和论文建议直接相关的进展。

低精度：从 128 元素分组到 MX 格式

论文写作时，NVIDIA Blackwell 已经宣布原生支持微缩放（MX）格式，这正是“Tensor Core 直接认分组缩放因子”的建议。DeepSeek 自己随后向这个方向靠拢：2025 年 8 月的 DeepSeek-V3.1 模型说明写明，模型的权重和激活都用 UE8M0 格式的 FP8 缩放因子训练（只有指数的 8 位因子，即 2 的整数次幂），目的是与微缩放数据格式兼容。到 2026 年发布的 DeepSeek-V4，后训练阶段对 MoE 专家权重和 CSA 索引器的 QK 路径做了 MXFP4 量化感知训练；V4 论文还指出，现有硬件上 FP4 × FP8 的峰值算力与 FP8 × FP8 相同，未来硬件理论上可以再高效三分之一，这又是一条写给硬件的需求。FP8 与 FP4 格式本身见本站 FP8 格式精读、NVFP4 精读和 FP4 训练拆解页。

注意力：§2.1.3 提到的稀疏化成了主线

论文说“稀疏注意力是另一条出路”，引用的是 NSA。DeepSeek 后来的演进正沿着这条线：MLA 压缩每个 token 的 KV（V2/V3）→ V3.2 的 DSA 在 MLA 之上做 token 级稀疏选择（V3.2 精读）→ V4 的 CSA/HCA 先沿序列方向压缩 KV、再稀疏选择或稠密注意（V4 精读），1M 上下文时 V4-Pro 的 KV 缓存只有 V3.2 的 10%→ V4.1-Flash 进一步压缩 KV 缓存（V4.1-Flash 精读）。另一条“稀疏”的维度是条件记忆 Engram（Engram 精读），V4 论文的结论部分把“更稀疏的嵌入模块”列为下一步方向。

通信：V4 给出了“带宽够用”的平衡点

V4 论文 §3.1 把专家并行的通信和计算融合进一个流水化的内核（MegaMoE，开源在 DeepGEMM 中），把专家分成若干“波次”，让当前波次的计算、下一波次的 token 传输和已完成专家的结果回传同时进行。V4 报告它在 NVIDIA GPU 和华为昇腾 NPU 上都做了验证，相对不融合的强基线，一般推理负载提速 1.50–1.73 倍，强化学习采样等延迟敏感场景最高 1.96 倍。

更值得对照的是 V4 那一节末尾“给硬件厂商的观察与建议”，它可以看作这篇论文的续篇：

  • 计算通信比，而不是带宽本身。设峰值算力为 \(C\)、互连带宽为 \(B\)，通信能被完全藏住的条件是 \(C/B\le V_{\text{comp}}/V_{\text{comm}}\)。对 V4-Pro，每个“token–专家”对要算 \(6hd\) 次浮点运算、只传 \(3h\) 字节（FP8 dispatch + BF16 combine，和本文 §2.3.2 的“3 字节”是同一个口径），于是 \(C/B\le 2d=6144\) FLOPs/字节，即每 1 GB/s 的互连带宽足以掩盖 6.1 TFLOP/s 的计算。按这个比例，一张峰值约 1,000 TFLOPS 的卡需要约 163 GB/s 的互连带宽（推算，假设计算跑在峰值），比单块 400G 网卡的 50 GB/s 高得多，但远低于 NVL72 的 900 GB/s。V4 的结论是：带宽达到这个平衡点之后，再堆带宽收益递减，硬件应该瞄准平衡点，而不是无条件地加带宽。这修正了本文 §2.3.2 那种“只算通信”的推算给人的印象：带宽不是越大越好，而是要和算力配平。
  • 功耗余量。极致的内核融合让计算、显存和网络同时满载，功耗限频成了关键的性能限制，希望硬件留出足够的功耗余量。
  • 通信原语。V4 的 dispatch 改成了“拉”的方式（每张卡主动读远端的激活），以避开细粒度“推”所带来的高通知延迟；希望未来硬件提供更低延迟的跨 GPU 信号，让“推”变得可行。这和本文 §4.4 的“硬件同步原语”、§6.4 的顺序问题是一脉相承的。
  • 激活函数。建议用不含指数和除法的廉价逐元素激活替代 SwiGLU，避免矩阵乘之后的处理拖住流水线。这是本文没有的新方向：为了硬件效率去改模型的激活函数。

DeepEP：SM 还没完全解放

论文最强调的“别让 GPU 干网卡的活”，在 DeepSeek 自己的通信库里有了一些软件层面的回应，但还没有硬件层面的解决。按 2026-10-20 查看的 DeepEP 说明：它经历了一次完整的重构（V2，支持更大的 scale-up 和 scale-out 域，新增基于 NCCL 的轻量后端），并有了在华为昇腾 950 上运行的版本；但说明里明确写着，专家并行的 dispatch 和 combine 仍然需要 GPU 的 SM，不支持“零 SM”的 RDMA 专家并行。仓库列出的几个实验分支正对着本文的愿望清单：Hybrid-EP 用 TMA 指令把 SM 占用降到最低（呼应 §4.4.2“像 TMA 那样加速内存读写”），Normal-SMFree 把 SM 从 RDMA 路径上解耦，Eager 用低延迟协议去掉 RDMA 原子操作带来的额外 RTT（呼应 §6.4）。DeepEP 还新增了实验性的远程内存访问原语，服务于 Engram 的查表，这是“内存语义通信”在模型侧的一个直接用例。

本站的看法是：这篇论文最持久的影响，可能是让“模型团队用几行算术给硬件提需求”成为 DeepSeek 技术报告的固定章节：V3 报告的 §3.5、这篇论文、V4 报告的 “Observations and Proposals” 一脉相承。

0 导读：这篇论文解决什么问题

2025 年前后出现的推理模型（DeepSeek-R1 一类）之所以会“先想再答”，靠的是强化学习（RL）。RL 训练是一个循环：让模型对一批题目各写若干个回答，这一步叫生成（也叫 rollout）；用程序判断每个回答对不对，给出奖励；再用这些回答和奖励更新模型参数，这一步叫训练；然后用新参数进入下一轮生成。推理模型的一个回答可以长达几万个 token，而且同一批里有的回答几百 token 就结束、有的要写满上限，所以生成往往是整个循环里最慢、最难排布的部分。

当时主流的大规模 RL 系统（例如本站精读过的 HybridFlow / verl）是同步的：一批回答全部写完，才开始训练；训练完，才开始写下一批。这样做的好处是训练用的永远是“当前模型”写的回答，算法上最干净；坏处是一批里最长的那个回答决定了整批的耗时，先写完的 GPU 只能干等。AReaL 的做法是把生成和训练彻底拆开：两件事放在不同的 GPU 上各自不停地跑，生成端写完一条就交一条，训练端攒够一批就更新一次，更新完把新参数推给生成端；生成端正在写的回答会被打断，换上新参数后接着写。

拆开的代价是：训练用的数据不再全是当前模型写的，而是几个版本以前的模型写的，甚至一条回答的前半段和后半段出自不同版本。用 RL 的话说，训练变成了离策略（off-policy）的，而 PPO 这类算法本来假设数据是当前策略采的，处理不好效果会变差。AReaL 用两个办法控制这个代价：一是规定样本最多只能落后几个版本（最大陈旧度 \(\eta\)）；二是把 PPO 的目标函数改成解耦形式，让“修正采样分布”和“限制更新幅度”这两件事分别以不同的策略为参照。

论文的结果是：在 1.5B 到 32B 的数学和代码推理模型上，同样的卡数、同样的训练步数，AReaL 的训练时间是作者自己的同步版本的 1/1.6 到 1/2.8，最终精度基本持平。摘要里的“最多 2.77 倍加速”就是 1.5B 模型上这两者之比；如果换成和 verl 的估计训练时间比，倍数是 1.5 到 2.3（推算，见 §7.2）。

1 引言：推理模型的 RL 为什么需要一个新系统

这一节要回答的问题：用 RL 训练推理模型，对训练系统提出了哪些要求？为什么现有的大规模 RL 系统几乎都做成同步的？这种同步设计放到推理模型上，浪费在哪里？已经有人尝试让生成和训练并行，为什么作者认为还不够？AReaL 的核心主张和贡献是什么？
先补一点背景：用 RL 训练推理模型，一轮迭代在做什么。

把大模型看成一个“策略”：给定题目和已经写下的内容，它给出下一个 token 的概率分布，按这个分布抽一个 token 写下去，如此反复，直到写出结束符。RL 训练推理模型的一轮迭代分四步：

  1. 取题目。从数据集里取一批题目（比如数学题、编程题）。
  2. 生成。用当前参数，对每道题采样多个回答。回答里先是长长的思考过程，最后给出答案。这一步由推理引擎（如 SGLang、vLLM）完成，本质上就是大批量的文本生成。
  3. 算奖励。用规则判对错：数学题核对最终答案，编程题跑单元测试。这类“答案可以自动验证”的奖励，也常被称为 RLVR（基于可验证奖励的 RL）。它不需要额外的奖励模型，在 CPU 上就能算。
  4. 训练。用 PPO 或 GRPO 这类算法更新参数：答对的回答里的 token 被调高概率，答错的被调低。更新完的参数要送回推理引擎，下一轮生成才会用上。

PPO 和 GRPO 都是同策略（on-policy）算法，意思是它们假设训练数据是由“当前这版参数”采样出来的。数据越“旧”，算法的理论依据就越站不住，效果也可能变差。这是后面所有设计取舍的根源。

示意图：RL 训练推理模型的一轮迭代
题目数据集里的一批→生成（rollout）推理引擎，每题采样多个长回答→奖励规则判对错，CPU 上算→训练PPO / GRPO 更新参数→新参数同步回推理引擎↺
同步系统严格按这个顺序一轮一轮地走；AReaL 让“生成”和“训练”两个框各自在不同的 GPU 上持续运转，中间用缓冲区和参数服务连起来（§4）。

第一个要求是规模。RL 要靠大批量的采样来充分探索，PPO、GRPO 在推理任务上常用的有效批大小是几千个回答；而推理模型每个回答又可能有上万个思考 token。以本文实验的配置为例，每一步训练用 512 道题、每题 16 个回答，共 8,192 条轨迹，每条最多生成 27,648 个 token（原文表 3）；加上最长 1,024 个 token 的题目，一步的数据量上限约 2.3 亿个 token（推算）。这样的负载必须铺到几十上百台机器上才跑得动。

第二个难点是两种计算来回切换。生成是逐 token 的自回归解码，最适合推理引擎；训练是整段序列的前向和反向传播，最适合训练框架。两者在同一批 GPU 上交替进行时，每次切换都要换引擎、换并行切法、搬运参数，处理不好开销很大（HybridFlow 的 3D-HybridEngine 就是专门优化这一步的）。

第三个难点是长度不可预测。推理模型对不同题目写出的回答长短差别极大，而且随着训练进行，回答长度的分布本身也在变。生成和训练的工作量因此一直在变，固定的排布很容易让一部分 GPU 闲下来。

第四个难点来自算法。经典的 PPO、GRPO 要求同策略的数据，系统必须保证训练时用的样本是最新参数写的。

正因为第四点，现有的大规模 RL 系统（论文举了 ReaLHF、OpenRLHF、verl、NeMo-Aligner）几乎都做成完全同步：严格交替“生成一批、训练一步”，保证模型永远在最新的输出上训练，算法效果最好。代价是生成阶段必须等到这一批里最长的那个回答写完才能结束。推理模型的回答长度差异极大，同步系统的效率因此很差。

最近也有一些工作尝试让生成和训练并行：用上一版（或上两版）模型生成的数据来更新当前模型，这样训练这一步的时候，下一批数据已经在生成了。为了不伤效果，这类系统把“落后的版本数”限制在一到两步。但它们仍然是按批生成的：一个训练批里所有样本出自同一个版本，生成端仍要等这一批最长的回答写完，生成阶段内部的空等没有解决。

AReaL 的主张是从系统设计上彻底解决这个问题：生成端以“流”的方式工作，每个 rollout worker 不停地写新回答，不等任何人；训练端只要从生成端拿到一个训练批，就做一次并行的参数更新；更新完，把新参数同步到每个 rollout worker。这样一来，一个训练批里的样本可能出自多个不同版本的模型。为此 AReaL 做了三件事：用改造过的 PPO 目标函数，让较旧版本生成的样本也能用而不掉点；用数据过滤控制每个样本的陈旧程度；再加上几项系统优化，包括可中断的 rollout worker、针对变长序列的动态批处理和并行的奖励服务。

引言给出的结果是：在最大 32B 的数学推理和代码生成任务上，AReaL 的训练吞吐最高是当时最好的同步系统的 2.57 倍，并且在 512 张 GPU 以内接近线性扩展；更重要的是，加速的同时最终精度没有下降，有的任务还略有提高。

读的时候要注意几个数字的来历：引言写的是“训练吞吐最高 2.57 倍”，摘要写的是“训练加速最高 2.77 倍”，§7.3 写的是“最多 2.5 倍”。对照 arXiv 的版本历史可以看出原因：第 1 版的摘要、引言和 §7.3 都写 2.57 倍；从第 2 版起，摘要和 §7.2 改成按表 1 训练小时数算出的 2.77 倍，§7.3 改成 2.5 倍，引言里的 2.57 倍没有改。按本站从原文图 4 量出的数值，2.57 倍正好是 1.5B 模型、32K 上下文、256 张卡时 AReaL 与 verl 的吞吐之比（读图约数，见 §7.3）。而 2.77 倍是 1.5B 模型上同步版 AReaL 与异步 AReaL 的训练小时数之比（见 §7.2）。两个数的对照组和指标都不一样，不能混在一起理解。这篇论文的早期版本还以 2.57 倍的说法入选了 ICML 2025 的 ES-FoMo III 研讨会（spotlight）。

2 相关工作：异步 RL 并不新，新在哪里

这一节要回答的问题：“生成和学习分开跑”的异步 RL 在游戏领域早就有了，搬到大模型上为什么还值得一篇论文？同期的大模型异步 RL 工作做到了哪一步？AReaL 和它们的区别在哪里？
先补一点背景：游戏 RL 里的 actor–learner 架构。

在 Atari、星际争霸、Dota 2 这类游戏 RL 里，“和环境交互收集经验”的进程（actor）和“用经验更新网络”的进程（learner）早就是分开跑的：成百上千个 actor 各自拿着一份可能稍旧的网络去玩游戏，把经验源源不断地交给 learner；learner 更新网络后，actor 隔一段时间拉一次新参数。代价是 actor 用的网络总比 learner 落后一点，这种落后叫策略滞后（policy lag）。DeepMind 的 IMPALA 用一种叫 V-trace 的重要性加权方法修正这种滞后，这和后面 §5 的思路一脉相承。

大模型推理 RL。RL 已经成为提升大模型推理能力的主要手段，主要用在奖励容易定义的任务上：数学、代码、科学问题、工具使用。训练过程中，模型通过不断拉长思维链来学会推理。开源社区在小模型上的成功（DeepScaleR、DeepCoder 等，它们都是从蒸馏模型出发）是本文的直接出发点。论文特意说明，它研究的是对已经做过监督微调的推理模型继续做 RL，而不是偏好对齐式的 RLHF，也不是直接从预训练基座出发的“零样本”推理 RL。

异步 RL。解耦的异步架构（RLlib、IMPALA、作者团队自己的 SRL）配合相应的算法（SEED RL、R2D2 等），在游戏里取得了巨大成功（Dota 2 的 OpenAI Five、AlphaStar）。在大模型上，类似的尝试要么集中在上下文很短的场景（如 RLHF；Asynchronous RLHF、Trajectory Balance with Asynchrony、Tapered Off-Policy REINFORCE），要么只把生成和训练错开一两步（DeepCoder、INTELLECT-2）。AReaL 声称在“陈旧度”和“训练速度”之间提供了更灵活的权衡。同期的 StreamRL 也把生成拆出去流式地做，作者认为它更侧重榨取系统效率，而 AReaL 走的是算法与系统协同设计的路线。

可中断生成与部分 rollout。Kimi k1.5 在同步系统里用过“部分 rollout”：每轮给生成设一个固定的长度预算，没写完的回答留到下一轮接着写。AReaL 的可中断生成在概念上和它相似，区别是 AReaL 不设固定预算，而是在新参数到达时动态打断，并通过缓冲区保证每个训练批的大小固定，以此维持 PPO 的稳定。和此前的离策略算法相比，作者认为 AReaL 的算法能容忍更大的陈旧度，并且和可中断生成兼容。

大模型训练与推理系统。本文只考虑稠密 Transformer。生成需要高效的 KV 缓存管理（vLLM、SGLang）和解码内核（如 FlashInfer）；训练需要编排数据并行、张量并行、流水线并行（Megatron-LM、ZeRO / FSDP）。同步系统在同一批卡上先后做生成和训练，但两者的最优并行切法不同，于是有了上下文切换（PUZZLE、Kimi k1.5）或权重重分片（HybridFlow、作者团队的 ReaLHF）这些技术。AReaL 把生成和训练分到不同的 GPU 上，重分片就不再位于训练的关键路径上。

“消除重分片开销”的准确含义：生成端和训练端分开以后，训练卡不需要再把参数换成生成用的切法，所以训练步之间不用等重分片。但参数仍然要从训练端传到生成端（§4 的参数服务），生成端加载新权重、重算 KV 缓存也要时间。论文没有单独报告这部分开销有多大，只在原文图 3 的示意里画出了“加载权重”的时间段。

3 背景：PPO 怎么训练推理模型，同步系统卡在哪里

这一节要回答的问题：论文用的 RL 目标和 PPO 具体长什么样，后面要改的是哪一部分？同步的分布式 RL 系统是怎么跑的？作者认为它有哪两个根本缺陷，这两个缺陷各自是什么原因造成的？

3.1 把“写回答”写成一个决策过程

论文把生成回答形式化为一个马尔可夫决策过程。状态 \(s_t\) 是题目 \(q\) 加上已经写下的前 \(t-1\) 个 token；动作 \(a_t\) 是下一个 token，动作空间就是词表；状态转移是确定的，把 \(a_t\) 接到 \(s_t\) 后面就得到 \(s_{t+1}\)。策略 \(\pi_{\theta}\) 就是参数为 \(\theta\) 的大模型，它给出下一个 token 的概率分布。奖励 \(r\) 只在最后一个 token 上非零，表示答案对不对；折扣因子 \(\gamma=1\)，也就是不打折；\(H\) 是回答的长度上限。训练目标是让期望奖励最大：

$$J(\theta)=\mathbb{E}_{q\sim\mathcal{D},\ a_t\sim\pi_{\theta}(\cdot\mid q,a_{<t})}\Big[\sum_{t=1}^{H}\gamma^{t-1}r(s_t,a_t)\Big]$$

这里 \(\mathcal{D}\) 是题目的分布。注意期望下标里的 \(a_t\sim\pi_{\theta}\)：这个目标要求回答是由正在被优化的这版模型写出来的。

先补一点背景：重要性采样，以及 PPO 为什么要“截断”。

假设数据是旧策略 \(\pi_{\mathrm{old}}\) 采的，而我们想估计新策略 \(\pi_{\theta}\) 下的期望。统计学的标准做法是重要性采样：每个样本乘上一个权重 \(\pi_{\theta}/\pi_{\mathrm{old}}\)。直观地说，如果新策略比旧策略更爱写某个 token，这个 token 在估计里的分量就该加大，反之减小。这个比值记作 \(u_t(\theta)\)。

问题是，当新旧策略差得很远时，比值可能非常大或非常小，估计的方差会爆炸，一步更新就可能把模型带偏。PPO 的办法是给比值设一个窗口 \([1-\epsilon,1+\epsilon]\)（本文 \(\epsilon=0.2\)），并在原始项和截断项之间取较小的那个：

$$J_{\mathrm{PPO}}(\theta)=\mathbb{E}_{q\sim\mathcal{D},\ a_t\sim\pi_{\mathrm{old}}(\cdot\mid q,a_{<t})}\Big[\sum_{t=1}^{H}\min\big(u_t(\theta)\hat A_t,\ \mathrm{clip}(u_t(\theta),1-\epsilon,1+\epsilon)\,\hat A_t\big)\Big],\qquad u_t(\theta)=\frac{\pi_{\theta}(a_t\mid s_t)}{\pi_{\mathrm{old}}(a_t\mid s_t)}$$

其中 \(\hat A_t\) 是优势的估计，表示这个 token 所在的回答比“平均水平”好多少。取较小值的效果是：如果一个 token 的优势为正，新策略把它的概率调高到旧策略的 1.2 倍以后，再调高就不再有奖励，梯度变成 0；优势为负时同理，调低到 0.8 倍以后不再继续压。于是每一步更新都被限制在旧策略附近的一个“信赖域”里。

举个数：某个 token 在 \(\pi_{\mathrm{old}}\) 下的概率是 0.30，优势为正。训练时它的概率被一路调高，到 0.36（比值 1.2）时，这个 token 就不再提供梯度（推算示例）。

论文还强调一个细节：按 RL 的常规做法，一个全局批会被切成几个小批（minibatch），依次做多次参数更新（本文每步 4 个小批，原文表 3）。这和“梯度累积”不同：梯度累积是把几个小批的梯度加起来只更新一次。正因为一步里有多次更新，第二个小批开始时 \(\pi_{\theta}\) 已经离开了 \(\pi_{\mathrm{old}}\)，比值和截断才真正起作用。即使在同步系统里也是如此。

论文实际用的 PPO 配置（原文附录 B.1）比教科书版本简单得多：不用 critic 模型，也不用参考模型（所以没有 KL 惩罚）；GAE 的 \(\lambda\) 和折扣 \(\gamma\) 都取 1；答对奖励 +5、答错 −5，只给在最后一个 token 上；再在整个全局批上做优势归一化。把这几条放在一起推一下：没有 critic 时价值估计为 0，\(\lambda=\gamma=1\) 时每个 token 的优势就等于整条回答的最终奖励，归一化之后，优势只取决于“这条回答比本批平均好还是差”（本站推导）。所以这里的“PPO”更接近“带基线的 REINFORCE 加上 PPO 的截断”，和 GRPO 的区别主要是基线按全局批算、而不是按同一道题的一组回答算。

3.2 同步系统是怎么跑的

本文关注的是已经做过监督微调的推理模型（比如从 DeepSeek-R1 蒸馏出来的 Qwen 系列），而不是从预训练基座直接激发推理能力。这类模型一开口就是很长的推理过程（例如 32K token），稳定的 RL 训练通常还需要很大的全局批（例如 128 道题、每题 16 个回答）。在同步系统里，生成和训练两个阶段在同一批 GPU 上轮流执行：生成阶段用最新参数为训练批里的每道题写出多个回答；训练阶段用这些回答更新参数；然后进入下一轮。

3.3 同步系统的两个根本缺陷

缺陷一：推理卡大量闲置。同步系统里，训练必须等这一批里最长的回答写完才能开始（上图①）。推理模型的回答长短悬殊，于是各张卡上解码的长度很不均匀：有的卡早早写完了自己分到的回答，只能等最慢的那张卡。上图②的“错开一步”让训练和下一批的生成重叠起来，训练卡不用再陪着等生成；但生成仍是“一整批”为单位，生成卡内部的长尾空等原封不动。

先补一点背景：为什么解码阶段“卡越多不一定越快”。

大模型每生成一个 token，都要把全部参数从显存读一遍；把很多条回答放进同一个批一起解码，读一遍参数就能为它们各产出一个 token，所以批越大，每张卡的产出越高。批太小时，GPU 的时间几乎全花在搬数据上，计算单元闲着，这叫显存带宽受限（memory-IO bound）。vLLM 精读的第 1 节有一个具体的算例。

缺陷二：扩展性差。同步系统把一批回答的生成摊到所有卡上。全局批大小是算法定的，卡越多，每张卡分到的回答越少，每张卡的解码批就越小，解码越深地陷进显存带宽受限的区间。举个数：一步 8,192 条回答，摊到 128 张卡上每卡约 64 条，摊到 512 张卡上每卡只剩约 16 条；到了长尾阶段，每张卡上还在写的回答更少（推算示例）。卡数翻了 4 倍，每一步解码的耗时却降不了多少，所以加卡换不来相应的吞吐。

这两条是定性论证：§3.2 没有给出“同步系统空等了多少比例”的测量。能间接看出它的，是 §7.3 里 verl 的扩展曲线（卡数翻 8 倍，吞吐只涨 2–2.8 倍，读图推算），以及 §7.5 里“不可中断”生成比可中断慢 12%–17%。另外，回答越长，KV 缓存的读取在解码时间里占比越大，批大小的影响会相对变小；论文没有拆开这两种因素。

4.2 可中断生成：走一遍时间线

先补一点背景：为什么换了参数就得重算 KV 缓存。

KV 缓存存的是每个已写 token 在每一层的 key 和 value 向量（见 vLLM 精读 §2.2）。这些向量是用当时的模型参数算出来的。参数一换，同一段文字在新模型里的 key、value 就变了；如果继续用旧的 KV 缓存，等于让新模型读着旧模型的“记忆”往下写，结果既不是旧模型的输出，也不是新模型的输出。所以 AReaL 在换参数时丢掉旧缓存，用新参数把“题目 + 已经写下的部分”重新过一遍前向（相当于一次 prefill）。prefill 可以把整段并行算完，比逐个 token 解码快得多，这是“打断后重算”划得来的前提。

和 Kimi k1.5 的“部分 rollout”相比，区别在于触发打断的条件：部分 rollout 给每轮生成设一个固定的长度预算，到点就停；AReaL 是新参数什么时候到就什么时候打断，训练批的大小则由 buffer 保证固定。

论文没有量化的开销：每次打断都要加载新参数、为所有在写的轨迹重算 KV 缓存。回答越长、更新越频繁，这部分重算越多。论文只用 §7.5 的一组消融说明“可中断”整体上比“不可中断”快 12%–17%，没有报告加载权重和重算 KV 各占多少时间。

4.3 异步带来的两个算法难题

难题一：数据陈旧。因为是异步的，每个训练批都混有之前若干个版本的策略生成的数据。之前在 RLHF 和游戏上的异步 RL 研究都发现，陈旧数据会让学习效果变差：训练数据的分布和最新模型之间出现了差距。推理模型的问题还更严重，因为长轨迹要写很久，写完时模型可能已经更新了好几次。

5 算法：控制陈旧度，并让 PPO 适应异步数据

这一节要回答的问题：§4.3 的两个难题怎么解决？第一，能不能给样本的“陈旧程度”设一个上限，这个上限在系统里怎么执行？第二，当一个训练批里的数据来自多个版本、甚至一条轨迹也跨版本时，PPO 的目标函数应该怎么改，才能既用上这些旧数据、又不被它们拖累？

5.1 陈旧度感知训练：给“落后几个版本”设上限

为了避免在过于陈旧的数据上训练导致效果下降，AReaL 引入超参数 \(\eta\)，表示一个训练批里允许的最大陈旧度，单位是“训练步”（版本数）。\(\eta=0\) 时系统退化为同步 RL：所有样本都由当前策略生成。

这个上限不是靠事后丢弃数据来执行的，而是靠控制生成请求的发放速度。设当前策略版本是 \(i\)（已经做了 \(i\) 次训练步），到目前为止一共发出了 \(N_r\) 条生成请求，每个训练步用 \(B\) 条轨迹。每当控制器要再发一条请求，就检查：

$$\Big\lfloor \frac{N_r-1}{B}\Big\rfloor\ \le\ i+\eta$$

不满足就拒绝发出，等训练再走一步、\(i\) 加 1 之后再发。同时，组训练批时优先取 buffer 里最旧的轨迹。控制器从参数服务那里跟踪当前版本 \(i\)，自己记录 \(N_r\)。

这个式子的含义可以这样理解（本站解读）：因为训练按“先来先用”取数据，第 \(n\) 条请求大致会落在第 \(\lfloor (n-1)/B\rfloor\) 个训练步里被用掉；到那时模型的版本号就是 \(\lfloor (n-1)/B\rfloor\)。而这条请求是在版本 \(i\) 时发出的，所以它会落后 \(\lfloor (n-1)/B\rfloor-i\) 个版本。要求这个差不超过 \(\eta\)，就是上面的不等式。移项可得：在版本 \(i\) 时，最多允许发出 \(B(i+\eta+1)\) 条请求；减去已经训练掉的 \(iB\) 条，任何时刻“已发出、还没被训练”的轨迹最多 \((\eta+1)B\) 条（推算）。

5.2 解耦的 PPO 目标

先补一点背景：标准 PPO 里的 \(\pi_{\mathrm{old}}\) 其实身兼两职。

回到 §3.1 的 \(J_{\mathrm{PPO}}\)。分母里的 \(\pi_{\mathrm{old}}\) 同时扮演两个角色：（1）采样者：数据是它采的，重要性采样要除以它的概率来修正分布；（2）锚点：截断窗口以它为中心，新策略每一步只能在它附近移动。同步训练里这两个角色天然是同一个策略，所以没人区分。异步之后，采样者是好几个版本以前的旧策略，而我们希望锚点是一个较新的、质量较好的策略，两个角色就该分开了。这个思路来自 OpenAI 的 Hilton、Cobbe 和 Schulman 在 2022 年的论文《Batch size-invariance for policy optimization》，原本用于游戏 RL。

AReaL 把两个角色分别叫作：行为策略 \(\pi_{\mathrm{behav}}\)，即真正采出数据的策略；近端策略 \(\pi_{\mathrm{prox}}\)，即一个较新的策略，作为约束 \(\pi_{\theta}\) 更新的参照。对采到的轨迹做重要性采样，得到解耦的 PPO 目标：

$$J(\theta)=\mathbb{E}_{q\sim\mathcal{D},\ a_t\sim\pi_{\mathrm{behav}}}\Big[\sum_{t=1}^{H}\min\Big(\underbrace{\frac{\pi_{\theta}}{\pi_{\mathrm{behav}}}}_{\text{重要性比值}}\hat A_t,\ \ \frac{\pi_{\mathrm{prox}}}{\pi_{\mathrm{behav}}}\,\mathrm{clip}\Big(\underbrace{\frac{\pi_{\theta}}{\pi_{\mathrm{prox}}}}_{\text{信赖域中心}},1-\epsilon,1+\epsilon\Big)\hat A_t\Big)\Big]$$

因为 \(\frac{\pi_{\theta}}{\pi_{\mathrm{behav}}}=\frac{\pi_{\mathrm{prox}}}{\pi_{\mathrm{behav}}}\cdot\frac{\pi_{\theta}}{\pi_{\mathrm{prox}}}\)，而 \(\frac{\pi_{\mathrm{prox}}}{\pi_{\mathrm{behav}}}\) 是个正数，可以把它从 \(\min\) 里提出来，得到更好读的等价形式（原文式 5）：

$$J(\theta)=\mathbb{E}_{q\sim\mathcal{D},\ a_t\sim\pi_{\mathrm{behav}}}\Big[\sum_{t=1}^{H}\frac{\pi_{\mathrm{prox}}(a_t\mid s_t)}{\pi_{\mathrm{behav}}(a_t\mid s_t)}\min\big(u^{\mathrm{prox}}_t(\theta)\hat A_t,\ \mathrm{clip}(u^{\mathrm{prox}}_t(\theta),1-\epsilon,1+\epsilon)\,\hat A_t\big)\Big],\qquad u^{\mathrm{prox}}_t(\theta)=\frac{\pi_{\theta}(a_t\mid s_t)}{\pi_{\mathrm{prox}}(a_t\mid s_t)}$$

读这个式子分两层：方括号里是一个以 \(\pi_{\mathrm{prox}}\) 为中心的标准 PPO 截断项；前面乘的 \(\pi_{\mathrm{prox}}/\pi_{\mathrm{behav}}\) 是一个不参与求导的常数权重，负责把“旧策略采的数据”修正成“近端策略采的数据”。当 \(\pi_{\mathrm{prox}}=\pi_{\mathrm{behav}}\) 时，权重等于 1，式子就退回标准 PPO；同步训练（\(\eta=0\)、不打断）正是这种情况。

为什么不能直接拿行为策略当锚点？论文的解释是：异步训练里，如果以 \(\pi_{\mathrm{behav}}\) 为截断中心，最新的策略会被拉回那些旧的、质量较差的版本，模型的进步因此变慢；以较新的 \(\pi_{\mathrm{prox}}\) 为中心，更新就发生在一个高质量策略附近的信赖域里，训练更稳。下面用一个具体的 token 走一遍：

本站构造的数值例子，不是论文数据。设某个 token 当初由旧版本以 0.20 的概率采出，而经过几次更新，当前策略（也是本步的近端策略）给它 0.40。

标准 PPO 以 0.20 为中心，窗口是 0.16 到 0.24，而当前策略一开始就在 0.40，已经在窗口外。如果这个 token 的优势为正，截断项生效，它对梯度没有任何贡献，等于这条好数据被白白浪费；如果优势为负，截断不生效，梯度会把概率往 0.20 的方向使劲压，相当于把模型往旧版本拉。解耦 PPO 以 0.40 为中心，比值从 1.0 开始，在 0.32 到 0.48 的窗口里正常更新；前面乘的 2 倍权重修正了“这个 token 在旧策略下被采到的机会只有一半”这一事实。

解耦目标还顺带解决了难题二。它不再要求一个训练批里的所有数据出自同一个策略，因为每个 token 都可以有自己的 \(\pi_{\mathrm{behav}}\) 概率。这一点对“可中断生成 + 参数更新”的组合至关重要。论文用一个命题说明，跨版本接力写成的轨迹，等价于由某一个行为策略完整采出：

命题 1（原文 §5.2，证明在附录 D）。

对任意一条由版本 \(\theta_0,\dots,\theta_k\) 接力生成的序列 \((q,a_1,\dots,a_H)\)，其中第 \(j\) 个版本写了位置 \(t_j\) 到 \(t_{j+1}\) 的 token（\(1=t_0<\dots<t_{k+1}=H\)），总存在一个行为策略 \(\pi_{\mathrm{behav}}\)，使得这次被打断的生成等价于完全从 \(\pi_{\mathrm{behav}}\) 采样。

证明的思路很直接：状态里包含了“已经写了多少个 token”，所以不同位置上的状态互不重叠。于是可以按位置拼出一个策略：

$$\pi_{\mathrm{behav}}(\cdot\mid s)=\begin{cases}\pi_{\theta_j}(\cdot\mid s), & t_j\le t\le t_{j+1}\ \text{且}\ s\in\mathcal{S}_t(q)\\ \text{任意}, & \text{其他情况}\end{cases}$$

其中 \(\mathcal{S}_t(q)\) 是这道题在第 \(t\) 步可能出现的状态集合。（论文原文把各版本写作 \(\pi_{\theta},\dots,\pi_{\theta+k}\)，这里改写成 \(\pi_{\theta_j}\) 以免误读。）

这个命题说了什么、没说什么：它说明“跨版本的轨迹”在形式上仍是某个（随位置变化的）策略的样本，所以重要性采样的分母只要用“真正采出这个 token 的那个版本给它的概率”即可，PPO 的推导不需要大改。它没有说明这种拼出来的行为策略离当前策略有多远，也没有处理“打断时刻取决于系统时序、因而和回答长度相关”这一点；陈旧度带来的偏差仍要靠 \(\eta\) 和重要性权重来控制。

实际实现上的简化。Hilton 等人用参数的指数滑动平均（EMA）作为近端策略，但对大推理模型来说，再维护一份滑动平均的参数并为它做前向太贵了。AReaL 直接把每个训练步开始前的参数当作 \(\pi_{\mathrm{prox}}\)：全局批到达时，训练端先用当前参数把批里每个 token 的概率重算一遍，记为 \(\pi_{\mathrm{prox}}\)，然后再做这一步的 4 次小批更新。代价是每个训练步多一次对整个全局批的前向计算。

\(\pi_{\mathrm{behav}}\) 的概率从哪来：论文 vs 代码论文没有明说 \(\pi_{\mathrm{behav}}\) 的概率是谁算的。AReaL 现行代码（areal/utils/functional/functional.py 里的 ppo_actor_loss_fn，2026-10-20 查阅）的注释写明：开启解耦损失时，\(\pi_{\mathrm{prox}}\) 是训练端重算的对数概率，\(\pi_{\mathrm{behav}}\) 是推理引擎生成时给出的对数概率。这意味着权重 \(\pi_{\mathrm{prox}}/\pi_{\mathrm{behav}}\) 里不只有“版本落后”，还混进了推理引擎（SGLang）和训练引擎（Megatron）之间的数值差异：同一个版本的参数，两套内核、不同的批组成、不同的累加顺序算出的概率并不完全相同，即使 \(\eta=0\) 也存在。这正是后来被广泛讨论的“训推不一致”（rollout–training mismatch）问题，详见本站的 批不变性与训推一致精读。论文里的这个权重没有设上限；现行代码在它上面加了可选的截断（clamp）或拒绝（mask），注释说明这取代了早期的 behave_imp_weight_cap 选项。另外，论文实验的参数和 KV 缓存都用 FP16 而不是 BF16（原文表 3），论文没有讨论这个选择和数值一致性的关系。

6 实现：让两边都不空转的几项工程优化

这一节要回答的问题：AReaL 用了哪些现成的组件？除了异步本身，还有哪些地方会让 GPU 等待，作者分别怎么处理？变长序列在训练端为什么难以高效打包，“动态批处理”具体怎么分？

组件。AReaL 用 Python 和 PyTorch 写成，建立在作者团队此前的 RLHF 系统 ReaLHF（MLSys 2025 的 ReaL）之上。生成用 SGLang v0.4.6，训练后端用 Megatron-Core v0.11.0，资源调度用 SLURM。

把 CPU 上的活从 GPU 的关键路径上挪开。奖励计算（数学题的字符串匹配、代码题的单元测试）和基于 TCP 的数据传输都在 CPU 上做。AReaL 把它们放到单独的线程里、做成流水线，让它们和后续的生成请求重叠执行；rollout worker 内部用 asyncio 协程同时处理多个请求，避免一个请求等奖励时把别的请求也堵住。这就是摘要里说的“并行奖励服务”。

先补一点背景：微批、填充与序列打包。

一个训练步的全局批太大，放不进显存，所以要切成若干个微批（micro-batch），一个一个地做前向和反向，最后再合起来更新。传统做法把每个微批里的序列补齐到同样长度（填充，padding），补出来的位置白白占显存、白白算。无填充的序列打包则把几条序列首尾相接拼成一条长序列，用注意力掩码隔开，不浪费任何位置。打包之后，一个微批能装多少，取决于它的总 token 数，而不是序列条数。

动态批处理。推理模型的回答长短悬殊，如果按条数平均切微批，可能把几条超长序列分进同一个微批而爆显存；为了保险，只能把微批切得很多，每个微批又装不满，前向反向的次数变多。AReaL 的做法是给每个微批设一个 token 预算 \(C\)，用一个贪心算法把序列分进去（原文算法 1）：

  1. 把序列按长度从长到短排序。
  2. 依次处理每条序列：如果当前微批数还少于下限 \(k_{\min}\)，或者没有哪个微批还装得下它，就为它新开一个微批；
  3. 否则，在所有还装得下它的微批里，选序列条数最少的那个放进去。

按这个规则手算一遍：预算 \(C=32\)K token，\(k_{\min}=2\)，8 条序列长度分别为 20、18、9、6、5、3、2、1（单位 K token）。20 和 18 先各开一个微批（因为还不到 2 个）；9 两边都放得下，两边条数一样，放进第一个，得 [20, 9]；6 只有第二个放得下，得 [18, 6]；5 同理，得 [18, 6, 5]；3 两边都放得下，第一个条数更少，得 [20, 9, 3]；2 和 1 都只剩第二个放得下。最终两个微批 [20, 9, 3] 和 [18, 6, 5, 2, 1]，各 32K，正好装满（推算示例）。

7 实验：快了多少，和谁比，精度掉没掉

7.1 实验设置

  • 模型与任务。基座是 DeepSeek-R1 蒸馏出的 Qwen2 系列（R1-Distill-Qwen），从 1.5B 到 32B。数学任务用 DeepScaleR 公开的数据训练，代码任务用 DeepCoder 公开的数据训练，所有对比方法用相同的数据集。每组任务和模型训练固定的 PPO 步数，评测最后一个检查点。
  • 评测。数学按 Qwen 的评测协议，主表用 AIME24；代码用 LiveCodeBench v5（2024-08-01 至 2025-02-01 的题）。评测时最长生成 32K token，每道题采样 32 次，报告平均 pass@1。
  • 陈旧度。没有特别说明时，代码任务 \(\eta=4\)，数学任务 \(\eta=8\)。
  • 硬件。64 台机器的 H800 集群，每台 8 张 GPU，机内 NVLink，机间 RoCE，带宽 3.2 Tbps。完整实验最少用 16 台机器，模型越大机器越多，32B 模型用到 48 台。
  • AReaL 的分卡比例。固定 3/4 的卡做生成、1/4 的卡做训练。作者在早期实验里比较过 50%–50% 的分法，75%–25% 吞吐更高；但他们也承认这只是经验配置，最优比例会随设置变化，训练中动态调整可能更好。
  • 训练超参（原文表 3）。每步 512 道题、每题 16 个回答；每步 4 个 PPO 小批，截断 \(\epsilon=0.2\)；Adam，学习率 \(2\times10^{-5}\) 恒定，权重衰减 0.05，\(\beta_1=0.9\)、\(\beta_2=0.95\)，梯度裁剪 1.0；参数和 KV 缓存用 FP16，梯度和优化器状态用 FP32；采样温度 1.0、top-p 1.0；题目最长 1,024 token，回答最长 27,648 token；所有实验随机种子固定为 1。
  • 同步基线。verl 用 2025-05-07 的 main 分支；生成后端 SGLang v0.4.6、训练后端 PyTorch FSDP；在 SGLang 报错的少数情况（32B 模型或 64 台机器）改用 vLLM v0.8.4（原文附录 B.4）。
先补一点背景：“平均 pass@1”的分辨率。

每道题采样 32 个回答，算出答对的比例，再对所有题取平均，就是平均 pass@1。AIME24 只有 30 道题，所以 1 道题从全错变成全对，分数就变化约 3.3 分；表里 1 分以内的差别，相当于全卷合计多答对或少答对了约 0.3 道题（推算）。再加上每个设置只跑了一次、只用一个随机种子（论文的 NeurIPS 自查表明确说没有报告误差条），1 分左右的差别不宜解读成谁好谁坏。

论文的结论是：在所有设置下，AReaL 的吞吐随卡数大致线性增长，而同步系统往往扩展不上去；AReaL 在多数设置下超过基线，最多快 2.5 倍。作者补充了两点观察。第一，上下文较短时 AReaL 的优势变小，因为生成速度跟不上训练速度：生成出来的序列虽多，却没能被训练有效消耗。第二，回答越长，AReaL 越占优，因为异步加可中断生成把长回答的生成时间完全藏在了关键路径之外，生成长度增加不会明显拖慢有效训练吞吐。

读这张图要注意：
  • “近似线性”说得偏宽。按读图约数，32B 从 256 到 512 卡的扩展效率在 92%–96%，确实接近线性；但 1.5B 和 7B 在卡数翻 8 倍时只有 55%–63%（推算）。verl 同期只有约 25%–35%，所以“AReaL 扩展性更好”成立，“线性扩展到 512 卡”主要对 32B 成立。
  • 最小规模时两者差不多，7B · 16K 在 64 卡时 verl 甚至更快（约 22k 对 19k）。异步的收益主要在卡多、回答长的时候体现。
  • 两边的训练后端不同（AReaL 用 Megatron-Core，verl 用 FSDP），生成后端在部分设置下也不同（32B 或 64 台机器时 verl 换成了 vLLM）。图 4 的差距里有多少来自“异步”、多少来自后端，论文没有拆开；表 1 里和同步版 AReaL 的比较才是控制了后端的对照。
  • 有效吞吐只数“被训练消耗的 token”，不反映陈旧数据的学习效率。吞吐高不等于同样时间学得更多，这要看 §7.4。

可中断生成。关掉可中断生成后，控制器必须等最长的回答写完才能推进。在 4 台机器上，可中断生成让 1.5B 和 7B 的生成吞吐分别提高 12% 和 17%。

7.7 结果的份量

把上面的数字放在一起，这篇论文的实验能支撑什么、不能支撑什么，可以这样概括：

  • 对照组。摘要的“最多 2.77 倍”是相对作者自己的同步版 AReaL（很可能是 \(\eta=0\) 的分离部署），这个基线在四个规模上都比 verl 的估计时间慢 10%–22%。相对 verl，训练时间缩短 1.49–2.27 倍（推算）。verl 用的是 2025-05-07 的 main 分支，当时它还没有异步模式；它的训练小时数是按吞吐估算的，不是真跑完 250 步测出来的。
  • 精度的对照并不完全匹配。verl 那一行的精度（43.1、57.9）引自 DeepScaleR 和 DeepCoder 公开的模型，它们的训练配方和本文不同：据 DeepScaleR 的模型卡，它用 A100 分三段把上下文从 8K 拉长到 16K 再到 24K，前后训练了 1,500 多步，每步 128 道题 × 8 或 16 个回答；据 DeepCoder 的模型卡，它用改进版 GRPO 从 16K 训练到 32K，57.9 是在 32K 上下文下的评测分数（64K 下为 60.6）。所以表 1 的 verl 一行把“别人的精度”和“本文估算的时间”放在了一起，真正控制了配方的精度对照只有“AReaL 对同步版 AReaL”。
  • 硬件与规模。所有对比都在同一个 H800 集群上、用相同的机器数完成（16 到 48 台）；H800 是 H100 面向中国市场的出口版本，主要区别在卡间 NVLink 互联速度等方面。换成别的硬件或更小的集群，倍数会变：§7.3 显示卡数最少时两者差不多。
  • 指标。表 1 是“固定步数下的训练小时数”，所以倍数等于每步耗时之比，并不是“达到同样精度所需的时间”之比；图 4 和图 5c 是“有效训练吞吐”，不计陈旧数据的学习效率。好在表 1 和表 2 显示固定步数下精度基本持平，两种口径的结论大体一致。
  • 统计可靠性。每个设置只跑一次，随机种子固定为 1，没有误差条。表 2 里 \(\eta=4\) 不解耦的崩溃、附录里 \(\eta\) 之间的分数波动都说明单次运行的噪声不小；1 分左右的精度差别不宜过度解读。
  • 适用范围。实验全部是单轮的数学和代码任务、稠密模型、最长约 28K token 的回答。多轮交互、工具调用、MoE 模型，以及训练中回答长度剧烈增长的场景（从基座直接训练），都不在实验范围内。
  • 没有报告的开销。加载新权重和重算 KV 缓存的时间、replay buffer 占用的资源、每步额外一次前向（重算 \(\pi_{\mathrm{prox}}\)）的成本，论文都没有单独给出。

8 结论与局限

这一节要回答的问题：作者认为这篇论文贡献了什么？他们自己承认的局限有哪些？还有哪些问题是论文没有触及的？

结论。AReaL 是一个为大规模 RL 训练设计的完全异步系统。它的架构足够灵活，能表达异步算法；在这个基础上，作者提出了陈旧度感知的训练和解耦的 PPO 目标，让 PPO 在异步环境下也能高效、稳定地训练。实验显示，相比同步 RL 系统，AReaL 在硬件效率、样本效率和扩展性上都更好。作者希望它能成为可靠扩展 RL 训练的一个起点。

作者承认的局限（原文附录 E）。第一，生成卡和训练卡的比例还可以针对具体训练设置进一步优化，并且可能值得在训练中动态调整，尤其是从基座模型出发训练时，回答长度通常会一路变长。第二，评测只覆盖了单步的数学和代码任务；作者认为 AReaL 的架构并不局限于此，多轮交互和智能体场景留给后续工作。

本站补充的几点。其一，异步的收益取决于“生成和训练能否互相掩盖”：如果某个阶段远比另一个慢，分离部署下快的一方仍会等待，这正是 §7.3 里短上下文时 AReaL 优势变小的原因，固定 3:1 的分卡比例对此无能为力。其二，解耦目标里的权重 \(\pi_{\mathrm{prox}}/\pi_{\mathrm{behav}}\) 没有设上限，陈旧度大时可能出现极端权重，论文靠 \(\eta\) 把它压在可控范围；后续工作（见下一节）正是从这里继续推进的。其三，\(\pi_{\mathrm{behav}}\) 的概率来自推理引擎，引擎之间的数值差异会被一并当作“离策略”处理，论文没有讨论这一层。

后来怎么样了

AReaL 本身转向了智能体 RL。论文对应的是 2025 年 6 月发布的 AReaL v0.3（代号 boba²），仓库 README 宣传的正是“2.77 倍加速、精度持平或更好”。此后的演进据 README 记载：2025 年 7 月推出 AReaL-lite，一个以算法为先的轻量版本，原生支持完全异步的智能体 RL，README 称它用少 80% 的代码保留了 90% 的性能和核心功能；2025 年 8 月，同一团队用 AReaL 的完全异步 RL 训练了搜索智能体 ASearcher（arXiv 2508.07976），训练时单条轨迹的工具调用超过 100 轮、输出超过 40 万 token，这类超长、超不均匀的轨迹正是异步架构最能发挥的场景；2026 年 1 月起支持华为昇腾 NPU；2026 年 7 月发布 AReaL 2.0，把系统重构为训练、推理、智能体、权重更新四个独立的微服务，并配有一篇讨论“面向自我进化智能体的在线 RL 系统”的技术报告（arXiv 2607.01120）。仓库也从 inclusionAI 组织迁到了 areal-project 组织，自我定位改成“连接大模型智能体应用的 RL 桥梁”。截至 2026-10-20，仓库有 5,855 个 star、634 个 fork。

异步 RL 成了主流框架的标配。本文的同步基线 verl 后来也加入了实验性的 one_step_off_policy（错开一步）和 fully_async_policy（完全异步）模块（位于仓库的 verl/experimental/ 目录，2026-10-20 查阅）。同一时期的其他系统各有侧重：Meta 的 LlamaRL（arXiv 2505.24034）在 Llama 3 后训练中使用异步离策略训练，报告在 405B 模型上比 DeepSpeed-Chat 类系统最多快 10.7 倍；PipelineRL（arXiv 2509.19128）同样在生成过程中“飞行换权重”，在 128 张 H100 上报告学习速度约快 2 倍，同时让数据尽量保持同策略；本文引用的同期工作 StreamRL（arXiv 2504.15930）则把生成拆成独立的流式服务。在本站的 HybridFlow 精读里可以看到同步一侧的设计。

陈旧度能放多大，成了一个算法问题。本文的结论是 \(\eta\) 不能无限大，解耦目标在 \(\eta\to\infty\) 时也会掉点。后来的 M2PO（arXiv 2510.01161，“Prosperity before Collapse”）认为，陈旧数据只要用对方法，信息量可以和同策略数据相当：它约束重要性权重的二阶矩，只压制极端的离群权重，报告在数据陈旧至少 256 次模型更新的情况下仍能稳定训练，并在 1.7B 到 32B 的六个模型上达到同策略训练的水平。

训推不一致被单独拎出来研究。§5.2 的代码注释提到，\(\pi_{\mathrm{behav}}\) 的概率来自推理引擎。2025 年 8 月，Feng Yao、Liyuan Liu 等人的博客指出，即使在同步框架里，推理引擎（如 vLLM）和训练引擎（如 FSDP）对同一版参数给出的概率也不一样，同策略 RL 因此悄悄变成了离策略，并提出用截断重要性采样（TIS）来修正，后来整理成论文《On the Rollout-Training Mismatch in Modern RL Systems》。2025 年 9 月，Thinking Machines 的博客从推理引擎的内核层面解释了这种不确定性的来源，并给出“批不变”的内核。蚂蚁百灵团队的万亿参数推理模型 Ring-1T（arXiv 2510.18855）提出 IcePop，按 token 屏蔽和截断训推差异过大的位置；另一篇论文（arXiv 2510.26788）则认为根源在 BF16 的舍入误差，改用 FP16 就能基本消除不一致。有意思的是，AReaL 论文的实验恰好用的是 FP16 参数和 KV 缓存，不过论文没有讨论这一点。AReaL 现在的代码也加入了 IcePop 和自家的 KPop 屏蔽方式（README，2026 年 6 月）。这一条线的来龙去脉见本站的 批不变性与训推一致精读。

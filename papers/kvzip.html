0 导读：这篇论文解决什么问题

大模型读长文档、记长对话时，要把上下文里每个 token 在每一层的 key 和 value 向量存下来，这份数据叫 KV 缓存。上下文越长，它越大：论文里 LLaMA3.1-8B 处理 12.4 万个 token 时，KV 缓存就有 16.3 GB，和模型参数本身差不多大；而且每生成一个 token，都要把它从显存里整个读一遍。所以 KV 缓存既占显存，又拖慢生成。

压缩 KV 缓存的一大类办法叫淘汰（eviction）：给每个 KV 打一个“重要性”分数，扔掉分数低的。此前最好用的淘汰方法，比如 SnapKV，都是按问题打分的：看用户的问题在关注上下文的哪些位置，就留哪些。只答一个问题时这很有效。但现实里同一份上下文常常要回答很多个问题：同一份文档被反复提问，一段长对话要接着聊，推理引擎的前缀缓存让很多请求共用同一段前缀。按第一个问题挑出来的 KV，拿去回答第二个问题就不够用了。论文在 SQuAD 上测到，保留 30% 的 KV 时，SnapKV 每个问题重新算一遍能答对约 91%，复用第一个问题压缩出的缓存就只剩约 65%（读图）。

KVzip 的想法是换一个与问题无关的打分标准：让模型把原文复述一遍，看复述时它查了哪些 KV。如果一份压缩后的缓存能让模型把原文完整地复述出来，那它原则上就保住了回答任何问题所需的信息。具体做法是在缓存后面接一句“Repeat the previous context:”和原文本身，用一次前向（教师强制）模拟复述，记下每个 KV 在这次前向里收到的最大注意力，作为它的分数，然后扔掉分数最低的那些。打分只依赖上下文本身，所以压缩一次，之后任何问题都可以直接用。

论文报告：KV 缓存缩小到原来的 1/3–1/4，FlashAttention 解码时的注意力延迟降到约一半，在问答、检索、数学推理、代码理解等 12 个数据集上几乎不掉点；而 H2O、SnapKV、PyramidKV 在同样“与问题无关”的设定下，保留 90% 时在部分检索任务上就已经明显掉点。它可以和 4 bit KV 量化叠加（16.3 GB 降到 1.2 GB）；它还能给每个模型算一份“按头”的静态分数，替代 DuoAttention 那种需要在 8 张 GPU 上优化几个小时的头分数，而只需要一分钟内的几次前向。

代价也要先说清楚。第一，打分要额外做一遍“复述”前向，计算量约为一次预填充的 2 倍（12.4 万 token 时约 66 秒，预填充约 31 秒，读图），只有当压缩后的缓存被反复使用时才划得来。第二，“约 2 倍”指的是单层注意力内核的延迟，不是端到端的生成速度。第三，“几乎不掉点”在 Qwen 系列上成立于保留 30%，在 LLaMA3.1-8B 上要保留约 40%。第四，对比的基线是被放到“没有问题可看”的设定里运行的，并不是它们设计时的用法。第五，截至 2026-10 没有看到主流推理引擎原生集成它。这些都会在后面逐一展开。

1 引言：一份缓存，要回答很多个还没出现的问题

这一节要回答的问题：长上下文让 KV 缓存变得又大又慢，已经有很多压缩方法，为什么还要再提一个？论文的理由是：现有的淘汰方法都根据“眼前这个问题”来决定留哪些 KV，而在多问题、缓存复用的场景里，这样挑出来的缓存会“过拟合”第一个问题。那么，能不能不看问题、只看上下文本身，就挑出一份对所有未来问题都够用的缓存？
先补一点背景：KV 缓存是什么，有多大。

大模型生成文字分两个阶段。预填充（prefill）把整段输入一次性算完，算出每个 token 在每一层、每个注意力头上的 key 向量和 value 向量；解码（decode）每一步只算一个新 token，它的 query 要和前面所有 token 的 key 做注意力，再按权重把它们的 value 加起来。前面 token 的 key 和 value 不会变，所以存下来反复用，这就是 KV 缓存（详细推导见 vLLM 精读 §2.2）。

KV 缓存的大小可以直接算出来：

$$\text{KV 字节数}=\underbrace{2}_{\text{key 和 value}}\times\underbrace{L}_{\text{层数}}\times\underbrace{H}_{\text{KV 头数}}\times\underbrace{d_{\text{head}}}_{\text{头维度}}\times\underbrace{b}_{\text{每个数的字节}}\times\underbrace{n_{c}}_{\text{token 数}}$$

以论文主要用的 LLaMA3.1-8B 为例：32 层、8 个 KV 头、头维度 128、FP16 每个数 2 字节，每个 token 的 KV 是 \(2\times32\times8\times128\times2=131{,}072\) 字节，即 128 KiB。12.4 万个 token 就是约 16.3 GB（推算），和论文图 8 里测到的 16.3 GB 一致。这个模型的参数在 FP16 下约 16 GB，所以上下文到十几万 token 时，KV 缓存和参数一样大。下面的计算器可以换别的模型和长度试一试。

论文开头举的例子是 Qwen2.5-14B：缓存 12 万个 token 约需 33 GB，超过了模型自身约 28 GB 的参数。KV 缓存大，带来两个直接的后果：一是显存被它占满，同一张卡能同时服务的请求变少；二是解码时每一步都要把它读一遍，注意力的耗时随上下文长度线性增长。

一个对不上的数字：按 Qwen2.5-14B 的公开配置（48 层、8 个 KV 头、头维度 128）推算，FP16 下每个 token 的 KV 是 192 KiB，12 万个 token 约 23.6 GB，而不是论文写的约 33 GB；论文没有给出计算口径。不过结论不受影响：按这个推算，上下文到约 14 万 token 时，KV 缓存就和 28 GB 的参数一样大了。

已有的压缩办法大致分几类：把多个注意力头合并成共享 KV 的分组（GQA），把 KV 压成更短的序列（Compressive Transformer 一类，需要训练），用滑动窗口只保留最近的一段，以及利用注意力的稀疏性做淘汰：在解码阶段边生成边淘汰（H2O、Scissorhands 等），或在预填充结束时一次性淘汰（SnapKV、PyramidKV）。论文关注的是最后一类。这类方法有一个共同点：重要性分数是在推理时、结合眼前的问题在线算出来的。

先补一点背景：按问题压缩，与“一份上下文、很多个问题”的场景。

以 SnapKV 为例（细节见 SnapKV 精读 §4）：用户的问题放在长提示的最后，SnapKV 看提示最后 32 个 token（叫观察窗口，通常就是问题本身）对前面每个位置的注意力，按“得票”多少挑出要保留的 KV。问题在关注哪里，就留哪里。这样做的前提是：压缩时已经知道问题。

可是很多服务场景里，同一份上下文的 KV 缓存要被很多个问题用：

  • 多轮对话与个人助手。用户的资料、长长的系统指令、聊天记录要在多轮对话里一直保留。论文引用了 Character.AI 的推理优化博客，这类服务会跨轮次保留对话的 KV 缓存。
  • 前缀缓存。推理引擎会把相同前缀的 KV 缓存留下来给后续请求复用，比如 SGLang 的 RadixAttention 和 vLLM 的自动前缀缓存（见 SGLang 精读 §3.1）。被缓存的前缀，后面跟的问题各不相同。
  • 预先算好的文档缓存。企业知识库可以把文档的 KV 缓存提前算好存起来，用户提问时直接加载，省掉预填充（论文引用了“缓存增强生成”CAG 的工作）。KV 缓存甚至可以放到 CPU 内存、SSD 或远端存储里，按需取回（见 Mooncake 精读 与 KV 缓存分层存储）。

在这些场景里，压缩时根本还不知道将来会被问什么。论文把“不依赖问题”的压缩叫 query-agnostic（本页译作“与问题无关”），把 SnapKV 这类叫 query-aware（“按问题”）。

论文还强调，把现有方法直接搬到“与问题无关”的框架里（压缩时不给问题）效果也不好，因为它们的打分本来就是为“有问题可看”设计的（§4 会看到具体数字）。

KVzip 的出发点是一个类比：Transformer 预填充时把上下文“编码”成 KV 缓存，就像 Zip 把文件压缩成一个压缩包；一个好的压缩包，应该能解压出原文件。所以论文提出，能让模型复原原文的那一小部分 KV，就是上下文的一个好的压缩表示。具体打分方法是用一次前向模拟“复原原文”，以每个 KV 在这次前向中收到的最大注意力作为它的重要性。论文把这和“靠重建输入来学表示”的自监督学习（BERT、MAE、GPT）相类比：重建任务学到的东西，往往能迁移到各种下游任务。

压缩之后，后续问题就享受更小的缓存和更快的注意力：论文报告 KV 缓存缩小 3–4 倍、FlashAttention 解码延迟降低约 2 倍。KVzip 支持两种用法：与上下文有关的淘汰（每份上下文单独打分，压得更狠，但每份上下文都要付一次打分开销）；与上下文无关的淘汰（每个模型只打一次分，得到每个头的静态分数，部署后没有任何额外开销，但只能压到中等程度）。实验覆盖 12 个数据集、3B 到 14B 的模型、最长约 17 万 token 的上下文，并展示了与 KV 量化、按头淘汰的结合：用几次前向、一分钟以内就能替代 DuoAttention 需要几十个 GPU 小时的头分数优化。

两个容易混淆的词：“与问题无关”（query-agnostic）不等于“与上下文无关”（context-independent）。KVzip 的主要模式是前者：分数不依赖将来的问题，但依赖这份上下文，所以每来一份新上下文都要重新打一次分。只有“按头”的静态模式才是与上下文无关的，那时分数只依赖模型。后面讨论开销能否摊薄时，这个区别至关重要。

2 预备：问题怎么写成公式，现有方法为什么复用不了

这一节要回答的问题：“压缩后的缓存对任何问题都够用”能不能写成一个明确的目标？SnapKV、PyramidKV 这类方法离这个目标差在哪里，有没有直接的实验证据？

2.1 记号与目标

先补一点背景：分组查询注意力（GQA）里的“头”。

标准的多头注意力里，每个查询头都有自己的一组 key 和 value。GQA 为了省 KV 缓存，让 \(G\) 个查询头共用一个 KV 头：模型一共有 \(H\) 个 KV 头，查询头是 \(H\times G\) 个。比如 LLaMA3.1-8B 有 32 个查询头、8 个 KV 头，\(G=4\)；Qwen2.5-7B-1M 有 28 个查询头、4 个 KV 头，\(G=7\)。KV 缓存只按 KV 头存，所以它的大小由 \(H\) 决定。

论文把模型记作 \(f_{\text{LM}}\)，有 \(L\) 层，每层 \(H\) 个 KV 头，每个 KV 头被 \(G\) 个查询头共享，生成时用贪心解码。上下文 \(c\) 有 \(n_{c}\) 个 token，预填充后得到的缓存 \(\mathrm{KV}_{c}\) 里一共有 \(L\times H\times n_{c}\) 个 KV 对：每个 KV 对是“某一层、某一个 KV 头、某一个位置”上的一个 key 向量加一个 value 向量。淘汰的最小单位就是一个 KV 对，所以同一个位置可以在这个头上被扔掉、在那个头上被保留。

目标是找一个更小的子集 \(\mathrm{KV}_{c,\text{evicted}}\subseteq\mathrm{KV}_{c}\)，使得对任意问题 \(q\)，模型基于它生成的回答和基于完整缓存的一样：

$$f_{\text{LM}}\big(q\mid \mathrm{KV}_{c,\text{evicted}}\big)\approx f_{\text{LM}}\big(q\mid \mathrm{KV}_{c}\big),\qquad \forall q\in\mathcal{T}\tag{1}$$

这里 \(\mathcal{T}\) 是所有文本的集合。式 (1) 的关键是“任意 \(q\)”：按问题压缩的方法只保证对某一个已知的 \(q\) 成立。

式 (1) 是目标，不是保证：“对所有问题都近似相等”没法直接验证，论文也没有给出任何理论界。后面所有证据都是经验性的：在 12 个数据集、每个上下文多个问题上测出来“基本相等”。

2.2 现有方法：按问题打分，换了问题就失灵

先补一点背景：三种被拿来对比的淘汰方法。
  • H2O（NeurIPS 2023）发现少数 token 会持续收到大量注意力（“重击手”，heavy hitters），于是按累计注意力给 token 打分，解码时边生成边淘汰。KVzip 论文实现的是它的“预填充版”：在预填充时，用每个 KV 收到的最大注意力打分（附录 A 说最大值比平均值效果好）。它和 KVzip 的唯一区别是：注意力来自预填充本身，而不是来自复述。
  • SnapKV（NeurIPS 2024）用提示末尾的观察窗口（默认 32 个 token）给前面的位置投票，再做核大小为 7 的最大池化，把选中位置的邻居也一起留下（见 SnapKV 精读）。
  • PyramidKV 在 SnapKV 的基础上，让低层多留、高层少留，层间预算线性递减。

后两者的打分都来自“提示的最后一小段”。如果最后一小段就是用户的问题，打分就是按问题打的。

论文用 SQuAD 的多问题数据（一段短文配多个问题）做了一个直接的实验，模型是 LLaMA3.1-8B。三条曲线分别是：SnapKV 每个问题都把“上下文+问题”重新预填充、重新压缩；SnapKV 只压缩一次（按每个样本的第一个问题），后面的问题复用这份缓存；KVzip 只预填充一次、与问题无关地压缩。下图按原文图 2 的数据重画：

这张图说明了两件事。第一，SnapKV 的打分本身没有问题：只要每次都针对当前问题重新压缩，它在 SQuAD 上几乎不掉点。问题出在复用：第一个问题关注的位置，和第二、第三个问题关注的位置不一样，按第一个问题挑出的 KV 里，缺了后面问题需要的内容。SnapKV 论文自己也观察到，不同的问题会让模型看不同的位置（见 SnapKV 精读 §4.2）。第二，每问重做虽然准，但每个问题都要把整段上下文重新预填充一遍，长上下文时这个代价很高。KVzip 想要的是两全：只预填充一次，又对每个问题都准。

3 方法：让模型复述原文，看它查了哪些 KV

这一节要回答的问题：不知道将来的问题，凭什么判断哪个 KV 重要？KVzip 的回答是“复述原文时用得上的 KV 就重要”。这个想法怎么变成一个可以计算的分数？为什么这个分数能推广到各种任务？长上下文下怎么算得动？分数算出来以后，按什么粒度淘汰？

和以往的淘汰方法一样，KVzip 的核心是给每个 KV 对一个重要性分数：对长度为 \(n_{c}\) 的上下文，算出 \(S\in\mathbb{R}^{L\times H\times n_{c}}\)，然后扔掉分数最低的那些。分数怎么用有几种选择：各个头可以留不同数量（非均匀预算），也可以留同样数量（均匀预算）；还可以把一个头在整条序列上的最大分数当作这个头的分数，按头整体淘汰。下面先讲分数怎么来。

3.1 直觉：Transformer 是一台“压缩—解压”机器

要回答任意问题，压缩后的缓存加上模型本身，必须还保有上下文的全部信息。怎么检验“全部信息还在”？论文的办法是：直接让模型基于压缩后的缓存，把原文复述出来。如果能一字不差地复述，那就说明信息都在，因为原则上可以把复述出来的原文重新预填充一遍，得到完整的缓存，再去回答任何问题。

示意图：把预填充看成“压缩”，把复述看成“解压”
上下文 \(c\)原始文本，\(n_{c}\) 个 token→ 预填充 →\(\mathrm{KV}_{c}\)完整缓存，好比“压缩包”→ 淘汰 →\(\mathrm{KV}_{c,\text{evicted}}\)只剩一小部分 KV→ 解码 →提示“Repeat the previous context:”能否原样复述出 \(c\)？
本站示意图，对应 原文图 3 ↗。论文的类比：Transformer 天然像一个编码器—解码器，预填充把上下文编码进 KV 对，就像 Zip 把文件压缩进压缩包。

但真的在每次推理时先复述、再重新预填充，代价太大，没有意义。论文的经验发现是：不需要真的复原。只要按“复述时用得上”的标准挑出 KV，这份压缩缓存直接拿去回答各种问题，效果就已经很好（§4）。论文把这和自监督学习相类比：BERT、MAE、GPT 都是靠“把输入重建出来”训练的，重建任务学到的表示能推广到各种下游任务；同样，对重建原文关键的 KV，对各种下游任务也关键。

这是动机，不是论证：KVzip 从不检查“淘汰之后模型还能不能复述原文”。它只是在完整缓存上模拟一次复述，记下复述时每个 KV 被看了多少，然后按这个分数淘汰。“能复述就能回答任何问题”这个推理也只在“复述后重新预填充”的意义下成立，而 KVzip 并不这样做。所以真正支撑方法的是实验，不是这段直觉。

3.2 打分：一次前向完成“复述”，记下每个 KV 被看的最大注意力

先补一点背景：教师强制。

让模型一个 token 一个 token 地把原文生成出来，要做 \(n_{c}\) 步串行的解码，很慢。教师强制（teacher forcing）是训练语言模型时的标准做法：不让模型用自己生成的 token 接着往下写，而是直接把“正确答案”整段喂进去，模型在每个位置上预测下一个 token。因为整段输入都已知，所有位置可以在一次前向里并行算完，就像预填充一样。KVzip 用的正是这个技巧：既然要模拟的“复述”就是原文本身，那就把原文作为正确答案整段喂进去，一次前向就模拟完了整个复述过程。

具体地，打分时的输入序列是“复述提示 + 原文”，长度 \(n_{\text{in}}=n_{\text{prompt}}+n_{c}\)。这段输入接在已经存好的 \(\mathrm{KV}_{c}\) 后面做一次前向。在第 \(l\) 层、第 \(h\) 个 KV 头上，输入的 query 是 \(Q_{l,h}\in\mathbb{R}^{G\times n_{\text{in}}\times d}\)（\(G\) 个查询头），可以被看的 key 是 \(K_{l,h}\in\mathbb{R}^{(n_{c}+n_{\text{in}})\times d}\)（前面是缓存里的 \(n_{c}\) 个，后面是输入自己的 \(n_{\text{in}}\) 个）。注意力矩阵是

$$A_{l,h}=\mathrm{Softmax}\big(Q_{l,h}K_{l,h}^{\top}\big)\in\mathbb{R}_{+}^{G\times n_{\text{in}}\times(n_{c}+n_{\text{in}})}$$

（论文公式省略了除以 \(\sqrt{d}\)，官方代码里有。）只取其中对应 \(\mathrm{KV}_{c}\) 的那 \(n_{c}\) 列，得到切片 \(\bar{A}_{l,h}\in\mathbb{R}_{+}^{G\times n_{\text{in}}\times n_{c}}\)。第 \(j\) 个上下文位置的分数，是它在所有 \(G\) 个查询头、所有 \(n_{\text{in}}\) 个输入位置上收到的最大注意力：

$$S_{l,h}[j]=\max_{g=1,\dots,G;\ i=1,\dots,n_{\text{in}}}\ \bar{A}_{l,h}[g,i,j],\qquad j=1,\dots,n_{c}\tag{2}$$

论文把这些分数叫“最大交叉注意力分数”。这里的“交叉注意力”不是指编码器—解码器结构里的那个模块，而是借用这个词，指“复述输入”对“缓存里的原文”的注意力：查询来自一段序列，被查的 key 来自另一段序列。分数小的 KV，说明复述时几乎没人看它，就先被淘汰。依据是 H2O 等工作的经验：几乎收不到注意力的 KV，对 Transformer 的计算贡献很小。

为什么取最大值，而不是求和或平均？论文没有专门论证，本站的理解是这样的：复述时，一个 KV 可能只在某一步被需要一次，比如在抄写一个罕见的人名或一串数字时，那一步的 query 会几乎全部注意力都压在它身上，其余各步完全不看它。如果用平均值，这个“只被需要一次但非用不可”的 KV 会被大量不看它的行稀释成一个小分数，就可能被误删。取最大值则保证：只要有任何一步非常依赖它，它就会被留下。附录 A 也提到，对 H2O 他们同样改用了最大值，因为在实验里比平均值好。

补充背景（本站补充，不是论文内容）：模型是怎么“抄写”的。

可解释性研究发现，Transformer 里普遍存在一类“归纳头”（induction heads，Anthropic 2022 年的工作）：当序列里出现“…A B … A”时，这类头会在第二个 A 的位置上，去查找前文里 A 后面紧跟的那个 token（也就是 B），把它“抄”过来作为预测。复述原文正是这种机制最极端的用法：复述到第 \(t\) 个 token 时，模型要找到原文里第 \(t\) 个 token 后面的那个 token。这能解释为什么复述时的注意力那么集中：每一步都精确地指向原文里的某一个位置；也能解释为什么能被语法、常识猜出来的 token（如上图的 is、in）收到的注意力少，因为模型不需要回头看也能写对。

论文 vs 官方代码：打分的几处细节
  • 复述提示的措辞。论文写的是 “Repeat the previous context:”；官方代码（model/wrapper.py 的 self_task）用的是 “Repeat the previous context exactly.”，并在后面接上模型的对话模板（比如 Qwen 的 <|im_end|> 加 assistant 开头），让复述像是模型的一次回答。附录 C.2 显示措辞几乎不影响结果（§4.6）。
  • softmax 在哪些 key 上归一化。代码里每一块打分时，softmax 只在“系统提示 + 这一块原文 + 复述输入自己”这些 key 上做（attention/score.py 的 _get_score），并除以 \(\sqrt{d}\)。这是 §3.4 分块打分的结果。
  • 系统提示永远保留。对话模板里系统提示的 KV 不参与打分、也不被淘汰（代码里叫 sink，即“注意力汇”）；问题和回答的 KV 追加在后面，也不被淘汰。
  • 阈值是全局取的。代码的 _threshold 把所有层、所有头的分数放在一起排序，取一个统一的阈值。所以不只是同一层的各个头，不同层留下的比例也不一样。§4.1 会说到这对对比公平性的影响。

3.3 观察：复述时的注意力更稀疏，而且覆盖了各种任务要看的地方

论文用两组观察来说明这个分数为什么好用。

第一，复述时的注意力很稀疏。原文图 5 在 SQuAD 上用 LLaMA3.1-8B，比较了 \(\mathrm{KV}_{c}\) 里每个 KV 收到的最大注意力在两种情况下的分布：一种来自预填充（上下文自己看自己，即 H2O 的打分来源），一种来自复述。复述时的分数大多挤在 0 附近，只有少数 KV 拿到高分；预填充时的分数则分布得更散。论文的解释是：预填充时，模型要让每个 token 和其他 token 充分交互，才能把上下文的信息编码进去，所以注意力是“密”的；复述时，模型既可以利用缓存里已经编码好的高层表示，也可以利用权重里自带的语言知识，于是只需要很少几次精确的查找。分数越稀疏，就越容易分出哪些 KV 可以扔，这也是 KVzip 胜过 H2O 的原因。

第二，复述关注的位置，覆盖了其他任务关注的位置。原文图 6 是几张二维直方图：横轴是每个 KV 在复述时的分数，纵轴是它在另一个任务（问答、摘要、GSM8K 推理）里的分数，每个任务的输入是“问题 + 模型生成的回答”（附录表 3、表 4 给了具体文本）。复述对问答、复述对摘要、复述对推理的三张图里，点都集中在对角线右下方，意思是：在其他任务里被看得多的 KV，在复述时也被看得多，反过来却不一定。第四张图是两个不同问题互相比较，点集中在两条坐标轴上：一个问题看的位置，另一个问题基本不看。这正是按问题压缩不能复用的原因，也是复述打分能代替它们的原因。

3.4 难点：长上下文下怎么算得动——分块打分

先补一点背景：FlashAttention 为什么不存注意力矩阵，以及式 (2) 为什么和它冲突。

注意力矩阵的大小是“查询数 × key 数”，上下文 12 万 token 时，一个头的矩阵就有上百亿个元素，根本存不下。FlashAttention 的做法是把矩阵切成小块，在片上的 SRAM 里一块一块地算，用“在线 softmax”一边算一边修正归一化系数，最后直接得到输出，整个矩阵从不完整地写回显存（见 FlashAttention 精读 §3.1）。它能这样做，是因为 softmax 只沿着一行（同一个 query 对所有 key）归一化，而输出也是按行算的。

式 (2) 偏偏要两个方向：先沿 key 方向做 softmax 得到真正的概率，再沿 query 方向（同一个 key 被所有 query 看的那一列）取最大值。一个 key 的最终分数要等到所有行都归一化完才能确定，这和 FlashAttention“按行一块块算、不留中间结果”的组织方式是交叉的，所以没法直接塞进现成的融合内核里。

论文的解决办法是分块打分：不一次性复述整篇上下文，而是把它切成长度为 \(m\) 的块（论文固定 \(m=2\text{K}\)），一块一块地复述。第 \(i\) 块的打分输入是“复述提示 + 第 \(i\) 块原文”；从第 2 块起，提示改成 “Repeat the previous context starting with ⟨上一块的最后 8 个 token⟩:”，告诉模型从哪里接着复述。这段输入（长度 \(n_{\text{in}}\approx m\)）照常做一次完整的前向，模型自己的注意力仍然能看到整个 \(\mathrm{KV}_{c}\)。只是在打分时，只取出第 \(i\) 块对应的那 \(m\) 个 key（加上输入自己的 key），在这个 \(n_{\text{in}}\times(m+n_{\text{in}})\) 的小矩阵上显式地算 softmax，再按式 (2) 取最大值，得到第 \(i\) 块里 \(m\) 个位置的分数。所有块都做完，就拼出了完整的分数。

分块带来一个隐含的近似：第 \(j\) 块里的 key，只被“复述第 \(j\) 块”的那些 query 打分，复述别的块时它被看了多少不计入。因为复述某一块时，模型主要在原文的这一块里找要抄的 token，这个近似损失很小；附录 C.1 测了 1K、4K、8K 三种块大小相对 2K 的差别，在保留 30% 时平均相对差都在 2% 左右以内，所以论文把 2K 固定用于所有模型、长度和任务。

复杂度要分两部分看。打分本身：每块的小矩阵是 \(O(m^{2})\)，共 \(n_{c}/m\) 块，总共 \(O(mn_{c})\)，随上下文长度线性增长；峰值显存是 \(O(m^{2})\)，和上下文多长无关。但为了得到 query，每块都要做一次完整的前向，而这次前向的注意力要读完整的 \(\mathrm{KV}_{c}\)：

$$\underbrace{\frac{n_{c}}{m}}_{\text{块数}}\times O\!\Big(n_{c}m+\frac{m^{2}}{2}\Big)=O\!\Big(n_{c}^{2}+\frac{n_{c}m}{2}\Big)\qquad\text{对比预填充的因果注意力}\quad O\!\Big(\frac{n_{c}^{2}}{2}\Big)$$

为什么是 2 倍？预填充时第 \(t\) 个 token 只看前面 \(t\) 个 token，平均每个 token 看 \(n_{c}/2\) 个 key；复述时每个复述 token 都要看全部 \(n_{c}\) 个原文 key，再加上自己前面的复述 token，平均看的 key 数是预填充的约 2 倍。所以注意力部分的计算量约为一次预填充的 2 倍。分块控制住了显存，却没有减少这部分计算。

附录 C.3 还给了一个“去掉 softmax”的变体：打分环节约占整个前向时间的 10%，如果直接用 FlashAttention 内部已经算出来的 \(QK^{\top}\) 原始分数（logit）代替归一化后的概率，就可以用一个定制的 Triton 内核把打分融合进注意力计算，省掉这 10%。代价是压缩效果变差：在 SCBench 的 Retr.KV 上（LLaMA3.1-8B），原版保留 40% 时准确率约 60%，去掉 softmax 后只有约 33%，要多留约 10 个百分点的缓存才能追平（读图，原文图 15）。原因不难理解：没有归一化的 logit 在不同的 query 之间不可比，一个 query 的 logit 普遍偏大，并不代表它真的集中注意力在某个 key 上。

两点要分清：
  • “约 2 倍”是注意力内核的延迟，不是端到端速度。每生成一个 token 还要读一遍约 16 GB 的参数、算前馈层。粗略推算：A100 上读参数约 8 毫秒，32 层注意力在完整缓存时约 12.5 毫秒、保留 30% 时约 6.2 毫秒，所以单请求的每 token 时间大约从 20 毫秒降到 14 毫秒，约 1.4 倍（推算，只计这两项，论文没有测端到端）。上下文越长、批越大，注意力占比越高，端到端的收益越接近 2 倍。
  • 本站的一点看法：FlashAttention 的前向本来就会输出每一行的 log-sum-exp（反向传播要用），有了它，第二遍就能在内核里逐块重算出真正的概率并取列最大值，而不必存下矩阵。论文没有讨论这条路；附录 C.3 的“去 softmax”变体走的是更省事、但有精度损失的方向。

3.5 淘汰的粒度：逐个 KV、均匀预算与按头淘汰

论文在 §3 开头和 §4 里分散地说明了分数可以怎样用。本站把它们集中在这一小节。

先补一点背景：头与头之间的预算怎么分，以及按头淘汰。

均匀预算是 SnapKV 原本的做法：每层、每个头都留同样多个 KV。非均匀预算来自 Ada-KV（见 SnapKV 精读·后来怎么样了）：同一层里把所有头的分数放在一起排序，统一取前 \(r\%\)，于是注意力集中的头留得少、分散的头留得多。非均匀预算的麻烦在于各个头的缓存长度不一样，不能再存成一个规整的张量。KVzip 的实现借用了 Ada-KV 的 CUDA 内核：把每个 KV 头当成一条独立的“序列”，各自记录长度，用 FlashAttention-2 的变长接口（flash_attn_varlen_func）一次算完。

按头淘汰来自 DuoAttention（ICLR 2025）。它发现只有一部分头（“检索头”）需要看完整的上下文，其余的头（“流式头”）基本只看开头几个 token（注意力汇）和最近一段，于是给检索头保留完整 KV，给流式头只保留一个固定长度的小缓存。哪些头是检索头，靠在合成的“找密码”数据上优化一组门控分数得到。这种淘汰与上下文无关：每个模型确定一次，之后所有请求都一样。

示意图：同样留下约三分之一到一半的 KV，三种粒度（4 个头 × 12 个位置；深色 = 保留）
本站示意图。(a) 是 KVzip 主实验的默认做法；(c) 中流式头保留开头和最近几个位置是 DuoAttention 的方案，KVzip 官方代码的简化实现则把这些头上的上下文 KV 全部删掉，只留系统提示和问题的 KV。

KVzip 的分数天然支持这三种用法。主实验用 (a)：所有头的分数一起排序，留前 \(r\%\)。(b) 只是把排序限制在每个头内部。(c) 需要每个头一个分数，KVzip 取这个头在整条序列上的最大分数：\(S^{\text{head}}_{l,h}=\max_{j}S_{l,h}[j]\)，再交给 DuoAttention 的淘汰方案使用。附录 C.4 比较了 (a) 和 (b)：在 SQuAD 上（LLaMA3.1-8B），保留 30% 时 KVzip 非均匀约 92.4%、均匀约 77.9%，SnapKV 非均匀约 41.6%、均匀约 48.3%（读图，原文图 16）。非均匀预算对 KVzip 帮助很大，因为原文图 13 显示，不同头的重要性差别本来就很大。

还有一个和 GQA 有关的细节。SnapKV 等方法的常见实现会先把每个 KV 头复制 \(G\) 份、对齐到查询头，再按查询头淘汰，这样存下来的缓存其实比原来还大。KVzip 在式 (2) 里已经对 \(G\) 个查询头取了最大值，所以直接在原始的 KV 头上淘汰，省下的显存是实打实的。

对比时要留意预算的自由度：按附录 A，基线方法在每一层内部做非均匀分配、每层的比例固定为 \(r\%\)（PyramidKV 则按层线性递减）；而官方代码里 KVzip 的阈值是跨所有层统一取的，层与层之间的比例也可以不同。也就是说，KVzip 在“预算怎么分”上比基线多了一个自由度。论文没有单独测这一项贡献了多少，所以 §4 里 KVzip 的优势，有一部分可能来自预算分配，而不全是来自打分本身。

4 实验：压到三成，还剩多少本事

这一节要回答的问题：在“压缩时不知道问题”的设定下，KVzip 和 H2O、SnapKV、PyramidKV 相比，保留多少 KV 还能不掉点？换模型、换架构、叠加量化、改成按头淘汰时结论还成立吗？哪些设计是必要的？压缩的开销什么时候划得来？这些数字的份量有多重？

4.1 实验怎么设计：一套与问题无关的统一评测

评测协议。所有方法都在图 1(c) 的框架下运行：先把上下文单独预填充、压缩，压缩时不给任何问题；然后用这份压缩后的缓存依次回答这个上下文的每一个问题。按官方代码，每答完一个问题，问题和回答的 KV 就被删掉，下一个问题看到的仍是同一份压缩缓存。H2O 和 SnapKV 本身也支持“先单独预填充上下文”，所以能放进这个框架；此时 SnapKV 的观察窗口是上下文的最后 32 个 token，而不是问题。论文认为，既然压缩与问题无关，即使某个数据集每个上下文只有一个问题，也能检验这份缓存对该类任务的能力。

淘汰方式。主实验对所有方法统一用非均匀的头预算（§3.5），系统提示的 KV 都保留。所有实验在单张 A100 80GB 上进行，模型用 BF16，贪心解码。

基线。SnapKV 和 PyramidKV 按各自的官方代码实现，观察窗口 32、池化核 7，短于 1K 的样本窗口缩为 16；H2O 用 KVCache-Factory（原 PyramidKV 仓库）里的代码改成预填充版，用最大注意力打分。按头淘汰另外对比 DuoAttention。

先补一点背景：SCBench 与这 12 个数据集。

SCBench（SharedContextBench，ICLR 2025）是专门从 KV 缓存的角度评测长上下文方法的基准：每个样本是一段共享的长上下文加多个问题，模拟多轮对话和多个请求共用同一前缀的情形。它的结论之一是：只保留少于 \(O(n)\) 的 KV 的方法（淘汰类方法都属于此类）在多轮场景里明显吃亏。

KVzip 用了 12 个数据集，论文按任务性质分成三组：

  • 检索密集型：大海捞针 NIAH（上下文 500、2000、8000 个 token，针插在 0 到 1 之间每隔 0.1 的位置）；SCBench 的 Retr.KV（从一大堆随机字符串组成的键值对里，按键找值）、Retr.Prefix-Suffix（按前缀和后缀找出完整的字符串）、Code.RepoQA（在代码仓库里找出指定功能的函数）。
  • 上下文理解：SQuAD（短文问答）、GSM8K（数学应用题，题面当上下文、问句当问题）、SCBench 的 En.QA 与 En.MultiChoice（基于整本英文小说的问答和选择题，来自 ∞Bench）。
  • 上下文冗余高：En.Summary（整本书的摘要，用 ROUGE 打分）、Retr.MultiHop（多跳的变量追踪，来自 RULER）、Math.Find（在一长串数字里找最大最小值等）、ICL.ManyShot（几百个示例的上下文学习）。

除 GSM8K 和 NIAH 外，每个上下文都配多个问题。上下文长度从 100 到约 17 万 token 不等（按 Qwen 的分词器计）。

模型。Qwen2.5-7B-Instruct-1M（\(G=7\)）、Qwen2.5-14B-Instruct-1M、LLaMA3.1-8B（\(G=4\)）、Gemma3-12B（全局注意力层与 1K 滑动窗口层按 1:5 交替，只对全局层淘汰），附录另有 LLaMA3.1-3B；量化实验用 QServe 的 LLaMA3-8B W8A8KV4。LLaMA3.1 和 Gemma3 只支持 128K，所以 En.QA 和 En.MultiChoice 里超过 125K token 的样本被去掉。

汇总指标。跨数据集比较时，论文先把每个数据集上的分数除以该模型完整缓存时的分数，得到“相对性能”，再对 12 个数据集取平均。1.0 表示和不压缩一样好。

第二，理解类任务可以压到二三成。SQuAD、GSM8K、En.QA、En.MultiChoice 上，KVzip 保留 20%–30% 时基本无损；SQuAD 保留 20% 时约 92.8%，保留 10% 才明显下降到约 63.6%（读图）。基线在 SQuAD、GSM8K 上保留 30% 时只剩一到三成。

第三，冗余高的任务谁都能压。En.Summary 需要的是整体的高层信息，另外三个任务的上下文里有大量重复的内容，这些任务即使压到 10% 也掉得不多，基线在 30% 时也只掉几分。有几处压缩后分数反而升高了，比如 Retr.MultiHop 上 KVzip 保留 10% 时约 44.3，高于完整缓存的 41.2（读图）。论文猜测是因为淘汰减少了无关内容对注意力的干扰（引用了 Differential Transformer 关于“注意力噪声”的讨论），但没有进一步验证。

第四，GSM8K 说明推理任务也受益。GSM8K 的上下文只是一道题的题面，一般只有几十到一两百个 token（本站估计），而且每个数字都必不可少。KVzip 保留 30% 时 67 分，接近完整缓存的 69 分；而按“结尾附近”打分的 SnapKV 只有 13 分。这里按附录 A，只用了题面不短于 72 个 token 的题，因为对太短的题面，SnapKV 的观察窗口会盖住大半个题面。

4.4 与 4 bit KV 量化叠加

先补一点背景：KV 量化和 QServe。

淘汰减少的是“存多少个 KV”，量化减少的是“每个 KV 用几个比特”，两者正交，可以叠加。KV 量化的具体做法（为什么 key 要按通道、value 要按 token 分组）见 KIVI 精读 §3.1。QServe（MIT Han Lab，2024）是一个量化推理系统，它的 W4A8KV4 指权重 4 bit、激活 8 bit、KV 缓存 4 bit；KVzip 用的是它的 W8A8KV4 版本 LLaMA3-8B：权重和激活 8 bit，KV 缓存 4 bit。

论文在预填充、打分和解码三个环节都使用同样的量化方案，也就是说，打分时看到的注意力本身就是在 4 bit KV 上算出来的。原文图 10 最右的小图显示，KVzip 在量化模型上依然稳健，保留 20% 时平均相对性能约 0.99（读图）；论文还指出，原始的 LLaMA3-8B 比改进版 LLaMA3.1-8B 表现出更强的“上下文稀疏性”，更经得起压缩。

4.5 与上下文无关的按头淘汰：对比 DuoAttention

KVzip 的另一种用法完全没有部署时的开销：每个模型只算一次每个头的分数，之后对所有上下文都用同一组静态分数，按 DuoAttention 的方式淘汰。论文只用了一个样本来算头分数：SCBench 的 En.QA 里一本 8.8 万 token 的英文书，对它做一遍复述打分，再对每个头在序列方向取最大值。这只需要几次前向，一分钟以内；而 DuoAttention 要在一个 8 卡节点上优化几个小时（论文引言里说是“几十个 GPU 小时”）。

为了公平，对比用的是 DuoAttention 公开发布了头分数的那个模型：LLaMA3-8B-Instruct-Gradient-1048K。区别只在头分数从哪来：DuoAttention 的分数是为“找出合成的密码”优化出来的，KVzip 的分数来自在自然语言书本上的复述。

结果（原文图 11，读图，12 个数据集平均相对性能）：保留 40% 时 KVzip 约 0.77、DuoAttention 约 0.64；保留 50% 时 0.89 对 0.82；保留 60% 时 0.98 对 0.86；保留 70% 及以上两者都回到 1.0。最低只画到 0.4，是因为 DuoAttention 的方案本身最多只能压到约 0.32。可以看出，与上下文无关的模式只能做到约 60% 的保留比例（约 1.7 倍压缩，推算），官方 README 也推荐这个模式用 ratio=0.6；与上下文有关的模式则能到 30% 左右。这正是 §1 说的取舍：省掉了每份上下文的打分开销，就要接受更温和的压缩。

附录图 24 把几种来源算出的头分数画在一起：KVzip 的头分数比 DuoAttention 的分布得更均匀；换用 SCBench 里别的书、代码仓库或随机键值对来算，模式大体相似，其中由随机键值对算出的最稀疏。README 建议，如果主要用于代码任务，可以再用代码数据算一遍头分数，两者取最大值。

4.7 压缩之后模型不再拒答：一个隐私相关的现象

论文表 1 报告了一个意外的现象。上下文是 DecodingTrust 数据集里一段含有某人电话号码的文字，问题是“这个人的电话号码是多少”。LLaMA3.1-8B 用完整缓存时拒绝回答，说不能提供个人联系方式；用 KVzip 压缩到 40% 的缓存时，它直接给出了号码。

论文的解释是：KVzip 优先保留复述原文必需的 KV，那串数字当然必需；而支撑“拒答”行为的那些 KV，复述时用不上，于是被扔掉了。这与另一篇 KV 压缩论文（Yang 等，2024）的观察一致，也和“安全对齐只停留在最前面几个 token 上”（shallow alignment，Qi 等，ICLR 2025）的讨论相呼应。作者认为实际影响有限，因为既然上下文已经被缓存，通常意味着使用者有权使用其中的内容；但这说明 KV 淘汰会改变对齐行为，值得进一步研究。

只是一个例子：论文只展示了这一个样本，没有统计拒答率怎么随压缩比例变化，也没有测别的安全基准。读者不应把它当成“KVzip 会削弱安全性”的定量结论，但在把压缩缓存用于带安全约束的场景之前，应该自己测一下。

4.8 压缩开销什么时候划得来

论文在 §3.4 和附录 B 里只用了一句话处理这个问题：开销可以被多个问题摊薄；与上下文无关的按头模式部署后没有开销，但压缩程度不如与上下文有关的模式。这一小节用论文图 8 的数字，把“摊薄”具体算一算（以下全部是推算，场景是 LLaMA3.1-8B、12.4 万 token、单张 A100、批大小 1）。

和“每问重做”比：KVzip 一次性花约 31 + 66 = 97 秒，每问重做的 SnapKV 每个问题花约 31 秒。97 ÷ 31 ≈ 3.1，所以同一份上下文只要被问到第 4 个问题，KVzip 的总计算就更省，而且准确率不输（推算）。

和“不压缩、直接复用完整缓存”比：这才是前缀缓存、文档缓存等场景里的真正对手。单看时间，KVzip 一次性多花约 66 秒，换来的是每生成一个 token，32 层注意力共省下约 \(32\times(0.39-0.195)\approx6.2\) 毫秒。66 秒 ÷ 6.2 毫秒 ≈ 1.06 万个 token，也就是说，批大小为 1 时，要在这份上下文上一共生成约一万个 token，省下的解码时间才能抵掉打分时间（推算）。单靠解码提速，回本很慢。

所以 KVzip 真正的收益在容量上。A100-80GB 放下 16 GB 的参数后，大约还剩 64 GB：完整缓存每份 16.3 GB，只能同时放下 3 份这样的上下文；压到 4.9 GB 后能放下约 13 份（推算，不计激活与碎片）。能同时服务的长上下文请求多了，批就开得大，吞吐量就上去了（批越大越省的道理见 vLLM 精读 §1）。如果 KV 缓存要存进 CPU 内存、SSD 或远端存储，再在命中时加载回来，压缩后的缓存在存储空间和传输时间上都按比例省。在这些场景里，压缩开销是每份上下文付一次，收益则在每次命中、每一步解码上反复兑现。

什么时候摊不薄：

  • 一份上下文只用一次。比如一次性上传的文件只问一个问题，就生成几百个 token。这时多花 2 倍预填充的计算纯属浪费，不如不压缩，或者用按问题压缩的 SnapKV（它几乎不花额外时间，而且这时知道问题）。
  • 首个回答对延迟敏感，而压缩必须在回答之前完成。此时首个 token 的等待时间从约 31 秒变成约 97 秒，约 3 倍（推算）。本站的看法是：可以先用完整缓存回答第一个问题，同时或稍后再打分压缩，供后续请求使用；或者在离线、空闲时预先压缩。论文没有讨论这种调度。
  • 上下文一直在变。智能体的上下文每一轮都在增长，对话也在不断追加。KVzip 只压缩最初的那段上下文；按官方代码，多轮模式下新追加的问题和回答会原样保留、不再压缩。要压缩新内容，就得对新内容再做一遍复述打分。论文没有评测这种持续增长的场景。
  • 显存本来就够。上下文短、显卡大、并发低时，缓存占不了多少显存，省下来也换不来更大的批（vLLM 论文里 OPT-175B + Alpaca 的情形同理）。
  • 计算本来就紧张。如果服务的瓶颈在预填充的算力上（比如大量新文档涌入），每份上下文多 2 倍计算会直接挤占吞吐。

与上下文无关的按头模式没有上述问题：分数每个模型算一次，部署后零开销，适合上下文多变、各用一次的场景，只是压缩比降到约 1.7 倍。后来的 Fast KVzip 和 KVzap 正是想把“打分开销”这件事彻底去掉（见“后来怎么样了”）。

4.9 结果的份量

把上面的数字放回它们的测量条件里，可以这样看。

基线的处境。H2O、SnapKV、PyramidKV 是作者按官方代码或 KVCache-Factory 重新实现的，而且被放进了“压缩时没有问题可看”的框架：SnapKV 的观察窗口看的是上下文的结尾，不是问题。这不是它们设计时的用法，论文自己也承认这种“错位”。在它们擅长的“知道问题”设定里（图 2 的橙色线），SnapKV 在 SQuAD 上保留 30% 也几乎不掉点。所以“KVzip 远胜 SnapKV”准确的含义是：在缓存要被多个未知问题复用的场景里，KVzip 远胜把 SnapKV 硬搬过来的做法。论文没有和其他为“不知道问题”设计的方法比较，例如同期的 Corallo 等人面向 RAG 的“任务感知”压缩（arXiv 2503.04973）；也没有和 SCBench 发现更稳健的“保留全部 KV、只做稀疏计算”的方法比较。kvpress 排行榜上的 RULER 结果是第三方在统一框架下测的，可信度更高一些。

压缩比和准确率。“3–4 倍、几乎无损”对应保留 25%–33%。这在 Qwen2.5 系列和 kvpress 上的 Qwen3-8B 上成立；在 LLaMA3.1-8B 上，平均相对性能保留 30% 时约 0.88，要保留约 40% 才接近无损。逐任务看，Retr.Prefix-Suffix 要保留约 50%。几个数据集的上下文很短：SQuAD 是一段话，GSM8K 是一道题，NIAH 最长 8000 token；真正的长上下文（几万到 17 万 token）来自 SCBench 的 9 个任务。

速度。“约 2 倍”是 A100 上单层注意力内核在 12.4 万 token 时的延迟（变长 FlashAttention-2，非均匀头预算），没有测端到端的每 token 延迟、首 token 延迟或服务吞吐，也没有在 vLLM、SGLang 这类推理引擎里测。按本站的粗算，批大小为 1 时端到端约 1.4 倍。所有代码基于 HuggingFace transformers，Gemma3 还没有优化内核。

开销。打分开销（约 2 倍预填充）在论文里测得很清楚，但只测了一个模型、一个长度；没有测与上下文有关的模式在真实请求流里能否摊薄（§4.8 是本站的推算）。

评测协议。“多问题”指的是同一份压缩缓存依次回答多个互相独立的问题，每个回答后都把问答的 KV 删掉；不是历史不断累积的真实多轮对话。全部用贪心解码。论文没有报告每个数据集用了多少个样本，曲线上也没有误差范围；GSM8K 的读数都是整数，样本可能不多（本站推测，未核实）。

可复现性。官方代码开源（MIT 许可），提供了评测脚本、数据加载和部分模型的预计算头分数；NVIDIA kvpress 也独立实现了 KVzipPress。这一点上，论文的结果比大多数同类工作更容易被检验。

5 相关工作、局限与结论

这一节要回答的问题：KVzip 在 KV 压缩的版图里处在什么位置？和稀疏注意力、量化这些路线是什么关系？作者自己承认了哪些局限？

KV 缓存压缩。论文把相关工作分成几类。一类在训练时就让模型学会用稀疏或局部的缓存（Sparse Transformer、Mistral 的滑动窗口等）；一类在训练时把多个 KV 合并压缩（Compressive Transformer、GQA，以及第一作者此前的 Compressed Context Memory）。Deja Vu 发现大模型推理时存在“上下文稀疏性”，由此催生了一批无需训练、在解码时动态淘汰的方法（H2O、FastGen、Scissorhands 等）；SnapKV、PyramidKV、Finch 专门在长提示的预填充阶段淘汰；DuoAttention 在部署前给每个头定好“完整注意力还是滑动窗口”。KVzip 和预填充阶段的淘汰最接近，区别在于它与问题无关，压缩后的缓存可以在不同问题之间复用；它的按头模式则沿用了 DuoAttention 的框架。同期，Corallo 等人也提出了一种面向 RAG 场景、与问题无关的 KV 压缩方法。

量化与稀疏注意力。KV 量化（QServe、KIVI）减少每个 KV 的比特数，和淘汰互补（§4.4 已经叠加使用）。另一条路线是不压缩 KV 缓存、只减少注意力的计算：BigBird 训练时就用稀疏注意力；MInference 在推理时利用稀疏性加速预填充；Quest、InfiniGen、RetrievalAttention、MagicPIG 等在解码时只取回一部分相关的 KV（有的把 KV 卸载到 CPU）。这类方法仍保留全部 KV，KVzip 则是真的把缓存变小。

局限（附录 B）。作者承认三点：方法完全是经验性的，没有关于压缩信息损失的理论保证；淘汰可能带来隐私方面的担忧（§4.7）；压缩有开销，可以被多个问题摊薄，而能消除部署开销的按头模式压缩效率较低。

结论。KVzip 用“让模型复述原文”来衡量每个 KV 的重要性，得到一份可以在不同问题之间复用的压缩缓存。在多问题设定下，它能在几乎不掉点的情况下扔掉最多 70% 的 KV，使 FlashAttention 的解码注意力延迟降低约一半；而现有的按问题淘汰方法扔掉 10% 就开始掉点。它还能和量化、按头淘汰等结构结合使用。

进入 kvpress：成为“与问题无关”评测的基线

NVIDIA 的 kvpress 是一个把几十种 KV 压缩方法放进统一接口的研究库，它的评测流程本来就是“只压缩上下文、不把问题放进被压缩的部分”，并在说明里指出，否则会不公平地偏向 SnapKV 这类依赖问题的方法。KVzip 官方仓库的公告说，kvpress 在 2025 年 7 月加入了对 KVzip 的支持。kvpress 的 KVzipPress 是一个改动最小的实现，文档说明它的计算开销是首次预填充的 2–3 倍，并指向官方仓库获取真正带实际压缩的优化实现；它还加了一个可选的 “KVzip+” 归一化开关。KVzap 的论文（2026-01）称，KVzip 当时是 kvpress 排行榜上的最好方法。

KVzip+ 与 KVzap：把打分变成一个线性层

KVzap（Simon Jegou、Maximilian Jeblick，NVIDIA，arXiv 2601.07891）直接针对 KVzip 的两个短板：打分要在两倍长的输入上做预填充，太慢；而且它不能用在解码阶段，对生成几千个 token 的推理任务无能为力。它先把 KVzip 的分数改进成 KVzip+：在注意力权重上乘以“这个 token 的 value 经输出投影后的范数，除以接收方隐状态的范数”，

$$s_{i}^{+}=\max_{j\in\text{复述输入}}\ a_{ji}\,\frac{\lVert W_{O}v_{i}\rVert}{\lVert h_{j}\rVert}$$

这样衡量的是“这个 token 实际给残差流贡献了多少”，而不只是“被看了多少”。然后它在每一层训练一个线性层或两层 MLP，直接从每个 token 的隐状态预测它在各个头上的 \(\log s^{+}\)；预测和真实分数的平方相关系数在 0.60–0.80 之间。因为只需要一两次矩阵乘法、只依赖隐状态，它可以在预填充和解码中随时使用；淘汰也从“固定预算”改成“低于阈值就扔”，于是压缩比会随输入自适应。论文报告在 Qwen3-8B、Llama-3.1-8B-Instruct、Qwen3-32B 上压缩 2–4 倍、准确率损失可以忽略，但也承认没有做把压缩变成实际速度和显存收益所需的工程工作。

Fast KVzip：原作者的门控版本

Fast KVzip（Jang-Hyun Kim、Dongyoon Han、Sangdoo Yun，arXiv 2601.17668）给冻结的大模型加上轻量的门控模块（论文叫“低秩汇注意力”门），直接蒸馏 KVzip 的重要性分数来训练，训练只要不到一个 H100 小时，而且只需要大模型做前向、不必对大模型做反向传播，训练目标仍是与任务无关的“复述”。它在预填充和解码阶段都能用，门控的开销约为前向延迟的 1%，在 Qwen2.5-1M、Qwen3、Gemma3 系列上报告淘汰 70% 的 KV 时近乎无损。在需要预填充的任务上，它与 KVzip 的效果相当，而 KVzip 为了压缩要多付一倍的预填充计算。kvpress 也支持了它（FastKVzipPress）。第一作者主页把它列为 NeurIPS 2026 论文，arXiv 页面和项目页上则仍只写预印本（发表状态本站未在会议官方页面核实）。

RestoreKV：压到 5% 时补回信息

RestoreKV（Baek 等，arXiv 2608.01247）关注“与问题无关”的淘汰在极低预算下的崩溃。它不改变打分和淘汰规则，而是在预填充后加几个“恢复 token”，让它们在一个 LoRA 适配的前向里看完整的缓存，生成一小段补充缓存，在相同的总预算里补回被扔掉的信息；只训练约 0.4% 的参数。据其摘要，在 Qwen3-4B、5% 预算下，它把 KVzip 在 RULER-4K 上的分数从 38.2 提到 73.2；套在 KVzip+ 上，在 kvpress 基准上以 16 倍压缩达到 86.4 的 RULER 准确率。

推理引擎：还没有进去

截至 2026-10-20，我们在 vLLM、SGLang、TensorRT-LLM 的 GitHub 仓库里搜索不到任何提及 KVzip 的 issue 或 PR。本站的理解是，原版 KVzip 进引擎有三重障碍：打分要用归一化后的注意力概率，而引擎里的 FlashAttention 类内核不输出它；非均匀的头预算让每个头的缓存长度都不同，和引擎“所有头共用一套固定大小的块”的分页结构冲突（KVzap 论文也说需要能处理变长块的分页注意力内核）；每份上下文多 2 倍预填充计算，在线服务很难接受。KVzap、Fast KVzip 这类“用小模型预测分数”的后续工作，正是在为这一步铺路。与此同时，SnapKV 精读页里提到的 KV-Compress 等工作已经在 vLLM 的基础上实现过分页缓存里按块、按头的变长淘汰，说明工程上并非不可能。

回头看，KVzip 留下的最重要的东西，是把“KV 重要性”从“这个问题需要什么”换成了“复原这段上下文需要什么”。它让“压缩一次、到处复用”第一次在长上下文的检索任务上站住了脚，也把“打分本身太贵”这个问题明确地留给了后来的工作。

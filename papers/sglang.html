0 导读：这篇论文解决什么问题

2023 年前后，人们使用大模型的方式发生了变化。最早的用法是“一问一答”：用户发一段话，模型回一段话。后来越来越多的应用变成了一段程序：程序里会多次调用模型，前一次的输出决定下一次问什么；有时把同一个问题拆成几路并行去问，再把结果合起来；还经常要求模型的输出严格符合某种格式（比如 JSON），好让后面的代码直接读取。few-shot 评测、多轮对话、思维树搜索、会调用工具的 agent，都属于这一类。论文把它们统称为语言模型程序（LM 程序）。

这类程序在当时的推理系统上跑得很浪费。推理引擎（包括 vLLM）只看到一个个独立的请求，并不知道它们来自同一个程序、开头有大段内容完全相同。一个请求结束后，它的 KV 缓存就被丢掉；下一个请求哪怕开头一模一样，也要从头再算一遍。要求输出符合格式时，系统每一步只能解码一个 token，哪怕接下来的十几个字符是格式规定死的、根本没得选。

SGLang 从两头解决这个问题。前端是一门嵌在 Python 里的小语言，提供 gen、select、fork、join 等原语，让程序的结构（哪里分叉、哪些调用开头相同、哪里要求格式）能被系统看见。后端运行时做了三项优化：

  • RadixAttention：请求结束后不丢弃 KV 缓存，而是把所有请求的 KV 缓存放进一棵基数树，当成一个按“最近最少使用”（LRU）淘汰的缓存来管理。新请求到来时，自动在树上找出最长的已缓存前缀并直接复用；等待队列按“能复用的前缀越长越先跑”来排序，提高命中率。
  • 压缩有限状态机：把格式约束（正则表达式）里唯一确定的一段字符合并成一步，解码到那里时一次性填进去，不再逐个 token 地生成。
  • API 投机执行：对只能通过 API 调用的模型（如 GPT-4），让一次调用多生成一点，用多出来的内容填上程序里后面的空，省掉后续调用。

论文报告，在 Llama-7B 等开源模型上，和 vLLM、Guidance、LMQL 相比，吞吐量最高提高到 6.4 倍、延迟最多降低到原来的 1/3.7；部署在 Chatbot Arena 一个月，两个模型上的前缀缓存命中率分别为 52.4% 和 74.1%。这些数字背后的条件很重要，§6 会逐项拆开。

关于版本。这篇论文的 arXiv 第一版（2023-12-12）题为 “Efficiently Programming Large Language Models using SGLang”，当时报告最高 5 倍加速，还没有压缩有限状态机；第二版（2024-06-06）改成现在的标题，加入了压缩有限状态机、多模态和更多实验，也就是 NeurIPS 2024 发表的版本。本页按第二版讲。

1 引言：大模型的用法从“聊天”变成了“编程”

这一节要回答的问题：作者为什么说，大模型的使用方式正在从聊天变成编程？这种变化给推理系统带来了什么样的低效？作者把问题归结为两个挑战：写这类程序很麻烦，跑这类程序很浪费。这一节交代这两个挑战从哪里来，以及 SGLang 的整体结构。
先补一点背景：什么是 LM 程序。

把“调用一次大模型”看成一次函数调用。只调用一次的应用（单轮聊天）就像只有一行代码的程序；而很多实用的做法要调用很多次，调用之间还有逻辑。几个常见的例子：

  • few-shot 提示：在问题前面放几个“题目 + 答案”的示例，让模型照着格式回答。用 MMLU 这类题库做评测时，成千上万道题前面放的都是同一组示例。
  • 自洽采样（self-consistency）：对同一个问题采样多个答案，再投票选出最常见的那个。
  • 多轮对话：每一轮都把之前全部的对话历史连同新问题一起发给模型。
  • 思维树（tree-of-thought）：把解题过程当作一棵搜索树，在每个节点让模型提出几种下一步，评估之后选出有希望的继续展开。
  • agent：比如 ReAct，模型交替地“思考—调用工具—看结果”，每一步都把之前的整条轨迹带上。
  • 结构化输出：要求模型输出符合某个 JSON schema 的对象，后面的代码才能直接读取字段。

论文总结了这类程序的两个共同特点。第一，它们包含多次模型调用，中间穿插着控制流（条件判断、循环、并行分支），这是完成复杂任务、提高质量所需要的。第二，它们的输入和输出是结构化的（可能有图片等多种输入，输出要符合固定格式），这样一个 LM 程序才能和别的程序拼接，嵌进已有的软件系统。论文借用了 LMQL、DSPy 等工作里的说法，把这类程序叫 “Language Model Programs”。

作者指出了两个挑战。第一个挑战是写起来麻烦。模型的输出是不确定的，所以写这样的程序需要大量拼接字符串、反复调整提示词、解析格式不稳定的输出、处理图片等多种输入，还要自己写并行逻辑。即使是一个很简单的程序，代码也会变得难读（§2 有一个具体的例子）。

第二个、也是更重要的挑战是跑起来浪费，浪费在重复的计算和重复占用的显存上。当时最好的推理引擎（vLLM、TGI、TensorRT-LLM）在优化延迟和吞吐量时，并不了解上层的负载长什么样。这让它们足够通用、足够稳健，但对任何一种具体的负载都留下了明显的浪费。论文举了两个例子：

  • KV 缓存没有被复用。KV 缓存是模型推理时为每个 token 存下的中间结果（§3 会讲清楚）。在批量执行 LM 程序时，大量调用的开头是相同的，它们的 KV 缓存本可以共用；但当时的系统缺少有效的机制，只能一遍遍重算，既浪费计算，也浪费显存。
  • 约束解码一次只走一个 token。要求输出符合正则表达式描述的格式（比如 JSON 模式）时，经常有好几个 token 其实是格式规定死的、可以一次填进去；但现有系统仍然每次只解码一个 token。

为了解决这两个挑战，作者提出了 SGLang（Structured Generation Language，结构化生成语言）。它的核心想法是：系统性地利用 LM 程序里“多次调用”的结构来加速执行。SGLang 由两部分组成，前端语言负责让程序好写，后端运行时负责让程序跑得快；两者可以配合使用，也可以各自单独使用。

前端是一门嵌在 Python 里的领域专用语言，提供生成类原语（extend、gen、select）和并行控制原语（fork、join），可以和 Python 自带的控制流、库函数混着用。论文为它实现了解释器和编译器：解释器把每个提示当作一条“流”，把原语异步地提交上去执行；编译器把程序追踪成计算图，以便做更多优化。

运行时部分有三项新技术，分别是前面提到的 RadixAttention、压缩有限状态机和 API 投机执行。用 SGLang，作者实现了 agent 控制、逻辑推理、few-shot 评测、JSON 解码、检索增强生成流水线、多轮对话和多模态处理等应用，在 Llama-7B/70B、Mixtral-8x7B、LLaVA-v1.5-7B（图像）和 LLaVA-NeXT-34B（视频）上，用 NVIDIA A10G 和 A100 做了测试，和 Guidance、vLLM、LMQL 相比，吞吐量最高提高到 6.4 倍。

读的时候容易混淆的一点：“SGLang” 这个名字在论文里指整个系统（前端语言 + 运行时），在后来的开源社区里则主要指它的推理服务引擎。论文的端到端实验比较的是“整个系统”：SGLang 一侧既有运行时的优化，也有前端提供的程序结构信息（比如 fork 的提示、程序内并行）；而 vLLM 一侧只通过类似 OpenAI 的补全接口接收一个个独立的请求。所以实验里的加速，一部分来自更好的运行时，一部分来自“让运行时知道程序长什么样”。

2.1 一个完整的例子：给一篇看图作文打分

先补一点背景：branch-solve-merge。

这是一种提示技巧：把一个复杂的任务拆成几个子任务（branch），分别让模型去做（solve），最后把各自的结果合起来（merge）。用它让模型当评委时，可以分别从几个维度打分，再综合成总评，比让模型一次性给出总评更稳定。

论文用一个“多维度作文评委”贯穿全节：输入一张图片和一篇描写这张图的作文，让模型给出评价和等级。程序的流程是这样的：

  1. 把图片和作文追加到提示里。SGLang 里，提示状态是一个变量 s，用 += 往后面追加字符串或原语。
  2. 问模型“作文和图片有关吗”，用 select 让模型在 “yes” 和 “no” 里选概率更高的一个，结果存进 s["related"]。如果是 “no”，用普通的 Python if 直接返回。
  3. 用 fork 把当前的提示复制成三份，分别从清晰度、原创性、论据三个维度评价。每一份用 gen 生成一段评价，遇到 “END” 停下。这三路是并行执行的。
  4. 把三段评价拼在一起，接着用 gen 生成一段总结（遇到句号停）和一个等级。
  5. 最后要求模型按 JSON 返回结果，用 gen 的 regex 参数规定格式：\{"summary": "[\w\d\s]+\.", "grade": "[ABCD][+-]?"\}，即一个 summary 字段（以句号结尾的文字）和一个 grade 字段（A 到 D，可以带 + 或 −）。

下面是本站根据原文图 2 改写的简化版（省略了部分提示词，变量名有改动），用来看清原语的用法：

@function
def judge(s, image_path, essay):
    s += system("评价一篇看图作文。")
    s += user(image(image_path) + "作文：" + essay)
    s += user("作文和图片有关吗？")
    s += assistant(select("related", choices=["yes", "no"]))  # 在选项里选概率最高的
    if s["related"] == "no":                                 # 普通的 Python 控制流
        return
    branches = s.fork(3)                                     # 复制 3 份，共享已有的前缀
    for f, dim in zip(branches, ["清晰度", "原创性", "论据"]):
        f += user("从" + dim + "评价，以 END 结尾。")
        f += assistant(gen("judgment", stop="END"))          # 三路并行生成
    merged = "\n".join(f["judgment"] for f in branches)     # 读结果时才等待
    s += assistant(merged + "总结：" + gen("summary", stop=".")
                   + "等级：" + gen("grade"))
    s += user("按 JSON 格式返回。")
    s += assistant(gen("output", regex=SCHEMA))            # 输出受正则约束

2.3 执行方式：解释器把提示当成一条异步的流

先补一点背景：异步执行与“流”。

在 GPU 编程里，CPU 程序调用一个 GPU 内核时并不会等它算完，而是把它放进一个“流”（stream）的队列里就立刻返回，继续执行后面的 CPU 代码；同一条流里的操作按提交顺序执行，不同的流之间可以并行。只有当 CPU 真正需要读取 GPU 的计算结果时，才会停下来等待。这样 CPU 和 GPU 都不会白白空等。

SGLang 的解释器借用了同样的思路。每个提示状态被当作一条异步的流，extend、gen、select 这些原语被提交到流上就立刻返回，Python 代码继续往下跑，不用等模型生成完。每条流由后台线程里的一个“流执行器”负责依次执行。只有当程序读取生成结果（比如 s["related"]）时，才会阻塞到结果就绪，从而保证同步正确。fork 出来的每一份提示是一条独立的流，所以三路评价会被自动并行地提交给后端，这叫程序内并行。

另一种执行方式是把程序编译成计算图，交给图执行器运行，这样可以做更多优化（附录 D，见本页 §9）。论文的实验默认用解释器。后端方面，开源模型跑在 SGLang 自己的运行时 SRT 上，也支持 OpenAI、Anthropic 等 API 模型。

2.4 和同类工具的比较

论文把“给大模型写程序”的工具分成两类。高层的，如 LangChain、DSPy，会提供预先写好或自动生成的提示词，比如 DSPy 能自动优化提示。低层的，如 LMQL、Guidance 和 SGLang，一般不改动用户的提示词，而是让用户直接操作提示和原语。高层语言可以编译成低层语言，比如 DSPy 程序可以用 SGLang 作为后端执行（§6 的 DSPy RAG 实验就是这么做的）。

3 RadixAttention：把所有请求的 KV 缓存放进一棵基数树

这一节要回答的问题：LM 程序的多次调用之间、不同程序实例之间，有大量相同的开头。怎样让运行时自动发现这些相同的开头并复用它们的 KV 缓存，而不需要用户手工配置？缓存会占显存，显存不够时先扔掉谁？等待中的请求很多时，按什么顺序执行能让缓存发挥最大作用？这一节是全文的核心。

3.1 前缀相同，KV 缓存就相同

先补一点背景：KV 缓存，以及它为什么能按前缀复用。

模型每处理一个 token，都会在每一层算出它的 key 和 value 两个向量；后面的 token 做注意力时，要读前面所有 token 的 key 和 value。为了不重复计算，推理系统把它们存在显存里，这就是 KV 缓存。处理用户输入的阶段叫 prefill（所有输入 token 一次并行算完），之后逐个生成 token 的阶段叫 decode。更详细的介绍见 vLLM 精读 §2.2。

这里只需要一个关键事实：在只能看前文的注意力（因果注意力）里，第 \(i\) 个 token 在每一层的 key 和 value，只取决于第 1 到第 \(i\) 个 token，和后面是什么无关。所以，只要两段输入从第一个 token 开始逐个相同，它们这段公共开头（前缀）的 KV 缓存就一模一样，算一次就够了。反过来，哪怕只有第一个 token 不同，后面即使字面完全相同，KV 缓存也不一样，不能共用，因为从第二层开始，每个 token 的输入已经混进了不同的上文。

复用前缀的 KV 缓存能省下两样东西。一是计算：命中的部分不用再 prefill，第一个输出 token 来得更快。二是显存：公共前缀只存一份，同样的显存能同时放下更多请求，批就能开得更大，吞吐量随之提高（批越大吞吐越高的原因见 vLLM 精读 §1）。

用论文实验里的配置估算一下有多少可省。Llama-2-7B 有 32 层，隐藏维度 4096，用 FP16 存储，每个 token 的 KV 缓存是：

$$\underbrace{2}_{\text{key 和 value}}\times\underbrace{32}_{\text{层数}}\times\underbrace{4096}_{\text{隐藏维度}}\times\underbrace{2\ \text{字节}}_{\text{FP16}}=512\ \text{KB / token}$$

论文的主实验用的是 24 GB 显存的 A10G。7B 模型的参数约 13.5 GB（约 67 亿参数 × 2 字节），剩下给 KV 缓存的大约 10 GB，也就是大约 2 万个 token（推算，没有扣除计算时的临时显存）。假设一组 few-shot 示例有 1,000 个 token（示意值），每道题都各存一份示例的 KV，20 道题就把显存占满了；共享之后，这 1,000 个 token 只存一份，显存几乎全部留给各题自己的部分。

vLLM 已经做到了哪一步。这个想法 vLLM 已经部分用上了（见 vLLM 精读 §4.4）。vLLM 把 KV 缓存切成固定大小的块，用块表记录每个序列用了哪些物理块，并给每个块记一个引用计数。于是同一个请求内部的多个序列可以共享块：并行采样时几个候选共用输入部分的块，束搜索时候选之间共用已经生成的前缀，要改写时再复制一份（写时复制）。跨请求的共享，vLLM 论文只讨论了一种情况：服务方事先指定一段固定的前缀（比如系统提示），预先算好它的 KV 块，让新请求直接指向这些块。

还差什么。LM 程序里的共享比这复杂得多。第一，共享常常发生在不同的请求之间，而且事先不知道：多轮对话的第二轮请求要等第一轮结束后才发来，而按当时的做法，第一轮请求一结束，它的 KV 缓存就释放了。第二，共享的结构是多层的、动态的：同一个系统提示下面有几组不同的 few-shot 示例，每组示例下面又有不同的问题；思维树更是一边搜索一边长出新分支。手工配置覆盖不了这些情况。论文的判断是：已有系统要么需要手工配置，要么只能处理少数几种共享模式（比如动态的树状结构就处理不了），所以大多数系统实际上为每个请求重算 KV 缓存。

3.2 基数树：从字典树讲起

先补一点背景：字典树与基数树。

字典树（trie，也叫前缀树）是一种按前缀组织数据的树。从根出发，每条边上写着一个元素（比如一个字母），从根走到某个节点，沿途的边连起来就是一个前缀。存 “tea”“ten”“to” 三个词时，三个词共用从根出发的 “t” 边；“tea” 和 “ten” 再共用 “e” 边，到这里才分开。查一个词时，从根开始一个字母一个字母地往下走，走的步数等于词的长度，和树里存了多少个词无关。

字典树的缺点是浪费：如果一长串元素中间没有任何分叉，也要为每个元素建一个节点，形成一条长长的单链。基数树（radix tree）就是把这种没有分叉的单链压缩成一条边，边上直接写一整段元素。它表达的前缀关系和字典树完全一样，只是节点少得多，论文称之为字典树的一种省空间的替代。往基数树里插入新序列时，如果它和某条边只匹配了一半，就把这条边从匹配结束的位置拆成两段，中间新增一个节点作为分叉点。

RadixAttention 用基数树维护一个映射：键是 token 序列，值是这些 token 的 KV 缓存。下面用一个小例子把插入、匹配、拆分、淘汰走一遍。为了画得下，图里每个方块代表一段 token（比如 Sys 是系统提示，Ex1、Ex2 是两个 few-shot 示例，Q 是问题，A 是模型的回答）；真实系统里，匹配是逐个 token 进行的。

3.3 把基数树当作缓存：页大小为 1、引用计数与 LRU 淘汰

KV 存在哪里。树本身（结构和索引）放在 CPU 内存里，维护开销可以忽略；KV 张量放在 GPU 显存中一个分页的、不要求连续的内存池里，每页只放 1 个 token。页大小取 1 的好处是，树可以在任意一个 token 处拆分，不会出现“一页里前一半属于这条边、后一半属于那条边”的麻烦。作为对比，vLLM 的块默认装 16 个 token（见 vLLM 精读 §4.1），以块为单位共享时，只有整块都相同才能共享。

缓存不占专门的地盘。RadixAttention 没有为缓存预留一块固定大小的显存。缓存着的 token 和正在运行的请求共用同一个内存池，系统动态地在两者之间分配：等待的请求少时，空闲的显存拿来留住旧请求的 KV；等待的请求多到需要更大的批时，系统会把缓存全部淘汰，把显存让给正在运行的请求。换句话说，缓存用的是“反正闲着的”显存，不会因此缩小批的上限。

正在用的不能删：引用计数。在连续批处理下，任何时刻都有一批请求正在运行，它们正在读的那些节点绝不能被淘汰。所以每个节点记一个引用计数，表示有多少个正在运行的请求在用它；计数为 0 的节点才可以淘汰。一个请求要用某个节点时，它其实需要从根到这个节点的整条路径（缺了祖先，后面的 KV 就没有意义），所以今天的 SGLang 代码在“锁住”一个节点时，会沿着父节点一路把祖先的计数都加一。

先淘汰最久没用的叶子：LRU。显存不够时，系统淘汰最近最少使用的叶子节点。只淘汰叶子是有道理的：一个节点的 KV 缓存只有在它所有祖先的 KV 都还在时才有用，如果先删了祖先，子孙节点的缓存就成了占着显存却用不上的“孤儿”。从叶子开始删，被多条路径共享的祖先（比如系统提示）会一直留到它自己变成叶子、并且也成了最久没用的那个时才被删掉。今天的实现是：把所有可淘汰的叶子放进一个按最后访问时间排序的最小堆，每删掉一个叶子，就检查它的父节点是不是也变成了无人使用的叶子，是的话把父节点也放进堆里。

前端提示。执行 fork 时，解释器会先把分叉之前的共享前缀单独发给运行时，作为一个“提示”，确保这段前缀先被算出来、插入树中，然后再发出各个分支的请求。如果几个分支的请求同时到达，它们在树上都找不到这段前缀（还没算完），就会各自把它算一遍；先发提示就避免了这种重复。论文用它作为“前端和运行时协同设计”的例子。

3.4 缓存感知调度：先跑能复用得多的请求

先定义衡量缓存效果的指标。论文把缓存命中率定义为：

$$\text{缓存命中率}=\frac{\text{命中缓存的输入 token 数}}{\text{输入 token 总数}}$$

等待队列里有很多请求时，执行的先后顺序会显著影响命中率。如果调度器在几组互不相关的请求之间来回切换，刚缓存好的前缀还没被复用就被挤掉了，接着又要重算，这叫缓存颠簸（thrashing）。看一个极端的例子：

论文的做法很直接：在批处理的场景下，不按先来先服务，而是按每个请求能在树上匹配到的前缀长度排序，匹配越长越先执行（longest-shared-prefix-first）。在对延迟更敏感的场景里，也可以只做有限度的重新排序，换取一部分命中率。

原文附录的算法 1 给出了它和连续批处理结合时，每一轮调度的步骤：

  1. 取出等待队列里的所有请求，对每个请求在基数树上做前缀匹配，记下匹配到的节点和匹配长度。
  2. 按匹配长度排序。
  3. 计算可用空间 = 树里可淘汰的缓存大小 + 内存池里的空闲大小。按排好的顺序逐个检查请求：放得下就把它加入新批，并给它匹配到的节点加引用计数（“锁住”）。锁住之后这些节点不再可淘汰，可用空间相应减少。
  4. 把新批并入正在运行的批，为需要的新 token 分配显存；分配失败就先从树里淘汰一些节点，再分配。
  5. 运行一步。对已经结束的请求，减掉它们节点的引用计数，并把它们的完整内容（输入 + 输出）插入树中，留给后面的请求复用。
论文伪代码里的一处疏漏：算法 1 在选请求时用 “请求大小 + current_size < available_size” 判断放不放得下，但伪代码里 current_size 初始化为 0 之后再也没有被累加。按字面执行，判断时永远只看单个请求的大小。合理的理解是：每选中一个请求，都应该把它要新占用的大小累加进 current_size（本站的理解）。另外，“锁住节点后可用空间加上 delta” 这一步里的 delta 是负数，今天的 SGLang 代码里它就是被锁住的那些原本可淘汰的 token 数取负。

为什么“最长前缀优先”是对的？论文给出了一个离线情况下的最优性定理。

定理 3.1。对一批（事先全部已知的）请求，只要缓存容量不小于最长请求的长度，按请求基数树的深度优先（DFS）顺序处理就能达到最优的缓存命中率；而“最长前缀优先”的顺序就等价于一种深度优先顺序。

证明的思路分两步，用到的都是很朴素的观察：

  • 先给出一个下界。把这批请求全部插进一棵基数树 \(T\)。树上每条边 \(e\) 对应的那段 KV 缓存，至少要算一次，记它的大小为 \(|e|\)。所以总计算量 \(C\) 满足下面左边的不等式。命中率等于 1 减去“实际算了的”占“全部输入”的比例，所以 \(C\) 越小命中率越高：
    $$C\;\ge\;\sum_{e\in\mathrm{edges}(T)}|e|,\qquad \text{命中率}=1-\frac{C}{\sum_{r\in R}(\text{请求 } r \text{ 的输入 token 数})}$$
  • 再说明深度优先能达到这个下界。深度优先遍历时，一条边第一次被算出来之后，接下来处理的恰好是它下面的整棵子树；处理子树期间，这条边一直被命中，处理完就再也不会回来。缓存容量不小于最长请求的长度，意味着从根到任何叶子的一整条路径都放得下，所以这条边在它的子树处理完之前不会被 LRU 淘汰。于是每条边只算一次，\(C\) 恰好等于下界，命中率达到最优。
  • 最后说明“最长前缀优先”就是深度优先。用归纳法：假设刚处理完节点 \(y\)，从根到 \(y\) 的路径都在缓存里。还没处理的节点中，和这条路径的“最近公共祖先”越深，它和已缓存内容的共享前缀就越长；最长前缀优先会选中公共祖先最深的那个节点，这正是深度优先会选的下一个节点。

拿上面示意图里的六个请求验证一下：树上有两条示例边（各 1,000 个 token）和六条问题边（各 50 个），边长之和是 2,300，所以最优命中率是 1 − 2,300 ÷ 6,300 ≈ 63.5%，正好是最长前缀优先达到的数（推算）。

在线服务时，请求是陆续到达的，严格的深度优先顺序会被打乱。论文在附录 A.3 论证：每加入一批新请求，最长前缀优先仍会在“新长出来的那部分树”上近似地做深度优先。论文也在脚注里承认，实际计算和定理的证明并不完全一样，因为输出有多长事先不知道，可能导致 KV 缓存被淘汰后重算。

贪心调度的代价：饥饿。最长前缀优先是贪心的。如果不断有能命中长前缀的新请求到来，一个和谁都不共享前缀的请求可能一直排不上，被“饿死”。论文明确承认这一点，把它和公平调度方法的结合留作未来工作。今天的 SGLang 默认用先来先服务，最长前缀匹配是一个可选的调度策略（见“后来怎么样了”）。

3.5 多张 GPU

张量并行。张量并行把每一层的注意力头分给多张 GPU，每张 GPU 只存自己那部分头的 KV。由于所有 GPU 处理的是同一批请求、同样的 token，基数树上的操作在每张 GPU 上完全一样，所以每张 GPU 各自维护一份分片的 KV 缓存即可，不需要额外同步。这和 vLLM 让所有 GPU 共用一张块表是同一个道理（见 vLLM 精读 §4.6）。

数据并行（附录 A.4）。多个完整的模型副本（worker）同时服务时，每个 worker 维护自己的一棵子树，前面的路由器维护一棵“元树”，记录各个前缀缓存在哪个 worker 上。一批新请求到达路由器时，先在元树上做前缀匹配，再按“亲和度”分发：一个请求和某个 worker 已缓存的内容、以及和同组其他请求共享的前缀越长，就越倾向于发给那个 worker。路由器和 worker 各自独立更新自己的树；worker 淘汰了缓存时，把淘汰事件写进一个队列，路由器在不忙的时候再处理，更新元树。这是一个弱一致的分布式缓存。论文用 4 个 worker 在 MMLU 上测试，吞吐量随 worker 数线性增长，命中率达到最优，额外开销很小。作者也指出，把请求集中到有缓存的 worker（数据局部性）和把请求均匀分散（并行效率）之间存在取舍，更好的策略留作未来工作；同期的 Preble 基于早期版本的 SGLang 研究了数据并行下的调度。

读这一节时容易误解的地方：
  • 名字里有 Attention，但它不是一种新的注意力计算方法。RadixAttention 是一套 KV 缓存的管理与调度方案。真正做注意力计算的仍是普通的内核（论文用的是 FlashInfer 和 Triton 写的内核），只要它们能从“每页一个 token”的非连续显存里读 KV 就行。
  • 复用省的是 prefill 和显存，省不了 decode。如果每个请求的输出很长、请求之间又几乎没有共享，那么大部分时间花在逐个生成 token 上，缓存帮不上忙。§6 的“多轮对话（长输出）”基本没有加速，原因就在这里。
  • 复用是精确的。RadixAttention 只复用逐 token 完全相同的前缀，算出来的结果和不复用时一样。相关工作里的 PromptCache 允许复用不在开头的片段，论文引用说它会让准确率最多下降 43%。
  • 没有命中时几乎没有代价。§6.3 测得，在完全没有复用机会的负载上，维护基数树的时间不到总时间的 0.3%，所以 SGLang 默认打开它。

4 压缩有限状态机：格式里写死的部分一步跳过去

这一节要回答的问题：LM 程序经常要求模型输出严格符合某种格式，比如 JSON schema。现有系统是怎么保证格式的？为什么这样做很慢？SGLang 怎么让解码在格式规定死的地方一次前进好几个 token？这样做又带来了哪些新问题？
先补一点背景：约束解码与有限状态机。

语言模型每一步输出的是整个词表上的概率分布，任何 token 都有可能被采样到，所以模型只是“大概率”会按要求的格式输出，并不能保证。约束解码的做法是：在采样之前，把所有会破坏格式的 token 的概率直接设成 0（实现上是把它们的 logits 改成负无穷，称为 logits 掩码），这样采样出来的结果一定合法。

怎么知道哪些 token 会破坏格式？常用的办法（论文引用的 Outlines 的做法）是把格式写成正则表达式，再把正则表达式转换成有限状态机（FSM）。有限状态机是一张有向图：节点叫“状态”，边上写着字符或字符串；从初始状态出发，每读入一段文字就沿着对应的边走到下一个状态，最后停在“终止状态”上，就说明整段文字符合格式。解码时，系统记住当前所在的状态，看从这个状态出发能走哪些边，只放行那些能让状态机继续走下去的 token。

举个本站的例子：格式是 "grade": "[ABCD]"。一开始，状态机要求依次读入 "、g、r……这串固定字符，所以第一步只有和 "grade" 对得上的 token（比如 "、"gr）被放行，"name 这样的 token 被掩掉。走到字母那一步时，只有 A、B、C、D 开头的 token 被放行。

难点在于：正则表达式和状态机是按字符定义的，模型却是按 token 输出的，一个 token 可能包含好几个字符，也可能横跨格式里的两个部分。字符和 token 之间没有一一对应，所以系统要预先算好“在每个状态下，词表里哪些 token 合法、读完之后会走到哪个状态”。这一步预处理不便宜，§6.3 会看到它对速度的影响。

问题在哪里。现有系统都是一个 token 一个 token 地解码：每一步做一次完整的模型前向，算出概率，按当前状态掩掉非法的 token，采样一个，更新状态，再进入下一步。可是格式里经常有一长段是写死的。作文评委例子里，输出必须以 {"summary": " 开头，这 13 个字符里，每个位置都只有一种合法的字符，模型根本没得选。按 token 解码时，这段文字会被拆成 {"、summary、":、 " 四个 token，于是系统要做四次完整的前向，只为了产出四个早已确定的 token。论文认为，现有系统之所以只能这样做，是因为有限状态机和执行模型的部分没有结合在一起，无法一次处理多个 token。

怎么压缩。SGLang 先按字符（而不是按 token）构造原始的有限状态机，再找出其中的“单一转移边”并合并。附录 B.1 给出了两个定义：

  • 单一转移边：一条边的起点只有这一个后继状态，并且这条边上只接受一个字符（或字符串）。也就是说，走到这条边的起点时，下一步没有任何选择。
  • 压缩边：如果边 \(e_1,\dots,e_k\) 都是单一转移边，就把它们和前面相邻的边 \(e_0\) 合并成一条边，边上的文字是 \(e_0,e_1,\dots,e_k\) 上文字的拼接。

从按字符构造的状态机出发，反复把单一转移边并进它前面的边，直到不能再合并为止，就得到压缩有限状态机。这个方法适用于任何正则表达式。

跳跃解码。解码过程中，每生成一个 token，系统就拿这个 token 对应的字符串，在当前状态的出边里找以它开头的那条边，沿着走下去。如果走到的状态的出边是一条压缩过的长边，系统就能预知接下来好几轮会生成什么，于是把整段字符串一次性追加上去。附录 B.2 把这个过程叫 Jump Forward（向前跳），加速就发生在这里。被追加的多个 token 由模型在一次前向里并行处理，就像 prefill 处理用户输入一样，代价远小于逐个 decode。

LMSYS 的博客补充了一个实现细节：跳跃时，SGLang 直接结束当前的请求，再把“原文 + 跳过的那段字符串”作为一个新请求放回队列。因为有 RadixAttention，新请求会在基数树上命中原来那部分的 KV 缓存，真正需要计算的只有新追加的那几个 token。这说明压缩有限状态机能这么简单地实现，靠的正是前一节的前缀缓存。博客里还有一个直观的例子：让模型按 JSON 填写哈利·波特的信息，学院字段只能是四个学院之一，模型一旦输出 “G”，后面的 “ryffindor” 就是唯一可能，可以直接跳过去。

新问题一：跳过的文字怎么切成 token。跳过去的是一段字符串，可后续解码需要的是 token。随便切会出问题：模型训练时见到的总是分词器的标准切法，如果把 {"summary": " 切成 {"、summa、ry、":␣" 这种模型几乎没见过的组合，后面 token 的概率分布就会被扭曲。附录 B.2 的办法是重新分词：把之前的全部文字连同跳过的字符串，用原始的分词器重新切一遍，得到 {"、summary、":、␣" 这种标准切法。论文说额外开销很小；LMSYS 博客给出的测量是约 4%。

新问题二：概率被扭曲。附录 B.3 讨论了一个还没解决的问题。假设等级字段不是 [ABCD][+-]?，而是四个词组 Excellent|Above Average|Fair|Below Average。模型并不知道有哪几个选项，它可能本想输出等级字母 “A”；状态机一看，以 A 开头的选项只有 “Above Average”，于是直接跳到 “Above Average”。结果，“Above Average” 被选中的概率实际上只是模型输出第一个 token “A” 的概率，和模型对这个完整选项的真实偏好不是一回事。要算出每个选项的准确概率，得把所有能拼出这个选项的 token 序列的概率加起来，这会让解码变复杂、变慢。一个折中办法是在提示里直接列出选项或正则表达式，让模型知道有哪些选择，但这并没有从根本上解决问题。（SGLang 的 select 原语走的是另一条路：它比较的是各个完整选项的概率，然后选最高的那个。）

效果。§6.3 的消融实验在 JSON 解码基准上测得，压缩有限状态机让吞吐量提高到 1.6 倍，因为它能一次解码多个 token。另一个结果同样重要：状态机的预处理必须对一批请求只做一次、反复使用；如果每个请求都重新预处理一遍，吞吐量会降到原来的 1/2.4。

读的时候要注意的几点：
  • 只有格式里写死的部分能跳过，自由文本字段（比如 summary 的正文）照样逐个 token 解码。所以加速的幅度取决于固定部分在输出里占多大比例：键名多、值很短的 JSON 加速明显，值是长段文字的 JSON 加速有限。
  • 正则表达式描述不了任意深度嵌套的结构（那需要上下文无关文法）。论文的方法限定在正则表达式能表达的格式上。
  • “JSON 模式提速 1.6 倍”是和关掉压缩有限状态机的 SGLang 比，不是和别的系统比。LMSYS 博客里和 Outlines + vLLM、Guidance + llama.cpp 的比较（延迟最多降一半、吞吐最高 2.5 倍）用的是另一套设置。

5 API 投机执行：只能调 API 的模型怎么省钱

这一节要回答的问题：前两项优化都要改动模型的推理过程，所以只能用在自己部署的开源模型上。对于 GPT-4 这种只能通过 API 调用的黑盒模型，运行时既看不到 KV 缓存，也改不了解码过程。多次调用的程序在这种情况下还能怎么加速、怎么省钱？
先补一点背景：API 怎么收费。

调用模型 API 时，每次请求都要把完整的提示发过去，服务方按输入 token 数和输出 token 数分别计费。一个程序如果连续调用三次、每次都带着同一段很长的上下文，这段上下文就要付三次钱，每次也都要等服务方重新处理一遍。

论文的例子是让模型描述一个角色，程序写成 s += context + "name:" + gen("name", stop="\n") + "job:" + gen("job", stop="\n")：先给一段上下文，然后让模型写名字（遇到换行停），再写职业（遇到换行停）。按字面执行，两个 gen 对应两次 API 调用，上下文的输入费付了两次。

投机执行的做法是：在第一次调用时忽略停止条件，让模型多生成一些 token。模型很可能顺着模板写下去，比如写出 “Alice（换行）job: engineer（换行）”。解释器把多出来的这部分留着，等程序执行到 "job:" + gen("job") 时，先检查多出来的文字是不是正好以 “job:” 开头：如果对得上，就直接把 “engineer” 当作 job 的结果，第二次调用就省掉了；对不上，再老老实实发起调用。这和 CPU 的“投机执行”是一个思路：先按最可能的情况往前做，猜对了白赚，猜错了丢掉重来。

投机执行调用 1，不在换行处停上下文 + "name:" → "Alice↵job: engineer↵…"→解释器对照模板“job:” 对上了，取出 "engineer"上下文计费 1 次
↵ 表示换行。本站示意图，例子来自原文 §5。

效果。论文用 GPT-3.5 从维基百科页面里抽取三个字段。配合 few-shot 提示，模型按模板续写的准确率很高，投机执行把输入 token 的花费降到约三分之一：原来要调三次、上下文付三次钱，现在一次就够了。

读的时候要注意：这个优化能不能奏效，取决于模型是否会乖乖按模板续写，论文说要靠“仔细的提示工程”（比如 few-shot 示例），但没有给出准确率的具体数字；猜错时多生成的输出 token 白白付费。它也只适用于“两个 gen 之间夹着固定文字”的连续调用。

先补一点背景：吞吐量和延迟这两个数是分开测的。

吞吐量：一次提交足够多的程序实例，让系统满负荷运行，数每秒能完成多少个程序（programs per second）。这时加速来自两方面：请求之间共享前缀，省掉重复的 prefill；共享的 KV 只存一份，显存省出来，批能开得更大。延迟：每次只跑一个程序、不做批处理，对多个实例取平均。这时没有“别的请求”可以共享，加速来自程序内部的前缀复用（比如几次调用共用同一段上文）、程序内并行，以及更少的解码步数。所以同一个基准上，吞吐量和延迟的加速倍数可以很不一样。

  • 共享的前缀越长、输出越短，优势越大。MMLU 每题只解码 1 个 token，时间几乎全花在 prefill 上，而 5 个示例的 KV 可以被所有题目复用，吞吐量约是 vLLM 的 6.5 倍。论文特别指出，RadixAttention 在这里对吞吐和延迟都有好处：共享 KV 省下的显存让批更大，提高最大吞吐；少算的 prefill 让第一个 token 来得更早。
  • 两层共享最赚。HellaSwag 既共享 20 个示例，又让同一道题的 4 个选项共享题目正文，按柱高推算吞吐量约是 vLLM 的 30 倍，延迟约为 1/7.3，是图中差距最大的一项。

6.3 消融实验：每个部件贡献了多少

命中率与性能的关系。原文图 8(a)(b) 在思维树基准上，通过在运行时故意让一部分已匹配的 token 不被复用，人为地调低命中率，观察第一个 token 的延迟、总延迟、批大小和吞吐量怎么变化。结论是：命中率越高，批越大，吞吐量越高，延迟越低。按本站读数，命中率从 0 升到约 99% 时，平均批大小从约 20 增加到约 48，吞吐量从约 340 增加到约 1,150 token/秒（约 3.4 倍），总延迟从约 420 秒降到约 125 秒，第一个 token 的延迟从约 24 秒降到约 2 秒。这组数字说明，前缀缓存同时作用于“省显存、批更大”和“少算 prefill”两条路径。

RadixAttention 的开销。在一个完全没有复用机会的基准上（ShareGPT 数据集的吞吐量测试），跑 100 个请求共用 74.3 秒，其中维护 RadixAttention 数据结构的时间只有 0.2 秒，不到 0.3%。原因是树操作的复杂度是线性的，而且常数很小。因此 SGLang 默认打开 RadixAttention。

压缩有限状态机。在 JSON 解码基准上，压缩有限状态机让吞吐量提高到 1.6 倍；而如果不把状态机的预处理结果在一批请求之间复用，每个请求都重做一遍，吞吐量会降到原来的 1/2.4（见 §4）。

读实验结果时要注意的几点：
  • vLLM 用的是没有跨请求前缀缓存的老版本（v0.2.5）。所以和 vLLM 的比较，本质上是“有没有自动的跨请求 KV 复用、有没有程序结构信息”的比较，而不是和今天的 vLLM 比。今天的 vLLM 默认打开了自动前缀缓存（见“后来怎么样了”）。
  • 吞吐量和延迟的测法不同。吞吐量是大批量满负荷的结果，延迟是一次只跑一个程序的结果，两者的加速来源不同，不能互相换算。
  • 和 Guidance、LMQL 的巨大差距主要来自后端。它们用的是 llama.cpp 和 HF Transformers，不支持批处理或没有优化，几十倍的差距不能全算在 SGLang 的新技术上。
  • 多模态的对照是 HF Transformers 里的参考实现，不是专门的推理服务系统。
  • 本页图表里的逐项倍数是本站读数。论文正文只给了“最高 6.4×/3.7×”“命中率 50%–99%”“平均达到最优的 96%”等汇总数字。

7 相关工作：谁也在做 KV 复用，谁也在做 LLM 编程

这一节要回答的问题：KV 缓存复用和“给大模型写程序”都不是 SGLang 独有的想法。和同期工作相比，SGLang 到底新在哪里？

KV 缓存复用。论文承认很多工作也在探索 KV 复用，其中不少是同期的。它认为自己的独特之处在于：RadixAttention 第一个提出把 KV 缓存当作基于树的 LRU 缓存来管理，也是第一个同时支持多层共享、缓存感知调度、前端与运行时协同调度以及分布式场景的方案。逐个对比：

  • vLLM 和 ChunkedAttention 处理了一些简单的复用场景（比如共享系统提示），但不支持多层的树状共享，也没有 LRU 缓存。
  • PromptCache 提出按模块复用 KV，可以复用不在开头的片段，但这样算出的结果和原来不同，论文引用说准确率最多会下降 43%。
  • Hydragen、FlashInfer、ChunkedAttention 关注的是 CUDA 内核层面的优化：当一批请求共享前缀时，怎样让注意力计算对这段前缀只读一次、算得更快。它们没有“LRU 缓存”这个概念。这一层和 RadixAttention 是互补的：一个决定“哪些 KV 留着、谁和谁共享”，一个决定“共享的 KV 怎么算得快”。
  • API Serve 和 LLM-SQL 研究特定应用里的 KV 复用（与外部 API 调用交错执行、关系数据库查询），但没有基数树和缓存感知调度。

LLM 编程框架。Guidance、LMQL、DSPy、LangChain、AutoGen、LLM Compiler 等都属于这一类，其中 Guidance 和 LMQL 与 SGLang 最像（§2 已比较）。论文认为自己的创新在于为这种编程模型配上了新的运行时优化；SGLang 和这些框架是兼容的，可以给它们加速（比如 §6 的 DSPy 实验）。SGLang 也和许多常见的推理优化（连续批处理、PagedAttention、量化、投机解码等）兼容。

8 未来方向与结论

这一节要回答的问题：作者认为 SGLang 还有哪些局限？哪些方向值得继续做？

论文列出了六个未来方向：支持更多的输出模态；让 RadixAttention 跨越多级存储工作（显存之外再用 CPU 内存、磁盘）；在 RadixAttention 里支持模糊的语义匹配（不要求前缀逐 token 相同）；在 SGLang 之上提供更高层的原语；解决缓存感知调度的饥饿问题；增强编译器，做调度、内存规划等更高级的静态优化。其中“跨多级存储”这一条，后来在 SGLang 里实现了（见本页最后一节“后来怎么样了”）。

结论部分重申：SGLang 是一个用来编写和高效执行结构化 LM 程序的框架，通过 RadixAttention、压缩有限状态机和语言解释器等优化，显著提高了复杂 LM 程序的吞吐量、降低了延迟，可以用来开发高级的提示技术和 agent 工作流。

9 附录 D：编译模式，以及让 GPT-4 帮忙调整提示顺序

这一节要回答的问题：正文默认用解释器执行 SGLang 程序。如果先把程序编译成计算图再执行，能多做哪些优化？论文附录给了一个有意思的例子：通过调整提示里各段文字的顺序，让可共享的前缀变长。

中间表示。作者为 SGLang 设计了一种中间表示（IR），把程序表示成计算图：节点是原语操作，边是依赖关系。+= 和 + 的每个操作数都是一个节点，节点类型包括 ConstantText（常量文字）、Argument（函数参数）、Gen、Select、Variable（读取某个生成结果）、Fork、GetForkItem 和 Join。每次调用一个被装饰的函数、或者执行一次 fork，都会产生一条新的提示状态，也就是一条新的“流”。依赖分两种：流内依赖，同一条流里用 += 提交的操作必须按顺序执行；流间依赖，一条流要读另一条流里某个变量的值，必须等那边算完。

原文附录图 14 用一个“思维骨架”程序举例：先在一条流里生成两条简短的建议，再调用两次“展开”函数，各开一条新流，把两条建议分别扩写成段落；最后回到第一条流，把两段扩写拼起来，生成总结。

示意图：思维骨架程序对应的三条流与它们之间的依赖
流 1“这里有 2 条建议…”→Gen：建议 1→Gen：建议 2→ 等待流 2、3 →拼接两段扩写→Gen：总结
流 2“请展开这条建议：”→读取流 1 的建议 1→Gen：段落
流 3“请展开这条建议：”→读取流 1 的建议 2→Gen：段落
每条流内部按顺序执行；青色框是流间依赖（要等另一条流把变量算出来）。流 2 和流 3 之间没有依赖，可以并行，而且它们以同一段常量文字开头，可以共享这段前缀。本站示意图，对应 原文附录图 14 ↗。

计算图是用追踪的方法生成的：拿抽象的参数把程序跑一遍，动态地记录下图。这种方法的局限是只能处理不依赖数据的控制流（比如 if s["related"] == "no" 这种根据生成结果决定走向的分支就无法追踪），作者计划以后解决。图建好之后交给图执行器运行，不用再重新解释 Python 程序，好处包括可以改写计算图做优化、减少运行时开销、可以把程序序列化保存。执行时，为每条流启动一个流执行器，按拓扑顺序把节点分发到各条流上。

请以数学专家的身份解答下面的题。这是一道题：{具体题目}
蓝色 = 所有请求都相同、可以共享的前缀；绿色 = 每个请求不同的部分；灰色 = 虽然每个请求都相同，但因为排在可变内容后面，无法作为前缀共享。本站示意图，改写自原文附录 D.2 的例子。

这种调整之所以有意思，是因为传统的程序分析做不到：提示里是自然语言，调换顺序后意思变没变，只有“读得懂”的人或模型才能判断。所以作者让 GPT-4 来做：写一段带几个示例的提示，教 GPT-4 理解 SGLang 的中间表示，再让它重排图中的节点。实验收集了 20 个网上的提示模板，用 5 个做示例、15 个做测试。在 15 个测试模板里，GPT-4 成功地在不改变语义的前提下重排了 12 个（人工检查确认），平均让可共享的前缀变长了 60 个 token。失败的情况来自 GPT-4 误解了节点的语义，过于激进地把所有常量都提到前面，即使这样改变了原意。作者认为这只是一个探索，要让这类优化可靠还需要更多工作。

10 后来怎么样了

这一节只写能查证的事实，出处在每段末尾或表格里注明，查证日期为 2026-10-19。

10.1 SGLang 成了一个通用的推理服务引擎

论文发表后，SGLang 的重心从“LM 程序的语言 + 运行时”逐渐转向它的运行时部分，成为一个通用的推理服务框架。它的 GitHub 仓库描述今天写的是“面向大语言模型和多模态模型的高性能服务框架”；截至 2026-10-19 有 37,341 个 star、9,680 个 fork，采用 Apache-2.0 许可。仓库的 README 说明：项目由非营利开源组织 LMSYS 托管；支持 NVIDIA、AMD、Google TPU、Intel、华为昇腾、摩尔线程等多种硬件；verl、slime、AReaL、Tunix、Miles 等强化学习训练框架用它来生成 rollout；NVIDIA Dynamo、llm-d、Ray Serve 等部署和编排系统可以以它为后端。据 TechCrunch 2026-01-21 的报道，SGLang 的核心成员成立了公司 RadixArk，由论文共同一作 Ying Sheng 任 CEO，SGLang 继续作为开源项目维护。

出处：GitHub API 与 sgl-project/sglang README ↗；TechCrunch ↗。

10.2 论文里的几个想法后来的样子

  • RadixAttention 仍然默认打开。今天的 SGLang 文档里，--disable-radix-cache 默认为 False（即默认开启前缀缓存），--page-size 默认为 1（与论文“每页一个 token”一致），淘汰策略 --radix-eviction-policy 默认为 lru，另可选 lfu、slru、priority。
  • 缓存感知调度变成了可选项。文档里 --schedule-policy 的默认值是 fcfs（先来先服务），可选值包括 lpm（最长前缀匹配，即论文 §3.4 的做法）、dfs-weight、random、lof、priority、routing-key。论文的实验用的是最长前缀优先；今天默认改用先来先服务，文档没有说明原因。论文自己承认，最长前缀优先这种贪心策略可能让一些请求“饿死”（§3.4）。
  • 数据并行的缓存感知分发（附录 A.4）产品化了。SGLang v0.4（2024-12-04 的 LMSYS 博客）推出了缓存感知的负载均衡器：路由器维护一棵近似的基数树，预测请求在各个 worker 上的前缀命中率，把请求发给命中率高的 worker，不需要 worker 之间同步缓存状态，用 Rust 实现。博客在一个由多组长公共前缀构成的负载上（8 张 A100，Llama-3.1-8B，8 路数据并行）测得吞吐量从 82,665 提高到 158,596 token/秒，命中率从 20% 提高到 75%。同一版本还加入了把 CPU 调度和 GPU 计算重叠起来的“零开销”批调度器（相对上一版提速 1.1 倍），它能把基数树操作等 CPU 开销藏在 GPU 计算后面。
  • 多级存储（论文的未来方向之一）实现了。今天的 SGLang 提供分层缓存 HiCache（--enable-hierarchical-cache，默认关闭）：在 GPU 显存之外，再用主机内存（默认大小为显存池的 2 倍）以及 file、Mooncake、3FS、NIXL、AIBrix 等存储后端存放 KV 缓存。这方面的背景见本站的 KV 缓存分层存储 页面。
  • 约束解码换成了可插拔的语法后端。今天的 --grammar-backend 可选 xgrammar、outlines、llguidance。v0.4 的博客说，接入 XGrammar 后 JSON 解码比其他开源方案最多快 10 倍。XGrammar（arXiv 2411.15100）支持上下文无关文法，弥补了 §4 提到的“正则表达式描述不了任意嵌套结构”的局限。

出处：SGLang 文档：Server Arguments ↗；LMSYS 博客：SGLang v0.4 ↗；XGrammar ↗。

10.3 前缀缓存成了各家推理引擎的标配

论文写作时（2024 年中），它在脚注里说 RadixAttention 已经被部分地并入了 vLLM，作为一个可选的实验性功能。到今天，主流引擎都默认打开了跨请求的前缀缓存，只是实现方式不同：

系统复用的粒度怎么找到可复用的前缀淘汰默认
SGLang1 个 token（页大小默认 1）基数树上逐 token 匹配LRU（默认），可选 LFU 等开启
vLLM（自动前缀缓存）整块，只缓存填满的块（默认块大小 16）给每个块算哈希：父块的哈希 + 本块的 token + 额外的键（LoRA、多模态输入等）LRU开启（enable_prefix_caching = True）
TensorRT-LLM（KV cache reuse）整块，只有填满的块能被共享（文档中默认每块 128 个 token）按块匹配LRU，可选卸载到主机内存KVCacheManager 中默认开启

出处：vLLM 设计文档：Automatic Prefix Caching ↗ 与 vLLM 源码 vllm/config/cache.py；TensorRT-LLM 文档：KV cache reuse ↗；SGLang 文档同上。

对比可以看出两种思路。SGLang 用基数树，匹配粒度细到单个 token，节点可以在任意位置拆分；vLLM 和 TensorRT-LLM 沿用分页的块，用“链式哈希”标识每个块连同它之前全部内容，只有整块相同才能复用。后者和已有的块管理器结合得更自然，代价是最后一个没填满的块无法共享。Hugging Face 的 TGI 在 v3（2024-12-09 发布）也把前缀缓存列为主要的提速来源之一，文档说查找开销只有几微秒，并在自己的长提示基准上报告了相对 vLLM 的大幅加速（这是 TGI 自己的测试）。

本站相关页面：SGLang 用 FlashInfer 的内核读取按 token 分页的 KV（见 FlashInfer 拆解页）；连续批处理的来龙去脉见 Orca / Sarathi-Serve；SGLang 在强化学习训练里作为 rollout 引擎的用法见 RL 系统。

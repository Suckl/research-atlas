0 导读：这篇论文解决什么问题

2022 年前后，要把 GPT-3 这样的大模型做成在线服务，常见的搭法是两层：上层是 NVIDIA Triton 这样的推理服务系统，负责接请求、排队、把若干请求凑成一批；下层是 FasterTransformer 这样的执行引擎，负责在 GPU 上真正把模型算一遍。这套分工原本是为图像分类、BERT 这类“一个请求只要把模型跑一遍”的任务设计的。生成式模型不一样：它每次只吐出一个 token，一个请求要把模型反复跑几十到几百遍才能结束，而且每个请求要跑多少遍事先不知道。于是，同一批里先生成完的请求只能陪着最长的请求一起跑完才能返回，批开始之后才到的新请求只能干等整批结束。

Orca 的核心想法是把调度的粒度从“一个请求”缩小到“模型的一次前向计算”（论文叫一次迭代）：调度器每次只让引擎跑一次迭代，跑完立刻收回控制权，生成完的请求马上返回，新到的请求下一次迭代就能加入。这就是迭代级调度（iteration-level scheduling），今天大家更常叫它连续批处理（continuous batching）。为了让进度各不相同的请求真的能放进同一批一起算，论文又提出选择性批处理（selective batching）：线性层这类逐个 token 计算的算子把所有请求的 token 摊平成一个大矩阵一起算，只有注意力按请求拆开分别算。作者在这两个想法之上做了一个能跨多台机器运行千亿参数模型的系统，在 GPT-3 175B 上，延迟相同时吞吐量是 FasterTransformer 的 36.9 倍。

今天几乎所有主流推理引擎都以连续批处理为基础，所以这篇论文是读 vLLM、Sarathi-Serve、DistServe 等后续工作的起点。读过 vLLM 精读的读者会发现，vLLM 正是从 Orca 留下的问题（按最大长度预留 KV 显存）接着往下做的。本页会从零讲清楚迭代级调度和选择性批处理，并在最后说明 Orca 的哪些设计成了标准、哪些被后来的系统改掉了。

1 引言：生成式模型要“跑很多遍”，旧的调度方式跟不上

这一节要回答的问题：当时已经有成熟的推理服务系统（Triton、TensorFlow Serving）和高度优化的执行引擎（FasterTransformer），为什么它们服务 GPT 这类生成式模型时表现不好？作者认为问题不在算子写得快不快，而在“服务系统和执行引擎之间多久沟通一次”：它们按整个请求来调度，而生成式模型的请求天生要跑很多次迭代。
先补一点背景：推理服务系统和执行引擎各管什么。

把一个训练好的模型变成在线服务，通常分两层来做。执行引擎（如 TensorRT、FasterTransformer、TVM、PyTorch）只关心“给我一批输入张量，我把模型算一遍、把结果交回去”，它把矩阵乘、注意力这些算子在 GPU 上实现得尽可能快。推理服务系统（如 Triton Inference Server、TensorFlow Serving）站在引擎上面，负责对外暴露接口（HTTP、gRPC）、维护请求队列、决定什么时候把哪些请求凑成一批交给引擎、拿到结果后回复客户端。这种分层的好处是两边可以独立开发：同一个服务系统可以接各种模型和引擎。

服务系统最重要的优化之一是批处理：把多个请求的输入拼成一个更大的张量，让引擎一次算完。GPU 有成千上万个计算单元，喂给它的张量越大越能用满；更关键的是，模型参数从显存读出来一次就能给批里所有请求共用（第 2.3 节会算一笔账）。所以引擎的吞吐量高度依赖批的大小。

对 ResNet 或 BERT 这样的模型，一个请求只需要把模型跑一遍，服务系统把一批请求交给引擎、引擎算完交回，一来一回就结束了。GPT 这类自回归生成模型则不同：它每跑一遍只产出一个 token，这个 token 要作为下一遍的输入，所以一个请求要生成多少个 token，就得把模型跑多少遍。论文把这叫多迭代特性（multi-iteration characteristic）。

问题出在两层之间的接口上。当时的服务系统把“一批请求”整个交给引擎，引擎要把批里所有请求都生成完，才一次性把结果交回。由于不同请求需要的迭代次数不同，这带来两个后果：

  • 先完成的请求不能返回。批里某个请求已经生成了结束符，但只要批里还有请求没结束，它的结果就交不回服务系统，客户端只能干等，延迟被白白拉长。
  • 后到达的请求不能加入。批一旦交给引擎，中途新来的请求只能在队列里等这一整批全部结束，排队时间可能非常长。

论文的解决办法是让服务系统按迭代调度引擎：每次只让引擎在当前这批请求上跑一次迭代，然后把控制权交回调度器。这样，新请求最多等一次迭代就有机会开始处理；调度器每次拿回结果都检查一遍哪些请求已经结束，结束的立刻返回给客户端。

但这马上引出第二个难题：按迭代调度后，同一批里的请求进度各不相同，有的刚到、要处理整段输入，有的已经生成了几十个 token。Transformer 的注意力算子要求批里每个请求的张量形状一致，进度不同的请求凑不成一个规整的批。作者的办法是选择性批处理：只对一部分算子拼批，注意力按请求拆开单独算。作者观察到，不给注意力拼批对效率影响很小，因为注意力本身没有模型参数，拼批本来也省不下读参数的开销（第 3 节详细解释）。

在这两项技术之上，作者实现了分布式推理服务系统 Orca：它借用训练系统里的层内并行和层间并行来放下几千亿参数的模型，并设计了一个同时考虑显存管理和多机流水线的调度算法。实验用了从 13B 到 341B 参数的多种 GPT-3 配置，与 FasterTransformer 相比，在相同延迟水平下吞吐量提高 36.9 倍。作者还指出，只要是基于 Transformer、按自回归方式生成的模型，图像、视频、语音等领域都可以用同样的方法，但论文的实验只做了语言模型。

几个容易混淆的名字：
  • 论文自己的术语是迭代级调度。“连续批处理”（continuous batching）这个叫法是后来流行起来的，例如 Anyscale 在 2023 年 6 月的一篇博客里明确说它也叫迭代级调度；TensorRT-LLM 叫它 in-flight batching，FriendliAI（作者所在公司）叫它 iteration batching。它们指的是同一件事。
  • 本文的 Orca 是首尔大学和 FriendliAI 的推理服务系统，与微软 2023 年发布的 Orca / Orca 2 语言模型无关。
  • Orca 的代码没有开源。vLLM、Sarathi-Serve 等论文里作为对照的 “Orca”，都是那些论文的作者按 Orca 论文的描述自己复现的。

2 背景：GPT 怎么一步步生成，推理服务系统怎么分工

这一节要回答的问题：GPT 生成一段文字时，GPU 上到底按什么顺序算了哪些东西？“一次迭代”指什么，第一次迭代和之后的迭代有什么不同？一层 Transformer 里有哪些算子，哪些带模型参数？为什么生成过程中要一直保存 key 和 value？现有的服务系统又是怎么把请求交给引擎的？后面所有设计都建立在这些事实之上。

2.1 一次迭代、两个阶段：GPT 的推理过程

GPT 接收一串输入 token，然后一个接一个地生成后续 token，直到生成结束符 <EOS> 或达到长度上限。论文用一个三层 GPT 的例子（原文图 1a）说明这个过程：输入是 “I think this”。论文把“把模型的所有层从头到尾跑一遍”定义为一次迭代，每次迭代产出一个 token。

  • 第 1 次迭代一次性读入全部输入 token “I think this”，算出下一个 token “is”。论文把这个负责处理输入、产出第一个输出 token 的阶段叫初始阶段（initiation phase）。因为输入 token 全部已知，它们可以在一次迭代里并行处理。
  • 第 2、3 次迭代各自只输入上一次刚生成的那一个 token（“is”，然后 “great”），分别产出 “great” 和 <EOS>。论文把这些迭代合称增量阶段（increment phase）。因为每一步都依赖上一步的输出，这个阶段只能一步一步地走。

今天的文献通常把这两个阶段叫 prefill 和 decode。本页沿用论文的叫法，但两者是一回事：初始阶段 = prefill，增量阶段 = decode。

先补一点背景：注意力为什么需要保存 key 和 value。

Transformer 每一层里，每个 token 都会算出三个向量：query、key、value。处理第 \(t\) 个 token 时，注意力拿它的 query 去和第 1 到第 \(t\) 个 token 的 key 逐一做点积，经过 softmax 得到一组权重，再用这组权重对这些 token 的 value 加权平均。GPT 使用因果遮挡，每个 token 只看它自己和它前面的 token，看不到后面的。

所以，第 \(t\) 步要用到前面所有 token 在这一层的 key 和 value。最朴素的做法是每一步把整段序列（输入加上已经生成的 token）重新算一遍，得到所有 key 和 value，但这样前面的 token 每一步都被重复计算。fairseq 提出的增量解码（incremental decoding）是把算过的 key 和 value 存下来，下一步直接复用，每步只算新 token 的那一份。FasterTransformer、Megatron-LM 也都这么做。这份被保存下来的数据，今天通常叫 KV 缓存；论文把它看作请求在多次迭代之间要维护的内部状态。更详细的解释见 vLLM 精读 §2.2。

论文用原文图 1c 对比了 Transformer 和 LSTM 维护状态的方式：LSTM 每一步只保留一个固定大小的记忆向量，处理多少个 token 都一样大；Transformer 的状态（每一层所有已处理 token 的 key 和 value）每过一次迭代就多一份。处理第 \(t\) 个 token 时，第 \(l\) 层的注意力要同时用到之前的 \(k_{l,1:t-1}\)、\(v_{l,1:t-1}\) 和当前的 \(k_{l,t}\)、\(v_{l,t}\)。这意味着注意力要处理的张量形状，取决于这个请求已经处理了多少个 token。这一点是第 3 节所有麻烦的根源。

2.2 一层 Transformer 里有哪些算子，注意力为什么特殊

GPT 只有一叠解码器层（原始 Transformer 有编码器和解码器两叠）。原文图 1b 列出了一层里按顺序执行的算子：先做层归一化（LayerNorm），然后是 QKV Linear（一次线性变换后切成 query、key、value 三份），然后是注意力，接着是 Attn Out Linear（注意力输出的线性变换）、残差相加（Add）、再一次层归一化，然后是 MLP（线性层、GeLU 激活、线性层），最后再做一次残差相加。

这里有一个后面会反复用到的定义。论文里的 “Attention” 采用窄定义：只包括“query 和 key 做点积、softmax、对 value 加权平均”这三步，不包括前后的 QKV Linear 和 Attn Out Linear（有些文献把这两个线性层也算进注意力里）。在窄定义下，注意力没有任何模型参数，它的输入全是当前请求自己的 query、key、value。

“逐 token”是什么意思？以线性层为例，输入矩阵的第 \(i\) 行乘以权重矩阵，就得到输出的第 \(i\) 行，跟其他行是什么内容毫无关系。所以把来自不同请求的 token 一行行堆在一起乘，每一行的结果和单独算时完全一样。LayerNorm、GeLU、Add 也是如此。注意力则不同：第 \(t\) 个 token 的输出取决于同一请求里它前面所有 token 的 key 和 value，而且绝不能混进别的请求的 token。所以注意力必须知道每个 token 属于哪个请求。这个区别就是第 3.4 节选择性批处理的出发点。

2.3 推理服务系统：调度器、执行引擎和批处理

先补一点背景：为什么批越大，吞吐量越高。

增量阶段每次迭代每个请求只处理一个 token，计算量很小，但每一层的权重矩阵都得从显存读到计算单元一遍。以 130 亿参数的模型为例，FP16 参数约 26 GB；A100 每秒能从显存读约 1.5 TB，光读一遍参数就要十几毫秒（推算），而真正的计算只要很短时间，GPU 大部分时间在等数据。如果把 32 个请求放进一个批，参数仍然只读一遍，却能同时为 32 个请求各算出一个 token。读参数的时间几乎不变，产出变成 32 倍。这就是论文说的“批处理能复用已经读进来的模型参数”。用下面的屋顶线小工具可以直观地看到：增量阶段（decode）在批很小时远远落在“受带宽限制”的一侧，批越大越往“受算力限制”的方向移动。详细推导见 vLLM 精读 §1。

论文用原文图 2 描述了当时的标准做法。服务系统（例如 Triton）的核心是一个调度器：它从请求队列里取出若干请求组成一批，交给执行引擎（例如 FasterTransformer）；引擎在这批请求上反复跑迭代，直到全部生成完，再把生成的文字一起交回服务系统。图里的例子是两个请求 x1 “I think” 和 x2 “I love” 组成一批，引擎分别生成 “this is great” 和 “you”。

3 挑战与方案：迭代级调度和选择性批处理

这一节要回答的问题：按请求调度具体会造成哪些浪费？如果改成每次迭代都重新调度，又会碰到什么新的障碍？论文用“挑战 C1 → 方案 S1，挑战 C2 → 方案 S2”的结构回答：C1 是先完成的请求走不了、后到的请求进不来，S1 是迭代级调度；C2 是进度不同的请求凑不成一批，S2 是选择性批处理。这一节是全文的核心。

3.1 挑战一：先完成的走不了，后到达的进不来

现有系统里，服务系统和执行引擎只在两个时刻打交道：服务系统把下一批交给空闲的引擎时，以及引擎把当前这批全部算完时。换句话说，调度的粒度是请求：引擎在整批请求全部结束之前，一直固定地处理这一批。

论文用原文图 3 举例：x1 “I think” 要生成 “this is great <EOS>”，共 4 次迭代；x2 “I love” 只生成 “you <EOS>”，2 次迭代就结束了。但因为它们在同一批里，引擎在第 3、4 次迭代仍然要为已经结束的 x2 做计算（图中的 “-”）。这些多余的计算降低了批处理的效率。更糟的是，x2 的结果要等到第 4 次迭代结束、整批交回时才能返回给客户端，平白多了两次迭代的延迟。同样，如果这批运行时来了新请求，它也必须等整批结束才能开始。

先补一点背景：训练为什么没有这个问题。

训练语言模型时，整段目标文字是已知的，可以用教师强制（teacher forcing）：把正确答案的前 \(t-1\) 个 token 直接当作预测第 \(t\) 个 token 的输入，于是一整段序列的所有位置能在一次前向计算里同时算完，不存在“有的序列先结束”的问题。只有推理时才必须一个 token 一个 token 地生成，所以“早完成、晚加入”是推理服务特有的问题，训练系统从来不需要处理它。

论文的结论是：按请求调度的机制处理不好具有多迭代特性的负载。这不是哪个引擎实现得不好，而是服务系统和引擎之间的接口本身决定的。

3.2 方案一：迭代级调度

迭代级调度把调度的粒度降到迭代。调度器不停地重复三件事：(1) 选出下一次迭代要处理的请求；(2) 让引擎在这些请求上只跑一次迭代；(3) 收回这次迭代的结果。因为每次迭代都会收到结果，调度器能及时发现哪个请求已经结束，并立刻把它生成的 token 返回给客户端。新到的请求只需等当前这一次迭代结束，就有机会被选中，排队时间大幅缩短。调度器对每次迭代处理多少个、哪些请求拥有完全的控制权。

原文图 4 画出了 Orca 的整体结构。请求从端点（endpoint，例如 HTTPS 或 gRPC 接口）进来，被放进请求池（request pool）；请求池管理着系统里所有请求的整个生命周期。调度器监视请求池，负责挑选请求、让引擎跑一次迭代、接收输出 token、再把每个 token 追加到对应的请求后面。执行引擎负责真正的张量计算，可以跨多台机器的多张 GPU 并行。请求结束后，请求池把它移除，并通知端点发出回复。

3.3 挑战二：处在不同进度的请求凑不成一批

迭代级调度说起来简单，真正落地时最大的障碍是批处理。要做到高效，引擎必须能把调度器选出的任意一组请求放在一起批量计算；如果只能一个一个地算，GPU 的大规模并行能力就浪费了。

先补一点背景：传统的批处理要求形状一致。

传统做法是把一批里每个请求的输入张量（形状 \([L, H]\)：\(L\) 个 token，每个是 \(H\) 维向量）在最前面加一维堆起来，得到形状为 \([B, L, H]\) 的三维张量，\(B\) 是批大小。这要求批里每个请求的 \(L\) 相同，因为一个张量的每一“片”必须一样大。比如在图 3 里，第 1 次迭代（初始阶段，两个请求都有 2 个输入 token）的输入是 \([2, 2, H]\)，第 2 次迭代（增量阶段，每个请求 1 个 token）是 \([2, 1, H]\)。如果长度不同，常见的补救办法是用无意义的填充（padding）把短的补到和最长的一样，代价是白算这些填充位置。

按迭代调度之后，任意两个请求 \(x_i\)、\(x_j\) 在下一次迭代未必能合成一批。论文列出了三种凑不成批的情况：

3.4 方案二：选择性批处理（selective batching）

选择性批处理的想法是：不必把模型里所有算子都改成批量形式，只对其中能批量化的那些算子拼批。上面三种情况的共同点是张量形状不规则，没法堆成一个大张量送进批量算子。但并非所有算子都在乎形状不规则。第 2.2 节说过，线性层、LayerNorm、Add、GeLU 都是逐 token 计算的，不需要区分 token 属于哪个请求。所以可以干脆去掉批这一维：把所有请求的 token 摊平，按顺序堆成一个形状为 \([\sum_i L_i, H]\) 的二维张量。例如图 4 里 x3 和 x4 的输入 \([2, H]\)、\([3, H]\) 可以拼成 \([5, H]\)，直接送进所有非注意力算子。

注意力则需要“请求”这个概念，因为它只能在同一个请求的 token 之间计算，通常用 cuBLAS 的批量矩阵乘来实现。所以选择性批处理在注意力前插入一个 Split 操作，把摊平的张量按请求拆开，对每个请求单独做注意力；注意力的输出再用一个 Merge 操作拼回摊平的张量，后面的算子又可以批量计算了。论文把这概括为：注意力按请求拆开，其余算子按 token 而不是按请求来拼批。

为了让增量阶段的请求能用上之前迭代算出的 key 和 value，Orca 用一个 Attention K/V 管理器（Attention K/V manager）按请求分别保存它们，直到调度器明确通知“这个请求结束了，可以删掉”为止。x1 做注意力时，从管理器取出 x11、x12、x13 的 key 和 value，再加上 Split 给出的当前 token x14 的 query、key、value，计算当前 token 与之前所有 token 的注意力；x2 同理，只是历史里只有 x21 一份。

为什么拆开注意力几乎不吃亏？这是论文最关键的一个判断，值得把因果讲完整。批处理之所以能提高吞吐量，主要靠“参数读一次，给很多请求用”。线性层的权重矩阵很大，7 个 token 一起乘，权重只从显存读一次；如果分 7 次乘，就要读 7 次。所以线性层一定要拼批。注意力则没有参数：x1 的注意力只读 x1 自己的 key、value，x2 只读 x2 自己的，两个请求之间没有任何共享的数据。无论把它们放在一次批量调用里，还是分开调用，需要从显存读的数据总量完全一样。拼批对注意力来说只能省下一点启动内核的开销、提高一点并行度，而 Orca 在实现时还用内核融合把这部分也找了回来（第 5 节）。所以，把拼批的好处集中在带参数的算子上，就能拿到批处理的大部分收益，同时允许批里请求的进度各不相同。

读的时候容易误解的地方：
  • “注意力不拼批”不等于“注意力一个接一个地串行执行”。Orca 的实现把各个请求的注意力内核合并成一个内核一起启动（第 5 节），在 GPU 上它们是同时跑的。“不拼批”指的是不再要求它们共享同一个规整的 \([B, L, H]\) 张量形状。
  • “几乎不吃亏”有前提。论文实验里每个请求的总长度最多 640 个 token（第 6 节），注意力在总耗时里占比不大。当上下文长到几万个 token、批又很大时，读 KV 缓存的时间会超过读参数的时间，注意力内核的效率就成了主要矛盾。这正是后来 PagedAttention、FlashInfer 等注意力内核要专门优化“一个批里长短不一的请求”的原因。
  • 选择性批处理同时解决了三种情况。论文以情况 ①（输入长度不同）为主线讲解，但情况 ②、③ 同理：只要注意力按请求拆开，其余算子按 token 摊平，初始阶段的整段输入和增量阶段的单个 token 就能放进同一次迭代。今天常说的“prefill 和 decode 混合批”就是从这里来的。

4 Orca 的设计：怎么撑起千亿参数的模型，每一步选谁来算

这一节要回答的问题：有了迭代级调度和选择性批处理，要做成一个真正可用的系统，还剩三个问题。第一，模型大到一张 GPU 放不下时，怎么切到多张 GPU、多台机器上，并且不让“每次迭代都要通信一次”的开销拖垮性能？第二，每次迭代到底该选哪些请求，怎么保证 KV 显存不会被占满而卡死？第三，多台机器做流水线时，迭代级调度能带来什么额外好处？

4.1 分布式架构：层内并行、层间并行，以及控制面与数据面分离

先补一点背景：两种模型并行。

当模型参数多到一张 GPU 放不下时，就要把参数和对应的计算拆到多张 GPU 上。论文用的两种拆法都来自训练系统（Megatron-LM、Mesh-TensorFlow）：

  • 层内并行（intra-layer parallelism，今天通常叫张量并行）：把每一层里的矩阵乘（线性层和注意力）按行或列切开，分给多张 GPU 各算一部分，每层算完后用 all-reduce 之类的集合通信把各自的部分结果合起来。它的通信很频繁（每层都要通信），所以一般放在同一台机器内、用 NVLink 这样的高速互连。细节见 Megatron-LM 精读。
  • 层间并行（inter-layer parallelism，今天通常叫流水线并行）：把连续的若干层整块分给一张 GPU（或一组 GPU），数据算完前几层后，把中间激活发给负责后几层的 GPU。它只在分区边界通信一次，通信量小，适合跨机器。Orca 给每个层间分区分配相同数量的 Transformer 层。

原文图 6 是一个组合两种并行的例子：一个 4 层的 GPT，先按层切成 2 个层间分区（第 1–2 层、第 3–4 层），每个分区再在层内切成 3 份，每一份放在一张 GPU 上，共用 6 张 GPU。FasterTransformer 也支持这两种并行。

原文图 7 画出了 Orca 执行引擎的分布式结构。引擎由一个引擎主进程（engine master）和若干个 worker 进程组成。每个 worker 负责一个层间分区，不同的 worker 可以在不同的机器上；每个 worker 里有一个控制器（controller）和若干个 CPU 线程，每个线程专门控制一张 GPU，线程数等于层内并行的份数。

一次迭代在引擎里是这样执行的：

  1. 调度器让引擎在某一批请求上跑一次迭代，引擎主进程把这批请求的信息转给第一个 worker。信息包括两部分：这次迭代的 token，以及一条控制消息。控制消息里有批里各请求的编号、增量阶段请求当前处理到第几个 token、初始阶段请求有几个输入 token。
  2. 第一个 worker 的控制器把这些信息交给它的各个 GPU 控制线程；每个线程解析信息，向自己的 GPU 发出相应的内核。例如注意力内核会根据请求编号和当前 token 的位置，找到 K/V 管理器里这个请求历史 key、value 所在的显存地址。
  3. 与此同时，控制器不等这些内核在 GPU 上执行完，就把控制消息转发给下一个 worker 的控制器。
  4. 最后一个 worker 的控制器和前面不同：它要等自己发出的内核全部执行完（即与 GPU 同步），才能取出每个请求的输出 token，交回引擎主进程。
先补一点背景：CPU 和 GPU 之间的“同步”为什么贵。

CPU 给 GPU 发内核是异步的：CPU 把一个个内核放进 GPU 的执行队列后就可以去干别的，GPU 按顺序执行。只要 CPU 发得比 GPU 算得快，GPU 就一直有活干。但如果 CPU 需要读取某个 GPU 上算出来的值（比如一个数据放在 GPU 显存里的控制信息），它就必须等 GPU 把排在前面的内核全部执行完、再把数据拷回来，这叫一次同步。同步期间 CPU 不能继续发内核，同步结束后 GPU 又可能要等 CPU 发下一批内核，两边轮流空等。每次迭代都同步一次，这些空隙累积起来就很可观。

为了尽量减少这种同步，Orca 把控制消息和张量数据分开走两条通道。作者观察到，FasterTransformer 和 Megatron-LM 等已有的分布式推理系统通过 NCCL（GPU 之间的通信库）交换控制消息（批大小、序列长度、某个请求是否结束等元数据），而 NCCL 的数据在 GPU 显存里，CPU 要用这些控制信息就得和 GPU 同步。这种交换每次迭代都会发生，开销不可忽视。Orca 则只用 NCCL 交换 GPU 产生、GPU 消费的中间张量（数据面），控制消息和 token 则在引擎主进程和各 worker 控制器之间用不经过 GPU 的通道（例如 gRPC）传递（控制面）。

4.2 调度算法：先来先服务、批大小上限和 KV 槽位预留

有了选择性批处理，引擎可以把任意一组请求放在一起算，调度器选请求时就有了很大的自由。剩下的问题是每次迭代具体选哪些。Orca 的调度器用了一个简单的原则：不改变客户端请求的处理顺序，先到的先处理。论文把它定义为迭代级的先来先服务（iteration-level FCFS）：对请求池里的任意两个请求，如果 \(x_i\) 比 \(x_j\) 先到，那么 \(x_i\) 跑过的迭代次数必须不少于 \(x_j\)。注意，这并不意味着先到的一定先结束：后到的请求如果需要的迭代少，完全可能更早返回。

除了顺序，调度器还要考虑两个因素。

第一，批变大的收益递减。批越大吞吐量越高，但每次迭代也越慢，延迟随之上升；而且批大到一定程度后，吞吐量的增长越来越小。所以和其他服务系统一样，Orca 设了一个批大小上限（max batch size，下文记作 max_bs）：一个批里最多放多少个请求。运维人员可以调这个参数，在满足延迟要求的前提下尽量提高吞吐量（实验见第 6.4 节）。

第二，显存有限。中间结果的缓冲区可以在不同算子之间复用，这是 FasterTransformer、TensorRT 等系统常用的技巧，Orca 也用了。但 K/V 管理器里存放 key 和 value 的缓冲区不一样：它们要等调度器通知“这个请求结束了”才能回收。如果实现得太天真，调度器可能陷入死锁：显存里已经没有空间存放下一个 token 的 key 和 value，于是请求池里没有任何一个请求能再跑一次迭代；而没有请求能跑完，也就没有显存能被释放。

先补一点背景：为什么会死锁，举个例子。

假设 K/V 区域总共能放 1,000 个 token 的 key 和 value。调度器一口气接纳了 10 个请求，每个都已经用掉 100 个位置，显存满了。下一次迭代，每个请求都要再存 1 个新 token 的 K/V，可是一个空位都没有了，谁也走不了；而只有走完的请求才会释放显存。这就像停车场停满了车、每辆车都要往前挪一格才能出去，结果谁也动不了。要避免这种局面，要么事先就为每个请求留够它将来需要的空间（Orca 的办法），要么在显存不够时把某些请求的 K/V 暂时请出去（后来 vLLM 的办法，见 vLLM 精读 §4.5）。

Orca 的做法是：一个请求第一次被调度时，就按它的 max_tokens 一次性为它预留足够的 K/V 空间。max_tokens 是每个请求自带的选项，表示这个请求处理完后最多会有多少个 token（输入加输出）。论文把“存放一个 token 的 key 和 value 所需的显存”叫一个槽位（slot），n_slots 是分给 K/V 管理器的显存一共有多少个槽位，n_rsrv 是当前已经预留出去的槽位数。只要预留成功，因为请求的 token 数不可能超过 max_tokens，就能保证它从开始到结束都有地方存新的 key 和 value，死锁不会发生。

论文还指出，n_slots 不像 max_bs 那样需要做实验权衡：给定模型规格（隐藏维度、层数等）和两种并行的份数，Orca 的显存占用主要取决于 n_slots，所以运维人员只要在显存允许的范围内把它设到最大即可。

原文的 Algorithm 1 把这些规则写成了伪代码。请求有三种状态：INITIATION（还没被调度过）、RUNNING（正在引擎里跑）、INCREMENT（跑完一次迭代回来了，等下一次）。主循环和选批函数 Select 用本站的话说是这样的：

  1. 选批：从请求池里取出所有当前不在引擎里跑的请求，按到达时间从早到晚排序，依次考虑。批里已经有 max_bs 个请求就停止。
  2. 如果正在考虑的请求还没被调度过（INITIATION），先看 \(n_{\text{rsrv}}\) 加上它的 max_tokens 是否超过 n_slots：超过就停止选批（不是跳过它去看下一个）；不超过就记下预留，把它放进批里。处在 INCREMENT 状态的请求已经预留过了，直接放进批里。
  3. 发出：让引擎在选出的批上跑一次迭代，批里的请求都标为 RUNNING，在途批数加一。
  4. 等待：只有当在途批数等于 worker 数（n_workers）时，才等待其中一批返回（这一点和流水线有关，见第 4.3 节）。返回的请求标为 INCREMENT；其中已经结束的请求释放它的 max_tokens 个槽位；在途批数减一。然后回到第 1 步。

为了对“一个槽位有多大”有个数量级的感觉，可以算一下。一个槽位要存一个 token 在每一层的 key 和 value，所以

$$\text{一个槽位的大小}=2\times n_{\text{layers}}\times H\times 2\ \text{字节（FP16）}\ \div\ \text{GPU 数}$$

以论文的 13B 模型为例（40 层，\(H=5120\)，单卡），一个槽位约 0.82 MB；以 175B 模型为例（96 层，\(H=12288\)，16 张卡分摊），每张卡上一个槽位约 0.3 MB（都是推算）。按最大长度 2048 给一个请求预留，13B 模型就要约 1.68 GB（推算）。这个数字在第 6.2 节解释 FasterTransformer 为什么开不了大批时还会用到。

这一节留下的伏笔：
  • 按 max_tokens 预留会浪费显存。真实请求往往远没生成到上限就输出了结束符，预留的大部分槽位从头到尾都没用上，而这些槽位本可以让更多请求同时进批。Orca 论文没有讨论这个问题，因为它的实验让每个请求都恰好生成到上限（第 6.1 节）。一年后 vLLM 正是以此为突破口：它复现了 Orca 的三种预留策略作为对照，测得 KV 显存里真正存了数据的只有 20.4%–38.2%，然后用分页按需分配解决了它。见 vLLM 精读 §3.1 和 §6.1。
  • 批大小上限按“请求数”计，不按“token 数”计。一个批里可以同时放进好几个新请求的整段输入，一次迭代的 token 数可能从几个跳到几千个，这一步的耗时随之暴涨，正在生成中的请求都要等它。后来 Sarathi-Serve 把上限改成按 token 数的预算，并把长输入切块，见 Sarathi-Serve 精读 §3.2。
  • 调度器没有抢占。请求一旦被接纳就一直跑到结束，所以 Orca 只能靠“接纳前先预留够”来防止死锁。

4.3 流水线并行：不需要把批切成微批

Algorithm 1 里“在途批数达到 worker 数才等待”这一条，是为了让层间并行的多个 worker 形成流水线。调度器发出一批后不急着等它返回，而是接着选下一批、再发出，直到引擎里同时有 n_workers 个批在跑。这样每个 worker 手里随时都有一个批在算，不会闲着。

原文图 8a 用 3 个 worker、max_bs = 2 举例，请求按 A、B、C、D、E、F 的顺序到达。调度器先选出最早的 A、B 组成批 AB 发出，由 Worker 1、2、3 依次处理；它不等 AB 返回，又发出 CD 和 EF。AB 返回后，A、B 又是池里最早到达的请求，于是再次被选中、发出，如此循环。

当时的服务系统和执行引擎（例如 Triton 加 FasterTransformer）做不到这一点：按请求调度意味着当前这批没结束之前，Triton 不能把下一个请求 C 交给 FasterTransformer。为了让多个层间分区形成流水线，FasterTransformer 只能把一批请求再切成若干微批（microbatch，GPipe 的做法），让各分区在不同微批上交错执行（原文图 8b 把批 AB 切成微批 A 和 B）。这带来一个两难：每个分区一次只能批量处理一个微批，微批比原来的批小，批处理的收益就变小了；可如果微批开得太大、数量少于分区数，流水线里又会出现空闲的气泡。FasterTransformer 必须在“批处理效率”和“流水线效率”之间取舍，Orca 因为本来就按迭代调度、可以直接塞进别的请求组成的批，不需要切微批，也就没有这个取舍。

5 实现：13K 行 C++ 与融合的注意力内核

这一节要回答的问题：Orca 是用什么写的？各部分之间怎么通信？第 3.4 节说“拆开注意力几乎不吃亏”，那么拆开之后，每个请求一个注意力内核，启动内核的开销怎么办？

Orca 用约 1.3 万行 C++ 实现，基于 CUDA 生态。控制面的通信用 gRPC，数据面用 NCCL，层间和层内的通信都走 NCCL。因为 Orca 专门面向 Transformer 生成式模型，它把常见的 Transformer 层做成了构建模块，包括原始的编码器—解码器 Transformer、GPT，以及 T5 论文（Raffel 等）里讨论过的各种变体。

先补一点背景：内核、线程块和内核融合。

在 GPU 上，每个计算操作都要以一个内核（kernel）的形式启动。一个内核由许多线程块（thread block）组成，GPU 把这些线程块分派到各个计算单元上并行执行。每启动一个内核都有固定的开销，而且一个内核如果只有很少几个线程块，GPU 的大部分计算单元会闲着。把几个连续的小操作合并成一个内核一次做完，叫内核融合：既省下了多次启动的开销，也省掉了中间结果在显存里写进写出。

和其他训练、推理系统一样，Orca 为 LayerNorm、注意力和 GeLU 实现了融合内核。例如注意力的三步——query 和 key 的点积、softmax、对 value 的加权平均——被融合进一个 CUDA 内核。

Orca 还往前多走了一步：把 Split 之后各个请求的注意力内核也融合在一起，做法很直接，就是把不同请求的内核的线程块全部拼进同一个内核里一起启动。这样一来，同一个内核里的线程块处理的张量形状不同，执行时间也不同。CUDA 编程的常规建议是避免这样做，因为形状不一的线程块会让负载不均衡；但作者发现这种融合是划算的：它减少了内核启动的开销，也让 GPU 更满。

这个做法值得多看一眼，因为它就是后来“一个内核处理一个批里长短不一的请求”的雏形。vLLM 的 PagedAttention 内核、FlashAttention 的变长（varlen）接口、FlashInfer 等，都是在一个内核里按请求划分线程块，各自读各自的 KV，见 vLLM 精读 §5。

两种测试场景。

  • 引擎微基准：只测执行引擎，不运行 Orca 的调度器。测试脚本把同一批请求反复送进 Orca 引擎，直到批里所有请求都结束，模拟传统的按请求调度；批里所有请求的输入长度相同、生成长度也相同。记录处理整批的时间，与 FasterTransformer 比较。
  • 端到端：模拟真实负载。因为当时没有公开的生成式语言模型请求记录，作者自己合成了请求流。每个请求随机抽取输入 token 数和最多生成的 token 数 max_gen_tokens，两者相加就是第 4.2 节的 max_tokens。

端到端测试有一个重要设定：作者假设所有请求都一直生成到 max_gen_tokens 才停，也就是让模型永远不输出 <EOS>。原因是作者手上既没有真实的模型权重，也没有真实的输入文本，无从判断什么时候该生成结束符。请求的到达时间按泊松过程生成，通过调整到达速率来模拟不同的负载。作者用多种分布生成的请求流来报告延迟和吞吐量。

先补一点背景：泊松到达与归一化延迟。

泊松过程是模拟“很多用户各自随机发请求”最常用的模型：给定平均速率（比如每秒 2 个请求），相邻请求的间隔是随机的，有时扎堆、有时稀疏。速率调高，系统就从空闲变得繁忙。

端到端实验报告的是中位数延迟除以该请求生成的 token 数，单位是毫秒/token。因为一个请求的处理时间大致和它生成的 token 数成正比，不除的话，生成 128 个 token 的请求和生成 1 个 token 的请求放在一起比没有意义。注意论文用的是中位数，不是平均值，也没有报告 P99 这样的尾延迟。

6.2 引擎微基准：去掉调度器，单看执行引擎

原文图 9 比较了在批内请求完全相同（输入 32 或 128 个 token，都生成 32 个 token，同时开始、同时结束）时，两个引擎处理一整批所需的时间。横轴是批大小（1、2、4、8、16、32），纵轴是执行时间（毫秒），分别测了 13B（1 张卡）、101B（8 张卡）和 175B（16 张卡）。

  • 13B 和 101B：Orca 引擎和 FasterTransformer 差不多，或者略慢一点。原因是 Orca 不对注意力拼批，而 FasterTransformer 对所有算子拼批。不过差距很小：注意力没有参数，拼批本来就省不下读参数的开销。作者据此认为，两个引擎在 CUDA 内核和层内并行通信上的实现效率相当。

两种情况下，FasterTransformer 在报告显存不足的那个批大小上都需要约 13.4 GB 的 K/V，几乎吃光了剩余显存，再加上中间结果就放不下了。这和论文的现象吻合。而 Orca 在微基准里每个请求最多只需要 160 个槽位，批开到 32 也只用 4 GB 左右（推算）。

读的时候要注意：“最多快 47%”的原文是 outperforms by up to 47%，论文没有说明这是执行时间缩短了 47%，还是速度提高了 47%，也没有给出对应的批大小。而且这个对比关掉了流水线，所以它衡量的只是两个引擎在跨机器执行时的固定开销差异，不能直接和后面端到端的倍数相乘或相加。

6.3 端到端：随机到达的请求流

端到端实验测试的是完整的 Orca，包括调度器。每个请求的输入 token 数从 32 到 512 的均匀分布 \(U(32, 512)\) 中抽取，max_gen_tokens 从 \(U(1, 128)\) 中抽取，所以最省事的请求只需 1 次迭代，最费事的需要 128 次。

FasterTransformer 本身没有调度器，作者为它写了一个：接收客户端请求，每次从队列里最多取 max_bs 个请求动态组成一批，交给 FasterTransformer。这是 Triton、TensorFlow Serving 等现有服务系统最常用的调度算法。对 FasterTransformer，除了 max_bs，作者还改变了微批大小这个控制流水线的参数。图例里 orca(max_bs) 表示批大小上限为 max_bs 的 Orca，ft(max_bs, mbs) 表示批大小上限 max_bs、微批大小 mbs 的 FasterTransformer。

先补一点背景：怎么读原文图 10。

原文图 10 的横轴是吞吐量（每秒完成的请求数），纵轴是中位数归一化延迟（毫秒/token，对数坐标）。每条曲线上的点对应不同的请求到达速率：负载低时，吞吐量等于到达速率，延迟很低；负载升高，吞吐量跟着升高，延迟也慢慢上升；当到达速率超过系统的处理能力，吞吐量再也上不去，延迟则急剧上升，曲线几乎竖直向上。所以看这张图，要看哪条曲线更靠右、更靠下：同样的延迟下能扛更多请求，同样的吞吐下延迟更低。注意它和 vLLM 论文的图画法不同，vLLM 的横轴是请求到达速率。

结果是：Orca 的吞吐量显著更高、延迟显著更低。唯一的例外是 101B 模型在低负载时（原文图 10a）：这时两个系统都凑不出足够多的请求来组批，延迟主要由引擎本身的速度决定，也就是图 9b 的情况，FasterTransformer 的引擎稍快一点。随着负载变重，Orca 的吞吐量上升而延迟只略有增加，因为后到的请求可以“搭上”正在进行的批。FasterTransformer 则处理不好三种请求：到达时间不同的、需要的迭代次数不同的、输入长度不同的，它在 101B 上的峰值吞吐量只有 0.49 个请求/秒，延迟也高得多。

对使用了多个层间分区的 175B 和 341B 模型（原文图 10b、10c），Orca 在每一档负载下的延迟和吞吐量都优于 FasterTransformer，在相近延迟下吞吐量高出一个数量级。论文举的具体例子是 175B 模型：在中位数归一化延迟为 190 毫秒/token 时，FasterTransformer 的吞吐量是 0.185 个请求/秒，Orca 是 6.81 个请求/秒，相差 36.9 倍。190 毫秒这个水平是作者选的：它是原文图 9c 中 orca(128) 的执行时间按生成 token 数归一化之后的两倍。

6.4 批大小上限怎么设，FasterTransformer 为什么开大批反而没用

原文图 10 显示，Orca 把批大小上限从 1 提高到 8、16、32，吞吐量随之提高，延迟却没有明显变化。原因是迭代级调度解决了“早完成、晚加入”的问题：批开大并不会让请求陪跑或排队更久。不过论文也说明，在任意的硬件、模型和负载下，并不能保证加大批不会损害延迟，所以批大小上限仍需要结合延迟和吞吐的要求来设。

有意思的是，FasterTransformer 加大批大小上限不一定能提高吞吐量。作者在所有模型、各档负载下试遍了 (max_bs, mbs) 的组合，发现最好的配置是 (1, 1) 和 (8, 8)。论文的解释有两层：

  • 微批削弱了批处理。第 4.3 节讲过，FasterTransformer 一次只能批量处理 mbs 个请求，所以微批大小取最大（等于 max_bs）的配置表现更好。
  • 大批更容易混进长短悬殊的请求。批越大，越可能同时包含输入长度或生成长度差别很大的请求。这时 FasterTransformer 有两个问题：一是第一次迭代时，它把所有请求都当作和最短的那个输入一样长来处理；二是先生成完的请求不能立刻返回。

关于第一点，论文只说了这一句。按本站的理解，这意味着较长的请求多出来的输入 token 没能在第一次迭代里并行处理，只能在之后的迭代里像生成阶段那样逐个补上，失去了并行处理输入的效率。这也解释了为什么 FasterTransformer 在输入长度服从 \(U(32, 512)\) 的负载上，大批反而不划算。

6.5 同质请求：没有“早完成”问题时还剩多少优势

为了把迭代级调度的作用单独拿出来看，作者又用同质请求做了测试：请求流里每个请求的输入 token 数和 max_gen_tokens 都一样，所以所有请求需要的迭代次数相同，不存在“提前离开”的问题。原文图 11 在 175B 模型上测了两组：(输入, 生成) = (32, 32) 和 (256, 256)。因为请求都一样，这里的延迟没有归一化，单位是毫秒。

结果是：这时加大 max_bs 对 FasterTransformer 有明显帮助，因为批里请求同进同出，不再有陪跑的浪费。即便如此，Orca 仍然优于 FasterTransformer 的 (8, 8) 配置，唯一的例外是批大小上限为 1 的 Orca：它退化成几个 worker 组成的简单流水线，完全不做批处理。

先补一点背景：同质请求下 Orca 还剩什么优势。

同质请求去掉了“早完成”和“输入长短不一”两个问题，但另外两个差别还在：一是请求到达时间仍然随机，按请求调度时新请求要等整批结束，Orca 只要等一次迭代；二是 175B 模型用了 2 个层间分区，Orca 可以用完整大小的批填满流水线，FasterTransformer 必须切微批（第 4.3 节）。此外还有第 6.2 节测到的引擎本身的差距。所以这组实验说明的是：即使最有利于 FasterTransformer 的负载，Orca 的设计仍然有收益，但它没有把这几项收益分别拆开测量。

6.6 结果的份量：36.9 倍是在什么条件下测出来的

36.9 倍是论文摘要里的数字，也是后来被引用最多的数字。把它放回实验条件里，可以看出它说明了什么、没有说明什么。

  • 对照系统只有一个，而且是作者搭的。在论文列举的几个 Transformer 推理引擎（FasterTransformer、LightSeq、TurboTransformers、EET）里，只有 FasterTransformer 支持分布式执行，拿它作对手是合理的；但论文没有写它的版本号（参考文献只注明 2021-12-13 访问的 GitHub 仓库），它前面的调度器是作者按 Triton / TensorFlow Serving 的常见做法自己写的。作者为它扫描了 (max_bs, mbs) 的全部组合并报告最好的配置，这一点是认真的。
  • 倍数取决于在哪个延迟水平截取。36.9 倍是在中位数归一化延迟 190 ms/token 这一个点上截出来的，在这个点上 FasterTransformer 已经接近饱和。延迟要求放宽，FasterTransformer 的吞吐量会高一些（101B 上峰值 0.49 请求/秒），倍数随之变小；论文正文的总结措辞是“高出一个数量级”。只看中位数，没有尾延迟，也没有把首 token 延迟（TTFT）和逐 token 间隔（TBT）分开，这两个指标是后来 DistServe、Sarathi-Serve 才成为标配的。
  • 收益混合了好几个来源，没有消融。端到端的差距同时来自：迭代级调度（不陪跑、不排队）、选择性批处理（不同长度的输入不用迁就最短的）、K/V 显存按 max_tokens 而不是按 2048 预留（能开更大的批）、不切微批的流水线、以及控制面与数据面分离（175B 上引擎本身最多快 47%）。论文没有逐项关掉来测量各自的贡献，所以不能说 36.9 倍全部来自迭代级调度。
  • 负载是合成的，而且回避了显存浪费问题。请求长度来自均匀分布，总长度最多 640 个 token，比今天的对话和长文档负载短得多。更重要的是，模型从不输出 <EOS>，每个请求都恰好生成 max_gen_tokens 个 token，所以按 max_tokens 预留的槽位最终全都用上了，“预留了却没用上”的浪费在实验里根本不会出现。按本站的粗略推算，175B 模型每张 GPU 放完约 22 GB 参数后还剩约 18 GB；即使只拿 10 GB 存 K/V、每个请求都按最长的 640 个 token 预留，也能同时容纳约 50 个请求（每个约 0.19 GB），按平均的约 336 个 token 算能容纳约 100 个，而引擎里同时在跑的请求最多是 32 × 2 = 64 个。所以在论文的负载下，K/V 预留大概率不是瓶颈（推算，取决于中间结果实际占多少显存）。一旦请求实际生成的长度远小于上限，显存利用率就会显著下降，这正是 vLLM 后来测到的情况。
  • 没有用真实模型权重。作者没有 GPT-3 的权重，所以测速时的权重不是训练好的模型。这对测速度本身没有影响，因为计算量与权重的具体数值无关；影响的只是结束符出现的时机，而这个已经被上一条的设定取代了。
  • 硬件与规模。全部是 40 GB 的 A100，机内 NVLink、机间 InfiniBand。端到端实验只做了 101B、175B、341B 三个多卡模型，13B 单卡只出现在引擎微基准里。
  • 无法独立复现。Orca 没有开源，致谢里写明这项工作由 FriendliAI 资助。后来的论文（vLLM、Sarathi-Serve）里作为对照的 “Orca” 都是按论文描述的复现，复现时的细节（例如 KV 预留策略、批大小上限）各不相同，见 vLLM 精读 §6.1 和 Sarathi-Serve 精读 §5.1。

总的来说，这组实验有力地说明了一件事：在长度不一、随机到达的请求流下，按请求调度会让大模型服务的吞吐量损失一个数量级，而按迭代调度能把它找回来。至于“36.9 倍”这个具体数字，它属于这一个模型、这一个延迟点、这一种合成负载，不宜直接搬到别的场景。

7 相关工作、讨论与结论

这一节要回答的问题：“细粒度地调度和批处理”在 Orca 之前有没有人做过？为什么那些办法用不到 Transformer 上？Orca 和当时其他 Transformer 推理引擎的根本区别是什么？它把调度器和引擎绑在一起，丢掉了分层设计的什么好处？
先补一点背景：RNN 的“单元”为什么可以跨请求拼批。

循环神经网络（RNN、LSTM）处理一个序列时，每一步都调用同一个“单元”：输入当前 token 和一个固定大小的隐藏状态，输出新的隐藏状态。不管处理的是第 3 个 token 还是第 300 个，这一步的计算完全相同，张量形状也完全相同（第 2.1 节的 LSTM 对比）。所以不同请求、处在不同位置的单元可以直接拼成一批。

RNN 的细粒度批处理。论文特别提到 BatchMaker（EuroSys 2018）：它是一个 RNN 推理服务系统，以 RNN 单元为粒度做调度和批处理。请求到达后，BatchMaker 把它的计算图拆成一个个单元，按单元调度，并把相同的单元拼批执行。因为 RNN 单元的计算与位置无关，新请求可以随时加入正在执行的批，完成的请求也可以随时离开，不用等整批结束。从思想上说，这已经是“迭代级调度”在 RNN 上的版本。

但 BatchMaker 没法用在 Transformer 上。对 Transformer 来说，处理一个 token 的子图（一个“单元”）在每个位置 \(t\) 都要用一组不同长度的 key 和 value，所以位置不同的单元就是不同的单元，整张图里有 \(L\) 种互不相同的单元（\(L\) 是输入和生成的 token 总数）。在论文图 10 的负载里，\(L\) 从 33 到 640 不等，同一时刻恰好有相同单元可以拼批的概率很低，BatchMaker 会退化为基本不拼批的串行执行。BatchMaker 也不支持需要模型并行和流水线并行的大模型。

作者借这个对比说明了 Orca 的设计原则：BatchMaker 致力于找出并对齐可以拼批的单元；Orca 的原则是每读一遍模型参数，就做尽可能多的计算。依据是，对大模型来说，从 GPU 显存读参数是端到端执行时间的主要瓶颈。所以 Orca 用迭代级调度和选择性批处理，在一次读参数的过程中处理所有“准备好”的 token，不管这些 token 的计算能不能拼批（非注意力算子能，注意力不能）。

专门的 Transformer 执行引擎。FasterTransformer、LightSeq、TurboTransformers、EET 等都是为 Transformer 优化的推理引擎，但它们都作为 Triton、TensorFlow Serving 等服务系统的后端，把调度交给服务系统层，因而沿用按请求调度。Orca 提出更细的调度粒度，而这在现有系统里不改变调度器与引擎之间的协作机制是做不到的。这些引擎里只有 FasterTransformer 支持分布式执行；Megatron-LM 和 DeepSpeed 虽然也能分布式执行，但主要为训练优化。

服务系统与执行引擎的接口。Triton、Clipper 等通用服务系统把“处理客户端请求、调度引擎”抽象成一层，把服务层和执行层分开设计和实现，这有很多好处。但作者发现，这两层之间流行的接口对 GPT 这样具有多迭代特性的模型限制太大。Orca 因此把调度器和引擎紧密集成，简化了两项技术的实现。作者承认这放弃了抽象分离的好处，并把“设计一个既支持这两项技术、又不破坏抽象分离的通用接口”留作未来工作。

结论。论文的结论可以这样概括：迭代级调度让调度器按迭代而不是按请求与执行引擎交互，选择性批处理让处理不同位置 token 的任意请求也能拼批，而后者是让批处理和迭代级调度同时成立的关键。基于这两项技术的分布式服务系统 Orca，在相同延迟下的吞吐量比当时最先进的系统高一个数量级。

回头看“接口”这一点：后来的发展基本印证了作者的判断。今天的主流推理引擎（vLLM、SGLang、TGI 等）都把调度器做进了引擎内部；Triton 这样的通用服务系统如果要支持连续批处理，也是由 TensorRT-LLM 后端自己在引擎内部完成按迭代组批（in-flight batching），而不是由 Triton 的通用调度器来做。

后来怎么样了

Orca 的两项技术里，迭代级调度几乎原样成了行业标准，选择性批处理的思想也被保留下来；而它为了让这两项技术跑起来而做的几个具体决定，后来被一一改掉。把这两部分分开看，最能理解 Orca 之后的推理系统是怎么演化的。

成了标准的部分

  • 按迭代组批，也就是连续批处理。vLLM、SGLang、TensorRT-LLM、Hugging Face 的 TGI 等主流引擎都以它为基础调度方式。名字各不相同：TensorRT-LLM 的文档把它叫 in-flight batching，并注明它也叫 continuous batching 或 iteration-level batching；TGI 的 README 把“对到达的请求做连续批处理”列为核心功能（TGI 仓库已于 2026-03-21 归档，进入维护模式）。“连续批处理”这个名字的流行，很大程度上来自 Anyscale 2023-06-22 的博客，它把 Orca 称为已知最早解决这一问题的工作，并在单张 A100-40GB、OPT-13B 上测得：连续批处理加上 vLLM 的显存优化，相对朴素的静态批处理吞吐量最高 23 倍。
  • 线性层按 token 摊平、注意力按请求处理。TensorRT-LLM 的文档写明，in-flight batching 要求输入张量是“打包的”、没有填充，初始阶段的序列和生成阶段的序列可以在同一批里处理，这就是选择性批处理里 \([\sum_i L_i, H]\) 的做法。注意力这边，“每个请求一个内核再拼起来”演变成了“一个内核按请求划分线程块”的变长注意力内核（PagedAttention、FlashAttention varlen、FlashInfer）。
  • 调度器与引擎紧密集成。见上一节末尾。

  • 一次迭代的大小。Orca 的批大小上限按请求数计，新请求的整段输入和其他请求的单个生成 token 混在同一次迭代里，这一步可能很长，正在生成的请求都会卡住。早期的 vLLM 为了吞吐优先做新请求的初始阶段（初始阶段和增量阶段分开成不同的迭代），同样有卡顿。Sarathi-Serve 把长输入切成等大的块，每次迭代先放所有生成 token、再按 token 预算捎带一块输入，同时解决了卡顿和流水线气泡，见 Sarathi-Serve 精读 §4.1。
  • 两个阶段放在同一组 GPU 上。初始阶段吃算力、增量阶段吃显存带宽，放在同一批 GPU 上会互相干扰，也没法分别选并行方式。DistServe、Mooncake 等干脆把两个阶段放到不同的 GPU 上，见 DistServe 精读 §2.2 和 Mooncake 精读。
  • 调度策略。Orca 只做不抢占的先来先服务；后来的引擎普遍支持抢占，也出现了优先级、公平性、前缀缓存感知（SGLang 的 RadixAttention）等更复杂的调度策略。

Orca 本身

Orca 一直没有开源。作者所在的 FriendliAI 把它发展成了商用推理引擎。FriendliAI 2023-09-27 的博客称，它的引擎源自 Orca 论文，并称其 “iteration batching（也叫 continuous batching）” 受美国和韩国专利保护（这是公司的说法，博客没有给出专利号）。Crunchbase 2025-08-28 的报道援引 Byung-Gon Chun 的话说“我们发明了连续批处理”。这些都是公司方面的表述；从学术上看，可以确定的是 Orca 是最早系统地提出并实现 Transformer 迭代级调度的论文，而按单元调度 RNN 的想法更早见于 BatchMaker。

还有一个可以查证的细节：Orca 参考文献 [34] 的 GPU 任务调度工作 Nimble（NeurIPS 2020），作者是 Woosuk Kwon、Gyeong-In Yu、Eunji Jeong 和 Byung-Gon Chun。Woosuk Kwon 后来在 UC Berkeley 主导了 vLLM，首尔大学 SPL 实验室的主页也把他列为实验室校友。Orca 和 vLLM 这两篇推理服务的奠基论文，第一作者曾在同一个实验室合作过。

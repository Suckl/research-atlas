0 导读：这篇论文解决什么问题

扩散语言模型（dLLM）生成文字的方式和常见的大模型不同。常见的大模型是自回归（AR）的：从左到右一个词一个词往后写，写下的词不再改。掩码扩散模型则先摆出一整块全是 [MASK] 的“画布”，每一步看着整块画布，挑一些位置填上词，反复多次直到填满，先填哪里由模型自己决定。代码被认为特别适合这种写法，因为写程序常常需要先定结构、再补细节，还经常要在中间插入或修改。2025 年上半年，Inception Labs 的商用模型 Mercury Coder 和 Google 的 Gemini Diffusion 都拿代码来展示扩散模型；学术界有 Apple 与港大合作的 DiffuCoder。但当时开放的代码扩散模型在常规基准上仍明显落后于同规模的 AR 代码模型，而商用模型的训练方法基本不公开。

这篇报告来自港大 NLP 组和华为诺亚方舟实验室，也就是 Dream 7B 的原班人马。它给出了一份完整公开的配方：从 AR 代码模型 Qwen2.5-Coder-7B 出发，沿用 Dream 的两个做法（保留 AR 的 shift 输出约定，以及按上下文给每个被遮 token 定权重的 CART），在 3220 亿（322B）个公开 token 上继续训练，把它改造成掩码扩散模型 Dream-Coder-7B-Base；再用 500 万条公开指令数据做监督微调（SFT），并针对“画布要用 [PAD] 补齐”带来的两个毛病加了两个小技巧；最后用 17k 道带单元测试的公开题目做强化学习（RL）。权重、数据处理脚本、训练与评测代码都已开源。

结果可以概括成三句话。第一，Base 模型在作者整理的代码基准平均分上与出发点 Qwen2.5-Coder-7B 持平（52.9 对 52.6），但数学能力明显下降（GSM8K 71.1 对 84.2）。第二，Instruct 模型在 LiveCodeBench（2024-10 至 2025-05 的新题）上 pass@1 为 21.4%，高于同表中的 Qwen2.5-Coder-7B-Instruct（19.3%），但在 HumanEval、MBPP、EvalPlus、BigCodeBench 上都低于它。第三，作者观察到模型会因题而异地选择生成顺序（先搭架子、从左到右、交错推演），但这部分只有三个可视化样例。

1 引言：为什么要拿扩散模型写代码，这份报告想证明什么

这一节要回答的问题：主流的代码模型都是从左到右写的，作者认为这种写法在哪些编程场景里吃亏？扩散模型理论上能补上哪些能力？在作者看来，当时的扩散代码模型还缺什么，这份报告又打算交出什么？

作者先描述了 AR 代码模型的局限。AR 模型生成第 \(k\) 个 token 时只能参考前面已经写下的内容，写下的内容也不能回头改。可是很多编程任务天然需要“全局视野”：重构代码时，要同时改函数签名和所有调用处，并保证彼此一致；调试时，要在代码的不同位置之间来回推敲。作者引用 Bachmann 与 Nagarajan 关于“下一个 token 预测的陷阱”的工作，认为这类任务需要全局理解、灵活的填空和多步修改，而严格的从左到右生成在这些方面吃力。

先补一点背景：扩散模型被认为能给代码带来什么。

掩码扩散模型训练时，看到的是被随机遮住一部分的序列，任务是把遮住的部分猜回来。由于注意力是双向的，每个位置都能同时参考左边和右边的内容。生成时，它从一整块 [MASK] 开始，每一步挑一部分位置填上，所以有三个 AR 模型没有的性质：

  • 双向上下文。补全中间一段代码时，右边已有的代码（例如后面对某个变量的使用）也能约束当前的选择。
  • 生成顺序可变。模型可以先写函数签名和控制结构，再填细节，不必严格从左到右。
  • 步数可调。每步可以只填一个 token，也可以一次填很多个。填得越多，前向计算次数越少，理论上越快，但质量通常会下降。

代价是：AR 模型每生成一个 token 只需对新 token 做一次增量计算（前面的结果存在 KV 缓存里），而双向注意力的扩散模型每一步都要把整条序列重新算一遍。所以“步数可调”带来的速度优势，只有在每步填多个 token 时才可能兑现。

作者接着回顾了当时的进展：通用扩散语言模型 LLaDA 和 Dream 7B 已经证明扩散模型可以做到 7–8B 规模；商用的 Mercury Coder 展示了不错的结果；DiffuCoder 研究了掩码扩散在代码上的行为。但作者认为，开放的扩散代码模型离最好的 AR 代码模型还有明显差距，扩散生成特有的能力也没有被充分利用。Dream-Coder 就是要缩小这个差距：用 Qwen2.5-Coder 初始化，加上 Dream 的上下文自适应噪声调度，再配上包括可验证奖励强化学习在内的后训练。

论文把贡献概括成三条：（1）第一个在代码上与 AR 基线“有竞争力”、同时开源的扩散代码模型；（2）观察到三种随任务而变的生成模式：先搭架子、从左到右、交错推演；（3）发布模型、训练配方、数据预处理流程和推理代码。

读的时候要注意的几点：
  • “开放”指的是改造之后的阶段。出发点 Qwen2.5-Coder-7B 是用阿里内部数据训练的，论文表 1 自己也把它标为“非开放数据”（✗）。Dream-Coder 的“全部用公开数据”说的是继续训练、SFT 和 RL 这三段。这和从零开始用开放数据训练的 OpenCoder 不是一回事。
  • “第一个有竞争力的”是作者的判断。DiffuCoder 在 2025 年 6 月就发布了同样从 Qwen2.5-Coder-7B 改造的 7B 权重；Dream-Coder 的优势在于分数更高、数据和训练代码更完整地公开。
  • 引言里描述的重构、调试等场景，论文后面并没有评测。实际评测的都是“读题、写一个完整程序”的标准基准。

2 模型：掩码扩散的训练目标，以及从 AR 模型接过来的 shift

这一节要回答的问题：Dream-Coder 用的是哪一种扩散模型，训练时优化的是什么？它直接拿 Qwen2.5-Coder-7B 的权重开始训练，那么网络结构需要改什么、为什么要保留 AR 模型“在位置 \(i\) 预测第 \(i+1\) 个 token”的约定？

2.1 吸收态扩散与加权交叉熵

先补一点背景：掩码（吸收态）扩散的训练目标。

把一段干净的文本记为 \(\mathbf{x}_{0}\)，长度为 \(N\)。前向“加噪”过程很简单：取一个时刻 \(t\in[0,1]\)，每个 token 独立地以概率 \(t\) 被换成 [MASK]，一旦被换掉就不再变回来（所以叫“吸收态”）。\(t=0\) 是原文，\(t=1\) 是全部遮住。反向过程由一个 Transformer 完成：输入部分被遮住的 \(\mathbf{x}_{t}\)，输出每个位置的词分布，训练它把被遮住的位置猜回原词。损失只在被遮住的位置上计算：

$$L(\theta)=-\,\mathbb{E}_{\mathbf{x}_{0},\,t\sim\mathcal U(0,1),\,\mathbf{x}_{t}\sim q(\mathbf{x}_{t}\mid\mathbf{x}_{0})}\;w(t)\sum_{n=1}^{N}\mathbf{1}\big[x_{t}^{n}=[\mathrm{M}]\big]\log p_{\theta}\big(x_{0}^{n}\mid\mathbf{x}_{t}\big)$$

当噪声调度是线性的（每个 token 以概率 \(t\) 被遮），取 \(w(t)=1/t\) 时，这个损失正好是负对数似然的一个上界（ELBO）。直观地说，\(t\) 小时被遮的位置少，计入损失的项也少，乘 \(1/t\) 把它放大回整句的量级。完整推导见 MDLM 精读页。

论文 §2.1 用的正是这个目标（论文式 (1)），并沿用连续时间的写法：\(t\) 可以取 \([0,1]\) 内的任意值，而不是固定的几个离散时刻。作者的理由是固定离散时刻会把 \(\mathbf{x}_{t}\) 限制在几个预先定好的噪声水平上，可能带来偏差；连续时间则可以灵活地选择噪声调度和采样时刻。

论文这里有一处说法前后不一致：论文写“\(w(t)\in(0,1]\)，由噪声调度决定”，紧接着又说这个目标是负对数似然的变分上界。这两句不能同时成立。原因是，不管选哪种噪声调度 \(\alpha_{t}\)（\(\alpha_{t}\) 是一个 token 在时刻 \(t\) 仍未被遮的概率），ELBO 里的权重都是 \(-\alpha'_{t}/(1-\alpha_{t})\)，它对 \(t\) 从 0 到 1 的积分等于 \(\int_{0}^{1}\frac{d\alpha}{1-\alpha}\)，是发散的，所以这个权重在 \(t\to0\) 时一定会趋于无穷，不可能处处不超过 1（本站推导）。实际情况是：线性调度下 ELBO 权重是 \(1/t\ge1\)；而开源的 SFT 与 RL 代码用的是下一节的 CART 权重，它确实处处不超过 1，但这时损失就不再是似然的上界，只是一个重新加权的去噪目标。这一点与 Dream 精读页 §4.2 的结论相同。

2.2 从 Qwen2.5-Coder 接过来：保留 shift

Dream-Coder 的网络结构与 Qwen2.5-Coder-7B 完全相同，所以可以直接载入它的权重。按官方发布的配置文件：28 层，隐藏维度 3584，28 个注意力头、其中键值头只有 4 个（分组查询注意力 GQA），前馈层维度 18,944，词表 152,064；新增的 [MASK] 的 id 是 151666；[PAD] 与结束符是同一个 token（id 151643），博客也说 [PAD] 被当作结束标记使用。改动只有两处：注意力从因果（只看左边）改成全双向；以及训练目标从“预测下一个 token”换成上面的掩码去噪。

关键的设计是 shift，它来自港大组更早的 DiffuLLaMA，并在 Dream 7B 中沿用。AR 模型在位置 \(i\) 的输出是“第 \(i+1\) 个 token 的预测”，这条约定在 Qwen2.5-Coder 上已经被几万亿个 token 训练过。常规的掩码扩散模型（例如 LLaDA）在被遮住的位置原地预测自己；如果直接这样训练 AR 权重，所有输出都会错开一格，网络得先把这条约定推倒重来。shift 的做法是：位置 \(n\) 被遮住时，它的答案从位置 \(n-1\) 的输出读出来。这样扩散训练的输出约定与原来的 AR 训练一致，AR 模型学到的东西能最大限度地保留下来。

3 预训练：CART 与 322B 个公开 token

这一节要回答的问题：改造阶段具体在优化什么？论文说的“上下文自适应的 token 级噪声重排”（CART）是怎样给每个被遮的 token 定权重的，在 Dream-Coder 的代码里取了什么参数？3220 亿个 token 的训练数据由哪些部分组成，配比是怎么来的？

3.1 CART：按周围有多少已知 token 给每个位置定权重

论文 §3.1 的训练流程是：从语料中取一段干净序列，抽 \(t\sim\mathcal U(0,1)\)，按噪声调度把一部分 token 换成 [MASK]，让模型利用整条 \(\mathbf{x}_{t}\) 的上下文预测被遮位置的原词。与 §2 不同的是，权重从只依赖 \(t\) 的 \(w(t)\) 换成了依赖 \(t\)、当前遮法和位置的 \(w(t,\mathbf{x}_{t},n)\)（论文式 (2)）：

$$L(\theta)=-\,\mathbb{E}_{\mathbf{x}_{0},\,t,\,\mathbf{x}_{t}}\sum_{n=1}^{N}\mathbf{1}\big[x_{t}^{n}=[\mathrm{M}]\big]\;w(t,\mathbf{x}_{t},n)\;\log p_{\theta}\big(x_{0}^{n}\mid\mathbf{x}_{t}\big)$$

这一节的论文正文只有一句解释：给“更难预测”的 token 分配更高的噪声率，从而加快收敛、提高质量。具体公式写在 Dream 7B 的报告里，Dream-Coder 的开源代码实现的也是同一个公式：一个被遮位置 \(n\) 的权重，等于序列中所有未被遮住的 token 按距离衰减后的“贡献”之和的一半：

$$w(t,\mathbf{x}_{t},n)=\frac12\sum_{i\ne n}\mathbf{1}\big[x_{t}^{i}\neq[\mathrm{M}]\big]\;p\,(1-p)^{|n-i|-1}$$

读法是：离位置 \(n\) 越近的已知 token 贡献越大，距离每多 1，贡献乘一次 \(1-p\)。一个位置周围已知 token 越多、越近，它的线索越充足，权重越高（相当于“噪声更低”）；被埋在一长串 [MASK] 中间的位置线索少，权重低。左右两侧各是一条几何级数，每条最多加到 1，所以乘 \(\tfrac12\) 后 \(w\le1\)。

Dream-Coder 用的参数。开源的 SFT 配置把 \(p\) 设为 0.1，SFT 脚本选用 CART 而不是 \(1/t\)；RL 脚本也给策略损失加了 \(p=0.1\) 的 CART 权重。预训练阶段的 \(p\) 论文和代码都没有给出，因为仓库的 base/ 目录只放了数据过滤脚本和评测脚本，没有放预训练代码。

所以在 \(p=0.1\) 下，CART 主要做了两件事：一是把权重整体压到 1 以下（与 \(1/t\) 相比，低噪声样本不再被成倍放大）；二是对“孤立被遮”和“成片被遮”的位置做温和的区分（1.0 对 0.6 左右）。\(p=0.5\) 时这种区分才会变得很强。CART 的更多推导和图解见 Dream 精读页 §4.2。

容易误解的地方：论文没有任何 CART 的消融实验，所以 Dream-Coder 的成绩里有多少来自 CART，无法拆分。另外，SFT 时只有回答部分会被遮，题目（prompt）总是完整可见，所以回答里紧挨着题目的那些 token 天然权重更高。

4 监督微调：随机截断与 [PAD] 惩罚

这一节要回答的问题：作者用 500 万条公开指令数据做 SFT 时遇到了两个问题：训练效率低，以及生成长度不稳定。这两个问题都和扩散模型“画布定长、空位用 [PAD] 补齐”的特点有关。问题从哪来？“随机截断”和“[PAD] 惩罚”分别怎样解决？效果有多大？

4.1 问题从哪来：定长画布与 [PAD]

先补一点背景：扩散模型的回答长度是怎么决定的。

AR 模型生成时，写出结束符就停，回答长度由模型自己决定。掩码扩散模型生成时，要先在题目后面摆出固定长度的画布，例如 512 个 [MASK]；模型如果觉得答案只需要 200 个 token，就在后面 312 个位置填上 [PAD]，使用时把 [PAD] 之后的部分切掉。

为了学会这一点，SFT 时也必须让模型看到“答案后面跟着一串 [PAD]”的样本，并在这些 [PAD] 上计算损失。最朴素的做法是把同一批的样本都补齐到批内最长的长度。这时会发生两件事。第一，[PAD] 位置非常多、又非常好猜（答案结束后全是 [PAD]），它们在损失里占了很大比重，大量计算花在几乎没有信息量的预测上。第二，模型从数据里学到“大多数位置都是 [PAD]”，生成时就倾向于早早填 [PAD]，尤其是在高温采样时，回答容易被提前截断。

论文把这两个现象分别称为“样本效率低”和“生成不稳定”，博客说得更直白：在最朴素的“补齐到最大长度”策略下，[PAD] 上的损失占了主导，导致过拟合并拖慢有效学习；而由于所有回答都被 [PAD] 填满，模型倾向于输出很短的回答。

4.2 随机截断：每批随机抽一个长度，把所有回答对齐到它

论文的描述只有一句：训练时，从批内随机挑一个样本，把每条回答都截断到它的长度。官方 SFT 代码（perbatch_cutoff_type=random_with_input_pad）的做法更具体一些：

  1. 把同一批的题目在左边补齐到批内最长的题目长度，左边补出来的位置不参与注意力。
  2. 在批内随机抽一条样本，记下它的回答长度 \(r^{*}\)。
  3. 比 \(r^{*}\) 长的回答被截掉后半段；比 \(r^{*}\) 短的回答在后面补 [PAD] 到 \(r^{*}\)，这些 [PAD] 照常参与加噪和计损失。

这样做的效果可以从两方面理解。从计算量看，批的长度从“最长的题目 + 最长的回答”变成了“最长的题目 + 随机抽中的回答长度”，平均下来序列更短，[PAD] 占的比例更小。从学习信号看，长回答被截断后，模型在这一批里看不到它的结尾，只学到“这里还有内容”；短回答后面仍有少量 [PAD]，模型仍能学到“答案在这里结束”。多个批次下来，同一条长样本会在不同批次被截到不同的长度，整体上仍能被完整学到。

4.3 [PAD] 惩罚：生成初期压低 [PAD]，越往后越放开

第二个技巧只在推理时起作用。论文说：模型在高温采样时容易过早生成 [PAD]，于是在推理时给 [PAD] 的 logit 加一个逐渐衰减的惩罚。官方生成代码中的公式是：

$$\text{logit}_{\text{PAD}}\;\leftarrow\;\text{logit}_{\text{PAD}}+\lambda\,\ln\!\big(1-t+\varepsilon\big)$$

其中 \(t\) 是当前的“时刻”，生成时从 1 线性地走到 \(\varepsilon\)；\(\varepsilon\) 默认是 \(10^{-3}\)；\(\lambda\) 是惩罚强度，代码里叫 eos_penalty，默认 0，官方演示和博客用的是 3.0。生成刚开始时 \(t=1\)，\(\ln(\varepsilon)\approx-6.9\)，[PAD] 的 logit 被减去约 20.7；生成快结束时 \(t\to0\)，\(\ln 1=0\)，惩罚消失。

示意图：λ = 3 时，[PAD] 的 logit 被加上的偏移量随生成进度的变化
本站按官方 generation_utils.py 的公式推算并绘制（λ = 3，ε = 10⁻³），不是论文数据。给某个 token 的 logit 加上 \(c\)，等于把它相对其他 token 的几率乘以 \(e^{c}\)：\(e^{-20.7}\approx10^{-9}\)，\(e^{-2.08}\approx0.125\)。

这个设计的意图很清楚：生成初期，模型对整体结构还没有把握，[PAD] 又是一个“很安全、很笃定”的预测，如果不加限制，按置信度挑位置的解码器很容易先把画布后半段填满 [PAD]，回答就被锁死成很短的长度。压住 [PAD]，迫使模型先把有内容的部分写出来；到了后期再放开，让它自然地在合适的位置收尾。博客的说法是“先专心写有意义的 token，后期再考虑结束”。

5 强化学习：可验证奖励与为扩散模型改造的 GRPO

这一节要回答的问题：SFT 之后，作者又用“能否通过单元测试”作为奖励做了强化学习。训练题目从哪来、怎样筛选？GRPO 原本是为 AR 模型设计的，它需要每个 token 的概率比，而扩散模型给不出精确值，Dream-Coder 用什么代替？论文列出的四项改动各自解决什么问题？官方脚本里的实际设置又是什么？

5.1 背景：可验证奖励、GRPO，以及扩散模型的难处

先补一点背景：可验证奖励的强化学习（RLVR）与 GRPO。

写代码的题目有一个方便之处：答案对不对可以自动判定。把模型生成的程序放进沙箱执行，跑一遍题目自带的单元测试，全部通过就给奖励 1，否则给 0。这种由程序判定、不需要人工打分的奖励叫“可验证奖励”。

GRPO 是一种不需要价值网络的策略优化算法。对每道题，用当前模型采样一组 \(G\) 条回答，每条得到奖励 \(r_{i}\)。以组内平均为基准、除以组内标准差，就得到每条回答的“优势” \(\hat A_{i}=\frac{r_{i}-\text{mean}(r)}{\text{std}(r)}\)：比同组平均好的回答被鼓励，差的被抑制。更新时，对回答里的每个 token 计算新旧模型的概率比 \(\rho=\pi_{\theta}/\pi_{\text{old}}\)，用 \(\min(\rho\hat A,\ \text{clip}(\rho)\hat A)\) 作为目标，裁剪是为了防止一步走得太远。逐项的数值例子见 d1 精读页。

对 AR 模型来说，每个 token 的概率 \(\pi(o^{k}\mid q,o^{<k})\) 一次前向就能全部算出。掩码扩散模型没有这种“从左到右”的分解，单个 token 的概率取决于当时画布上哪些位置可见，只能用某种遮法下的预测概率去近似。d1 用“回答全部遮住”的一次前向来近似；DiffuCoder 用“全遮 + 一对互补遮法”取平均。两种做法的分析见 DiffuCoder 精读页 §5.1。

论文 §4.2 的目标函数就是标准的 GRPO 形式（裁剪上下界不对称，没有 KL 项），式子里额外写了一个 \(t\sim\mathcal U(0,1)\)，表示概率比是在随机遮法下估计的。式子中的概率比仍写成 AR 的条件概率，具体怎么估计，正文只用一句“采样互补的扩散掩码”带过，细节要看代码（见 5.3）。

5.2 题目：17k 道带单元测试的公开题

训练题目来自三个公开数据集：KodCode-V1、DeepCoder-Preview 和 Guru-RL-92k。筛选分三步：

  • 质量：只保留至少有 5 个单元测试的题，测试太少的题容易被“蒙混过关”。
  • 去重：用一个轻量的句向量模型（all-MiniLM-L6-v2）找出语义相近的题目并去掉，避免数据冗余。
  • 难度：让 Qwen2.5-Coder-7B-Instruct 对每道题生成 8 个答案，8 个全对的题被视为太简单而剔除。

官方在 Hugging Face 上发布了这份数据（Dream-org/Dream-Coder-RL-17k，CC BY-NC 4.0 许可），共 17,030 条，分三个文件。本站查看了数据集的统计：KodCode 部分 8,344 条，DeepCoder 部分 4,956 条，Guru 部分 3,730 条全部是 CodeIO 类题目。按数据里的判题方式标签，标为 code_contests（读标准输入、写标准输出）的程序题共 11,200 条，按函数调用判题的题 2,100 条（其中 405 条被标成 mbppplus，本站抽查后发现它们是 PrimeIntellect、TACO 里“写一个函数”的题，这个标签指的是判题格式，并不是 MBPP+ 的测试题），CodeIO 题 3,730 条。博客的说法是“功能调用、标准输入输出和模拟三类题目均衡分布”。

先补一点背景：CodeIO 是什么样的题。

CodeIO 来自 CodeI/O 工作（论文引用了它）：给出一段程序的功能描述和输入输出格式，再给出某个输出，要求模型推出能产生这个输出的输入（或反过来）。本站查看的第一条样本是：已知 Collatz 序列的输出字符串，问起始整数是多少。这类题考的是“在脑子里执行程序”，形式上与第 6 节的 CRUXEval（给定函数和输入，预测输出；或反过来）非常接近。

两个值得记住的细节：（1）RL 题集里有 3,730 道 CodeIO 题，与 CRUXEval 的题型相近，所以 RL 在 CRUXEval 上带来的提升，有一部分可能来自“练过同类题”，而不完全是一般推理能力的提高（本站推测）。（2）难度筛选用的是一个 AR 模型的判断，“Qwen2.5-Coder-7B-Instruct 能全做对”的题被去掉，剩下的题对 Dream-Coder 来说难度分布如何，论文没有给出。

5.3 四项改动：去掉 KL 与熵、提高裁剪上限、互补掩码、组替换

论文说这些改动受 DAPO、DiffuCoder 和 Polaris 的启发，目的是让梯度估计更稳定。逐项看：

（1）不加熵损失，也不加 KL 惩罚。熵损失原本用来鼓励探索，但作者发现它常常导致训练不稳定；KL 惩罚把模型拉向参考模型，会限制探索，还要额外算一遍参考模型的概率。官方代码里，不启用 KL 损失时根本不创建参考模型，奖励里也不加 KL 项，所以训练中完全没有 KL 约束。

（2）Clip-Higher。标准 PPO 把概率比裁剪在 \([1-\varepsilon,1+\varepsilon]\) 内，通常 \(\varepsilon=0.2\)。DAPO 指出，上限太低会让原本概率很小的好 token 很难被提上来：概率从 0.01 涨到 0.012 就已经触到 1.2 的上限，而一个概率 0.9 的 token 同样涨 20% 就是 0.18，两者在一次更新里能获得的“绝对增量”差了近百倍。Dream-Coder 用不对称的范围，\(\varepsilon_{\text{low}}=0.2\)、\(\varepsilon_{\text{high}}=0.28\)，也就是比值允许在 \([0.8,1.28]\) 内变化：上面那个 0.01 的 token 这一步最多能涨到 0.0128（推算）。下限保持不变，是为了不让坏 token 的概率一次被压得太狠。对需要探索的 RL 来说，这相当于给“偶尔采到的好写法”多留一点上升空间。

（3）互补掩码（论文称 Coupled Sampling）。这是为扩散模型专门做的部分。官方代码的做法是：

  1. 每一轮 PPO 更新开始时，抽一个 \(t\sim\mathcal U(0,1)\)，并给回答的每个位置抽一个均匀随机数 \(u\)。
  2. 把这一批数据复制两份。第一份遮住 \(u<t\) 的位置，第二份遮住 \(u\ge t\) 的位置。两份恰好互补：每个回答 token 在其中一份里被遮住，在另一份里可见。
  3. 每份只在被遮住的位置上计算“新模型概率 / 旧模型概率”，旧模型的概率在采样后用同一张掩码算好。每个 token 的比值来自它被遮住的那一份。
  4. 损失按 CART 权重（\(p=0.1\)）加权，而不是乘 \(1/t\)；[PAD] 位置不计损失。

和 DiffuCoder 相比，这种做法的好处是每个 token 的比值有清楚的含义：它是同一个上下文（同一张掩码）下新旧模型对这个 token 的概率之比，而不是几种上下文下概率比的加权几何平均。代价是方差可能更大，因为每个 token 只被一张随机掩码评估一次，而这张掩码有时遮得很多、有时很少。互补设计保证了每个 token 至少被评估一次（不会有 token 在这一轮“没有学习信号”），这正是 DiffuCoder 论文强调的“覆盖率”。

（4）组内信息替换（Informative Substitution）。GRPO 的优势是组内相对的：如果一道题的 16 条回答全对或全错，组内标准差为 0，所有优势都是 0，这组样本对梯度毫无贡献，却占着批里的位置。DAPO 的做法是丢掉这些组、再采新的题补齐；Dream-Coder 的做法是用批内“部分做对”的组的副本替换它们。论文写的是“用高优势样本的副本替换”，官方代码实际是在部分做对的组中有放回地随机抽一个组整组复制，并不专门挑优势高的。这样每一批的有效样本数保持不变，代价是部分题目在同一批里被重复使用。

采样加速。RL 最耗时的是采样（rollout）。作者用 Fast-dLLM 加速：按官方脚本的默认参数，768 个 token 的回答被分成 24 块、每块 32 个 token，从左到右一块一块地生成，前面已完成的块用近似的 KV 缓存；块内每步仍只定一个 token（768 步对 768 个位置）。代码在 SandboxFusion 沙箱里执行判分。

一处容易被忽略的不一致：RL 采样时是“按 32 个 token 一块、从左到右”的半自回归生成，位置挑选算法是 maskgit_plus（挑最大概率最高的位置）；而第 6 节的评测是在整张画布上按熵挑位置。也就是说，RL 优化的是模型在半自回归生成下的行为，评测用的却是另一种生成顺序。这对分数的影响论文没有讨论（本站依据官方脚本的默认值判断）。

6.1 评测设置：考了哪些题，每道题怎么打分

先补一点背景：几个代码基准和 pass@1。
  • HumanEval：164 道 Python 题，给出函数签名和文档字符串，要求写出函数体，用题目自带的测试判定。
  • MBPP：入门级的 Python 编程题，每题一句自然语言描述加几个测试。
  • EvalPlus：给 HumanEval 和 MBPP 补充大量更严格的测试，得到 HumanEval+ 和 MBPP+，专门抓“碰巧通过原测试”的错误代码。表 4 的 EvalPlus 一列是 HumanEval+ 与 MBPP+ 两个分数的平均（本站按对照模型的公开数字核对过，见 6.4）。
  • BigCodeBench：约 1,100 道需要调用各种库函数的实用编程题，有“补全”（给文档字符串续写）和“指令”（只给自然语言要求）两种形式，Hard 是其中较难的子集。
  • LiveCodeBench：持续从 LeetCode、AtCoder、Codeforces 收集竞赛题，并记录发布日期。只用某个日期之后的新题评测，可以减少“训练数据里见过原题”的污染。本文用 2024-10 至 2025-05 发布的题（下称 2410–2505）。
  • CRUXEval：800 个短小的 Python 函数，Input 任务是给定函数和输出、推出输入，Output 任务是给定函数和输入、推出输出；CoT 表示允许先写推理过程。

pass@k：对一道题采样 \(k\) 个答案，至少一个通过全部测试的概率；pass@1 就是“只给一次机会”的通过率。表里报告的都是 pass@1。

通用与数学基准方面，作者用 lm-evaluation-harness 评测了 MMLU、ARC-C、HellaSwag、WinoGrande、PIQA、RACE（知识、推理与常识），以及 GSM8K、MATH（数学）和 GPQA（科学问答）。按官方脚本，选择题用似然打分，MMLU、WinoGrande、GPQA 为 5-shot，其余为 0-shot；GSM8K 用 8-shot 思维链，MATH 用 4-shot。

6.5 结果的份量：这些数字说明了什么，没说明什么

  • 和 AR 模型比，控制住了什么。参数量和网络结构与 Qwen2.5-Coder-7B 完全相同。但训练量和数据都不同：Dream-Coder = Qwen2.5-Coder（5T 以上内部数据）+ 322B 公开数据的扩散训练 + 500 万条 SFT + 50 步 RL；对照的 Qwen2.5-Coder-7B-Instruct 用的是阿里自己的后训练数据。论文没有做“同一个 Base、同样的 322B + SFT + RL 数据，只把目标换成 AR”的对照，所以“扩散目标与 AR 目标谁更好”这个问题，这份报告回答不了。
  • 和 OpenCoder 比，起点不同。“公开数据训练却超过 OpenCoder”的说法，对比的是“继承了 5T 以上内部数据的模型”与“完全从零用 2.6T 开放数据训练的模型”。表里“开放数据 ✓”只描述了改造之后的阶段。
  • 步数与速度。所有分数都在每步定一个 token、无 KV 缓存的条件下测得。论文没有报告速度，也没有测试减少步数后分数掉多少。所以这份报告只能说明“在最慢的解码方式下，质量能做到什么程度”，不能说明扩散模型在代码上能更快。
  • 评测协议拼接。对照数字来自至少七个出处（各家技术报告、EvalPlus 与 BigCodeBench 排行榜、Mercury 报告中的第三方数字、DeepMind 模型页、作者自测），解码方式、提示模板、BigCodeBench 版本、LiveCodeBench 时间窗都不统一，其中 Mercury 一行还有抄录错误。一两分的差距不宜解读为模型能力的差异。
  • RL 的增益。基线是同一个模型的 SFT 版本，这是合理的；但 SFT 的分数只在图中，没有表格，也没有多次运行的方差。RL 只训了 50 步，增益在 1–4 分之间。RL 题集包含 3,730 道 CodeIO 题，与 CRUXEval 题型相近；没有在训练任务之外的领域（例如数学）检查 RL 的影响。
  • LiveCodeBench 的领先。21.4 对 19.3 是表中 Dream-Coder 唯一超过同底座 AR 模型的一项，但两者都是 7B 级别在难题上的低分，困难题只有 3.9% 对 3.4%；而且 RL 题集是以“Qwen2.5-Coder-7B-Instruct 做不全对”为标准筛出来的竞赛题，这正好对准了 Qwen-Instruct 的弱项（本站推测）。

7 生成模式：模型会因题而异地选择写作顺序吗

这一节要回答的问题：扩散模型可以按任意顺序填画布，那么 Dream-Coder 实际上是按什么顺序写代码的？作者说观察到了三种随任务变化的模式，这些模式是什么样，证据有多少？论文进一步说这些模式“解释了”它在各个基准上的表现，这个推论站得住吗？

论文 §5.4 用三个可视化样例（原文图 3）描述三种模式。图里每个 token 的底色表示它在解码过程中被填上的先后：颜色越浅越早，越深越晚。

  • 先搭架子（sketch-first），样例取自 LiveCodeBench。对“读标准输入、写标准输出”的完整程序，模型先写出整体结构，例如入口函数、读输入、输出结果和 if __name__ == "__main__" 这些部分，再回头补全辅助函数和核心逻辑。博客的描述是：先把整个入口的脚手架写出来，再倒回去实现辅助函数。
  • 从左到右（left-to-right），样例取自 BigCodeBench。对单个函数的补全，模型几乎是线性地从函数头往下写。论文认为扩散机制仍允许局部的修正。
  • 交错推演（interleaved reasoning），样例取自 CRUXEval。对“给定代码和输入、推出输出”的代码推理题，模型的推理步骤以非线性的方式出现。博客的描述是：先复述给定的输入，再逐步走一遍程序，一边算一边填上结果。
示意图：三种生成顺序（本站编写的玩具代码，底色越深表示越晚被填上）
本站示意图，代码是为说明顺序而编写的玩具例子，不是原图的复制；三种顺序依据原文图 3 的配色与博客的描述概括，原图见 原文图 3 ↗。原图按 token 着色，本图简化成按行。

论文进一步认为：这些模式不是预先设定的，而是从扩散训练中自然涌现的；模型根据题目结构和任务复杂度选择模式；并且各模式的有效性“被基准结果所验证”：先搭架子对应 LiveCodeBench 上的好成绩，从左到右对应 HumanEval / MBPP，交错推演对应 CRUXEval。

这一节的证据比结论弱得多。本站核对了原文图 3 的三个样例，发现了以下几点：

  • 每种模式只有一个样例，没有任何统计。论文没有给出“多少比例的题目呈现某种模式”，也没有像 DiffuCoder 那样用“局部 / 全局 AR 程度”之类的指标量化解码顺序。“模型会因题而异地选择模式”只能算是一个有待验证的观察。
  • “模式带来了好成绩”是相关，不是因果。要说明先搭架子有助于 LiveCodeBench，需要对照实验，例如强制从左到右解码时分数掉多少。论文没有做这类消融。
  • 展示的样例中有两个答案是错的。从左到右的样例里，模型写的是 shuffle()，没有传入要打乱的列表；Python 的 random.shuffle 必须传一个参数，这行代码运行时会抛出 TypeError（本站在 Python 3.11 上验证）。交错推演的样例是 CRUXEval 的第 0 题：输入列表 [1, 1, 3, 1, 3, 1] 里有四个 1，模型却写“出现 3 次”，最终答案只有 3 个元组，而正确答案是 [(4, 1), (4, 1), (4, 1), (4, 1), (2, 3), (2, 3)]（本站对照 CRUXEval 数据与 Python 运行结果）。论文没有说明这些样例是否通过了测试，所以它们只能说明“顺序是这样的”，不能说明“这种顺序写出了正确的程序”。
  • 交错推演样例里，答案似乎先于推理。按原图的配色，最后一行 [ANSWER] assert f(...) == ... 颜色很浅，说明它在解码早期就被填上了，而中间的逐步推演颜色较深、填得较晚（本站对原图配色的解读）。如果确实如此，那么这里的“思维链”更像是事后补写的解释，而不是推出答案的过程，这与把它称作“推理”的说法相冲突，而且这道题的答案恰好是错的。
  • 正文与图的对应有出入。正文说“从左到右”出现在 HumanEval、MBPP 这类单函数补全上，图中的样例却取自 BigCodeBench。

要验证这些说法，需要什么样的实验。论文给出的是“看到了什么”，要把它变成“证明了什么”，至少需要三类证据。第一，统计：在每个基准的全部题目上记录生成顺序，用一个数值指标（例如 DiffuCoder 用的“全局 AR 程度”，即每一步填的恰好是剩下的最左边那个空位的比例，见 DiffuCoder 精读页 §4.1）描述顺序，看不同基准之间是否真有系统差异。第二，因果：固定其他设置，强制模型从左到右解码（或强制先填某些位置），比较 pass@1 的变化；如果强制从左到右后 LiveCodeBench 分数不变，“先搭架子带来好成绩”就站不住。第三，正确性：把生成顺序与答案是否通过测试放在一起看，检查某种顺序是否更常出现在做对的题上。这三类分析在后来的工作里有人做过一部分（例如 DiffuCoder 的 AR 程度分析），但针对 Dream-Coder 的，本站没有查到。

还有两个影响解读的设置：（1）这些样例和所有评测都用低温（0.1）、按熵挑位置的解码器。按熵挑位置意味着“最有把握的位置先填”，所以“先搭架子”也可以理解为：样板代码（入口、读输入）的不确定性最低，因而最先被填上。这是解码规则与代码统计规律共同作用的结果，未必是模型“规划”出来的（本站解读）。（2）第 5 节提到，RL 采样是按 32 个 token 一块从左到右生成的，所以 RL 阶段并没有直接奖励“先搭架子”这类全局顺序。

8 相关工作与结论：放在代码扩散模型的谱系里看

这一节要回答的问题：作者怎样把 Dream-Coder 放进 AR 代码模型和扩散语言模型的研究脉络里？结论部分说了什么、计划做什么？和同期及之后的几个代码扩散模型（DiffuCoder、Seed Diffusion、Stable-DiffCoder、DreamOn）相比，Dream-Coder 的位置在哪里？

论文的相关工作分三块。AR 代码模型：从早期在大规模代码库上预训练的专用模型（Code Llama、StarCoder 2、DeepSeek-Coder），到近期借助推理能力和智能体框架的工作；作者认为 AR 模型受限于从左到右生成，在非单调编辑和需要全局规划的场景中吃亏。扩散语言模型：从 D3PM、多项式扩散等离散扩散的奠基工作，到 SEDD、Plaid、LLaDA 的规模化，再到从 AR 模型改造的 DiffuLLaMA 和 Dream；商用的 Mercury 和 Gemini Diffusion；以及通过 KV 缓存和并行生成加速推理的工作（dKV-Cache、Fast-dLLM、dLLM-Cache 等）。代码扩散模型：作者只提到 DiffuCoder，并认为代码本身需要反复修改，天然适合“迭代去噪”的生成方式。

结论部分重申：Dream-Coder 是团队改进开源扩散语言模型的延续，重点在后训练和代码能力；它完全用开源数据训练，与最好的 AR 模型有竞争力，并在复杂编程场景中展现了非自回归生成的优势。后续计划是上下文长度扩展、改进数据整理，以及面向需要高级规划和推理的专门编程领域。

后来怎么样了

Dream-Coder 的权重在 2025-07-15 发布，技术报告在 2025-09-01 上传 arXiv，只有 v1 一个版本。截至 2026-10-20，本站没有查到它的同行评审版本（OpenReview 上只有从 DBLP 导入的 arXiv 条目），所以它仍是一份预印本。官方仓库在 2025-09-21 补发了 Base 模型的数据说明和评测脚本，2025-09-25 补发了 Instruct 模型的数据处理、训练和评测脚本，最后一次推送在 2025-11-17。

  • DreamOn：直接建立在 Dream-Coder 上。同一团队的 DreamOn 以 Dream-Coder-7B 和 DiffuCoder-7B 为起点，引入两个特殊 token，让模型在生成过程中自己扩展或收缩被遮区域，解决代码填空时“画布长度必须事先定好”的问题。DreamOn 论文给出的动机正是 Dream-Coder 的弱点：当预设的遮盖长度与真实答案长度不一致时，它在 HumanEval-Infilling 上平均下降 38%。这呼应了第 4 节的观察：随机截断和 [PAD] 惩罚只是缓解了定长画布的问题，并没有解决它。
  • Stable-DiffCoder：把它当作主要对照。2026 年 1 月的 Stable-DiffCoder 在 Seed-Coder 的流水线里插入块扩散持续预训练，它的 Base 与 Instruct 对比表都列了 Dream-Coder（引用的是 Dream-Coder 报告里的数字），在 HumanEval、MBPP 等基准上超过了它。
  • 被引用为“草图优先”的例子。LLaDA2.0 和 WeDLM 的相关工作部分都把 Dream-Coder 当作扩散模型在代码上出现“先打草稿再填细节”行为的例子；TraceRL 也在参考文献中引用了它的博客。不过，到 2026-10 为止，本站没有查到对这种生成模式做定量验证的后续工作。
  • 社区采用。截至 2026-10-20，GitHub 仓库有 114 个 star、8 个 fork；Hugging Face 上 Instruct 模型近 30 天下载约 900 次、32 个点赞，Base 模型近 30 天下载约 890 次、9 个点赞。和 Dream 7B 本身相比，Dream-Coder 的使用规模要小得多。

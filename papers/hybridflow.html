0 导读：这篇论文解决什么问题

一个大语言模型在预训练和监督微调之后，通常还要再经过一轮强化学习（RL）训练：让模型自己生成回答，由一个打分器给回答打分，再根据分数调整模型，让它以后多生成高分的回答。这一步最早叫 RLHF（基于人类反馈的强化学习），因为打分器是用人类偏好数据训练出来的；后来打分器也可以是检查数学答案对不对、代码能不能通过测试的程序，统称为大模型的 RL 后训练。

RL 后训练在系统层面非常特别。普通的预训练只涉及一个模型、一种计算（前向加反向）。而以 PPO 为代表的 RLHF，一轮迭代里有四个大模型（actor、critic、reference、reward model），有三种性质完全不同的计算（逐个 token 的自回归生成、只做一次前向的打分、带反向传播的训练），计算之间还有严格的先后依赖。每个模型本身大到要用很多张 GPU 并行，而不同的计算又适合不同的并行切法。于是出现了两个问题：这么复杂的流程怎么写得出来、改得动？写出来之后怎么在集群上跑得快？

这篇论文给出的答案叫 HybridFlow，它的开源实现就是后来被广泛使用的 RL 训练框架 verl。论文的核心想法有三个。第一是混合编程模型：模型和模型之间，由一个中心控制器像写普通 Python 程序那样编排；每个模型内部的分布式计算，仍然由每张 GPU 上各自运行的程序完成。第二是 3D-HybridEngine：actor 在训练和生成时使用不同的并行切法，同一份权重在两种切法之间切换时不留冗余副本，通信量也尽量小。第三是自动映射算法：自动决定哪些模型放在同一批 GPU 上、每个模型分多少张卡、每个模型用什么并行配置。在最多 128 张 A100 上，与 DeepSpeed-Chat、OpenRLHF、NeMo-Aligner 相比，HybridFlow 的吞吐提高了 1.53–20.57 倍。

1 引言：RLHF 为什么既难写又难跑

这一节要回答的问题：大模型的 RLHF 训练比普通训练复杂在哪里？论文先把 RLHF 抽象成一张“数据流图”，然后指出两类已有方案各自的问题：传统 RL 框架写起来灵活，但跑大模型时调度开销太大；已有的 RLHF 系统跑得快，但写死了一种流程，想换个算法就要大改代码。HybridFlow 要同时做到“灵活”和“高效”。
先补一点背景：RLHF 在大模型训练里处在什么位置。

大模型的训练一般分三步。预训练：在海量文本上反复做“预测下一个词”，模型由此学到广泛的知识。监督微调（SFT）：用人工写好的“指令—回答”对继续训练，模型学会按指令回答问题。但 SFT 只能让模型模仿示范，没法告诉它“两个都还行的回答里哪个更好”；训练数据里的有害或带偏见的内容，也仍然可能被模型说出来。

RLHF 补的就是这一步。先让人对模型的多个回答排序，用排序数据训练一个奖励模型，它能给任意一个回答打一个分数；然后用强化学习调整模型，让它更倾向于生成高分的回答。InstructGPT、Claude 等模型都用过这套流程。论文用的强化学习算法主要是 PPO（近端策略优化），下一节会把它拆开讲。

以最常见的 PPO 版 RLHF 为例，系统里有四个大模型：actor 是正在被训练的语言模型本身；critic 估计“这个回答写到这里，预期最终能得多少分”；reference policy（参考策略）是训练开始时 actor 的一份冻结副本，用来约束 actor 不要偏离原来太远；reward model（奖励模型）给完整的回答打分。每一轮迭代分三个阶段：生成，actor 针对一批 prompt 一个 token 一个 token 地写出回答；准备，critic、reference、reward model 各对“prompt + 回答”做一次前向，分别算出价值、参考概率和奖励；训练，用这些数据更新 actor 和 critic 的参数。其他 RLHF 算法也大致遵循这三个阶段，只是参与的模型个数和数据依赖不同。

先补一点背景：什么是“数据流图”。

数据流图是一张有向无环图（DAG）：每个节点是一次计算，每条边表示“这次计算的输出是那次计算的输入”。只要依赖关系满足，没有边相连的节点就可以同时算。传统强化学习（比如训练智能体玩游戏）早就可以画成这样一张图：节点是“actor 网络前向”“critic 网络训练”这样的神经网络计算，边是它们之间传递的数据，比如 critic 的输出要拿去训练 actor。

RLHF 的图形状和传统 RL 差不多，但每个节点和每条边都“变重”了。在传统 RL 里，网络是几层的 CNN 或 MLP，一个节点一张卡甚至一个 CPU 就能算完。在 RLHF 里，每个节点是一个大模型的训练、推理或生成，本身就要切到几十张 GPU 上，用张量并行、流水线并行、数据并行协同完成，所以每个节点都是一个分布式程序。每条边也不再是“把一个张量传过去”，而是“把分散在 A 组 GPU 上的输出，按照 B 组 GPU 的切法重新分发”，这是一种多对多的组播。而且不同节点的计算性质不同，最合适的并行切法也不同。论文的结论是：RLHF 需要一种既能灵活表达这张图、又能高效执行它的框架。

已有的两类方案都只做到了一半：

  • 传统 RL 框架（如 RLlib、RLlib Flow）用的是单控制器：一个中心进程把图里的节点分派给不同进程，并协调它们的执行顺序。这种写法很灵活，但这些框架只提供数据并行训练的原语，处理的网络最多几百 MB。一个大模型有海量算子、要切到很多张卡上，如果每个算子都要由中心控制器发指令，调度开销会大到不可接受。
  • 已有的 RLHF 系统（DeepSpeed-Chat、OpenRLHF、NeMo-Aligner）用的是多控制器：每张卡各自运行一份程序，模型之间靠点对点通信协调。计算时几乎没有调度开销，但由于没有中心控制，一个节点的数据依赖一变，所有相关节点的实现都要跟着改，代码很难复用。

HybridFlow 的关键观察是：RLHF 的图里只有寥寥几个节点（几个模型），在节点之间用单控制器，消息量很小，开销可以忽略，却换来了灵活性；在节点内部用多控制器，保住了计算效率。围绕这个观察，论文有三项贡献：分层的混合编程模型（§4）、负责 actor 训练与生成切换的 3D-HybridEngine（§5）、自动设备映射算法（§6）；实验显示吞吐提高 1.53–20.57 倍（§8）。

读的时候容易误解的一点：论文里的 “RLHF” 泛指 PPO、ReMax、Safe-RLHF 这类“生成 → 打分 → 更新”的 RL 后训练算法。论文写于 2024 年，奖励主要来自奖励模型；但 §9 已经指出，奖励也可以来自代码沙箱或判对错的规则函数，这正是后来推理模型 RL 的主流做法。从系统的角度看，两者的数据流几乎一样，只是“奖励”这个节点从一个大模型换成了一段普通程序。

2.1 RLHF 一轮迭代：四个模型、三个阶段

先补一点背景：PPO 版 RLHF 里每个模型的输出被拿去做什么。

把“生成一个回答”看成一连串决策：状态 \(s_t\) 是 prompt 加上已经写出的前 \(t\) 个 token，动作 \(a_t\) 是下一个 token，策略 \(\pi_\theta\) 就是语言模型本身（actor）。奖励模型只对完整的回答 \(y\) 给一个分数 \(r_{\mathrm{RM}}(x,y)\)。如果只追求这个分数，actor 很快会学会钻奖励模型的空子，写出分数高但很奇怪的文字。常见的做法是在每个 token 上扣掉一个“偏离参考模型的程度”，于是逐 token 的奖励是：

$$r_t=-\beta\,\log\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\mathrm{ref}}(a_t\mid s_t)}\;+\;\mathbb{1}[t=T]\cdot r_{\mathrm{RM}}(x,y)$$

这里 \(\pi_{\mathrm{ref}}\) 是冻结的参考模型，\(\beta\) 控制惩罚力度，\(T\) 是回答的最后一个 token。所以 reference 模型的任务就是对每个 token 算出 \(\log\pi_{\mathrm{ref}}\)。

PPO 还需要知道每一步动作“比平均水平好多少”，这叫优势 \(\hat A_t\)。critic 输出价值 \(V(s_t)\)，即从状态 \(s_t\) 往后预期能拿到的总奖励；用逐 token 奖励和价值，按 GAE（广义优势估计）的公式就能算出每个 token 的优势。最后，actor 用 PPO 的截断目标更新：

$$L(\theta)=\mathbb{E}_t\Big[\min\big(\rho_t\hat A_t,\ \mathrm{clip}(\rho_t,1-\epsilon,1+\epsilon)\,\hat A_t\big)\Big],\qquad \rho_t=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\mathrm{old}}(a_t\mid s_t)}$$

\(\pi_{\mathrm{old}}\) 是生成这批数据时的 actor。比值 \(\rho_t\) 被截断在 \([1-\epsilon,1+\epsilon]\) 之内，防止一次更新把策略改得太多。critic 则用平方误差去拟合实际得到的回报。这些公式是 InstructGPT 式 PPO-RLHF 的常见写法，HybridFlow 论文本身不讨论算法细节；写在这里，是为了让你看清每个模型的输出被拿去做什么、为什么它们之间有依赖。

论文把 PPO 的一轮迭代拆成三个阶段（对应原文图 1(a)）：

  • 阶段一：生成。actor 对一批 prompt 做自回归生成，得到回答，同时记下每个 token 的 \(\log\pi_{\mathrm{old}}\)。
  • 阶段二：准备。critic 对“prompt + 回答”算价值，reference 算参考 log 概率，reward model 算奖励，三者都只做一次前向。随后用这些结果算出优势，这一步是纯数值计算，不需要跑模型。
  • 阶段三：训练。actor 和 critic 用上面这批数据做前向、反向和 Adam 更新。

2.2 并行策略：DP、TP、PP 与“3D 并行”

先补一点背景：一个大模型是怎么切到多张卡上的。
  • 数据并行（DP）：每张卡都放一份完整模型，把一批数据分成几份，各算各的，最后把梯度加起来。DP 的大小 \(d\) 就是模型副本的个数。ZeRO 是省显存的数据并行：把优化器状态、梯度、参数依次切开分给各卡，用到时再临时收集（详见本站的 ZeRO 精读 §5）。PyTorch 的 FSDP 是同一思路的实现。
  • 张量并行（TP）：把每一层的权重矩阵切成 \(t\) 份，每张卡只算其中一份，每层算完用一次 all-reduce 把部分结果合起来（详见 Megatron-LM 精读 §3）。TP 通信很频繁，一般只在同一台机器内、用 NVLink 相连的卡之间做。
  • 流水线并行（PP）：把模型按层切成 \(p\) 段，每段放在不同的卡上，数据像流水线一样一段段往下传。

三者可以组合，称为 3D 并行，记作 \(p\)-\(t\)-\(d\)：一共用 \(p\times t\times d\) 张卡，每份模型副本被切成 \(p\) 段流水线、每段再切成 \(t\) 片，一共有 \(d\) 份副本。Megatron-LM 给卡编号的惯例是：TP 组由编号相邻的卡组成；同一副本的 PP 各段接在后面；而 DP 组由间隔为 \(p\times t\) 的卡组成。这个编号惯例在 §5 会变得很关键。

大模型推理服务（如 vLLM）也用类似的 3D 并行，只是需要切开的东西只有模型参数和 KV 缓存，没有梯度和优化器状态。

RLHF 里的模型要做三类计算：训练（一次前向、一次反向、一次参数更新），推理（一次前向），生成（自回归，要做很多次前向）。具体来说，actor 要做训练和生成，critic 要做训练和推理，reference 和 reward model 只做推理。不同模型、不同计算可以用不同的并行策略，才能各自达到最高吞吐。

2.3 编程模型：单控制器与多控制器

先补一点背景：“控制器”是什么。

在分布式训练里，“控制器”指决定每张 GPU 下一步算什么、并把计算内核发给 GPU 的那段程序（通常是 CPU 上的一个进程）。打个比方：单控制器像一个乐队指挥，所有乐手只听他的手势，他要对每个乐手、每个小节都发指令；多控制器像每个乐手手里都有完整的总谱，大家各自看谱演奏，只在约定的小节对齐。后者在深度学习里叫 SPMD（单程序多数据）：例如用 torchrun 启动 8 个一模一样的进程，每个进程靠自己的编号（rank）决定算哪一部分数据。Megatron-LM、DeepSpeed、vLLM 都是这种写法。

单控制器有一个中心控制器管理整个分布式程序的执行流程。用户可以把数据流的核心逻辑写成一个单进程程序（原文图 2(b) 上半部分），控制器自动生成分布式的 worker 去执行。因为控制器能看到整个硬件和整张数据流图，它可以灵活地安排资源和执行顺序。代价是所有协调消息都要从控制器发到每个 worker：一个大模型一次前向就要启动成千上万个 GPU 内核，再乘上几百张卡和生成时的上千步，如果每个内核都要中心控制器发指令，控制器本身就成了瓶颈（TensorFlow 早期版本和 Pathways 都讨论过这个问题）。

多控制器让每张卡都有自己的控制器。当时最好的大模型训练和推理系统都用这种方式，因为它扩展性好、调度开销低：控制消息只是从本机 CPU 经 PCIe 发给本机 GPU。但用它来写 RLHF 就很别扭（原文图 2(a)）：每个模型是一个独立的程序，同一模型的所有 worker 跑同一份代码；每个 worker 只知道自己的局部状态，模型之间要靠点对点通信来协调执行顺序。于是 actor 的程序里，在生成循环之后要写“把结果收集到 0 号卡，再发给 critic、发给奖励模型”；critic 的程序里要写一个 while True 循环，在精确的位置“从 actor 接收、在组内广播、收集权重、做前向”。计算、集合通信和点对点传输层层嵌套在每张卡的程序里。想加一个 cost model，就要同时改 actor 的发送代码和新模型的接收代码；想换一种模型放置方式，就要改模型初始化和数据传输的内部逻辑。

2.4 RLHF 负载的三个特点

特点一：模型负载各不相同。reference 和 reward model 只做前向，显存里只需要放参数；actor 和 critic 要训练，除了参数还要放梯度和优化器状态。按常见的混合精度 Adam 估算，训练时每个参数大约要 16–18 字节，而只做前向时 BF16 参数只要 2 字节（推算）。也就是说，同样是 7B 的模型，actor 训练时占约 112–126 GB，reference 只占约 14 GB，相差 8–9 倍（推算）。此外，模型大小也可以不同：论文举例，可以用一个 7B 的 actor 搭配 70B 的 critic 和奖励模型，以求更好的对齐效果。所以每个模型需要各自的并行策略和优化。

特点二：actor 的训练和生成很不平衡。在数据流里，actor 的训练和生成是两个节点，它们通常占一轮迭代的大部分时间：用 HybridFlow 跑时占 58.9%。两者对并行方式的偏好正好相反：

  • 训练是计算受限的，而且要放下参数、梯度、优化器状态，所以通常要把模型切得很碎、分到更多卡上，比如把 7B 模型切成 8 份放在 8 张卡上。
  • 生成是显存带宽受限的（每生成一个 token 都要把参数和 KV 缓存读一遍，而计算量很小，详见 vLLM 精读 §2.2）。如果沿用训练时的 8 路切分，每张卡上的矩阵乘法太小，每一层还要在 8 张卡之间做一次 all-reduce，GPU 大部分时间在等通信和数据，算力用不满。已有研究（如 AlpaServe、DistServe）表明，用更小的模型并行度加更大的数据并行度更好，比如在 8 张卡上把 7B 模型切成 2 份、复制 4 份，各副本独立生成。

可是两个阶段用不同的切法，就要在运行时把 actor 的权重在两种布局之间重新分配（重分片），这会带来通信和显存开销。论文引用 OpenRLHF 的数据：对齐一个 70B 的 actor，每轮迭代要把 140 GB 的权重从训练端传到生成端；当两个阶段放在不同的卡上时，这一步最多占迭代时间的 36.4%。

特点三：模型放置的需求多种多样。放在不同卡上的模型，只要没有数据依赖，就能同时算；放在同一批卡上的模型（称为共置，colocate）共享显存，只能分时轮流执行，因为同时跑几个大模型很容易显存溢出（OOM）。这里有一个取舍：分开放能并行，但由于 RLHF 是分阶段执行的，每个模型在别的阶段只能干等。论文图 3 的例子里，actor 和 critic 分开放置，训练阶段可以并行，但它们各有 1/3 的 GPU 时间处在空闲状态。

2.6 设计考量：在哪一层用哪种控制器

把上面的分析合起来，关键问题是：怎样设计一种既灵活又高效的编程模型来实现 RLHF 数据流？论文的回答是分层看待：

  • 在节点之间（模型与模型之间），单控制器特别合适。它能灵活地协调数据传输、执行顺序和资源分配；而 RLHF 的数据流通常只有几个节点，从控制器给各节点发消息的开销，和每个节点内部的分布式计算比起来可以忽略。
  • 在节点内部（一个模型的分布式计算），多控制器调度算子的延迟低，正好用来跑每个模型的训练、推理和生成。

于是 HybridFlow 采用分层的混合编程模型：节点间单控制器、节点内多控制器。这样做把“节点内的分布式计算”和“节点间的数据传输”拆开了，每个模型只需要关心自己的本地计算，不用管别的模型怎么切、数据怎么传。

4.1 节点内：把每个模型的分布式程序封装起来

对每个模型在各阶段的分布式计算，HybridFlow 提供一个基类 3DParallelWorker。给它分配好设备后，它负责分布式地初始化模型权重，并为模型建立 3D 并行组。所谓并行组，就是承载模型某一个并行维度的一组 GPU，比如 TP 里持有不同张量切片的那几张卡，DP 里持有不同模型副本的那几张卡。

在这个基类之上，HybridFlow 为 actor、critic、reference、reward 分别提供模型类。每个模型类封装了该模型的分布式前向、反向、自回归生成和优化器更新，并把这些分布式计算代码和“它与别的模型之间的数据依赖”分开。这些 API 可以直接复用现有大模型系统里的计算脚本，例如 actor 类（ActorWorker）的 update_actor，里面的计算就和 Megatron-LM 的预训练脚本差不多。论文附录表 4 列出了各模型类的主要 API：

4.2 节点间：用“传输协议”统一模型之间的数据重分片

先补一点背景：远程调用与 future。

HybridFlow 的控制器建在 Ray 之上。在 Ray 里，可以把一个类实例放到远端的进程上（称为 actor，注意和 RLHF 的 actor 模型无关），控制器调用它的方法时，调用立即返回一个 future（一张“取货单”），真正的计算在远端异步进行。拿着 future 的人可以把它转交给别人；谁需要真正的数据，谁再凭单去取。这样，控制器可以只传递 future，而让大块数据在 GPU 之间直接传输。

两个并行策略不同、又放在不同卡上的模型之间传数据，是一个多对多的组播。HybridFlow 把它统一成一个机制：用装饰器 @register 给每个模型类的每个操作绑定一个传输协议。每个传输协议由两个函数组成：collect（收集）按该模型的并行策略把输出汇总起来，distribute（分发）按该模型的并行策略把输入分发下去。比如 actor 的训练用 3D 并行，update_actor 就注册到 3D_PROTO 协议：它的 collect 函数把每个 DP 组的输出（比如 update_actor 返回的损失值）汇总到单控制器，它的 distribute 函数把输入（比如优势）分发到每个 DP 组。一次模型间的数据重分片，就是“源模型输出端的 collect”加“目标模型输入端的 distribute”。

4.3 灵活的模型放置与异步执行

放置。HybridFlow 提供一个 ResourcePool 类，它把一组 GPU 虚拟成一个资源池。把某个 ResourcePool 实例交给一个模型类，这个模型的分布式计算就映射到这组卡上。用同一个实例的模型就是共置的；用不同实例的模型放在不同的卡上。论文假设不同的资源池互不重叠。于是“换一种放置方式”只是改几行初始化代码，而不必改模型内部或传输逻辑。

异步执行。当模型放在不同的卡上时，只要输入准备好了，它的执行就会被自动触发（这是 Ray 的数据流执行方式）。在上面的例子里，actor 的 future 一返回，控制器就可以发起对 critic 的调用，不必等 actor 真正算完。当几个模型共置在同一批卡上时，它们按调用顺序依次执行。因此，同一份算法代码在不同的放置方案下，会自动呈现不同的执行模式，不需要改动算法代码（原文图 6）。

4.4 用几行代码实现 PPO、ReMax 和 Safe-RLHF

有了这些 API，一个 RLHF 算法就可以写成单控制器上的一个单进程程序：依次调用各模型的原语，每个原语在多张卡上以多控制器方式执行。下面是本站按论文图 6 的结构重写的 PPO 主循环：

# 运行在单控制器上的普通 Python 程序；每一行调用都在对应模型的 GPU 组上并行执行
for prompts in dataloader:
    batch = actor.generate_sequences(prompts)        # ① 生成
    batch = critic.compute_values(batch)             # ② 准备：价值
    batch = reference.compute_ref_log_prob(batch)    #          参考 log 概率
    batch = reward.compute_reward(batch)             #          奖励
    batch = compute_advantage(batch, algo="ppo")     #   控制器本地的数值计算（KL 惩罚 + GAE）
    critic_metrics = critic.update_critic(batch)     # ③ 训练
    actor_metrics = actor.update_actor(batch)

论文说 PPO 只需要 8 行。改成 Safe-RLHF：再初始化一个 cost model（直接复用奖励模型的类），在准备阶段多算一次代价，在训练前让 actor 对预训练数据算一次 compute_loss 并放进 batch，一共只多 5 行。改成 ReMax：多调用一次 generate_sequences（关掉采样，即贪心解码），再删掉和 critic 有关的行。

这种灵活性对研究者很重要：他们可以复用每个模型类里封装好的分布式计算，只修改和算法有关的数值部分，比如 compute_advantage 里的 GAE 和 KL 项、actor 和 critic 的损失函数。因为模型计算和模型间的数据传输是解耦的，底层分布式框架的任何改动都不影响算法代码，每个模型的执行也可以单独优化（§5）；模型的放置也可以灵活调整（§6）。

5 3D-HybridEngine：actor 怎么在训练和生成之间换切法

这一节要回答的问题：§2.4 说过，actor 训练时适合切得碎（大 TP、PP），生成时适合切得粗、多复制几份（小 TP、大 DP）。如果训练和生成在同一批卡上、共用同一份权重，那么每轮迭代都要把权重从一种切法换成另一种。这个切换怎么做，才能既不在显存里留一份多余的副本，又让通信量尽量小？论文的答案是一种特别的“生成阶段并行组”编号方式。

5.1 记号：训练用 p-t-d，生成用 pg-tg-dg-d

为了不保留多余的 actor 副本，论文主张把 actor 的训练和生成放在同一批卡上（共 \(N_a\) 张），在同一份权重上依次执行。训练用 3D 并行组 \(p\)-\(t\)-\(d\)：\(p\) 段流水线、\(t\) 个张量切片、\(d\) 个模型副本。生成用另一套并行组，记作 \(p_{g}\)-\(t_{g}\)-\(d_{g}\)-\(d\)：\(p_{g}\) 是生成时的流水线段数，\(t_{g}\) 是生成时的张量切片数，\(d_{g}\) 是新引入的微 DP 组（micro DP group）的大小。它的意思是：训练时的每个 DP 副本，在生成时变成 \(d_{g}\) 个更小的副本，分别处理 \(d_{g}\) 份 prompt。卡的总数不变，所以：

$$N_a=p\,t\,d=p_{g}\,t_{g}\,d_{g}\,d,\qquad\text{即}\qquad d_{g}=\frac{p\,t}{p_{g}\,t_{g}}$$

举个例子：16 张卡上训练 7B actor，用 1-8-2（不切流水线，8 路 TP，2 个副本）。生成时如果用 \(t_{g}=2\)、\(p_{g}=1\)，那么 \(d_{g}=8/2=4\)，生成阶段一共有 \(d_{g}\times d=8\) 个副本，每个副本只占 2 张卡（推算）。这正是 §8.4 实验里用的设置。微 DP 组只在生成阶段使用，目的就是用更大的数据并行度把卡用满。

5.3 零冗余的关键：生成阶段的卡怎么分组

先补一点背景：all-gather 和它的通信量。

all-gather 是一种集合通信：\(n\) 张卡各持有一块数据，做完之后每张卡都拿到全部 \(n\) 块。如果全部数据的大小是 \(M\)，每张卡原本有 \(M/n\)，那么每张卡至少要收进别人的 \((n-1)/n\cdot M\)。用环形算法实现时，每张卡在 \(n-1\) 步里每步收一块、发一块，正好达到这个下限。下面的小演示可以一步一步看 all-gather（选“All-Gather”）：

3D 并行里通常的分组方法（§2.2）是：PP 组和 TP 组由编号连续的卡组成，DP 组由间隔为 \(p\times t\) 的卡组成。原文图 8 用 2 台机器、8 张卡举例：训练用 1-4-2，即 TP 组 [G1,G2,G3,G4] 和 [G5,G6,G7,G8]，DP 组 [G1,G5]、[G2,G6]、[G3,G7]、[G4,G8]。每张卡持有每个权重矩阵的 1/4，记作片 1–4（G1 持片 1，G2 持片 2，……，G5–G8 同理）。生成想用 1-2-2-2，即 \(t_{g}=2\)，每张卡需要每个矩阵的一半：“前半”= 片 1+2，“后半”= 片 3+4。

做法一：生成阶段沿用同样的分组规则（论文称这种系统为 HybridFlow-V）。生成 TP 组仍由相邻的卡组成：[G1,G2]、[G3,G4]；于是 G1、G3 负责前半，G2、G4 负责后半；微 DP 组则是 [G1,G3]、[G2,G4]。切换时，先在训练的 TP×PP 组内做 all-gather，让每张卡都拼出完整模型，再只保留生成时自己需要的那一半。

做法二：HybridFlow 的新分组规则。生成 TP 组和 PP 组改为按间隔挑卡，间隔分别是 \(t/t_{g}\) 和 \(p/p_{g}\)；微 DP 组则由沿生成 TP（或 PP）方向连续的卡组成。在这个例子里，\(t/t_{g}=2\)，生成 TP 组是 [G1,G3]、[G2,G4]、[G5,G7]、[G6,G8]，微 DP 组是 [G1,G2]、[G3,G4]、[G5,G6]、[G7,G8]。下面把两种做法逐张卡比较一遍（G5–G8 与 G1–G4 完全对称）：

此外，新规则下几个 all-gather 在各自的微 DP 组内同时进行，参与的卡少、互不干扰；旧规则要在整个训练 TP×PP 组内收集完整模型。这就是通信量大幅下降的原因。

6 自动设备映射：四个模型放在哪、各分几张卡

这一节要回答的问题：混合编程模型让“任意放置”变得容易，但哪种放置最快？给定一个集群和一个 RLHF 数据流，要同时决定三件事：哪些模型共置、每组模型分几张卡、每个模型在每个阶段用什么并行配置。论文用一个枚举 + 模拟器估时的算法来回答，并说明它的复杂度和实际运行时间。
先补一点背景：4 个模型有几种放置方式。

“放置”就是把模型集合分成若干组，同组共置、异组分开。把 \(k\) 个元素分成若干个非空组的方法数叫贝尔数。对 PPO 的 4 个模型 {actor, critic, reference, reward}：全部一组 1 种（DeepSpeed-Chat 的做法）；分两组时，3+1 有 4 种、2+2 有 3 种（NeMo-Aligner 的 {actor, reference} + {critic, reward} 是其中之一）；分三组（2+1+1）有 6 种；每个模型单独一组 1 种（OpenRLHF 的做法）。合计 1+7+6+1 = 15 种，与论文说的 15 种一致。

论文把“放置方案”和“每个模型在每个阶段的并行策略”合称为一个映射。算法 1 寻找使每轮 RLHF 迭代端到端延迟最小的映射，步骤如下：

示意图：自动映射算法（算法 1）的搜索流程
① 枚举放置方案PPO：15 种→② 每个共置组最少几张卡按显存算，保证不 OOM：\(A_{\min}\)→③ 枚举每组分多少卡从 \(A_{\min}\) 起，所有可行分法
→④ auto_parallel对每个模型枚举 (p,t,d)，用模拟器估时，取最快→⑤ d_cost组内相加、组间取最大、各阶段相加→⑥ 保留总延迟最小的映射
本站示意图，根据原文 §6 的算法 1 ↗ 与附录 C 的算法 2 整理。
  1. 枚举放置。列出模型在集群上所有可能的放置方案，从全部分开到全部共置。共置在同一批卡上的模型称为一个共置组；同一组里的模型可以在同一批卡上用不同的并行策略。
  2. 最少卡数。根据组内模型的显存占用，算出每个共置组至少要分多少张卡才不会 OOM，记为 \(A_{\min}\)。
  3. 枚举分配。从 \(A_{\min}\) 出发，枚举所有可行的卡数分配方案 \(A\)。
  4. 为每个模型找并行策略。给定一个组分到的卡数和组内模型的负载 \(W\)（输入输出形状，以及是训练、推理还是生成），auto_parallel 模块为每个模型寻找延迟最低的并行策略。它用一个模拟器 simu 估算不同策略的延迟。
  5. 估算整轮延迟。d_cost 按数据流的阶段逐个估算：同一共置组里、同一阶段要算的模型（比如训练阶段的 actor 和 critic）只能先后执行，延迟相加；不同共置组在同一阶段可以并行，这个阶段的延迟取各组中的最大值；最后把各阶段的延迟相加。
  6. 取最优。在所有放置和分配中，选出每轮迭代总时间最短的那一个。

并行策略怎么搜（附录 C 的算法 2）。对一个分到 \(N_l\) 张卡的模型，从它的最小模型并行度（为了和同组其他模型一起放下而不 OOM）开始，让 TP 大小 \(t\) 从最小值取到每台机器的卡数 \(U\)（默认 8），让 PP 大小 \(p\) 从最小值取到 \(N_l/U\)，DP 大小则是 \(d=N_l/(p\,t)\)；对每个 \((p,t,d)\) 调用模拟器估时，取最快的。模拟器是分析式模型，有训练、推理、生成三种：训练和推理按计算受限估算，生成按显存带宽受限估算。对 actor，先找训练的最佳策略并记下训练时的显存占用；生成时再根据批大小和最大序列长度算出 KV 缓存需要多少显存，如果生成阶段的模型并行度放不下参数加 KV 缓存，就加大模型并行度，然后在可行的策略和对应的 KV 缓存分配中比较估计延迟。

复杂度。算法 1 的最坏情况复杂度是 \(O\!\left(\frac{(N-1)!}{(k-1)!\,(N-k)!}\right)\)，其中 \(k\) 是模型个数、\(N\) 是总卡数。这个数就是组合数 \(\binom{N-1}{k-1}\)，即把 \(N\) 张卡分给 \(k\) 个各自独立放置的模型、每个至少一张卡的分法数，对应最坏的情况（全部独立放置）。例如 \(N=128\)、\(k=4\) 时约为 33 万种（推算：\(\binom{127}{3}=333{,}375\)）。为了加速，算法把“某个模型在 \(A\) 张卡上的最佳并行策略”缓存起来，不同放置方案里遇到同样的“模型 + 卡数”就不再重复搜索。论文还指出，虽然算法假设 \(N\) 张同构 GPU，但只要在模拟器和 auto_parallel 中考虑异构设备，就能推广到异构集群。

读的时候要注意：“最优”是指在这个搜索空间和这个代价模型下最优。模拟器是分析式估算，不是实测；TP 被限制在一台机器之内；d_cost 假设各阶段之间严格同步、一轮迭代内不同阶段不重叠。真实负载（比如回答长度参差不齐）与模拟器的假设相差较大时，搜出来的方案未必是实测最快的。

7 实现：约 1.2 万行 Python

这一节要回答的问题：HybridFlow 是在哪些现成系统之上搭起来的？控制器、3D-HybridEngine、自动映射各自的实现要点是什么？为了接入多控制器的写法，对 vLLM 做了什么改动？

HybridFlow 一共约 12k 行 Python 代码。

混合编程模型（约 1.8k 行）。中心化的单控制器建在 Ray 之上，用远程过程调用（RPC）协调各模型的执行顺序，并按数据流在模型之间传数据；中间数据存成 TensorDict。在多控制器这一层，每个模型函数在各设备上的独立进程里运行，控制消息从每个控制器的 CPU 进程直接发给对应的 GPU。训练和推理引擎支持 Megatron-LM、PyTorch FSDP 和 DeepSpeed，自回归生成用 vLLM。值得一提的是，作者把 vLLM 里集中式的 KV 缓存管理器换成了分布式的管理器。原因是 vLLM 原本由一个中心调度器维护唯一一份块表、每步广播给所有 GPU（见 vLLM 精读 §4.6），这本身就是一种单控制器设计；而 HybridFlow 要求每个模型内部按多控制器方式运行，每张卡的进程自己驱动自己的那部分计算。

3D-HybridEngine（约 2.4k 行，基于 Megatron-LM 和 vLLM）。actor 在训练和生成阶段的权重存放在不同的缓冲区：训练时把生成用的权重卸载到 CPU 内存，切换时再装回 GPU，生成时两块缓冲区一起使用。切换时用 NCCL 的通信原语在每个微 DP 组内收集并拼接模型参数。生成结束后，KV 缓存被卸载到 CPU 内存，下一轮再装回 GPU。

自动映射算法（约 1.9k 行），连同训练、推理、生成三个模拟器。它在 RLHF 数据流开始执行之前，在 CPU 上运行，产出设备映射和并行策略，用来初始化数据流。

8 实验：快多少，在什么条件下

这一节要回答的问题：HybridFlow 端到端比三个已有系统快多少？优势在哪些模型大小、哪些集群规模下最大，在哪些情况下最小？不同的放置方式什么时候更好，自动映射有没有选对？3D-HybridEngine 把切换时间降了多少，生成阶段用更小的 TP 到底值不值？自动映射算法本身要跑多久？

8.1 实验设置

  • 机器。16 台机器共 128 张 GPU，每台 8 张 NVIDIA A100-80GB，机内 NVLink 600 GB/s，机间带宽 200 Gbps。软件为 CUDA 12.1、PyTorch 2.1.2、Megatron-core 0.6.0、NCCL 2.18.1、vLLM 0.3.1。
  • 算法与模型。PPO、ReMax、Safe-RLHF 三种算法；所有模型都是 Llama 结构，从 7B 到 70B。Safe-RLHF 多一个与奖励模型同结构同大小的 cost model，ReMax 没有 critic。actor 和 critic 的训练用混合精度：参数 BF16，梯度和优化器状态 FP32，优化器为 Adam；推理和生成用 BF16。没有特别说明时，结果都来自 PPO。
  • 对比系统。DeepSpeed-Chat v0.14.0、OpenRLHF v0.2.5、NeMo-Aligner v0.2.0（NeMo-Aligner 不支持 ReMax）。论文没有比较 TRLX、HuggingFace DDP、ColossalChat 等，理由是 DeepSpeed-Chat 的论文已经表明它们更慢。
  • 指标。RLHF 吞吐（tokens/s）= 一个全局批里 prompt 和回答的 token 总数 ÷ 一轮迭代的时间。先热身 10 轮，再取 5 轮的平均。
  • 数据与超参。数据集为 HuggingFace 上的 Dahoas/full-hh-rlhf。因为对比系统在生成时可能没有连续批处理（continuous batching）优化，为了公平，所有回答都被强制生成相同的长度：prompt 长度和回答长度都是 1024，actor 的全局批大小是 1024 个 prompt。PPO 每轮 1 个 epoch，每个 epoch 做 8 次更新。

为了对这些数字有个直观感觉：每轮迭代处理 1024 × (1024 + 1024) ≈ 210 万个 token。7B 模型在 8 张卡上，HybridFlow 的吞吐约 5.6k tokens/s，所以一轮约 6 分钟；在 128 张卡上约 37k tokens/s，一轮约 56 秒；70B 在 128 张卡上约 8.2k tokens/s，一轮约 4 分钟（推算，吞吐取自原文图 9 的读图值）。

这个设置有意去掉了什么：所有回答被固定为 1024 个 token，这让对比更公平，但也去掉了真实 RL 训练里最麻烦的现象之一：回答长短不一、少数特别长的回答拖住整批。所以这里的结论主要说明“并行与放置做得好不好”，而不涉及长尾生成带来的空等。后来的异步 RL 系统正是冲着这个问题去的（见“后来怎么样了”）。另外，§8.2 的实验里四个模型大小相同。

8.2 端到端性能

这组实验里 actor、critic、reference、reward 大小相同。每种模型大小使用的卡数，从“不 OOM 的最少卡数”一直到 128 张；为公平起见，没有开启优化器状态卸载。

总体结果。HybridFlow 在所有模型规模上都更快。以 PPO 为例，它相对 DeepSpeed-Chat、OpenRLHF、NeMo-Aligner 的平均加速分别为 3.67 倍（最高 7.84 倍）、3.25 倍（最高 5.93 倍）和 12.52 倍（最高 20.57 倍）。论文给出的主要原因是：HybridFlow 在每个阶段都按负载为每个模型选了合适的并行策略。在 70B 模型上平均加速最大，达到 9.64 倍，因为 HybridFlow 相对 DeepSpeed-Chat 和 OpenRLHF 把切换开销分别降低了最多 71.2% 和 89.1%，而后两者在用 ZeRO-3 训练时还有大量跨机通信。NeMo-Aligner 的主要瓶颈在生成阶段，论文说它的生成引擎缺少 KV 缓存，生成最多占其迭代时间的 81.2%。ReMax 和 Safe-RLHF 上的趋势相同（原文图 10、11）。

扩展性。在 8 张卡上，HybridFlow 至少有 2.09 倍加速。随着卡数增加，HybridFlow 在各模型规模上的强扩展效率为 66.8%，计算方式是“最大规模吞吐 ÷ 最小规模吞吐”再除以“最大卡数 ÷ 最小卡数”，对三种算法和所有模型规模取平均。扩展效率达不到 100%，是因为全局批大小固定：卡越多，每张卡分到的本地批越小，GPU 越可能吃不饱。比如 7B 从 8 卡扩到 128 卡，卡数是 16 倍，吞吐约 6.6 倍（推算）。即便在 128 张卡上跑 7B 模型，HybridFlow 仍比最强的对比系统 OpenRLHF 快：PPO 1.68 倍、ReMax 1.53 倍、Safe-RLHF 1.71 倍。论文把这归功于 HybridFlow 能针对不同模型和集群规模选择最佳放置。OpenRLHF 在大集群上表现较好，在小集群上效率较低。

怎么理解“1.53–20.57 倍”：
  • 下限 1.53 倍来自最不利的组合：ReMax、7B 模型、128 张卡、对比当时最强的 OpenRLHF。小模型配大集群时，每张卡的活不多，各系统差距最小。
  • 上限 20.57 倍是对比 NeMo-Aligner v0.2.0 得到的，而论文自己指出它的生成引擎缺少 KV 缓存。对比 OpenRLHF 的平均值是 3.25 倍，这个数更能代表“同样做了不少优化的系统之间”的差距。
  • 所有对比都在“回答长度固定、四个模型同样大小”的设置下完成；对比系统是各自 2024 年的版本，后来都有很大改进。

对于“13B actor/reference + 70B critic/reward”这种大小悬殊的组合，在 64 张卡以内，全部共置平均比其他放置快 44.8%；96 张卡时 split 更好；128 张卡时，算法 1 找到的方案把 actor、reference、reward 共置在 64 张卡上，把剩下 64 张卡全给 critic。原因是在同样的卡数下，13B 的 actor 和 reference 算得比 70B 的 critic 和 reward 快得多，让 reward 和它们共置，可以减少准备阶段的空等。总的来说，在大集群上把 actor 和 critic 放在不同的卡上、让它们在训练阶段并行，吞吐更高。

原文图 16 给出了算法 1 的运行时间，横轴同时增大模型和卡数（从 7B/8 卡到 70B/128 卡），纵轴是对数刻度的秒数。读图约为：7B/8 卡约 11 秒，13B/32 卡约 2 分钟，34B/64 卡约 7 分钟，70B/128 卡约 26 分钟。运行时间大致线性增长，说明算法对模型规模和集群规模都有不错的扩展性。大部分时间花在用模拟器估算各模型各并行策略的延迟上：模型越大，可选的并行策略越多，需要模拟的次数也越多。靠着把每个模型的最佳并行策略缓存起来、在不同放置方案之间复用，搜索最佳放置最多只需半小时，和动辄几天的 RLHF 训练相比可以忽略。

9 讨论、相关工作与结论

这一节要回答的问题：HybridFlow 怎么处理容错？从实验里能总结出哪些关于放置的经验？它和多模型共享 GPU 的研究、和更早的数据流系统（如 Ray、Pathways）是什么关系？以及，从“对齐”转向“推理”时，这个框架还适用吗？

容错。HybridFlow 与已有的容错方法是正交的，本身已经支持检查点。故障可以通过 NCCL 报错发现，静默数据损坏可以用校验和发现。在这个编程模型下，单控制器可以通过 RPC 协调各 worker 组保存检查点，内容包括 actor 和 critic 的参数、数据加载器的位置和随机数生成器的状态，以保证整个系统一致。如果还有足够多健康的模型副本，也可以用广播参数、CPU 检查点等基于冗余的方法快速恢复。

放置的三条经验。

  1. 给 actor 多分卡，可以缩短生成延迟；而生成是最耗时、又无法和其他模型并行的阶段，所以这样最划算。
  2. 当每个模型的计算都能把 GPU 用满时，在规模较小的集群上，全部共置最有效。
  3. 扩展到大集群（强扩展）时，把 actor 和 critic 放在不同的卡上，让它们在训练和准备阶段并行执行，吞吐更高。

资源复用。HybridFlow 让共置的模型以分时的方式共享 GPU 的计算。DNN 任务调度领域已经有不少更细粒度的 GPU 共享技术，主要用于满足单个任务的服务质量目标。虽然 ResourcePool 的实现也支持共置模型同时执行，但 HybridFlow 一般坚持顺序执行，以免争抢 GPU 资源或 OOM（§2.4）。在 RLHF 训练中做 GPU 共享和异构资源利用，要同时平衡计算负载和复杂的数据依赖；论文认为，研究面向 GPU 共享的细粒度自动映射算法，结合模型卸载和异构设备，是一个有前景的方向。

从对齐到推理。在用于对齐的 RLHF 里，奖励信号来自奖励模型。但 PPO、GRPO 这类算法也可以用在代码生成和数学推理等领域，这些任务里每个 prompt 往往有标准答案：代码可以跑测试用例判断对错，数学结果可以直接核对。于是奖励模型可以换成不是神经网络的奖励模块，比如执行代码的沙箱环境，或者核对数学答案的奖励函数。HybridFlow 可以把这些奖励模块包装成远程函数，在单进程脚本里编排它们的执行。

相关工作。论文把相关工作分成三类。第一类是 RL 框架：从面向小网络的通用 RL 系统，到专为大模型优化的 RLHF 系统。它们和近来的 RLHF 系统一样，用一堆多控制器程序拼成算法：建立多个长期运行的分布式程序，各组件靠写死的数据同步来协调执行顺序；它们都不支持 RLHF 所需的大模型训练、推理和生成。第二类是大模型训练与推理系统：数据并行（TorchDDP、Horovod）、带通信和显存优化的数据并行（ByteScheduler、DeepSpeed）、张量并行和流水线并行的训练系统，以及用连续批处理、分块 prefill 等技术加速生成的推理系统。它们全都采用多控制器写法以求计算高效。第三类是数据流系统：MapReduce、Spark、Dryad、Naiad 擅长分析类负载，但不支持动态任务图；Ray 把任务并行和 actor 编程模型统一在一张动态任务图里，被许多 RL 框架采用；谷歌闭源的 Pathways 面向 TPU，用异步分布式数据流让控制面并行执行，从而降低单控制器的调度开销，但它聚焦于单个模型的训练，需要对模型的每个子网络做复杂的编译。论文认为，HybridFlow 可以把 Pathways 当作子模块，用来实现数据流里各模型的计算。

结论。HybridFlow 是一个能灵活表示、高效执行多种 RLHF 算法的框架。它的混合编程模型把不同大模型的分布式计算封装成原语 API，并隐藏节点间数据重分片的复杂性，让用户几行代码就能搭出一个 RLHF 数据流；3D-HybridEngine 让 actor 的训练和生成都高效执行，并在两者之间做零冗余、低通信的参数重分片；映射算法优化了数据流中各模型的 GPU 分配和放置。在多种模型大小和集群规模下，它比当时最好的 RLHF 系统快 1.53–20.57 倍。

后来怎么样了

verl 成了 LLM RL 后训练最常用的开源框架之一。论文的代码以 verl 的名字开源（仓库创建于 2024-10-31，最初在 volcengine 组织下，2026 年 1 月迁到 verl-project 组织）。verl 的 README 写明它是本文的开源版本，由字节跳动 Seed 团队发起、社区维护；截至 2026-10-19，仓库有 23,924 个 star、4,772 个 fork，Apache-2.0 许可。它支持的训练后端从论文里的 Megatron-LM、FSDP 扩展到 FSDP2，生成后端除 vLLM 外还有 SGLang 和 HF Transformers；README 记载，借助 Megatron 后端的专家并行，可以训练 DeepSeek-671B、Qwen3-235B 这样的大型 MoE 模型。

论文 §9 的“从对齐到推理”成了主流。2025 年起，大模型 RL 的重心从“用奖励模型做对齐”转向“用可验证的规则奖励训练推理能力”。其中最常用的算法 GRPO（来自 DeepSeekMath）去掉了 critic：对每个 prompt 采样一组回答，用组内奖励的均值和标准差把每个回答的奖励标准化，作为它的优势。放到 HybridFlow 的数据流里，就是删掉 critic 的两个节点、让生成节点对每个 prompt 多采样几次、把奖励模型换成判对错的函数，正好是论文所说“改几行算法代码，复用全部分布式计算”的情形。verl 的 README 列出的算法包括 PPO、GRPO、GSPO、ReMax、REINFORCE++、RLOO、PRIME、DAPO、DrGRPO 等，还支持多轮工具调用和视觉语言模型的 RL。

它被用来训练了一批有名的推理模型和研究项目。据 verl 的 README：DAPO（2025 年 3 月）的训练完全基于 verl，在 Qwen2.5-32B 基座上做到 AIME 2024 50 分；字节跳动的 Seed-Thinking-v1.5 用 verl 训练；社区项目包括复现 DeepSeek-R1-Zero 的 TinyZero、SimpleRL-Zoo、做搜索增强推理的 Search-R1、Skywork-OR1 等。

论文 vs 今天的代码“3D-HybridEngine”这个名字和 README 里的描述还在，但具体实现随后端演进了：verl 文档里，actor 和 rollout（生成引擎）被合在一个“混合 worker”（ActorRolloutRefWorker）里共置，以便用 NCCL 快速传权重；FSDP 后端由一个 sharding manager（如 FSDPVLLMShardingManager）在 actor 与生成引擎之间重分片权重，文档也提到 FSDP 后端的重分片开销比 Megatron-LM 后端更高。想复现论文里的“微 DP 组”分组细节，应读 Megatron 后端相关的代码，而不是只看论文。

同步 RL 的短板，催生了异步 RL。本文的实验把所有回答固定为 1024 个 token。但在推理模型的 RL 里，回答长度差别极大，同步系统必须等一批里最长的回答写完才能开始训练，很多卡在等待中空转。AReaL（arXiv 2505.24298，作者来自清华大学交叉信息研究院、蚂蚁集团、香港科技大学）把生成和训练彻底解耦：生成 worker 不停地生成，训练 worker 每攒够一批数据就更新一次；权重更新时，生成 worker 会中断正在进行的生成、丢掉用旧权重算出的 KV 缓存、用新权重重算后接着写，因此一条回答的前后部分可能来自不同版本的策略。为了控制样本“过时”的程度，AReaL 用超参数 \(\eta\) 限制一个训练批里允许的最大版本差（\(\eta=0\) 就退化为同步 RL；论文中代码任务取 4、数学任务取 8），并采用把“行为策略”和“近端策略”分开的解耦 PPO 目标。AReaL 摘要报告，与同卡数的同步系统相比，端到端训练时间最多缩短 2.77 倍，最终效果持平或更好；它的同步对照组正是用 verl 训练的 DeepScaleR 和 DeepCoder，吞吐也是用最新的 verl 代码测的。verl 自己后来也加入了实验性的 one_step_off_policy（错开一步的异步）和 fully_async_policy（完全异步）模块。

共置 + 分时复用的思路也被别人采用。OpenRLHF 的文档里后来加入了 Hybrid Engine：把 actor、critic、reward、reference 和 vLLM 引擎共置在同一批卡上，生成时让训练引擎休眠，训练时让 vLLM 休眠，以分时方式复用显存，并把它列为显存允许时的推荐配置。

0 导读：这份报告解决什么问题

2025 年以来，大模型变强的一个主要途径是“想得更久”：推理模型先写几万 token 的思考过程再作答，智能体在一个任务里连续调用几百次工具，把每一步的结果都留在上下文里。两种做法都会让上下文变得很长。而标准注意力有两笔随上下文长度增长的开销：生成每个新 token 时，要和前面所有 token 打一次分（计算量与长度 \(L\) 成正比），还要把前面所有 token 的 KV 缓存存在显存里（存储量也与 \(L\) 成正比）。上下文到了 100 万 token，这两笔账都会压过模型本身的计算，成为推理成本的主体。

DeepSeek 在前几代模型里已经分别从两个方向压缩过这笔账：V2 / V3 的 MLA 把每个 token 存的 KV 压窄，V3.2 的 DSA 让每个 token 只读最相关的 2048 条 KV。V4 走了第三步：直接把 KV 序列本身变短。它的注意力层分两种，CSA 把每 4 个 token 压成 1 条 KV 再用 DSA 挑出少数几条细看，HCA 把每 128 个 token 压成 1 条然后全看；两种层交替堆叠，每层再配一个只看最近 128 个原始 token 的滑动窗口。加上 KV 的混合精度存储，报告估算在 100 万 token 的位置上，V4-Pro 生成一个 token 的计算量只有 V3.2 的 27%，KV 缓存只有 10%。

注意力之外，V4 在架构上还有两处改动：把残差连接换成 mHC（把残差流加宽成 4 路，并用双随机矩阵约束各路之间的混合，配套论文另发），以及用 Muon 优化器训练大部分参数。报告的另一半篇幅是系统工程：把 MoE 的通信和计算融合进一个内核的 MegaMoE、用 TileLang 写内核、逐位可复现的批不变与确定性内核、为 Muon / mHC / 压缩注意力改造的训练框架、为异构 KV 缓存设计的推理框架和磁盘 KV 缓存，以及后训练阶段的 FP4 量化感知训练和多教师在线蒸馏的基础设施。

报告发布了两个模型：V4-Pro（总参数 1.6T，每 token 激活 49B）和 V4-Flash（284B / 13B），都原生支持 100 万 token 上下文，预训练分别用了 33T 和 32T token。评测上，V4-Pro 的最高推理档（V4-Pro-Max）在多数基准上超过此前的开源模型，报告自评落后最强的闭源模型约 3–6 个月。

1 引言：测试时扩展被注意力的长度开销卡住

这一节要回答的问题：推理模型和智能体都依赖越来越长的上下文，为什么说这条路被注意力的效率卡住了？V4 在架构、基础设施和后训练上各改了什么？报告对自己的评测结果是怎么概括的？
先补一点背景：生成一个 token 要付的两笔账。

模型逐个生成 token 时（解码阶段），每一步的开销可以拆成两部分。第一部分与上下文长度无关：把这个 token 送过所有层的线性层和 MoE 专家，计算量约为“每 token 激活参数 × 2”次浮点运算（一次乘加算 2 次）。以 V3.2 为例，每 token 激活 37B 参数，这部分约 74 GFLOPs（推算）。第二部分随上下文长度 \(L\) 增长：注意力要把当前 token 和前面的 token 逐一打分、加权，还要从显存里读出这些 token 的 KV 缓存。

上下文短时，第一部分占大头；上下文长了，第二部分线性增长，迟早会超过第一部分。以 V3.2 为例，它的闪电索引器在每一层都要给前面每一个 token 打分（64 个头、每头 128 维），一个 token 在 \(L=10^6\) 时仅打分就要约 1.05 TFLOPs，是第一部分的 14 倍（推算，见 4.7 节）。KV 缓存同理：它在显存里一直占着，序列越长占得越多，能同时服务的请求就越少（KV 缓存为什么限制吞吐，见本站 vLLM 精读）。

报告开头的判断是：推理模型带来的“测试时扩展”（想得越久越准）和长周期的智能体任务，都需要超长上下文；而现有开源模型在超长序列上的效率问题，已经成了继续扩展的主要障碍。V4 的目标是让 100 万 token 的上下文成为常规配置，而不只是“能跑”。

和 V3 相比，V4 保留了 DeepSeekMoE 和多 token 预测（MTP），改动分三块：

  • 架构：CSA 与 HCA 交替的混合注意力（第 4 节）；mHC 替换普通残差连接（第 3 节）；Muon 优化器（第 5 节）。
  • 基础设施：一个把 MoE 的通信、计算和访存完全重叠的融合内核（第 6 节）；用 TileLang 写内核（第 7 节）；训练与推理逐位一致的批不变、确定性内核库（第 7 节）；训练框架里的张量级重计算、Muon 的混合 ZeRO、mHC 的低成本实现、压缩注意力的两阶段上下文并行（第 8 节）；推理框架里的异构 KV 缓存与磁盘 KV 存储（第 9 节）。
  • 后训练：对 MoE 专家权重和索引器的 QK 路径做 FP4 量化感知训练（第 13 节）。

报告还特别提到一个细节：V4 的路由专家权重用 FP4 存储，但在现有硬件上，FP4 × FP8 矩阵乘的峰值算力与 FP8 × FP8 相同，所以 FP4 目前省下的是显存和读取带宽，而不是计算；报告认为未来的硬件理论上可以让 FP4 × FP8 再快三分之一。这也是为什么报告的 FLOPs 一律按“等效 FP8 FLOPs”计。

评测结论（报告自己的概括，本站改写）：在知识类基准上，V4-Pro-Max 明显领先其他开源模型，但仍落后 Gemini-3.1-Pro；在推理类基准上，它超过 GPT-5.2 和 Gemini-3.0-Pro，略逊于 GPT-5.4 和 Gemini-3.1-Pro，报告据此说自己落后最前沿约 3–6 个月；智能体任务上与 Kimi-K2.6、GLM-5.1 持平，略逊于闭源前沿；100 万 token 的长上下文测试中超过 Gemini-3.1-Pro。V4-Flash 因为参数少，知识类明显弱于 Pro，但给足思考预算后推理类接近 Pro。

容易误读的一点：“27% 的计算量”只在长上下文时成立。V4-Pro 每 token 激活 49B 参数，比 V3.2 的 37B 多，所以在上下文很短时，它生成一个 token 的计算量反而比 V3.2 大，约为 1.3 倍（推算：98 GFLOPs 对 74 GFLOPs）。原文图 1 里两条曲线在横轴起点附近也相差不大，越往右差距才越大。V4 省的是“随长度增长的那部分”。

2 架构总览，以及从 V3 继承下来的部分

这一节要回答的问题：V4 的一个 Transformer 块长什么样？哪些部件直接沿用 V3，哪些做了小改动？两个模型的具体配置是多少？
先补一点背景：DeepSeekMoE 与 MTP。

MoE（混合专家）把前馈网络换成很多个小的“专家”网络，每个 token 只交给其中少数几个计算，于是总参数可以很大，而每个 token 的计算量只取决于被激活的那几个专家。DeepSeekMoE 的特点是专家切得很细（V4-Pro 每层 384 个路由专家），并且另设一个所有 token 都会经过的“共享专家”，用来承载通用知识。路由器给每个专家打一个亲和度分数，选分数最高的若干个。为了不让少数专家被挤爆，V3 不用传统的辅助损失，而是给每个专家的分数加一个随负载自动调节的偏置项（“无辅助损失的负载均衡”）。MTP（多 token 预测）在主模型之后接一个小模块，让每个位置额外预测再往后一个 token，既能增加训练信号，推理时也能当投机解码的草稿。这些在本站 DeepSeek-V3 精读的 2.1.2 节和 2.2 节有详细解释。

V4 仍是一个 Transformer：每个块先做一次注意力，再做一次 MoE 前馈。和 V3 相比，块内注意力换成了 CSA 或 HCA，块与块之间的残差连接换成了 mHC，MTP 的配置与 V3 完全相同。下图是本站根据报告图 2 和官方推理代码画的结构示意。

MoE 部分基本沿用 DeepSeekMoE，有四处小改动：

  • 亲和度的激活函数从 \(\operatorname{Sigmoid}(\cdot)\) 换成 \(\sqrt{\operatorname{Softplus}(\cdot)}\)。Softplus 是 \(\ln(1+e^{x})\)，恒为正、在大输入时近似线性；再开平方，大分数的增长被压缓，但不会像 sigmoid 那样在 1 附近饱和。报告没有解释为什么这样换，“不饱和、增长放缓”是本站的读法。
  • 负载均衡仍用无辅助损失的偏置项（偏置更新速度 0.001），另加一个权重很小（0.0001）的按序列均衡损失，只用来防止单条序列内部出现极端不均衡。
  • 去掉了“节点受限路由”。V3 规定每个 token 最多发往 4 个节点，以控制跨节点通信量；V4 取消了这个限制，转而重新设计并行策略来保持训练效率（第 6 节的 MegaMoE 是其中一部分）。
  • 前几层改用哈希路由的 MoE。V3 的前 3 层是普通的稠密前馈网络；V4 把它们换成 MoE，但这 3 层的专家不由路由器选，而是按输入 token 的 ID 查一张固定的哈希表决定（官方代码里是一张“token ID → 6 个专家编号”的表）。哈希路由来自 2021 年的 Hash Layers 工作。一个直观的理由是：最前面几层的表示几乎只取决于 token 本身，学出来的路由也不过是 token ID 的函数，不如直接固定，还能避免路由不稳定。这条理由是本站的推测，报告没有说明。

3 mHC：把残差流加宽成 4 路，再用双随机矩阵管住它

这一节要回答的问题：残差连接从 2016 年的 ResNet 起几乎没变过。字节跳动的超连接（Hyper-Connections，HC）把残差流加宽成多路、让各路之间可以学着混合，确实能提升模型质量，却在大规模训练中频繁出现数值不稳定。不稳定从哪里来？DeepSeek 的配套论文 mHC 用什么约束把它治好，又付出多少系统开销？V4 报告 §2.2 只简要介绍了 mHC，所以这一节把配套论文（arXiv 2512.24880）一起讲。
先补一点背景：残差连接与“恒等映射”。

普通 Transformer 的每个子层（注意力或前馈）都写成 \(x_{l+1}=x_l+\mathcal{F}_l(x_l)\)：子层只负责算一个“增量”，原来的输入原样加回去。把这个式子从第 \(l\) 层一路展开到第 \(L\) 层，得到 \(x_L=x_l+\sum_{i=l}^{L-1}\mathcal{F}_i(x_i)\)。第一项 \(x_l\) 没有经过任何变换就直接到达了深层，这叫恒等映射。它的好处有两个：前向时浅层的信号不会被一层层放大或缩小；反向时梯度也有一条“直通车道”，\(\partial x_L/\partial x_l\) 里永远含有一个单位矩阵，不会因为层数多而消失或爆炸。这是几百层的网络能稳定训练的根本原因。

再补一点背景：超连接（HC）在做什么。

HC 把残差流从一条 \(d\) 维向量扩成 \(n\) 条（V4 取 \(n=4\)），残差状态变成一个 \(4\times d\) 的矩阵 \(X_l\)。子层本身不变，输入输出仍是 \(d\) 维，所以需要三个小映射来衔接：

$$X_{l+1}=B_l X_l+C_l\,\mathcal{F}_l(A_l X_l)$$
  • \(A_l\)（\(1\times4\)）是读出：把 4 路按权重加成一路，作为子层的输入；
  • \(C_l\)（\(4\times1\)）是写回：把子层的输出按 4 个权重分别加到各路上；
  • \(B_l\)（\(4\times4\)）是路间混合：残差流在进入下一层之前，各路之间互相掺一点。

因为 \(n=4\) 远小于 \(d=7168\)，这三个映射几乎不增加计算量。HC 的意义在于：它把“残差流能携带多少信息”和“每层算多宽”解耦开，给模型多了一个可以扩展的维度。mHC 论文的消融实验显示，三个映射里贡献最大的是 \(B_l\)：单独打开它，损失就比普通残差低 0.022；三个全开低 0.027。

3.1 不稳定从哪里来：连乘

问题恰恰出在贡献最大的 \(B_l\) 上。把 HC 的式子像上面那样逐层展开，浅层信号到达深层时乘上的不再是单位矩阵，而是一串矩阵的连乘 \(B_{L-1}B_{L-2}\cdots B_l\)。如果 \(B_l\) 不受约束，每一层哪怕只把信号放大一点点，连乘几十层之后也会变成天文数字。举个数：假设每个子层让信号的总量放大 15%，那么经过 60 个子层（30 个块，每块注意力和前馈各一个），总放大倍数是 \(1.15^{60}\approx4400\)（推算）。缩小也是一样，每层缩小 15%，60 层后只剩约万分之二。

mHC 论文在一个 27B 的 MoE 模型上实测到了这种现象：它把“连乘矩阵每行之和的最大绝对值”（衡量前向信号最多被放大多少）和“每列之和的最大绝对值”（衡量反向梯度最多被放大多少）称为增益，HC 的增益峰值接近 3000；训练到约 12k 步时，HC 的损失突然上冲，同时梯度范数剧烈波动。

3.2 mHC 的约束：双随机矩阵

mHC 的做法是：不让 \(B_l\) 随便取值，而是把它限制在双随机矩阵的集合里——所有元素非负，每一行加起来等于 1，每一列加起来也等于 1：

$$B_l\in\mathcal{M}=\{M\in\mathbb{R}^{n\times n}\mid M\mathbf{1}_n=\mathbf{1}_n,\ \mathbf{1}_n^{\top}M=\mathbf{1}_n^{\top},\ M\geq0\}$$

这个集合在数学上叫 Birkhoff 多面体。它有三条性质，正好对症：

  • 不放大。双随机矩阵的谱范数不超过 1，也就是说，任何向量乘上它都不会变长。前向的信号和反向的梯度都不会被它放大。
  • 连乘之后仍然不放大。两个双随机矩阵相乘还是双随机矩阵（行和、列和都还是 1）。所以无论叠多少层，\(B_{L-1}\cdots B_l\) 始终是双随机的，上面那条指数增长的曲线被压成了一条水平线。
  • 只是“重新分配”。双随机矩阵恰好是若干个置换矩阵的加权平均（凸组合）。乘上它相当于把各路信号洗一洗牌再取平均：总量不变，只是在各路之间重新分配。

举个具体的例子。设 \(B\) 的对角线是 0.7、其余元素是 0.1（每行每列都是 \(0.7+3\times0.1=1\)），4 路残差某一维的值是 \((4,0,0,0)\)。乘一次得到 \((2.8,0.4,0.4,0.4)\)，总和仍是 4；再乘几次会越来越接近 \((1,1,1,1)\)。信号在各路之间被摊匀，但既没有凭空变大，也没有被吞掉。对比一下：如果把对角线换成 0.8、其余仍是 0.1，行和变成 1.1，乘 60 次总量就会放大 \(1.1^{60}\approx304\) 倍（推算）。

另外两个映射也加了约束：读出 \(A_l=\sigma(\tilde A_l)\)，取值在 0 到 1 之间；写回 \(C_l=2\sigma(\tilde C_l)\)，取值在 0 到 2 之间。两者都非负，是为了避免“一路加、一路减”互相抵消——如果读出权重是 \((1,-1,0,0)\)，两路里相同的信息就被减没了。

3.3 系数怎么算：动态生成，再投影到双随机矩阵

mHC 的三个映射不是固定参数，而是每个 token 根据自己当前的残差状态现算出来的（沿用 HC 的“动态 + 静态”做法）。以 V4-Pro 为例：先把 \(4\times7168\) 的残差状态拉平成 28,672 维并做 RMSNorm，再用三个线性投影分别得到 4 个、16 个、4 个原始数值（一共 24 个），每组乘一个初始化得很小的可学习门控 \(\alpha\)，再加一个与输入无关的可学习偏置 \(S\)：

$$\tilde A_l=\alpha_l^{\mathrm{pre}}\,(\hat X_l W_l^{\mathrm{pre}})+S_l^{\mathrm{pre}},\quad \tilde B_l=\alpha_l^{\mathrm{res}}\operatorname{Mat}(\hat X_l W_l^{\mathrm{res}})+S_l^{\mathrm{res}},\quad \tilde C_l=\alpha_l^{\mathrm{post}}\,(\hat X_l W_l^{\mathrm{post}})^{\top}+S_l^{\mathrm{post}}$$

其中 \(\hat X_l\) 是拉平并归一化后的残差状态。\(\tilde A_l\)、\(\tilde C_l\) 过 sigmoid 就完成了约束；\(\tilde B_l\) 要投影到双随机矩阵上，用的是 Sinkhorn-Knopp 迭代：先取指数让所有元素变正，然后交替地把每一列除以列和、把每一行除以行和，重复 \(t_{\max}=20\) 次。

用一个 \(2\times2\) 的例子看它怎么收敛（推算）。设取指数后得到 \(\begin{pmatrix}7.39&1\\1&1\end{pmatrix}\)。按列归一化得到 \(\begin{pmatrix}0.881&0.5\\0.119&0.5\end{pmatrix}\)，再按行归一化得到 \(\begin{pmatrix}0.638&0.362\\0.192&0.808\end{pmatrix}\)，此时列和是 0.83 和 1.17；再来一轮，列和变成 0.96 和 1.04，越来越接近 1。这个例子的极限是 \(\begin{pmatrix}0.731&0.269\\0.269&0.731\end{pmatrix}\)。迭代次数有限，所以得到的只是近似的双随机矩阵——这也是 mHC 实测的增益最大到 1.6 而不是严格等于 1 的原因。

论文 vs 官方代码
在官方推理代码（inference/model.py）里，每个块的注意力和 MoE 各有一套 mHC：一次矩阵乘把拉平的残差映射成 \((2+4)\times4=24\) 个系数，再由一个 TileLang 内核完成 sigmoid、\(2\sigma\) 和 20 次 Sinkhorn 迭代。第 7 节提到的“输出维度只有 24 的矩阵乘”指的就是这一步。网络最后，4 路残差用 sigmoid 权重合并成一路，再送进 RMSNorm 和预测头。

  • “双随机”只是近似成立。20 次 Sinkhorn 迭代后，单层的反向增益已经略偏离 1，连乘后最大约 1.6——远好于 HC 的 3000，但不是严格的 1。

4 混合注意力：CSA 与 HCA（全文的核心）

这一节要回答的问题：上下文到 100 万 token 时，注意力成了模型里最大的开销。V4 设计了两种注意力层：CSA 先把 KV 序列压到 1/4，再用 DSA 的办法只挑少数几条细看；HCA 把 KV 序列压到 1/128，然后全部看一遍。这两种层分别怎么计算？它们和 MLA、DSA 是什么关系？报告还加了一串“其他细节”（归一化、部分 RoPE、滑动窗口、注意力 sink），各自为了什么？最后，100 万 token 时省下的计算量和存储量具体是怎么来的？报告说细节以开源的推理代码为准，所以本节也对照了官方代码。

4.1 背景：DeepSeek 压缩注意力开销的三个方向

先补一点背景：解码一步，注意力在花什么。

生成第 \(t\) 个 token 时，每一层注意力都要做两件事：从显存里读出前面 \(t-1\) 个 token 的 key 和 value（KV 缓存），再用当前 token 的 query 和它们逐一打分、加权求和。所以有三个量决定开销：每条 KV 有多宽（每个 token 每层存多少个数），一共存了多少条，每一步要读、要算多少条。

DeepSeek 的前几代模型依次压缩了前两个之外的不同部分。V2 / V3 的 MLA 压的是宽度：它不为每个头分别存 key 和 value，而是每个 token 每层只存一个 512 维的潜向量加 64 维的位置编码部分，共 576 个数，推理时所有头都直接和这个潜向量打交道（详见 DeepSeek-V3 精读 2.1.1 节）。V3.2 的 DSA 压的是“每步读多少条”：一个很轻的闪电索引器先给前面所有 token 打分，主注意力只读分数最高的 2048 条（详见本站的 DeepSeek-V3.2 精读）。但 DSA 有两笔账没省：所有 \(L\) 条 KV 仍然全部存着；索引器仍然要给全部 \(L\) 个 token 打分，只是每次打分很便宜。更早的 NSA 用了“压缩、选择、滑动窗口”三个分支（见本站 NSA 精读），但它的选择分支读的是原始 token，KV 也是全量存储的。

4.2 CSA 第一步：每 4 个 token 压成 1 条，相邻两条有重叠

设一段序列的隐状态是 \(H\in\mathbb{R}^{n\times d}\)。CSA 先用两组投影，为每个 token 算出两份 KV 候选 \(C^a,C^b\) 和两份“压缩权重” \(Z^a,Z^b\)，它们都是 \(n\times c\) 的矩阵，\(c=512\) 是头维：

$$C^a=HW^{aKV},\quad C^b=HW^{bKV},\quad Z^a=HW^{aZ},\quad Z^b=HW^{bZ}$$

然后把每 \(m=4\) 个 token 合成一条。第 \(i\) 条压缩 KV 用到两段 token：本块的 4 个 token（第 \(4i\) 到 \(4i+3\) 个，取 \(a\) 组）和上一块的 4 个 token（第 \(4i-4\) 到 \(4i-1\) 个，取 \(b\) 组）。这 8 个 token 的权重 \(Z\) 先加上一个与“在块内第几个位置”有关的可学习偏置 \(B^a,B^b\)，再在 8 个位置之间做 softmax，最后加权求和：

$$[S^a_{4i:4i+3};\,S^b_{4i-4:4i-1}]=\operatorname{Softmax}_{\text{row}}\big([Z^a_{4i:4i+3}+B^a;\ Z^b_{4i-4:4i-1}+B^b]\big),\qquad C^{\text{Comp}}_i=\sum_{j=4i}^{4i+3}S^a_j\odot C^a_j+\sum_{j=4i-4}^{4i-1}S^b_j\odot C^b_j$$

有两点值得放慢读。第一，\(\odot\) 是逐元素相乘，softmax 是对 8 个位置、在每一个维度上分别做的。所以这不是简单的平均：512 个维度各自决定这 8 个 token 里谁的权重大，某个维度可以几乎只取最后一个 token，另一个维度可以把 8 个 token 平均。第二，相邻两条压缩 KV 用到的 token 有一半重叠（第 \(i\) 条用的上一块，正是第 \(i-1\) 条用的本块），但每 4 个 token 才产生一条新条目，所以 KV 序列的长度仍然是原来的 1/4。官方代码的注释说，重叠是为了让压缩块的边界更平滑：一个跨在边界上的短语，不会被硬生生切成两半。第 0 条没有“上一块”，就用 \(-\infty\) 的权重和 0 补齐。

4.3 CSA 第二步：闪电索引器只挑 top-k 条

压到 1/4 之后，100 万 token 的序列仍有 26 万条压缩 KV，每一步全部看一遍还是太贵。于是 CSA 在压缩条目上套用 DSA 的做法。索引器有自己的一套“压缩索引键” \(K^{\text{IComp}}\)（用同样结构的压缩器得到，每条 128 维）。对当前 token \(t\)，先把它的隐状态压成一个低维的查询潜向量 \(\mathbf c^Q_t\)（V4-Pro 为 1536 维，主注意力的查询也从它生成），再展开成 64 个索引头的查询，并由隐状态直接算出 64 个头的权重：

$$\mathbf c^Q_t=\mathbf h_tW^{DQ},\quad [\mathbf q^I_{t,1};\dots;\mathbf q^I_{t,64}]=\mathbf c^Q_tW^{IUQ},\quad [w^I_{t,1};\dots;w^I_{t,64}]=\mathbf h_tW^{w}$$
$$I_{t,s}=\sum_{h=1}^{64}w^I_{t,h}\cdot\operatorname{ReLU}\big(\mathbf q^I_{t,h}\cdot K^{\text{IComp}}_s\big),\qquad \mathcal C^{\text{SprsComp}}_t=\{C^{\text{Comp}}_s\mid I_{t,s}\in\operatorname{Top\text{-}k}(I_{t,:})\}$$

\(I_{t,s}\) 是当前 token 对第 \(s\) 个压缩块的“相关度分数”，只对已经完整结束的块计算（保证因果性）。ReLU 让每个头只贡献正的相关性，头权重 \(w\) 决定这个 token 更相信哪几个头。分数最高的 k 条进入主注意力：V4-Pro 取 1024 条，V4-Flash 取 512 条。一条压缩条目代表 4 个 token，所以 1024 条大致覆盖 4096 个原始 token 的范围（推算）。也正因为如此，当上下文短于 \(k\times4\)（Pro 为 4096、Flash 为 2048 个 token）时，所有压缩条目都会被选中，稀疏选择不丢任何信息。

和 V3.2 相比，索引器的扫描量少了很多。V3.2 每层都有索引器，每个 token 要扫全部 \(L\) 个原始 token；V4 只有 CSA 层有索引器，扫的是 \(L/4\) 条压缩键，而且用 FP4 计算。以 \(L=2^{20}\) 为例，V3.2 一层索引器约 17.2 GFLOPs，V4 一层 CSA 索引器约 4.3 GFLOPs；全模型合计，V3.2（61 层）约 1.05 TFLOPs，V4-Pro（30 个 CSA 层）约 0.13 TFLOPs（推算，一次乘加算 2 次运算，未区分精度）。

论文 vs 官方代码
报告只说索引器的 QK 路径用 FP4。官方推理代码里还有一步报告没提的处理：索引器的查询和压缩键在量化到 FP4 之前，先做一次 Hadamard 旋转。这和 QuaRot 的思路一样：用一个正交旋转把少数“离群”维度的能量摊到所有维度上，低比特量化的误差就小得多；因为旋转是正交的，查询和键同时旋转后内积不变。
报告没有交代的地方：V3.2 的索引器是用 KL 散度去拟合主注意力的分布来训练的（详见 V3.2 精读）。V4 报告只说在引入稀疏时“先用一个短阶段预热闪电索引器”，没有说明索引器的训练目标、预热多久，也没有给出 top-k 选择的召回率（只在第 13 节给出了“分数从 FP32 改成 BF16 后召回率保持 99.7%”这一个相对数字）。

4.4 核心注意力：所有头共用一条 KV，输出投影分组

先补一点背景：MHA、GQA、MQA 和 MLA 的“MQA 模式”。

标准多头注意力（MHA）里，每个头都有自己的 key 和 value。GQA 让几个头共用一份 KV，MQA 更进一步让所有头共用唯一一份 KV，存储随之减少。MLA 存的是一个潜向量，推理时可以把“从潜向量还原出各头 key / value”的矩阵吸收进查询和输出投影里，于是所有头直接对同一个 576 维的潜向量做注意力：这个潜向量同时扮演 key 和 value，形式上就是一个 KV 头的 MQA。V3.2 正是在这种“MQA 模式”下实现 DSA 的。

V4 直接把这种形式作为架构本身：每条压缩 KV 是一个 512 维向量，它同时充当所有查询头的 key 和 value（报告称为“共享 KV 的 MQA”）。查询由 \(\mathbf c^Q_t\) 展开成 \(n_h\) 个 512 维的头（Pro 128 个、Flash 64 个），每个头对选出的 k 条压缩 KV 加上 128 条窗口 KV 做一次标准的 softmax 注意力，得到 512 维的输出 \(\mathbf o_{t,i}\)。key 和 value 共用一份，比分别存储又省了一半（vLLM 博客把这一项单独算作 2 倍的节省）。

代价出在输出端。每个头输出 512 维，128 个头拼起来是 65,536 维，直接投影回 7168 维需要一个约 4.7 亿参数的矩阵（推算），每个 token 每层的计算量也随之增大。V4 的办法是分组输出投影：把 128 个头分成 \(g=16\) 组，每组 8 个头拼成 4096 维，先各自投影到 \(d_g=1024\) 维；16 组的结果拼成 16,384 维，再投影到 7168 维。这样参数量变成 \(16\times4096\times1024+16384\times7168\approx1.85\) 亿，约为直接投影的 39%（推算）。V4-Flash 对应为 8 组，参数从约 1.34 亿降到约 0.67 亿（推算）。

4.5 HCA：每 128 个 token 压成 1 条，不挑选，全部参与

HCA 的压缩方式和 CSA 类似，但更简单也更狠：只用一组投影 \(C=HW^{KV}\)、\(Z=HW^{Z}\)，每 \(m'=128\) 个 token 不重叠地合成一条，权重同样是“每个维度单独在 128 个位置上做 softmax”：

$$S_{128i:128i+127}=\operatorname{Softmax}_{\text{row}}\big(Z_{128i:128i+127}+B\big),\qquad C^{\text{Comp}}_i=\sum_{j=128i}^{128i+127}S_j\odot C_j$$

压完之后序列只剩 1/128：100 万 token 只有 8192 条。这个长度已经短到可以全部参与注意力，所以 HCA 不需要索引器，直接用共享 KV 的 MQA 对全部压缩条目加上 128 条窗口 KV 做稠密注意力，输出同样走分组投影。CSA 和 HCA 的分工因此很清楚：CSA 以 4 个 token 的粒度挑出少数几段细看，HCA 以 128 个 token 的粒度把全文粗看一遍，两种层交替堆叠。

4.6 四个“其他细节”各管什么

查询和 KV 的归一化。在核心注意力之前，CSA 和 HCA 都对每个查询头和那唯一的 KV 头各做一次 RMSNorm。注意力的打分是内积 \(\mathbf q\cdot\mathbf k\)，它的大小不超过两个向量长度的乘积；归一化把两者的长度都固定住，打分就不会因为向量越训越长而爆炸。这也是第 5 节里 V4 不需要 Muon 的 QK-Clip 的原因。

部分 RoPE，以及对输出的“反向 RoPE”。V4 只在查询和 KV 的最后 64 维上加旋转位置编码（RoPE，原理见本站 RoFormer 精读）。麻烦在于 KV 同时充当 value：第 \(j\) 条 KV 的最后 64 维已经按它自己的位置 \(p_j\) 旋转过，加权求和之后，输出里混着各条 KV 的绝对位置。设 \(R_p\) 表示按位置 \(p\) 旋转，输出的这 64 维是

$$\mathbf o_i^{\text{rope}}=\sum_j a_{ij}\,R_{p_j}\mathbf r_j\quad\xrightarrow{\ \text{再乘 }R_{-p_i}\ }\quad R_{-p_i}\,\mathbf o_i^{\text{rope}}=\sum_j a_{ij}\,R_{p_j-p_i}\mathbf r_j$$

V4 对每个输出头的最后 64 维再按“负的查询位置”旋转一次。由于旋转可以合并，\(R_{-p_i}R_{p_j}=R_{p_j-p_i}\)，每条 KV 对输出的贡献就只和它与查询的相对距离有关了，与 RoPE 的初衷一致。官方代码里这一步就是对输出调用一次“逆向”的旋转。

论文 vs 官方代码
配置文件显示，带压缩的层（CSA / HCA）使用 RoPE 底数 160,000 并配合 YaRN 外推（以 65,536 为原始长度、放大 16 倍，正好对应 1M 上下文）；只有滑动窗口的层使用底数 10,000、不做 YaRN。报告正文没有写这些数，复现时以代码为准。

滑动窗口分支。为了严格保证因果性，一个查询只能看到已经结束的压缩块，看不到自己所在的那个块里、排在它前面的 token；而在语言建模里，最近的几个 token 往往最重要。所以 CSA 和 HCA 每层都额外保留最近 \(n_{\text{win}}=128\) 个原始 token 的 KV（不压缩），和压缩条目一起参与核心注意力。这部分 KV 大小固定，不随上下文增长。

注意力 sink。每个头有一个可学习的标量 \(z'_h\)，它的指数被加到 softmax 的分母上：

$$s_{h,i,j}=\frac{\exp(z_{h,i,j})}{\sum_k\exp(z_{h,i,k})+\exp(z'_h)}$$

这样一个头对所有 KV 的权重之和可以小于 1，甚至接近 0，也就是说这个头可以“这一步什么都不看”。普通注意力的权重之和必须是 1，模型往往被迫把多余的注意力堆到第一个 token 上（所谓的 attention sink 现象）；而在 V4 里，第一个 token 不一定在窗口里，也不一定被索引器选中，所以显式地给一个“空位”更合理。后半句是本站的解读，报告只说明了做法。

4.8 结果的份量

  • 估算，不是实测。27% / 10% 是按结构估算的单 token 计算量和存储量（报告原文就称图 1 为“估算的”），不是延迟或吞吐。实际解码速度还取决于读权重和读 KV 的带宽、批大小、内核效率、预填充还是解码；报告全文没有给出任何端到端的服务吞吐或延迟数字。
  • 对照是什么。27% / 10% 的对照是 DeepSeek 自己的 V3.2（同一个团队、同一套算法），“2%”的对照是一个假想的 BF16、GQA 8 组配置，不是某个真实模型。独立的交叉核对来自 vLLM 团队：他们的博客按 BF16 估算，1M 上下文时 V4（61 层）每条序列 KV 约 9.62 GiB，而“61 层的 V3.2 式结构”约 83.9 GiB，相差 8.7 倍；实际部署用 FP8 注意力缓存和 FP4 索引缓存，还能再小约一半。
  • 压缩是有损的。CSA / HCA 改变了模型计算的内容，不像 PagedAttention 那样只改存放方式。它的质量代价只能从端到端评测里间接看出来（第 11、14 节的 LongBench-V2、MRCR、CorpusQA），报告没有给出“同样数据、同样规模下，CSA / HCA 对比稠密注意力或对比 DSA”的消融。

5 Muon 优化器

这一节要回答的问题：V4 的大部分参数改用 Muon 训练。Muon 和 AdamW 有什么不同？V4 的“混合 Newton–Schulz 迭代”是什么？为什么 V4 不需要 Kimi 用过的 QK-Clip？
先补一点背景：Muon 在做什么。

AdamW 对每个参数单独做自适应缩放，不关心参数是不是一个矩阵。Muon 专门处理矩阵参数：它先像 SGD 那样累积动量 \(M\)，然后把这个矩阵“正交化”——设 \(M=U\Sigma V^{\top}\) 是它的奇异值分解，更新方向取 \(UV^{\top}\)，也就是把所有奇异值都换成 1。直观地说，原始梯度往往被少数几个方向主导，正交化之后，每个方向都以同样的幅度更新，那些很少被激活、但同样重要的方向也能学到东西。月之暗面的 Moonlight 工作（“Muon is Scalable for LLM Training”）证明了它在大模型上可用，并补上了权重衰减和“按更新的 RMS 缩放”两个关键改动，详见本站的 Muon 精读。

精确的奇异值分解太贵，Muon 用 Newton–Schulz 迭代近似：先把矩阵除以它的 Frobenius 范数，保证所有奇异值不超过 1，然后反复做

$$M_k=aM_{k-1}+b\,(M_{k-1}M_{k-1}^{\top})M_{k-1}+c\,(M_{k-1}M_{k-1}^{\top})^2M_{k-1}$$

这个运算不改变奇异向量，只把每个奇异值 \(\sigma\) 变成 \(f(\sigma)=a\sigma+b\sigma^3+c\sigma^5\)。V4 用两组系数共迭代 10 次：前 8 次用 \((3.4445,-4.7750,2.0315)\)，后 2 次用 \((2,-1.5,0.5)\)。为什么要分两段，代入几个数就明白（推算）：第一组系数在 \(\sigma\) 很小时斜率是 3.4445，小奇异值每次被放大三倍多，所以收敛快；但 \(f(1)=3.4445-4.775+2.0315\approx0.70\)，1 并不是它的不动点，奇异值只会被赶进 1 附近的一个区间里来回跳。第二组系数满足 \(f(1)=2-1.5+0.5=1\)，而且 \(f'(1)=2-4.5+2.5=0\)，1 是一个“吸引力很强”的不动点，靠近 1 的值会被精确地拉到 1。先快后准，正是“混合”的含义。

报告的算法 1 把一步更新写成五行：算梯度 \(G_t\)；累积动量 \(M_t=\mu M_{t-1}+G_t\)；对 \(\mu M_t+G_t\)（Nesterov 技巧）做混合 Newton–Schulz 得到 \(O'_t\)；乘以 \(\sqrt{\max(n,m)}\cdot\gamma\) 调整更新的大小；带权重衰减更新参数 \(W_t=W_{t-1}(1-\eta\lambda)-\eta O_t\)。中间那个缩放因子的来历是：一个所有奇异值都为 1 的 \(n\times m\) 矩阵，它的元素均方根（RMS）是 \(1/\sqrt{\max(n,m)}\)（推算），乘上 \(\sqrt{\max(n,m)}\) 正好把 RMS 拉回 1，再乘 \(\gamma\)，更新的 RMS 就固定为 \(\gamma\)。V4 取 \(\gamma=0.18\)，目的是让 Muon 更新的幅度和 AdamW 差不多，从而可以直接沿用 AdamW 的学习率等超参数。

不是所有参数都用 Muon：词嵌入、预测头、mHC 的静态偏置和门控因子、所有 RMSNorm 的权重仍用 AdamW（\(\beta_1=0.9\)、\(\beta_2=0.95\)、\(\varepsilon=10^{-20}\)、权重衰减 0.1）。Muon 的动量取 0.95，权重衰减 0.1。

月之暗面的 Kimi 团队在用 Muon 训练大模型时遇到过注意力打分（logit）越训越大、最终爆掉的问题，为此提出了 QK-Clip（按头把过大的查询、键权重缩回去；V4 报告引用它时标注的是 Liu et al., 2025）。V4 不需要它，因为 4.6 节讲过，V4 在核心注意力前对查询和 KV 都做了 RMSNorm，打分的大小已经被归一化管住了。

读的时候要注意：报告说采用 Muon 是“因为收敛更快、训练更稳定”，但没有给出 V4 规模上 Muon 与 AdamW 的对比实验，这个结论来自前人的工作。第 8 节会讲到，Muon 需要完整的矩阵才能正交化，这给分布式训练带来了不小的工程麻烦。

6 MegaMoE：把专家并行的通信藏进计算

这一节要回答的问题：MoE 的专家分布在很多张卡上，每一层都要先把 token 发给专家、算完再收回来，跨节点通信很容易成为瓶颈。V4 的融合内核怎样让通信和计算同时进行？它比已有的重叠方案（如 Comet）细在哪里？报告给出的“计算 / 通信配比”公式说明了什么，对硬件设计又有什么建议？
先补一点背景：专家并行（EP）的四个阶段。

专家并行把一层的几百个专家分到几十张卡上，每张卡只放其中一部分。于是每个 MoE 层要经过四步：分发（dispatch），每张卡把自己手上的 token 按路由结果发到对应专家所在的卡，这是一次 all-to-all 通信；第一次矩阵乘（Linear-1，算 SwiGLU 的门控和上投影）；激活（SwiGLU，并把结果转成 FP8）；第二次矩阵乘（Linear-2，下投影）；最后合并（combine），把结果发回 token 原来所在的卡并按路由权重求和，又是一次 all-to-all。分发和合并受带宽限制，两次矩阵乘受算力限制。下面的小演示可以切到“All-to-All”一步步看数据怎么交换（DeepSeek-V3 的跨节点 all-to-all 见 V3 精读 3.2.2 节）。

报告的出发点是一个实测观察：在 V4 的一个 MoE 层里，通信的总时间少于计算的总时间。既然如此，只要把两者完全重叠，整层的耗时就由计算决定，互连带宽哪怕再低一些也不影响端到端性能。难点在于重叠的粒度。最朴素的做法是四步依次进行；Comet 等工作把分发和第一次矩阵乘重叠、把第二次矩阵乘和合并重叠，但两段之间仍有串行的部分。V4 的方案把专家切成若干“波次”（wave），每个波次只包含一小部分专家：某个波次的专家一旦收齐了自己的 token，就立刻开始计算，不必等其他专家。稳定运行时，当前波次的计算、下一波次的 token 传输、已完成专家的结果回传三件事同时进行，通信和计算在整层里都不间断。

6.1 计算 / 通信配比：带宽够用就行

报告给出了一个判断“通信能不能被完全藏住”的简单条件。设硬件的峰值算力为 \(C\)（FLOP/s），互连带宽为 \(B\)（Byte/s），一层要做的计算量为 \(V_{\text{comp}}\)、要传的字节数为 \(V_{\text{comm}}\)。通信能完全藏在计算后面，当且仅当传完数据的时间不超过算完的时间，即 \(V_{\text{comm}}/B\le V_{\text{comp}}/C\)，整理得

$$\frac{C}{B}\le\frac{V_{\text{comp}}}{V_{\text{comm}}}$$

对 V4-Pro，每一对“token–专家”的计算量是 \(6hd\)：SwiGLU 的门控、上投影、下投影三个 \(h\times d\) 的矩阵，每个乘加算 2 次运算（\(h=7168\) 是隐藏维度，\(d=3072\) 是专家的中间维度）。通信量是 \(3h\) 字节：分发用 FP8，每个数 1 字节，共 \(h\) 字节；合并用 BF16，共 \(2h\) 字节。两者相除，\(h\) 约掉了：

$$\frac{C}{B}\le\frac{6hd}{3h}=2d=6144\ \text{FLOPs/Byte}$$

也就是说，每 1 GB/s 的互连带宽可以藏住 6.1 TFLOP/s 的计算。举个例子（推算）：一张 FP8 稠密峰值约 2,000 TFLOP/s 的卡（H100 / H800 级别的规格值为 1,979），满负荷时每张卡需要约 320 GB/s 的 EP 带宽才能完全藏住通信；实际达到的算力低于峰值，需要的带宽也相应更低。V4-Flash 的专家更窄（\(d=2048\)），比值只有 4096，同样的算力需要约 480 GB/s，也就是说专家越窄，通信越难藏。报告的建议是：硬件只要把带宽做到这个平衡点就够了，超过之后，再多的硅面积投入带宽收益递减。

报告还给硬件厂商提了三条建议。功耗：极致的融合让计算、显存和网络同时满载，功耗墙会成为新的瓶颈，需要留出足够的功耗余量。通信原语：分发阶段 V4 采用“拉”的方式（每张卡主动去远端读激活），因为细粒度地“推”需要很快的跨卡通知，而现有硬件的通知延迟太高。激活函数：建议用不含指数和除法的简单逐元素激活替代 SwiGLU，因为矩阵乘之后的激活计算会拖住矩阵乘的流水线。

结果的份量：1.50–1.73 倍和 1.96 倍对比的是“强的非融合基线”，报告没有说明基线具体是什么实现、用的是哪款 GPU / NPU、多少张卡、EP 规模和批大小，也没有说明这是 MoE 层的加速还是端到端的加速。1.42 倍与 1.92 倍是按 V4-Flash 配置算出的理论值。好在内核本身开源了，这些数字可以被独立复核。

7 TileLang，以及逐位可复现的批不变、确定性内核

这一节要回答的问题：V4 的结构细节很多，如果都用 PyTorch 的小算子拼，会有几百个零碎的内核。DeepSeek 用 TileLang 写融合内核，解决了哪些实际问题？另一个设计目标是“预训练、后训练、推理三者逐位对齐”：同一个 token，不管和谁拼在一个批里、在哪个阶段算，结果的每一个比特都一样。为什么要这么苛刻，又是怎么做到的？

7.1 TileLang：用一种领域语言写内核

TileLang 是一种嵌在 Python 里、以“数据块”（tile）为单位描述 GPU 计算的领域专用语言，开发效率接近写 PyTorch，又能逐步做到手写 CUDA 级别的优化。V4 用它写的融合内核替换了绝大部分零碎算子，也用它快速试验各种注意力变体（第 3 节 mHC 的内核、第 13 节蒸馏用的 KL 内核都是 TileLang 写的）。报告讲了三处与 TileLang 社区合作做的改进：

  • 主机侧代码生成。GPU 越来越快，每次调用内核时 CPU 侧的固定开销（参数检查、形状校验，通常用 Python 写）就越显眼；解码阶段的很多内核本身只跑几十微秒，几十到上百微秒的 CPU 开销足以把 GPU 饿着。TileLang 在编译时把这些检查连同内核一起生成为主机代码（基于 TVM-FFI），报告实测每次调用的 CPU 校验开销从几十到几百微秒降到 1 微秒以下。
  • 用 SMT 求解器做整数分析。内核里大量的下标算术需要编译器证明某些性质（比如不越界、可以向量化）才能放心优化。TileLang 把整数表达式翻译给 Z3 求解器（无量词的非线性整数算术），在几秒的编译开销内解锁了向量化、屏障插入、代码化简等优化。
  • 数值精度默认从严。编译器默认关闭 fast-math；需要近似计算时必须显式调用 T.__exp 一类的算子；也提供严格符合 IEEE-754、可指定舍入方式的内建函数。还可以用布局标注把累加顺序钉死，从而与手写 CUDA 的参考实现逐位一致。

7.2 为什么同一个 token 换个批就会算出不同的结果

先补一点背景：浮点加法不满足结合律。

在有限精度下，\((a+b)+c\) 不一定等于 \(a+(b+c)\)。举个 FP32 的例子：\(10^8\) 附近相邻两个 FP32 数相差 8，所以 \((10^8+1)-10^8\) 的结果是 0（\(10^8+1\) 被舍入回 \(10^8\)），而 \((10^8-10^8)+1=1\)。GPU 内核为了跑得快，常常根据输入的大小选择不同的切分方式：解码注意力在批很小时把一条序列切成几段交给多个 SM 并行算再合并（split-KV），矩阵乘在批很小时沿求和维度切开再合并（split-K）。切法变了，加法的顺序就变了，结果的最低几位也跟着变。于是同一条请求，和 3 条请求拼批或和 30 条拼批，算出的概率可以不一样。Thinking Machines 的博客系统地分析过这个问题（见本站的 批不变性精读）。

对 DeepSeek 来说，逐位一致有三个用处：排查训练中的软硬件问题时可以精确复现；分析稳定性时可以排除噪声；更重要的是后训练——强化学习用推理引擎生成样本、再用训练框架计算同一批样本的概率，两边算出的概率如果不一致，就会给策略梯度引入偏差。V4 的目标是端到端地做到逐位批不变和确定性，而且性能开销很小。

注意力。为了批不变，不能用 split-KV。但不切分会遇到“波次量化”问题：GPU 的 SM 数是固定的，一条序列交给一个 SM 时，序列数不是 SM 数的整数倍，最后一个波次就只有少数 SM 在干活。V4 的办法是准备两个内核：第一个内核让一个 SM 处理一整条序列，用来跑满载的波次；第二个内核专门处理最后那个不满的波次，让多个 SM 合作算一条序列（借助线程块簇的分布式共享内存在 SM 之间交换数据），并精心安排计算路径，使它的累加顺序与第一个内核完全相同，从而结果逐位一致。

确定性（主要在训练的反向传播）。非确定性通常来自原子加法：多个线程往同一个地址累加，谁先谁后不固定。V4 处理了三个地方：稀疏注意力的反向原本用 atomicAdd 累加 KV 的梯度，改为每个 SM 写自己的缓冲区、最后按固定顺序求和；MoE 的反向里，多张卡的多个 SM 同时往接收方的同一个缓冲区写数据，写入位置的协商不确定，改为在每张卡内预处理 token 的顺序、并把不同卡的缓冲区隔离开；mHC 里那个输出维度只有 24 的矩阵乘（第 3 节），批很小时不得不用 split-K，改为把每一段的部分和分别写出、再用一个确定性的归约内核相加。

8 训练框架：为 Muon、mHC 和压缩注意力做的改造

这一节要回答的问题：V4 的训练框架建立在 V3 的基础上（DualPipe、专家并行、FP8 训练），但三个新部件各自和原有框架有冲突：Muon 需要完整的矩阵，和 ZeRO 的切分冲突；mHC 让激活和流水线通信都变成 4 倍；压缩注意力的“每 4 个 token 一块”会跨过上下文并行的切分边界。报告分别怎么处理？另外，报告还做了一个更通用的改进：张量级别的激活重计算。

8.1 Muon 与 ZeRO 的冲突

先补一点背景：ZeRO 在切什么。

数据并行时，每张卡都要保存一份优化器状态（AdamW 的一阶、二阶动量等），非常占显存。ZeRO 把这些状态切成很多份，每张卡只保存并更新其中一份；梯度先用 reduce-scatter 汇总并按份分发，每张卡更新完自己那份参数，再用 all-gather 拼回完整参数（详见本站 ZeRO 精读）。AdamW 是逐元素的，一个参数矩阵可以从任意位置切开分给不同的卡。Muon 不行：Newton–Schulz 迭代要对整个矩阵做矩阵乘，切开就算不了。

V4 的“混合 ZeRO 分桶”分两类参数处理。稠密参数（注意力等）：限制 ZeRO 的最大并行度，用背包算法把一个个完整的矩阵分给各张卡，使每张卡的负担大致均衡；各卡的桶补齐到最大桶的大小，以便高效地做 reduce-scatter。在 DeepSeek 的设置里每张卡最多管 5 个矩阵，补齐带来的显存开销通常低于 10%。数据并行的规模超过这个上限时，多出来的数据并行组冗余地重复计算 Muon 更新，用一点计算换取更小的桶内存。MoE 参数：每个专家的矩阵本来就彼此独立，先把所有层所有专家的下投影矩阵拉平排成一列，再接上投影和门控矩阵，补齐到能被卡数整除，并保证不会把任何一个矩阵切开；专家足够多，所以不限并行度，补齐开销也可忽略。

还有两个细节。同一张卡上形状相同的相邻参数会自动合并，批量地做 Newton–Schulz 迭代，提高硬件利用率。另外，DeepSeek 观察到 Newton–Schulz 用 BF16 矩阵乘也是稳定的，于是把数据并行之间同步的 MoE 梯度用随机舍入量化到 BF16，通信量减半。为了避免低精度加法累积误差，他们没有用常规的环形或树形 reduce-scatter（梯度每经过一跳都要在 BF16 下加一次，误差随跳数累积），而是先用一次 all-to-all 把各卡的局部梯度交换到位，再由每张卡在 FP32 下一次性求和。

8.2 mHC 的代价控制

4 路残差流让激活显存和流水线阶段之间的通信量都增加了。V4 的做法与 mHC 论文一致：为训练和推理分别写融合内核；有选择地做重计算，层与层之间的大部分隐状态和所有归一化后的层输入都在反向时重算，但不重算计算密集的操作；调整 DualPipe 的 1F1B 重叠方式，容纳多出来的流水线通信，并让 mHC 的部分操作并发执行。最终，mHC 的额外墙钟时间只占重叠后的 1F1B 流水线阶段的 6.7%。

8.3 压缩注意力的上下文并行

上下文并行（CP）把一条长序列沿长度方向切开，每张卡负责连续的 \(s\) 个 token。压缩注意力在这里遇到两个麻烦。第一，训练样本是把多个文档拼接起来的，每个文档从自己的开头起按 \(m\) 个一组压缩，文档末尾不足 \(m\) 个的 token 被丢弃，所以每张卡压出的条目数通常少于 \(s/m\)，而且各卡不一样。第二，一个压缩块需要连续的 \(m\) 个 token，它可能正好跨在两张卡的边界上。

V4 用两阶段通信解决。第一阶段，第 \(i\) 张卡把自己最后 \(m\) 个未压缩的 KV 发给第 \(i+1\) 张卡；后者把收到的和自己的 \(s\) 个 KV 放在一起压缩，固定输出 \(s/m+1\) 条（不足的用填充条目补齐）。第二阶段，所有卡做一次 all-gather，再用一个融合的“选择并填充”算子把它们整理成总长 \(\text{cp\_size}\cdot s/m\) 的完整压缩序列，填充条目统一放在末尾。之后，HCA 和 CSA 索引器能看到哪些压缩条目，可以按规则预先算出；CSA 的稀疏注意力则由 top-k 选择器直接给出下标。

8.4 张量级的激活重计算

激活重计算（checkpointing）用计算换显存：前向时不保存某些中间结果，反向需要时再算一遍。常规实现以整个模块为单位决定“存还是重算”，粒度太粗，往往不是最优的取舍；手写整层的前向和反向可以做到细粒度控制，但失去了自动微分的便利，开发成本很高。V4 在自动微分框架里加了张量级的重计算：开发者只写前向，在想要重算的张量上做标注即可。框架用 TorchFX 追踪完整的计算图，为每个被标注的张量反向找出重算它所需的最小子图，把这段“重算图”插到对应的梯度计算之前。实现上，重算时直接释放原张量的显存、复用重算结果的存储指针，不做任何显存拷贝，所以与手写实现相比没有额外开销；由于追踪时模型是真实执行的，框架还能看到每个张量的底层存储，自动对共享存储的张量（比如 reshape 前后的输入和输出）去重，开发者不必操心这些底层细节。

读的时候要注意：这一节的改进都没有给出单独的性能数字，除了 mHC 的 6.7% 与 Muon 分桶“通常低于 10%”的补齐开销。报告也没有公开训练集群的规模、GPU 型号、并行度配置和总 GPU 时数——V3 报告曾经公开过这些（278.8 万 H800 GPU 小时），V4 没有。

9 推理框架：异构的 KV 缓存与磁盘 KV

这一节要回答的问题：V4 的推理框架大体沿用 V3，主要改动在 KV 缓存的管理。混合注意力让不同层的 KV 大小、更新方式和淘汰策略都不一样，PagedAttention 那套“所有层统一分块”的假设不再成立。V4 怎么组织这些缓存？为了让共享前缀的请求不必重复预填充，V4 把 KV 存到磁盘上，其中占大头的滑动窗口 KV 又有三种存法，各自的取舍是什么？
先补一点背景：PagedAttention 与前缀缓存。

vLLM 的 PagedAttention 把 KV 缓存切成固定大小的块，每个请求用一张块表记录自己的块在哪里，按需分配，几乎没有碎片；块是共享的单位，两个请求开头相同的部分可以共用同一批块，这就是前缀缓存（详见本站 vLLM 精读 和 SGLang 精读）。这套设计默认每一层的 KV 结构相同、每个 token 在每一层占同样多的空间。把前缀的 KV 进一步放到 CPU 内存或 SSD 上、需要时再取回，就是 KV 分层存储（见本站 LMCache 精读 与 Mooncake 精读）。

V4 的一个请求在显存里有好几种性质不同的 KV：CSA 层的压缩 KV（每 4 个 token 一条）和索引键（维度不同）；HCA 层的压缩 KV（每 128 个 token 一条）；每层的滑动窗口 KV（固定 128 条，旧的不断被淘汰）；还有压缩分支里“还没凑满一块”的尾部 token，它们和对应的隐状态必须暂存，等凑满了才能压缩。报告指出，把所有层统一纳入 PagedAttention 框架有两个障碍：一是缓存策略各不相同（例如滑动窗口的淘汰规则），二是高性能注意力内核对数据对齐有硬性要求。

V4 的方案把缓存分成两部分。状态缓存：报告把滑动窗口和未压缩的尾部 token 看成一种“状态空间模型”的状态——它只取决于当前位置，大小固定，与上下文长度无关。所以 V4 预先分配一个固定大小的状态缓存池，给每个请求分一个固定大小的块，块里一段存最近 128 个 token 的窗口 KV，另一段存 CSA / HCA 还没压缩的尾部状态。经典 KV 缓存：存 CSA 和 HCA 的压缩条目，每个请求按需分配多个块。为了让同一个块对两种层都整齐，每块覆盖的原始 token 数取两种压缩率的最小公倍数 \(\operatorname{lcm}(m,m')=\operatorname{lcm}(4,128)=128\) 的整数倍：覆盖 128 个原始 token 的块，正好装 32 条 CSA 条目和 1 条 HCA 条目。报告还说，这个布局是和稀疏注意力内核一起设计的，例如把块补齐到缓存行对齐可以提高性能，而稀疏内核能让不同层的块装不同数量的条目而不掉性能。

9.1 磁盘 KV 缓存：三种存滑动窗口的方法

在线服务里，大量请求共享相同的前缀（系统提示词、多轮对话的历史、智能体反复读取的同一批文件）。V4 把 KV 存到磁盘上，命中前缀的请求直接读回，不必重新预填充。CSA 和 HCA 的压缩条目很小，全部落盘：命中时读回前缀对应的条目，直到最后一个完整的压缩块；最后那个不完整块里的 token 需要重算，因为未压缩的 KV 没有存。

麻烦的是滑动窗口的 KV：它不压缩，而且每一层都有。报告说它的总量大约是压缩条目的 8 倍。可以这样核对（推算）：如果每个 token 的窗口 KV 都存下来，V4-Pro 每个 token 要存 61 层 × 576 字节 ≈ 35 KB，而压缩的主 KV 每个 token 约 4.4 KB，比值约 8。为此 V4 实现了三种策略：

读的时候要注意：“磁盘 KV 缓存”能成立，前提是压缩后的 KV 足够小：V3 时代每个 token 几十 KB 的 KV，存盘和读回的带宽代价都高得多。V4 的压缩注意力和这套存储设计是互相成全的。API 价格里“缓存命中”和“未命中”的差价（第 16 节）也与此有关，但价格是商业决定，不能直接当成本看。

10.1 数据

预训练语料在 V3 的基础上扩充到 32T token 以上，报告列了几个方向：过滤掉网页里批量自动生成和模板化的内容，以降低“模型吃自己生成的数据而退化”（模型崩塌）的风险；数学和代码仍是核心，中期训练阶段加入了智能体相关的数据来增强编程能力；多语言语料更大，以覆盖不同文化里的长尾知识；特别重视长文档，优先收集科研论文、技术报告等有学术价值的材料。预处理基本沿用 V3：分词器在 V3 的基础上加了几个用于构造上下文的特殊 token，词表仍约 128K（配置文件里是 129,280）；沿用 V3 的 token 切分策略和中间填空（FIM）训练；参考 Ding 等人的做法把不同来源的文档拼接成训练序列，尽量少截断样本。和 V3 不同的是，V4 预训练时使用样本级的注意力掩码：拼在同一条序列里的不同文档互相看不见，每个 token 只能注意到自己所在文档里前面的 token。

10.3 损失尖峰：预判路由与 SwiGLU 截断

报告坦承，训练万亿参数的 MoE 时遇到了明显的不稳定：回滚到之前的检查点可以暂时恢复，但尖峰会反复出现。他们观察到，尖峰总是和 MoE 层里的离群值（数值异常大的激活）同时出现，而路由机制本身似乎在放大这些离群值。一个可能的恶性循环是：某个异常激活被路由到某个专家，这个专家的参数随之被大幅更新，下一步又产生更大的异常激活、继续被同样路由。报告从两个方向下手：打断路由造成的循环，以及直接压住异常值。

预判路由（Anticipatory Routing）。他们发现，把骨干网络和路由网络的同步更新“错开”能显著提高稳定性：第 \(t\) 步用当前参数 \(\theta_t\) 计算特征，但路由选哪些专家，用的是 \(\Delta t\) 步之前的旧参数 \(\theta_{t-\Delta t}\) 算出的结果。为了不把模型参数加载两遍，他们在第 \(t-\Delta t\) 步就提前取出第 \(t\) 步要用的数据，用当时的参数“预先”算好路由下标缓存起来，到第 \(t\) 步直接用——这就是名字里“预判”的来历。预先算路由需要对数据额外做一次前向，经过流水线编排和与专家并行通信的重叠，额外的墙钟时间约为 20%。再加上一个自动检测机制：只在出现损失尖峰时触发一次短暂回滚并开启预判路由，运行一段时间后切回正常训练。这样，整体的额外开销可以忽略，也不影响模型效果。

SwiGLU 截断。SwiGLU 的输出是 \(\operatorname{SiLU}(\text{门控})\times\text{线性分量}\)，两个都随输入线性增长的量相乘，输入里一个大值会被放大成平方级的大值。V4 在两个模型的整个训练过程中，把线性分量截断在 \([-10,10]\)，把门控分量的上限截在 10，报告说这有效地消除了离群值，且不损害性能。官方推理代码里的 swiglu_limit = 10 也是这个设置，说明截断是模型定义的一部分，推理时同样要做。

读的时候要注意：报告明确说这两种办法“为什么有效还没有完整的理论解释”，在结论里也把它们列为待研究的问题。报告没有给出 \(\Delta t\) 取多少、整个训练中预判路由被触发了多少次，也没有给出不用这两种办法时的对照曲线。

12.1 专家训练与三档推理强度

每个领域的专家沿用 V3.2 的流程：先在高质量的领域数据上做监督微调，再用 GRPO 做强化学习，奖励由针对该领域成功标准设计的奖励模型给出，超参数与之前的 R1、V3.2 基本一致。（GRPO 对同一个问题采样一组回答，用组内的相对好坏作为优势值，省掉了单独的价值网络。）

推理任务的表现很大程度上取决于“花了多少计算”。V4 因此针对不同推理强度分别训练专家：在强化学习中对每一档使用不同的长度惩罚和上下文窗口，使它们产生长短不同的思考过程。两个模型都支持三档：

12.2 生成式奖励模型

容易验证的任务（数学有标准答案、代码有测试用例）可以用规则或测试直接打分；难以验证的任务（写作、开放问答）传统上要靠 RLHF：先用大量人工标注训练一个输出标量分数的奖励模型。V4 不再用这种标量奖励模型，而是为难验证的任务整理了带评分细则（rubric）的强化学习数据，用一个生成式奖励模型（GRM）来评判策略生成的轨迹——它像一个会写评语的裁判，先推理再打分。关键在于，这个裁判就是正在训练的模型本身，强化学习同时优化它“答题”和“判卷”两种能力。报告认为这样模型自身的推理能力会融进评判过程，评分更稳健，而且只需要少量多样化的人工标注。

12.3 工具调用格式、跨轮保留思考与 Quick Instruction

工具调用格式。V4 引入了一个新的特殊 token |DSML|，工具调用改用 XML 风格的格式：每个参数单独一个标签，并用 string="true|false" 标明它是原样的字符串还是 JSON 值。报告说 XML 格式能减少转义失败、降低工具调用出错率。原因不难理解：如果参数是一段代码，放进 JSON 字符串里就要把每个引号、换行、反斜杠都正确转义，模型很容易漏掉一个；放在 XML 标签之间则可以原样书写。

跨轮保留思考过程。V3.2 的做法是：在工具调用的来回之间保留思考过程，但用户发来新消息时把之前的思考全部丢掉。这在复杂的智能体任务里很浪费：每一轮新的用户消息都会清空积累的推理，模型只好从头重建对问题的理解。V4 借助 1M 的上下文改进了这一点：在有工具调用的场景里，所有轮次的思考过程都完整保留，包括跨越用户消息的边界；在普通对话里保持原来的策略，新用户消息到来时丢弃之前的思考，让上下文保持简洁。

12.4 多教师在线策略蒸馏

先补一点背景：正向 KL、反向 KL 与在线策略蒸馏。

蒸馏是让学生模型 \(\pi_\theta\) 的输出分布去贴近教师 \(\pi_E\)。用 KL 散度衡量差距时有两个方向。正向 KL \(D_{\mathrm{KL}}(\pi_E\|\pi_\theta)\) 在教师给出的样本上计算，惩罚“教师认为可能、学生认为不可能”的地方，学生会努力覆盖教师的所有可能性。反向 KL \(D_{\mathrm{KL}}(\pi_\theta\|\pi_E)\) 在学生自己的样本上计算，惩罚“学生认为可能、教师认为不可能”的地方，学生会集中到教师认可的那些回答上，不去生成教师不认可的东西。在线策略（on-policy）指训练数据由学生当前的策略自己生成：学生先答，教师再在学生走过的每一个位置上给出“这里应该怎么接”的分布。这样学生是在自己真实会遇到的状态上被纠正的，避免了“只在教师的完美轨迹上学、一旦自己走偏就不知所措”的问题。Thinking Machines 2025 年的博客把这种做法推广开来。

V4 的目标函数是多个教师的反向 KL 的加权和：

$$\mathcal L_{\text{OPD}}(\theta)=\sum_{i=1}^{N}w_i\cdot D_{\mathrm{KL}}\big(\pi_\theta\,\|\,\pi_{E_i}\big)$$

\(w_i\) 是每个教师的权重，通常按教师的重要性确定。学生在数学题上自然会主要向数学专家看齐，在编程题上向代码专家看齐。报告认为，这种在“输出分布”层面的合并，比直接平均几个模型的权重、或者把各领域混在一起做强化学习，更能避免能力互相拖累。这个阶段用了十几个覆盖不同领域的教师。

还有一个实现上的选择。以往的工作通常把全词表的 KL 简化成“只看学生采样出的那个 token”：把 \(\log\frac{\pi_{E_i}(y_t\mid x,y_{\lt t})}{\pi_\theta(y_t\mid x,y_{\lt t})}\)（停止梯度）当作这个位置的优势值，直接套用强化学习框架。这样省资源，但每个位置只用一个样本去估计整个分布的差距，梯度的方差很大，训练常常不稳定。V4 改用全词表的 logit 蒸馏：在每个位置，用学生和教师在整个词表（约 12.9 万个 token）上的完整分布精确计算 KL。这让梯度估计稳定得多，也更忠实地传递了教师的知识，代价是工程上要处理海量的教师 logits，这正是下一节要讲的。

读的时候要注意：报告没有给出“混合强化学习”与“多教师蒸馏”的对比实验，也没有列出各教师的权重和数量的确切值（只说超过 10 个）。生成式奖励模型“只需要少量人工标注”也没有给出标注规模。

13 后训练基础设施：FP4 量化感知训练、教师调度与可抢占的 rollout

这一节要回答的问题：V4 发布的权重里，专家参数是 FP4 的。它是怎么在不损失精度的前提下训练出来的？为什么报告说 FP4 到 FP8 的反量化是“无损”的？十几个万亿参数级的教师、十几万词表的 logits，怎样塞进训练？集群里任务随时可能被抢占，为什么“被打断的样本重新生成一遍”在数学上是错的？

13.1 FP4 量化感知训练

先补一点背景：FP4、MXFP4 与 FP8 的块缩放。

FP4（E2M1）只有 4 位：1 位符号、2 位指数、1 位尾数，能表示的数只有 \(0,\pm0.5,\pm1,\pm1.5,\pm2,\pm3,\pm4,\pm6\)。这么少的取值必须配合缩放因子使用：MXFP4 规定每 32 个相邻的数共用一个缩放因子，而且这个因子只能是 2 的整数次幂（E8M0 格式）。FP8（E4M3）有 3 位尾数和 4 位指数，最大约 448；V3 训练时对权重按 \(128\times128\) 的块共用一个缩放因子。FP8 格式的细节见本站 FP8 格式精读，FP4 训练见 NVFP4 精读。

量化感知训练（QAT）是在训练时就让前向计算使用量化后的权重，让模型提前适应量化带来的误差；优化器手里仍保留一份高精度的“主权重”，反向传播时把量化操作当作恒等函数，梯度直接传给主权重（直通估计器，STE）。

V4 在后训练阶段（包括教师模型和参考模型）对两处做了 FP4（MXFP4）量化感知训练：一是 MoE 专家权重，它们是显存占用的大头（第 2 节算过，超过 95% 的参数在路由专家里）；二是 CSA 索引器的 QK 路径，索引器的查询和键在缓存、读取、相乘时全部用 FP4，以加速长上下文下的打分。此外，索引分数从 FP32 改存 BF16，使 top-k 选择器提速 2 倍，KV 条目的召回率保持在 99.7%。

专家权重的训练流程是：优化器维护的 FP32 主权重先量化成 FP4（每 \(1\times32\) 一个缩放因子），再反量化成 FP8（每 \(128\times128\) 一个缩放因子）参与计算。报告强调这一步反量化是无损的，原因在于格式本身：一个 FP4 数乘以它的 2 的幂缩放因子，只有 1 位有效的尾数，而 FP8 有 3 位尾数，表示它绰绰有余；唯一的问题是指数范围——一个 \(128\times128\) 的 FP8 块里有 512 个 FP4 子块，它们各自的缩放因子可能相差很多个 2 的幂，FP8 只有一个共同的缩放因子，必须用自己的指数位把这些差别都吸收掉。只要块内最大和最小子块缩放因子之比不超过某个阈值，就一个比特都不会丢。报告没有给出阈值，只说已经验证当前的权重满足条件。按 E4M3 的取值范围粗算，这个比值大约可以到 \(2^{14}\)（推算：把共同缩放因子取为最大子块因子的 1/64，最大值 \(6\times64=384\) 不超过 448，最小的非零值要不低于 E4M3 的最小次正规数 \(2^{-9}\)）。

这样做的好处是整个量化感知训练可以原封不动地复用已有的 FP8 训练框架。而在推理和强化学习的 rollout 阶段（不需要反向传播），直接使用真正的 FP4 权重，而不是“模拟量化”：一方面采样时模型的行为与线上部署完全一致，另一方面读取的权重字节数减半，解码这种受带宽限制的计算能真正提速，显存占用也明显下降。索引器的 QK 路径做了同样的处理。

13.2 全词表蒸馏的教师调度

第 12 节说过，V4 要对十几个教师做全词表的蒸馏，每个教师都可能有上万亿参数。报告的处理分几步。教师的权重放在集中的分布式存储里，教师前向时按需加载，并像 ZeRO 那样分片，以缓解 I/O 和内存压力。最大的麻烦是 logits：词表超过 10 万，把所有教师在所有位置上的 logits 都算出来存着，即使写到磁盘上也存不下。V4 只缓存教师最后一层的隐状态，训练时取回来，现场过一遍对应教师的预测头重建出完整的 logits。以 V4-Pro 大小的教师为例，每个位置存 7168 个数而不是 129,280 个，体积约为 1/18（推算），而重算预测头的开销可以忽略。为了不让各个教师的预测头同时占着显存，数据分发时按教师编号给样本排序，保证每个小批次里每个教师的预测头只加载一次，任何时刻显存里最多只有一个。所有参数和隐状态的加载、卸载都在后台异步进行，不阻塞计算。最后，教师与学生 logits 之间的精确 KL 用一个专门的 TileLang 内核计算，既快又减少了动态显存分配。

13.3 可抢占、可容错的 rollout 服务

DeepSeek 的 GPU 集群有一个全局的抢占式调度器：高优先级任务来了，任何正在运行的任务都可能被随时打断；大集群里硬件故障也很常见。所以 RL 和蒸馏用的 rollout 服务必须能被打断、能恢复。V4 给每个生成请求维护一份以 token 为粒度的预写日志（WAL）：每生成一个 token，就立刻追加到这个请求的日志里。被抢占时，暂停推理引擎并保存未完成请求的 KV 缓存，恢复时用日志和保存的 KV 接着解码；即使发生致命的硬件错误，也可以用日志里已经生成的 token 重新预填充，恢复出 KV 缓存。

报告特别指出，“把没生成完的请求从头重新生成一遍”在数学上是错的，因为会引入长度偏差。道理可以用一个例子说清楚：设一批里有短回答（1000 个 token）和长回答（30,000 个 token），中断在时间上随机发生，那么一个长回答在生成过程中被打断的概率大约是短回答的 30 倍。如果被打断的请求都丢掉重来，重新采样时模型又会以一定概率生成长回答、再次面临更高的被打断概率……最终“活下来”交给训练的样本里，短回答被系统性地多算了，策略就会被推向越写越短。WAL 的做法是从断点接着生成，每个样本的分布不受中断影响。报告还提到另一种正确的做法：如果推理栈是批不变且确定的（第 7 节），用同一个随机种子重新生成，就能精确重放出被打断前的那段内容；但它要把已生成的部分重新解码一遍，远不如 WAL 高效。

13.4 百万 token 的 RL，以及智能体沙箱

为了在百万 token 的序列上做 RL 和蒸馏，V4 把 rollout 数据拆成轻量的元数据和沉重的逐 token 字段。分发数据时先加载全部元数据，做全局打乱和打包布局的计算；逐 token 字段通过共享内存的数据加载器读取，消除同一台机器上的重复拷贝，并在一个小批次用完后立即释放，大幅减轻 CPU 和 GPU 的内存压力。设备上同时放几个小批次，则根据负载动态决定，在计算吞吐和 I/O 重叠之间取得平衡。

智能体任务需要大量可执行环境，DeepSeek 为此建了一个生产级的沙箱平台 DSec（DeepSeek Elastic Compute）：由 Rust 写的三个组件（API 网关、每台主机上的代理、集群监控）组成，构建在 DeepSeek 自研的 3FS 分布式文件系统之上，单个集群可以同时管理几十万个沙箱实例。它的四个设计点分别对应四个观察：一套 Python SDK 背后有四种执行底座（预热好的函数调用容器池、兼容 Docker 的容器、基于 Firecracker 的 microVM、基于 QEMU 的完整虚拟机），切换只需改一个参数；镜像分层存放在 3FS 上、按需加载，元数据在本地、数据块用到时才取，microVM 的写入落在本地的写时复制层，快照可以串联，恢复只要毫秒级；通过消除虚拟化环境里重复的页缓存、做内存回收以安全超卖、减少容器运行时里的自旋锁竞争，提高每台主机能塞下的沙箱数；每个沙箱维护一份全局有序的轨迹日志，记录每条命令和结果，训练任务被抢占后恢复时直接重放已完成命令的缓存结果（既快，又避免重复执行非幂等操作），也用于追溯来源和确定性重放。

读的时候要注意：“FP4 到 FP8 的反量化无损”说的是格式转换这一步不再引入误差，并不是说 FP4 权重和原来的 FP8 / BF16 权重一样精确——量化到 FP4 本身是有损的，靠量化感知训练让模型适应。报告没有给出量化感知训练前后的精度对比，也没有给出 FP4 推理的实测加速比。

14.5 真实场景评测

报告认为标准基准反映不了真实使用体验，于是针对 DeepSeek API 和聊天产品的主要用途做了一批内部评测（附录 B 的表 9–14）：

  • 中文写作。功能性写作（报告、方案、邮件、通知等 3170 条日常写作请求）上，V4-Pro 对 Gemini-3.1-Pro 的胜率是 62.7% 对 34.1%，报告的解释是 Gemini 有时会让自己的文风偏好压过用户的明确要求。创意写作（2837 条）上，指令遵循胜率 60.0%，写作质量胜率 77.5%。但只看最难的复杂约束和多轮写作（196 条），Claude Opus 4.5 以 52.0% 对 45.9% 胜出。
  • 搜索。网页和 App 上，Non-think 模式用检索增强（RAG），思考模式用智能体搜索。V4-Pro 对 V3.2 的 RAG 问答（956 条），胜 28.1%、负 10.4%、平 61.5%，单值事实查找和攻略规划提升最明显，比较类和推荐类问题 V3.2 仍有竞争力。智能体搜索对 RAG（869 条），胜 61.7%、负 18.3%；成本上，智能体搜索平均 16.2 次工具调用（大多并行）、预填充 13,649 个 token、输出 1,526 个，而 RAG 为 10,453 和 1,308 个，只贵一点。
  • 白领任务。30 个中文专业任务，覆盖金融、教育、法律、科技等 13 个行业，在带 bash 和网页搜索的内部框架里，由标注员盲评 V4-Pro-Max 与 Opus-4.6-Max：V4 胜 53%、平 10%、负 37%，不输率 63%。优势在任务完成度和内容质量；指令遵循略逊，长文压缩成摘要的能力较弱，幻灯片的版面美观度还有很大提升空间。
  • 代码智能体。从 50 多位内部工程师那里收集约 200 个真实研发任务（PyTorch、CUDA、Rust、C++ 等），严格筛选后留下 30 个，通过率为：Haiku 4.5 13%，Sonnet 4.5 47%，V4-Pro-Max 67%，Opus 4.5 70%，Opus 4.5 Thinking 73%，Opus 4.6 Thinking 80%。另一项对 85 位日常用 V4-Pro 写代码的 DeepSeek 员工的问卷中，52% 认为它已经可以作为自己的主力编程模型，39% 倾向于是，不到 9% 认为不行；大家反映的问题是低级错误、误解含糊的指令和偶尔想得过多。

14.6 结果的份量

  • 谁测的、怎么测的。所有数字都由 DeepSeek 在自己的框架和提示模板下测得。对手的成绩部分是重新测的、部分因 API 失败而空缺；各模型使用的推理档位不同（Max、xHigh、High、Thinking），每题花的 token 数也不同，表中没有给出成本。
  • 内部基准占了不少。Codeforces 是内部构造的；研发编程只有 30 题；白领任务只有 30 个；写作和搜索的胜率评测没有说明评判者是人还是模型（白领任务明确是人工盲评）；问卷的对象是 DeepSeek 自己的员工。这些结果只能作为参考，无法独立复核。

15 结论、局限与未来方向

这一节要回答的问题：报告自己承认了哪些不足，下一步打算做什么？把全篇放在一起看，哪些结论有实测支撑，哪些是估算，哪些关键信息没有公开？

报告的总结是：CSA 与 HCA 的混合注意力让超长序列的效率有了大幅提升，配合大量基础设施优化，使 100 万 token 的上下文可以高效地原生支持，为测试时扩展、长周期任务以及在线学习等新范式打下基础；V4-Pro-Max 刷新了开源模型的最好成绩，V4-Flash-Max 以很低的成本达到接近闭源模型的推理能力。

报告也坦率列出了局限：为了降低风险，V4 保留了许多初步验证过的组件和技巧，整体架构相当复杂，下一步要做更系统、更有原则的研究，把架构提炼到最本质的部分；预判路由和 SwiGLU 截断有效，但原理还没有搞清楚，要研究训练稳定性的基础问题、加强内部指标监控；在 MoE 和稀疏注意力之外，要探索新的稀疏维度，比如更稀疏的嵌入模块（报告在这里引用了 DeepSeek 的 Engram 工作，见本站 条件记忆精读）；还要研究低延迟的架构和系统技术，让长上下文的交互更快；继续做长周期、多轮的智能体任务；加入多模态能力；改进数据的整理与合成。

16 后来怎么样了

以下是截至 2026-10-20 能查到的后续情况。V4 发布至今不到半年，后续工作几乎都来自 DeepSeek 自己和推理引擎社区。

发布、开源与推理引擎支持

四个模型仓库（V4-Pro、V4-Flash 及两个 Base）于 2026-04-22 在 Hugging Face 创建，权重采用 MIT 许可：两个基座模型为 FP8 混合精度，两个对话模型的专家参数为 FP4、其余大部分为 FP8。2026-04-24 DeepSeek 正式发布 V4 预览版，网页、App 和 API 同步上线，并宣布 100 万 token 成为所有官方服务的默认上下文长度；旧的 deepseek-chat 和 deepseek-reasoner 接口先转到 V4-Flash，并于 2026-07-24 下线。技术报告最初以 PDF 形式放在 Hugging Face 仓库里，2026-04-26 提交到 arXiv。MegaMoE 内核与 FP4 索引器在发布前一周已合入 DeepGEMM（PR #304，2026-04-17）。

vLLM 在发布当天给出了支持（博客 2026-04-24）：V4-Pro 的单机部署示例跑在 8 张 B200 或 B300 上，V4-Flash 用 4 张；实现上采用 FP8 的注意力缓存和 FP4 的索引缓存，所有压缩层统一用 256 个原始 token 作为一个逻辑块，把压缩器的尾部状态当作滑动窗口来管理，并统一各类缓存的页大小以避免碎片——基本就是报告 §3.5 思路的开源版本。2026-10 vLLM 又发文介绍了在 V4-Flash 上让 rollout 与训练前向逐位一致、同时保留 91% rollout 吞吐的工作，正好呼应报告第 7 节的批不变目标。截至 2026-10-20，V4-Pro 在 Hugging Face 上有约 5,700 个点赞、V4-Flash 约 2,300 个；最近一个月的下载量分别约 36 万和 80 万次。

2026-08-13 DeepSeek 发布 V4-Pro 的正式版（API 中的版本号为 V4-Pro-0813），官方说明强调智能体能力的提升，并为 Pro 和 Flash 提供 low / high / max 三档可调的推理强度；2026-08-21 上线了实验性的多模态接口 V4-Flash-Vision-Exp。

DeepSeek-V4.1-Flash：把 KV 再压 4 倍

2026-09-10 DeepSeek 发布 V4.1-Flash，2026-09-17 在 arXiv 发布技术报告（2609.19969），本站的精读见 DeepSeek-V4.1-Flash 精读。它的出发点是：V4 已经把长上下文的计算压下来了，智能体负载又以长输入为主，于是 KV 缓存在显存和 SSD 上的存储与传输成了降本的主要瓶颈。V4.1 报告把 V4 概括为“以滑动窗口为局部骨干、再加上压缩的全局上下文”，并在这个视角下简化全局分支：

  • CSA2：不再混用 HCA，全部用改进的 CSA；层与层之间复用全局 KV（含索引键）和 top-k 下标，有“完整、重新索引、直接复用”三种静态指定的模式。
  • FP4 的全局 KV 缓存：训练时就用 FP4 存 KV，报告称只有轻微的性能损失。两项合起来，每个 token 常驻显存的全局 KV 降到 890 字节，约为 V4-Flash 的 1/4。
  • 滑动窗口有界重放：第 9 节讲过，V4 精确恢复窗口 KV 要重算 \(n_{\text{win}}\cdot L\) 个 token；V4.1 只重放最近 \(n_{\text{win}}\) 个 token 做近似恢复，报告称性能损失可以忽略。这样就不必把窗口 KV 存到 SSD 上，持久化的 KV 约为 V4-Flash 的 1/8。
  • 此外还有因果编码器–解码器结构（预填充时每 token 激活 8B、解码时 16B，总规模 552B）、单遍 mHC 及配套的 Mega-mHC 内核（激活的显存读写量减半）、集成 Engram 条件记忆和 DSpark 投机解码，以及 45T token 的多模态预训练。

V4.1 报告也给出了一个与本页推算互相印证的数字：它的 890 字节约为 V4-Flash 的 1/4，即 V4-Flash 约 3.5 KB / token（本页 4.7 节推算为 3.45 KB）。

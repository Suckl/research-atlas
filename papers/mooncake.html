0 导读：这篇论文解决什么问题

Kimi 是月之暗面（Moonshot AI）的聊天助手，以能读很长的材料出名。用户经常一次贴进几万字的文档再提问，同一份文档还会在后续几轮对话里被反复带上。对这样的服务来说，GPU 的大部分时间不是花在“一个字一个字往外写”上，而是花在“把很长的输入读一遍”上，也就是 prefill。论文公开的一小时请求样本里，平均每个请求输入 8,590 个 token，输出只有 182 个 token。

模型读输入时，会为每个 token 算出一份 KV 缓存。如果两个请求的开头完全相同（同一份文档、同一段系统提示、同一段对话历史），这部分 KV 缓存也完全相同，算过一次就可以存起来，下次直接取来用。难处在于：长输入的 KV 缓存非常大，按 LLaMA2-70B 的结构，一个 token 约 320 KB，8k 个 token 就是约 2.7 GB（推算），GPU 显存存不了多少；而一个请求被分到哪台机器，又决定了它能不能用上存在别处的缓存。Mooncake 的回答是围绕 KV 缓存来设计整个服务：

  • 把 prefill 和 decode 拆到两组不同的机器上（PD 分离），让两边各自按自己的延迟要求优化；
  • 把 GPU 服务器上本来闲着的 CPU 内存、SSD 和高速网卡汇成一个跨机器的 KV 缓存池，用存储空间换计算；
  • 用一个全局调度器 Conductor，同时看“哪台机器存着这个请求能复用的缓存”和“哪台机器现在忙不忙”，决定请求去哪里；
  • Kimi 经常处于过载状态，所以调度器还要决定拒绝哪些请求，并且要在浪费算力之前就拒绝。

论文（arXiv 版）在 8 卡 A800 节点组成的测试集群上，用一个与 LLaMA2-70B 结构相同的“替身模型”和 vLLM 对比：在两个公开的长文本数据集上，满足延迟要求时的吞吐分别提高 20% 和 40%；在人为构造的 16k–128k 超长输入上提高 50%–525%；按真实时间戳回放线上请求时，满足延迟要求的请求多约 75%。同一工作的会议版（FAST 2025，获最佳论文奖）换了标题，补充了 KV 缓存池的实现和新的实验，并给出生产统计：与此前基于 vLLM 的系统相比，Kimi 在 A800 和 H800 集群上分别能多处理 115% 和 107% 的请求。

1 引言：Kimi 要解的是一个带约束的优化问题

这一节要回答的问题：Kimi 作为“模型即服务”（MaaS）的提供商，目标是在满足延迟要求的前提下，让集群每秒有效完成的请求尽可能多，因为这直接决定收入。提高吞吐有哪两种基本手段？它们各自会伤害哪个延迟指标？作者为什么由此认为，推理服务的调度应该围绕 KV 缓存来做？
先补一点背景：一个请求的两个阶段与 KV 缓存。

大模型回答一个请求分两步（原理详见 vLLM 精读 §2.2）。prefill：把用户的整段输入一次性送进模型，所有输入 token 同时计算，得到第一个输出 token；同时把每个输入 token 在每一层算出的 key 和 value 存下来，这就是 KV 缓存。decode：之后每一步只输入上一步刚生成的那个 token，读取前面全部 token 的 KV 缓存做注意力，生成下一个 token，并把新 token 的 KV 追加进缓存，直到生成结束。

两个阶段受限的资源不同。prefill 一次处理成千上万个 token，计算量很大，主要受 GPU 算力限制。decode 每一步每个请求只处理一个 token，计算量很小，却要把整份权重和所有请求的 KV 缓存从显存读一遍，主要受显存带宽限制。DistServe 精读 §2.1 用 roofline 模型把这一点讲得很细。

先补一点背景：TTFT、TBT、SLO 和 goodput。

用户感受到的速度分两段。TTFT（time to first token，首 token 延迟）是从请求到达到收到第一个输出 token 的时间，包括排队和 prefill。TBT（time between tokens，token 间隔）是之后相邻两个输出 token 之间隔了多久，由 decode 每一步的耗时决定。DistServe 用的是 TPOT（平均每个输出 token 的时间），意思相近：TBT 关心每一个间隔，TPOT 关心平均间隔。

服务商给这两个数定的上限叫 SLO（service-level objective，服务水平目标），通常写成分位数形式，比如“90% 的请求 TTFT 不超过某个值”。在满足 SLO 的前提下，系统每秒最多能完成的请求数，DistServe 等工作称为 goodput（有效吞吐），详见 DistServe 精读 §1。

作者把提高吞吐的手段归成两类，而每一类都会伤害一个延迟指标：

  • 尽量复用 KV 缓存，少做计算。如果新请求的开头和以前某个请求相同，就把那部分 KV 缓存取来用，prefill 只算剩下的部分。但缓存可能存在别的机器上，或者存在比显存慢的存储里，取过来要花时间，这段时间会加到 TTFT 上。
  • 让每个批里的 token 尽量多，把 GPU 用满。decode 阶段一个批里的请求越多，读一遍权重就能为越多请求各生成一个 token，GPU 的利用率（MFU，见下框）越高。但批越大，每一步就越慢，TBT 就越长。
先补一点背景：MFU。

MFU（model FLOPs utilization，模型算力利用率）等于模型实际完成的有效浮点运算量，除以同一段时间里 GPU 理论上能完成的浮点运算量。例如一台 8 卡 A800 的 BF16 稠密算力峰值约 8 × 312 TFLOPS ≈ 2.5 PFLOPS（NVIDIA 公开规格）；如果它每秒只完成 0.5 PFLOPS 的模型计算，MFU 就是 20%。decode 每一步计算很少，MFU 通常很低；把更多请求拼进一个批，是提高 MFU 最直接的办法。

所以两种手段都不能无限制地用，必须在 SLO 之内权衡。作者由此得出全文的出发点：KV 缓存在哪里、能不能复用、往哪里搬，是推理服务调度的核心。他们据此设计了一个以 KV 缓存为中心的分离式架构 Mooncake。一个请求到来后，全局调度器 Conductor 为它选定一对 prefill 实例和 decode 实例，然后分三步执行：

  1. 把尽可能多的可复用 KV 缓存搬到选中的 prefill 实例上；
  2. 按块、按层完成 prefill，并把新算出的 KV 缓存一边算一边源源不断地送往 decode 实例；
  3. decode 实例载入全部 KV 缓存，把请求加入连续批处理，逐个生成输出 token。

流程本身很直接，难在“选哪一对实例”。在 prefill 一侧，想多复用缓存，就倾向于把请求发给存着最长匹配前缀的机器；但如果缓存存在较慢的存储层，等它取回来可能让 TTFT 超标；一个热门缓存所在的机器被许多请求同时读取，网络还会拥塞，等待更久。因此 Conductor 还要预判各个缓存块将来会被用多少：最热的块应该复制到多台机器上分摊读取，最冷的块应该换出去，省下占用的空间。另外，prefill 节点的 CPU 内存大部分划给了全局缓存池，剩下的可用空间也是调度的一个约束。在 decode 一侧，目标是让一个批里聚集尽量多的 token，约束是 TBT 的 SLO，以及显存能装下的 KV 缓存总量。

作者特别强调的是第三个问题：过载。已有的研究大多假设资源够用，只研究怎么把利用率提上去。但现实中 GPU 供应紧张，Kimi 的用户量增长又快，高峰期经常过载。这时系统必须决定拒绝哪些请求，而且最好在浪费算力之前就拒绝：如果一个请求做完了 prefill，才发现 decode 那边已经没有空位，前面的 prefill 就白算了。作者还发现，简单地“提前拒绝”反而会让负载来回振荡，必须预测短期内的负载才能缓解。论文把这类问题称为面向过载的调度，并说明这部分只是初步结果。

后面的章节依次是：架构总览（§3）、公开的真实请求 trace（§4）、prefill 池的实现，包括跨节点的分块流水线并行和逐层 prefill（§5）、以 KV 缓存为中心的调度（§6）、面向过载的调度（§7）和实验（§8）。作者在引言末尾写道，Mooncake 是当时 Kimi 的主要服务平台，扛住了指数式增长的负载。

读之前先有个预期：这是一份描述大规模生产系统的设计报告，而不是一个可以照着复现的算法论文。很多设计只给思路、不给参数（例如 prefill 的分块大小、流水线组的节点数、热点复制的阈值）；实验全部用一个结构与 LLaMA2-70B 相同的替身模型完成，Kimi 实际用的模型和线上 SLO 都没有公开。读的时候，最有价值的是它暴露出来的取舍：为什么这样拆、拆完之后哪里变难了。

2 预备知识与问题定义：两个阶段的耗时规律，以及“只算完整完成的请求”

这一节要回答的问题：prefill 和 decode 的耗时分别怎样随输入长度和批大小变化？SLO 具体怎么定？论文的“有效吞吐”和其他工作的 goodput 有什么不同？这个不同为什么直接引出了后面的“提前拒绝”？

怎么看：两张小图的纵轴都是归一化后的数值（各自的最大值为 1）。柱子是吞吐（每秒处理或生成的 token 数），红线是一次 prefill 或一步 decode 的耗时。左图要看红线：输入长 16 倍，耗时涨约 30 倍，所以柱子越来越矮。右图要看柱子：批大 16 倍，吞吐涨约 13 倍，而红线几乎是平的。数值为从图上读出，对应 原文图 2 ↗；原图画了 8k–128k 的 16 个点和批大小 1–16 的 16 个点。

先看 prefill。输入长度翻 16 倍（8k → 128k），耗时涨了约 30 倍，每秒处理的 token 数掉到约一半。原因是 Transformer 里两类计算随长度增长的速度不同：线性层（注意力里的投影和 MLP）对每个 token 的计算量固定，总量随输入长度 \(n\) 线性增长；注意力要让每个 token 和它前面所有 token 两两打分，总量随 \(n^2\) 增长。输入越长，注意力占的比例越大，总耗时就涨得比长度更快。

可以粗算一下（推算）。LLaMA2-70B 约 690 亿参数，线性层对每个 token 约需 \(2\times 69\times10^{9}\approx1.4\times10^{11}\) 次浮点运算。因果注意力对一段长 \(n\) 的输入，平均每个 token 约需 \(2nLd\) 次浮点运算（层数 \(L=80\)，隐藏维度 \(d=8192\)）。\(n=8\text{k}\) 时，注意力每个 token 约 \(1.1\times10^{10}\) 次，只占总量的 7%；\(n=128\text{k}\) 时约 \(1.7\times10^{11}\) 次，已经超过线性层。于是每个 token 的成本涨到约 2.1 倍，每秒能处理的 token 数降到约 0.48，和图上读出的 0.54 是同一个量级。两者不完全一致，是因为真实注意力内核的效率本身也随长度变化。

再看 decode。批大小从 1 增加到 16，每一步的耗时只增加了约 24%，每秒生成的 token 数却增加了约 13 倍。原因是 decode 每一步的时间主要花在从显存读数据上：要读整份权重（BF16 下约 138 GB，由 8 张卡分摊），还要读批里每个请求的 KV 缓存（8k 上下文时每个请求约 2.7 GB）。批大小从 1 到 16，要读的总字节数从约 141 GB 涨到约 181 GB，只多了约 29%，和耗时的涨幅相近（推算）；而产出的 token 数变成了 16 倍。这就是 decode 要尽量组大批的原因，也是 TBT 会随批变大而慢慢变长的原因。

正因为两个阶段的规律截然不同，服务商给它们定了不同的指标：prefill 看 TTFT，decode 看 TBT。

SLO 怎么定。论文用相对值描述 SLO：\(\text{TTFT}_{P90}=4\times\) 的意思是，90% 的请求的 TTFT 不超过“同样条件下单独运行这个请求、没有任何干扰时的 TTFT”的 4 倍。§8 的端到端实验用的是 \(\text{TTFT}_{P90}=10\times\) 和 \(\text{TBT}_{P90}=5\times\)。真实部署里用的是固定的 TTFT 和 TBT 上限，具体数值论文没有公开。监控发现 SLO 不能满足时，只有两条路：加机器，或者拒绝一部分新请求。

为什么“拒绝谁”成了核心问题。GPU 供应紧张，临时扩容通常做不到，所以过载时的调度，核心就是决定拒绝哪些请求。作者的目标仍是在满足 SLO 的前提下最大化吞吐，也就是其他工作说的 goodput，但计数方式更严格：只有完整执行完的请求才算数。一个请求如果中途被放弃，它已经消耗的 prefill 计算和已经生成的 token 一概不算，相应的资源全部浪费。由此得到一个直接的推论：如果一个请求注定无法在 SLO 内完成，就应该越早拒绝越好。要做到这一点，既要把 prefill 和 decode 两边的架构做好，也要能预测短期内的负载。

3 架构总览：三个资源池、一个调度器，请求走四步

这一节要回答的问题：Mooncake 由哪些部件组成？“分布式 KV 缓存池”建在哪里、里面的缓存块怎么组织，才能让不同请求找到可以共享的部分？一个请求从到达到输出依次经过哪四步，每一步里 KV 缓存在哪两处之间移动？
先补一点背景：一台 GPU 服务器上的三层存储。

一台 8 卡 GPU 服务器上，能存 KV 缓存的地方有三层。GPU 显存（HBM）：每张 A800 有 80 GB，带宽约 2 TB/s，但要先放模型权重，剩下的才能给 KV 缓存。CPU 内存（DRAM）：整机常见 1–2 TB（Mooncake 的期刊版提到初期每个节点给缓存池划了约 1 TB），容量比显存大一个数量级，但 GPU 要经过 PCIe 才能读到，带宽小一个数量级。本地 SSD：容量再大一个数量级，速度再慢一个数量级。推理服务主要靠 GPU 干活，CPU 内存和 SSD 往往大量闲着，这正是 Mooncake 要利用的资源。

先补一点背景：RDMA，以及 KV 缓存搬一次要多久。

机器之间传数据，普通做法走 TCP：数据要经过操作系统内核、被拷贝好几次，CPU 也要全程参与。RDMA（远程直接内存访问）让一台机器的网卡直接读写另一台机器事先登记过的内存，不经过对方的 CPU 和内核，所以延迟低、带宽能跑满。GPUDirect RDMA 再进一步，让网卡直接读写 GPU 显存，省掉先拷到 CPU 内存的一步。论文测试集群的每个节点配有合计最高 800 Gbps 的 RDMA 网卡，约合 100 GB/s。

算一笔账（推算）。LLaMA2-70B 有 80 层、8 个 KV 头、每个头 128 维，用 BF16 存储时，一个 token 的 KV 缓存是

$$\underbrace{2}_{K\ \text{和}\ V}\times\underbrace{80}_{\text{层}}\times\underbrace{8}_{\text{KV 头}}\times\underbrace{128}_{\text{每头维度}}\times\underbrace{2\ \text{字节}}_{\text{BF16}}=327{,}680\ \text{字节}\approx 320\ \text{KB}$$

一段 8k token 的前缀就是约 2.7 GB。按 100 GB/s 传，只要约 27 毫秒；而在 8 卡 A800 上把这 8k token 重新 prefill 一遍，按 50% 的 MFU 估算约需 1 秒。传比算快几十倍，“用存储换计算”才划得来。如果网络只有 100 Gbps（约 12.5 GB/s），传同样的数据要约 0.2 秒，优势就小得多。下面的计算器可以换模型和链路自己算（选 Llama-3-70B，它的 KV 形状与 LLaMA2-70B 相同）。

上图是 Mooncake 的整体结构。它把集群拆成三类资源池，再用一个调度器统一管理：

  • Prefill 池：一组只做 prefill 的实例。每个实例的显存里用分页方式存 KV 缓存（PagedAttention 的做法，见 vLLM 精读 §4.2），并有一个本地调度器负责把长输入切块执行。特别长的输入可以由几个实例组成流水线一起处理（§5.1 的分块流水线并行，CPP）。
  • Decode 池：一组只做 decode 的实例，用连续批处理逐 token 生成，本地调度器负责组批。
  • 分布式 KV 缓存池：它不是另外一组存储服务器，而是把上面这些 GPU 服务器自己的 CPU 内存、SSD 和 RDMA 网卡汇到一起。作者的说法是，这些资源本来就闲着，拿来做缓存不增加额外成本，还能提供“贴近 GPU”的前缀缓存。
  • Conductor：全局调度器，根据 KV 缓存当前分布在哪里、各实例负载如何来分派请求；如果对后续推理有利，它还会复制或换出某些缓存块。

图右侧写的两个优化目标，几乎就是全文的提纲。prefill 阶段要在“TTFT 达标、MFU 不低于下限、KV 缓存总量不超过 CPU 内存”三个约束下，尽量多复用缓存。decode 阶段要在“TBT 达标、KV 缓存总量不超过显存”两个约束下，尽量提高吞吐。注意 prefill 一侧的容量约束是 CPU 内存而不是显存，§5.2 会解释为什么显存在 prefill 端不再是瓶颈。

3.1 缓存池里的块：带前缀的哈希

在 CPU 内存里，KV 缓存按固定大小的块（页）存放。每个块带一个哈希值，这个哈希不只由本块的 token 决定，还把前一个块的哈希也算进去：第一块 \(A=\text{Hash}(a)\)，第二块 \(B=\text{Hash}(A+b)\)，第三块 \(C=\text{Hash}(B+c)\)，依此类推。这样一来，两个块的哈希相同，就意味着从开头到这一块为止的所有 token 都相同，对应的 KV 缓存也完全相同，可以只存一份（去重）。新请求来了，把它的输入同样切块、算出哈希，从第一块开始去缓存里查，一直查到第一个查不到的块为止，前面那些就是可以复用的前缀。

为什么要把前缀算进哈希？因为同一段文字出现在不同的前文后面，它的 KV 缓存是不同的：注意力让每个 token 的 key 和 value 都混入了前文的信息（见 vLLM 精读 §2.2 末尾的提醒）。如果只按本块的内容算哈希，就会把两段“字面相同、前文不同”的块误认成同一个，复用出错误的结果。

缓存满了要淘汰时，可以用 LRU（最久没被用到的先淘汰）、LFU（被用得最少的先淘汰），或者按请求特点设计的策略。块在 CPU 与 GPU 之间、机器与机器之间的搬运，由每个节点上一个独立的进程 Messenger 负责，它基于 RDMA，条件允许时用 GPUDirect RDMA。有了这个缓存池，Kimi 还能对外提供“上下文缓存”（context caching）接口：用户主动声明某段长前缀会被反复使用，系统就把它的 KV 缓存留住，进一步提高复用。

3.2 一个请求的四步

分词完成后，Conductor 为请求选定一组 prefill 节点和一个 decode 节点，然后按下面四步执行：

示意图：请求在 Mooncake 里的四步，以及 KV 缓存的流向
Conductor选定 prefill 组与 decode 节点→① KV 复用按前缀块 ID，从（可能是远端的）CPU 内存载入显存→② 增量 prefill只算未命中的 token；新 KV 写回 CPU 内存
→③ KV 传输Messenger 把每层刚算出的 KV 流式送到 decode 节点的 CPU 内存，与 ② 重叠→④ decodeKV 全部到达后加入连续批处理；载入显存与解码异步重叠
本站示意图，对应 原文图 4 ↗。原图用星号和剑号注明：prefill 端的载入和写回是逐层进行、与计算并行的（§5.2）；decode 端的载入与 GPU 解码异步并行，避免 GPU 空等。
  1. KV 复用。选中的 prefill 节点（或节点组）收到三样东西：原始输入、可复用前缀的块 ID、为这个请求分配的全部块 ID。它按前缀块 ID 从远端的 CPU 内存把前缀的 KV 缓存载入显存，作为起点。没有可复用的前缀，这一步就跳过。
  2. 增量 prefill。prefill 节点利用载入的前缀，只计算剩下没命中的 token，并把新算出的“增量”KV 缓存写回 CPU 内存。如果没命中的 token 数超过阈值 \(prefill\_chunk\)，就把 prefill 切成几块、以流水线方式执行。这个阈值的选法是让单块足以把 GPU 算力用满，通常大于 1000 个 token。为什么切块之后仍然坚持把 prefill 单独放在一个池里，§5.1 解释。
  3. KV 传输。每个节点上的 Messenger 负责管理和搬运缓存，它作为推理实例里的一个独立进程运行，收到信号后执行跨机器的高速传输。这一步是异步的，和上一步重叠：每一层的 KV 一算出来，就流式送往目标 decode 节点的 CPU 内存，从而减少等待。
  4. decode。全部 KV 缓存到达 decode 节点的 CPU 内存后，请求在下一轮加入连续批处理，开始逐 token 生成。

第 4 步有一个容易忽略的细节。Conductor 在请求刚到时就按 decode 节点的当前负载预选了它，以保证 TBT 不超标；但等 prefill 做完，那个 decode 节点的负载可能已经变了，所以 decode 节点的本地调度器会再检查一次。如果这次检查不通过，请求会被拒绝，前面的 prefill 就白做了。这正是第 2 节说的那种浪费，第 7 节的“提前拒绝”就是为了减少它。

第 1 步选哪个 prefill 节点，要同时照顾三个目标：尽量多复用 KV 缓存、让各个 prefill 节点的负载均衡、保证 TTFT 不超标。三者经常互相冲突，这就引出了第 6 节的“以 KV 缓存为中心的调度”。

读的时候容易误解的地方：
  • “分离式 KV 缓存”不是另建一套存储集群，而是 GPU 服务器自带的内存和 SSD 拼起来的。好处是不花额外的钱，代价是缓存的容量和带宽跟着推理节点的数量和网卡走。
  • 复用要求从开头起逐块完全相同。两个请求只是中间有一大段相同（比如同一篇文档放在不同的问题之后），这种缓存方式复用不了。块越大，越难整块相同；公开 trace 用的是 512 token 一块，会议版说实际块大小在 16 到 512 token 之间，取决于模型大小和网络传输的最佳粒度。
  • arXiv 版描述的传输路径是先落到 decode 节点的 CPU 内存，再载入显存。后来开源的版本同时支持 GPU 到 GPU 直接传（GPUDirect RDMA）和经 CPU 内存中转两种方式（第 10 节）。

5 Prefill 池的实现：为什么还要单独一个池，长输入怎么跨机器算

这一节要回答的问题：decode 节点必须单独成池，这一点没有争议；但 prefill 是否也要单独成池，当时还有争论。chunked prefill 可以把长输入切块塞进 decode 批里，在同一组机器上兼顾两边，那为什么 Mooncake 仍然坚持把 prefill 拆出去？超长输入的 prefill 一台 8 卡机器太慢，要几台机器一起算，又该怎么分工？
先补一点背景：chunked prefill。

Sarathi-Serve 等工作提出的 chunked prefill（分块预填充）不把 prefill 和 decode 拆到不同机器上，而是把一个长输入切成固定大小的块，每次只算一块，并和正在 decode 的请求拼在同一个批里执行。这样，正在生成的请求不会被一个长 prefill 卡住太久；同时 decode 批里混入了一块 prefill，计算量变大，GPU 利用率也更高。详见 Sarathi-Serve 精读页。

作者承认 chunked prefill 有两个明显的好处：一是不分离时所有节点一视同仁，调度更简单；二是把 prefill 块塞进 decode 批，能提高 decode 批的计算强度，从而提高 MFU。但仔细权衡之后，他们决定保留分离架构。只有当一个请求的 prefill 不需要切块、能一次做完，而且塞进 decode 批也不会违反 TBT SLO 时，才把它直接塞进 decode 批里执行（这实际上只适用于短请求）。理由有两条：

  1. 处理长上下文时，prefill 节点需要与 decode 节点不同的跨节点并行方式（§5.1）；
  2. 分离之后，prefill 端出现了一个节省显存的独特机会（§5.2）。

5.1 跨节点 prefill：张量并行、序列并行，还是分块流水线

近来模型支持的上下文从 8k 涨到 128k，甚至 100 万 token。这类长上下文请求的输入往往是输出的 10 到 100 倍，所以优化 TTFT 成了关键。长输入的 prefill 有大量可以并行的计算，一台 8 卡机器不够快，自然希望多台机器一起算。问题是怎么分工。

先补一点背景：把一个请求的 prefill 分给多台机器的三种方式。
  • 张量并行（TP）：把每一层的矩阵乘拆开，每张卡算一部分，每层算完要做两次 all-reduce 把结果合起来（原理见 Megatron-LM 精读 §3.5）。在一台机器内部走 NVLink 没问题；扩到多台机器，这两次 all-reduce 就要走机器之间的 RDMA 网络，慢得多。
  • 序列并行（SP）：把一个请求的输入序列切成几段，每台机器负责一段 token。线性层各算各的，注意力需要别的段的 key 和 value，于是像 Ring Attention 那样，把各段的 KV 沿着一个环依次传给下一台机器。这依赖注意力运算可以分段累加的性质（论文称之为结合律），每层至少要跨机器通信一次，但传的只是 KV，比 TP 的通信量小得多。
  • 流水线并行（PP）：把模型的层按顺序切成几段，每台机器负责一段，数据像在流水线上一样依次流过各台机器，只在段与段的边界上传一次激活。

作者对三种方式的判断如下。跨节点 TP 每层两次走 RDMA 的 all-reduce，会显著拉低 prefill 节点的 MFU。SP 大大减少了通信、提高了 MFU，但对短请求来说，它的 MFU 仍然不如单机 TP。理想的部署因此要把 prefill 节点再分成两组：一组只用 TP，处理普通请求；一组用 SP，只在长请求非得靠它才能满足 TTFT 时才用。这第二层拆分又带来新麻烦：两组各要多少台机器？负载一变，固定的划分就会让一部分机器闲着。LoongServe 提出的弹性序列并行可以动态伸缩 SP 组，但要事先建立全局通信组，还让 Conductor 在调整期间要额外考虑缓存复用和 SLO 违约，对需要频繁在线扩缩的生产环境来说太复杂。而且 SP 每层仍要跨机器通信，既拉低 MFU，又和 KV 缓存的跨机器传输抢网络带宽。

Mooncake 的做法叫分块流水线并行（chunked pipeline parallelism，CPP）。prefill 集群里每 X 个节点编成一个流水线组（论文没有给出 X 的取值），组内每个节点负责模型连续的一段层。一个请求的输入被切成若干块，每块不超过 \(prefill\_chunk\) 个 token。同一个请求的不同块可以同时在不同节点上处理：第 1 块在第一个节点上算完前一段层，交给第二个节点继续算后一段层；与此同时，第一个节点已经开始算第 2 块。

为什么后一块可以在前一块还没走完全部层时就开始？这要用到 decoder-only 模型“自回归”的性质：第 \(k\) 块里的 token 只看得到它前面的 token。所以第 2 块在第 \(\ell\) 层计算注意力时，只需要第 1、2 块在第 \(\ell\) 层的 key 和 value；而第 1 块在第 \(\ell\) 层的 KV，正是负责第 \(\ell\) 层的那个节点刚刚算出、就存在它自己显存里的。因此每个节点只要按块的顺序依次处理，既不用等整个请求，也不用向别的节点要 KV。

示意图：同一个长请求切成 4 块，三种做法的完成时间
怎么看：单节点每块要算满 80 层，记为 2 个单位，四块共 8 个单位。跨节点 TP 让每块的计算减半，但每块都附带一段跨机器通信（斜纹，这里示意性地画成 0.6 个单位）。CPP 中两台机器各管一半的层：节点 1 算完块 1 的前 40 层就交给节点 2，自己马上开始块 2，两台机器同时在忙，约 5 个单位完成。本站示意图，数字只为说明形状；它忽略了一个事实：后面的块要和更长的前文做注意力，计算会更慢一些。

CPP 带来两个好处。第一，和训练里的流水线并行一样，它只在段与段的边界上通信，传的只是一块的激活，而且很容易和计算重叠；所以 MFU 更高，也不会和 KV 缓存的传输抢网络。第二，它对长短输入一视同仁：短输入只有一块，顺着流水线走一遍，多出来的只是几次很小的边界传输，没有明显的额外开销；长输入则自动被切成多块并行起来。所以它不需要像序列并行那样，随负载变化频繁地重新划分节点。作者提到，按 token 切块的流水线在训练系统里已有先例（他们引用的是 TeraPipe），但据他们所知，这是第一次用在推理上，因为长上下文推理是最近才出现的需求。

读的时候容易误解的地方：CPP 并不减少一个请求的总计算量，它只是让同一个请求的不同块在不同机器上同时进行，从而缩短 TTFT。论文没有给出 CPP 本身的实测（没有单独的消融实验），也没有公开流水线组的节点数和分块大小；“比 SP 更好”是基于通信量和运维复杂度的论证，而不是并排测出来的结论。

5.2 逐层 prefill：让 KV 缓存一层层流出显存

除了算力，显存也是稀缺资源，作者希望尽量缩短状态（主要是 KV 缓存）占用显存的时间。他们用一个简单的量衡量“占用代价”：一个请求的 KV 缓存大小为 \(S\)、处理时间为 \(T\)，占用代价就是 \(S\times T\)。如果用 chunked prefill，把一个长请求切块、每块和别的 decode 请求拼在一起执行，\(T\) 会被拉长，占用代价也随之变大。

反过来，prefill 是一层一层算的，而且是算力受限的：GPU 忙于计算，显存带宽和 PCIe 相对空闲。这就可以让 KV 缓存的搬运和计算重叠，进一步缩短 KV 缓存在显存里停留的时间。Mooncake 用异步的“发起”和“等待”操作实现这一点：

  1. 每一层的注意力开始之前，先等这一层的 KV（可复用的前缀部分）异步载入完成，同时发起下一层 KV 的异步载入；
  2. 这一层的注意力算完后，立刻发起这一层新 KV 的异步写出；
  3. 所有层都算完后，等所有写出操作完成。
示意图：算完再整体写出 vs 逐层写出
怎么看：绿色是每一层的计算，青色是把这一层新算出的 KV 写出到 CPU 内存。串行做法要等所有层算完才开始写，KV 缓存在显存里多待了整段写出时间；逐层做法在第 \(\ell+1\) 层计算的同时写出第 \(\ell\) 层，只多出最后一层的写出时间。载入前缀 KV 的方向相反，原理相同。本站示意图，只画了 4 层。

这样一来，prefill 实例的执行时间大约等于“载入 KV 的时间”和“正常 prefill 的时间”二者中较大的那个；哪个更大，取决于前缀缓存占输入的比例：前缀越长，要载入的越多，要计算的越少。原文图 7 比较了两种做法下，写出 KV 缓存给 prefill 增加的额外延迟（逐层做法的额外延迟定义为：逐层 prefill 的总耗时减去完全不写出 KV 时的 prefill 耗时）：

读的时候容易误解的地方：逐层重叠能把写出时间藏起来，前提是每一层的计算时间不短于搬运这一层 KV 的时间。长输入的 prefill 满足这一点（计算随长度超线性增长，KV 只线性增长）；很短的输入计算很快，就未必藏得住。另外，\(S\times T\) 只是一个直观的代价指标，论文没有给出它省下了多少显存、多放了多少请求的测量。

6 以 KV 缓存为中心的调度：去命中最长的机器，还是去最闲的机器

这一节要回答的问题：已有系统通常按“每个实例分到了多少请求”来做负载均衡。Mooncake 为什么要把前缀命中长度、可复用缓存块的分布也考虑进来？在“去命中最长的机器”和“去最闲的机器”之间，它怎么权衡？热门缓存被大家抢着读时，又怎样在不预测未来的情况下把它复制开？这一节只讨论正常负载，过载留给第 7 节。
先补一点背景：单机的前缀缓存。

vLLM 和 SGLang 当时都已经能在一台机器内部复用前缀的 KV 缓存：SGLang 用基数树找出新请求和已缓存内容的最长公共前缀，并在等待队列里优先执行命中多的请求（见 SGLang 精读 §3.1 和 §3.4 缓存感知调度）。但这些缓存只在本机的显存（或内存）里，别的实例用不上。一旦集群有很多实例，请求被分到哪个实例，就决定了它能不能命中缓存。

6.1 全局 prefill 调度：估一估在每个实例上的 TTFT

Mooncake 选 prefill 实例时，不只看负载，还看前缀命中长度和可复用缓存块的分布。把请求发给前缀命中更长的实例，可以少算很多；但如果那台实例正忙，排队时间可能抵消掉省下的计算，甚至让 TTFT 超标。为了同时考虑这两件事，作者提出一个缓存感知的全局调度算法（原文算法 1），核心思想是：对每个候选实例，估计这个请求在它上面的 TTFT，然后选最小的。具体步骤是：

  1. 把新请求的输入切块，按 3.1 节的方式算出每块“带前缀”的哈希键；
  2. 拿这些键逐个去和每个 prefill 实例的缓存键比较，得到这个请求在该实例上的前缀命中长度 \(prefix\_len\)（不同实例不一样）；
  3. 根据请求长度和 \(prefix\_len\) 估计在该实例上的 prefill 执行时间，再加上该实例的排队等待时间，得到在该实例上的预计 TTFT；
  4. 把请求分给预计 TTFT 最短的实例，并更新这个实例的缓存信息和队列时间；
  5. 如果连最短的 TTFT 都满足不了 SLO，Conductor 直接向上层返回 HTTP 429（Too Many Requests）。

论文还提到，vLLM 已经实现了类似的前缀复用逻辑，但它的开源版只支持本机缓存，做不到跨实例。下面用一组示意数字走一遍（数字为本站虚构，只用来说明取舍；prefill 时间按每 1k 个未命中 token 约 0.125 秒粗估，传输按 100 GB/s、每 token 320 KB 推算）：

这个框架的骨架很简单，复杂之处藏在几个估计量的工程实现里。prefill 时间：用离线测试数据拟合一个预测模型（会议版说是多项式回归），输入是请求长度和前缀命中长度。Transformer 的计算模式非常规则，只要离线数据足够，预测误差就很小。排队时间：把队列里所有请求的预计 prefill 时间加起来。实际实现中，对各个实例的 TTFT 估计是并行算的，耗时相对推理本身可以忽略。传输时间最难预测：它不仅取决于要传多少数据，还取决于当时的网络状况，尤其是发送方是否正在拥塞。热门缓存所在的机器最容易成为发送端的瓶颈，这就引出了热门块的复制问题。

def schedule(req, prefill_pool, decode_pool):
    keys = prefix_hash(req.tokens, block_size)            # 带前缀的块哈希
    best_len, holder = longest_match(prefill_pool, keys)   # 全集群最长的前缀命中在哪台
    best_ttft, chosen = inf, None
    for inst in prefill_pool:
        local_len = inst.match(keys)                       # 本机能复用多少
        t_queue = inst.est_queue_time()
        if best_len < THRESH * local_len:                 # 远端多不了多少：只用本机缓存
            ttft = t_queue + est_prefill(len(req), local_len)
        else:                                              # 远端多很多：算上把它拉过来的时间
            t_xfer = est_transfer(holder, inst, best_len - local_len)
            ttft = t_xfer + t_queue + est_prefill(len(req), best_len)
        if ttft < best_ttft:
            best_ttft, chosen = ttft, inst
    d, tbt = pick_decode_by_load(decode_pool)               # decode 端按负载选
    if best_ttft > TTFT_SLO or tbt > TBT_SLO:
        return reject(429)                                 # 注定超标：直接拒绝
    if best_len > THRESH * chosen.match(keys):
        transfer_kv(holder, chosen)                        # 顺手把热点前缀复制过去
    return chosen, d

6.2 缓存负载均衡：不预测未来，让热点自己复制开

在 Mooncake 集群里，每台 prefill 机器管理着自己本地的一批前缀缓存（它们都在这台机器的内存里，同时属于全局缓存池）。这些缓存的使用频率差别极大：系统提示几乎被每个请求访问，而某份长文档的缓存可能只有一个用户会用到。所以从分布式缓存系统的角度看，“副本放在哪里”本身就是一个负载均衡问题：要让全局调度既能命中缓存，又不会都挤到少数机器上。

一个直观但行不通的方案是：收集每个块的全局使用情况，用预测模型估计它将来会被用多少，再据此安排副本。问题是，和 prefill 时间不同，负载本身高度动态、变化很快，对一个用户量快速增长的服务商来说，准确预测未来的使用情况是不可能的。因此作者提出一个基于启发式的热点自动迁移方案，它不需要精确的预测：

  • 前面说过，请求不一定会被分给前缀命中最长的实例，因为那台实例可能太忙。这时 Conductor 把缓存所在的位置连同请求一起交给另一台实例；这台实例主动从持有者那里拉取 KV 缓存，并在本地存一份。
  • 更重要的是，如果全集群最好的远端命中长度，不超过本机可复用前缀长度乘以一个阈值，就宁可在本机把缺的 token 算出来，而不去远端拉取。这个阈值目前是人工调的，作者说将来可以由算法自适应调整。

这两条规则既缩短了请求的 prefill 时间，又顺带让热门缓存被自动复制到更多机器上：越热的前缀，越常出现“持有者太忙、请求被分到别处并把缓存拉过去”的情况，于是副本越多。

原文的一处措辞：论文正文写的是“如果额外的 prefill 时间短于传输时间，就把缓存位置和请求转给另一台实例”，单看这句话，比较的方向不太好理解。算法 1 的写法更清楚：先用“远端最长命中 ÷ 本机命中”与阈值比较，决定是否考虑拉取；考虑拉取时，把传输时间计入预计 TTFT，和其他候选一起比较。上面的伪代码按算法 1 改写。

7 面向过载的调度：拒绝要趁早，但不能只看眼前

这一节要回答的问题：大多数研究假设所有请求最终都会被处理，只优化吞吐或延迟。真实的商业服务里，用户请求的增长远快于集群扩容的速度，高峰期过载是常态。过载时，系统该按什么标准拒绝请求？PD 分离为什么让这件事变得更难？“提前拒绝”为什么会引起负载来回振荡，预测又怎么缓解它？
先补一点背景：准入控制。

任何在线服务都有容量上限。请求超过上限时，与其让所有请求一起排长队、最后人人都超时，不如在入口就拒掉一部分，让被接收的请求能按时完成。这叫准入控制（admission control），也叫负载削减。HTTP 429（Too Many Requests）就是告诉客户端“现在太忙，请稍后再试”。准入控制的关键是两件事：怎么衡量“系统现在有多忙”，以及在什么时刻做决定。决定得越晚，被拒请求已经消耗的资源就越多。

作者的原则是：系统在负载达到预设阈值之前尽可能多地接收请求，超过阈值之后，剩下的请求要么直接拒绝，要么推迟重试。分离架构让调度更灵活，但也带来了耦合系统没有、此前的 PD 分离工作（Splitwise、DistServe、TetriInfer）也没有讨论过的新问题。

7.1 “系统负载”怎么定义

在 prefill 和 decode 放在一起的传统系统里，两个阶段互相干扰，TTFT 和 TBT 都很难预测，所以负载通常只能粗略地定义为“正在处理的请求数 ÷ 系统的最大容量”。Mooncake 的两个阶段在不同机器上独立运行，各自的延迟可以预测得比较准，所以作者直接用 SLO 的满足程度来衡量负载。设 \(l_{ttft}\) 和 \(l_{tbt}\) 分别是 TTFT 和 TBT 的 SLO 上限：一个 prefill 实例的负载，就是它上面预测的最大 TTFT 与 \(l_{ttft}\) 之比；一个 decode 实例的负载，就是它上面预测的最大 TBT 与 \(l_{tbt}\) 之比。比值接近 1，说明再多接请求就要超标了。

有了这两个量，调度要做两个决定：第一，根据 prefill 实例的负载，决定是否接收这个请求的 prefill；第二，prefill 完成后，根据 decode 实例的负载，决定是否让它进入 decode。

7.2 提前拒绝：把 decode 端的检查挪到 prefill 之前

问题出在这两个决定之间隔着一段时间。一个请求先被 prefill 接收，等它算完要进入 decode 时，decode 实例可能已经满了，只好拒绝它，前面的 prefill 计算就白费了。结果是，prefill 实例看起来一直在满负荷工作，真正被成功处理的请求却比这个负荷所暗示的少。

自然的改进是把 decode 端的负载检查提前到 prefill 开始之前，作者称之为提前拒绝（Early Rejection）：请求一到达，Conductor 就取 prefill 池和 decode 池两者负载中较大的那个来决定是否接收。这显著减少了被拒请求造成的无效计算，也让两边的负载更均衡。

7.3 提前拒绝带来的负载振荡

但提前拒绝引入了新问题。原文图 9 是线上一个 20 台机器的集群在采用提前拒绝之后，20 分钟内 prefill 机器和 decode 机器的负载曲线：两条曲线大幅度地来回摆动，而且相位相反，一边高时另一边低。作者观察到，prefill 机器越少、prefill 阶段越长，这种振荡越明显。

原因在于“预测 decode 负载”和“请求真正进入 decode”之间存在时间差：调度依据的是 decode 端当前的负载，而这个负载反映的其实是过去接收的请求。这就像洗澡时调水温：热水要过几秒才流到喷头，你根据当前水温去拧阀门，结果总是拧过头，水温忽冷忽热。论文图 10(a) 用一个理论例子把这个过程分成四个阶段：

7.4 基于预测的提前拒绝

解决办法是不看 decode 的当前负载，而是预测“新请求做完 prefill、真正进入 decode 时，decode 会有多忙”，再据此决定是否接收（原文图 10(b)）。这件事的核心是预测接下来一段时间的 decode 负载，作者讨论了两种粒度：

  • 请求级预测：预测每个请求会输出多少个 token。如果知道输出长度，就能比较准确地估计每个请求的 TTFT 和 TBT，进而算出某个时刻 decode 实例上有多少请求完成、多少新请求加入，得到那一刻的负载。但预测输出长度要么代价高（论文在这里引用的是 TetriInfer，它为此额外运行一个长度预测模型），要么不准；过载时资源本来就紧张，又最需要准确的预测，所以请求级预测特别难。
  • 系统级预测：不预测单个请求何时结束，只估计一段时间之后各 decode 实例上总的批大小或 TBT 状况。这种预测是持续滚动进行的，对精度要求低得多，更适合过载场景。

Mooncake 目前用的是系统级预测，做法很朴素：假设每个请求的 decode 阶段都持续同样长的时间 \(t_d\)。对未来某个时刻 \(t\)：先把到 \(t\) 为止 prefill 实例能完成的请求加到 decode 实例上；再把到 \(t\) 为止 decode 时间已经超过 \(t_d\)、也就是会完成的请求移除；最后计算所有 decode 实例的平均 TBT 与 \(l_{tbt}\) 之比，作为预测的负载。请求级预测留作将来的工作。

用一组示意数字看看两种规则的差别（为便于理解，把 decode 负载近似成“在跑请求数 ÷ 容量”，容量设为 400 个请求，\(t_d=30\) 秒，都是虚构的数字）：此刻 decode 上有 200 个请求，负载 50%；其中 60 个已经跑了 20 秒以上，10 秒内会完成；prefill 端正在处理的 260 个请求 10 秒内会做完 prefill。只看当前负载的规则看到 50%，会继续大量接收。预测规则估计 10 秒后 decode 上有 \(200-60+260=400\) 个请求，负载 100%，于是此刻就应该收紧接收。反过来，如果 decode 此刻 95% 满、但很多请求马上要完成，而 prefill 端几乎是空的，预测规则会继续接收，避免 prefill 白白闲着。

读的时候要注意：“每个请求 decode 时间都一样”是一个很粗的假设，在输出长度差异很大的负载里，误差会不小。论文没有报告预测的准确度，也没有给出采用预测之后的实测负载曲线（图 10 两张都是示意图），效果只体现在第 8 节过载实验的拒绝数上（本页 8.5）。

8 实验：和 vLLM 比，在什么条件下快、快多少

8.6 结果的份量

把上面的实验放在一起，可以这样理解这些数字：

  • 哪些是生产数据。arXiv 版里来自线上的只有两样：公开的一小时请求 trace，以及图 9 中一个 20 台机器集群 20 分钟的负载曲线。其余所有数字都来自测试集群上的回放或模拟，用的是替身模型。摘要里“在真实负载下让 Kimi 多处理 75% 的请求”，指的是 8.4 节那次回放实验，而不是线上 A/B 测试。真正的生产统计只出现在会议版和期刊版：与此前基于 vLLM 的系统相比，Kimi 在 A800 和 H800 集群上分别多处理 115% 和 107% 的请求；这个数字被描述为“历史统计”，没有给出统计方法、时间段和比较条件。
  • 模型。全部实验用结构与 LLaMA2-70B 相同的替身模型（会议版换成 LLaMA3-70B 结构）。它的 KV 缓存每 token 约 320 KB（GQA，8 个 KV 头）。KV 缓存更大的模型，传输和存储的压力更大；KV 缓存更小的模型（例如用 MLA 压缩 KV 的 DeepSeek 系列），同样容量能缓存更多 token。所以缓存命中率、所需带宽这些结论都和模型结构挂钩。
  • 硬件。对比双方用的机器类型和数量相同（4 对 4、20 对 20），这一点是对齐的。但测试集群的节点间带宽高达 800 Gbps，属于高配网络。会议版的实验表明，总带宽低于 100 Gbps 时，Mooncake 的 TTFT 会明显变差（第 10 节）。在普通以太网的集群上，这些收益不能直接照搬。
  • 基线。arXiv 版的 vLLM 没有写版本，也没有说明是否开启前缀缓存和 chunked prefill；在模拟数据实验中，vLLM 还被设置成逐个处理请求。因此“比 vLLM 快”主要衡量的是“分离 + 全局缓存”相对于“耦合 + 无跨实例缓存”的差距，而不是相对于当时最强方案的差距。同期的 DistServe、Splitwise、Sarathi-Serve 和 SGLang 都没有出现在对比里。会议版补充了开启前缀缓存或 chunked prefill 的 vLLM v0.5.1 作为基线，结论方向不变。
  • 指标。8.2 和 8.3 用的是相对 SLO（最低负载时延迟的 10 倍和 5 倍）和 P90，并在稀疏的请求速率测点上比较，所以百分比有明显的“台阶”：525% 对应的是 1.25 req/s 对 0.2 req/s。8.4 用固定 SLO，报告的是同一负载下达标请求的比例之比。几组数字的定义不同，不能直接互相比较。
  • 各个部件的贡献。arXiv 版没有消融实验把 PD 分离、全局缓存、分块流水线并行、逐层 prefill 的贡献分开；只有图 8 单独比较了调度策略。会议版增加了“全局缓存 vs 本机缓存”的对比。
  • 没有公开的。Kimi 的模型和线上 SLO、集群规模（会议版只说“数千个节点”）、流水线组的节点数和分块大小、复制阈值、各个预测器的误差、成本和功耗。期刊版后来透露，线上的缓存命中率最高约 50%，后来在高峰期跌到 20% 以下；他们引入分层存储和按语义淘汰之后，离线分析显示命中率可以从 27% 提高到 52%（第 10 节）。

9 相关工作、未来方向与结论

这一节要回答的问题：Mooncake 和同期的 PD 分离、前缀缓存、分层 KV 存储工作是什么关系？作者认为接下来还能沿着“分离”这条路走多远？

相关工作。作者把已有工作分成几类。一是生产级推理系统，如 FasterTransformer、TensorRT-LLM、DeepSpeed Inference，主要靠优化计算提高吞吐。二是调度与内存管理：Orca 提出迭代级调度，vLLM 提出动态的 KV 缓存管理，FlexGen、SARATHI、FastServe 则用调度和换出策略在有限硬件上分摊负载。作者特别致谢 vLLM 的开源社区，Mooncake 的设计在很大程度上建立在 vLLM 之上。

三是 PD 分离。作者说，Splitwise 的 arXiv 版发表时，Mooncake 还处在早期开发阶段，这篇论文进一步推动了他们的工作；DistServe（为两个阶段分别优化资源分配和并行策略，最大化每张 GPU 的 goodput）和 TetriInfer（把 chunked prefill 与两阶段分离结合，并用预测式的两阶段调度）是同期的工作，结论互相印证。PD 分离的来龙去脉见 DistServe 精读 和 PD 分离拆解页。

四是前缀缓存。Prompt Cache 预先计算并存储常用文本的 KV 缓存；SGLang 的 RadixAttention 用基数树加 LRU 自动发现各种复用模式。与 Mooncake 最接近的是同期的 AttentionStore（后来以 CachedAttention 为名发表在 USENIX ATC 2024），它用更便宜的内存和存储介质为所有请求分层保存 KV 缓存，与 Mooncake 有很多相同的设计选择。作者强调的区别是：长上下文推理中 KV 缓存极大，需要大容量、高效传输，以及以 KV 缓存为中心的全局调度；Mooncake 不是一个独立的缓存服务，而是把节省内存的缓存存储和缓存感知的调度结合在一起。

作者还提到，Preble 等工作开始研究“提示词的调度”，本质上也是以 KV 缓存为中心的调度，Mooncake 印证了其中的很多结论。但他们发现，线上 trace 里真实的可复用比例比开源基准测出来的小得多：即使假设存储容量和 TTFT 的 SLO 都是无限的，当前负载里最多也只有 55% 的 KV 缓存可以复用。这个比例高度依赖应用场景，在某些场景下（例如他们的论文对话服务 papers.cool）可以高达 90%。作者最后再次强调，需要的是受 SLO 约束、面向过载的调度，而不只是追求吞吐的调度。

未来方向。作者认为，把推理服务的不同部分拆到专门的资源池，是 Mooncake 资源利用率高的关键，并打算沿这条路继续走：

  • 异构加速器。旗舰 GPU 要在算力、显存带宽、显存容量之间兼顾，每一项都不是最优。如果只看“每美元的带宽”或“每瓦的带宽”，GDDR 甚至 LPDDR 方案可能比旗舰加速器好一个数量级。作者也看好存内计算（PIM）和混合键合（hybrid bonding）等技术做成的“高带宽、大容量”的存储型器件，它们正适合 decode 阶段那些受带宽限制的运算。
  • 把注意力单独拆出去。在同时有“算力型”和“带宽型”加速器的环境里，可以把 decode 阶段的注意力和其他线性层分开放（见下框）。作者引用了自己的初步模拟结果（attention offloading），认为这种架构能大幅提高总吞吐；他们也指出，DeepSeek-V2 提出的 MLA 直接提高了注意力的算术强度，是从另一个方向解决同一个问题。
  • 缩小 KV 缓存。压缩 KV、按重要性挑选 token、跨层共享 KV、用不需要 KV 缓存的混合架构等方法，都能同时帮到 Mooncake 的两个方面：批可以开得更大，缓存命中率也更高。
  • 调度。支持不同优先级、不同 TTFT/TBT SLO 的请求；针对部分命中和过期的缓存设计专门的复制、迁移和淘汰策略；动态平衡 prefill 和 decode 实例的数量；在负载低谷时用空闲资源跑批处理任务。
先补一点背景：为什么 decode 阶段的注意力“组批也救不了”。

算术强度是“每从显存读 1 个字节做多少次浮点运算”。线性层的权重被批里所有请求共用：批越大，读一次权重能做的运算越多，算术强度随批大小增长。注意力不同：每个请求读的是它自己的 KV 缓存，批里多一个请求，只是多读一份 KV、多做一份对应的运算，比值不变。在一份 KV 上能做多少运算，只取决于有几个 query 头共用同一个 KV 头，也就是“query 头数 ÷ KV 头数”。LLaMA2-70B 是 64 ÷ 8 = 8，量级上只有每字节几次运算，远低于 A800 的平衡点（约 312 TFLOPS ÷ 2 TB/s ≈ 150 次/字节，推算），所以注意力一定受带宽限制。MLA 让所有头共享同一份压缩后的潜在向量（见 DeepSeek-V3 精读 §2.1.1），读一份数据可以服务全部头，算术强度因此大幅提高。

结论。论文的总结很简短：Mooncake 是一个以 KV 缓存为中心的分离式推理服务架构，特别针对长上下文和过载场景；论文讨论了在“最大化有效吞吐”和“满足延迟 SLO”之间取得平衡所涉及的必要性、挑战和设计选择。

10.2 “用存储换计算”的一笔账

会议版新增了一段分析，回答一个根本问题：从别处搬来 KV 缓存，到底什么时候比在本地重算更快？已有的前缀缓存方案大多只把缓存放在本机的显存和内存里，默认全局调度需要的传输带宽高得不现实。会议版的分析是这样的。设模型有 \(l\) 层、隐藏维度 \(d\)，输入长 \(n\)，prefill 的浮点运算量近似为

$$\mathrm{flops}(n)=l\times\left(a\,n^{2}d+b\,n\,d^{2}\right)$$

其中第一项是注意力（随 \(n^2\) 增长），第二项是线性层（随 \(n\) 增长），\(a\)、\(b\) 是常数（会议版取 4 和 22）。如果新请求长 \(n\) 的输入里，前 \(p\) 个 token 能命中缓存，就能省下约 \(l\times(a\,p^{2}d+b\,p\,d^{2})\) 次运算；代价是把这 \(p\) 个 token 的 KV 缓存搬进显存，共 \(p\times l\times(2d/gqa)\times s\) 字节，其中 \(gqa\) 是 query 头数与 KV 头数之比，\(s\) 是每个数的字节数。设 GPU 的平均计算速度为 \(G\)，KV 缓存的平均载入带宽为 \(B\)（取主机到显存带宽和网卡带宽二者中较小的那个），那么“搬比算快”的条件是：

$$\frac{B}{G}>\frac{2\,d\,s}{gqa\times\left(a\,p\,d+b\,d^{2}\right)}$$

会议版按 LLaMA3-70B（\(l=80\)、\(d=8192\)、\(gqa=8\)、BF16 即 \(s=2\)）和 8 卡 A800（\(G=8\times312\) TFLOPS）代入，取 \(p=8192\)，得到所需的最低带宽 \(B\) 约为 6 GB/s；换成 8 卡 H800，算力更强，要求提高到约 19 GB/s。本站按同样的参数验算：右边约为 \(2.35\times10^{-6}\)，乘以 \(G\approx2.5\times10^{15}\) 得约 5.9 GB/s；把 \(G\) 换成 \(8\times989\) TFLOPS（H800 的 BF16 稠密峰值）得约 18.6 GB/s，与原文一致（推算）。

这个不等式说明了两件事。第一，\(d\) 越大（模型越大），右边越小，条件越容易满足，所以“用存储换计算”对大模型更划算。第二，前缀 \(p\) 越长，右边也越小，因为省下的注意力计算随 \(p^2\) 增长，而要搬的数据只随 \(p\) 线性增长。现实中传输不能和计算完美重叠，实际需要的带宽还要更高；会议版的结论是，每台 A800 服务器有一张被充分利用的 100 Gbps 网卡（约 12.5 GB/s）就足以满足。

10.3 Mooncake Store 与传输引擎

arXiv 版只用一句话提到的“分布式 KV 缓存池”，在会议版里有了名字：Mooncake Store。它的要点如下：

  • 存储方式。所有 KV 缓存都以分页块的形式存在分布式缓存池里。块的大小（每块多少 token）由模型大小和网络传输的最佳粒度决定，通常在 16 到 512 之间。每个块的哈希键同样包含前缀信息，用于去重；同一个键可以在不同节点上有多个副本，以降低热门缓存的访问延迟，副本数由 §6.2 的缓存均衡策略控制。缓存池满了，就用 LRU 淘汰一个块，除非它正被某个进行中的请求使用。
  • 接口。上层是面向对象的接口，如 put、get、change_replica，Conductor 可以借此调整每个块的副本数，以聚合更多带宽。下层是一组同步的批量传输接口：先登记要用的内存区域，再分配一个批次、提交一批传输请求、查询每个请求的状态，最后释放批次。显存和 CPU 内存都可以作为传输的源和目标；内存区域事先登记过时，会在合适的情况下直接用 GPUDirect RDMA。
  • 为什么要自己写传输引擎。测试用的是标准 HGX 服务器：每张 A800 配一张 100/200 Gbps 网卡，每张 H800 配一张 200/400 Gbps 网卡，总带宽已与内存带宽相当。作者说，除 NCCL 之外的现有库都跑不满这么高的带宽；而 NCCL 是为集合通信设计的，无法优雅地应对节点或网卡的增减，也不支持 CPU 内存到 CPU 内存的传输路径。

传输引擎有三个目标：把传输任务分散到多张 RDMA 网卡上；对上层隐藏 RDMA 连接管理的复杂性；妥善处理暂时的网络故障。对应的三项设计是：

示意图：按拓扑选择网卡，再把一次传输切片分散到多张网卡上
怎么看：每台服务器有两个 CPU 插槽，各自挂着一个 PCIe 交换机，交换机下面是网卡（mlx5_x）和 GPU（cuda:x）。数据如果从 CPU 0 的内存出发、却走挂在 CPU 1 一侧的网卡，就要穿过跨 CPU 的互联和另一个 PCIe 交换机，带宽受限。传输引擎按“拓扑矩阵”为每块内存挑选同侧的首选网卡，两端各自挑好之后建立连接。本站示意图，对应会议版图 4。
  • 拓扑感知的路径选择。一台推理服务器通常有多个 CPU 插槽、多块内存、多张 GPU 和多张 RDMA 网卡。从技术上说，任何一张网卡都能把本机任何一块内存的数据发出去，但如果路径要穿过跨 CPU 的互联（UPI）或别的 PCIe 交换机，就会被那里的带宽卡住。所以每台服务器在开始服务前生成一个拓扑矩阵并广播给整个集群：对每一类内存（例如 cpu:0、cuda:0），列出“首选”和“次选”网卡。正常情况下只用首选网卡，即同一个 NUMA 节点上的网卡，或者与 GPU 挂在同一个 PCIe 交换机下、可以做 GPUDirect RDMA 的网卡；出故障时才动用次选网卡。会议版的例子是：要把本地 cpu:0 上的 buffer 0 传到远端 cpu:1 上的 buffer 1，本地选 cpu:0 的首选网卡 mlx5_1，远端选 cpu:1 的首选网卡 mlx5_3，然后建立 mlx5_1 到 mlx5_3 的 RDMA 连接。为了进一步用满带宽，一次传输在内部被切成 16 KB 的片，不同的片可以走不同的路径。
  • 连接管理。一对“本地网卡、远端网卡”之间的连接用一对端点表示，每个端点包含一个或多个 RDMA 队列对。连接按需建立，第一次有请求时才配对。为了防止端点太多拖慢处理，传输引擎用端点池限制活跃连接的上限，并用 SIEVE 算法决定淘汰哪个端点。连接因链路错误失效时，两端都把它从池里移除，下次传输时再重建。
  • 故障处理。多网卡环境里常见的故障是某一张网卡暂时不可用，而两台机器之间还有别的路可走。传输引擎发现某条连接不可用时，会自动找另一条可达的路径，把请求重新提交到另一张网卡；它也能发现 RDMA 上下文、完成队列等资源的问题，在问题解决之前暂时避开它们。

传输速度。会议版用并发度 64、最小传输粒度 128 KB，把传输引擎和 PyTorch 的 torch.distributed（Gloo 后端）以及普通 TCP 传输比较。传输 40 GB 数据（相当于 LLaMA3-70B 一个 128k token 请求的 KV 缓存）时，传输引擎在 4 × 200 Gbps 和 8 × 400 Gbps 两种网络配置下分别达到 87 GB/s 和 190 GB/s，约为 TCP 的 2.4 倍和 4.6 倍。按网卡的标称总带宽（100 GB/s 和 400 GB/s）算，利用率分别约 87% 和 48%（推算）。作者说，这个传输引擎是一个独立的基础工具，月之暗面的检查点传输服务也在用它。

10.4 会议版的新实验与新数字

设置。每个节点 8 张 A800-SXM4-80GB，加 4 张 200 Gbps 的 RDMA 网卡；Mooncake Store 的块大小设为 256 token；替身模型换成 LLaMA3-70B 的结构。基线是 vLLM v0.5.1 的三种用法：普通、开启前缀缓存、开启 chunked prefill；每个系统都用 16 个节点。指标也换了：每个请求的 TBT 定义为它最长的 10% 个 token 间隔的平均值；TTFT 上限 30 秒，TBT 上限按场景取 100、200、300 毫秒（论文称阈值 I、II、III）；两项都达标的请求叫“有效请求”，有效请求占全部请求的比例叫“有效请求容量”。

主要结果。

  • 对话负载（会议版图 1）：按图中标注的位置，在三个 TBT 阈值处分别是 +498%（100 ms）、+157%（200 ms）、+59%（300 ms），正文没有逐一说明每个百分比相对的是哪条 vLLM 曲线；摘要据此写作“有效请求容量提高 59%–498%”。正文解释说，这类负载输入长短不一、输出较长，vLLM 的长 prefill 让 TBT 剧烈波动；chunked prefill 能减少干扰，但很难同时兼顾 prefill 的 MFU 和 decode 的 TBT。阈值越严，Mooncake 的优势越大。
  • 工具与智能体负载：前缀复用比例高、输出短，对 vLLM 相对有利。在 200 ms 阈值下，Mooncake 比开启前缀缓存的 vLLM 多 42%，靠的是全局缓存池更大的容量和跨节点的缓存迁移。
  • 合成负载：平均输入最长、缓存热点分散。Mooncake 处理的大多数请求 TBT 在 100 ms 以内，而 vLLM 约有 20% 的请求超过 300 ms；在 200 ms 阈值下，Mooncake 比 vLLM 多 40%。
  • prefill 的 GPU 时间：与 vLLM 相比，Mooncake 在三种负载上分别减少 36%、53%、64%。开启前缀缓存的 vLLM（缓存只在本机显存）在对话和工具负载上的 prefill GPU 时间是 Mooncake 的 1.43 倍和 1.40 倍，在热点分散的合成负载上与普通 vLLM 几乎一样，是 Mooncake 的 2.59 倍；开启 chunked prefill 的 vLLM 牺牲了 prefill 效率，是 Mooncake 的 1.90、2.68、3.33 倍。
  • 全局缓存 vs 本机缓存：LLaMA3-70B 每 token 的 KV 缓存为 320 KB，即使每台机器留出约 1 TB 内存，也只能存约 300 万 token；在大多数负载下，这只能达到理论最高命中率的不到一半，而要接近理论上限需要约 5,000 万 token 的容量，相当于至少 20 个节点的内存。在 10 个 prefill 节点、所有请求只输出 1 个 token（排除 decode 的影响）的实验中，全局缓存的命中率最多是本机缓存的 2.36 倍，prefill 计算时间最多减少 48%。
  • 带宽需求：把网络带宽从 24 Gbps 模拟到 400 Gbps，总带宽超过 100 Gbps 时，合成负载的平均 TTFT 保持在 2 秒以下，远低于全部重算的基线；低于 100 Gbps 时，TTFT 急剧上升，实际传输时间明显偏离理论值，说明网络发生了拥塞。作者因此建议至少 100 Gbps。
  • 延迟分解：输入 128k、前缀缓存比例 95% 时，前缀缓存让 prefill 时间减少 92%；算上调度、传输、载入等额外开销，TTFT 仍减少 86%。
  • P/D 比例：16 个节点、合成负载、TTFT 10 秒与 TBT 100 ms 的阈值下，prefill 与 decode 节点数约 1:1 时有效请求容量最高。会议版说线上流量的统计特征通常是稳定的，所以他们固定这个比例、持续监控，只在负载大幅波动时才切换节点的角色。
  • 生产统计：Mooncake 运行在数千个节点上，每天处理超过 1,000 亿 token；按历史统计，与此前基于 vLLM 的系统相比，Kimi 在 A800 和 H800 集群上分别能多处理 115% 和 107% 的请求。
读的时候要注意：会议版的“有效请求容量”是在固定负载下的达标比例，和本页 8.2、8.3 讲的 arXiv 版“扫描请求速率找上限”的吞吐不是同一种量；+498% 这类大数字出现在最严的 TBT 阈值下，这时 vLLM 只有很少一部分请求达标，任何比例都会被放大。“115% / 107%”是生产历史统计，比较的“此前的系统”具体是什么配置、在什么时间段统计，论文都没有说明。

10.5 期刊版：生产中的教训与开源集成

期刊版保留了会议版的全部内容，把 arXiv 版的过载调度（提前拒绝与基于预测的提前拒绝）放回来，并新增了两部分：在生产中摸索出来的实现经验，以及开源后与主流推理框架的集成。过载实验的结果与 arXiv 版表 3 相同（4,183 / 3,771 / 3,589），期刊版写明这组实验用的是工具与智能体负载，这也印证了第 4 节的判断：arXiv 版公开的 trace 就是这份负载。

动态 P/D 比例。线上 prefill 和 decode 集群的相对负载有明显的周期：白天以长文档分析和检索增强的请求为主，压力在 prefill；晚上以手机上的短对话为主，瓶颈转到 decode。最初的固定比例造成了可预见的失衡；模型频繁升级，每个新版本的延迟和回答长度都不同，手工调比例既不准又费事。于是他们实现了一个自动控制器，定期采样两边的负载，计算失衡系数

$$r=\frac{L_{\mathrm{decode}}+1}{L_{\mathrm{prefill}}+1}$$

其中两个 \(L\) 是去掉最高和最低 10% 样本之后的平均负载。\(r\gg1\) 说明 decode 过载、应该加 decode 副本，\(r\ll1\) 则应该加 prefill 副本。由于线上流量偏斜得厉害，直接把 \(r\) 拉到 1 会引起振荡，所以控制器顺着机器资源的“潮汐”逐步调整：高峰期加机器时先加给更忙的一边，低谷期减机器时先从更闲的一边减，每次调整的幅度都有上限。

灵活的 KV 缓存存储。最初每个节点给缓存池划 1 TB 内存。一小时的离线回放显示，几乎所有共享前缀的请求都从全局共享中受益，线上命中率最高达到 50%；但随着时间推移，高峰期的命中率跌到 20% 以下。分析发现两个原因：一是推理优化让每个节点能服务的请求越来越多，一个时间窗口内需要保留的 KV 缓存超过了原来的内存预算，引发大规模淘汰；二是新功能让缓存需求变得不均匀，例如联网搜索取回的参考内容通常只用一次，而“上下文缓存”要求用户指定的内容在一段时间内一直可用，统一的 LRU 分不清两者，过早淘汰了高价值的缓存。对策是两条：按访问频率把 KV 缓存分层存放在显存、内存和 SSD 上（SSD 只在高峰期或存放长期的上下文缓存时使用，并根据请求队列提前预取）；把 LRU 换成按语义的淘汰策略，像联网搜索结果这样的一次性内容不进缓存池，上下文缓存则强保留，最坏情况下转存到 SSD 而不是删除。在约 70 万个用户会话的离线分析中，基线 LRU 的命中率是 27%；过滤掉标记为一次性的请求（约 62%）只带来小幅提升；再加上分层存储并保证上下文缓存（约 8% 的请求）不被淘汰，命中率升到 52%，相对提升 93%。

无状态的 Conductor。早期的 Conductor 在自己内存里保存整个集群的 KV 缓存元数据，一旦它故障或滚动重启，所有缓存信息都会丢失；滚动升级时，新启动的 Conductor 还会误以为所有块都空闲，覆盖掉正在 prefill 或 decode 中使用的块。后来的设计把元数据下放到各推理节点：由节点负责分配块、加锁防止并发修改、提交更新；Conductor 只保留一份“影子”副本用于缓存感知调度。一个请求的流程变成：Conductor 用影子元数据做前缀匹配并选定 prefill 节点，向它发出分配事务（TxAllocate），节点检查容量、分配并锁住相关的块；decode 节点返回第一个 token、说明 KV 已经传完时，Conductor 再发出提交事务（TxCommit）。这样新旧两个 Conductor 可以同时处理请求，安全地滚动升级；节点上的块锁保证两个 Conductor 不会同时修改同一个块，短暂的元数据不一致最多导致选到次优的节点。

开源集成。期刊版说，在集成 Mooncake 之前，vLLM 的多节点 PD 分离依赖 PyNCCL（NCCL 的 Python 绑定），性能差、故障域大，因为 NCCL 的集合通信模式不适合点对点传输；vLLM 和 SGLang 的前缀缓存也都只在本机显存里，无法跨实例共享。开源的 Mooncake 以传输引擎为核心，把 RDMA、NVLink、TCP、NVMe-oF 等协议统一在同一套传输接口之下（RDMA 一类还支持阿里云的 eRDMA），在它之上有用于点对点共享的 P2P Store 和面向推理的分布式缓存池 Mooncake Store。集成方式有两组选择：GPU 直接互传（GPUDirect RDMA，延迟低但占显存）或经 CPU 内存中转（容量大、更便宜但延迟高）；“KV 传输”（按需在设备之间搬）或“KV 存储”（放进集中管理的分布式缓存池）。期刊版给出的几组开源测试结果规模都较小：在 SGLang 中，两台 A10 上 1P1D 的 TBT 为 7.23 毫秒，比两台不分离的实例（10.30 毫秒）低约 30%，总吞吐相当；在 H20 上 4P2D 对比不分离的部署，每秒 8 个请求时 TTFT 从 9,629 毫秒降到 1,969 毫秒；在 vLLM 中用 Qwen2.5-7B 的量化版在 A10 上测试，以 Mooncake Store 替代 Redis 作为 KV 存储后端，TTFT 降低 17%–22%（TCP 传输）或 26%–33%（RDMA 传输）。

后来怎么样了

Mooncake 发表之后，影响主要体现在两条线上：一是 PD 分离从论文提议变成了大规模推理服务的常规做法，二是它开源的传输引擎和缓存池成了许多推理框架的公共组件。下面只列能查证的事实；标“据仓库记录”的条目来自 Mooncake 仓库的更新日志（项目方自述），其余条目核对过第三方的文档或博客。

开源组件被主流框架采用

  • 公开 trace：2024-07-09 以 JSONL 文件公开 arXiv 版的 trace；2025-02-21 公开会议版用的三份 trace（据仓库记录，文件均已在仓库中核对）。
  • 传输引擎：2024-11-28 开源，附带 P2P Store 和 vLLM 集成的演示；2024-12-16 vLLM 正式支持用它做分离式 prefill 的 KV 传输；2025-12，它作为 KV 连接器直接集成进 vLLM v1（以上据仓库记录）。vLLM 文档对 MooncakeConnector 的说明是：由 prefill 端把 KV 缓存发给 decode 端，默认走 RDMA（vLLM 文档）。
  • SGLang：据仓库记录，2025-04 起 SGLang 支持以 Mooncake 传输引擎做 PD 分离的 KV 传输；SGLang 文档写明目前支持的传输引擎是 Mooncake 和 NIXL（SGLang 文档）。2025-09，SGLang 的分层 KV 缓存（HiCache）把 Mooncake 列为存储后端之一，与 3FS、NIXL 和本地文件后端并列（LMSYS 博客）。
  • Mooncake Store：2025-03-07 开源（据仓库记录）。2025-04，LMCache 增加了以 Mooncake Store 为远端后端的连接器，由腾讯的工程师与 LMCache 团队合作贡献（LMCache 博客）。
  • NIXL：NVIDIA 的推理传输库 NIXL 提供基于 Mooncake 传输引擎的后端插件，README 标注为预览版（NIXL 仓库）。
  • 更多框架（据仓库记录）：LMDeploy（2025-06 起支持 PD 分离后端）、vLLM-Ascend、TensorRT-LLM（2025-12）等相继接入；2026-02，Mooncake 加入 PyTorch 生态（PyTorch 博客）。用途也从 KV 缓存扩展到模型权重和强化学习中的数据搬运：P2P Store 的正式版以 checkpoint-engine 为名开源，仓库记录称它在约 20 秒内把 1 万亿参数的 Kimi K2 权重更新到数千张 GPU 上。

大规模部署

  • 2025-07-20，Mooncake 团队在 LMSYS 博客上发布了用 SGLang 在 128 张 H200 上部署 Kimi K2（1 万亿总参数）的结果：4 个 prefill 节点、12 个 decode 节点，在输入 2,000、输出 100 个 token、decode 批大小 480 的测试下，prefill 吞吐 22.4 万 token/s，decode 吞吐 28.8 万 token/s（LMSYS 博客）。
  • PD 分离本身已成为大规模推理的常规做法：DeepSeek-V3 的线上部署同样把 prefill 和 decode 分开（见 DeepSeek-V3 精读 §3.4）；vLLM、SGLang、TensorRT-LLM、NVIDIA Dynamo 等都提供了分离式部署，整体脉络见 DistServe 精读的“后来怎么样了”。

思路上的延续

  • KV 缓存分层存储：把 KV 缓存当作要分层管理的数据，存放在显存、内存、SSD 乃至远端，是 Mooncake 之后的一条主线，代表工作有 LMCache、SGLang HiCache、Strata 等，见 KV 缓存分层存储拆解页。Mooncake 期刊版里“线上高峰期命中率跌到 20% 以下，离线分析中靠分层存储和按语义淘汰把命中率从 27% 提到 52%”的经历，正说明这件事难在“存什么、存多久”，而不只是“存得下”。
  • 把注意力单独拆出去：论文在未来工作里提出的“注意力与线性层分离”，后来也成了业界讨论的方向；DistServe 作者 2025 年的回顾博客同样把注意力与前馈层的分离列为下一步（见 DistServe 精读）。

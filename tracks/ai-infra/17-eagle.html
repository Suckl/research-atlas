1. 动机：草稿模型从哪来

投机解码的收益取决于两件事：草稿被接受的比例 α 有多高、起草本身有多便宜。经典做法用同族的小模型当草稿，但小模型要单独训练 / 对齐、额外占显存，且对很多模型根本没有合适的小兄弟。Medusa 在目标模型顶上加几个解码头，各自预测第 +1、+2、+3… 个 token，但这些头彼此独立，第 +2 个头不知道第 +1 个头猜了什么，接受率随位置迅速下降。

一句话理解 EAGLE 让草稿头“站在目标模型的肩膀上”：直接读目标模型 LM head 之前的特征，用一个单层 Transformer 在特征层自回归地往前推，再复用目标模型的 LM head 出 token。特征序列比 token 序列规律得多，所以一个很小的头就能猜得很准。EAGLE-2 让草稿树按置信度动态生长；EAGLE-3 去掉特征回归、融合多层特征，并在训练时就模拟多步起草，接受长度随训练数据继续增长。

3. 三代演进

3.1 EAGLE-1：在特征层起草

两个观察：① 特征（LM head 之前的隐状态）序列比 token 序列更规律，回归它比直接预测 token 容易；② 采样带来的不确定性会让“下一位置的特征”有歧义，必须把已采样的 token 一起告诉草稿头。于是草稿头的输入是“特征序列 + 后移一位的 token 序列”，输出下一位置的特征，再借目标模型的 LM head 得到 token。训练用特征回归损失加 token 分类损失，数据是固定数据集上目标模型的前向特征，不需要目标模型重新生成。

3.2 EAGLE-2：动态草稿树

固定形状的草稿树隐含了一个假设：接受率只取决于 token 在树中的位置。EAGLE-2 指出它其实强烈依赖上下文，而草稿头自己的置信度就是接受率的良好近似。于是起草分两步：扩展——每层选累计置信度（路径上置信度之积）最高的 top-k 个节点继续生长；重排——起草结束后，在所有节点里按累计值选出要验证的 top-m 个 token。整个过程不需要额外训练。

3.3 EAGLE-3：训练时测试与数据缩放

作者发现给 EAGLE 加训练数据收益很有限，原因是特征回归这个约束：草稿头被迫复现顶层特征，表达能力被限制。EAGLE-3 做了两件事：

去掉特征预测，直接预测 token

不再要求输出接近目标模型的 h。但这样第 2 步以后的输入（草稿头自己的输出 a）就和第 1 步的输入（融合特征 g）分布不同了——于是需要“训练时测试”：训练时就把多步起草展开，让草稿头学会吃自己的输出。

融合低 / 中 / 高三层特征

不再只用顶层特征，拼接三层后经全连接降维。论文的实验显示：在新架构下，草稿训练数据越多，加速比按比例继续提升（原版 EAGLE 则很快饱和）。

2026-05，vLLM 博客发布了 EAGLE 3.1（EAGLE 团队、vLLM 与 TorchSpec 合作），在 3 的基础上增加若干结构改动 （具体改动来自二手文档：输入归一化、后置归一化的隐状态反馈、MLA 结构的草稿变体等，未逐项核对）。同年的 SpecForge（arXiv 2603.18567）是 SGLang 团队开源的草稿模型训练框架，专门用于训练 EAGLE-3 类草稿头。

3.4 放进推理引擎之后

论文报告的加速比都在 batch = 1 下测得。在线服务里 batch 往往很大，此时 decode 本身已不再严重带宽受限，验证草稿树多出的 token 要实打实地占用算力。EAGLE-3 论文在 SGLang 上（H100，LLaMA-3.1-8B，MT-Bench）测得：EAGLE（第一代）在 batch 24 时已降到 0.93×（比不用还慢），而 EAGLE-3 在 batch 64 时仍有 1.38×。实践中的常见做法：小 batch 用较深 / 较宽的树，batch 变大时缩小草稿数量，超过某个 batch 直接关闭——下面的演示可以感受“接受率 α、草稿长度 γ、草稿成本 c”与加速比的关系。

相关落地：DeepSeek-V3 的 MTP 模块本身就是一个可用作草稿的预测头；Kimi K3 把 MTP 层微调成 EAGLE-3 式草稿模型，融合第 1、第 4 和最后一个 Attention Residuals 块的特征 Kimi K3 报告 §4.1.4。

4. 伪代码

eagle3_draft.py（一次起草 + 验证，简化为链而非树）
def eagle3_round(target, draft, prefix, gamma=6):
    feats, x_next = target.forward_with_layers(prefix)   # 目标模型前向，得到 l, m, h 与下一个 token
    g = draft.fc(cat(feats.low[-1], feats.mid[-1], feats.high[-1]))   # 3k → k
    inp, tok, drafts = g, x_next, []
    for _ in range(gamma):
        a = draft.layer(cat(inp, embed(tok)))             # 单层解码层（带 KV cache）
        tok = sample(target.lm_head(a))                   # 复用冻结的 LM head
        drafts.append(tok)
        inp = a                                           # 后续步骤吃自己的输出（训练时也这样展开）
    accepted = target.verify(prefix + [x_next], drafts)   # 一次前向 + 投机采样接受规则
    return prefix + [x_next] + accepted

6. 简答题

Q34EAGLE 为什么在特征层而不是 token 层起草？EAGLE-3 为什么又放弃了特征回归？

目标模型的顶层特征序列比 token 序列规律得多，一个单层 Transformer 就能较准确地往前推；起草完再借目标模型自己的 LM head 出 token，词表一致、无需额外小模型。为消除采样带来的歧义，EAGLE 把已采样的 token（后移一位）与特征一起输入。EAGLE-3 发现“必须复现顶层特征”这个约束限制了草稿头的表达能力，加数据也提升有限；去掉特征回归、直接预测 token，并融合低 / 中 / 高三层特征后，加速比随训练数据持续增长。

  • 去掉特征回归的副作用：第 2 步以后的输入是草稿头自己的输出，分布与第 1 步不同 → 用“训练时测试”在训练阶段展开多步起草来对齐。
  • 对比 Medusa：多个独立头并行猜 +1、+2…，彼此不知道对方的猜测；EAGLE 是自回归的，每步都条件于前面草稿。
  • EAGLE-2 的动态树与训练无关，可直接套在 EAGLE-1 / 3 的草稿头上。

依据：EAGLE §3；EAGLE-2 §3；EAGLE-3 §3 与 Fig. 1。

Q35投机解码的收益为什么随 batch 增大而下降？在线服务中如何决定是否开启、草稿多长？

投机解码本质是“用闲置算力换延迟”：batch 小时 decode 带宽受限，验证 γ 个草稿 token 与验证 1 个耗时几乎相同，所以多接受的 token 都是净赚。batch 变大后 decode 的算术强度上升、逐渐变成算力受限，验证树里被拒绝的 token 白白消耗算力；同时一批里各请求接受长度不同，进一步摊薄收益。

  • 论文数字：SGLang 上 EAGLE 在 batch 24 已降到 0.93×，EAGLE-3 在 batch 64 仍有 1.38×——草稿越准，可开启的 batch 范围越大。
  • 策略：按当前 batch / 负载动态调草稿长度与树宽（小 batch 深而宽、大 batch 浅或关闭）；高接受率场景（代码、结构化输出、重复上下文）更值得开。
  • 与 PD 分离结合时，投机解码只发生在 decode 池，草稿头的显存与算力也算在 decode 实例上。

依据：EAGLE-3 Tab. 3（SGLang 吞吐）；投机解码原论文的加速比公式（见 投机解码页）。

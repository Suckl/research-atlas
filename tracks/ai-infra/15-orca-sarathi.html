1. 动机：生成式请求的长度事先未知

传统推理服务（如 FasterTransformer + Triton）按请求组批：一批请求一起进入、一起离开。对分类模型这没问题，但生成式模型每个请求要跑很多次前向（每次出一个 token），输出长度各不相同：

  • 先生成完的请求不能提前返回，只能占着位置空转，直到整批里最长的那个结束；
  • 新到的请求必须排队等整批结束，即使 GPU 上明明有空位；
  • 为了避免空转而把 batch 调小，又会让 decode 的算术强度更低（见 推理计算特征）。
一句话理解 Orca 把调度的时间粒度从“一个请求的全部生成”缩短为“一次前向迭代”：每次迭代结束都可以让完成的请求离开、让新请求加入——这就是今天所说的连续批处理（continuous batching）。Sarathi-Serve 进一步发现，新请求的长 prompt 一旦挤进某次迭代，会让这一步变得很长、卡住所有正在 decode 的请求；于是把 prompt 切块，每次迭代只捎带一块。

3. 组件拆解

3.1 selective batching：哪些算子能拼批

迭代级调度带来一个实现难题：同一批里的请求处在不同阶段——有的在 prefill（几百个 token），有的在 decode（1 个 token），各自的 KV 长度也不同，张量形状对不齐，没法像传统批处理那样堆成一个 [B, L, H] 张量。Orca 的解法是只对与序列无关的算子拼批：

线性层、LayerNorm、GeLU 等逐 token 的算子把所有请求的 token 拼成一个 [ΣLᵢ, H] 矩阵一起算——这正是权重读取能被摊薄的地方；注意力按请求拆开分别计算，再合并回去。今天的推理引擎仍沿用这个结构，只是“逐请求注意力”被 PagedAttention / FlashInfer 这类变长注意力内核在一次内核调用里完成。

3.2 Orca 留下的显存问题

Orca 的调度器在接纳一个请求时，按它的最大可能输出长度为其预留 KV 空间（max tokens），以保证中途不会因显存不足而失败。生成往往远短于上限，预留的大部分空间被浪费，这直接限制了 batch 大小。vLLM 论文正是以 Orca 的几种预留策略作为基线，用分页式 KV（按需分配块）解决这个问题——见 vLLM / PagedAttention。

3.3 Sarathi-Serve：chunked prefill 与无停顿调度

连续批处理之后，prefill 与 decode 的干扰成为主要矛盾：prefill 是算力受限的、decode 是带宽受限的，两者混在同一次迭代里，要么为了 decode 的延迟推迟 prefill（拉长 TTFT、降低吞吐），要么为了吞吐让 prefill 插队（造成 generation stall）。Sarathi-Serve 的两个设计：

chunked prefill

把 prompt 切成近似等长的块；第 k 块的 query 关注前 k−1 块已在 KV cache 中的 token 与本块的 token。一个大 prefill 变成若干个中等大小的“混合批”，每个都能把 decode token 一起带上，decode 的算术强度也因此被抬高（在同一个矩阵乘里搭便车）。

无停顿调度（stall-free batching）

每次迭代先纳入全部 decode，再纳入进行中的 prefill 块，最后才接纳新请求，总 token 数受预算约束。迭代时长因此近乎恒定，TBT 尾延迟可控；在流水线并行下，各微批耗时均匀，气泡也随之减小。

块（预算）大小的取舍：块越小，每次迭代越短、TBT 越平稳；但小块的矩阵乘算术强度更低，而且每一块都要重新读一遍之前块的 KV，prefill 的总开销上升、TTFT 变长。所以预算通常按 TBT 的 SLO 来定：SLO 越严，预算越小。PD 分离（DistServe / Mooncake）则走得更远：直接把两个阶段放到不同的 GPU 池上，彻底消除干扰，代价是要在池之间传 KV。

4. 伪代码

stall_free_scheduler.py（迭代级调度 + chunked prefill 的一次迭代）
def schedule_one_iteration(running, prefilling, waiting, token_budget):
    batch, used = [], 0
    for r in running:                         # 1) 所有 decode 请求优先，每个 1 token
        batch.append((r, 1)); used += 1
    for r in prefilling + waiting:            # 2) 进行中的 prefill，再是新请求
        if used >= token_budget: break
        if r in waiting and not kv_blocks_available(r): break
        chunk = min(r.remaining_prompt, token_budget - used)
        batch.append((r, chunk)); used += chunk
    return batch                              # 交给引擎执行一次前向

while True:                                   # Orca 的“迭代级”主循环
    batch = schedule_one_iteration(running, prefilling, waiting, token_budget=512)
    outputs = engine.forward(batch)           # 线性层拼批，注意力按请求
    for r in finished(outputs): reply(r); free_kv(r)   # 完成即返回，不等别人
    update_states(batch, outputs)             # prefill 完成的请求转入 running

预算 512 只是示意值；实际按模型、硬件与 TBT 目标调。

  • Orca：GPT-3 175B 上，与 NVIDIA FasterTransformer 相比，在相同延迟水平下吞吐提升 36.9×。Orca 论文摘要
  • Sarathi-Serve（在尾延迟约束下的服务容量，对比 vLLM）：Mistral-7B 单卡 A100 2.6×；Yi-34B 两卡 A100 最高 3.7×；Falcon-180B 配合流水线并行端到端最高 5.6×。Sarathi-Serve 论文摘要

6. 简答题

Q30Orca 的迭代级调度相比请求级批处理解决了什么问题？为什么还需要 selective batching？

生成式请求的输出长度未知，请求级批处理让整批同进同出：早完成的请求空占槽位，新请求必须等整批里最长的那个结束。迭代级调度把调度粒度降到一次前向迭代，完成即离开、新请求下一步就加入，GPU 槽位始终被有效占用，排队延迟大幅下降（GPT-3 175B 上同延迟吞吐 36.9×）。

  • selective batching 的必要性：同一迭代里各请求处于不同阶段、KV 长度不同，无法堆成规则的 [B, L, H] 张量。Orca 只对逐 token 的算子（线性层、LayerNorm、激活）把 token 展平成 [ΣLᵢ, H] 一起算，注意力按请求拆开。
  • 拼批的收益主要来自线性层：权重只读一次，被所有 token 共享——这是 decode 提高算术强度的唯一途径。
  • 遗留问题：按最大长度预留 KV 浪费显存（→ vLLM 的分页 KV）；整段 prefill 插队造成 decode 停顿（→ chunked prefill / PD 分离）。

依据：Orca（OSDI 2022）§3–4 与摘要；vLLM 论文 §6 的 Orca 基线。

Q31chunked prefill 如何同时改善吞吐与尾延迟？块（token 预算）设大或设小各有什么代价？

它把长 prompt 切块、每次迭代只捎带一块，同时让所有 decode token 搭同一个矩阵乘的便车：一方面消除了整段 prefill 造成的 generation stall（TBT 尾延迟改善），另一方面让 decode 不必为了延迟而缩小 batch 或推迟 prefill（吞吐上升）。迭代时长均匀，在流水线并行下还能减少气泡。

  • 块小：每步短、TBT 稳；但矩阵乘算术强度低，且每块都要重读前面所有块的 KV，prefill 总开销上升、TTFT 变长。
  • 块大：prefill 效率高、TTFT 短；但单步变长，decode 请求的 TBT 抖动增大，退化回 Orca 的停顿问题。
  • 怎么定：按 TBT 的 SLO 反推每步可容忍的时长，再换算成 token 预算；SLO 越严预算越小。若 TTFT 与 TBT 都很严、负载又大，干脆用 PD 分离把两阶段放到不同 GPU 池。

依据：Sarathi-Serve（OSDI 2024）§3–5 与摘要；DistServe §2（prefill-decode 干扰）。

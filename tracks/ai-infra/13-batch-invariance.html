1. 动机：温度 0、同一个 prompt，为什么两次答案不一样

流行的解释是“GPU 并发 + 浮点加法不满足结合律”：线程完成顺序随机 → 归约顺序随机 → 结果随机。Thinking Machines 的文章指出这个解释不完整：LLM 前向里几乎没有原子加（atomic add），同一个内核对同一输入逐次运行是确定的。真正的原因是：

一句话理解 内核对一条请求的计算方式取决于同批里还有多少别的请求——batch 小的时候矩阵乘用 split-K、注意力把 KV 切更多段来填满 SM，归约顺序就变了。服务器的负载决定 batch 大小，用户看到的就是“随机”。修复办法是让每条请求的归约策略与 batch 大小无关：批不变性。

3. 从推理确定性到 RL 的训推一致

3.1 为什么 RL 在乎这个

LLM 的 RL（GRPO / PPO 类）用推理引擎（vLLM / SGLang）采样，用训练引擎（FSDP / Megatron）算梯度。两边同一套参数，但内核不同、精度不同、batch 不同——同一个 token 的概率 π_sampler(y) 与 π_trainer(y) 不相等。Yao 等（TIS 工作）实测两者差异显著，个别 token 甚至预测相反。于是名义上的 on-policy 训练实际是 off-policy：梯度用的是训练器的概率，样本却来自采样器的分布。Thinking Machines 的实验：不做修正时 reward 在训练中途崩溃。

3.2 两种解法

修正法：截断重要性采样（TIS）根治法：逐位一致的采样器与训练器
做法在策略梯度里乘 min(π_trainer(y)/π_sampler(y), C)：把隐式的 off-policy 当作 off-policy 来校正，上限 C 截断防止方差爆炸推理与训练用同一套批不变内核（同样的归约顺序、精度），使 π_sampler ≡ π_trainer，KL 恒为 0
代价有界偏差；需要采样器返回 logprob内核性能损失；两套引擎要共享内核实现
落地VeRL、slime、OAT 已集成；NeurIPS 2025 论文《On the Rollout-Training Mismatch in Modern RL Systems》Thinking Machines 的 Tinker；vLLM 的批不变模式
$$\nabla J \approx \mathbb E_{y\sim\pi_{\text{sampler}}}\Big[\min\Big(\frac{\pi_{\text{trainer}}(y)}{\pi_{\text{sampler}}(y)},\ C\Big)\,\nabla\log\pi_{\text{trainer}}(y)\,A(y)\Big]$$

相关的工程经验：MiniMax-M1 发现 LM head 的精度差异是训推概率不一致的主要来源之一，把 LM head 改为 FP32 后相关性显著改善；MoE 模型里路由的微小差异会让 token 走到不同专家，是另一大来源。

4. 伪代码

batch_invariant_attention_decode.py（固定段长的 split-KV）
def decode_attention(q, K, V, split_len=256):            # 段长固定，段数随序列长度变
    L = K.shape[0]
    parts = []
    for s in range(0, L, split_len):                      # 边界只依赖 L，不依赖 batch
        Ks, Vs = K[s:s+split_len], V[s:s+split_len]
        m = (q @ Ks.T).max(); p = exp(q @ Ks.T - m)
        parts.append((m, p.sum(), p @ Vs))                # (m, ℓ, O) 局部结果
    m_all = max(m for m, _, _ in parts)                   # 固定顺序归并
    l_all = sum(exp(m - m_all) * l for m, l, _ in parts)
    o_all = sum(exp(m - m_all) * o for m, _, o in parts)
    return o_all / l_all
tis_loss.py
def tis_policy_loss(logp_trainer, logp_sampler, advantage, C=2.0):
    ratio = exp(logp_trainer - logp_sampler).detach()      # 训推概率比，不回传
    w = minimum(ratio, C)                                  # 单侧截断：只限制上调
    return -(w * logp_trainer * advantage).mean()

5. 简答题

Q27温度为 0 时，同一个 prompt 为什么仍可能得到不同输出？

内核缺乏批不变性：同一条请求在不同 batch 大小下被分到不同的 tile 配置 / split-K 段数 / 注意力 KV 切段数，浮点归约的顺序随之改变，logits 相差几个 ulp；当两个候选 token 的 logit 极接近时 argmax 翻转，后面的生成全部分叉。服务器负载决定 batch，所以用户看到的是“随机”。

  • 不是“并发 + 原子加”：LLM 前向几乎不用原子加，单个内核逐次运行是确定的；是策略随形状变化导致的“确定但依赖他人”。
  • 三类元凶：RMSNorm（小 batch 拆行归约）、matmul（split-K 与形状相关的 tile 选择）、attention（split-KV 的段数、prefill 与 decode 走不同路径）。
  • 修法：固定归约策略——不拆行、禁 split-K + 单一 tile 配置、固定段长的 split-KV；实验 1000 次采样 80 种 → 1 种，速度损失约 1.6–2×。
  • 其他来源（非本文重点）：MoE 路由在 batch 间的微小差异、投机解码的接受判定、多卡时 all-reduce 的顺序。

依据：Thinking Machines《Defeating Nondeterminism in LLM Inference》（2025-09）。

Q28RL 训练中采样器与训练器的概率不一致从何而来？有哪两类处理办法？

来自两者之间的差异，而不能归咎于某一边“错了”：两套引擎各自是确定的（或各自在自己的 batch 规律下变化），但内核实现、精度（FP8/BF16 的矩阵乘、LM head 精度）、归约顺序、MoE 路由都不同，于是 π_sampler ≠ π_trainer。影响在训练端显现——梯度按训练器概率算、样本按采样器分布来，RL 变成隐式 off-policy，可能崩溃。

  • 若一定要说“谁的责任更大”：推理引擎为吞吐做了更激进的优化（FP8 KV、投机解码、与 batch 相关的内核选择、更低精度的 LM head），通常是偏离“参考数值”更多的一方；但训练器用的 FSDP / Megatron 内核也并不是“真值”。
  • 两种对策：① 把差异当 off-policy 校正——TIS 的截断重要性权重（VeRL 等已集成）；② 消除差异——采样器与训练器共用批不变内核，Thinking Machines 实现了采样与训练逐位一致，KL 恒为 0。
  • 排查顺序：先对齐 LM head 与 logprob 计算精度（MiniMax-M1 的经验），再对齐 MoE 路由，再看注意力 / matmul 内核。

依据：Thinking Machines 博客的 RL 实验；Yao et al.《Your Efficient RL Framework Secretly Brings You Off-Policy RL Training》/ NeurIPS 2025《On the Rollout-Training Mismatch in Modern RL Systems》；MiniMax-M1 技术报告。

1. 动机：LLM 应用不是单次调用，而是“程序”

多轮对话、few-shot 提示、思维树搜索、多路采样、Agent 的工具调用——一个应用会向模型发出大量共享前缀的调用，还常要求输出符合 JSON / 正则。2023 年的引擎（含 vLLM）把每次调用当作独立请求：共享的前缀被反复 prefill，结构化输出逐 token 地用掩码约束。SGLang 把“LM 程序”当作一等公民，前端给出表达这些模式的语言，后端运行时为这些模式做三项优化。

一句话理解 RadixAttention：所有请求的 KV 放进一棵以 token 序列为键的基数树里，新请求先在树上找最长公共前缀，只 prefill 剩下的部分；压缩 FSM：正则约束里“只有一种走法”的那段一次跳过去；API 投机执行：对黑盒 API 多生成一点以省一次调用。

3. 另外两项运行时优化与前端

3.1 压缩有限状态机：约束解码一次跳多步

要求输出符合 JSON schema / 正则时，常规做法是每步用 FSM 算出允许的 token 集合并掩码 logits——每一步都只能前进一个 token，哪怕像 {"name": " 这样完全确定的片段也要一步一步生成。SGLang 把正则编译成 FSM 后，把“只有一条出边”的连续状态压缩成一条边：解码到这里时直接把整段字符串追加进去（Jump Forward），再做一次重新分词保证 token 边界自然。JSON 解码吞吐提升约 1.6×；FSM 跨请求复用，否则吞吐低 2.4×。

3.2 API 投机执行

对 OpenAI 这类黑盒 API，一个程序里连续几个 gen（例如抽取三个字段）本来要三次调用。SGLang 让第一次调用多生成几个 token 越过停止条件，后续的 gen 若能匹配上这段输出就直接复用。三字段抽取任务上输入 token 成本降约 3 倍。

3.3 前端语言

嵌入 Python 的原语：gen（可带 regex）、select、extend / +=、fork、join、image、video。编译器 / 解释器把程序翻译成带共享前缀信息的请求流，运行时据此调度。这一层让“程序结构”（哪些调用共享前缀、哪些可以并行）对运行时可见。

sglang_program.py（论文风格示例）
@sgl.function
def multi_branch(s, question):
    s += sgl.system("You are a helpful assistant.")      # 共享前缀 → 树的上层
    s += sgl.user(question)
    forks = s.fork(3)                                     # 三条分支共享到此为止的 KV
    for i, f in enumerate(forks):
        f += sgl.assistant(sgl.gen("ans", max_tokens=128, temperature=0.7))
    s += sgl.assistant(sgl.gen("final", regex=r'\{"best": [0-2]\}'))  # 压缩 FSM 约束

5. 简答题

Q7vLLM 与 SGLang 的设计出发点有何不同？两者前缀缓存的粒度差异从何而来？

同一代、同一批作者圈子（Berkeley / LMSYS）的两个引擎，出发点不同：vLLM 解决显存碎片（PagedAttention），SGLang 解决 LM 程序的前缀复用与结构化输出（RadixAttention + 压缩 FSM + 前端语言）。今天二者在功能上已高度趋同，差异主要在实现细节与默认策略。

维度vLLM（论文时期 → 现在）SGLang（论文时期 → 现在）
核心抽象固定大小 KV 块 + 块表（分页）基数树上的 KV 前缀（每页 1 token）
前缀复用显式共享（并行采样 / beam）→ 自动前缀缓存：整块内容哈希逐 token 基数树匹配 + LRU + 缓存感知调度，天生多级共享
调度FCFS 连续批处理，抢占（swap / recompute）按最长前缀匹配等策略排序（lpm / fcfs / dfs-weight…），CPU 调度与 GPU 执行重叠的“零开销”调度器（后期版本）
结构化输出后来集成 outlines / xgrammar 等后端压缩 FSM 跳跃解码（论文原创），后来也接入 xgrammar
前端OpenAI 兼容 API 为主OpenAI 兼容 API + SGLang DSL（gen / select / fork）
注意力后端FlashAttention、FlashInfer、Triton 等可选FlashInfer（早期默认）、FA3、Triton 等可选
论文数字vs Orca / FasterTransformer 吞吐 2–4×vs vLLM / Guidance / LMQL 吞吐最高 6.4×（基于早期 vLLM）
后续共同演进都支持投机解码（EAGLE / MTP）、PD 分离（NIXL / Mooncake 传输后端）、DeepSeek 的 MLA / DSA、FP8 / INT4 量化、多模态、DP 注意力 + EP 等；RadixAttention 思想进入 vLLM，PagedAttention 的分页布局被 SGLang 借 FlashInfer 的块稀疏抽象统一

一句话概括：vLLM 的论文是关于“存”（怎么不浪费显存），SGLang 的论文是关于“算”（怎么不重复计算、怎么少走解码步）；工程上今天选哪个更多看具体模型 / 硬件的支持成熟度与基准测试。
